# etcd-io/etcd#20893: `--force-new-cluster` can't remove learners after creating a snapshot

- URL: https://github.com/etcd-io/etcd/issues/20893 (closed 2025-11-06; labels `type/bug`,
  `release/v3.4`–`v3.6`)
- Affected: 3.4, 3.5, 3.6 and `main` before the fix. Reproduction: a 3-member cluster with
  `--snapshot-count=2`, add a learner, write a few keys (so that a snapshot holds the learner),
  stop everything, then restart one member with `--force-new-cluster`. `member list` still shows
  the learner.
- Fix: PR #20894 (merge `c58e6f1ca`, 2025-11-06; backports #20896–#20898).
  `storage.GetEffectiveNodeIDsFromWALEntries` also collects `snap.Metadata.ConfState.Learners`.
  Before, it collected only `Voters`.

What goes wrong (pre-fix). With `--force-new-cluster`, the bootstrap
(`bootstrapWALFromSnapshot` → `bootstrappedWAL.NewConfigChangeEntries`) computes the member set
from the snapshot's `ConfState` and the WAL's conf entries, and appends `RemoveNode` entries for
everyone but itself (`storage.CreateConfigChangeEnts`). A learner added before the snapshot
appears only in `ConfState.Learners`. That field was ignored, so no `RemoveNode` was generated for
it and the forced single-member cluster kept it.

## Classification

**F (fixed before the verified code); counterfactual F− (O-fn).** The fix `c58e6f1ca` is an
ancestor of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes). At the pin the loop
over `GetLearners()` is present (`server/storage/util.go:121-123`). Both functions involved are
names-only in this repository: `Code/go_etcd_io/etcd/server/v3/storage.toml` translates only the
backend hooks, and `server/storage/util.go` has no translated function. The bootstrap that calls
them is not translated either (`verified.txt`). No spec constrains them, so the buggy version
would have gone through as well.

## The code path (at the pin)

Source: `verified.txt` and `Code/.../storage.toml`.

| Go function | State |
|---|---|
| `etcdserver.bootstrap` → `bootstrapWALFromSnapshot` (`ForceNewCluster`) | not translated |
| `bootstrappedWAL.NewConfigChangeEntries`, `AppendAndCommitEntries` | not translated |
| `storage.GetEffectiveNodeIDsFromWALEntries`, `storage.CreateConfigChangeEnts` (the bug) | names only |
| `EtcdServer.applyConfChange` (applies the forced `RemoveNode`s) | assumed (axiom) |
| raft `confchange` (the configuration the entries produce) | verified (`Spec/go_etcd_io/raft/v3/confchange/`) |

## The counterfactual (step 5)

No statement mentions these functions, so nothing could fail on the pre-fix code: **F−**. The
property that would have caught it is the one the forced bootstrap exists for: *after the
snapshot and the generated entries, the configuration is `{self}`*. Raft already has the pure
model to state it: the configuration after a `ConfState` and a sequence of `ConfChange` entries
(`confchange`'s `applyM`/`simpleM`, and `RawNode.ApplyConfChange`'s dynamic mode). Two side notes
for such a spec. The fixed function still ignores `ConfState.VotersOutgoing` and
`EntryConfChangeV2` entries (`if e.GetType() != raftpb.EntryConfChange { continue }`). That is
harmless today only because etcd never proposes joint or V2 changes, a fact the spec would need
as a premise. The bug was also only visible through `member list`: membership comes from the
backend, while raft's view comes from `ConfState`. The two disagreed, which is the subject of
the existing proposal `membership-read-barrier`.

## Proposal

Slug **`verify-force-new-cluster`**. Translate `server/storage/util.go`'s
`GetEffectiveNodeIDsFromWALEntries` and `CreateConfigChangeEnts` (~110 lines, pure apart from
`pbutil`'s marshal and unmarshal, which are already trust-boundary specs). Spec: for a snapshot
`ConfState cs` and entries whose conf changes are V1 and non-joint (`cs.VotersOutgoing = []`),
the returned IDs are the voters and learners of the configuration that raft's
`applyM`-fold of the entries gives from `cs`. The generated entries, folded the same way, give
the configuration `{self}`. Cost: small to medium (a pure fold over raft's existing model).
Wiring it into the bootstrap needs `bootstrapWALFromSnapshot` translated (medium, together with
the WAL as a trust boundary).
