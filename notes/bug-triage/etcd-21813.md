# etcd-io/etcd#21813: grpcproxy: new watchers may be added to a disconnected watchBroadcast and miss all subsequent events

- URL: https://github.com/etcd-io/etcd/issues/21813 (open, filed 2026-05-26; labels `type/bug`,
  `gRPC-proxy`). Reported on v3.5.4; the code is unchanged on `main`.
- Fix: none merged. PR #21814 (open) adds a `stopped` flag to `watchBroadcast`, guards `add` and
  `coalesce` with it, and re-attaches a dead broadcast's watchers. The thread turned into a
  discussion of deprecating the proxy or moving it to its own repository.

What goes wrong (at the pin, `server/proxy/grpcproxy/`): `newWatchBroadcast`'s goroutine
(`watch_broadcast.go:55-76`) runs `for wr := range wch { wb.bcast(wr); update(wb) }` and then
only closes `donec`. The broadcast stays in `watchBroadcasts.bcasts`. `watchBroadcast.add`
(`:97-122`) and `watchBroadcasts.coalesce` (`watch_broadcasts.go:53-80`) check `nextrev` and
`responses` only, so they keep putting watchers into it, and those watchers never get another
event. It is worse than the report says. When the client's watch stream ends with an error, the
verified client sends a last `WatchResponse{Header: {}, Canceled: true, closeErr}` before it closes
the channel (`client/v3/watch.go:494-495`, `closeSubstream`). `bcast` then sets
`wb.nextrev = wr.Header.Revision + 1 = 1` (`watch_broadcast.go:83-84`). With `nextrev = 1` and
`responses > 0`, the dead broadcast accepts every new watcher with `nextrev ≥ 1`. `coalesce` also qualifies
it as a target for every live broadcast of the same range that has fewer than 5 receivers
(`wb.nextrev >= wbswb.nextrev && wbswb.responses > 0`). On that broadcast's next update, its
receivers move into the dead broadcast whenever the map iteration reaches the dead one first. Neither
the final `Canceled` response nor the channel's close reaches the proxy's clients:
`watcher.send` drops a response that has no events, no `Created` flag and no `CompactRevision`
(`watcher.go:106-108`). This is the mechanism of etcd#18231 and of the "both watchers hang" in
etcd#19296.

## Classification

**O-pkg** (O-path in kind). The buggy code is in `server/proxy/grpcproxy`, which this repository
does not translate: no `Code/` module, and no function of it is in the inventory
(`/shared/etcd-grove-triage/coord/verified.txt`, 0 `proxy` rows). The one verified function on the
path is the backend watch, `clientv3.watcher.Watch` (verified, sorry-free). Its contract is the
reason the proxy is wrong, not something the bug breaks. The returned SPSC channel's elements
satisfy `rangeWatchElem` and the channel "may be closed"
(`Spec/go_etcd_io/etcd/client/v3/watcher__Watch.lean`, docstring and the `isSpsc` postcondition).
A consumer that wants every event therefore has to handle the close (re-watch from `nextrev`, or
cancel its own clients). The proxy does neither. The bug is present at the pin (the lines quoted
above are at `107edf7e4`).

## Proposal: `grpcproxy-watch-relay`

Translate and verify the proxy's watch path (`watch.go` 332 Go lines, `watch_broadcast.go` 167,
`watch_broadcasts.go` 135, `watcher.go` 132, `watch_ranges.go` 69). Build it on the client's
`watcher.Watch` spec (the channel's `rangeWatchElem` elements) and the server's `serverWatchStream`
reply model (`ctrlAnswers`, `Proof/.../v3rpc/InvWatchStream.lean`), which the proxy's server side
reuses. The property is the server's watch guarantee restated for the proxy's clients. For each
proxy watcher `w` with range `R` and start `s`, the responses posted on its stream are the
backend's events in `R` from `s` on, in order and each once, up to some revision. They are
followed by nothing or by a `Canceled` response:

```lean
proxyWatchOk w : postedEvents w = (logEvents log s r).filter (inRange R) ∧
  (bcastEnded (bcastOf w) → ∃ resp ∈ posted w, resp.canceled ∨ reassigned w)
```

Its safety core is an invariant of `watchBroadcasts`: every member of `bcasts` has a live
goroutine (no `stopped` broadcast is in `bcasts`). At the pin it fails at the goroutine's exit,
and it is what PR #21814 establishes. Cost: medium to large. The package has to be translated
first; `grpcproxy` imports metrics, `zap` and the client, of which only the client has specs. Then
an invariant over two locks (`wbs.mu` and each `wb.mu`), with ownership of the receivers moving
between broadcasts in `coalesce`. Liveness ("eventually receives") is out of reach; the
safety statement above catches this bug, etcd#18231 and the watch half of etcd#19296.

## Findings

None new for `issues/`: the bug is in an untranslated package (O-pkg), and step 7 records only
bugs in translated code. One detail is not in the upstream report: the client's final `Canceled`
response resets the dead broadcast's `nextrev` to 1, which makes the dead broadcast an eligible target
of every `coalesce` in its range.
