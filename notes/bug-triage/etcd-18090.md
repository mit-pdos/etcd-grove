# etcd-io/etcd#18090: client panics, index out of range in `Client.dial` (v3.5.11)

- URL: https://github.com/etcd-io/etcd/issues/18090 (closed 2025-05-27 by the stale bot; labels
  `type/bug`, `stale`, `priority/awaiting-more-evidence`)
- Affected: client v3.5.11, after killing all three members at once and restarting them
  (reported, low probability, not reproduced).
- Fix: none for the report itself (diagnosis unsettled). Related: PR #18220 (merge `b96b6ba04`,
  2024-06-24, commit `281f17734`, on `main`) adds to `Client.Sync` an assertion that the endpoint
  list is non-empty; the maintainer (ahrtr) holds that a successful `MemberList` never yields an
  empty list and asked for a reproduction, which never came.

What goes wrong (the reporter's hypothesis): `autoSync` (`client/v3/client.go`) calls `Sync`
periodically; `Sync` keeps the client URLs of members with a non-empty `Name` that are not
learners, and calls `SetEndpoints(eps...)` even when `eps` is empty. A later `dial` reads
`c.Endpoints()[0]` (v3.5.11 `client.go:302`) and panics. In v3.5.11 `dial` runs from `newClient`
(which rejects an empty `cfg.Endpoints`) and from the exported `Client.Dial(ep)`; the panic needs
the latter (or a caller of `SetEndpoints()` with no argument) after the list was emptied.

## Classification

**O-fn (secondary O-pkg; unsettled, possibly N).** At the pin the same shape is still possible:
`Sync` (`client.go:186-205`) still calls `SetEndpoints(eps...)` unconditionally; #18220's check is
`verify.Verify`, which runs only when `ETCD_VERIFY` asks for assertions
(`client/pkg/verify/verify.go:69-74`), so in production nothing stops an empty list; and `dial`
(`:327`) and `dialWithBalancer` (`:312`) index `[0]` (`Dial(ep)`, `:277`, reaches `dial`). None of
these is translated (`client/v3.toml` has no `Sync`/`dial`/`Dial`), and whether `MemberList` can
answer with no named voting member is a server-side membership question (`membership` not
translated: O-pkg). No spec here states or relies on a non-empty endpoint list.

Source of verification states: no `verified.txt`; the `.toml`, `Spec/`, `Proof/` files.

## Does the spec exclude it?

No spec covers the path. The only verified reader of the endpoint list is the retry interceptor's
backoff (`roundRobinQuorumBackoff`, through the `Client.Endpoints` axiom), which uses its length
and is unaffected by an empty list. The crash, if it happens, is in untranslated code, so this is
O. Whether it is a bug at all depends on the server: if a linearizable `MemberList` always names
a started voting member (the maintainer's view; members' names are recovered from the backend on
restart), `Sync` never empties the list and the report is N (some other cause, e.g. an
application clearing the endpoints). Not reproduced here; no `issues/` file, since the reachable
step (a `MemberList` with no named voter) is not established.

## Proposal: `client-endpoints-nonempty` (part of `verify-client-new`)

A lock invariant of `Client.epMu`: `c.endpoints ≠ []`. `newClient` establishes it (it rejects an
empty `cfg.Endpoints`); `SetEndpoints` takes `eps ≠ []` as a premise; `Sync` meets it either by a
spec of `Cluster.MemberList` at the gRPC boundary ("a successful answer lists a non-learner member
with a name and a client URL": an assumption about the server, or a theorem once membership is
verified) or, better, by hardening the code to skip `SetEndpoints` when `eps` is empty (the
premise then becomes the code's own check, and `verify.Verify`'s assertion a dead branch). `dial`'s
`[0]` is then safe. Cost: small for the invariant and the three functions; the `MemberList`
statement is free as an axiom and large as a theorem.
