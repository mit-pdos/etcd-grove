# etcd-io/etcd#18267: Filtering GET via With{Min,Max}{Create,Mod}Rev has wrong result Count

- URL: https://github.com/etcd-io/etcd/issues/18267 (closed 2025-09-26; labels `type/bug`,
  `area/documentation`, `help wanted`).
- Affected: every version; the behavior is unchanged at the pin.
- Resolution: documentation, no code change. PR #18268 (count after filtering) was abandoned.
  ahrtr ruled that `Count` is the number of keys in the range. sig-etcd reframed the issue as
  documentation. `rpc.proto`'s `count` comment was updated in `97c63c9fd` (2025-02-18, PR
  #19446): "Unlike Kvs, it is unaffected by limits and filters (e.g., Min/Max, Create/Modify,
  Revisions)", which is at the pin (`api/etcdserverpb/rpc.proto:518-521`). The website's API pages
  followed (etcd-io/website#1063, closed 2026-01-23 via website PR #1070).

The report: `get --prefix --max-create-rev 1454 /k` over three keys returns one KV and `Count: 3`.
`executeRange` (`server/etcdserver/txn/range.go`) prunes `rr.KVs` with `filterRangeResults`/
`pruneKVs`, but `asembleRangeResponse` sets `resp.Count = rr.Count`, mvcc's count of the keys in
the range before filtering (`range.go:163`).

## Classification

**N (works as documented; the spec states exactly the reported outcome).** At the pin the API
documents that `count` ignores the revision filters and the limit. The verified spec of
`executeRange` gives the response's count as `srvCount o st withTotal`
(`Proof/go_etcd_io/etcd/server/v3/etcdserver/txn/RangeModel.lean:134-138`). That is the number of
keys of the state in the range (`rangeIn s o`). The key-values are `srvPre`
(`RangeModel.lean:102-106`): the same range, filtered by `kvFilterOk`. The reporter's `Count: 3`
with one KV is precisely what the spec says. The specs were written to the documented contract,
which is what a spec is for here.

Source of verification states: the proof files (`executeRange.lean:158`: `cnt = srvCount o st
withTotal`, `vs0.filter (kvFilterOk o) = srvPre o st`).

## Side note

`srvCount` also shows the case ahrtr left out. With a positive limit and no `withTotalCount`, the
count is capped at the limit mvcc reads with (`totalOf`, `Proof/.../storage/mvcc/Hist.lean:908-911`,
of `rangeLimitOf o`, the request's limit plus one when the server neither sorts nor filters by revision), not the full
range count. `rpc.proto` covers this with "set to the actual
number of keys within the range *when requested*". The client's `WithMin/Max*Rev` comments
(`client/v3/op.go:479-489`) still do not mention `Count`. That is a documentation nicety, not a
code/doc contradiction, so there is no `issues/` file.
