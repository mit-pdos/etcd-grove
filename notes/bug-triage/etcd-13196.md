# etcd-io/etcd#13196: etcd 3.5.0 resurrects ancient (unremovable) members

- URL: https://github.com/etcd-io/etcd/issues/13196 (closed 2022-01-20; labels `type/bug`,
  `priority/important-soon`)
- Affected: v3.5.0, after an upgrade from v3.4 (or older) of a cluster that had membership
  changes over the years. Not reproduced by the maintainers.
- Fix: PR #13348 "Fix for v3.5 Ensure that cluster members stored in v2store and backend are in
  sync" (`release-3.5` only, merge `4312298b7`, in v3.5.1). Not a fix of the cause. The equivalent
  PR for `main` (#16655) was closed unmerged. On `main` the v2 store stopped holding membership
  ("Remove v2 store", `fdedec1ed`, 2025-06-07, an ancestor of the pin). Later reports with the same
  symptom: #13697, #20967.

What goes wrong: up to v3.4 the v2 store was membership's source of truth, and the `members` /
`members_removed` buckets of bbolt were a mirror. That mirror could diverge. Members that had been
removed long ago were still in the `members` bucket. The #20967 thread later found two causes:
v3.4's `etcdctl snapshot restore` does not clear those buckets, and a `--force-new-cluster` restart
can drop a committed AddNode. v3.5.0 made `RaftCluster.Recover` load the members from bbolt. The
zombies then showed up in `member list`, and rafthttp probed them. `member remove` failed with
`ErrIDNotFound`, because the validation looked at the v2 store. #13348 made v3.5.1 use the v2 store
again and made Add/Remove work on both stores, so a zombie can now be removed. The divergence
itself was not fixed.

## Classification

**F (release-branch code replaced); counterfactual F−, gap O-fn.** The decisive fact: at the etcd
pin `107edf7e4`, membership has one store. `RaftCluster.AddMember`/`RemoveMember`/`PromoteMember`
write only the backend (`cluster.go:394-533`). `Recover` → `UnsafeLoad` reads it
(`cluster.go:256-262`). The v2 store gets only an export (`RaftCluster.Store`, `cluster.go:896`).
So two stores that diverge, which is the mechanism here, cannot happen in the pinned code.
Counterfactually, nothing here specifies membership's contents, so the buggy version would verify
just as well (below).

Source of verification states: the batch's `verified.txt` (`etc/verified-code.py --functions`, at `d606c9cac`).

## The counterfactual

On the buggy code, would any existing statement fail? No.

- `EtcdServer.applyConfChange.spec` (the axiom, `EtcdServer__applyConfChange.lean:37-56`) says
  only where the change's backend writes happen (one critical section of the batch lock, after the
  hook) and that `cc`'s `Id` is kept. It says nothing about which members end up in the cluster or
  in the `members` bucket.
- `RaftCluster.Members.spec` (`RaftCluster__Members.lean:30-34`) returns "some list of fresh
  members", `∃ ms, membership.membersAt sl ms`, with no relation to the applied log. The zombie
  list satisfies it.
- The apply-determinism results (`applyEntries_kv`, apply `Results.lean`) model the key-value
  state only. Membership is not in the modeled state, so a member store that diverges from the
  log is invisible to them.

So the gap is that this code is not specified (**O-fn**: the `membership` package, 6 of 71
functions and 37 of 934 lines verified; the schema's membership backend is not translated). It is
not a weak spec.

## Proposal: `membership-state-model`

A pure membership state of the applied log, and the invariant that both the in-memory cluster and
the backend's buckets equal it:

```lean
structure MemState where
  members : GMap w64 MemberM      -- peer URLs, isLearner, attributes
  removed : GSet w64
def memOf (ents : List EntryM) : MemState   -- folds ConfChange and ClusterMemberAttrSet entries
-- conjunct of the apply thread's invariant at applied index i:
isRaftClusterAt c (memOf (applied i)) ∗ membersBuckets b (memOf (applied i)) ∗
  ⌜confStateOf (memOf (applied i)) = cfgAt i⌝
```

To prove it: replace the `applyConfChange` axiom (this is `verify-apply-conf-change`) and prove the
`RaftCluster` writers and the schema backend's put and delete against `memOf`. Prove `Recover`/
`UnsafeLoad`/`MustReadMembersFromBackend` return `memOf` of the bucket. Prove `applySnapshot`'s
snapshot branch: a received snapshot's buckets are `memOf` at the snapshot index. Strengthen
`Members.spec` to "the members of `memOf (applied i)`".

Cost: medium to large, about 500 Go lines (the cluster.go writers, `schema/membership.go`, the
snapshot branch of `applySnapshot`, `buildConfStateFromV3store`). For the restart half (the bucket
read at boot is the state of the persisted applied index), `crash-restart-model` is also needed.
It would have caught this bug's class, a member store that diverges from the log, at the first
writer that diverges.

## Findings

None new. The two-store mechanism is not in the pinned code, so there is no `issues/` file.
`etcd-20967.md` has a related observation: at the pin the `members` bucket also seeds raft's
`ConfState` at restart.
