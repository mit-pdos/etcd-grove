# etcd-io/etcd#16596: etcd fails to start after power failure

- URL: https://github.com/etcd-io/etcd/issues/16596 (closed 2023-09-15, "won't fix"; `type/bug`).
- Affected: 3.4.25 (reported); reproduced on 3.5 (`7ed8970e2`) and 3.6/main (`9ec5f9818`). Found
  with LazyFS's split-write fault.
- Fix: none in code. bbolt documented the limitation (etcd-io/bbolt#567 → PR #1151; bbolt v1.5.0
  `README.md:901-904`, "Bolt db can be corrupted during the initialization phase due to abrupt power
  failure"). Follow-ups: etcd#16597 (LazyFS power-failure scenarios in the robustness tests) and
  bbolt#568.

What goes wrong: on first start, `backend.newBackend` → `bolt.Open` → `DB.init`
(bbolt `db.go:646-689`) writes the two meta pages, the freelist and an empty leaf in one
`writeAt` of `4 × pageSize` = 16 KiB, then `fdatasync`. A power failure in between can persist half
of the write (a torn write). On restart, `bolt.Open` finds invalid meta pages, `newBackend` panics
"failed to open database", and the member does not start. The file holds no data yet. Once init
has succeeded the problem cannot recur, because bbolt keeps two meta pages and writes one
meta page per commit.

## Classification

**O-pkg (bbolt internals); secondary A-model (torn writes, crashes) and N (won't fix,
documented).** The bug is still present at the pin. etcd's `go.mod` at `107edf7e4` uses bbolt
v1.5.0, whose `init` is unchanged. But the faulty code is in bbolt's `init`, which nothing here
translates (bbolt is a trust boundary: 19 assumed specs in `verified.txt`). The etcd caller
`backend.newBackend` is translated but not verified. No spec is contradicted. The trust-boundary
`bbolt.Open_kv.spec` (`Spec/go_etcd_io/bbolt/Open_kv.lean`) has the premise `fileHolds path D` and
allows an error result (`⌜err ≠ nil⌝ ∨ …`). A torn file holds no `D`, and the failure observed is
an error from `Open` that etcd turns into a panic. So the axiom is not falsified (not A-axiom).

## Argument

There is no crash in the model (`notes/STATUS.md:1137-1141`), and no file-system state between
processes beyond the opaque `fileHolds` (`Proof/.../storage/backend/InvBbolt.lean:27,89`). Nothing
here states "a power failure at any point leaves a file that `Open` accepts", so the report's
expectation is not a property any spec claims. Upstream considers it acceptable: only an empty,
never-initialized database is affected, and it is now documented.

## Proposal: `fs-crash-model` (new, shared with etcd#6368)

With a file-system model that allows torn page writes and the loss of unsynced data at a crash,
state bbolt's open contract as crash-safe:
`fileHolds path D` survives a crash during a commit as `fileHolds path D ∨ fileHolds path D'`.
`init` would fail that statement unless the initial write is made atomic: write the leaf and
freelist pages, `fdatasync`, then write the meta pages, or write a single meta page first. This
belongs to bbolt's verification and needs Perennial crash semantics, which the Lean port lacks.
Cost: large, and low priority for this bug (it only affects initialization).

None: the bug is not in code this repository translates, so no `issues/` file is needed.
