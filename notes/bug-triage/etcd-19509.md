# etcd-io/etcd#19509: [3.6] panic: Write called after Handler finished

- URL: https://github.com/etcd-io/etcd/issues/19509 (closed 2025-03-05; label `type/bug`)
- Affected: v3.6.0-rc.0 and rc.1. Triggered by a gRPC-JSON gateway watch stream (`POST
  /v3/watch`, chunked body) over TLS whose client disconnects. Bisected to the grpc-gateway bump
  2.22.0 → 2.23.0 (`f43c6815b`).
- Fix: grpc-gateway v2.26.3 (grpc-ecosystem/grpc-gateway#5303 reverted the change), taken by etcd
  PR #19521 (merge `3d381537c`, 2025-03-04), which bumps the module and regenerates
  `api/etcdserverpb/gw/rpc.pb.gw.go`.

What goes wrong: since 2.23.0 the generated `RegisterWatchHandlerClient` started a goroutine
that, when decoding the request body failed (`STREAM_CLOSED` after the client left), wrote the
error to the `http.ResponseWriter` with `runtime.HTTPStreamError`. That happened after the
handler had returned, and `x/net/http2`'s `responseWriter.write` panics on a write after the
handler finished. The server crashed.

## Classification

**F (fixed before the verified code), counterfactual O-pkg.** `3d381537c` is an ancestor of
the pin `107edf7e4` (`git merge-base --is-ancestor`: yes). At the pin, `api/go.mod` and
`server/go.mod` require grpc-gateway v2.31.0, and `request_Watch_Watch_0`'s sender goroutine
(`rpc.pb.gw.go:198-207`) only decodes and `stream.Send`s; it never touches the response writer.
The code is generated gateway glue plus a third-party runtime, neither translated (no
`etcdserverpb/gw` function in `verified.txt`). Counterfactually nothing here would have seen
it: F−, gap O-pkg.

## The counterfactual (step 5)

The bug is a use of a resource after its owner gave it up. An ownership-style spec would exclude
it: the handler receives `ownWriter w` and must return it at its end, and no goroutine it forks
may keep a share. Goose/Iris specs of this shape exclude it by construction (the forked
goroutine would need the writer after the handler's postcondition consumed it). This needs (a)
translating the generated gateway file (about 2,500 lines, one pattern repeated per RPC) and
(b) trust-boundary specs of grpc-gateway's `runtime` and `net/http` with that ownership.

## Proposal: `verify-grpc-gateway-handlers` (new)

Spec: for each generated handler `h`, `{{ ownWriter w ∗ ownReq r }} h w r pathParams {{ True }}`
with `ownWriter w` consumed exactly at the handler's return (forked goroutines may hold only the
request body and the gRPC stream). Axioms: `runtime.HTTPError`/`HTTPStreamError`/
`ForwardResponseStream` need `ownWriter w`. Cost: medium. The generated code is uniform, so one
proof pattern repeated over the RPCs, but it hinges on modeling `net/http`'s handler-lifetime rule
in Perennial (not there today; a general model of the library, to be proposed per CLAUDE.md).
It would catch a regression of this class at each grpc-gateway bump, but only if the generated
file is re-translated and re-proved on every bump. Low priority next to the server's own code.

## Findings

None: fixed at the pin. No bug in this repository's specs.
