# etcd-io/etcd#17155: The ETCD cluster experiences data inconsistency issues during a large number of write operations

- URL: https://github.com/etcd-io/etcd/issues/17155 (closed 2023-12-27, "no useful info provided";
  label `type/bug`).
- Affected: unknown (the version field says "none"); no logs, no configuration, no db files.
- Fix: none.

The report gives no observation, only a generic recipe: drive many concurrent writers, then
compare `etcdctl get` results. The maintainer asked whether reads went to different members
without `--consistency=l` while traffic was still running (that is, serializable reads), and for
db files. Nobody answered.

## Classification

**N (not an actionable bug report: no version, no observation, no data).** The likeliest reading,
the one the maintainer suggested, is documented behavior: a serializable read is served from the
member's local state, which may lag behind the cluster. The specs state exactly that. Nothing to
reproduce or to locate.

## What the specs say about the likely reading

`rangeReadOk` (`Proof/go_etcd_io/etcd/server/v3/etcdserver/InvRead.lean:180-188`), the
postcondition of `EtcdServer.Range` (`Spec/.../etcdserver/EtcdServer__Range.lean`):

- the response is the state after a **certified** log `log` (`mvcc.idxCert`, `mvcc.certOk`) that
  extends the caller's floor `F`;
- the read-index conjuncts `readLogOk γr c log` and the committed raft log `L` with
  `kvModel γr.kv L = log` are required **only if not `o.base.serializable`** (lines 184-186).

So a serializable `get` returns some applied, certified prefix of the one KV history, possibly
older than another member's. Two members can return different values for a key during writes, but
neither can return a state that is not a prefix of the common history. A linearizable `get`
(`etcdctl`'s default) reads at or after the committed index the caller saw (`readLogOk`,
`range_linearizable`/`applied_log_at`, `Proof/.../etcdserver/Results.lean:31-36,181`). Any other
kind of "inconsistency" would need data, and the report has none.
