# etcd-io/etcd#20271: panic: assertion failed: Page expected to be: 5

- URL: https://github.com/etcd-io/etcd/issues/20271 (closed 2025-09-22; `type/bug`)
- Affected: `main` and `release-3.6` (found by Antithesis, robustness tests with fault injection;
  fuweid reproduced it in e2e with SIGSTOP, PR #20503); the race exists in 3.4/3.5 too (backports
  #20653, #20650, #20659).
- Fix: PR #20553 "[fix #20271] protect backend usage from concurrent `applySnapshot` and `defrag`"
  (merge `581b0b577`, 2025-09-11), plus bbolt's `(*Tx).WriteTo` reusing the open file instead of
  reopening `db.path` (etcd-io/bbolt#1057, in bbolt v1.4.3; the pin uses bbolt v1.5.0).

What goes wrong (pre-fix code). A follower receiving a snapshot runs `applySnapshot` on the apply
goroutine: `OpenSnapshotBackend` renames `<index>.snap.db` onto `member/snap/db` and opens it.
The maintenance RPC's `Defragment` called `s.be.Defrag()` with no server lock. Defrag writes a
compacted copy and renames it onto the same path `member/snap/db`. When the defrag's rename lands
between the snapshot's rename and its `Open`, the server opens the old, defragmented data (consistent
index 67 instead of 74 in fuweid's trace). A later defrag renames another file over the path while
the server holds the open file descriptor of the previous inode. bbolt's `WriteTo` (used by
`backend.Snapshot` to send a snapshot to a peer) then reopened `db.path`, so it streamed the meta pages
of one inode and the data pages of another. The receiving follower got a db whose root page was
all zeros, and bbolt's `Open` → `loadFreelist` → `freepages` panicked on `FastCheck`.

## Classification

**F (fixed before the verified code); counterfactual F− (A-pre, O-fn; secondary A-model; the bbolt
half O-pkg).** The fix `581b0b577` is an ancestor of the etcd pin `107edf7e4` (`git merge-base
--is-ancestor`: yes). At the pin, `applySnapshot` holds `s.bemu.Lock()` from before
`OpenSnapshotBackend` to the backend swap (`server.go:1040-1084`), and `EtcdServer.Defragment` holds
`s.bemu.RLock()` around `s.be.Defrag()` (`server.go:964-976`, upstream's non-blocking-defrag variant
of the fix). The existing proofs would also have gone through on the buggy code. The verified
`applySnapshot` covers only the empty-snapshot case (premise `rnApP`'s `ap.snapshot = null`), and
`Defragment`/`Defrag` and `OpenSnapshotBackend` are not translated. The race is also on a file
*path*, which nothing here models: bbolt's `Open` takes `fileHolds path D`, an abstract
caller assumption, and no verified function calls it.

Source of verification states: `verified.txt` (`etc/verified-code.py`, this batch).

## The counterfactual (step 5)

The buggy version is `applySnapshot` taking `bemu` only around `s.be = newbe`, with `Defrag`
unlocked. Two things keep the existing proofs from seeing it:

1. **A-pre.** `EtcdServer.applySnapshot.spec` requires `taSnapshotAddr ap ↦□ null`, which comes
   from `rnApP` (`InvRaftNode.lean:682`, raft's contract as stated here: a `toApply` carries no
   snapshot). The snapshot branch, where the lock placement changed, is dead code in the proof.
   Real followers receive snapshots (the reporter's log: "applying snapshot ... incoming-leader-snapshot-index 81").
2. **O-fn / A-model.** Even with the branch proved, the conflict is between two renames onto the
   path `cfg.BackendPath()`. The only file-level fact here is `fileHolds path D`
   (`InvBbolt.lean:89`, an axiom, `Timeless`, not exclusive). It holds no ownership of the path,
   so a proof would not need a lock to rename over it. The defrag side is not translated at all.

So the existing statements admit the buggy version. Under the proposal below, the buggy version
fails: `OpenSnapshotBackend`'s rename needs the exclusive path resource, `bemuP` holds it with `s.be`,
and the buggy `applySnapshot` calls `OpenSnapshotBackend` without owning `bemu`.

The bbolt `WriteTo` half (reopening `db.path` instead of the open descriptor) is inside bbolt,
which is a trust boundary here (`Spec/go_etcd_io/bbolt/*_kv.lean`): O-pkg. Its fix is in the pin's
bbolt v1.5.0.

## Proposal: `server-apply-snapshot` (with the defrag of `backend-commit-saves-ci`)

The receiver's half of `server-apply-snapshot`: drop `rnApP`'s `ap.snapshot = null` and prove the
snapshot branch. Add the file-ownership part already suggested for this slug (each `.snap.db` a
resource). Make the backend path an exclusive resource `dbPath γ path D` (replacing the persistent
`fileHolds`). It is owned by `bemuP` together with `s.be`. `os.Rename(snapPath, BackendPath)`
consumes `snapDB id` and needs `dbPath`; `bolt.Open` needs it and gives `ownDB db γ D`. Translate
`EtcdServer.Defragment` and `backend.Defrag` (the `backend-commit-saves-ci` defrag, ~350 lines,
bbolt as boundary). Then `finishDefrag`'s rename requires `dbPath`, which it can reach only through
the `bemu` reader slot. Since `applySnapshot`'s writer lock excludes readers, the two renames are
serialized. Cost: the path resource and the defrag translation are medium. The rest is the large
`server-apply-snapshot` (it depends on `mvcc-restore-from-backend` and `raft-pending-snapshot-ready`).
The whole would have caught this bug. The bbolt `WriteTo` half needs bbolt's own verification
(`bbolt-kv-contract`, `etcd-15498.md`).

## Findings

None new. The race is fixed at the pin, and the bbolt half is fixed in the pinned bbolt. Related:
`etcd-20426.md` (the same snapshot path; its case 2, a received snapshot with a lower
consistent index, matches fuweid's trace here: a defrag overwrote the snapshot db before it was
opened). `etcd-17084.md` names this race as a possible cause.
