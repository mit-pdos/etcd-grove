# etcd-io/etcd#14143: Possible split-brain & loss of committed write with loss of un-fsynced data

- URL: https://github.com/etcd-io/etcd/issues/14143 (closed 2025-07-28 as stale; `type/bug`,
  `priority/important-soon`, `release/v3.5`).
- Affected: 3.5.3. Jepsen, five nodes on LazyFS, `kill :all` with loss of un-fsynced data. A
  comment says it was seen on 3.4 too.
- Fix: none. The thread has these leads:
  - ahrtr pointed at #13937, fixed for 3.5.4 by #13946.
  - aphyr was still fixing LazyFS bugs.
  - endocrimes (2022-08-02) found the bug "significantly harder to reproduce" when raft's
    `MustSync` always returned true, "implies that there is a path that is writing data and
    failing to fsync it".
  - A 2023 scenario (a stale `HardState.Commit` in the WAL letting a lagging node lead) was
    rejected by ahrtr and tbg: elections compare the last index, not the commit index. tbg
    added that "known committed" matters only for conf-change activation.

  Never root-caused.

What was observed: after a whole-cluster kill and restart, an acknowledged append (key 233 ← 4)
was gone. In a second run, `n3` repaired a torn WAL tail ("unexpected EOF", `wal/repair.go`). It
then held entries 906-907 at term 4 that the others lacked: their last entry was term 4, index 905. It
served client requests from its own divergent state until `checkInitialHashKV` stopped it on a
later restart. A third run panicked on a missing `<index>.snap.db` ("failed to recover v3 backend
from snapshot") and showed every anomaly type.

## Classification

**A-model (diagnosis unsettled); secondary O-pkg (WAL repair, snapshot files) and N (possibly
LazyFS).** The decisive fact is the same as for etcd#14140. Both symptoms, a lost committed write and
two timelines, need the loss of durable state at a crash. The proofs have no crash and no stable
state (`notes/STATUS.md:1137-1141`, 2239). The code that decides the outcome on restart is not
translated or not verified:
- `wal.Repair`, `ReadAll`, and the snapshot file lookup (`snap.Snapshotter.LoadNewestAvailable`,
  `snap/db.go`): `storage/wal` has 0 of 78 functions verified, `etcdserver/api/snap` names only.
- the server's bootstrap from a WAL: not modeled (STATUS stage R8a, D11).

Within one crash-free execution, the raft results (one committed log, `isCommitted`; leader
uniqueness per term) exclude a split brain. Here the cluster's state was produced by restarts the
model cannot represent (`RestartNode`'s `rnInit`, `raft-197.md`), so there is no X.

## Argument

- **Lost committed write.** Raft's guarantee is that a committed entry is in the log of every
  later leader (Leader Completeness, in the protocol invariant behind `isCommitted`). It holds for
  volatile logs that never lose entries. If un-fsynced appends of a majority vanish at a crash,
  the committed entry can be on a minority, and a new leader without it is legal for the
  restarted nodes. `MustSync.spec` shows that etcd fsyncs whenever entries are appended. A loss
  therefore points either at a missing fsync elsewhere in the WAL (file creation or cut,
  `etcd-6368.md`'s class; the torn-tail `Repair`) or at LazyFS. endocrimes' `MustSync` experiment
  fits a commit-only `HardState` written without fsync. That is by design and harmless to the log
  itself, but it gives a stale `Commit` after a crash, which matters for conf-change activation
  (`issues/raft-commit-lost-with-entries-kept.md`, also tbg's remark in the thread).
- **Split brain.** `n3` kept entries 906-907 (term 4) after `Repair`, while a new leader at term 5
  overwrote index 906. That is ordinary raft: uncommitted entries are replaced. Divergent *applied*
  state on `n3` additionally needs `n3` to have applied entries past what the cluster committed,
  that is, a lost `HardState`/log on the others or a backend ahead of the WAL (#22028, Antithesis:
  "backend.ConsistentIndex must be <= WAL.HardState.commit"). Both are crash-recovery states
  outside the model.

## Proposal: `crash-restart-model` (existing), with `raft-durable-acks` and `fs-crash-model`

- `raft-durable-acks` (`etcd-14370.md`): committed implies the entries are on a quorum's WAL, as
  a ghost fact.
- `fs-crash-model` (`etcd-6368.md`): what `wal.Open`+`Repair`+`ReadAll` return after a crash
  extends what synced `Save`s wrote. This is the step a torn WAL tail exercises.
- `crash-restart-model`: the restart composes them, so Leader Completeness, and hence no lost
  write and no split brain, holds across whole-cluster crashes. A server-side conjunct
  `consistentIndex ≤ walDurable commit` covers the bbolt/WAL ordering (#22028).

Cost: large; crash semantics are not in Perennial's Lean port.
