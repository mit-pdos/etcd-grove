# etcd-io/etcd#18881: etcdserver: data corruption detected, unable to start etcd member

- URL: https://github.com/etcd-io/etcd/issues/18881 (closed 2024-11-12, the day it was filed;
  label `type/bug`).
- Affected: v3.5.0, after a sudden power outage; the member would not start.
- Fix: none. The maintainer's answer: "3.5.0 is known to have corruption issues. Please try the
  latest version". That points at etcd-io/etcd#13766 (crash during apply, fixed in 3.5.3,
  `c83b1ad9b`).

The report's logs do not hold together. `data corruption detected, unable to start etcd member` and
`panic: corrupted data detected` are not messages etcd v3.5.0 emits (`git grep` at `v3.5.0`:
no match). `member … has already been bootstrapped` is real (`server/etcdserver/server.go:445` at
v3.5.0), but it comes only from the `!haveWAL && cfg.NewCluster` branch. The stated configuration
is `--initial-cluster-state=existing`, and the text also describes "a single-node Kubernetes
cluster" alongside a three-member `--initial-cluster`. If that message is real, the member started
without its WAL directory, perhaps lost in the outage. With no WAL, no db and no real stack, the
cause cannot be found.

## Classification

**A-model (diagnosis unsettled): whatever happened needs a crash, and the proofs have no crash or
disk-durability model; secondary F+ (the maintainer's candidate, etcd#13766) and N (the report's
logs are inconsistent with its configuration and with etcd's messages).** The candidate causes:

- **etcd#13766** (3.5.0–3.5.2: the consistent index persisted ahead of its entry's effects, so a
  crash under load leaves a member whose state differs from its peers'). Fixed at the pin, and
  **F+** per `notes/bug-triage/etcd-13766.md`: at the pin the index of an entry with writes is set
  only by the post-lock hook under the batch lock, and the apply-thread protocol
  (`Proof/.../etcdserver/InvApply.lean`) cannot justify the pre-fix `SetConsistentIndex`, so the
  proof of `applyEntryNormal` would fail at that call.
- **Power loss destroying unsynced files**: a torn bbolt page, a lost WAL segment or WAL
  directory entry. This is the class of etcd#16596 (bbolt `init` after a power failure) and
  etcd#22340/#22498 (missing directory fsyncs): O-pkg (WAL, bbolt internals, not translated) and
  A-model (no crash semantics, no file-system durability model).

## Code path

None can be placed, because the failing startup check is not identified. The startup path is not
verified either way: `embed`, `etcdserver.bootstrap*`, `storage/wal` (0 of 78 functions verified,
`verified.txt`) and bbolt's `Open`/`init` are untranslated or names-only; `store.restore` is an
axiom for an empty bucket only (`Spec/.../storage/mvcc/store__restore.lean`).

## Proposal: `fs-crash-model` (existing)

A file-system model where unsynced data and directory operations can be lost at a crash and page
writes can tear. With it: after a crash, WAL `Open` + `Repair` + `ReadAll` returns a log extending
what synced `Save`s wrote, and bootstrap finds the WAL whenever a previous run had synced one. That
is the statement that would turn a startup failure after power loss into either a proof or a found
bug. Large: Perennial's Lean port lacks crash semantics, so this needs a Perennial proposal first
(cost as in the index). For the 13766 candidate nothing new is needed (F+).

## Findings

None: nothing points at the pinned code; no bug in this repository's specs.
