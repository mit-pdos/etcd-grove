# etcd-io/etcd#17623: blocked election campaign fails with "Invalid auth token" when the leader dies after the token expired

- URL: https://github.com/etcd-io/etcd/issues/17623 (closed by the stale bot; labels `type/bug`,
  `stale`). Not fixed. PR #22270 (documentation only, closed unmerged). PR #22560 (open, commit
  `7a87a72d1` on a contributor's fork, not in etcd-io/etcd) adds `RenewToken` to the auth store
  and a retrying interceptor to `v3client`.
- Affected: 3.5.5 as reported. A contributor could not reproduce it with jetcd 0.8.5 and etcd
  3.6.6 (etcd-io/jetcd#1131), so whether 3.6 still shows it end to end is unsettled. The code
  shape the maintainers point at is unchanged at the pin `107edf7e4`.
- The report: a jetcd client calls the gRPC `Election.Campaign` with simple-token auth and blocks
  as a follower. More than 5 minutes later (the simple token's TTL) the leader dies, and the
  blocked `Campaign` fails with `etcdserver: invalid auth token`. A retry succeeds. etcdctl over
  the Go client also logs an error and retries.

What goes wrong (maintainers' diagnosis, checked at the pin): `v3election.Campaign`
(`server/etcdserver/api/v3election/election.go:40`) runs `concurrency.Election.Campaign(ctx, …)`
on the in-process `v3client` with the RPC's context, so every internal request carries the token
of the original call. When the watched key is deleted, `waitDeletes` issues its next `Get`
(`client/v3/concurrency/key.go:56`). The server's `Range` reads the token from the context and
rejects it because it expired while the caller was blocked: `waitDeletes` returns the error, and
so does `Campaign` and the RPC. The Go client hides this. Its retry interceptor
(`Client.unaryClientInterceptor`, verified) refreshes the token on `ErrInvalidAuthToken`
(`shouldRefreshToken`). `v3client` has no credentials to refresh with.

## Classification

**O-path (secondary A-model, C-err).** The failing composition is the untranslated `v3election`
server on the untranslated `v3client`/adapter. The token's expiry is in the untranslated
`simple_token.go`/`jwt.go`. The verified parts are not at fault. `Election.Campaign.spec` allows
"an error, in some state" (`Spec/go_etcd_io/etcd/client/v3/concurrency/Election__Campaign.lean:53`),
and `waitDeletes.spec` allows any error (`.../waitDeletes.lean:39`). Token lifetime is time, and
time is outside the model (A-model). The Go client's refresh path is verified only as "returns
some boolean" (`Spec/go_etcd_io/etcd/client/v3/Client__shouldRefreshToken.lean`). Even a verified
`v3election` would meet a spec that allows an error here (C-err), unless the spec says which
errors a blocked `Campaign` may return.

A side effect at the pin: the `Campaign` error comes from the `default:` branch of `waitDeletes`'
error handling, so the candidate key is left in etcd with the session cleared
(`issues/etcd-election-campaign-error-orphan-key.md`, etcd-io/etcd#21128). The jetcd retry with
the same lease reuses that key (the transaction's `Else`), which is why retrying works.

## Proposal

`inproc-client-auth-identity` (`etcd-17502.md`): verify `v3client` and the adapter with
`v3election`/`v3lock`, and state that each internal request is authorized as the RPC's user. For
this bug it also needs one of the following:

- a token-lifetime model (a token valid from issue until expiry by a ghost clock: A-model, which
  needs a clock in Perennial and is not available today), so that "an internal request of a live
  RPC is not rejected for an expired token" can be stated; or
- the safety stand-in that needs no clock: `v3election.Campaign`'s spec allows an auth error only
  if the user's permission on the prefix was revoked (the auth store's revision moved and the new
  state denies it). With PR #22560's renew-and-retry interceptor this is provable. At the pin it
  is not.

Cost: medium for the identity part, as for #17502. The clock-free stand-in adds a small auth
revision model.

## Findings

No new `issues/` file. The bug is in untranslated code (`v3client`'s missing token renewal), and
the documentation question is upstream's (#22270). It touches
`issues/etcd-election-campaign-error-orphan-key.md` (new in this batch) as described above. No
