# etcd-io/etcd#9416: clientv3: Canceling `Watch()` doesn't send `&pb.WatchCancelRequest`

- URL: https://github.com/etcd-io/etcd/issues/9416 (closed 2020-05-07; label `type/bug`).
- Affected: clientv3 v3.2 and v3.3, and `master` at the time (`00b84235df`). Seen in production with
  v3.2.24: server-side watchers grew to about 30k, and then there were slow watchers.
- Fix: PR #11850, "clientv3: cancel watches proactively on client context cancellation" (commit
  `87aa5a9e6`, merge `6d067997e`, 2020-05-07).

What goes wrong (pre-fix code). `watchGRPCStream.run` (`clientv3/watch.go`) takes a substream whose
watch context was canceled from `closingc`. It calls `closeSubstream`, which forgets the substream
on the client side, and sends nothing to the server. The server's `mvcc` watcher for that id stays
alive until the next event for its key range arrives. Then `dispatchEvent` fails, and the
"unexpected watch id" branch sends a cancel. If the range is never written again, the watcher lives
as long as the gRPC stream does. A client that watches and cancels in a loop leaks one server
watcher per iteration (`etcd_debugging_mvcc_watcher_total` grows).

## Classification

**F (fixed before the verified code); counterfactual F−, gap C-perf.** The fix `6d067997e` is an
ancestor of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes). At the pin, the
`closingc` case sends a cancel request for an established substream (`client/v3/watch.go:688-710`).
The existing specs would have allowed the pre-fix code too. `run`'s spec and its model say which
requests `run` *may* have sent, but never that a cancel *must* be sent, and a leaked server watcher
is a resource. **Still present at the pin, in a narrower window: a new finding.** A watch canceled
after its create request is sent but before the `Created` response arrives also leaks its server
watcher, and nothing then cancels it (`issues/etcd-watch-cancel-before-created-leak.md`, reproduced
by a Go test at the pin).

Sources of the verification states: the proof files and `Proof/go_etcd_io/etcd/client/v3/Link.lean`
(`verified.txt` was not produced). Each proof is a `theorem`, with no `sorry` and no `axiom`.

## The counterfactual (step 5)

The pre-fix `closingc` case is the current one without lines 695-709. Would the existing specs
still hold?

- `watchGRPCStream.run.spec` (`Spec/.../watchGRPCStream__run.lean`) says only that `run` "closes
  the substreams that stop (`closingc`)". It says nothing about the requests sent on the gRPC
  stream.
- The invariant `gOk`/`phOk` of `WatchClientModel.lean` tracks the requests sent (`L`) and
  `cancelSet` (`CS`). The step taken after a cancel is `RunSt.sentCancel S X L'` (`:482`), with
  `L' = S.L ∨ L' = S.L ++ [.cancel X]` (`cancel_ok`, `:499`). The case `L' = S.L` exists because a
  failed `Send` is allowed, and it is exactly the pre-fix behavior, so the pre-fix code meets the
  same model. No conjunct of `phOk` requires that a registered id with no substream be canceled.
  `.reg X` constrains only cancels that were already sent (`:66-68`).
- The server specs are about the requests the server receives, and they hold whatever the client
  sends.

So the buggy client would verify: **F−**. The gap is **C-perf**. The specs are partial-correctness
statements about the client's own maps and channels. Nothing relates the server's live watchers on
a stream to the client's live substreams, and the leaked watcher is a server resource. The pinned
code keeps the same gap. `RunSt.answer S m i X h reg` (`WatchClientModel.lean:757`), for a
`Created` response whose head substream was closed (`h = null`, `reg = false`), adds `X` to `regs`,
does not put it in `M`, and sends no cancel. That state is the residual leak of
`issues/etcd-watch-cancel-before-created-leak.md`, admitted by the model as stated.

## Proposal: `watch-client-cancel-reaches-server`

This is a safety property that stands in for "no server watcher outlives its client substream". It
is a new conjunct of `gOk`:

```lean
-- every id the server announced on this stream that no live substream holds is canceled:
-- a cancel request for it was sent (Send succeeded) or the server already canceled it
∀ X, idLive S.Dm X → (∀ ws, S.M !! X ≠ some ws) → S.CI !! X = none →
  (S.CS !! X = some () ∧ ∃ i, S.L[i]? = some (.cancel X)) ∨ srvCanceled S.Dm X
```

`run`'s postcondition would then carry it. Proving it needs `GenericClientStream.Send`'s spec to
tell a successful send (the request is in the stream's log) from a failed one (the stream is broken,
and its server-side watchers go with it). In the `Created` case with a closed head
(`resuming[0] == nil`), the code would have to send a cancel for `X`, which the current code does
not do, so the new conjunct fails there: it would have caught both this bug and the residual one.
On the server side, `recvLoop`'s cancel case already removes the watcher (W-S). Cost: small to
medium. The model already has `L`, `Dm`, `CS` and `CI`. The work is the conjunct, its preservation
in `run`'s cases (about 6 of them), and a stronger trust-boundary `Send` spec. Liveness proper
("the server watcher is eventually removed") stays out of reach, as it does for every Iris-style
spec here.
