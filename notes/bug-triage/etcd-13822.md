# etcd-io/etcd#13822: jetcd watch become invalid after network isolation and compact

- URL: https://github.com/etcd-io/etcd/issues/13822 (closed 2022-03-24 by the reporter; label
  `type/bug`). The reporter refiled it as etcd-io/jetcd#1055 ("Sorry but, I mistakenly raised a bug
  report on etcd-io/etcd"), which was closed as stale without a diagnosis.
- Affected: etcd 3.4.13 with jetcd 0.5.0. No fix, PR or commit.

The report. A 5-member cluster is partitioned into `{A,B}` and `{C,D,E}`. Clients `a` and `b`
watch through members `A` and `B`, which are cut off. During the partition `C` (the new leader)
compacts to its newest revision while clients keep writing. After the partition heals, `a` and `b`
receive nothing, neither the missed events nor a notice that events were lost. The reproduction
uses three members, iptables, a compaction during the isolation, and jetcd.

## Classification

**N (withdrawn by the reporter as a jetcd bug); the server path it involves is outside the
verified scope (O-fn: `watchableStore.Restore`; C-scope: watch under compaction).** What etcd's
server does is to answer a watcher whose `minRev` is below the compaction revision with a
`CompactRevision` response and drop it. That is the "notified that something is lost" the reporter
expected (`watcherGroup.chooseAll`, `watcher_group.go:255-263` at the pin). Showing it to the
application is the client's job. etcd's Go client delivers it (the `default` case of `run`
dispatches a `Canceled` response with `CompactRevision ≠ 0` to the substream). The reporter
attributed the silence to jetcd. Without a server log there is no evidence that the server failed
to send the response. The specs here cannot decide the server half either way, because the paths
involved are outside them:

- A member that rejoins after its leader compacted the raft log installs a snapshot
  (`applySnapshot` → `kv.Restore` → `watchableStore.Restore`, `watchable_store.go:207-221`), which
  moves every synced watcher to `unsynced`. `watchableStore.Restore` is not specified, and the
  server's `applySnapshot` spec covers only `ap.snapshot = nil`
  (`Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__applySnapshot.lean`).
- The compaction branch of `choose`/`chooseAll` is dead under the watch specs' premise
  `crevFrozen` (`Spec/go_etcd_io/etcd/server/v3/storage/mvcc/rangeEvents.lean:30,39`; see
  `etcd-18089.md`).
- A watch on a member cut off from the leader stays silent unless it was created with
  `WithRequireLeader`. That is documented etcd behavior, not a bug.

## Code path (at the pin)

| Go function | State |
|---|---|
| `EtcdServer.applySnapshot` (snapshot case) → `watchableStore.Restore` | spec only for no snapshot; `Restore` not specified |
| `watchableStore.syncWatchers` → `watcherGroup.choose`/`chooseAll` (compacted response) | verified, frozen store only (`crevFrozen`) |
| `serverWatchStream.sendLoop` (forwards the `CompactRevision` response) | verified (W-S) |
| `client/v3.watchGRPCStream.run` (dispatches it) | verified (W-C); jetcd is not Go and is not in scope |

## Related findings

`issues/etcd-watch-restore-quiet-watcher-compacted.md` (written in this batch) is the opposite
failure on the same path. After `Restore`, a watcher that missed nothing can be canceled as
compacted. In this report's scenario the compacted cancel is legitimate, since `A`'s watchers did
miss the events written during the partition. Fixed restore bugs on the same path:
etcd-io/etcd#15271, #19487 (`etcd-15271.md`, `etcd-19487.md`).

## Proposal

None for this report (class N). The server half is covered by existing proposals:
`verify-watchable-restore` (specify `watchableStore.Restore`) and `watch-under-compaction` (drop
`crevFrozen`). Together they would state that, after a snapshot install, every watcher either gets
every event from its `minRev` or a `CompactRevision` response.

## Findings

None new. No bug in this repository's specs.
