# etcd-io/etcd#22498: `OpenSnapshotBackend` renames the db without a directory sync

- URL: https://github.com/etcd-io/etcd/issues/22498 (**open**; label `type/bug`; filed 2026-09-29)
- Affected: etcd 3.7.2 (reported), and `main`. **Present at the pin.**
- Fix: none merged. Open PRs: #22499 "fix: fsync snap directory after adopting a snapshot db" and
  #22518 "server/storage: fsync snap directory after adopting snapshot db".
- Sibling: etcd-io/etcd#22340 (the receive-side rename in `SaveDBFrom`, fixed by #22314, in the
  pin: `etcd-22340.md`).

What goes wrong (at the pin). A follower installs a leader snapshot in `applySnapshot`
(`server/etcdserver/server.go:1001`). `storage.OpenSnapshotBackend`
(`server/storage/backend.go:63-71`) renames `member/snap/<index>.snap.db` to `member/snap/db`
(`:68`) and opens it, without fsyncing `member/snap`. `applySnapshot` then calls
`consistIndex.SetBackend(newbe)` (`server.go:1060`), which zeroes the in-memory index so that it
reloads from the new db, as the snapshot's index. It closes the old backend in a goroutine
(`server.go:1095`). The old backend's final commit runs the shared pre-commit hook
`BackendHooks.OnPreCommitUnsafe` → `ci.UnsafeSave(tx)` (`server/storage/hooks.go:45-46`). That
writes the *snapshot's* index into the *old* db file, and bolt fsyncs it. If power is lost before
the rename's directory entry is durable, `member/snap/db` on restart is the old file. It carries
the snapshot's consistent index but not the snapshot's data. `RecoverSnapshotBackend` then sees
`snapshot index ≤ consistent_index`, logs "Skipping snapshot backend" (`backend.go:112`), and the
member serves a db missing the snapshot's writes. The divergence is silent: no panic.

## Classification

**O-fn (the faulty function is names-only, and the verified caller's spec excludes its branch);
secondary A-model (crash and file-system durability) and C-scope (the snapshot-install
branch).** `OpenSnapshotBackend` is names-only in `Code/go_etcd_io/etcd/server/v3/storage.lean:93`
(not in `verified.txt`'s function list). Its caller `applySnapshot` is "verified (sorry-free)"
(`verified.txt`), but its spec covers only `ap.snapshot = nil`, which returns at once
(`Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__applySnapshot.lean`). The raft wrapper's
`rnApP` provides that premise (`Proof/.../InvRaftNode.lean:682`), and `ownRawNode`'s
`snap = none` is behind it. Even with the branch in scope, the bug needs a crash that loses a
directory operation, which nothing here models.

Source of verification states: `verified.txt` (`etc/verified-code.py`, at `d606c9cac`).

## Does the spec exclude the bug? (step 4)

1. As the specs would see it: a follower whose `Ready` carries a snapshot at index `i > applied`.
   `applySnapshot` swaps backends. A crash then loses the rename, and the restart reads the old
   db with stored index `i`.
2. Premises: `applySnapshot.spec`'s `taSnapshotAddr ap ↦□ null` is violated by any follower that
   falls behind the leader's log compaction (the issue's step 2). That is a scope premise, recorded
   as a gap of the server's raft contract (`notes/STATUS.md:7580`: "no snapshots ... in a
   `Ready`"; raft side `notes/STATUS.md:1395`, S2). Not a premise real deployments meet.
3. Model: the bug needs a crash between the rename and its directory entry reaching the disk.
   Perennial's Lean port has no crash or file-system semantics (`notes/STATUS.md:1137-1141`).
4. Within what is stated, the apply protocol (`Proof/.../InvApply.lean`, header) says the right
   thing about one backend. Every commit persists a `ci` matching the effects it persists. "An
   entry at or below the saved `ci` whose effects are not in the backend is never applied (lost
   update)", and that is this bug's outcome. But `applyBackend γ ci b` ties the consistent index to
   a single backend `b`, and a backend swap is not one of its steps. The old backend's
   `Close`-commit, which saves the new backend's index into the old file, is outside the protocol.
   With the swap specified, that commit would break the protocol's "saved `ci` matches its
   effects" for the old file. That is harmless only because the old file is unlinked, which is
   true only once the rename is durable. So the fix belongs in the statement of the swap, not
   only in an fsync.

Not X: no verified spec covers the snapshot-install branch.

## Proposal: `fs-crash-model` (existing, from `etcd-6368.md`), with `server-apply-snapshot`

- `server-apply-snapshot` (new, `etcd-5857.md`) brings `applySnapshot`'s snapshot branch into
  scope. As part of it, the apply protocol gets a backend-swap step: after `SetBackend(newbe)`,
  `applyBackend γ' ci newbe` with fresh protocol names, and the old backend handed to `Close`
  under a "retired" token whose commits the protocol no longer constrains. That part stays
  crash-free.
- `fs-crash-model`, crash-free first step as in `etcd-22340.md`: contracts for `os.Rename` and
  `fileutil.Fsync(dir)` over a ghost durable directory map. `OpenSnapshotBackend`'s spec returns
  only once `member/snap/db ↦durable newImage`. `applySnapshot` requires that fact before
  `SetBackend` (before any commit can save the snapshot's index into either file). The pin fails
  this; PR #22499/#22518 would meet it. The full restart statement needs crash semantics, a
  Perennial proposal first.

Cost: medium for the crash-free durability-ordering step (`OpenSnapshotBackend` is 9 lines, plus
the file-system axioms). The backend-swap step depends on `raft-pending-snapshot-ready` and is
large together with the store, lessor, auth and alarm restores.
