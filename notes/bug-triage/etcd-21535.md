# etcd-io/etcd#21535: experimental cache: data race with `store.Get` and `Apply`

<https://github.com/etcd-io/etcd/issues/21535>. Filed 2026-03-27 by upamanyus against `main`
(3.7.0-alpha.0), with a reproduction under `-race` (`TestStoreConcurrentGetApply`, fork commit
`8a3487332`). Closed 2026-03-30. Fixed by PR #21540 (commit `4f081fb1a`, merged as `3efe157f6`),
the same fix as #21536 (`etcd-21536.md`). The earlier PR #21537 was closed unmerged.

**The bug.** `store.getSnapshot(rev)` (`cache/store.go`) ran under `s.mu.RLock`. When no history
snapshot was at or above `rev`, it returned `&s.latest`, a pointer to the store's own mutable
working snapshot, and released the lock. `store.Get` then called `snapshot.Range` on that pointer,
which walks `s.latest.tree` (`btree.AscendGreaterOrEqual`) without the lock. Meanwhile
`store.Apply`, under the write lock, mutated the same tree in place (`applyEventsLocked` →
`ReplaceOrInsert`/`Delete`). The two goroutines raced on the B-tree's nodes, and `Cache.Get` and
the watch loop's `applyStorage` do run concurrently in `cache.go`. The fix makes `getSnapshot`
return only history snapshots, which are immutable clones (`newClonedSnapshot`), and return
`ErrCompacted` when there is none, so `&s.latest` never leaves the lock.

## Classification

**F+** (fixed before the verified code, and the spec excludes the buggy version). The fix
`3efe157f6` is an ancestor of the etcd pin `107edf7e4`. At the pin, `getSnapshot`
(`cache/store.go:74`) returns a history item or `nil`. The decisive fact: `store.getSnapshot.spec`
(`Spec/go_etcd_io/etcd/cache/v3/store__getSnapshot.lean:35-37`) returns `snapCert E p (r, m)`, and
`snapshot.Range.spec` (`.../snapshot__Range.lean`) requires `snapIs p h`. `snapIs`
(`InvStore.lean:706`) is persistent: `p ↦□ snapshot{rev, tree}` with a read-only
(`DFrac.discard`) B-tree. `&s.latest` cannot be given that. Its fields are written by `Apply`
(`latest.rev`), and its tree is owned exclusively, lent from `storeTreeInv` to the write-lock
holder (`InvStore.lean:32-34`, `storeTree_borrow`/`storeTree_return`). The buggy proof would have to
produce a discarded fraction of memory that the invariant still owns in full, and later writes
through. That is impossible in the separation logic, so the race is excluded by construction.

## The counterfactual (step 5)

Pre-fix, take `history = [(10, m10)]` and `latest.rev = 12`. That is reachable: `Restore` at 10,
then a progress notification at 12 (`applyProgressNotifyLocked`). A `Get(WithRev(11))` finds no
history item `≥ 11` and returns `&s.latest`. The postcondition's `match snapModel st 11` is
`.ok 10 m10`, which needs `snapCert E p (10, m10)` for `p = &s.latest`, so
`&s.latest ↦□ snapshot.mk 10 t` for a read-only tree `t`. The store's lock invariant holds
`latest.rev`'s points-to as a fraction that the writer later takes in full to write `12`, then
`13`, .... A persistent `↦□` of the same location is incompatible with that, so the proof fails at
the final `match` arm. This is the same step at which `etcd-21536.md` shows the wrong-snapshot
half of the bug failing. Even setting the value aside, the `Range` precondition `snapIs` needs a
discarded B-tree, and the latest tree's `ownBTree` lives exclusively in `storeTreeInv`. The
argument rests on ownership alone, not on how the model treats a racing access.

## Proposal

None (F+). Data-race freedom is a by-product of every proved spec here. The race class is excluded
wherever the code is verified.

## Findings

None: the bug is fixed at the pin. No `issues/` file, and no bug in this repository's specs.
