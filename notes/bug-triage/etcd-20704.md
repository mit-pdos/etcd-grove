# etcd-io/etcd#20704: Several correctness bugs in `client/v3/leasing` cache

<https://github.com/etcd-io/etcd/issues/20704>. Filed 2025-09-23 by upamanyus against `main`
(3.7.0-alpha.0, `d6f4ce3a9`). Closed 2025-11-30 by the stale bot, with no fix. Two
non-deterministic integration tests are on the fork (`upamanyus/etcd` `e11ce2ae7`,
`TestLeasingConcurrentPutGet`, `TestLeasingConcurrentPutDelete`).

**The report**: four ways the leasing KV's cached reads break the package's promise that it
"serves linearizable reads from a local cache" (`client/v3/leasing/doc.go:15`), all with
concurrent operations of one leasing KV on one key:

1. `Delete` + `Put`: etcd orders the delete after the put, but `cache.Update` runs after
   `cache.Delete` and re-creates the key. The cache stays wrong until eviction.
2. `Put` + `Get`: the put's `Commit` fails (a partition), `tryModifyOp` evicts the key and closes
   the waiter, and the waiting `Get` serves the old entry although the put may have committed.
3. `Put` + `Put` + `Get`: `Update` increments `Version` by one per response. When the responses
   arrive out of order, a `Get` in between sees a value/version pair etcd never had.
4. `Put` + `Put` + `Get`: the second `Lock` replaces the waiter channel. When the second put
   finishes first, a `Get` sees a closed channel while the first put, possibly committed later, is
   still in flight.

## Classification

**C-scope** (the buggy code is verified at the pin, the premises hold, and the spec admits all four
behaviors), with C-other for case 3's pair. All four are present at the pin `107edf7e4` and on
upstream `main`. The decisive fact: the leasing specs state each mechanism exactly, but they claim
freshness of a cached read only while the lease holder commits nothing.
`leasing_cached_get_stable` (`Proof/go_etcd_io/etcd/client/v3/leasing/Results.lean:180-187`)
requires `h.writer z ≠ e.lease` on `(e.rev, b]`, and in every case the holder, this client, has
written the key. Linearizability is proved for the uncached operations only (theorem 2). Cases 1
and 3 are already this repository's finding `issues/leasing-update-stale.md` (its cases 4 and 3,
proved as `leasing_update_out_of_order`). Cases 2 and 4 were not recorded and are now
`issues/leasing-get-inflight-write.md`, reproduced at the cache level by unit tests at the pin.

## The argument (step 4)

1. **The observations, as the specs see them.** In each case a `Get(k)` returns `getCached`
   (`InvLeasingKV.lean:414-417`): an entry `e` of a state `st` of the cache's log, `e` the key's
   entry or frozen, with `entryFacts` (etcd's record at `e.rev` is `e.acq`) and the answer
   `getResult o e`. The bad outcome is that `getResult o e` differs from etcd's record at every
   revision reached during the `Get`, while etcd has a later write of `k` by this client.
2. **Premises.** Single client, no other writer of `k`: `LeasingProtocol` holds. `Put`/`Delete`
   need `isCancelCtxCtx ctx` (met by the tests' contexts), and nothing restricts concurrent calls
   on one leasing KV (the `Get`, `Put` and `Delete` specs take shared reader slots). No A-pre.
3. **Assumptions.** Case 2 needs a `Commit` that errors after the transaction committed. The
   client contract (`txnCommitResult`) allows "some error" with an unknown outcome, which is true
   of the real client. No axiom is stronger than reality here. No A-model: the timing is ordinary
   concurrency, which the model covers.
4. **The postconditions allow each outcome.**
   - Case 1: `leasing_put`'s cache step is `st.modify key (e.update …)` whatever `del` did before.
     `LeaseEntry.update` (`InvLeaseCache.lean:173-181`) on `kvs = []` appends the fresh key-value.
     The spec derives the resurrected key.
   - Case 3: `leasing_update_out_of_order` (`Results.lean:220-226`) *proves* the intermediate
     pair `{version + 1, modRev := r2, value := v2}`.
   - Case 2: `leaseCache.Get.spec` (`Spec/.../leaseCache__Get.lean:41`) allows
     `(o.key, e) ∈ st.frozen`, an entry evicted while the `Get` waited. `tryModifyOp.spec`
     (`Spec/.../leasingKV__tryModifyOp.lean:33-48`) evicts and hands the channel back closed on
     error, with no claim about the outcome.
   - Case 4: `leaseCache.Lock.spec` (`Spec/.../leaseCache__Lock.lean:36-38`) gives each writer its
     own `waitcClose wc`. A `Get`'s wakeup on whichever channel it read promises nothing about
     the other writers.
   - What the user expected, "the answer is etcd's state at a revision reached during the call",
     follows only from `leasing_cached_get_stable` plus `e.kv = e.acq`
     (`leasing_getResult_acq`), and both hypotheses fail: the holder wrote (`hw` fails at the
     write's revision), and for cases 1 and 3 the cached key-value is no longer `e.acq`. The
     cached-read theorem was deliberately weakened when proved (STATUS, leasing units 3-4:
     "**Changed from the plan:** … holds only while this client has not written the key since
     acquiring it"). The weakening is exactly what lets these bugs through.

Reproduction at the pin (cases 2 and 4, at the cache level): `TestTriageGetServesEvictedEntry` and
`TestTriageGetIgnoresFirstWriter` in package `leasing` (described in
`issues/leasing-get-inflight-write.md`) both fail. Cases 1 and 3 have deterministic integration
tests on the fork branch `leasing-update-stale` (`issues/leasing-update-stale.md`).

## Proposal: `leasing-cached-read-own-writes`

Prove that a cached read is linearizable with respect to this client's own writes. This is the
half of `getCachedLin` (`etcd-19091.md`, `leasing-linearizable-with-clock`) that the clock does not
give:

```lean
-- a ghost per-key record of this client's writes in flight, owned by the cache invariant:
--   pending k : Nat   (incremented by Lock, decremented before each close)
-- and an invariant conjunct: if pending k = 0, the entry's cached record is etcd's record of k
--   at every revision since the holder's last write of k (no own write is in flight or unreflected)
theorem leasing_cached_get_fresh :
  getCached γ pfx key o ret ⊢ ∃ r s, etcdState r [] s ∗ etcdReached r ∗ ⌜lo ≤ r⌝ ∗
    ⌜e.kv = kvOf s key⌝   -- for the entry e served, under LeasingProtocol and an unexpired lease
```

It fails on the pin's code: case 2 (a frozen entry), case 4 (the replaced channel), case 1 and
case 3 (`Update` out of order). It needs the fixes of `issues/leasing-get-inflight-write.md` (a
re-check and a pending count) and of `issues/leasing-update-stale.md` (read the key in the put's
transaction, apply only newer responses). Cost: large. It needs a new ghost protocol tying each
write's commit (from the client contract's `opCommitted`) to the cache step that reflects it,
before the channel closes, plus re-proofs of `Lock`, `LockRange`, `LockWriteOps`, `Get`,
`tryModifyOp`, `put`, `delete`, `commitToCache` and the transaction path. The cross-client part
(other clients' writes revoke the lease first) is already `LeasingProtocol` and
`leasing_cached_get_stable`. Together with `leasing-linearizable-with-clock`, it gives the
package's documented promise.
