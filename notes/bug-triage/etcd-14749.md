# etcd-io/etcd#14749: ETCD-3.5.5: panic: failed to recover v3 backend from snapshot

- URL: https://github.com/etcd-io/etcd/issues/14749 (closed 2022-11-22; `type/bug`,
  `priority/important-soon`, `release/v3.5`).
- Affected: 3.5.5 (3.5.0-3.5.5; same root cause as #14382/#14569). The reporter's deployment ran a
  periodic `etcdctl defrag` that was killed together with the etcd process.
- Fix (maintainer diagnosis from the logs; the data directory was gone, so never confirmed on
  the reporter's data): PR #14730 "etcdserver: call the OnPreCommitUnsafe in unsafeCommit" (main,
  merge `0e4bf4ac4`, 2022-11-13), backported as #14733 (release-3.5, 3.5.6).

What goes wrong (pre-fix code): `batchTxBuffered.commit` ran the pre-commit hook
(`BackendHooks.OnPreCommitUnsafe`, which saves the consistent index and conf state) and then
`unsafeCommit`. `backend.defrag` called `unsafeCommit` directly, so a defragmentation committed
the applied entries' pending writes to bbolt **without** the matching consistent index. After a
crash in that window the persisted data is ahead of the persisted index. In the reporter's run the
WAL's last snapshot (index 5001) was above the stored consistent index. Bootstrap therefore took
the backend to be older than the snapshot and looked for `0000000000001389.snap.db` to recover from
(`snap/db.go: failed to find [SNAPSHOT-INDEX].snap.db`), which did not exist, and `NewServer`
panicked. Without the panic the same state means re-applying entries already in the db, so revisions
diverge from the other members ("revision inconsistency").

## Classification

**F (fixed before the verified code); counterfactual F− (O-fn, A-model).** The fix `0e4bf4ac4`
is an ancestor of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes). At the pin
`batchTxBuffered.unsafeCommit` itself runs the hook (`batch_tx.go:381-386`), and both defrag paths
call it (`backend.go:673`, `:765`). Counterfactually the existing proofs would also go through on
the buggy code. The hookless commit was reached only from `defrag`, which is not translated. The
verified `commit`/`unsafeCommit` specs do not require that a bbolt commit carry a freshly saved
consistent index. And the harm only shows after a crash, which is not modeled.

Source of verification states: `verified.txt` (`etc/verified-code.py`, this batch).

## The counterfactual (step 5)

Pre-fix, `unsafeCommit` would not run the hook; `commit` would run it before taking `readTx`'s
lock. The two would need specs where the hook's resource `Pk` passes from `commit` to the hook
call instead of through `unsafeCommit`. Which existing statement would break?

- `batchTxBuffered.unsafeCommit.spec` (`batchTxBuffered__unsafeCommit.lean:28-40`) and
  `batchTx.commit.spec` (`batchTx__commit.lean:27-35`) describe the commit's effect on the
  session's data (`ownDB db γ.db st.S`). Their preconditions (`freeOk`, `hookPre`, `hookStep`,
  `Model2.lean:219-221,290-302`) constrain the buffers and the hook's window flag `cnt.hw`. They
  do not require that the hook ran in the interval being committed. A hookless `unsafeCommit`
  keeps them: `hookStep_refl` (`CommitLemmas.lean:202`) is exactly the hookless case.
- The consistent-index protocol (`InvApply.lean`) gets `commitOk s m` (`:466`: `eff ≤ m ≤ p`, no
  processed-but-unsaved writes below the saved index `m`) **at a save**, from `commit_save_au`
  (`:472`), used only by the hook (`CindexBackend.lean:603`). Nothing ties `commitOk` to every bbolt
  commit: no invariant relates the bucket data committed (`ownDB … st.C`) to the meta key's index.
  So a commit that skips the save is not excluded. Contrast etcd#13766 (F+): there the buggy
  `SetConsistentIndex` broke `stOk` itself. Here the protocol is untouched and a commit
  simply does not consult it.
- `defrag` is not translated, so the one caller that skipped the hook has no proof to fail.

So the buggy code meets the specs: **F−**. Two gaps let it through. **O-fn**: defrag is
unverified. **A-model**: the property violated, "what is on disk after a crash is a consistent
(data, consistent index) pair", is about crashes. A safety stand-in without crashes is
possible: see the proposal.

## Proposal: `backend-commit-saves-ci`

State "every bbolt commit persists a consistent pair" per commit, as `commitOk` is per save:

```lean
-- batchTx.commit.spec gains, in its precondition, the hook's receipt for this interval:
--   ciSaved γA st  :=  ∃ s m, ⌜commitOk s m⌝ ∗ metaKeyIn st.S m ∗ ⌜kvEffectsUpTo st.S m⌝
-- produced only by `commit_save_au` (the hook), consumed by the bbolt commit.
theorem batchTx.commit.spec' : … {{ … ∗ ciSaved γA st }} t.commit(stop) {{ … ∗ persistedOk γA st.S }}
```

`persistedOk γA D` holds when the committed data `D` holds the effects of exactly the entries ≤ its
meta key's index. A hookless commit has no `ciSaved` and fails. Discharging it
needs the receipt threaded from the hook (at the pin `unsafeCommit` runs it: small) and `defrag`
translated (`defragBlocking`/`defragNonBlocking` and `defragdb*`, ~350 Go lines with bbolt as
trust boundary: medium). With `crash-restart-model` the receipt becomes the crash invariant. Cost:
small (receipt, through `unsafeCommit`/`commit` and the hook's proof) plus medium (defrag).
