# etcd-io/etcd#20009: 3.6.0 fails to start with `--force-new-cluster` on reused storage (nil pointer)

- URL: https://github.com/etcd-io/etcd/issues/20009 (closed 2025-07-17; labels `type/bug`,
  `area/raft`, `priority/critical-urgent`, `release/v3.4`–`v3.6`)
- Affected: 3.6.0 (the panic). The commit-index half affects 3.4, 3.5, 3.6 and `main`.
- Fixes (both ancestors of the etcd pin `107edf7e4`, `git merge-base --is-ancestor`: yes):
  - PR #20055 (merge `f23c9d7fd`, commit `ec416efcc`): with `--force-new-cluster`, bootstrap sets
    `HardState.Commit = max(Commit, consistent_index)` before discarding "uncommitted" entries
    (`server/etcdserver/bootstrap.go:612-624` at the pin).
  - PR #20026 (merge `929ac02db`, commit `69f0771c8`): `RaftCluster.PromoteMember` and
    `UpdateRaftAttributes` skip the v2store update of a member that is not in `c.members`.
- Related: etcd-io/raft#300 (closed, unmerged), "`MustSync` should return true if
  `HardState.Commit` differs". Our finding `issues/raft-commit-lost-with-entries-kept.md` has the
  same root cause.

What goes wrong (the maintainer's diagnosis, two causes).
1. *Commit index not durable.* raft's `MustSync` asks for a sync only when there are entries or the
   term or vote changed. A `Ready` that only advances `HardState.Commit` is written without fsync,
   or not at all. Its committed entries are still applied, and the backend's consistent index
   (fsynced by bolt) moves past the WAL's `Commit`. `--force-new-cluster` keeps only the WAL's
   committed entries (`CommitedEntries()`) and appends `RemoveNode` entries for the other members.
   Applied entries (here a member addition/promotion) are dropped, and the forced removals do not
   match the membership the db has.
2. *v2/v3 membership disagree during replay (3.6).* 3.6 bootstraps `c.members` from the v3 backend
   (the latest state) but replays WAL entries at or below the consistent index against the v2
   store (`shouldApplyV3 = false`). `PromoteMember` dereferenced `c.members[id]` unconditionally
   (`m := *(c.members[id])`). A replayed promotion of a member the v3 state no longer has panics:
   the reported nil pointer, in job `server_applyAll`.

## Classification

**F (fixed before the verified code); counterfactual F−, gaps A-axiom (the panic) and O-fn +
A-model (the commit index).** The panic is reached from the *verified* apply loop (`applyAll` →
`applyEntries` → `apply`), but through `EtcdServer.applyConfChange`, a trust-boundary axiom. That
axiom promises a return for any change, with or without `v3`. On the pre-fix membership code it
would have been false, so the loop's proof would have gone through anyway. The commit-index half
lives in the untranslated bootstrap and needs a crash (lost `HardState`) to happen.

Source of verification states: `verified.txt` (`etc/verified-code.py`, at `d606c9cac`).

## The counterfactual (step 5)

**The panic (cause 2).** `EtcdServer.applyConfChange.spec` takes `ownCCV1 cc … m`, the
confState cell, the hook/advance triples when `v3`, and `Pre`. It has no premise about the
cluster's members or about `cc`'s content, and for `v3 = false` it returns `Pre`
(`EtcdServer__applyConfChange.lean`, the `RET (PairV #removed #err)` post). On the pre-fix code,
a replay (`v3 = false`) of an `AddNode` entry with `IsPromote` for a member missing from
`c.members` panics in `PromoteMember`. The postulated triple is false for that input.
`apply.spec` and `applyAll.spec` consume the axiom as stated, so their proofs would not have
noticed: **F−, by A-axiom.** At the pin the v2store update is gone from these methods (later
refactors), and `PromoteMember`/`UpdateRaftAttributes` touch `c.members[id]` only under
`ok` (`membership/cluster.go:498-533`). So the axiom is consistent with the pin, but only
because of that code (and because every `lg.Panic` in `applyConfChange`, `server.go:2002-2075`,
is on malformed entries that etcd does not propose). The axiom's statement records neither
fact. Whether a `v3 = false` conf
entry is reachable in the verified scope at all is a separate question: the server starts from a
backend at `γr.kv.c0` and replays entries `≤ c0`
(`applyEntryNormal`'s `v3 = decide (c0 < m.index)`). But no restart from a WAL is modeled, so in
practice the replay case is vacuous today.

**The commit index (cause 1).** `MustSync.spec` states exactly the behavior at fault: it returns
`decide (n ≠ 0 ∨ Vote ≠ Vote' ∨ Term ≠ Term')`, so a commit-only change needs no sync
(`Spec/go_etcd_io/raft/v3/MustSync.lean`). The server's `Save` contract is `True → True`, and no
statement relates the durable `HardState.Commit` to the consistent index (STATUS "Out of scope for
now": no stable vs. volatile state). The bootstrap that trusts the WAL's `Commit` is not
translated. **F−, gaps O-fn (bootstrap) and A-model (durability).** This is the same gap as
`issues/raft-commit-lost-with-entries-kept.md`, seen from the etcd side.

## Proposals

- **`verify-apply-conf-change` (new):** prove `EtcdServer.applyConfChange` (63 lines, now an axiom)
  and the membership methods it calls: `ValidateConfigurationChange`,
  `AddMember`/`RemoveMember`/`PromoteMember`/`UpdateRaftAttributes`, about 200 lines in
  `membership/cluster.go`, now untranslated. Use a pure membership model with its v2 and v3 views
  and the backend writes under the batch lock (the axiom's `Post ∨ Adv`). Statement: the present
  spec, with the premise "`v3 = true` → `cc` passes or fails validation against the v3 view;
  `v3 = false` → any `cc` well formed by `ConfigChangeContext`" and no premise on the v2 view. On
  the pre-fix code the `v3 = false` promotion branch fails (nil deref), so the bug class becomes
  F+. Cost: medium (the membership store's backend helpers `MustSaveMemberToBackend` etc. become
  trust-boundary axioms over the v3 view). It also yields the "transport peer set" half of
  `transport-tracks-confstate`.
- **`crash-restart-model` (existing),** for cause 1: the restart invariant "every entry at or
  below the durable consistent index is durable and committed", with bootstrap's
  `Commit := max(HardState.Commit, ci)` (`bootstrap.go:624`) proved to re-establish
  `committed ≥ ci`. A crash-free first step: give `isRNWal`'s `Save` a durable-state ghost
  (`raft-durable-acks`) and state, at each backend commit, `ci ≤` the largest index whose entry is
  durable. That is true at the pin, since entries are saved before they are applied. Without the
  `max`, the force-new-cluster path would then visibly lose an entry. Cost: large overall
  (crash semantics in Perennial).

## Findings

None new: both causes are fixed at the pin. Suggested link for
`issues/raft-commit-lost-with-entries-kept.md`: etcd-io/etcd#20009 (same root cause, a
force-new-cluster symptom, fixed on the etcd side by #20055). No bug in this repository's specs.
One trust-base remark: `EtcdServer.applyConfChange.wp_proof` holds at the pin only because the
membership methods check `c.members[id]`, which its statement does not mention. The axiom is
not false at the pin.
