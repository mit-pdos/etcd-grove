# etcd-io/etcd#20269: etcd panic on member rejoin after reset: tocommit(...) is out of range [lastIndex(...)]

- URL: https://github.com/etcd-io/etcd/issues/20269 (closed 2026-01-21, completed, by serathius;
  `type/bug`, `stale`). Continued as #21178 (`etcd-21178.md`).
- Affected: 3.5.21. The code is unchanged on `main`.
- Fix: none. silentred's diagnosis: if the data (WAL, snap) is lost, the member must be removed and
  re-added with `member add`; restarting it is "supposed to panic".

What goes wrong: a learner's binary is renamed (simulated failure), its data directory is wiped, and
the operator "re-adds" it. The restarted process, with an empty log, receives `MsgHeartbeat` at term
18 with `Commit = 10563786`, and `raftLog.commitTo` panics (`tocommit(10563786) is out of range
[lastIndex(0)]`; the stack runs through `node.run` from `RestartNode`, `stepFollower`,
`handleHeartbeat`). Later the reporter says the flow was `member remove` and then `member add` with
a fresh name.

## Classification

**A-model (secondary O-path; N upstream: closed as operator error).** Same mechanism as `etcd-21178.md`
and `raft-197.md`. A heartbeat's commit is `min(pr.Match, committed)`. `Match` starts at 0 for a
new leader term and for a newly added ID, and rises only on that ID's own `MsgAppResp`. So the member
ID the process runs under had acknowledged index ≥ 10563786 in term 18, and the process has lost
that log. The member list confirms the identity reuse: the learner `bf4c5f14c328e1d3` is `started`
with the name `4554913594194925-2213`, while the panicking process is configured as `...-2229`. etcd's
join path assigns the local ID by peer URL (`ValidateClusterAndAssignIDs`, `membership/cluster.go:755`
at the etcd pin), so the wiped process took over the old learner's ID, which was not actually
removed. The log line "restarting local member" with `RestartNode` fits a second start: the first
start after the wipe created a WAL with that ID's metadata and then panicked the same way.

The raft spec excludes the panic: `raftLog__commitTo.lean:46` has the premise `tocommit ≤
lastIndex`, discharged in `raft__Step.lean:204` by `heartbeat_commit_le_last` from the receiver's
`isAcked`. That holds only for a node whose ghost started from `rnInit`, which cannot be produced
again for an ID that has already run. The model has no crashes and no stable state, so losing the
data directory under a kept ID is outside it. etcd's join and restart path (`bootstrapExistingClusterNoWAL`,
`bootstrapClusterWithWAL`, `newRaftNode`'s `RestartNode` branch) is not verified (O-path). Full
argument and code-path table: `etcd-21178.md`.

Source: `verified.txt` (scratchpad inventory at `d606c9cac`).

## Proposal

`raft-durable-acks` → `crash-restart-model` (as raft#197) and `join-fresh-identity` (see
`etcd-21178.md`). The latter would state, as a premise of etcd's join path, the rule silentred gives:
each member ID is started from an empty data directory at most once.
