# etcd-io/etcd#14571: 3.5.5: client auth failures on new member first startup

- URL: https://github.com/etcd-io/etcd/issues/14571 (closed 2022-10-27; labels `type/bug`,
  `area/auth`, `priority/important-soon`)
- Affected: v3.5.5 (a regression from 3.5.4, brought by the 3.5 backport #14227 of the eagerly
  refreshed, `RWMutex`-guarded permission cache), also 3.4. Fixed by PR #14574 (commit
  `fbed8cb64`, merge `1570dc9c4`, 2022-10-27; backports in 3.4.22 and 3.5.6). Same root cause as
  #14355 (restart, fixed by #14358, `NewAuthStore` refreshes the cache) and #13883 (the same
  `Recover` gap, reported earlier, `etcd-13883.md`).

What goes wrong (pre-fix code): `authStore.Recover(be)` (`server/auth/store.go`), which
`EtcdServer.applySnapshot` calls after it installs a snapshot's backend, reloaded `enabled` and
`revision` but did not call `refreshRangePermCache`. A new member that joins by snapshot
therefore has auth enabled with an empty `rangePermCache`. Every permission check of a non-root
user goes to `isRangeOpPermitted`, misses the user in the map ("user doesn't exist") and returns
`false`. So `authApplierV3.Put`/`Txn`/... reject entries that the other members apply. The
new member's KV diverges from the cluster's (the maintainers confirmed the data inconsistency),
and its API layer refuses the reads too. A restart (`NewAuthStore` refreshes the cache since
#14358) clears the symptom but not the divergence.

## Classification

**F (fixed before the verified code); counterfactual F−, gap O-fn and C-other.** The fix
`fbed8cb64` is an ancestor of the etcd pin `107edf7e4`. At the pin, `Recover` calls
`as.refreshRangePermCache(tx)` (`store.go:396-411`). Counterfactually the specs **admit** the
buggy version, for three independent reasons:

- `Recover`, `refreshRangePermCache` and `getMergedPerms` are not translated;
- `EtcdServer.applySnapshot.spec` covers only `ap.snapshot = nil`;
- even with them verified, the auth layer's decision is a free choice in the apply model: no
  invariant ties the cache to the backend's users and roles.

Source of verification states: the inventory
`/tmp/claude-0/-shared-etcd-grove/c22270a5-a99f-4bfe-8204-a0d29e5800a4/scratchpad/verified.txt`.

## The counterfactual (step 5)

Take the pre-fix `Recover` (no `refreshRangePermCache`), so the cache is empty while auth is
enabled.

- The permission checks' specs say nothing about the permission.
  `authStore.isRangeOpPermitted.spec` returns "some boolean" (`(b : Bool), RET #b; cacheRd st ∗
  …`). `isOpPermitted.spec` returns `authErrIs err`, which is nil or one of the package's errors.
  The cache's guard `cacheP` (`Proof/.../auth/InvAuth.lean`, `def cacheP`) holds only that each
  entry is `permsOk` (two queryable trees). Nothing relates the map to the backend's users and
  roles. An empty map meets it, so the store's specs hold of the buggy code.
- The apply model makes the auth layer's rejection a free choice: `chainStep`'s `.auth` case is
  `(authMayReject on rq ∧ o = .rejected .auth) ∨ chainStep B c rq log o`
  (`Proof/.../etcdserver/apply/Chain.lean:174-177`), and `authMayReject on rq` holds whenever
  auth is enabled (`:158`). The same choice appears in the batch result:
  `alarmPut … := … o = .rejected .auth ∨ ∃ o', putModel op log o' ∧ …`
  (`apply/Results.lean:85-88`), used by `applyEntries_kv`. So "every member applies the same
  entry with the same outcome" is not a consequence of the results. A member rejecting what the
  others commit is a run the specs allow.
- The snapshot branch where the bug lives is outside every spec anyway
  (`applySnapshot.spec`: `ap.snapshot = nil`, raft's contract `rnApP` in this proof).

Hence F−. The gap is of two kinds: **O-fn** (the admin side of the auth store and the snapshot
install are unverified) and **C-other** (the auth decision is unconstrained, so cross-member
determinism of apply does not cover auth-enabled clusters).

## Proposal: `auth-state-model` (new)

Model the auth store's state as a pure record and make the auth layer's outcome a function of it:

```lean
structure AuthState where
  enabled : Bool
  rev     : Nat
  users   : GMap GoString (List GoString)                  -- user ↦ roles
  roles   : GMap GoString (List Perm)                      -- role ↦ permissions
def permitted (σ : AuthState) (user : GoString) (k e : List w8) (pt : PermType) : Prop := …
-- chainStep's auth case: o = .rejected .auth ↔ σ.enabled ∧ ¬ permitted σ info.user … ∨ info.rev < σ.rev
-- cacheP st q σ: the map's entries are exactly the merged permissions of σ.users/σ.roles
```

Then prove that `refreshRangePermCache` establishes `cacheP … σ` from the backend's auth buckets
(`σ = authOf bucket`), and that `NewAuthStore`, `Recover` and each admin method
(`UserAdd`…`RoleRevokePermission`, `AuthEnable`/`Disable`) keep it. With the snapshot case of
`applySnapshot` (`Recover` given the snapshot backend's `σ`), the apply results then carry
`σ` in `ApplyKV`. Two members with equal `(x, σ, c)` then end equal. The buggy `Recover` breaks
`cacheP … σ` at its return (empty map, `σ.users ≠ ∅`).
Cost: large. It needs about 600 untranslated lines of `store.go` (the admin side) and
`range_perm_cache.go` (`getMergedPerms`, 39 lines). `authpb.User`/`Role` are axiomatized types
today, so they need translating, and so do the bytes-affine interval trees (`adt.ownIvt` covers
string-affine intervals). It also needs the snapshot branch of `applySnapshot`, shared with
`mvcc-restore-from-backend`. It would have caught #14571, #13883 and #14355, and it is the auth
half of the cross-member determinism that `etcd-20451.md` relies on.

## Findings

None new: the bug is not in the pinned code. No bug in this repository's specs. A side
correction to an earlier report: `etcd-20451.md` says KV entries are applied deterministically,
"rejected by the same admin checks". With auth enabled that does not follow from the results.
`alarmPut`/`alarmDelete`/`alarmTxn` and the `.rejected` admin outcome are free choices, so two
members with equal `(x, c)` may differ by auth decisions in the model.
