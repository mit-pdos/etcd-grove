# etcd-io/etcd#20059: etcd data inconsistency in 3.5.11

- URL: https://github.com/etcd-io/etcd/issues/20059 (closed 2025-08-07 as stale; labels
  `type/bug`, `stale`).
- Affected: v3.5.11 on arm64 (Kubernetes static pods). Very rare, by the reporter's account.
- Fix: none. serathius: "That's data corruption, there is not much we can do … other than
  restoring this member", and "WAL might be missing some safety checks".

What was observed: a `kubectl get cm` returned different contents depending on the member, and the
etcd data on node 2 differed from its peers'. Before that, node 2's process died with
`unexpected fault address 0xc00000000` / `SIGSEGV` inside `raftpb.(*ConfState).Size`, called from
`(*Snapshot).Size` ← `(*Message).Size` ← `rafthttp.(*streamReader).decodeLoop`
(`stream.go:503`). That is a wild pointer in a message the member was decoding off the peer
stream, while it was creating a new WAL segment every few seconds. On restart its initial
corruption check logged `found different compact revision values from remote peer` (local
compaction revision 3242299756, the peers' 3242320888) and then `initial corruption checking
passed`. The reporter's follow-up point: `InitialCheck` counts a hash mismatch only when the
compaction revisions are equal (`server/etcdserver/corrupt.go:118-124` at the pin, unchanged), so
it does not stop a diverged member whose compaction revision differs.

## Classification

**A-model (diagnosis unsettled): the one hard fact is a memory fault in the process (a corrupt
pointer in a decoded raft message), and the proofs assume reliable memory and a correct runtime;
secondary O-pkg (the faulting code is `rafthttp`, not translated; the corruption check,
`corrupt.go`, is not translated) and N (the check's behavior is by design).** Whatever corrupted
node 2's state, its path does not go through a verified function behaving against its spec.
Nothing in the report shows etcd's code writing wrong data under the model's assumptions, so it is
not X. The `InitialCheck` complaint is a limit of a heuristic detector, not a wrong result. Hashes
at different compaction revisions are not comparable: the peer hashes from its own
`compactMainRev`, and the restarted member had not yet applied the later compaction. The
compaction-hash check (`CompactHashCheck`, `corrupt.go:277`, not enabled by default in 3.5)
exists to compare hashes at matching compaction revisions.

Source of verification states: `verified.txt` (`etc/verified-code.py`, at `d606c9cac`).

## The argument (step 4)

The apply results (`applyEntries_model`, `Proof/.../etcdserver/Results.lean:156-160`;
`applied_log_at`, `:181`) make the KV state a function of the applied committed entries. Raft's
results make committed entries agree across members. Two members at the same applied index with
different data are therefore outside the specs, *given* the model's assumptions. Those include a
heap that only the program writes (Perennial's semantics: no stray writes, no bit flips) and
storage that returns what was written (the bbolt postulates, `Spec/go_etcd_io/bbolt/*_kv.lean`;
and no crash). The report's fault at address `0xc00000000` is a pointer that no Go program writes
without `unsafe` or a runtime bug. The likely sources are hardware (memory) or a corrupted byte
slice handed to the decoder, and either breaks the memory assumption. A corrupt decoded message
that did *not* fault could equally have reached raft and the apply path as valid data. Messages
from the network are inputs that raft's `Step` spec takes as well-formed. So this is A-model, with
`rafthttp` (O-pkg) as where the fault surfaced. serathius's remark about the WAL does not match
the stack: the fault is in a network decode, not in WAL reading.

For the detector: with no translation of `corrupt.go`, nothing here states what `InitialCheck`
guarantees. It would be a spec of the form "returns an error if some peer's hash at the same
`(rev, compactRev)` differs" (exactly what the code does). That does not cover the reporter's case
and should not: unequal compaction revisions make the hashes incomparable.

## Proposal: `model-kv-hash` (existing; the detector side only)

Memory corruption itself is outside any software proof; no verification here would exclude it.
What verification can give is a precise statement of what the corruption checks detect.
`model-kv-hash` makes `HashByRev` return `crc (kvHashIn log c rev)`. On top of it, translating
`corrupt.go`'s `InitialCheck`/`checkPeerHashes` (~200 lines, the peer RPCs as a trust boundary)
gives `InitialCheck` returning `nil` ⇒ every peer that answered with the same compaction revision
has the same `kvHashIn` crc. That states in the spec the reporter's point that a differing
compaction revision is inconclusive, and gives `CompactHashCheck` the matching-revision guarantee.
Small to medium on top of `model-kv-hash`; low priority, since it hardens a detector rather than
the code.
