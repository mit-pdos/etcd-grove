# etcd-io/etcd#20133: Panic "failed to open snapshot backend" when multiple snapshots are received in short time

- URL: https://github.com/etcd-io/etcd/issues/20133 (closed 2025-06-06 by its author as a
  duplicate of #18055; `type/bug`).
- Affected: main at `3be967f` (3.7.0-alpha.0), basic 3-node cluster, **default** configuration
  (`snapshot-count` 10000). Found by Antithesis ("No Panics"). The follower received snapshots
  `0x89` (137) and `0x8b` (139). Releasing 139 deleted `0000000000000089.snap.db` before
  `applySnapshot(137)` opened it.
- Fix: none merged (see #18055: PR #22046 open).

## Classification

**A-pre (duplicate of etcd#18055; secondary O-fn).** It is the same race between
`raftNode.start`'s `storage.Release` (`raft.go:281` at the pin) and `applySnapshot`'s
`OpenSnapshotBackend` (`server.go:1048`). It is present at the pin, in code verified only under
the premise that a `Ready` carries no snapshot (`rnReadyData`,
`Proof/go_etcd_io/etcd/server/v3/etcdserver/InvRaftNode.lean:190`;
`EtcdServer__applySnapshot.lean:30`). The argument is in `notes/bug-triage/etcd-18055.md`.
This report adds one fact: the race needs no unusual configuration, so the premise is
violated in default deployments whenever a follower lags past the leader's compaction.

Source of verification states: `verified.txt` (this batch).

## Proposal

`server-apply-snapshot` (as etcd#18055).
