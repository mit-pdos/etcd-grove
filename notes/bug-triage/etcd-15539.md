# etcd-io/etcd#15539: `EtcdError` is missing `GRPCStatus`, so `status.FromError` always returns `codes.Unknown`

- URL: https://github.com/etcd-io/etcd/issues/15539 (closed 2025-06-21 by the stale bot; labels
  `type/bug`, `stage/tracked`)
- Affected: etcd 3.4, 3.5, `main`. Still present at the pin `107edf7e4`.
- Fix: none. PR etcd-io/etcd#15540 ("v3rpc/rpctypes: added GRPCStatus for EtcdError", with unit and
  integration tests) was closed unmerged. No commit in the pin.

What goes wrong: `rpctypes.EtcdError` (`api/v3rpc/rpctypes/error.go:241-254`) has `Code()` and
`Error()` but no `GRPCStatus()`. Every client error that `ContextError` (`client/v3/client.go:606`)
converts through `rpctypes.Error` therefore loses its gRPC status: `status.FromError` gives
`codes.Unknown`. On a client with a user name and password, the stream interceptor calls
`c.getToken(ctx)` before opening any stream (`retry_interceptor.go:118`). `getToken` → `c.Auth.
Authenticate` returns `ContextError(ctx, err)` (`auth.go:138`). So a transient
`ErrGRPCLeaderChanged`/`ErrGRPCNoLeader` (code `Unavailable`) reaches `watchGRPCStream.
openWatchClient` (`watch.go:1057-1061`) as an `EtcdError` of code `Unknown`. `isHaltErr`
(`client.go:570`) returns `true`, and the watch stream gives up instead of retrying: every watcher
of the stream is closed with the error. The same loss makes `isUnavailableErr` false (no backoff)
and makes the gRPC Prometheus interceptor count `Unknown`.

**Reproduced at the pin** (2026-10-16): a test in package `clientv3`,
`isHaltErr(ctx, ContextError(ctx, rpctypes.ErrGRPCLeaderChanged))` is `true` (the error is
`rpctypes.EtcdError`, `status.Code` `Unknown`), while `isHaltErr(ctx, rpctypes.ErrGRPCLeaderChanged)`
is `false`. Test in `issues/etcd-client-etcderror-no-grpcstatus.md`.

## Classification

**C-err (the spec allows giving up on any error); secondary O-fn.** The halting decision is
verified, but its specs are stated over an *opaque* status code. `isHaltErr.spec`
(`Spec/go_etcd_io/etcd/client/v3/isHaltErr.lean`) says only `b = false → err = nil ∨ statusCode
err ∈ {14, 13}`. `statusCode` is `opaque` (`Spec/google_golang_org/grpc/status/FromError.lean:31`),
so nothing relates an `EtcdError`'s code to the status `FromError` reads. `openWatchClient.spec`
allows "a `nil` stream and an error … `rpctypes.Error` of a halting one". The watch client's result
lets the stream end with its close error. The step that loses the code, `getToken` inside
`streamClientInterceptor`, is not translated (O-fn), and `getToken`'s verified spec
(`Client__getToken.lean`) says only `clientErrOk err` (an `EtcdError`, status accepted).

## The argument (step 4)

1. Observed: the stream's `openWatchClient` calls `remote.Watch`. The interceptor's `getToken` fails
   with `EtcdError{code: Unavailable, desc: "etcdserver: leader changed"}`. `isHaltErr` returns
   `true`, `openWatchClient` returns `(nil, v3rpc.Error(err))`, and `run` closes every substream
   with that error. The user's watch channel closes although the cluster recovers in milliseconds.
2. Premises: `noRetryableStreamErr` (`Proof/.../client/v3/InvWatch.lean:163-171`) is about the
   stream's `Recv` errors and `io.EOF`, not the error from opening the stream, so it does not
   exclude this. It does show the scope, though: the watch is verified for a stream that never
   reconnects, so "every error halts" is inside the verified behavior.
3. Postcondition: `isHaltErr.spec` has only the implication `false → code ∈ {14,13}`. Returning
   `true` for an error whose real code is `Unavailable` meets it, and because `statusCode` is
   opaque the spec could not say otherwise. `openWatchClient`'s error disjunct is
   `⌜ws = nil ∧ err ≠ nil⌝ ∗ statusErrOk err`, which is met. The run is admitted: the specs say
   *how* the client halts, never that it halts *only* on a permanent error. What the user expected
   is P: "a watch is not closed for a transient (`Unavailable`) server condition while its context
   is live". That is a liveness-flavored property, and its safety core is about error codes, which
   the model abstracts.

## Proposal: `client-error-status-codes`

Make the status code of etcd's client errors part of the model, then state that the watch halts
only on a non-retryable code:

```lean
-- rpctypes: an EtcdError's status, as grpc computes it (no GRPCStatus method: Unknown)
theorem statusCode_etcdError (c : w32) (d : GoString) :
  statusCode (interface.mkOk EtcdError.ty (EtcdError.mk c d)) = codes.Unknown   -- at the pin
-- openWatchClient: an error return is the context's, or carries the server's halting code
… ∨ (⌜ws = nil ∧ err ≠ nil⌝ ∗ (ctxDone cd ∨ ∃ e₀, serverErr e₀ ∗ ⌜haltCode (statusCode e₀) ∧ err = v3rpc.Error e₀⌝))
```

Here `statusCode` is refined from opaque to "`GRPCStatus()`'s code if the type has the method,
else `Unknown`" (true of grpc). Proving it needs `streamClientInterceptor` translated (34 lines)
with `getToken`'s spec keeping the code (`clientErr` carrying `statusCode err = code of the server's
error`). That conjunct fails at the pin, because `EtcdError` has no `GRPCStatus`, and holds with
#15540's method. Cost: small to medium (the `statusCode` refinement is a change to a trust-boundary
spec here, not to Perennial; the stream interceptor; re-proving `openWatchClient`, `isHaltErr`,
`isUnavailableErr`). A full fix of the watch's reconnection (dropping `noRetryableStreamErr`) is
the larger related direction (`issues/etcd-watch-resume-closing-substream.md`).
