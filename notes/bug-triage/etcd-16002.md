# etcd-io/etcd#16002: a new member with a wrong member ID panics every member ("failed to update; member unknown")

- URL: https://github.com/etcd-io/etcd/issues/16002 (closed 2025-06-11 as not planned, by the
  stale bot; labels `type/bug`, `area/raft`, `stale`). No fix, PR or commit.
- Affected: reported on 3.5.3 ("seen in other versions as well"). The code is unchanged at the
  etcd pin `107edf7e4` (checked below).

What goes wrong. A member is added (`member add`), then started with `--initial-cluster-state
existing`. At startup, `bootstrapExistingClusterNoWAL` (`server/etcdserver/bootstrap.go:343`)
builds the cluster from `--initial-cluster` and calls `membership.ValidateClusterAndAssignIDs`
(`api/membership/cluster.go:755`), which copies each existing member's ID onto the local member
whose peer URLs are "equal" by `netutil.URLStringsEqual`, which resolves host names. If DNS
resolves the new member's host to an existing member's address, the matching is ambiguous and
the new member's local entry can keep an ID the cluster never added. The new member then
publishes its attributes under that ID (`publishV3`, `server.go:1793`: a
`ClusterMemberAttrSet` with `Member_ID = s.MemberID()`). Nothing checks the ID before the entry is
proposed or committed. Every member applies it: `uberApplier.dispatch` →
`applierV3backend.ClusterMemberAttrSet` (`apply/backend.go:287`) →
`RaftCluster.UpdateAttributes` (`cluster.go:467`). That function panics with `lg.Panic("failed to
update; member unknown")` (`cluster.go:482`) when the ID is neither a member nor removed. The entry
is committed, so every member panics again on every restart (the reported crash loop).

## Classification

**A-axiom (secondary O-fn).** The panic is reached from the *verified* apply chain, through the
contract that the apply package assumes for the names-only `*membership.RaftCluster`. In
`isCluster` (`Proof/go_etcd_io/etcd/server/v3/etcdserver/apply/Contracts.lean:323-347`),
`UpdateAttributes` returns for **every** `id` (`{{ cPre b P f Pre Q Post }} c.UpdateAttributes(id,
attr, b) {{ RET #(); cPost b Pre Post }}`, lines 339-343). A `RET` triple excludes panics
(Perennial's `PERENNIAL_PROOF_REFERENCE.md`, "Panics"). The real method panics for an unknown ID,
**at the pin**, so the contract is false. The cause upstream of it, the ID assignment in
`ValidateClusterAndAssignIDs` and bootstrap, is not translated (O-fn).

**This is a bug in this repository's trust base**, not only a triage result. `isCluster` is a
premise of the apply package's specs and, through `backendOptsOk` (`apply/Chain.lean:740`) and
`applierFor`, of the server's end-to-end apply results (`etcdserver/Results.lean:12-15`, "the
components' contracts"). The real cluster object does not satisfy it. The results are conditional
on a hypothesis that the real code does not meet, so they say nothing about any execution that
commits a `ClusterMemberAttrSet` for an unknown ID. The analogous `SetVersion` panic is handled the
right way: a premise on the entry (`rqOk`'s `clusterVersionSet → semverValid`,
`apply/Chain.lean:244-252`). `UpdateAttributes` has no such premise. Compare the `applyConfChange`
axiom (`etcd-20009.md`), which was false on 3.6.0 and is true at the pin; this one is false at
the pin.

Reproduced at the pin (a unit test of the membership package, `go test`, passes: the call
panics). See `issues/etcd-membership-attrset-unknown-member-panic.md`.

## The argument (step 4)

1. Observed: a committed normal entry whose request is `ClusterMemberAttrSet{Member_ID = x}`, with
   `x ∉ c.members ∪ c.removed`, applied with `shouldApplyV3 = true` (or `false` on replay). The
   outcome is a panic in the apply goroutine.
2. Premises. `rqOk` (`apply/Chain.lean:244`) is `True` for this request kind (the `_` case), so no
   premise on the entry excludes it. The entry decodes and has an ID (`entriesOk`), so it meets
   the server's KV premises.
3. Assumption. `applierV3backend.ClusterMemberAttrSet.spec` is proved from `isCluster`'s
   `UpdateAttributes` triple (`Proof/.../apply/applierV3backend__ClusterMemberAttrSet.lean:39`,
   `iunfold apply.isCluster at Hc`). That triple promises a return for any `id`. The Go method
   (`cluster.go:467-493`) returns only if `id ∈ c.members` or `id ∈ c.removed`, and panics
   otherwise. The test below makes it panic at the pin. So the assumption is false: **A-axiom**.
4. With a true contract (one that requires `id` known), the proof of `ClusterMemberAttrSet` would
   need that fact from `dispatch`'s caller. The server could not supply it: `publishV3` sends any
   `s.MemberID()`, and nothing ties a committed `Member_ID` to the applied membership. That missing
   premise is exactly this bug.

The reachability needs an ambiguous URL match (misconfigured or hostile DNS). The upstream thread
did not diagnose it further. The panic itself depends on nothing more than the committed ID.

## Proposal

Slug **`cluster-attrset-known-member`**.
- *Fix the trust base* (small): parameterize `isCluster` by a ghost set `K` of known IDs
  (`members ∪ removed`), require `id ∈ K` in the `UpdateAttributes` triple, and add a `rqOk` case
  `clusterMemberAttrSet → memberID ∈ K`. The second part needs `K` maintained by
  `applyConfChange`'s contract (add/remove), which is the membership model that
  `verify-apply-conf-change` proposes. With that in place the premise shows up as an explicit
  A-pre on the server's results, which is the honest statement of this bug.
- *Close it* (small, after an upstream change): either `UpdateAttributes` warns and skips an
  unknown ID (as `RemoveMember` does since 3.6 for an absent member), or the leader validates
  `ClusterMemberAttrSet` before proposing. Then the triple holds for every `id` and no premise is
  needed. The cause in bootstrap (`ValidateClusterAndAssignIDs` choosing among ambiguous URL
  matches) needs `bootstrap` translated, which is O-pkg-sized (~600 lines of `bootstrap.go`),
  low priority.
- *Audit* (small): the other names-only contracts in `apply/Contracts.lean` (`SetDowngradeInfo`,
  `SetVersion`) and the lessor, alarm and auth contracts, checked against their Go bodies for
  `lg.Panic` and `panic` on inputs that a committed entry controls.
