# etcd-io/etcd#21610: a learner removes itself from the member list after receiving a snapshot

- URL: https://github.com/etcd-io/etcd/issues/21610 (open; filed 2026-04-14; label `type/bug`; an
  assignee, no diagnosis, no PR)
- Affected: 3.6.8 (raft v3.6.0).

What was reported. In a 3-voter cluster, `member add --learner` and start the new member
(`57af20a01bb3d0e5`). It downloads the leader's snapshot (index 1760405075). Raft restores it
with `voters=(3) learners=(57af…)`, so the snapshot's `ConfState` does contain the learner. The
server restores its stores and publishes its attributes (a committed `ClusterMemberAttrSet`).
About 11 s later raft logs `switched to configuration voters=(3)` with no learners, and
`membership/cluster.go:460` logs "removed member … 57af… is-learner true". The member finds
itself removed and stops ("the member has been permanently removed from the cluster"). The
reporter adds: promoting the member before that log line keeps it alive. The `member list` and
`endpoint status` pasted in the report show a *different* learner ID (`58d2fdf2cf3c2cf6`) for
the same name and URL, so they come from another attempt.

## Classification

**N, unsettled (secondary O-pkg).** The log shows a *committed* `ConfChangeRemoveNode` for the
learner. Every member applies it (raft switches configuration, then `RaftCluster.RemoveMember`).
At the pin, etcd proposes `ConfChangeRemoveNode` in exactly one place,
`EtcdServer.RemoveMember` (`server.go:1435-1447`, the `MemberRemove` RPC).
`storage.CreateConfigChangeEnts` (`server/storage/util.go:77`) appends removals only to the
local log of a member started with `--force-new-cluster`, which would also have removed the
voters. Raft originates no removals: its leader appends only proposed entries, plus the empty
auto-leave `ConfChangeV2`, which removes no one. That is `stepLeader`'s spec (`MsgProp`) under
the verified `raft.Step`. So the most likely cause is a `MemberRemove` by the reporter's tooling.
That also fits the timing: the removal happens whenever the learner is not promoted soon enough.
No etcd code path explains it. If an etcd cause turns up, it would sit in the membership and
transport code, which is not translated (O-pkg).

## The code path (at the pin)

Source: `verified.txt`.

| Go function | State |
|---|---|
| `EtcdServer.RemoveMember` → `configure` (the only server-side proposer of `RemoveNode`) | not translated |
| raft: propose, commit, `ApplyConfChange` | verified (`Spec/go_etcd_io/raft/v3/stepLeader.lean`, `RawNode__ApplyConfChange.lean`) |
| `EtcdServer.applyConfChange` (raft, then `RaftCluster.RemoveMember`; returns `removed`) | assumed (axiom) |
| `membership.RaftCluster.RemoveMember`, `rafthttp` peer removal | not translated |
| the member stopping on `ErrMemberRemoved` | not translated |

What the specs say. The removal is applied only because it was committed: under the dynamic mode
of `RawNode.ApplyConfChange.spec`, the change applied is the next committed conf entry
(`DynCCPre`, `Proof/go_etcd_io/raft/v3/InvRawnode.lean:533-548`; see `raft-372.md`). Raft's
proposal path appends only proposed entries. Neither excludes an operator's `MemberRemove`, and
neither should.

## Proposal

None (class N). If a reproduction shows a removal that no client requested, the place to look is
`EtcdServer.RemoveMember`/`configure` and the leader's membership checks (not translated). The
existing `verify-apply-conf-change` would cover the apply side.
