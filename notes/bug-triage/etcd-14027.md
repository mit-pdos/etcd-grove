# etcd-io/etcd#14027: etcd leader change leads to "timed out waiting for read index response"

- URL: https://github.com/etcd-io/etcd/issues/14027 (closed 2022-10-16 by the stale bot; labels
  `type/bug`, `stale`). Reports on v3.4.x (a commenter: v3.4.13).
- Observed: after a follower with a higher term rejoins and forces an election, linearizable reads
  issued around the election fail with `etcdserver: request timed out` after the full request
  timeout (log: "timed out waiting for read index response"); the reporter says the leader answers
  more slowly than the followers.
- Diagnosis: not settled in the thread. The maintainer's (serathius): "the first request after
  leader election timing out", etcd-io/etcd#12680, fixed in v3.5 and backported to v3.4.20 (July
  2022, after this report): raft `3189a66af` "postpone MsgReadIndex until first commit in the term"
  (backport `9c9148c4c`) and etcd `3d485faac` "resend ReadIndex request on empty apply request"
  (backport `f53db9b24`). The reporter disputes it without new evidence; nobody reproduced it.

What goes wrong under that diagnosis (v3.4 before 3.4.20): since #7332 (see
[etcd-7331](etcd-7331.md)) a leader that had not yet committed an entry of its term **dropped** a
`MsgReadIndex` (`stepLeader`: `return`), and a follower without a leader also drops one
(`stepFollower`: "no leader at term; dropping index reading msg"). etcd 3.4's read loop sent one
request and waited for its `ReadState` until `RequestTimeout`, so a read that raced the election
hung for the whole timeout. The fix keeps the request pending until the first commit of the term,
and etcd resends on its first-commit-in-term notification.

## Classification

**F (fixed before the verified code); counterfactual split: F+ at `stepLeader`, F− at the API, with
gap C-live.** Both fix commits are ancestors of the pins (`3189a66af` ⊑ raft `509271dac`, `3d485faac`
⊑ etcd `107edf7e4`). `stepLeader.spec` is functional and states the postponement, so the dropping
code would fail it. But nothing above it states that a read request is ever answered: the specs are
partial correctness, and a read loop that returns `ErrTimeout` after the request is dropped meets
every spec from `raft.Step` to `LinearizableReadNotify`. The reporter's other claim (the leader being
slower than the followers after the election) is unexplained; if real, it is a performance question
(C-perf), likewise outside what the specs say.

## The counterfactual (step 5)

- **`stepLeader`: F+.** `LeaderNonpropResultC` (`Spec/go_etcd_io/raft/v3/stepLeader.lean:243-247`)
  says, for `MsgReadIndex`: if the entry at the commit index is not of the leader's term,
  `s' = { s with rd := { s.rd with pend := s.rd.pend ++ [(m, ents)] } }`. The v3.4 code returns with
  `s' = s`, so `stepLeader.wp_proof` would fail at that branch. (The statement would of course have
  been written for the old code instead; as it stands it records the postponement.)
- **The API: F−.** `Read.requestCurrentIndex.spec`
  (`Spec/go_etcd_io/etcd/server/v3/etcdserver/read/Read__requestCurrentIndex.lean`) returns
  `applyErrIs err` and, only if `err = nil`, an index at least the bound. `ErrTimeout` is allowed in
  every state. `node.ReadIndex.spec`/`RawNode.ReadIndex.spec` promise `readStateOk` for every
  `ReadState` handed out, not that one is handed out. In the model, a request dropped by a follower
  without a leader, or discarded when `readOnly` is reset on a term change, is a legitimate step. So
  the v3.4 behavior (a request dropped by a leader before its first commit, then a timeout) meets
  every spec above `stepLeader`, and so would a pinned read loop without the
  `firstCommitInTermNotifier` resend.

Gap: **C-live**, the read path's progress. Liveness is outside Iris-style partial correctness. The
closest safety property that would have caught the drop is a bookkeeping invariant: no read request
a leader accepts in its term is lost while it stays leader.

## Proposal: `readindex-no-silent-drop`

A ghost "outstanding" set of read contexts per leader term, a safety stand-in for "every read is
eventually answered or fails visibly":

- raft invariant (in `ownRaftGhost`'s read part): every context deposited at the leader of term `T`
  while it leads `T` is in `s.rd.pend`, in `s.rd.ro.pending`, or has a `ReadState`/`MsgReadIndexResp`
  issued; and `plogTermAt … s.commit = some s.term → s.rd.pend = []` (the release after the first
  commit, `releasePendingReadIndexMessages`). A `MsgReadIndex` dropped by a follower or a reset at a
  term change must be visible to the client: `node.ReadIndex`'s spec returns, or `Ready` reports, a
  leader change (`SoftState.Lead`).
- etcd: `requestCurrentIndex` returns `ErrTimeout` only after it has sent a request on every
  `firstCommitInTerm` notification since its first send (a ghost counter of notifications against
  sends), which the pre-`3d485faac` loop fails.

Cost: small to medium. The raft half is a conjunct over state the specs already track (`pend`,
`ro.pending`); the etcd half is a ghost counter on the server's first-commit notifier
(`FirstCommitInTermNotify`, `isReadServer`). It catches dropped-request regressions, not slowness.

## Findings

None new: the bug (under the maintainers' diagnosis) is fixed at both pins; no `issues/` file. The
reporter's "the leader is slower" claim is unsubstantiated and unclassified beyond C-perf.
