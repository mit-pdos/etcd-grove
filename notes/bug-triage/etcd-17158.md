# etcd-io/etcd#17158: `(*batchTx) UnsafeDelete` may break linearizability

- URL: https://github.com/etcd-io/etcd/issues/17158 (closed 2024-11-10; labels `type/bug`,
  `priority/important-soon`, `backport/v3.4`, `backport/v3.5`). All releases before the fix.
- Fix: PR #17195 "Fix delete inconsistencies in read buffer" (merge `b3bf59a35`, 2024-01-11;
  backports #17230, #17238). Related, same thread: #17228 (dedupe the read buffer on write-back,
  merge `ed994248e`), reverted by #17285 (`8bd34cf23`) after #17247; #17359 (`8c7f911b3`,
  `VerifyTxConsistency`, now `VerifyBackendConsistency`). #17157 (commit on every delete) was the
  first proposal, closed for #17195.

What goes wrong (pre-fix code, `server/storage/backend/batch_tx.go`): a delete goes only to
bbolt's write transaction (`batchTx.UnsafeDelete`); the read buffer has no tombstones. Readers
(`ReadTx`, `ConcurrentReadTx`) read bbolt's read transaction opened at the last commit, under the
read buffer. `batchTxBuffered.Unlock` wrote the write buffer back and committed only when
`pending >= batchLimit`. So after a request that deleted a key and before the next periodic
commit, a reader still found the key in the old bbolt snapshot: e.g. auth's `UserDelete` then
`UserAdd` of the same name failed with `ErrUserAlreadyExist` (the apply reads through a read
transaction), and mvcc-level reads in the window could return deleted data.

## Classification

**F+ (fixed before the verified code).** The fix `b3bf59a35` is an ancestor of the etcd pin
`107edf7e4`; at the pin `batchTxBuffered` counts `pendingDeleteOperations` and `Unlock` commits
when it is positive (`batch_tx.go:355`). The backend's invariant would have failed on the
pre-fix code: when the batch lock is free the session must have no pending delete (`freeOk`,
`st.ndel = W64 0`, `Proof/.../storage/backend/Model2.lean:220`), and `Unlock`'s postcondition
gives the clients the readers' view *at the writer's contents* (`bView γ 1 (sData P st.S)`,
`Spec/.../storage/backend/batchTxBuffered__Unlock.lean`). With a delete pending and no commit,
the readers' view (`viewOf`: committed data under the read buffer, `Model2.lean:109`) still
holds the key; neither holds.

Source of verification states: `verified.txt` was not produced; read from the `Spec/`, `Proof/`
and `Link.lean` files of `server/v3/storage/backend` (every function below a `theorem … wp_proof`).

## The counterfactual (step 5)

The model's session state `BSess` (`Model2.lean:98`) has `ndel`, the pending deletes, which
`UnsafeDelete` increments (`Model2.lean:273,283`). Two clauses tie it to what readers see:

- `sessWf` (`Model2.lean:215`): `st.ndel = 0 → agreeOff P.HB (dget st.S) (ovB P.BT st.W.bks
  (viewOf P st))` — without a pending delete, the writer's contents are the write buffer over the
  readers' view. This is exactly what a delete breaks: bbolt's writer lost the key, the readers'
  view and the write buffer did not.
- `freeOk` (`Model2.lean:219-221`): the batch lock is released only with `ndel = 0`.

Pre-fix, `Unlock` with `pending < batchLimit` and a delete in the session does not commit. In
the proof of `Unlock` that branch must re-establish `freeOk` and deliver `bView γ 1 (sData P
st.S)` (the readers' new view equals the writer's contents, off the hook's buckets); the
key deleted in `S` but present in `viewOf` makes `vData P (C, writeback R) ≠ sData P st.S`, so
the step fails — at the no-commit branch of `Unlock`. Without the counter at all, the
invariant `sessWf`'s agreement clause could not even be stated unconditionally (it is false
right after any delete), so a proof of the old code needs the commit. And the clients' read
specs (`rtRange rv`) are answered from the view the `Unlock` handed over, so mvcc's readers
(`kbView`, the bridge) would otherwise see a state that is not the store's: the
linearizability of mvcc's reads rests on this step.

## Proposal

None needed for this bug (F+). Related existing findings in the same code, both open at the pin
and both caught by the same view invariant's limits (`wbDupOk`, `Model2.lean:111-117`; the

not on `merge`'s fast paths the file describes, and was reverted by #17285) and `issues/etcd-backend-read-buffer-cache-stale-after-commit.md`.
