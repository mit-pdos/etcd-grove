# etcd-io/etcd#20488: Client Cache breaks Resumable guarantee

<https://github.com/etcd-io/etcd/issues/20488>. Filed 2025-08-14 by serathius, closed 2025-08-27.
Found by the robustness tests run on the experimental `cache` package through PR #20354.
Affected: `main` of August 2025 (the cache was not in any release). Fixes: PR #20491 ("cache:
preserve resumable guarantee with empty history watchers", merge `1cae3b3b6`, 2025-08-15) and the
follow-up PR #20499 ("cache: remove early compaction check from Cache.Watch", merge `6fca19f04`,
2025-08-22).

**The bug.** A `Cache.Watch(prefix, WithRev(989))` received its first event at revision 1540, but
etcd had an event under the prefix at 989 (`key13`). The maintainers' diagnosis, which the fix
confirms: `ready` was set before the demux's history had anything in it, so a watcher could
register while the history was empty. `demux.Register` (`cache/demux.go`) then made a watcher with
a nonzero `startingRev` *active* with `nextRev = startingRev`, because the "starting revision is
behind the history" test had nothing to compare with. The cache's own upstream watch started at
its Get revision + 1, which was after 989, so 989's events were never in the cache's stream.
`Broadcast` sent the next batch (1540) to every active watcher without checking that the batch
started at or before the watcher's `nextRev`. The fix registers a watcher with a nonzero start as
*lagging* while the history is empty. `Broadcast` also moves an active watcher to lagging when the
batch's first revision is above its `nextRev`. The lagging path either resyncs the watcher from
the history or cancels it as compacted.

## Classification

**F+** (fixed before the verified code, and the spec excludes the buggy version). Both fix merges
are ancestors of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes). At the pin,
`demux.Register` (`cache/demux.go:85`) has the `maxRev == 0` guard that puts a nonzero start in
`laggingWatchers`, and `broadcastEventsLocked` (`:258`) has the gap check. Two specs exclude the
buggy version. The demux's lock invariant `RegsStart.start_ok` (`InvDemux.lean:413-415`) allows
an *active* watcher with a nonzero start `s` only when `c.minRev ≠ 0 ∧ c.base < s`. The buggy
`Register` breaks it, and so would its proof. One level up, the exported delivery theorem
`cache_Watch_delivery` (`Results.lean:72-83`) rules out the observed log.

## The counterfactual (step 5)

The observed log is `L` = the response with the batch at 1540 and later batches, for a watch with
`sr = 989`. The delivery theorem (`Results.lean:72-83`) says that, outside the compaction and
rejection cases, `eventsOf L = bs.flatten.filter (key range)` with
`certChain (etcdStepCert pfx) p₀ bs` and, because `sr ≠ 0`, `p₀ < 989`. The first batch, 1540, is
then certified by etcd's step from `p₀ < 989` to 1540, and the step says the batch's events are
all that changed under the prefix in `(p₀, 1540]`. etcd changed `key13` at 989, so no such
certificate exists. The theorem forbids the observed log.

Where the proof of the buggy code would break: the certificates the demux holds start at the
stream's `base`, which `Init(m)` sets to `m - 1` (`InvDemux.lean:95,155-158`). That is the cache's
upstream watch start, here at or above 989. `RegsStart.start_ok` is the invariant that lets a
watcher's chain start below its `s`. It holds when `s = 0`, or when the demux is initialized with
`base < s`, or when the watcher is lagging at `n = s`. Pre-fix `Register`, with an empty history
and `startingRev = 989`, wrote `activeWatchers[w] = 989`. If this happened before `Init`
(`minRev = 0`), the second disjunct is false. If it happened after `Init` at a `base ≥ 989`, the
inequality is false. The third disjunct needs the lagging phase. So `Register`'s proof cannot
re-establish the lock invariant. I did not check whether the proof of `broadcastEventsLocked` also
depends on the gap check, the fix's second half; the first half is enough for F+. Nothing was
re-proved. The argument is that `start_ok` is false in the post-state of the buggy branch, which
is a direct reading of the invariant.
