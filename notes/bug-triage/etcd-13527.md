# etcd-io/etcd#13527: A disk-stalled, partitioned leader does not step down

- URL: https://github.com/etcd-io/etcd/issues/13527 (closed 2025-10-17 by the stale bot, not
  fixed; labels `type/bug`, `stale`, `stage/tracked`, `release/v3.4`). Reported on v3.4.18.
- Fix: none. PR #16847 "etcdserver/raft.go: separate raft tick and ready" (closed, not merged)
  and PR #15440 (stalled-write watchdog, closed) were attempts. Related: #15247 (leases revoked by
  a disk-stuck old leader; fixed by #16822, triaged in `etcd-15247.md`), #14338, #16007.

What goes wrong: `raftNode.start`'s goroutine runs a single `select` over `r.ticker.C` (→
`r.tick()` → `Node.Tick`) and `r.Ready()`. While it handles a `Ready` it calls the WAL's
`r.storage.Save` inline (`raft.go:256`). If the disk stalls (an `fsync` that does not return),
the loop never comes back to the `select`, so no tick reaches raft. A leader partitioned from its
followers at that moment never runs `CheckQuorum`'s step-down (`tickHeartbeat` → `MsgCheckQuorum`).
It keeps reporting itself leader (`etcd_server_is_leader 1`, `endpoint status`) while the others
elect a new leader at a higher term. The report asks whether tick and `Ready` handling must be
mutually exclusive.

## Classification

**C-live (secondary A-model, A-pre).** The code is in the pin unchanged (`raft.go:174-256`: the
tick case at `:183`, `Save` at `:256`), and `raftNode.start` and `raftNode.tick` are verified. Its
spec is partial correctness over a WAL contract whose `Save` is a Hoare triple
(`isRNWal`, `Proof/.../etcdserver/InvRaftNode.lean:566-578`). A `Save` that never returns meets it,
and a loop that never takes another tick meets `raftNode.start.spec` (post `True`). Nothing stated
here requires ticks to be delivered, or the leader to step down, in bounded time. Two further
limits apply. Time is not modeled: the ticker is an unbounded source of tick resources
(`decisions.md`, "The server's raft wrapper"). And the server's raft is proved with `CheckQuorum`
off (`Spec/.../etcdserver/bootstrappedRaft__newRaftNode.lean:19-21,71-76`), so the step-down the
user expected is outside the proved configuration even with ticks.

There is no safety contradiction: the old leader is a leader of an older term. The proved election
safety is one leader per term (`isLeader_unique`), not one leader at a time. Its writes cannot
commit without a quorum. Serializable reads from it are allowed to be stale, and linearizable reads
need a heartbeat quorum (`ReadOnlySafe`).

The bug is present at the pin in translated code, and a cheap unit reproduction exists. New
finding: `issues/etcd-stalled-wal-no-tick.md`.

Source of verification states: `/shared/etcd-grove-triage/coord/verified.txt`.

## The argument (step 4)

1. **Observed**: after a `Ready` from leader state, the loop is inside `Save` forever. Ticker
   events accumulate and none is turned into `Node.Tick`, so raft's state stays `StateLeader` at
   term 35 while the cluster moves to a later term.
2. **Premises**: the setting has `CheckQuorum = true` (etcd's `bootstrap.go:572`), which violates
   the server-level result's premise (A-pre). That premise explains why raft's step-down is not
   proved here. It does not explain this bug: with `CheckQuorum` in scope, the stalled loop would
   still deliver no tick.
3. **Model**: the stall is a disk that does not answer. Perennial's model has no notion of a call
   taking too long. A non-returning `Save` is a valid execution, and partial correctness says
   nothing about the steps after it (A-model: time and progress).
4. **Postcondition**: `raftNode.start.spec` ends in `True` for the spawning call, and the loop's
   invariants (`rnLoopTok`, `rnApP`) are safety invariants about what is sent on `applyc` and
   persisted. A loop stuck in `Save` violates none. What the user expected, "a leader that cannot
   hear from a quorum for an election timeout stops acting as leader", is a timed liveness
   property. → **C-live**.
5. **The missing property and the closest safety statement.** In partial correctness, the closest
   checkable design property is that the tick path does not wait on the WAL. PR #16847's design (a
   separate tick goroutine) would make this a proof obligation: the tick goroutine's only shared
   resources are `tickMu` and the raft `Node`'s `Tick`, and neither is held across `Save`. With a
   clock model, the real property is "a member that reports itself leader (`isLeader`, `Status`,
   the gauge) at real time `t` received a quorum's responses after `t − electionTimeout`".

## Proposal: `stalled-leader-stepdown` (new)

- **Safety first (no clock):** prove, for the loop as it stands or as split by #16847, that no lock
  or channel the tick path needs is held while `storage.Save`/`SaveSnap`/`Sync` run. Today this
  fails for the single loop, and the failure is this bug. Concretely, give the WAL's `Save` an
  abstract "may block" token and require `raftNode.tick` to be callable from a separate goroutine
  while the loop holds it:

  ```lean
  -- the loop holds `walBusy γ` across Save; tick's spec does not mention it
  {{ isRaftNode E γ r ∗ rnTickRes E }} r.tick() {{ True }}   -- callable concurrently with
  {{ walBusy γ ∗ … }} st.Save(hs, es) {{ walBusy γ ∗ … }}    -- the loop's Save
  ```

  This is small to medium once the loop is restructured upstream, and nothing for this repository
  to prove before then.
- **The property itself** needs a clock model with real time and bounded drift (shared with
  `lease-clock-model` from `etcd-15247.md`) and `CheckQuorum` on in the server's raft (lift the
  premise of `bootstrappedRaft__newRaftNode.lean:76`: raft's `MsgCheckQuorum`/`RecentActive`
  handling verified). Then state a leader-lease property: a member's `isLeader` at real time `t`
  implies a quorum heard after `t − electionTimeout`. Large, and it needs a Perennial time model
  (CLAUDE.md, "Changes to Perennial": a separate proposal). The tick-starvation part stays
  liveness.

## Findings

- New: `issues/etcd-stalled-wal-no-tick.md`, with the reproduction
  `issues/etcd-stalled-wal-no-tick/stalled_wal_no_tick_test.go`. It passes at the pin: with a WAL
  whose `Save` blocks, no `Tick` reaches the node over 40 heartbeat intervals, after 20 ticks in
  the preceding idle 100 ms.
- No bug in this repository's specs.
