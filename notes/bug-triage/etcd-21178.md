# etcd-io/etcd#21178: Panic: tocommit(...) out of range [lastIndex(0)] on fresh Learner join after member remove/add

- URL: https://github.com/etcd-io/etcd/issues/21178 (open; `type/bug`; it continues #20269)
- Affected: 3.5.25 (reported; 3.5.21 in #20269). The code involved is unchanged on `main`.
- Fix: none. PR #21271 (open, unreviewed) has been reduced to an e2e "reproducer". No maintainer
  diagnosis: ishan16696's comment says the learner "didn't get a raft snapshot ... directly got a
  raft message to commit".

What goes wrong: the reporter wipes the data directory of a node, runs `etcdctl member add
--learner`, and starts etcd with `--initial-cluster-state existing`. The new process starts with an
empty log (`newRaft 5cda505f2ab9e012 [peers: [], term: 0, ..., lastindex: 0]`). It receives a
`MsgHeartbeat` at term 9 with `Commit = 5099750` from the leader `5996a09fdc632a12`.
`stepFollower` → `handleHeartbeat` → `raftLog.commitTo(5099750)` panics (`log.go:326` at the raft
pin): `tocommit(5099750) is out of range [lastIndex(0)]`.

## Classification

**A-model (secondary O-path; N upstream so far).** The decisive fact: a leader sends `Commit =
min(pr.Match, committed)` (`raft.go:702`), and `pr.Match` for a peer is 0 when the leader takes
office (`reset`, `raft.go:797`) and when the peer is added (`confchange.initProgress`,
`confchange.go:262`). It rises only on a non-rejecting `MsgAppResp` *from that peer* in the
leader's term (`raft.go:1519`, `Progress.MaybeUpdate`). So member `5cda505f2ab9e012` acknowledged
index ≥ 5099750 in term 9, and the process now running under that ID has lost it. The reporter's own
`member list` confirms it. The learner `5cda505f2ab9e012` is shown as *started* with the name
`181140269087284-164`, which only a process that ran under that ID and applied its own publish entry
can have written; the panicking process applied nothing. (In #20269 the listed learner's name,
`...-2213`, even differs from the configured `...-2229`.) etcd's join path
(`bootstrapExistingClusterNoWAL` → `membership.ValidateClusterAndAssignIDs`,
`membership/cluster.go:755-782` at the etcd pin) takes the local member's ID from the existing
cluster **by peer URL**, so a wiped node that reuses a peer URL inherits a member ID that already has
acknowledged entries. That is the raft#197 situation, a node that lost its persisted log rejoining
under its ID, and the proof's model cannot express it. The raft spec excludes the panic by a premise
that the run does not meet.

Source: `verified.txt` (scratchpad inventory at `d606c9cac`) and the spec files.

## The argument (step 4)

As in `raft-197.md` ("The argument"), checked again for this setting:

1. `raftLog.commitTo.spec` requires `uint.Z tocommit ≤ plogLastIndexZ ...` (the premise that makes
   the `Panicf` dead). `raft.Step` discharges it for a heartbeat with `heartbeat_commit_le_last`
   (`Proof/go_etcd_io/raft/v3/raft__Step.lean:204`): a heartbeat's `isMessage` carries
   `isAcked γ m.dst m.term i` with `Commit ≤ i`. The receiver acknowledged `i` in this term, and
   its ghost ties its acks to its current log.
2. In the report the ack is real: the earlier incarnation of `5cda505f2ab9e012` sent it. The log is
   gone. In the logic, the new process would need `ownRaftGhost γ id` at an empty state, through
   `rnInit γ md id V`. That ghost state is minted once per ID when the cluster ghost is allocated,
   and is exclusive, so no proof can produce it for an ID that has already run. The premise of the
   start is violated, and the deeper cause is the model: no crashes, no stable versus volatile state
   (`notes/STATUS.md`, "Out of scope for now"). Losing the data directory while keeping the member
   ID is a crash that loses durable state: **A-model**.
3. The etcd side is not verified: the joining member's bootstrap and the `RestartNode` branch of
   `newRaftNode` are out of scope (secondary **O-path**). Nothing here states which member ID a
   joining process may take.
4. Not X: under the premises the panic is excluded, and the run does not meet them. Not C: no
   strengthening of `handleHeartbeat`'s spec is wanted. raft's `doc.go:75-82` documents
   persist-before-send, and the panic message names the cause.

**The reporter's claims, checked.** "A fresh Member ID": a fresh ID's `Progress.Match` is 0, so its
heartbeats carry `Commit = 0` and cannot panic. The reported heartbeat proves the ID had history.
Either the `member add` was not the last one for this peer URL, or an earlier start of this
incarnation ran and caught up before the wipe. The `started` name in the member list is the evidence.
"Strictly learner": nothing in raft's heartbeat path distinguishes learners. The difference is
presumably in the operator's flow.

Upstream status: no maintainer has diagnosed #21178. silentred's answer on #20269 ("it is supposed
to panic" if the data is lost without remove/add) matches this analysis. etcd could refuse the join
in `bootstrapExistingClusterNoWAL` when the matched existing member already has a published name
(`Member.IsStarted()`). That catches the reported runs, though not an incarnation that acked entries
before publishing. This is a hardening suggestion, in untranslated code, so there is no `issues/`
file.

## Proposal: `raft-durable-acks` → `crash-restart-model` (as raft#197), plus `join-fresh-identity` (new)

- `raft-durable-acks` / `crash-restart-model`: see `raft-197.md`. Acks justified by the persisted
  storage, and a restart theorem in which a storage holding less than the old incarnation persisted
  fails the premise.
- `join-fresh-identity`: verify etcd's existing-cluster join path. That is `bootstrapExistingClusterNoWAL`
  (31 lines) and `ValidateClusterAndAssignIDs` (28), with `GetClusterFromRemotePeers` (HTTP) as a
  trust boundary, and `newRaftNode`'s `RestartNode` branch, establishing raft's dynamic-mode
  `rnInit` for the assigned ID. The ghost would be a one-shot token `memberFresh γ id`, minted when
  `applyConfChange` applies the `AddNode`/`AddLearnerNode` of `id`, and consumed by the first start
  from an empty data directory:

  ```lean
  -- bootstrapExistingClusterNoWAL.spec, post (sketch)
  {{ RET (bc, nil); ∃ id, bcNodeID bc id ∗ memberFresh γ id }}   -- needs the matched member's token
  ```

  At the pin the proof cannot get the token: etcd assigns the ID by peer URL with no check. The spec
  would therefore state the operational rule as a premise ("each member ID is started from an empty
  data directory at most once"), for upstream's documentation. Cost: medium to large. It needs the
  untranslated bootstrap pieces, a dynamic-mode start for a joining node, and the token threaded
  through `verify-apply-conf-change`.
