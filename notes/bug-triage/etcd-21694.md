# etcd-io/etcd#21694: MemberUpdate forgets that the member is a learner

- URL: https://github.com/etcd-io/etcd/issues/21694 (closed 2026-05-27, completed; `type/bug`)
- Affected: 3.6.10 (reported), 3.5, and `main` before the fix.
- Fix: PR #21719 "bugfix: MemberUpdate implicitly and unexpectedly promotes a learner" (commits
  `c61d35f0d` test, `7c528e856` fix; merge `0369e327b`, 2026-05-10); backports #21736/#21737
  (3.6/3.5).

What goes wrong (pre-fix code): `ClusterServer.MemberUpdate` (`v3rpc/member.go:80-84`) builds a
`membership.Member` with `RaftAttributes{PeerURLs: r.PeerURLs}`, so `IsLearner` is `false`.
`EtcdServer.UpdateMember` proposes it as a `ConfChangeUpdateNode`. `EtcdServer.applyConfChange`
(`server.go:2057-2069`) decodes the member and calls `RaftCluster.UpdateRaftAttributes(id, attrs,
v3)`, which before the fix replaced the member's whole `RaftAttributes` (`m.RaftAttributes =
raftAttr`) and saved it to the backend. The member list then shows the learner as a voter, while
raft's configuration is unchanged (`ConfChangeUpdateNode` is a no-op in `confchange`). Promotion is
refused (`ValidateConfigurationChange` sees `IsLearner = false`), and the one-learner limit counts
one learner fewer, so a second learner can be added.

## Classification

**F (fixed before the verified code); counterfactual F−, gap O-fn (secondary C-obs).** The fix
merge `0369e327b` is an ancestor of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes).
At the pin `UpdateRaftAttributes` (`membership/cluster.go:535-555`) copies only `PeerURLs`.
Counterfactually nothing here would have excluded the buggy version. `UpdateRaftAttributes` is not
translated, `applyConfChange` is a trust-boundary axiom that says nothing about the members map, and
the one verified reader, `RaftCluster.Members`, returns members whose `IsLearner` is an unconstrained
existential.

## The counterfactual (step 5)

The pre-fix `UpdateRaftAttributes` (parent `76af2fe95`) would meet every statement here:

- `EtcdServer.applyConfChange.spec` (`EtcdServer__applyConfChange.lean:41-58`) is about the
  ownership of `cc`, `ep.confState`, the backend's batch lock and the consistent index. Its
  postcondition says nothing about the members map's contents. It holds of any membership update,
  including one that clears `IsLearner`.
- `membership.memberIs` (`Proof/.../api/membership/Defs.lean:70-74`) quantifies
  `∃ ... (il : Bool) ...`: the `IsLearner` field is owned, but not tied to raft's
  configuration or to any earlier value. `RaftCluster.Members.spec` therefore returns the wrong
  flag as readily as the right one.
- raft's own results (configuration, quorum) are unaffected: the learner stays a learner in raft's
  `ConfState`, which matches the maintainer's observation that the quorum calculation still
  treats it as a learner.

So the observed state, member list `IsLearner = false` while `ConfState.Learners ∋ id`, violates no
stated property. The missing property is the agreement of the two views of the configuration.

## Proposal: `verify-apply-conf-change`

Prove `EtcdServer.applyConfChange` (63 lines) and the membership writers it calls (`AddMember`,
`RemoveMember`, `PromoteMember`, `UpdateRaftAttributes`, about 135 lines in `cluster.go`, plus
`membershipBackend`'s saves). Replace the axiom with a spec over a pure membership model, with the
invariant that the members map agrees with raft's configuration:

```lean
def membersMatchConf (ms : GMap w64 MemberV) (cs : ConfStateV) : Prop :=
  (∀ id m, ms[id]? = some m → (m.isLearner ↔ id ∈ cs.learners) ∧
                              (id ∈ cs.voters ∨ id ∈ cs.learners)) ∧
  (∀ id, id ∈ cs.voters ∨ id ∈ cs.learners → id ∈ ms)
```

The invariant is kept by `applyConfChange` together with the returned `ep.confState`. The pre-fix
`UpdateRaftAttributes` breaks it on an `UpdateNode` of a learner. `RaftCluster.Members.spec` would
then return `il` from the model. Cost: medium (about 300 lines of Go, a pure model of the v2/v3
member maps, `membersMatchConf` threaded through `isRaftCluster`). Translating `member.go`'s
`MemberUpdate` and `server.go`'s `UpdateMember` is not needed to catch this bug: the corruption
happens at apply.
