# etcd-io/etcd#22440: rafthttp: snapshotHandler panics on MsgSnap with missing Snapshot

- URL: https://github.com/etcd-io/etcd/issues/22440 (open; `type/bug`).
- Affected: etcd v3.7 (main since `4715a5474`, 2026-05-27, "build: upgrade go.etcd.io/raft to
  v3.7.0-beta.0", an ancestor of the pin). With raft v3.7's protobuf-go `raftpb`,
  `Message.Snapshot` is a `*Snapshot`. Before, under gogoproto, it was a value, so an omitted field
  decoded to the zero `Snapshot`.
- Fix: PR #22441 "rafthttp: return 400 when MsgSnap lacks Snapshot" (open; not in the pin).

What goes wrong: a peer (or anything that passes the peer TLS and the cluster-ID header checks)
POSTs to `/raft/snapshot` a well-formed `Message{Type: MsgSnap}` without field 9. At the pin,
`snapshotHandler.ServeHTTP` (`server/etcdserver/api/rafthttp/http.go:208`) checks only
`m.GetType()` (`:251`). It then dereferences `m.Snapshot.Metadata` (`:272`, again `:279`) and
panics with a nil pointer. `net/http` recovers a handler's panic and aborts that request, so the
member likely survives, but the panic is still reachable from one malformed peer message.
Upstream asks for a 400.

## Classification

**O-pkg.** The faulty function is in `rafthttp`, which nothing here translates beyond names
(`verified.txt`: `etcdserver/api/rafthttp` 105 functions, 0 verified, 33 names only). The bug is
present at the pin (`git show 107edf7e4:…/http.go`, lines 272/279/286/301 dereference
`m.Snapshot` unguarded).

Two facts on the verified side:

- Raft is not affected. `raft.handleSnapshot` (raft pin `509271dac`, `raft.go:1832-1837`) reads
  through `m.GetSnapshot()` and `pb.EnsureSnapshot`, so a nil snapshot is the zero snapshot. In
  any case `MsgSnap` is outside `RawNode.Step`'s specified types (`netStepTypes`,
  `Proof/go_etcd_io/raft/v3/InvRawnode.lean:465`).
- The server's verified `raftNode.processMessages` handles outgoing `MsgSnap` through getters. It
  is not on this path.

The bug is a regression of the raft v3.7 retarget upstream (value → pointer), the same change this
repository's raft retarget (`notes/raft-retarget-plan.md`) tracked on the raft side. Go code that
read `m.Snapshot.Metadata` was safe before and is now partial.

Source of verification states: `verified.txt` (this batch).

## Proposal: `verify-rafthttp-handlers`

Translate `rafthttp/http.go`'s three handlers (`pipelineHandler`, `snapshotHandler`,
`streamHandler`.ServeHTTP, about 330 of its 543 lines). Use as trust-boundary specs the decoder
(`messageDecoder.decodeLimit`: a `Message` or an error, any field possibly absent), `Snapshotter.SaveDBFrom`,
and `Raft.Process`, and the transport's peer and cluster-ID checks as names. Even a weak spec,
`{{ True }} h.ServeHTTP(w, r) {{ True }}`, rules this bug out. Goose's semantics make a
nil dereference a stuck program, so the proof fails at `:272` on the pin and goes through with
PR #22441's check. A useful spec adds that every message handed to `Raft.Process` is a
well-formed `isRaftMsg` of `netStepTypes` (or a `MsgSnap` with a snapshot), which ties the
transport to raft's `RawNode.Step` precondition (`transport-tracks-confstate` touches the same
package). Cost: small to medium (~330 Go lines, mostly logging and metrics).
