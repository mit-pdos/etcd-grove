# etcd-io/etcd#17780: Revision decreasing after panic during compaction

- URL: https://github.com/etcd-io/etcd/issues/17780 (closed 2024-10-26; labels `type/bug`,
  `area/robustness-testing`, `priority/critical-urgent`, `release/v3.4`/`v3.5`/`v3.6`).
- Affected: `main`, 3.5 and 3.4 before the fix. It was found by the robustness tests
  (`TestRobustnessExploratory/Kubernetes/LowTraffic/ClusterOfSize1`, failpoint
  `compactBeforeSetFinishedCompact=panic()`) and reproduced by fuweid after ~4.8 h.
- Fix: PR #17815, "fix revision loss issue caused by compaction" (`9ea234913`, merge `dd4e35a58`,
  2024-04-22; backported). Related: #17791 adds a bootstrap check that the revision does not
  decrease, #17792 changes the compaction log, and #18099 adds a robustness test for this issue.

What goes wrong (pre-fix code). The last revisions before the crash were deletes. `Compact(c)`,
with `c` the current revision, persisted `scheduledCompact = c` and began deleting bucket
revisions in batches. Pre-#18274 (etcd#18089's fix, Aug 2024), compaction at `c` also deleted the
tombstones at or below `c` of keys whose last generation had ended. So the batches removed the
`Key` bucket's highest revisions, and a batch commit persisted that. The process then died before
`finishedCompact` was written. On restart, `store.restore` (`server/storage/mvcc/kvstore.go`) set
`currentRev` to the highest revision found in the `Key` bucket (`restoreIntoIndex`'s `revc`). That
is lower than the revision clients had already been given. New writes then reused revisions
(298 was observed as two different deletes), and the restored revision went backwards.

## Classification

**F (fixed before the verified code); counterfactual F−, gap O-fn (secondary A-model).** The fix
`dd4e35a58` is an ancestor of the pin `107edf7e4`. At the pin, `restore` lifts `currentRev` to
`scheduledCompact` (`kvstore.go:383-385`). Independently, #18274 keeps a tombstone at the
compaction revision, which also removes the trigger. Counterfactually, nothing here would have
excluded the buggy `restore`: `store.restore` is a trust-boundary **axiom** stated only for an
**empty** `Key` bucket (`Proof/.../storage/mvcc/store__restore.lean`, `axiom
mvcc.store.restore.wp_proof`). A crash between compaction batches is also outside the model (no
crash semantics).

Source of verification states: the proof files and `Proof/.../storage/mvcc/Link.lean`
(`verified.txt` not produced).

## The counterfactual (step 5)

The spec of `restore` is about a fresh store only. Its premise is `mvcc.bucketView γ q ∅`, and its
postcondition fixes `currentRev = 1` and `compactMainRev = -1` (`store__restore.lean`, the
docstring: "A backend with data is out of scope"). The pre-fix `restore` behaves the same on an
empty bucket (no keys, `scheduledCompact = 0`, so the new `max` is a no-op). Its axiom would be
stated identically, and nothing else reads the formula that computes `currentRev` from a non-empty
bucket. The compaction specs say which revisions compaction deletes (`keepAt`). They do not say
that what any intermediate commit persists determines the store's revision, so they hold of the
pre-#18274 compaction too. That compaction deletes the tail tombstones (`etcd-18089.md`: F−). And
no statement spans a crash. **F−.**

The missing property, stated without crashes in the manner of the consistent index's `commitOk`
(`etcd-13766.md`): *every backend commit persists a state from which `restore` recovers a
`currentRev` at least the store's revision*. Pre-fix and pre-#18274 it fails at the first batch
commit of `scheduleCompaction` that deletes the bucket's top tombstone.

## Proposal: `mvcc-restore-from-backend` (existing slug)

As sketched in `etcd-19179.md`: specify and prove `store.restore` (`restoreIntoIndex`,
`restoreChunk`, `keyIndex.restore`, `keyIndex.restoreTombstone`) on a non-empty backend whose
`Key` bucket is `bucketMap (thin log c)` with finished compaction `c`. A scheduled compaction
`c' ≥ c` has its batches applied to a prefix of the keys. The postcondition includes
**`currentRev = max(log.length - 1, c')`**, the clause this bug violates. Add an invariant of the
backend's committed view: each commit, including the batch commits inside `scheduleCompaction`,
persists such a state. That invariant needs no crash semantics, so the crash itself only needs
`crash-restart-model` to reach an end-to-end statement. Cost: medium to large (the helpers must be
added to `mvcc.toml`; the committed-view invariant touches `scheduleCompaction`'s proof). This
would have caught this bug, etcd#19179 and probably etcd#16693.
