# etcd-io/etcd#14140: Stale read with loss of un-fsynced writes

- URL: https://github.com/etcd-io/etcd/issues/14140 (closed 2025-07-31 as stale; `type/bug`,
  `priority/important-soon`, `release/v3.5`).
- Affected: 3.5.3 (Jepsen, five nodes, data directories on LazyFS, kill nemesis with loss of
  un-fsynced data). A comment says it was also seen on 3.4. Not reproduced by maintainers. The reporter was
  unsure of LazyFS at the time. ahrtr closed it: no reproduction "in the past a couple of years",
  and no transaction details or data bundle to debug.
- Fix: none. The thread rules out etcd#14370 (single-member durability, fixed in 3.5.5), because
  this run had five members.

What was observed: a guarded transaction T3 appended 16 to key 180, and T4 read `[… 15 16]`.
About five seconds after T4 completed, T2 read key 180 as `[… 15]`. The reads were not
`serializable`, so this is a linearizability violation (a stale read), occurring after some
members were killed and lost un-fsynced writes.

## Argument

In a crash-free execution, `read_notify` excludes the observed stale read: a linearizable
`Range` returning before the applied index reaches an index the client knows committed. Under a
crash, `committedAtLeast` and `isCommitted` are facts about the dead incarnation, and no premise of
the restarted servers' specs can be established (`rnInit` needs fresh ghost state,
`raft-197.md`). So the specs say nothing about this run, whatever its cause. No cause was
identified, so no `issues/` file and no F/F+ counterfactual.

## Proposal: `crash-restart-model` (existing), first step `raft-durable-acks`

With `raft-durable-acks` (`etcd-14370.md`), `isCommitted L` yields a quorum whose WALs hold `L`.
`crash-restart-model` then carries `isCommitted` across a restart: a restarted node's
`RestartNode` state is its `walDurable` log. With that, `read_notify` would hold for a cluster
whose members crash and lose unsynced data. A LazyFS-style "lose unsynced writes" fault is
exactly the crash this model allows. Cost: large (Perennial crash semantics; see the index).
