# etcd-io/etcd#15220: Requested watcher progress notifications are not synchronised with stream

- URL: https://github.com/etcd-io/etcd/issues/15220 (closed 2023-04-05; `type/bug`,
  `priority/important-soon`)
- Affected: v3.4, v3.5 (≤ 3.5.7) and `main` before the fix.
- Fix: PR #15237 "etcdserver: Send requested progress notifications through watchStream (fix
  #15220)", merge `f6bb87429` (2023-04-05; backported for v3.5.8). It introduced a regression,
  etcd-io/etcd#17507 (`etcd-17507.md`), fixed by #17557 (`ddf54715b`). Later: #18926/#20427
  (regression test); #21517 (closed unmerged, an unreviewed rewrite).

What goes wrong (pre-fix code): `serverWatchStream.recvLoop` (`server/etcdserver/api/v3rpc/watch.go`)
answered a `WatchRequest_ProgressRequest` itself, putting `&pb.WatchResponse{Header:
newResponseHeader(watchStream.Rev()), WatchId: -1}` on `sws.ctrlStream`. `sendLoop` selects
between `ctrlStream` and `watchStream.Chan()`, so this response could overtake mvcc responses
already queued (or not yet generated by `syncWatchers` for an unsynced watcher) with events
at or below the header revision. A client treats a progress notification at revision `R` as
"every event up to `R` has been delivered" (the bookmark guarantee), so a reconnect from `R + 1`
after it drops events. The fix routes the request through `watchStream.RequestProgressAll()` →
`watchableStore.progressAll` → `progressIfSync`, which sends the id `-1` response on the
watchers' own channel, under `s.mu`, only if every watcher of the stream is synced.

## Classification

**F (fixed before the verified code); counterfactual split: F+ by the statement's form, F− by its
content (gap C-other, "progress means synced").** The fix `f6bb87429` is an ancestor of the etcd pin
`107edf7e4` (`git merge-base --is-ancestor`: yes); at the pin `recvLoop`'s progress branch calls
`RequestProgressAll()` (`watch.go:395-399`). Counterfactually, the existing proof of `recvLoop`
would fail on the pre-fix code, but only because `watchDn` enumerates where a response may come
from and has no control answer to a progress request (`ctrlAnswers req m` is `False` for
`.progress`, `InvWatchStream.lean:173`). No spec states what a progress notification's revision
promises, so a spec admitting the control-stream answer (what a proof of the old code would have
written) would also admit the bug — and so would a buggy `progressIfSync` that sent while a
watcher is unsynced.

## The argument (step 5)

What the client sees, in the spec's terms: at down position `j` a response `m` with `m.watchId =
-1`, no events and `m.hdr.revision = R`, while some watcher `w` of the stream has events `≤ R` that
are sent at positions `> j` (or never, after the connection drops).

- **The pin's statement.** `watchStreamSpec` (`InvWatchStream.lean:543`) makes every response
  `watchDn` (`:534`): the server's header and either `ctrlOk` (`:484`, a control answer to a
  request, `ctrlAnswers`) or `mvccOk` (`:519`, an mvcc response). `ctrlAnswers` (`:165-173`) allows
  only create and cancel answers; `| _ => False`. The pre-fix control response for a progress
  request is neither: `ctrlOk` fails (`ctrlAnswers .progress m = False`), and `mvccOk` needs an
  mvcc response `r` with `m = mvccResp r m.hdr` (`m.src = some r`), which a response built in
  `recvLoop` is not. So `recvLoop`'s proof breaks at the control send of its progress branch: F+
  in form.
- **What the statement says of a progress response's content.** An id `-1` mvcc response gives
  `mvccExtra` (`:499-503`): it answers *some* progress request (`progQ`); `mvcc.watchRecvOk`
  (`mvcc/WatchRecv.lean:91`): the responses received for its watcher are a prefix of the
  deliveries (events of `[lo, d)` for some `d`); and `respOk` (`mvcc/InvWatchStore.lean:431-433`):
  its events are at or below its revision, vacuous with no events. Nothing ties the revision `R` of
  an event-less response to `d`: the deliveries may stop below `R`. The `progressIfSync` spec
  (`watchableStore__progressIfSync.lean:24-39`) says in prose "if every watcher is synced ... a
  progress response ... is sent", but its postcondition is only `m ↦ M ∗ watchReader`, the
  boolean unconstrained. So if the proof of the old code had added `.progress => m.watchId = -1 ∧
  ...` to `ctrlAnswers` (the natural statement of what that code did), the bug would satisfy it;
  likewise a `progressIfSync` that skipped its synced check meets its spec. F− in content.
- **Who relies on the missing property.** The cache's watcher contract assumes it (its
  `isEtcdWatcher`'s progress case: a progress notification certifies the state up to its
  revision, `notes/decisions.md` "progress notifications trustworthy", and STATUS "W-K"): it is a
  premise there, not something the server's spec supplies. STATUS "W-K" plans exactly the missing
  pieces as stages K1 (mvcc: progress means synced) and K2 (the client: progress responses
  complete).

## Proposal: `watch-progress-synced` (STATUS "W-K", stages K1–K2)

Give an mvcc progress response its content: in the channel invariant and in `watchRecvOk`, a
response with no events at revision `R` (id `w.id` from `progress`, or `-1` from `progressAll` for
every watcher of the map) comes after deliveries covering `[lo, R + 1)` for its watcher (for `-1`,
for every watcher of the stream). Sketch:

```lean
-- in mvcc.watchRecvOk / respOk, for the last response r received for w:
r.evs = [] → (D.map Prod.fst).flatten = watchEvents L rg γw.lo (sint.nat r.rev + 1)
-- in mvccExtra, for id -1: the same for every watcher idAssigned on the stream
```

`progressIfSync` proves it from `σ.Ws !! w` (synced) and `synced_d`/`syncedAbove`
(`InvWatchStore.lean:345,355`), under `s.mu`'s read side (no writer moves `rev`); `recvLoop` and
`sendLoop` carry it unchanged, and `ctrlAnswers .progress = False` already keeps the control
stream out. Then the client side (K2) states "a progress notification at `R` means nothing under
the range changed that was not delivered up to `R`", and the cache's premise becomes a theorem.
Cost: medium (one conjunct through the channel invariant and `watchRecvOk`, re-proving
`progressIfSync`, `notify`, `syncWatchers`, `moveVictims` against it; K2 is the larger part). It
would have caught this bug, and the class of "progress overtakes events".

## Findings

None new: the bug is not in the pinned code; no bug in this repository's specs (the form-only
catch is a strength of `ctrlAnswers`' exhaustive shape, not an error). The fix's regression is
`etcd-17507.md`; its pinned semantics (a request is dropped when a watcher is unsynced) is
`issues/etcd-watch-progress-request-dropped-unsynced.md`.
