# etcd-io/etcd#20451: one member of a 3.5.6 cluster serves out-of-sync data indefinitely

- URL: https://github.com/etcd-io/etcd/issues/20451 (closed 2025-10-21 as stale; labels
  `type/bug`, `stale`).
- Affected: etcd 3.5.6 (bitnami chart on Kubernetes). It started after a rolling restart of the
  StatefulSet (`helm upgrade`). No fix, no diagnosis. The maintainer (ahrtr) said the member "was
  out of sync with other members for a long time", advised upgrading from 3.5.6, and suggested
  replacing the member.

What was observed. All three members report the same raft index and applied index (41386), but
member 1's MVCC revision is below the compaction revisions the leader proposes. Every auto
compaction (`15452`, `15482`, `15511`) fails on member 1 with `mvcc: required revision is a
future revision`, and its DB is 14 MB against 2.9 MB on the others (its compactions never run).
It keeps serving serializable reads from the stale state. The other members apply the same
entries and compact normally.

## Classification

**A-model (diagnosis unsettled; candidate alternatives O-fn and F).** The same raft log applied
to the same initial state gives the same KV state at the pin. `applyEntries_kv`
(`Proof/go_etcd_io/etcd/server/v3/etcdserver/Results.lean:292`) and `applyEntries_replay_all`
(`:346`) tie the KV state after a batch to the entries applied, entry by entry. So a member whose
revision lags at an equal applied index started from a different state. It could have lost writes
it had counted as applied, or installed a different snapshot. Each candidate cause falls outside
the verified scope:

1. **A crash or restart that loses or skips applied writes** (the rolling restart preceded the
   report). This is the mechanism of etcd-io/etcd#13766 (consistent index persisted without the
   entry's writes, fixed in 3.5.3, before 3.5.6; `etcd-13766.md`: F+ for that specific bug).
   A different restart-time loss in 3.5.6 would be **A-model**: crashes and recovery from the
   backend are not modeled (`EtcdServer.Start`'s bootstrap and `store.restore` are specified only
   for an empty backend; the `crash-restart-model` gap of `etcd-16666.md` and `raft-197.md`).
2. **A snapshot install** (a member that fell behind during the restarts receives the leader's
   snapshot). This is **O-fn**: `EtcdServer.applySnapshot.spec` covers only `ap.snapshot = nil`
   (`Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__applySnapshot.lean`), and
   `store.Restore` from a non-empty backend is not specified (`mvcc-restore-from-backend`,
   `etcd-19179.md`).
3. **A 3.5-branch bug fixed after 3.5.6** (the maintainer's advice to upgrade). This would be
   **F**, but no fix is named, so it cannot be checked against the pin.

None of them is X. For X, the member would have to diverge while applying a common log from a
common verified state, and the report gives no sign of that.

| restart: `bootstrap`, `store.restore` from a non-empty backend, raft replay from the consistent index | outside the model (no crashes); `store.restore` specified on an empty backend only |
| `store.Compact` on the lagging member (`ErrFutureRev`) | verified (it fails as the spec states) |

## The argument (step 4)

The observed state, as the apply-thread results see it: the members applied the same committed
entries `1..41386`, but member 1's `ApplyKV` (its log `o.logAfter`) is shorter than the others'.
By `applyEntries_kv`, every KV entry above the consistent index `c` is applied deterministically
(skipped, rejected by the same admin checks, or committed as `txnModel` etc. of the state it meets).
`applyEntries_replay_all` says that entries at or below `c` write nothing. Two members with equal
`(x, c)` and the same entries therefore end in equal states. (Caveat, from the batch's auth
triage, `etcd-14571.md`: this holds with auth disabled. With auth enabled the apply model's auth layer
rejects or passes by free choice (`apply/Chain.lean:174-177`, `authMayReject`), so the results also
admit two members diverging by auth decisions; whether the reporter had auth enabled is not known.
`auth-state-model` would close this.) So member 1 had a different `x` or a
`c` ahead of its writes when its current run began. Both come from a restart or a snapshot install,
which the results take as given (the initial `x` of the batch is a parameter). The consistency of
`(x, c)` across a crash is the property `crash-restart-model` would state.

## Proposal: `crash-restart-model` (existing)

A restart step through the server's bootstrap. The backend's persisted consistent index and KV
state are related by an invariant kept across crashes (the post-lock hook writes both in one batch,
the property that excluded #13766), and the restarted member's `(x, c)` equals some prefix of the
log applied by a crash-free run. The second candidate cause needs `mvcc-restore-from-backend` plus
the snapshot case of `applySnapshot` (a snapshot's KV state is the leader's state at its index).
Cost: large (crash semantics; see `etcd-16666.md`).

A cheaper operational guard that would have exposed this case: etcd's corruption checks (the periodic
`--experimental-corrupt-check-time`, or the compaction hash check of later releases) would have
flagged member 1. That is detection, not verification, and gets no proposal here.
