# etcd-io/etcd#9988: watch through grpc proxy results in delayed or missed events

- URL: https://github.com/etcd-io/etcd/issues/9988 (filed 2018-08-08, closed 2025-12-23 by the
  stale bot; labels `type/bug`, `gRPC-proxy`, `stale`). Version v3.3.9 (client, proxy and
  server). The setup was 20 clients, 3 proxies and 6 members.
- Observed: clients sometimes get events minutes late, or not at all, through the proxy; with
  direct connections everything works. No logs, and no reproduction (a maintainer asked for one
  in 2025). Not diagnosed. A maintainer (serathius) recommends against using the proxy: "highly
  likely the gRPC proxy has significant correctness flaws". No fix.

## Classification

**O-pkg** (diagnosis unsettled). Every candidate cause is in `server/proxy/grpcproxy`, which is not
translated (no `Code/` module, no row in the inventory `/shared/etcd-grove-triage/coord/verified.txt`).
The v3.3 code has been rewritten into `server/proxy/grpcproxy` since then, but the watch
broadcast's structure is the same at the pin `107edf7e4`, so the candidates below are checked
against that code:

| Candidate cause (at the pin) | Explains | Class |
|---|---|---|
| a broadcast whose backend watch ended stays registered and keeps taking watchers (`watch_broadcast.go:71-74`, `watch_broadcasts.go:53-80`; etcd#21813, etcd#18231) | events missed with no error | O-pkg, present |
| the backend's final `Canceled` response is dropped by `watcher.send` (`watcher.go:106-108`) | the client never learns its watch ended | O-pkg, present |
| `watcher.post` gives up after 50 ms and cancels the whole proxy stream (`watcher.go:123-131`) | not silent: the client's stream ends, and the client re-watches, which can look like a delay | O-pkg, present by design |
| a backend reconnect: the client re-watches from the last revision it got (verified, `watchGRPCStream.run`) | delay only | as designed, verified |

The first candidate is the likeliest: a silent loss with no error log is exactly its symptom. The
verified backend client is on the path, `clientv3.watcher.Watch` (verified, sorry-free). Its spec
allows the channel to close (`Spec/go_etcd_io/etcd/client/v3/watcher__Watch.lean`), and the proxy
mishandles that close.

## Proposal: `grpcproxy-watch-relay` (see `etcd-21813.md`)

Verify the proxy's watch path against the client's watch spec. The statement says that each proxy
watcher gets the backend's events in its range from its start revision on, gap-free, or a
`Canceled` response. It would exclude the first two candidates. Delays (the last two) are
liveness and stay outside Iris-style specs.

## Findings

None new. The likely cause is the one recorded upstream as etcd#21813.
