# etcd-io/etcd#20434: Antithesis found "update of consistent index not advancing"

- URL: https://github.com/etcd-io/etcd/issues/20434 (closed 2025-09-29: "Antithesis marked the
  issue as resolved"; label `type/bug`)
- Affected: `main` (3.6 development), under Antithesis fault injection. The assertion is
  `schema.unsafeUpdateConsistentIndex`'s `verify.Verify("update of consistent index not
  advancing")` (`currentIndex` 100, `previousIndex` 105).
- Fix: none. ahrtr (on #20426) called it "actually the same issue as #20426", caused by "a bad
  snapshot". The assertion is still in the pinned code (`server/storage/schema/cindex.go:76-84` at
  `107edf7e4`).

What happened (from etcd1's log in #20426's thread). etcd1 has applied index 105, and its old db
stores `consistent_index` 105. It receives a snapshot at index 106 whose db stores
`consistent_index` 100. `applySnapshot` opens the new backend, calls `ci.SetBackend(newbe)` (which
resets the in-memory index to 0), and the "restored mvcc store" log line re-reads it from the new
db: 100. Then it closes the old backend in a goroutine (`oldbe.Close()`, server.go:1088-1097). The
assertion fires between "closing old backend file" and "closed old backend file". The old
backend's final commit runs its pre-commit hook. That hook is the server's shared
`BackendHooks.OnPreCommitUnsafe` → `ci.UnsafeSave(tx)`, which writes the *new* backend's index
(100) into the *old* backend's `Meta` bucket, whose stored index is 105.

## Classification

**A-pre (diagnosis unsettled; secondary N: closed without a fix, declared a duplicate).** The code
that fired is verified. `schema.unsafeUpdateConsistentIndex` is proved, and its spec makes the
caller show `stored ≤ index` (`Spec/go_etcd_io/etcd/server/v3/storage/schema/unsafeUpdateConsistentIndex.lean:34`).
Every proved caller discharges that through the apply protocol of *one* backend (`commit_save_au`,
`InvApply.lean:472`; `ci_hook_backend`, `CindexBackend.lean`). The run is outside every premise:
the snapshot branch of `applySnapshot`, which swaps the consistent index's backend while the old
backend still has the same hook, is excluded by raft's no-snapshot contract (`rnApP`:
`⌜ap.snapshot' = null⌝`, `Proof/.../etcdserver/InvRaftNode.lean:682`). Followers that fall behind
compaction receive snapshots, so real deployments violate this premise.

Source of verification states: `verified.txt`.

## Does the spec exclude it? (step 4)

1. **Observed behavior, as the spec sees it.** A commit of backend B_old runs `ci.UnsafeSave` with
   `ci = 100` while B_old's stored index is 105. In the proof, the hook's precondition
   (`hookFnSpec`) holds the batch-lock resource `batchLockInv γA (metaTM γB P)` of *the*
   backend whose ghost mirror the consistent index tracks. Under that resource, `ci ≥ stored`
   holds because `ci` only grows between saves (`InvApply.lean`, the protocol). After
   `SetBackend`, the consistent index belongs to B_new. B_old's hook still points at the same
   `ci`, but no ghost state relates B_old's stored index to the new `ci`.
2. **Premises.** `applySnapshot.spec` takes `taSnapshotAddr ap ↦□ null`, which comes from `rnApP`
   (`InvRaftNode.lean:679-683`). The run has `ap.snapshot ≠ nil`, so the premise is violated:
   **A-pre**. The premise is recorded in STATUS (request path, unit 4b: "under raft's no-snapshot
   contract") and in raft's `ownRawNode` `snap = none` (`raft-pending-snapshot-ready`).
3. **Assumptions.** None of the axioms is involved. `verify.Verify`'s spec requires the condition,
   so the assertion is not assumed away.
4. **The trigger.** For the assertion to fire, the new db's index (100) must be below the old db's
   stored index (105). With a good snapshot, the new index is ≥ `snapi` > the receiver's raft commit.
   A leader sends a snapshot only when it has compacted past the follower's log, and so past
   anything the follower's db can have committed. The firing therefore needs the bad snapshot of
   #20426's case 2 (db index < snapshot index), whose cause is undiagnosed. I found no fault-free
   path at the pin that produces one. The proofs of `applyEntryNormal` and the commit protocol give
   the sender `ci ≥` every applied index once an entry is applied (`etcd-21636.md`), but
   `createMergedSnapshotMessage` is an axiom (`etcd-20426.md`).

So this is not an X: no proved statement covers the run. The writing of the new index into the
discarded backend is present at the pin. It is harmless: the old db file has been replaced by the
renamed snapshot db, `Verify` is off in production, and `UnsafeSave` skips index 0. It would be a
proof obstacle for the proposal, though: the old backend's commit-at-close runs a hook whose ghost
state now belongs to the new backend.

## Proposal: `server-apply-snapshot` (see `etcd-20426.md`)

In addition to what `etcd-20426.md` lists, the receiver's proof must handle the old backend.
Either the old backend's final commit is proved to store an index `≥` its stored one, which
requires the snapshot premise `new db index ≥ old stored index` (true when `snapi` > the receiver's
committed index ≥ its db's index; this needs the `a ≤ ci` and `ci ≤ committed` bounds, the second
one false after a crash: `crash-restart-model`), or the fix is in the code: detach the hook from
`oldbe` before `Close`, or use `UnsafeUpdateConsistentIndexForce` there. The second option makes
the assertion's premise local to one backend and keeps the proof per-backend. Cost: part of
`server-apply-snapshot` (large); the old-backend part is small, since `backend.Close` is already proved (the work is the ghost hand-over of the hook's resource at `SetBackend`).

## Findings

No `issues/` file. The trigger is an undiagnosed bad snapshot. The one mechanism present at the
pin, the old backend's close writing the new index into the discarded db, is harmless in
production, and I could not make it fire from a good snapshot. A candidate for `issues/` only if a
fault-free reproduction of the bad snapshot appears.
