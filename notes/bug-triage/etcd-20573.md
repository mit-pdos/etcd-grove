# etcd-io/etcd#20573: Antithesis found Watch failure

- URL: https://github.com/etcd-io/etcd/issues/20573 (filed 2025-08-27, closed 2025-11-20 by
  serathius, "No failures for long time", after the stale bot).
- Affected: `main` at the time, under the Antithesis robustness setup. No version was given.
- Observed: the watch validation failed with "broke Resumable". The dump (henrybear327) has
  `client-2` receive a `put` of `/registry/pods/default/yOJfD` at revision 2, but that key's
  revisions are 132, 152 and 155, and revision 2 belongs to another key.
- Diagnosis: **not settled in the thread**. On 2025-09-20 serathius reproduced a watch failure with
  a modified robustness test (branch `serathius:robustness-reproduable`). A watch created with
  `start_revision: 13`, unsynced, was next sent the events `52-52`, so it skipped revisions 13 to
  51. Two days later he opened PR #20693, "Reject watch request with -1 revision to prevent invalid
  resync behavior on uncompacted etcd and make rangeEvents safe against negative revision"
  (`afeab20ac`, merged 2025-09-23 as `c9d4602c7`; backports #20709 and #20711). The PR says the
  issue was found with that same branch. The PR does not name #20573, and nothing in the thread
  links the original Antithesis dump to it.

What goes wrong in the #20693 mechanism (pre-fix code): `serverWatchStream.recvLoop` passed any
`StartRevision` to `watchStream.Watch`. `watchableStore.watch` puts a watcher with
`startRev = -1` in the unsynced group (`minRev = -1`). On a store that was never compacted,
`compactMainRev = -1`, so `chooseAll`'s `w.minRev < compactRev` test does not reject it. The next
`syncWatchers` takes the group's minimum, `minRev = -1`, and calls `rangeEvents(-1, curRev+1)`.
`RevToBytes` encodes `-1` as the largest key, so the range is empty. Every chosen unsynced watcher
then gets no events and moves to the synced group at `curRev + 1`, which silently skips its
history. That fits the reproduction's `startRev 13 → events 52-52` exactly.

## Classification

**F (fixed before the verified code), F+ for the server-side cause.** The diagnosis is unsettled,
so the candidates are classified separately below. #20693's commit `afeab20ac` is an ancestor of
the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes). Counterfactually, the specs exclude
the pre-fix code. `watchStream.Watch` and `watchableStore.watch` require `0 ≤ startRev`
(`Spec/go_etcd_io/etcd/server/v3/storage/mvcc/watchStream__Watch.lean:45`,
`watchableStore__watch.lean:42`). `recvLoop`'s proof discharges that premise *only* through the
fix's `creq.StartRevision < 0` branch (`Proof/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/serverWatchStream__recvLoop.lean:243`,
"a negative start revision: the compacted response"; `hsr0 : 0 ≤ sint.Z c.startRev` at `:312` is
derived from that branch's condition). Without the branch, the proof of the pre-fix `recvLoop`
breaks at `:312`.

The candidate causes:

| Candidate | Class | Why |
|---|---|---|
| a watch at revision `-1` (PR #20693) | F, **F+** | as above; it is the one cause the maintainers reproduced |
| the robustness client's slice race (`6fd984fd6`, 2025-09-12, the cause of etcd#20655) | N | a test-harness bug that loses or misplaces recorded responses; it was present when the Antithesis run was reported (2025-08-27) and fixed 2025-09-12 |
| the dump's "wrong key at revision 2" event | unexplained | neither mechanism above produces an event with another key's revision; no further data in the thread |

## The counterfactual (step 5)

What the bug looks like to the specs: a watcher `w` with `startRev = 13`, unsynced, and a second
watcher with `startRev = -1` in the same group. `w` then receives an event at revision 52, although
revisions 13 to 51 hold events in its range. The exported watch result forbids that. `watchRecvOk_cert`
(`Proof/.../mvcc/WatchRecv.lean:407`) says the client received exactly the changes in the
watcher's range from its first revision on, in order and once each, up to some revision. `rangeEvents.spec` returns exactly
`logEvents log minRev maxRev` filtered (`rangeEvents.lean:46-50`).

Where the proof keeps `-1` out:

1. `rangeEvents.spec` requires `0 ≤ minRev` (`:42`). The pre-fix `rangeEvents` with `minRev = -1`
   returns `[]` and not `logEvents log 0 maxRev`, so the premise is necessary. The fix's clamp to
   `0` in `rangeEvents` is not used by the spec.
2. `syncWatchers` gets `0 ≤ minRev` from the watch invariant. Each registered watcher carries
   `⌜0 ≤ sint.Z r.startRev⌝` (`storeWatchParams.IW`,
   `Proof/.../mvcc/InvWatchStore.lean:762-763`), established by `watchableStore.watch`'s premise.
3. `recvLoop` meets that premise only because of the fix's early return (`:243`, `:312`). Pre-fix,
   the step `wp_apply hPerm …` and then `watchStream.Watch` with `c.startRev = -1` has no proof of
   `0 ≤ startRev`. So the proof of the pre-fix `recvLoop` fails, and it fails for a real reason,
   since step 1 shows the premise is not an artifact.

So the existing specs would have rejected the buggy version. Note that the watch specs' scope is a
never-compacted store (`crevFrozen`). That is exactly this bug's setting: `compactMainRev = -1` is
what let `-1` through `chooseAll`.

## Proposal

None for the server-side cause (F+). The open part is the unexplained dump, which no verification
here addresses without a diagnosis. As a related observation, not a proposal: the fix encodes
"uncompacted" as `compactMainRev = -1`, and the specs carry that sentinel
(`mvcc.crevFrozen`, compaction revision `-1`). Under `watch-under-compaction` (etcd#18089) the
premise `0 ≤ startRev` must stay alongside `compactRev ≤ minRev`, because the latter alone admits
`-1` before the first compaction.

## Findings

None for `issues/`: the bug is fixed at the pin. No bug in this repository's specs.
