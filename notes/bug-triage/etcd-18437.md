# etcd-io/etcd#18437: something wrong with simple_token

- URL: https://github.com/etcd-io/etcd/issues/18437 (closed 2024-08-21; labels `type/bug`,
  `area/documentation`, `help wanted`, `good first issue`)
- Affected: v3.5.14 (the report), with a 3-member cluster and about 200 ms RTT. A fresh simple
  token used at once on another member fails with `invalid auth token`. Upstream outcome: the
  maintainer confirmed it and attributed it to token validation in the API layer not being
  linearizable. The issue was closed after a documentation note (etcd-io/website#883, "known
  issue" on simple tokens). No code fix.

What goes wrong, in Go terms. A simple token is `"<prefix>.<index>"`.
`tokenSimple.isValidSimpleToken` (`server/auth/simple_token.go:229-245`) waits on
`indexWaiter(index)`, which is `applyWait.Wait` (`server/etcdserver/server.go:355-358`), before
`info` looks the token up. The design is that a member which receives the token waits until it
has applied the entry that issued it. But the index comes from `applierV3backend.Authenticate`
(`server/etcdserver/apply/backend.go:157-163`), which passes
`a.options.ConsistentIndex.ConsistentIndex()`. While an entry is being applied, that is still
the *previous* entry's index:

- `applyEntries` sets only the applying index (`SetConsistentApplyingIndex(e.Index)`,
  `server.go:1908`);
- the stored index moves later, in the post-lock hook (`server.go:2448-2455`) or after the entry
  (`server.go:1945-1948`), and `Authenticate` takes no batch lock before it reads it.

So the Authenticate entry `e` issues a token naming `e-1` (or lower). A member that has applied
`e-1` but not `e` finds `applyWait` already triggered for `e-1` (`server.go:984`), looks up a
token it has not assigned yet, and returns `ErrInvalidAuthToken` at once instead of waiting. The
reporter's log shows exactly this: the entry is 19146857, the consistent index 19146856, and the
token is `….19146856`. This is a regression from 3.5.3: up to 3.5.2 `applyEntryNormal` stored
`e.Index` before applying (v3.4/v3.5.0 `server.go`). The change came with `66c7aab4d` ("fix the
data inconsistency issue by adding a txPostLockHook", #13844, the fix of #13766), which made the
stored index lag during apply.

## Classification

**O-fn (secondary C-err); present at the pin, reproduced.** The off-by-one is at the pin
(`backend.go:158`, unchanged on upstream `main`). The verified functions on the path admit it:

- `applierV3backend.Authenticate.spec` says nothing about the token or the context it passes;
- `authStore.AuthInfoFromCtx.spec` allows `ErrInvalidAuthToken` for any token;
- the token provider is a contract (`tokenProviderOk`: `info` returns any auth info and
  boolean);
- `tokenSimple`, the code that interprets the index, is not translated.

Upstream treated it as N (documented known issue). The documented cause, a non-linearizable
check, is not the whole story: the index the check waits for is wrong, and with the right index
the wait would close the window this report hits.

Source of verification states: the inventory
`/tmp/claude-0/-shared-etcd-grove/c22270a5-a99f-4bfe-8204-a0d29e5800a4/scratchpad/verified.txt`.

## The argument (step 4)

The observed behavior, as the specs see it: member B, with auth enabled and a token in the
context, calls `AuthInfoFromCtx` and gets `(nil, ErrInvalidAuthToken)`. Meanwhile member A has
applied, at index `e`, the Authenticate entry that issued the token.

- No premise is violated. The default token type is `simple` (`--auth-token`), and the request
  path is the verified one.
- `AuthInfoFromCtx.spec` concludes `authInfoRO a ∗ authErrIs err`, and `authErrIs` admits
  `ErrInvalidAuthToken` (`InvAuth.lean`, `def authErrIs`). It allows the outcome whatever the
  token. The contract `tokenProviderOk` says `info` returns some `(a, ok)`.
- `applierV3backend.Authenticate.spec` concludes only `mPost … ∗ applyErrIs err`. The context it
  builds is not mentioned, and the store's `Authenticate` is a contract taking any `ctx`
  (`Contracts.lean:183-187`).

So the outcome satisfies every spec on the path. The property the user expects is: "a token
issued at entry `e` is accepted by any member once that member has applied `e`, and a member
that has not yet applied `e` waits for it". It is not stated anywhere, and it cannot be stated
without a model of the token provider. The ingredient that makes it fail is in the verified
part, though. The cindex specs already separate the stored index (`ciIdx`, what
`ConsistentIndex()` returns) from the applying one (`ConsistentApplyingIndex`). The apply
thread's invariant knows the stored index is below the entry being applied, so a spec that
names the token's index would fail on `backend.go:158` as written.

Reproduced at the pin: a Go test in `server/etcdserver/apply` (in
`issues/etcd-simple-token-index-off-by-one.md`). With the stored index 9 and the applying index
10, `Authenticate` issues `prefix.9`. A second store whose waiter reports index 9 applied returns
`ErrInvalidAuthToken` after 28 µs without waiting.

## Proposal: `simple-token-index` (new)

Two steps, small then medium:

1. In the apply model, `applierV3backend.Authenticate.spec` states the context it hands the
   store: `AuthenticateParamIndex = i` where `ciApplying γ i` is the entry being applied (the
   cindex ghost state has it). This fails at the pin (`ConsistentIndex()` returns `ciIdx`,
   which is less than `i`), and holds after the fix `ConsistentApplyingIndex()`. Cost: small. Only
   the spec and the proof of `Authenticate` change, plus the store contract's `Authenticate`
   precondition on `ctx`.
2. Translate `simple_token.go` (about 250 lines; `simpleTokenTTLKeeper` uses a timer) and
   replace `tokenProviderOk` with a ghost map of issued tokens. `assign` at index `i` records
   `tok ↦ (user, i)`, and `info` returns `ok` for a token whose index has been applied
   (`indexWaiter`'s channel closed ⇒ the apply thread is past `i`). Together with step 1, this
   gives "a member that has applied the issuing entry accepts the token" (until TTL expiry,
   which needs a clock: state it with the keeper as an unconstrained revocation). Cost: medium.
