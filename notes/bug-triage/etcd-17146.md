# etcd-io/etcd#17146: v3.4 broke the `snapshot.Metadata.Index ≤ db.consistentIndex` invariant

- URL: https://github.com/etcd-io/etcd/issues/17146 (closed 2025-07-09 as stale; labels `type/bug`,
  `stale`, `release/v3.4`)
- Affected: etcd v3.4.21. An overloaded member was killed by its liveness probe. On restart it
  crash-looped with `failed to recover v3 backend from snapshot`: the db's consistent index was
  below the index of the last snapshot (1357226403, taken 1.5 minutes before the kill), so
  bootstrap looked for `<index>.snap.db`, which did not exist. A second panic, a nil dereference in
  the error path, followed.
- Fix: none for the cause, which is undiagnosed. The maintainer "not sure how it's possible"; the
  db was purged, and hardware or unflushed writes were suspected. Follow-ups for the error path
  and logging: #17151 (release-3.5), #17154 (release-3.4: nil backend check), #17152 and #17153
  (`main`: logs and an e2e test of bootstrapping with an older db). Related open issue: #18055
  (panic when two snapshots are received in a short period).

## Classification

**A-model (diagnosis unsettled; secondary O-fn).** The invariant the restart checks (db index ≥
the snapshot's index) depends on durability across a kill: bolt's commit and `fsync` against the
snap file and the WAL. Crashes and disk durability are not modeled here (`crash-restart-model`).
Without crashes, the pinned code (on `main`, which replaced 3.4's) keeps the in-memory index
at the applied index after each entry, proved, but the function that commits and then saves the
snapshot (`EtcdServer.snapshot`) is an axiom, and bootstrap is not translated (O-fn). So no
statement here covers either the kill or the step that establishes the invariant. A 3.4-specific
code cause of the class of `etcd-21636.md` or `etcd-19571.md` (an entry that advances the
applied index but not the stored consistent index) would be F, and F+ for the alarm case. Nothing
in the report points to one: no alarm, no membership change, and the snapshot log shows a normal
`triggering snapshot`.

Source of verification states: `verified.txt`.

## Argument (step 4)

The observed state after the restart: snap file at index S = applied index at the snapshot, and db
stored index c < S. On `main`, without crashes, the chain that should exclude it is:

1. after each applied entry, `ci` = its index (`applyEntryNormal.spec`'s postcondition
   `applyThread γ ⟨m.index, m.index, …⟩`, `EtcdServer__applyEntryNormal.lean:76`; conf changes by the
   axiom `applyConfChange.spec`, `Post ∨ Adv`);
2. `snapshot` commits before `SaveSnap` (server.go:2099, `SaveSnap` at :2117), and a commit saves `ci`
   (`commit_save_au`, `InvApply.lean:472`), so after the commit the stored index is ≥ S;
3. the snap file is written after that commit.

Step 1 is proved. Step 2 is the axiom `EtcdServer.snapshot.wp_proof` (O-fn). Step 3, and the
conclusion that after a kill the db still holds index ≥ S, need a model where a completed bolt
commit survives the kill while the later snap write does too. That is crash semantics and
`fsync` ordering, which is **A-model**. bolt commits with `fsync` and the snap file is written
after it, so in a correct storage stack the inequality should hold. That is why the maintainers
suspected hardware or unflushed writes. The verified code cannot decide the question, and the
report has no reproduction.

## Proposal: `server-snapshot-ci-latest`, then `crash-restart-model`

- **`server-snapshot-ci-latest`** (no crashes; see `etcd-21636.md`): add `a ≤ ciEff k` to
  `loopOk` and prove `EtcdServer.snapshot`. Its `KV().Commit()` stores an index ≥ `ep.appliedi`
  before `SaveSnap`, and `verifyConsistentIndexIsLatest` never fires. Small to medium. It confines
  this bug class to durability: any remaining violation needs a crash.
- **`crash-restart-model`** (existing): a crash step that keeps the committed bolt state and the
  fsynced WAL and snap files, plus bootstrap's `RecoverSnapshotBackend` proved to pick a backend
  with stored index ≥ the snapshot's. Large. It needs crash semantics that Perennial's Lean port
  lacks (a separate Perennial proposal, CLAUDE.md "Changes to Perennial").

## Findings

None. The cause is undiagnosed, and the `main` code on the path is either proved without crashes
or untranslated.
