# etcd-io/etcd#21536: experimental cache: Get(WithRev(rev)) can return the wrong value

<https://github.com/etcd-io/etcd/issues/21536>. Filed 2026-03-27 by upamanyus against `main`
(3.7.0-alpha.0, `832072d57`). Closed 2026-03-29 by the fix, PR etcd-io/etcd#21540 ("cache: return
correct data when there are revision gaps in the watched prefix"), commit `4f081fb1a` (2026-03-28),
merged as `3efe157f6`. An earlier PR, #21537, which also fixed #21535, was closed unmerged.

**The bug.** `store.getSnapshot(rev)` (`cache/store.go`) chose the snapshot with
`s.history.AscendGreaterOrEqual(rev, ...)`, which is the *oldest snapshot at or above* `rev`. If
there was none, it served `&s.latest`. The cache keeps one snapshot per revision at which something
under its prefix changed, so the history has gaps. Take snapshots at 10 (`/a = b`) and 20
(`/a = c`). Then `Get("/a", WithRev(15))` returned revision 20's value `c`, but etcd's state at 15 is
`b`. The fix walks down instead (`DescendLessOrEqual(rev, ...)`, the *newest snapshot at or below*
`rev`). It also returns `ErrCompacted` when there is no such snapshot, in place of the separate
`PeekOldest` check.

## Classification

**F+** (fixed before the verified code, and the spec excludes the buggy version). The decisive fact:
the fix `4f081fb1a` is an ancestor of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`). At
the pin, `getSnapshot` calls `DescendLessOrEqual` (`cache/store.go:92`). The spec
`store.getSnapshot.spec` fixes the result to `snapModel st rev`, which is "the greatest history
revision at most `rev`". The buggy code returns a different `*snapshot` in a reachable state, so its
proof of `snapCert E p (r, m)` would fail. The Lean-first cache spec was written in 2026-10, after
the fix, so the spec did not catch this bug. But it would have.

## The counterfactual (step 5)

The specs that exclude the buggy version:

- `store__getSnapshot.lean:35-37`: the postcondition is
  `∃ st, storeSeen … st ∗ … ∗ snapErr (snapModel st rev) err ∗ match snapModel st rev with | .ok r m
  => ⌜lrev = st.latestRev⌝ ∗ snapCert E p (r, m) | _ => ⌜p = null ∧ lrev = 0⌝`.
- `InvStore.lean:205` defines `snapModel`. After the `notReady`, `invalid` and `future` cases, it is
  the last element of `st.history.filter (· .1 ≤ rev')`, which is the greatest snapshot revision at
  most `rev'`, or `.compacted` if there is none. `snapModel_ok_spec` (`InvCache.lean:1477`) states
  this: `r ≤ rev'`, and every history revision `≤ rev'` is `≤ r`.
- `snapCert E p (r, m)` contains `snapIs p (r, m)` (`InvStore.lean:706`), and that contains
  `p ↦□ snapshot.mk r t`.

Take the issue's state: history `[(10, m10), (20, m20)]`, `latestRev = 20`, and a call with
`rev = 15`. This state is reachable by the cache's own writers: `Restore` at 10, then an `Apply` of
a batch at 20. `snapModel st 15 = .ok 10 m10`. The buggy code's `AscendGreaterOrEqual` gives the
history item `p20`, whose ring item predicate is `snapIs p20 (20, m20)`, so `p20 ↦□ snapshot.mk 20
_`. The postcondition needs `p20 ↦□ snapshot.mk 10 _`, and the agreement of persistent points-to
assertions makes that false. The proof breaks at the final `match` arm, whatever invariant is
chosen, because the spec is a functional model. One layer up, `cacheGetOk` (`InvCache.lean:1449-1450`)
would then claim `isEtcdKvs 10 pfx m20` with `m20` = etcd's state at 20. That is false too.

The buggy version breaks the spec in two more ways:

- The fallback `targetSnapshot = &s.latest`, for `newest snapshot < rev ≤ latestRev` (after a
  progress notification), returns a pointer to the store's own `latest` field. That field is not a
  history item, so there is no `snapCert` for it. `snapModel` gives the newest snapshot below `rev`
  instead.
- `&s.latest` is then read by `snapshot.Range` after `RUnlock`. Its `tree` field is replaced by
  `Restore` under the write lock, so this is also a data race. The read-only `snapIs` (`↦□`) could
  not be produced for it.

So this is a definite **F+**. No proof attempt is needed: the counterexample is the issue's own
reproduction, and the obligation is plainly false there.

## Proposal (step 6)

No proposal is needed for the bug itself (F+). It does show a limit of the client-level statement,
worth recording as a possible strengthening:

**`cache-get-state-at-requested-rev`.** `cacheGetOk` says the answer is etcd's state at `r`, the
snapshot that `snapModel` picks, with `r ≤ o.rev`. It does not say the answer is etcd's state *at
`o.rev`* (or at the header revision for `rev = 0`). That is what the user of `WithRev` relies on,
and it is what #21536 is about. The current spec excludes this bug only because `snapModel` is an
exact model of the code's choice of snapshot. A history that missed a snapshot (a gap that hides a
change) would still meet `isEtcdKvs r pfx m`. A sketch of the statement:

```lean
-- in cacheGetOk, in place of / beside `isEtcdKvs r cf.pfx m`:
isEtcdKvs (if o.rev = W64 0 then st.latestRev else o.rev) cf.pfx m
```

To prove it, the store's certificate must become an interval: every history snapshot `(r, m)` is
etcd's state at every revision from `r` up to the next snapshot's revision (or `latestRev` for the
newest snapshot). That means an `EtcdStep r r' pfx []` ("nothing under the prefix changed") between
them. The ingredients exist: `TailOk`/`WriterOk` (`InvCache.lean:268-298`) already carry
`EtcdStep q cursor pfx []` for the writer, and `InvEtcd.lean:385` composes steps with
`isEtcdKvs`. The cost is moderate, about a few hundred lines. `E`/`R` would be generalized
(`InvStore.lean`), the certificates asked of `Restore`/`Apply`/`applyProgressNotifyLocked`
re-proved, and `cacheGetOk` and `Cache.Get`'s proof adjusted. Nothing about Perennial blocks it.
