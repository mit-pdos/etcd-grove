# etcd-io/etcd#18933: Etcd cluster keeps getting corrupted on Talos since version 1.8.x upgrade (etcd 3.5.16)

- URL: https://github.com/etcd-io/etcd/issues/18933 (closed 2025-01-16; `type/bug`)
- Affected: v3.5.16 on Talos 1.8.3 (3 nodes, home lab; a second reporter on VMware). After several
  hours, every request fails with `etcdserver: corrupt cluster`, the `CORRUPT` alarm. The logs
  start after the alarm, there is no db file, and no cause was identified.
- Fix: none. In the sig-etcd triage it was converted into a support discussion ("no clear
  reproducible bug on the project side").

## Classification

**N (no diagnosed bug: a support case); if a bug, O-pkg / A-model.** The only evidence is the
reaction to an alarm: the `CORRUPT` alarm makes the server install `applierV3Corrupt`, which answers
every request with `ErrCorrupt`. That part is verified and documents the observed behavior. The
`applierV3Corrupt.{Put,Range,DeleteRange,Txn,Compaction,LeaseGrant,LeaseRevoke}` specs
(`Spec/go_etcd_io/etcd/server/v3/etcdserver/apply/applierV3Corrupt__*.lean`) are proved sorry-free
over the corrupt chain (`.corrupt c`). What raised the alarm, a hash mismatch between members, is
undiagnosed. The hash checkers (`EtcdServer.monitorKVHash`, `monitorCompactHash`) are assumed, and
the divergence itself would come from bbolt, the disk or a crash. None of these is verified or
modeled here (compare `etcd-17084.md`, `etcd-18096.md`).

## Proposal

— (no bug to exclude). If a divergence were diagnosed, the relevant proposals are `model-kv-hash`
(the checker compares the right hashes) and `bbolt-kv-contract`/`fs-crash-model` (the divergence
cannot arise below the apply thread).
