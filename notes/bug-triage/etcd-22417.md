# etcd-io/etcd#22417: client/v3/leasing: clear RangeResponse.Count after deleting a cached key

<https://github.com/etcd-io/etcd/issues/22417>. Filed 2026-09-11 against `main` (`e041c4fa2`) and
still open. Three open PRs carry the same one-line fix: #22418, #22507 and #22585. None is merged.

**The bug.** `leaseCache.delete` (`client/v3/leasing/cache.go:160-165`) clears the cached
response's `Kvs` and leaves its `Count`. Every cached answer copies `Count`
(`leaseKey.get` → `copyGetResponseMetadataOnly`). So after `Delete("k")` through the leasing KV,
`Get("k")` returns `Kvs = []` with `Count = 1`, and a `WithCountOnly` get answers 1 for a deleted
key.

## Classification

**C-obs** (the buggy code is verified at the pin, and the spec states the stale field). The bug
is present at the pin `107edf7e4` (`cache.go:162` sets only `Kvs = nil`) and on upstream `main`.
The spec of `Delete` keeps `count` (`LeaseEntry.del`, `InvLeaseCache.lean:192-195`), and the cached
get returns it (`freshGetResp … e.count …`). The client-level theorems tie only the returned
key-value to etcd's record. `Count` is a field the specs carry but no statement constrains, which
makes this C-obs rather than C-other. Reproduced at the pin by a unit test (below).

## The argument (step 4)

1. The observed run: a cached entry `e` with `e.kvs = [k↦v]`, `e.count = 1`. Then
   `leaseCache.Delete(k, hdr)` with `hdr.revision ≥ e.hm.revision`, then a cached `Get(k)`.
2. Premises: none fails. The run is the issue's own single-client sequence, and the protocol
   premise `LeasingProtocol` is irrelevant.
3. Assumptions: no axiom is involved (the cache is plain memory under `lc.mu`).
4. The postconditions allow it. `leaseCache.Delete.spec`
   (`Spec/.../leaseCache__Delete.lean:32`) moves the state to `st.modify key (fun e => e.del h' hm)`.
   `LeaseEntry.del` (`InvLeaseCache.lean:192-195`) is
   `{ e with kvsSl := slice.nil, kvs := [], hdr := h, hm := hm }`, which keeps `e.count = 1`. The
   cached get, `leaseCache.Get.spec` (`Spec/.../leaseCache__Get.lean:41-42`) and `getCached`
   (`InvLeasingKV.lean:414-417`), returns `freshGetResp ret e.hm e.more e.count (getResult o e)`,
   and `freshGetResp` (`InvLeaseCache.lean:570-578`) writes `Count ↦ count`. So the spec
   *derives* `Kvs = [], Count = 1`. What the user expected, "the answer is etcd's", is stated only
   for the key-value: `leasing_getResult_acq` and `leasing_cached_get_stable`
   (`Results.lean:180-196`) speak of `getResult o e` and `e.acq`. No statement compares `Count` (or
   `More`) to etcd's response, and no invariant ties `e.count` to `e.kvs` (`LeaseCacheWf`,
   `InvLeaseCache.lean:240-247`).

Reproduction at the pin (scratch worktree of the fork at `107edf7e4`, a test in package
`leasing`; the code is in `issues/leasing-delete-keeps-count.md`): `TestTriageDeleteKeepsCount`
fails with `len(Kvs)=0 Count=1`.

## Proposal: `leasing-cached-resp-count`

Make the cached response's metadata part of what the cached-read theorems state:

```lean
-- LeaseCacheWf (InvLeaseCache.lean), a new conjunct, for entries and frozen entries:
count_kvs : ∀ k e, st.entries !! k = some e → e.count = W64 e.kvs.length ∧ e.more = false
-- getCached / leasing_getResult_acq, strengthened: the whole answer is etcd's RangeResponse for o
-- at e.rev (Kvs = rangeSel, Count = the range's size) when e.kv = e.acq
```

Cost: small, around 100 lines. The conjunct is preserved by `Add` (the acquisition's response is a
single-key get: its `Count` comes from the client contract's `rangeBodyOwn … count`,
`InvEtcdTxnOwn.lean:354-360`, provided the contract ties `count` to the selection's size, which I
did not check) and by `Update` (`count := 1` when it appends, `InvLeaseCache.lean:175`). Its proof
fails on `del` at the pin, which is the bug, and goes through with the fix. That would also
classify the code at the pin as a finding instead of a silently specified behavior.
