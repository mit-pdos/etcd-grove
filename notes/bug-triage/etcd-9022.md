# etcd-io/etcd#9022: functional-tester: fail with "found data inconsistency with peers"

- URL: https://github.com/etcd-io/etcd/issues/9022 (closed 2017-12-18; labels `type/bug`,
  `area/functional-testing`).
- Affected: `master` of December 2017 (pre-3.3), from PR #8922 ("enable initial corrupt check in
  tests") on; found by the functional tester after "kill majority of the cluster": the restarted
  member's `HashKV` differed from its peers' at the same revision and compaction revision, and the
  corruption check stopped it.
- Fix: PR #9031, "mvcc: fetch revisions with current revision, not 0, in HashByRev" (`2e95ace82`,
  merge `95ecf9602`, 2017-12-18).

What goes wrong (pre-fix code): `store.HashByRev(0)` (`mvcc/kvstore.go`, today `store.hashByRev`)
computed `keep := s.kvindex.Keep(rev)` *before* replacing `rev == 0` by `currentRev`. `Keep(0)`
is empty (no revision is `≤ 0`). The hash loop skips a bucket revision below `compactRev + 1`
only if it is not in `keep` *and* `len(keep) > 0`; with `keep` empty it hashes every revision
below the compaction revision that the bucket still holds. How many those are depends on how far
the asynchronous `scheduleCompaction` has deleted them — a member that just restarted (and resumed
its compaction) and its peers hash different sets, and the initial and periodic corruption checks
(`HashByRev(0)` locally, `HashKV(rev)` remotely) report a false inconsistency.

## Classification

**F (fixed before the verified code); counterfactual F−, gap O-fn.** `2e95ace82` is an ancestor of
the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes); at the pin `hashByRev` sets
`rev = currentRev` before `s.kvindex.Keep(rev)` (`server/storage/mvcc/kvstore.go:183-186`).
Counterfactually nothing here covers the buggy caller: `store.hashByRev` and `unsafeHashByRev` are
not translated, and the hasher is assumed with a spec that says nothing of the hash. But the
callee's existing spec already excludes the buggy call: `treeIndex.Keep.spec` requires
`c ≤ rev` with `c` the store's compaction revision (`crevUB γ q c`), so `Keep(0)` after any
compaction is outside its premise — verifying `hashByRev` against it would make this bug F+.

Source of verification states: `verified.txt` (`etc/verified-code.py`, at `d606c9cac`).

## The counterfactual (step 5)

The pre-fix `HashByRev(0)` calls `Keep(0)`. `treeIndex.Keep.spec` (`treeIndex__Keep.lean:28-35`)
has the premise `mvcc.crevUB γ q c ∗ ⌜-1 ≤ c ∧ c ≤ sint.Z rev ∧ …⌝`, where `crevUB γ q c` is a part
of the compaction revision's authority *at* `c` (`Proof/.../mvcc/InvIndex.lean:627-630`: "whoever
holds a part knows the compaction revision is `c`"). Once the store has been compacted
(`c ≥ 1`), `c ≤ 0` fails: a proof of `hashByRev` would be stuck at the call. (Before any
compaction `c = -1` and `Keep(0)` is legitimate, and the bug is harmless: nothing is below
`compactRev + 1 = 0`.) So the specs that exist are strong enough at the one verified function on
the path; the gap is that the caller is not translated (O-fn), and that the hasher's specs carry no
content — even a verified `hashByRev` would have no postcondition stating *which* revisions it
hashes, which is what the corruption check relies on.

## Proposal: `model-kv-hash` (existing)

As in `notes/bug-triage/etcd-15919.md` and `etcd-18337.md`: a pure `kvHashIn log c r`, the crc
opaque, and `HashByRev rev` returns `⟨crc (kvHashIn log c rev'), c, rev'⟩` with `rev' = rev` or
`currentRev` for `0` — a function of the log, not of how far the bucket's compaction has
progressed. The buggy code fails it twice: at `Keep`'s premise above, and because with `keep = ∅`
the hashed set depends on the thinned bucket (`keyReaderD … (delKey γ)`), not on `log`. This
bug is the simplest instance of the proposal (cost as there: medium, translate `hash.go`'s
`unsafeHashByRev` and `store.hashByRev`).
