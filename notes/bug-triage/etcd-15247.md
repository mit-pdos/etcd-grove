# etcd-io/etcd#15247: All leases are revoked when the leader is stuck handling raft Ready (slow fdatasync)

- URL: https://github.com/etcd-io/etcd/issues/15247 (closed 2024-02-23; labels `type/bug`,
  `priority/important-soon`). Reported on 3.4.3; 3.4, 3.5 and `main` affected.
- Fix: PR #16822 "Ignore old leader's leases revoking request" (merge `4e986363a`, 2023-12-15;
  commits `67f17166b` "Safeguard lease operations by double checking the leadership",
  `f7ff898fd`); backports to 3.5/3.4 were requested in the thread (the cross-referenced PRs
  #17425, #17465, #17480 among them; not checked here).

What goes wrong (pre-fix): the leader's raft loop blocks in the WAL's `fdatasync` while processing a
`Ready`. Raft steps down and a new leader is elected, but the old leader's server never sees the
`SoftState` change, so it never calls `lessor.Demote()`: its lessor stays primary. (1) Its expiry
loop (`lessor.runLoop` → `expiredC` → `EtcdServer.revokeExpiredLeases`) keeps proposing
`LeaseRevoke` for leases whose keep-alives now go to the new leader; once the disk returns, the
proposals are forwarded and committed, and those leases are revoked. (2) Clients connected to the
old leader keep renewing there (`EtcdServer.LeaseRenew` checks only `s.isLeader()`), while the new
leader, which never sees those renewals, expires their leases. The fix adds
`EtcdServer.ensureLeadership` (a linearizable read-index round plus `raftStatus().Lead == self`)
before the expiry loop's revocations, before `LeaseRenew`'s local renewal, and in the checkpointer
(which now returns an error that `Renew` and `checkpointScheduledLeases` honour).

## Classification

**F (fixed before the verified code); counterfactual F−, gap O-fn and A-model.** `4e986363a` is an
ancestor of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes); at the pin
`EtcdServer.LeaseRenew` calls `ensureLeadership` (`server/etcdserver/v3_server.go:503`), as does
`revokeExpiredLeases`. The specs would have admitted the buggy version: `revokeExpiredLeases` is a
names-only axiom whose postcondition is `True`, `LeaseRenew` and `ensureLeadership` are not
translated, and `lessorOk`'s `Promote`/`Demote` are `{{ True }} … {{ True }}`. Beneath that, what
went wrong is a statement about time (a lease kept alive within its TTL is revoked), which the
model cannot express: Perennial has no clock, and the KV model treats an expiry revocation as a
step any client has agreed to.

## The counterfactual (step 5)

Pre-fix, `revokeExpiredLeases`'s goroutine skips the leadership check and `LeaseRenew` renews
whenever `s.isLeader()`. Against the existing statements:

- `EtcdServer.revokeExpiredLeases.spec` (post `True`) holds of both versions as an axiom; `run`'s
  proof passes it the slices `ExpiredLeasesC` yields, which carry no logical content.
- No spec of `LeaseRenew` or of the keep-alive path exists; the client side's `isEtcdLease`
  (`Proof/go_etcd_io/etcd/cache/v3/InvEtcdTxn.lean:1121`) promises nothing of `KeepAlive`'s channel
  (`isChanAny`), and `notes/decisions.md:1476` ("Leases without liveness") rejected modelling TTLs
  and expiry.
- The KV model has no lease table yet (unit T3, `decisions.md:6621`); its plan makes expiry
  revocations authorised by the client's agreement to any revocation ("Leases may expire at any
  time"). Under that design both cases of the bug are allowed steps: the revocation is a committed
  `LeaseRevoke`, and the apply thread applies it exactly as specified.

So F−. The gap is two-fold: the functions are unverified (O-fn), and the property is about time
(A-model: clocks are not modelled; `time.Now` is an arbitrary value).

## Proposal: `verify-lease-expiry-leadership` (clock-free), then `lease-clock-model`

The clock-free part, which would have caught this bug's mechanism (an old leader acting as
primary): translate `EtcdServer.revokeExpiredLeases`, `ensureLeadership` and `LeaseRenew` with
bodies and prove that each revocation the expiry loop proposes, and each local renewal, follows a
successful read-index round in which this member was the leader of the round's term:

```lean
-- revokeExpiredLeases: every LeaseRevoke it proposes is preceded, after the expiry decision,
-- by a confirmed leadership of this member
{{ isServerReq s γ ∗ … }} s.revokeExpiredLeases(leases)
{{ RET #(); True }}   -- and the goroutine's proposals carry a witness
   ∃ t, leaderAt γ t (s.MemberId()) ∗ readConfirmedAt γ t   (from LinearizableReadNotify's spec)
```

reusing the verified `LinearizableReadNotify` and the read loop's `rdFresh`/read-index results.
Cost: medium (three server functions; the witness has to be carried into the proposal, which the
T3 lease model needs anyway: the expiry loop's revocations are the "revoke-anything" credit's
deposits). This also replaces the axiom `EtcdServer.revokeExpiredLeases.wp_proof`.

The full property — a lease whose keep-alives reach the leader at least every TTL is never revoked
— needs `lease-clock-model`: a clock with bounded rate drift (each member's `time.Now` monotone and
within a factor of real time), a ghost real-time, and the lessor's `expiry` related to the
granted/renewed TTL, `Promote`'s extension and `Demote`; plus a liveness-free statement "a
revocation of `id` is proposed only after `id`'s last renewal + TTL (+ election timeout) in real
time". Perennial's Lean port has no time model: a Perennial proposal (CLAUDE.md, "Changes to
Perennial"). Cost: large.

## Side note (trust base, not a soundness alert)

`EtcdServer.revokeExpiredLeases.wp_proof` (pre `isPkgInit`, post `True`) admits any slice, while
the real function starts a goroutine that does a linearizable read and proposes `LeaseRevoke`s
through raft without the proposal credits the raft contract (`srvPropAu`) assumes of every
committed entry. It is harmless at present only because no lease is ever granted in the verified
scope (a grant is non-plain, `decisions.md:6291`), so `expiredC` stays empty in reality; it will
not be once unit T3 adds leases. The same pattern as `EtcdServer.Cleanup`'s axiom (G06, etcd#17223,
proposal `cleanup-backend-quiescence`, which lists auditing the names-only server axioms with `True`
preconditions); `verify-lease-expiry-leadership` replaces this one.
