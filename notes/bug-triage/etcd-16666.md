# etcd-io/etcd#16666: --experimental-wait-cluster-ready-timeout causing stale response to linearizable read

- URL: https://github.com/etcd-io/etcd/issues/16666 (closed 2023-10-04)
- Affected: `main` before v3.6.0 only. The flag came in with PR #13525 (`1713dc67b`) and was never in a
  release.
- Fix: PR #16677 (merge `1c5289dd7`) reverts #13525, so `serve` waits on `ReadyNotify()` again with
  no timeout. Reproductions: #16672 (single node, linearizable) and #16678 (merged e2e tests
  `TestCtlV3LinearizableRead`). Alternative fixes, not merged: etcd-io/raft#105 (the read index
  returns the "actually committed" index) and etcd#16675 (sync the HardState before applying).
  Follow-ups: #16673 (bootstrap races) and #16687 (readiness design).

What goes wrong in the pre-fix code: in a single-member cluster that is SIGKILLed, the raftNode
loop (`server/etcdserver/raft.go`) sends committed entries to `applyc` before it calls
`storage.Save(rd.HardState, …)`. So a write can be applied and acknowledged while the WAL still
holds an older `HardState.Commit`. The entries themselves are in the WAL, because the leader
self-acks only after they are persisted. On restart, raft's committed index is that older value.
With the flag, `embed.serve` stopped waiting for `ReadyNotify()` after the timeout, so client
requests were served before `publishV3`'s proposal (an entry of the new term) committed. In that
window, a linearizable `Range` goes through `LinearizableReadNotify` → `ReadIndex`. raft's
single-voter shortcut (`stepLeader`, `MsgReadIndex`, `IsSingleton`) answers with the stale
`raftLog.committed`. The read loop then waits only for that index to be applied, and the server
returns a value older than the acknowledged write. The report has two more parts. Serializable
reads can also go back in time after the restart, which does not violate linearizability. A
third suspected race without the flag was not confirmed and was argued away in the thread
(publish is queued behind the replayed entries).

## Classification

**Class F (fixed before the verified code). Counterfactual: F−. The gaps are A-model (crashes and
durability, which decide the outcome) and O-pkg (`embed`).** The revert `1c5289dd7` is an
ancestor of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes). Both the original
`1713dc67b` and its revert are ancestors. At the pin, `server/embed/serve.go:133-137` again waits
for `<-s.ReadyNotify()` with no timeout. Counterfactually, no spec here excludes the buggy
version, for two reasons:

- The bug needs a crash that loses `HardState.Commit` while the effects of the applied entries
  were already visible. The proofs have no crash semantics (`notes/STATUS.md:1123-1127`: "crashes
  and durability" are out of scope, and the WAL `Save` contract is `True → True`). Restart from a
  WAL is not one of the modeled start paths (`notes/STATUS.md:150-155`, D11).
- The changed code is in `embed`, which is not translated. Its gate, `ReadyNotify`, together with
  `publishV3` (an `axiom`, names-only), is not part of any spec.

## Argument (step 5, counterfactual)

1. **What the bad behavior is, in spec terms.** A client knows a committed bound `c` (its own
   acknowledged write at index `c`). It calls `LinearizableReadNotify` and gets `nil`, but the
   applied index never reached `c` before the range ran. In a single crash-free execution, this
   contradicts `read_notify` (`read/Results.lean`): `nil` only with `readIndexOk γr c`, where
   `committedAtLeast γr c` is the client's knowledge (`read/Inv.lean:7-8`). But the bad behavior
   only happens across a crash. `c` was committed in the execution before the SIGKILL. The model
   has a single execution of fresh nodes with no crash-restart (`notes/STATUS.md:2225`), and the
   ghost `committedAtLeast` does not survive a restart. So the spec says nothing about the reported
   run, with or without the flag.
2. **Assumptions.** Crashes, and the order of `applyc <- ap` (raft.go:232) before
   `storage.Save(rd.HardState, …)` (raft.go:256), are what make the persisted commit index lag the
   acknowledged one. That ordering is outside the model, because `Save` is `True → True`. This is
   A-model.
3. **The `embed` change.** Without the flag's timeout, the gate is `ReadyNotify`. It closes after
   `publishV3`'s request has been applied, and that request is an entry of the current term, so
   raft's committed index has caught up to the end of the log, which includes every pre-crash
   committed entry. No spec states this ordering. `publishV3` is an axiom with post `True`, and
   `serve` is not translated. So even a crash model would need `publishV3`/`ReadyNotify` specified
   before the fix could be shown to matter.
4. **Raft-level observation.** At the raft pin, the single-voter shortcut is postponed until
   `committedEntryInCurrentTerm()` (`raft.go:1354-1364` at `509271dac`). This is the fork's fix
   from `issues/raft-readindex-singleton-stale.md`, verified as `StepR.readSingle`/
   `readReleaseSingle`. With that fix, a restarted single leader holds a `ReadIndex` until an entry
   of its term commits. Because the leader self-acks only after persisting (`appendEntry`,
   `raft.go:835-837`), its committed index then covers every entry it acknowledged before the
   crash. So the fork's raft closes the linearizable half of this bug even with the flag's early
   serving. Upstream raft v3.7.0 does not: it still has the unconditional shortcut, and etcd relies
   on `ReadyNotify` to cover that gap. This is an informal argument, not a theorem. Stating it
   needs the crash model of the proposal below.
5. **Serializable half.** Serializable reads promise no recency, so a reader is not entitled to
   monotonic serializable reads across a restart. That is class N for the code. A "no going back in
   time" property would also need a crash model.

## Proposal (step 6)

**Slug `crash-restart-model`** (A-model): make the execution model cover a crash and restart from
durable state. Specifically:

- give the WAL `Save` contract a durable/volatile split (`HardState`, entries) and a restart step
  that rebuilds the raft state from it (raft `RestartNode` from a non-empty `MemoryStorage`, the
  server's WAL bootstrap path);
- carry the ghost committed index across the crash as a lower bound on durable entries, rather
  than on `HardState.Commit`;
- state the read result across the restart: `committedAtLeast γr c` held before the crash
  ⇒ after restart, `LinearizableReadNotify` returning `nil` ⇒ `readIndexOk γr c`.

Sketch:
`theorem read_notify_after_restart : crashInv γ ∗ committedAtLeastPre γr c ⊢ restart … {{ isReadNotify r γr' ∗ committedAtLeast γr' c }}`.
With that, the existing `read_notify` gives the conclusion, provided raft's postponed single-voter
read (already proved) and the leader's persist-before-self-ack are part of the restart invariant.

Cost: large. Perennial's Lean port has no crash semantics (`notes/bbolt-unsafe.md`,
`notes/STATUS.md:1123`), so this needs a Perennial extension, proposed upstream on its own
(CLAUDE.md, "Changes to Perennial"). The closest safety property reachable now, at small cost, is
a spec for `publishV3`: a postcondition that its request was applied at an index whose entry has
the current term. A `ReadyNotify` contract that says "closed ⇒ committed ≥ every entry in the log
at start" would then document why the readiness gate matters (and would have flagged #13525). This
cannot be stated without the restart, though.

## Findings

- No new `issues/` file. The bug is fixed at the pin, and its raft-side enabler is already
  `issues/raft-readindex-singleton-stale.md`. I added `links:` lines there for etcd#16666 and
  etcd-io/raft#105, as related and not the same bug. The crash path (a stale persisted commit
  index after restart) is a second way to reach that shortcut's stale answer, in a single-member
  cluster with no reconfiguration. Upstream v3.7.0 raft is exposed to it whenever etcd serves
  before `ReadyNotify`.
- No bug in this repository's specs. No X.
