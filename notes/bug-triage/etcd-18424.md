# etcd-io/etcd#18424: etcd Go & Java client SDK's retry mechanism may break `Serializable`

- URL: https://github.com/etcd-io/etcd/issues/18424 (closed 2025-06-01 by the stale bot; labels
  `type/bug`, `area/clientv3`, `area/robustness-testing`). Origin: Jepsen's jetcd 0.8.2 analysis
  (etcd-io/etcd#14890).
- Affected: jetcd (Java), and the Go client's `unaryClientInterceptor` by design. No fix in the Go
  client. The maintainers concluded the Go path was unreachable because the server's
  `errors.ErrCanceled` had no gRPC mapping, so a client never saw `codes.Canceled` from the server.
  etcd-io/etcd#21122 (merged 2026-02) added that mapping, which makes the path reachable. Both are
  in the pin: `server/etcdserver/api/v3rpc/util.go:54`, `errors.ErrCanceled:
  rpctypes.ErrGRPCCanceled`.

What goes wrong: a non-idempotent RPC (`Put`, `DeleteRange`, `Txn`) is applied by the server, but
the client gets an error and resends it. Another client's transaction may run in between, so the
two transactions see each other's writes (a cycle), or a later put is overwritten by the resent
older one. In the Go client the resend is `unaryClientInterceptor`'s `isContextError` branch
(`client/v3/retry_interceptor.go:76-83` at the pin): a `Canceled`/`DeadlineExceeded` status while
the caller's context is live `continue`s the loop before the policy check `isSafeRetry`, whatever
the call's retry policy. The report's second scenario (a resend after a server restart) is not a
Go-client path: the error is `Unavailable` with a transport description, and
`isSafeRetryMutableRPC` (`retry.go:85`) does not retry it. The Java client is outside this
repository.

**This is our finding `issues/etcd-client-retry-put-ctx-error.md`** (reproduced 2026-10-14: a mock
server answering the first `Put` with `codes.Canceled` receives it twice, and `Put` returns
success).

## Classification

**C-other (the spec admits re-execution); secondary O-pkg for jetcd.** The retry interceptor is
verified at the pin (`Client.unaryClientInterceptor`, linked `Proof/go_etcd_io/etcd/client/v3/
Link.lean:371`), and its premises hold. Its contract `etcdInterceptorOk`
(`Proof/go_etcd_io/etcd/client/v3/InvKVConn.lean:760-774`) takes the server's spec as
**persistent** (`□ ▷ Spec m Φ`): the handler may be run any number of times, and a success is the
last run's. The client results inherit this. `client_put_end_to_end`/`client_txn_end_to_end`
(`client/v3/Results.lean:2014, 2203`) take a persistent update `kvOpAu`, so a reply says what one
run did, nothing about the other runs. The property the user relies on, write-at-most-once (the
design comment on `isSafeRetryMutableRPC`, `retry.go:77-84`), is not stated anywhere.

## The argument (step 4)

1. Observed: the client calls `Txn` once. The server applies it at revision `r₁` and answers
   `codes.Canceled` (its proposal context ended after the entry committed). The interceptor
   resends it, and the server applies it again at `r₂ > r₁`, after another client's transaction.
   The caller gets success with the reply of the second run.
2. The premises hold: `retryClientOk` (built by `New`), the context live, the request plain. No
   premise excludes a server status `Canceled`. `statusErrOk` only asks that `status.FromError`
   accept it.
3. The postcondition allows it. `etcdInterceptorOk`'s success branch is `∃ m', Rep.recv out m' ∗
   Φ m'` from one use of the persistent `Spec m Φ`. Since the spec is persistent, earlier uses
   (earlier applications) leave no trace in the conclusion. `isContextError`'s and
   `isSafeRetryMutableRPC`'s specs say nothing about the boolean, so the loop's choice to retry is
   unconstrained. At the system level the transaction's linearization point is the second run's.
   The first run is one more linearized write that no caller is told about, and every state
   statement remains true.
4. What would exclude it: a one-shot server spec for a `nonRepeatable` call. The interceptor would
   get `▷ Spec m Φ` (not `□`), and the transport contract would say when a failed attempt has
   *not* consumed it ("there is no address/connection available": the request was not sent). The
   proof at the pin then fails at the `isContextError` branch (`retry_interceptor.go:82`, the
   `continue`), which needs the spec a second time without having it back.

## Proposal: `client-write-at-most-once`

Split `etcdInterceptorOk` by retry policy:

```lean
-- nonRepeatable: the server's spec is used at most once; on an error, either unused or spent
{{ … ∗ ▷ Spec m Φ ∗ ⌜policy = nonRepeatable⌝ … }} interceptorCall …
{{ err, RET #err; (⌜err = nil⌝ ∗ ∃ m', Rep.recv out m' ∗ Φ m') ∨
    (⌜err ≠ nil⌝ ∗ (▷ Spec m Φ ∨ spent)) }}
```

with a refined `grpc.ClientConn.Invoke` axiom: a client-side "no address/connection available"
error returns the spec unused, and any other error may have consumed it. Downstream,
`client_put_end_to_end`/`client_txn_end_to_end` would take an exclusive (one-shot) update instead
of `kvOpAu`'s persistent one, so "a successful `Put` was applied exactly once". Cost: small to
medium (the interceptor's proof, about 60 Go lines; the `Invoke` axiom's restatement; the two
client results and C1's `putRunOk`, which today drops the revision token for this reason,
`notes/STATUS.md:3862-3866`). It fails at the pin and succeeds with the fix in the issue file.
It would also catch the same class in the stream interceptor once that is translated.
