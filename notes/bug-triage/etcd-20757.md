# etcd-io/etcd#20757: Cannot promote member from follower when auth is enabled

- URL: https://github.com/etcd-io/etcd/issues/20757 (closed 2026-07-07; labels `type/bug`,
  `good first issue`, `backport/v3.5`, `backport/v3.6`)
- Affected: v3.6.1, v3.6.5 and `main` before the fix (and 3.5). Fixed by PR #20792 (merge
  `37531e62f`, 2025-10-31; the fix commits on its branch, e.g. `5410751ff`). Backports: 3.5
  #21494, 3.6.

What goes wrong (pre-fix code): `MemberPromote` sent to a follower goes through
`EtcdServer.PromoteMember` → `promoteMember`, which, not being the leader, forwards over the
peer HTTP API (`promoteMemberHTTP`, `server/etcdserver/cluster_util.go`). The leader's
`peerMemberPromoteHandler.ServeHTTP` (`server/etcdserver/api/etcdhttp/peer.go`) calls
`h.server.PromoteMember(r.Context(), id)` with a context that carries no gRPC metadata. Its
`checkMembershipOperationPermission` → `AuthInfoFromCtx` gets no token and returns `(nil, nil)`,
and `IsAdminPermitted` of an empty user returns `ErrUserEmpty`. The follower retries until it
times out. The fix copies the caller's token into an `Authorization` header in
`promoteMemberHTTP` and rebuilds incoming metadata from it in the handler.

## Classification

**F (fixed before the verified code), counterfactual F− trivially (O-pkg/O-fn).** The fix
`37531e62f` is an ancestor of the etcd pin `107edf7e4`. At the pin, `promoteMemberHTTP` sets the
header and the handler restores the metadata. Nothing on the path is verified except the two
auth checks. Their specs state exactly the observed outcome for a token-less context, so they
are not the gap:

- `authStore.AuthInfoFromCtx.spec`: "an auth info (`nil` if auth is disabled or the context has
  no token)";
- `IsAdminPermitted`: some error.

The gap is the forwarding code, which is not translated.

Source of verification states: the inventory
`/tmp/claude-0/-shared-etcd-grove/c22270a5-a99f-4bfe-8204-a0d29e5800a4/scratchpad/verified.txt`.

## The counterfactual (step 5)

On the pre-fix code the leader's context has no metadata. `AuthInfoFromCtx.spec` returns
`authInfoRO a ∗ authErrIs err` and allows `(nil, nil)`. The real code returns exactly that,
because `FromIncomingContext` fails. `IsAdminPermitted` may return any `authErrIs` error. Every
verified function meets its spec on the buggy run, and the bug is in what the unverified caller
passes. F−. Even with the forwarding verified, no spec here states *whose* identity a request
carries: the auth specs have no identity (`auth-state-model`, `etcd-14571.md`). So the
property "a forwarded admin request is authorized as the original caller" cannot be stated yet.

## Proposal: `inproc-client-auth-identity` (new; same class as `inproc-client-auth-identity`)

Verify the membership-change request path, follower to leader: `PromoteMember`/`promoteMember`/
`mayPromoteMember`, `checkMembershipOperationPermission`, `promoteMemberHTTP` and the peer
handler (about 150 Go lines, with `net/http` as trust boundary). The statement, over
`auth-state-model`'s identity: the auth info the leader's check sees equals the one the
follower's API layer would derive from the client's context (`AuthInfoFromCtx ctx_leader =
AuthInfoFromCtx ctx_client`, up to token validity). `etcd-17502.md`'s `inproc-client-auth-identity`
is the same property for the in-process client: one auth-identity-preservation proposal across
internal hops would cover both. Cost: medium, plus the membership store as a contract.

## Findings

None new: fixed in the pin. No bug in this repository's specs. (A remark on the fix at the pin:
`promoteMemberHTTP` checks `len(ts) > 0` before `ts[0]`, unlike `AuthInfoFromCtx`,
`issues/etcd-auth-token-md-empty.md`.)
