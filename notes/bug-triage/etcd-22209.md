# etcd-io/etcd#22209: A `RangeRequest` with `keys_only` no longer includes `lease` in the response

- URL: https://github.com/etcd-io/etcd/issues/22209 (open; label `type/bug`; proposed for v3.7.4)
- Affected: v3.7.0 onward (regression from PR #21791, commit `7624a8a2e`, "Range with
  --keys-only retrieves from memory when possible"); v3.6 returns the lease.
- Fix: none merged. PR #22550 (open: records the lease in the key index; ahrtr objects to the
  design), PR #22212 (closed: lessor lookup, wrong for past revisions). Our fix branch
  `range-keys-only-lease` (fork commit `01e522548`).

What goes wrong: `executeRange` (`server/etcdserver/txn/range.go:67` at the pin) sets
`FastKeysOnly` for a keys-only range not sorted by value; `storeTxnCommon.rangeKeys`
(`server/storage/mvcc/kvstore_txn.go`) then builds the key-values from the in-memory index, which
has no lease, so every `Lease` is 0.

## Classification

**A-pre (a premise of the client contracts), found by the proof; the server's specs state the
bug exactly.** This is our finding `issues/etcd-range-keys-only-lease.md` (txn unit 2,
2026-10-11; it already links #22209). The code is in the pin and verified: the server-side range
specs are stated as the code computes the range, with the fast read's lease zeroed (`leaseZ`), so
they admit the observed response by construction. The client-level contracts, which say a get
returns etcd's key-values (`rangeKvsOk`, lease included), are derived only for gets that are
`getExact`, whose first conjunct is `o.keysOnly = false`: the issue's request violates it.

Source of verification states: `verified.txt` was not produced; states read from `Spec/`,
`Proof/` and the txn and mvcc `Link.lean` files.

## The argument (step 4)

1. Observed: state with `k ↦ (v, lease L ≠ 0)`; `Range{key: k, keys_only: true}` (sort target
   `KEY`); response key-value with `Lease = 0`.
2. Server specs: `fastKeysOnly o = o.keysOnly && sortTarget ≠ 4`
   (`Proof/.../txn/RangeModel.lean:96`), `kvRead` drops value and lease on a fast read (`:99-100`),
   and the bridge to the client's model is "up to `leaseZ (fastKeysOnly o)`" (`leaseZ`, `:151`;
   `srvRangeOk_rangeKvsOk`, `:640-645`; `executeTxn`/`InvTxn.lean:119`:
   `kvs = kvs'.map (leaseZ (fastKeysOnly o))`). The observed response satisfies them.
3. Client contracts: `OpFull.getExact` (`Proof/go_etcd_io/etcd/cache/v3/InvEtcdTxn.lean:552-558`)
   starts with `o.keysOnly = false` ("a fast keys-only read zeroes the leases,
   `issues/etcd-range-keys-only-lease.md`"); the derived `isEtcdKV`/`isEtcdTxnKV` and the
   recipes', cache's and leasing's proofs use only `getExact` gets (STATUS, "Limitations of the
   client contracts as derived"). The premise excludes the request; no verified client issues one.
4. What the user expected (the key's lease at the revision read) is `rangeKvsOk` without
   `leaseZ`, i.e. the premise dropped: false at the pin, which is why the premise is there.

## Proposal: `range-keys-only-lease-fix`

Take the fork fix `01e522548` (keys-only ranges read the backend again), re-translate, and
remove `leaseZ`: `fastKeysOnly o = false` for every request `executeRange` builds, so
`srvRangeOk_rangeKvsOk` holds without the `leaseZ` map, and `getExact` loses `o.keysOnly = false`.
Statement: `srvRangeOk o s kvs more → ∃ kvs', rangeKvsOk o (rangeSel s o) kvs' ∧ kvs = kvs'` (for
`¬ cutEarly o`). Cost: small (one Go line; the `executeRange` proof loses a case; the client
contracts' consumers re-run unchanged, since dropping a conjunct of a premise only widens them).
If upstream keeps the fast path (#22550, the lease in the key index), the same statement needs
the key index's model to carry the lease per revision: medium (`keyIndex`/`treeIndex` specs).
