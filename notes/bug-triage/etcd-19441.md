# etcd-io/etcd#19441: Watch sync fails when Fragment is false

- URL: https://github.com/etcd-io/etcd/issues/19441 (closed 2025-02-19 by a maintainer).
- Affected: the reporter's test fails on v3.3.27, v3.4.35, v3.5.18 and `main`. No fix. The test is
  in PR #19442 (not merged).

The report: four transactions each put 12 values of 100 KB. A new watch then starts at the first
transaction's revision with `Fragment = false`. The server sends the 48 events in one response of
4.8 MB, and the receive fails with gRPC `ResourceExhausted` ("received message larger than max
(4802091 vs. 4194304)"). The reporter expected four responses, one per revision. The thread's
diagnosis (gRPC maintainers, then ahrtr) is that the limit is the *client's* gRPC receive limit.
The test opened the stream with the raw generated client
(`integration.ToGRPC(...).Watch.Watch(ctx)`), so it got gRPC's default of 4 MiB. `clientv3`
passes `grpc.MaxCallRecvMsgSize(math.MaxInt32)` on every watch stream
(`client/v3/watch.go:1057`, `w.remote.Watch(w.ctx, w.callOpts...)`), so a `clientv3` user does not
see the error.

## Classification

**N** (working as intended: a test that bypasses the client library). Two facts decide it.

- One response for several revisions is the specified batching. `syncWatchers` builds the
  responses with `eventBatch.add`, whose model `ebAdd`
  (`Proof/go_etcd_io/etcd/server/v3/storage/mvcc/InvWatchBatch.lean:62-71`) puts the events of up
  to `watchBatchMaxRevs = 1000` revisions (`:56`) in one batch. Four revisions therefore go in one
  response. The verified spec here is `Spec/.../mvcc/eventBatch__add.lean`.
- The failure is the receiving client's gRPC limit. That is a property of the caller's gRPC call
  options, which no spec here models. The verified client path keeps the call options:
  `watchGRPCStream.openWatchClient`'s spec (`Spec/go_etcd_io/etcd/client/v3/watchGRPCStream__openWatchClient.lean:39-40`)
  has the stream opened with `w.callOpts` (`callOptsOk`).

Source of verification states: the `Spec/`/`Proof/` files, because `verified.txt` was not produced.

A side note on sizes: the specs say nothing about message size, because response sizes are
abstracted away (C-obs territory). A per-response size bound would be a resource statement, and
those are outside the partial-correctness specs. It is not needed here, since the behavior is the
intended one.
