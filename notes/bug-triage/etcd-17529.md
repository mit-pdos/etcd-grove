# etcd-io/etcd#17529: etcd watch events starvation / lost, multiplexed on a single watch stream

- URL: https://github.com/etcd-io/etcd/issues/17529 (closed 2024-10-05; `type/bug`,
  `priority/critical-urgent`)
- Affected: v3.4, v3.5 (≤ 3.5.12), `main` before the fix. Reported on a Kubernetes cluster with
  hundreds of `prevKV` watches on one gRPC stream, a client compacting every minute at a
  minute-old revision; a pod's `DELETE` event missing from one stream.
- Fix: PR #17555 "Fix watch event loss", merge `fca3e8a9b` (2024-03-16; backports #17610 for 3.4,
  #17612 for 3.5). The starvation half (responses delayed for minutes, pending events in the
  millions) is etcd-io/etcd#16839 (open), not fixed by it; #17563 ("Reuse events used for syncing
  watchers", merged `6fa734266`) is a related performance change.

What goes wrong (pre-fix code): in `watchableStore.syncWatchers`
(`server/storage/mvcc/watchable_store.go`), `choose` → `chooseAll` tries to send a
`CompactRevision` response to each chosen watcher whose `minRev` is below the compaction revision;
if the watcher's channel is full (a slow `sendLoop`, the stream multiplexing hundreds of
watchers) it only skips it, leaving it in the chosen group. `syncWatchers` then set its `minRev =
curRev + 1` and, finding no events for it in `rangeEvents(minRev(others), ...)` (or only some),
moved it to the synced group: the events between its old `minRev` and the compaction revision
were never sent and no compaction notice either. The fix skips such a watcher in `syncWatchers`
(`if w.minRev < compactionRev { continue }`), so it stays unsynced and the compaction response is
retried.

## The argument (step 5)

Observed, in spec terms: a watcher `w` of start revision `lo` receives events of revisions `≥ c'`
but not some event at `lo ≤ v < c'`, and no compaction response (`watchRecvOk` would need the
received events to be `watchEvents L r lo d`, gap-free).

- In the verified model this is excluded by `mvcc.watchRecvOk` (`mvcc/WatchRecv.lean:91`): the
  deliveries' events, concatenated, are the range's events of `[lo, d)`. The invariant for a
  synced watcher (`popFacts`, `InvWatchStore.lean:604-605`) is `lo ≤ minRev ≤ d` with `evsWf γ r
  lo evsw d` (delivered exactly the events of `[lo, d)`).
- Pre-fix, the bad step moves an unsynced watcher with `d = minRev < compactRev` (unsynced clause
  `:607`) to the synced group with `d` unchanged and `minRev = curRev + 1 > d`: the synced clause
  `minRev ≤ d` fails, or, if the proof raised `d` to `curRev + 1`, `evsWf` fails (the events of
  `[old d, curRev]` were not delivered). So the step would break the invariant — but it is
  unreachable under the premises: with `crevFrozen` the compaction revision is `-1`, `chooseAll`'s
  premise `compactRev ≤ minRev` holds, and its compaction branch (the send that can fail) is dead.
  The pre-fix and fixed `syncWatchers` are the same program on that domain: **F−**.
- The scope gap is the one recorded for etcd#18089 (`etcd-18089.md`): watch completeness is proved
  only for a store that is never compacted, while etcd compacts (here every minute). Under
  `watch-under-compaction` (`chooseAll.spec` stating that a member below `compactRev` is either
  sent the compaction response and removed, or kept in the group with its `minRev` and `d`
  unchanged), the invariant argument above makes the pre-fix code fail: **F+** under the proposal.

The starvation half (minutes of delay with 8.7M pending events, 722 slow watchers): no spec here
bounds latency or orders service among watchers; `syncWatchersLoop` and `syncVictimsLoop` are
verified for safety only. C-live/C-perf, outside Iris partial correctness; the closest safety
statement is not useful (a bound on `pendingEventsGauge` is a metric).

## Proposal: `watch-under-compaction` (mvcc unit 6b; as etcd#18089)

Drop `crevFrozen` from the watch path, as proposed in `etcd-18089.md`: `New` returns the
compaction right, the loops read `compactMainRev` under `s.revMu`, and `chooseAll.spec` covers
members below `compactRev`:

```lean
-- postcondition, per member w with st.minRev < compactRev:
(sent w (compactResp compactRev) ∧ w ∉ wg' ∧ st'.compacted = true) ∨
(w ∈ wg' ∧ st' = st)          -- channel full: unchanged, retried
```

and the unsynced clause of `popFacts` allows `minRev < compactRev` only while `d = minRev`
(nothing delivered past it), so `syncWatchers` must leave such a watcher unsynced (the fix's
`continue`). The watch-stream result: a watcher's events are a gap-free suffix of the log from its
start revision, or end with a compaction response at `c > d`. Cost: medium to large (mvcc 6b; the
pure lemma `keepAt_main_eq` of `etcd-18089.md`, re-proving `choose`/`chooseAll`/`syncWatchers`/
`rangeEvents`/the loops over a compacting store). It would have caught this bug and etcd#18089,
and states the property violated by the open etcd-io/etcd#22294 (below).

## Findings

None new from this bug (fixed at the pin). Related, present at the pin and not in `issues/`:
etcd-io/etcd#22294 (open): in `choose`'s capped branch (≥ `maxWatchersPerSync` unsynced watchers)
`chooseAll` deletes a compacted watcher from the temporary group only, so it stays in
`s.unsynced` and is sent a `CompactRevision` response again every resync. Same branch, same scope
gap (`watch-under-compaction` would exclude it: a compaction-cancelled watcher must leave
`s.unsynced`). Not filed here (not this group's bug; a candidate `issues/etcd-watch-choose-capped-compacted.md`).
No bug in this repository's specs.
