# etcd-io/etcd#17507: etcd does not respond to a progress request on a new watch until there is an event

- URL: https://github.com/etcd-io/etcd/issues/17507 (closed 2024-03-11; `type/bug`,
  `priority/important-soon`)
- Affected: v3.5.8–v3.5.12 and `main` after #15237 (the fix of etcd-io/etcd#15220,
  `etcd-15220.md`), before the fix; reported on v3.5.10 embedded (Kubernetes'
  `ConsistentListFromCache`).
- Fix: PR #17557 "Fix progress notification for watch that doesn't get any events", merge
  `ddf54715b` (2024-03-11; in v3.5.13).

What goes wrong (pre-fix code): #15237 made `recvLoop` answer a progress request with
`watchStream.RequestProgressAll()` and, when it returned `false` (some watcher of the stream not
synced), set `sws.deferredProgress = true`; while it was set, every later progress request was
ignored, and only `sendLoop`, after sending an mvcc response, retried `RequestProgressAll()` and
cleared the flag. A watcher that is unsynced only because it was created with an old start
revision and whose range has no events becomes synced in `syncWatchers` without any response, so
`sendLoop` never retries: the stream answers no progress request again. The fix deletes
`deferredProgress`: `recvLoop` calls `RequestProgressAll()` and ignores the result, so a request
made while a watcher is unsynced is dropped (no response) and the client re-requests.

## Classification

**F (fixed before the verified code); counterfactual F−, gap C-live.** The fix `ddf54715b` is an
ancestor of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes); at the pin
`recvLoop`'s progress branch is `sws.mu.Lock(); sws.watchStream.RequestProgressAll();
sws.mu.Unlock()` (`watch.go:395-399`) and the field is gone. The bug is a missing response, and the
specs are partial correctness: nothing says a progress request is ever answered (the
`RequestProgressAll` and `progressIfSync` postconditions leave the boolean and the send
unconstrained), so the pre-fix code meets every spec. The pinned behavior is itself only
"no response when a watcher is unsynced", which the client's documentation does not say
(`issues/etcd-watch-progress-request-dropped-unsynced.md`).

## The argument (step 5)

Observed, in spec terms: after a progress request at up position `i`, no response of id `-1` is
ever sent down, although from some point on every watcher of the stream is synced.

- `recvLoop.spec` (`serverWatchStream__recvLoop.lean:28-37`): "each progress request asks for the
  progress of all"; its obligations are about create and cancel answers (`ctrlP`). It promises no
  answer to a progress request.
- `RequestProgressAll.spec` returns an arbitrary `b` and `P.R`; `progressIfSync.spec` returns
  `m ↦ M ∗ watchReader`, with the send described only in prose. The pre-fix `deferredProgress`
  flag (a bool under `sws.mu`) adds a skip in `recvLoop` and a call in `sendLoop`; both meet these
  specs as the pinned code does (the extra `RequestProgressAll()` in `sendLoop` needs only the
  reader slot `sendLoop` already holds for `RequestProgress`, `InvWatch.lean:439-440`).
- `watchStreamSpec` (`InvWatchStream.lean:543`) is a safety statement on the responses sent
  (`watchDn`); a response never sent violates nothing. F−; the class is **C-live**: "every
  progress request is eventually answered" is not expressible as an Iris partial-correctness
  postcondition.

## Proposal: `watch-progress-answered`

The closest safety property that excludes the pre-fix code: a progress request received when
every watcher of the stream is synced is answered before `recvLoop` reads the next request.
Statement sketch:

- `progressIfSync.spec`: `b = true ↔ ∀ w ∈ M, synced w ∧ minRev ≤ rev+1`, and on `b = true` with
  `M ≠ ∅` an id-`rid` response at `rev` is in the first watcher's channel (`chanSent` grows by
  it); `RequestProgressAll.spec` passes both through.
- `recvLoop.spec`: an up-queue progress request at position `i` gives either an id `-1` mvcc
  response sent after `i`, or a witness that some watcher of the stream was unsynced at the
  call (a ghost record `progUnsynced γs i`).

The pre-fix code fails it: with `deferredProgress = true`, `recvLoop` skips the call even when
all watchers are synced. Cost: small to medium (the `progressIfSync` postcondition, a ghost log
of progress requests in `InvWatch.lean`, re-proving `recvLoop`). A full liveness statement (the
request is answered once all watchers sync) is outside Perennial's logic; with this property and
`watch-progress-synced` (`etcd-15220.md`) a client can soundly retry, which is the protocol
upstream chose.

## Findings

`issues/etcd-watch-progress-request-dropped-unsynced.md` (new, documentation): at the pin a
progress request made while any watcher of the stream is unsynced gets no response, which
`clientv3.Watcher.RequestProgress`' and the proto's documentation do not say. No bug in this
repository's specs.
