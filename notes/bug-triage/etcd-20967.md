# etcd-io/etcd#20967: Upgrade to etcd 3.6 recovers old/duplicate members from store

- URL: https://github.com/etcd-io/etcd/issues/20967 (closed 2025-12-25; labels `type/bug`,
  `priority/important-soon`, `priority/critical-urgent`)
- Affected: a 5-member cluster created on v3.3.17 and upgraded through 3.4 and 3.5 to 3.5.25, run
  with `--unsafe-no-fsync`. On upgrading one member to v3.6.6, that member lists 8 members: 3
  zombies with new IDs and the peer and client URLs of real members. `member remove` of a zombie
  works, but the zombies come back when the member is re-added.
- Fix: PR #20995 "[release-3.5] server: cleanup zombie membership information" (merged
  2025-12-12, v3.5.26). On `release-3.5` it deletes from the v3 store the members the v2 store does
  not have: on `UpdateAttributes`, on applying a snapshot, and after each ConfChange. Users are
  told to pass through v3.5.26 before 3.6. Nothing on `main`. The WIP #20981 ("Bootstrap etcd from
  consistent_index") was closed. Duplicate in kind of #13196.

What goes wrong: v2 and v3 membership diverged long ago. bbolt's `members` bucket holds 3 members
that neither store's `members_removed` lists. 3.5 uses the v2 store, so they were invisible there.
3.6 loads the bucket (`RaftCluster.Recover`). The maintainers found two ways such zombies get
created:

1. v3.4's `etcdctl snapshot restore` does not delete the old members. Its `DeleteRange` goes
   through mvcc and so touches only the `key` bucket (`clientv3/snapshot/v3_snapshot.go:417` on
   `release-3.4`). This was reproduced in #20995's e2e test.
2. A `--force-new-cluster` restart after a crash in which bbolt kept an applied AddNode but the
   WAL lost `HardState.Commit`: the AddNode is dropped as uncommitted while the bucket keeps the
   member. The reporter's `--unsafe-no-fsync` makes that kind of loss easier.

Cause 1 is the one shown to happen; the reporter never confirmed which cause applied.

## Classification

**F (both causes are absent from the pinned code); counterfactual F−, gaps O-pkg / A-model;
residual hazard at the pin (below).** The decisive facts at the etcd pin `107edf7e4`:

- (1) `etcdutl`'s restore calls `TrimMembershipFromBackend` (`etcdutl/snapshot/v3_snapshot.go:362`)
  and then re-adds the `--initial-cluster` members (`:513`). v3.4's `etcdctl snapshot restore` is
  not on `main`.
- (2) `bootstrapWALFromSnapshot` with `ForceNewCluster` sets `Commit = max(HardState.Commit,
  consistent_index)` before it discards uncommitted entries (`bootstrap.go:612-631`; commit
  `ec416efcc`, 2025-05-30, an ancestor of the pin). An entry already applied to bbolt is no
  longer dropped.
- There is one membership store at the pin (the v2 membership writes were removed in `fdedec1ed`).
  So "v2 and v3 disagree" cannot arise, and nothing remains on `main` for #20995's v2-based cleanup
  to do.

Source of verification states: the batch's `verified.txt`. `etcdutl` is not translated (O-pkg).
`bootstrap`, `bootstrapWALFromSnapshot`, `recoverSnapshot`, `buildConfStateFromV3store` and
`bootstrappedCluster.Finalize` are not translated (O-fn). `RaftCluster.Recover`/`UnsafeLoad` and
the schema membership backend are not translated. `EtcdServer.applyConfChange` is assumed.

## The counterfactual

- Cause 1 (restore leaving old members): the restore tool is untranslated (**O-pkg**), and no
  statement here describes the `members` bucket (`etcd-13196.md`: the `applyConfChange` axiom
  fixes only where writes happen, and `RaftCluster.Members.spec` returns some list). So **F−**.
- Cause 2 (bbolt ahead of a WAL that lost data, then a force-new-cluster restart): crashes and
  `fsync` are not modeled (**A-model**: there is no crash semantics in Perennial's Lean port, see
  `crash-restart-model`). `--force-new-cluster` bootstrap is untranslated. So **F−**.

## A residual hazard at the pin (not the reported bug)

On `main` the `members` bucket now matters to raft as well as to `member list`. Since #21138
(`25a5bb287`, 2026-01-15, an ancestor of the pin), every restart with a WAL builds the raft
snapshot's `ConfState` from the bucket: `buildConfStateFromV3store` (`bootstrap.go:112,132-149`)
makes every non-learner in the bucket a voter. The consequence for a member whose bucket still holds
zombies (data from a cluster that reached 3.6 from a 3.5 release before 3.5.26, which 3.6 does not
clean): when it restarts on the pinned code, its raft configuration contains the zombies as voters.
That configuration differs from the other members' configurations at the same index. If every
member holds the same zombies, each one's quorum grows (5 real + 3 zombies needs 5 votes), so one
failure stops the cluster. This is reasoned from the pinned code and has not been reproduced. It
needs a 3.5.25 → 3.6 → pin upgrade with zombie data, as in #20995's e2e helper, and has not been
checked upstream. It is reported here and to the coordinator, not filed in `issues/`.

The specs show exactly where this sits. raft's `RestartNode.spec` (`Spec/go_etcd_io/raft/v3/RestartNode.lean`)
covers only an empty log (`σ.ents = []`, `HsEmpty hs`, `cv.Applied' = 0`). It ties the ghost
configuration to the storage's conf state by premise: `γ.reCfg = GMap.listToSet csm.Voters'`.
`notes/STATUS.md` (D11, stage R8a) records that none of etcd's start paths is `RestartNode` as verified. A
restart from a WAL whose `ConfState` comes from a diverged bucket is therefore outside every result.
Discharging that premise for etcd's restart is the bucket-equals-configuration invariant that
`membership-state-model` states.

## Proposal: `membership-state-model` (+ `crash-restart-model` for the restart)

As in `etcd-13196.md`, with the conjunct that matters most at the pin:
`confStateOf (memOf (applied ci)) = cfgAt ci` for the persisted consistent index `ci`. Together
with `buildConfStateFromV3store.spec` ("returns `confStateOf` of the bucket's members") this
discharges the restart's `γ.reCfg = listToSet csm.Voters'`-shaped premise for a real restart. The
crash side (cause 2) needs `crash-restart-model`, specifically the bbolt-ahead-of-WAL case:
`max(commit, ci)` is the bootstrap step whose spec would say "no applied entry is discarded". Cost:
medium to large for the membership half (about 500 Go lines). The restart half is large and needs
Perennial crash semantics.

## Findings

No `issues/` file. The bug's causes are not in the pinned code. The residual hazard above is an
unconfirmed inference: it is flagged to the coordinator for a decision and an upgrade
reproduction before it becomes an `issues/` entry.
