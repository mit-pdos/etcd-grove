# etcd-io/etcd#17247: Duplicated watch event detected in robustness test

- URL: https://github.com/etcd-io/etcd/issues/17247 (closed 2024-04-12; `type/bug`,
  `priority/important-soon`, `area/robustness-testing`)
- Affected: `main` only, from PR #17228 (merge `ed994248e`, 2024-01-12, "Fix tx buffer
  inconsistency if there are duplicate keys in one tx") to the fix; its backports (#17239 for 3.5)
  were blocked, so no release had it. Found by the robustness tests (Kubernetes traffic, 3 members,
  failpoints `raftAfterSaveSnap=panic()` and `MemberReplace`): a watch response with the event of
  revision 882 twice. Bisected to #17228 by the reporter.
- Fix: PR #17263 "Fix tx buffer inconsistency if there are unordered key writes in one tx", merge
  `a22ae624e` (2024-03-28; after the revert discussion of #17280/#17285 and the alternatives
  #17281/#17290, both closed).

What goes wrong (buggy code): #17228 split `bucketBuffer.dedupe` out of `merge`
(`server/storage/backend/tx_buffer.go`) and called `wb.dedupe()` unconditionally in
`txWriteBuffer.writeback` when the read buffer has no entry for the bucket. `dedupe` ends with
`bb.used = widx + 1`, so on an empty buffer it sets `used = 1`. `txBuffer.reset` keeps a bucket
that was used with `used = 0` and its old slots, so an empty write-buffer bucket handed to the read
buffer exposes its stale first slot: an entry already committed to bbolt. `ReadTx`'s
`UnsafeRange` then returns that key from both bbolt and the buffer. An unsynced watcher's
`syncWatchers` → `rangeEvents` reads the `key` bucket through `ReadTx` and builds the event twice.
The fix returns early in `dedupe` when `used <= 1` and dedupes only non-sequential buckets in
`writeback`.

## Classification

**F+ (fixed before the verified code, and the spec excludes the buggy version).** The fix
`a22ae624e` is an ancestor of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes); at the
pin `dedupe` starts with `if bb.used <= 1 { return }` (`tx_buffer.go:229-232`). Counterfactually the
buggy `dedupe` fails its spec on the empty buffer: `bucketBuffer.dedupe.spec` returns `ownBB bb
(canon es)`, and `ownBB` fixes `used` to the entries' length (`bbAt`'s `used' := W64 es.length`,
`InvBuffer.lean:91-93`); for `es = []`, `canon [] = []` but the buggy code stores `used = 1`.

Source of verification states: the `Spec/`, `Proof/` and `Link.lean` files (`verified.txt` not
produced in this run); `bucketBuffer.wp_dedupe` (`backend/Link.lean:314`) and `writeback`
(`:334`) are theorems without `sorry`.

## The argument (step 5)

- **Where the proof breaks.** `bucketBuffer.dedupe.spec` (`bucketBuffer__dedupe.lean:28-32`):
  `{{ ownBB bb es }} bb.dedupe() {{ ownBB bb (canon es) }}` for every `es`, the empty list included.
  `ownBB bb es` (`InvBuffer.lean:96-97`) is `bbAt bb 1 p es`, whose points-to is `bb ↦ {buf' :=
  p.buf, used' := W64 es.length}` (`:91-93`). On `es = []` the buggy body skips the loop (`ridx :=
  1; 1 < 0` false) and writes `used = widx + 1 = 1`; the postcondition needs `used = 0`
  (`canon [] = dedupLast ([].mergeSort _) = []`, `Model.lean:105`). The proof of `dedupe` fails at
  that store.
- **Why the bug reaches the watch.** Above `dedupe`, the read buffer's content is a model value:
  `writeback`'s spec gives `writebackR W R` (the canonical merge, newest wins), and
  `readTx.UnsafeRange.spec` (`readTx__UnsafeRange.lean`) returns `rtRange rv bi kb eb limit`, a
  function of the readers' model state, not of stale slots. `rangeEvents.spec` returns the log's
  events of `[minRev, maxRev)` filtered, each revision once. So in the verified model the duplicate
  event cannot arise (frozen store; this bug needs no compaction), and on the buggy code the first
  statement to fail is `dedupe`'s, whose postcondition is what keeps the stale slot out of the
  model. (Not traced further: which of `writeback`'s or `Unlock`'s proof would fail next.)
- The failpoints (`raftAfterSaveSnap=panic()`, member replacement) only made a member's watchers
  unsynced (a restart or a snapshot install) so that `syncWatchers` read through the buffer; they
  are not the cause.

This is the expected payoff of a functional buffer spec: the bug lives in a boundary case
(`used = 0`) that a test of "duplicate keys in one tx" did not exercise and that the universally
quantified `es` covers.

## Proposal

None needed for this bug (F+). Related, existing: `issues/etcd-backend-duplicate-put-stale-read.md`
is the class #17228 set out to fix (duplicate keys within one batch); the pinned `writeback.spec`
records it as the premise `W.WfR` (no duplicate keys in a non-sequential bucket whose read-buffer
entry exists).

## Findings

None new: the bug is not in the pinned code; no bug in this repository's specs. Suggested `links:`
lines for `issues/etcd-backend-duplicate-put-stale-read.md`: `etcd-io/etcd#17228 pr merged: earlier
fix attempt for intra-transaction duplicate keys (dedupe on writeback to an empty read bucket);

(dedupe of non-sequential buckets only, empty-buffer guard), the pinned code`.
