# etcd-io/etcd#14211: 3.4.18 etcd data inconsistency

- URL: https://github.com/etcd-io/etcd/issues/14211 (closed 2025-05-07; labels `type/bug`,
  `priority/important-soon`, `release/v3.4`, `area/bbolt`, `data/corruption`).
- Affected: v3.4.18 (original report, 2022-06), v3.4.20 (2023-09) and v3.4.18 (2023-11, with two
  bbolt panics on the bad node in two days). No reproduction, no db files, no WAL.
- Fix: none specific. The maintainer closed it pointing at "a revision inconsistency issue fixed in
  v3.4.32 and v3.5.14" (etcd-io/etcd#17780, PR #17815, `dd4e35a58`) and at the separate bbolt
  issue etcd-io/etcd#17084 ("panic: page xxx already freed", closed 2026-06). serathius: the
  corruptions he has seen follow no single pattern, "mostly memory stamping (page written under a
  wrong page id)". Also cross-referenced: PR #14667 (more context in the panic message).

What was observed: one member of three diverged — a lower mvcc revision and a different
`dbSizeInUse` than its peers at the same raft applied index — and a serializable `Range` on it
hit `lg.Fatal("range failed to find revision pair")` (`storeTxnRead.rangeKeys`): the in-memory
index named a revision the bolt `key` bucket did not hold. The third report shows extra keys
(deleted elsewhere) still in the bad member's bbolt. `bbolt check` passed on the files.

## Classification

**A-axiom (diagnosis unsettled; the leading candidate): bbolt's key-value contract, which the
backend's proofs assume, failed on the bad member; secondary A-model (memory corruption, a crash
during compaction) and F− (the one concrete upstream fix, etcd#17780).** At the pin the path is
verified and its spec excludes the observation: `rangeKeys`' postcondition is
`rangeOutcomeC … log rev c …` — the index's answers with the bucket's values, no `Fatal` — under
the store's invariant tying the index to the bucket, and the apply results make members that
applied the same entries hold the same KV log. So the bad state needs the bucket to lose or keep
data against what the backend wrote: either bbolt broke its postulated contract (the
`page already freed` panics of the third report, etcd#17084, are bbolt freelist corruption), the
hardware corrupted memory, or a crash interrupted a compaction (etcd#17780: fixed in the pin; and
crashes are not modeled). None of these is a counterexample to a proof: they are outside its
assumptions, so not X.

Source of verification states: `verified.txt` (`etc/verified-code.py`, at `d606c9cac`).

## The argument (step 4)

1. *As the spec sees it.* A read transaction at revision `rev` of a log `log` whose index answers
   name a revision `(m, 0)` (`m = 165519108`), and the reader's bucket holds no key for it.
2. *Premises.* `rangeKeys.spec`'s reader is `keyReaderD … (delKey γ)` of a bucket holding `log`'s
   revisions except those compaction may delete (`storeTxnCommon__rangeKeys.lean:25-36`); a revision
   the index answers at `rev ≥ c` is not deletable (`named_not_del`, `Proof/.../mvcc/Compact.lean`;
   the compaction result `mvcc_rangeOutcomeC_ge`). So under the premises the bucket has the key and
   the `Fatal` branch is dead: the spec's postcondition (`rangeOutcomeC`) has no `Fatal` outcome.
   The divergence across members is likewise excluded by the apply results
   (`applyEntries_model`, `applied_log_at`, `Proof/.../etcdserver/Results.lean:156-186`: the KV log
   is a function of the applied entries) — all three members report the same applied index.
3. *Assumptions.* What the premises rest on below the backend is the bbolt postulates: a committed
   `Put` is read back by `Seek`, a `Delete` removes only its key, across transactions. A bbolt that
   double-frees a page (etcd#17084's `page already freed`) or a page written under a wrong id
   (serathius's "memory stamping") breaks exactly these, and gives both observations: a key missing
   (the `Fatal`) and keys present that were deleted (the third report). Memory corruption of the
   process is the same failure one layer down (A-model: memory is reliable). The other concrete
   candidate, etcd#17780 (a crash between compaction batches making `restore` pick a lower
   `currentRev`, so later writes reuse revisions and members diverge), is fixed at the pin
   (`kvstore.go:383-385` lifts `currentRev` to `scheduledCompact`), and is F− / O-fn + A-model per
   `notes/bug-triage/etcd-17780.md`; the first report shows no restart before the `Fatal`, the
   third shows two (after the bbolt panics).
4. Hence not X: the verified specs exclude the behavior *given* bbolt's contract and a reliable
   machine, and no evidence points at etcd's own code at the pin.

## Proposal: `fs-crash-model` (existing) for the crash candidate; for bbolt, none practical here

- The bbolt candidate: verifying bbolt's page allocator and freelist (`go.etcd.io/bbolt`, not
  translated; the `freelist` and `node`/`page` code, several thousand lines) against the key-value
  contract the backend already assumes (`Spec/go_etcd_io/bbolt/*_kv.lean`) would discharge the
  axioms. Large; only worthwhile with `fs-crash-model`'s file model underneath, since bbolt's
  correctness argument is about its meta pages and fsync order. Recorded under `fs-crash-model`
  (its "later bbolt's crash-safe open/commit").
- The crash candidate (etcd#17780): `mvcc-restore-from-backend` with its per-commit addition
  (every backend commit, including `scheduleCompaction`'s batches, persists a state from which
  `restore` recovers the right revision), as in `etcd-17780.md`.
- Memory corruption: outside any software proof. The closest safety net is a runtime check, not a
  proof: etcd's corruption checks, whose spec is `model-kv-hash`'s.
