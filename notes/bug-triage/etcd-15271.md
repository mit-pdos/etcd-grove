# etcd-io/etcd#15271: Watch response traveling back in time when a reconnecting member downloads a snapshot from the leader

- URL: https://github.com/etcd-io/etcd/issues/15271 (closed 2023-03-20; `type/bug`,
  `release/v3.5`, `release/v3.6`)
- Affected: v3.4, v3.5 (≤ 3.5.7), `main` before the fix; found by the robustness tests'
  watch validation ("Expect revision to grow by 1, last: 3924, mod: 2171") with the snapshot
  failpoints.
- Fix: PR #15492 "Fix 15271", merge `6d01ab641` (2023-03-20; backported for v3.5.8). An earlier
  attempt, #15439 "mvcc: update minRev when watcher stays synced", was closed. Related later bug of
  the same `Restore` path: etcd-io/etcd#19487 (`etcd-19487.md`).

What goes wrong (pre-fix code): `watchableStore.notify` (`server/storage/mvcc/watchable_store.go`)
set `w.minRev = rev + 1` only when moving a slow watcher to the victims; a synced watcher that
received the events of `rev` kept the `minRev` it had when it last became synced. When the member
installs a snapshot, `watchableStore.Restore` moves every synced watcher to the unsynced group, and
`syncWatchers` re-reads the backend from that stale `minRev`: the watcher receives again events it
already had, with revisions going back. The fix sets `w.minRev = rev + 1` for every watcher with
events in `notify`.

## Classification

**F (fixed before the verified code); counterfactual F−, gap O-fn (`watchableStore.Restore` not
verified).** The fix `6d01ab641` is an ancestor of the etcd pin `107edf7e4` (`git merge-base
--is-ancestor`: yes); the pinned `notify` sets `w.minRev = rev + 1` after both branches
(`watchable_store.go:488-491`). Counterfactually, the pre-fix `notify` meets its spec: the lock
invariant lets a synced watcher's `minRev` lag behind its delivery point (`lo ≤ minRev ≤ d`,
`InvWatchStore.lean:605`), and the only reader of a synced watcher's `minRev` is `Restore`, which is
translated but not specified (the invariant fixes `restore = false`, `InvWatchStore.lean:341`).

Source of verification states: the `Spec/`, `Proof/` and `Link.lean` files (`verified.txt` not
produced in this run).

## The argument (step 5)

Observed, in spec terms: a watcher `w` whose received events (`watchRecvOk`, `mvcc/WatchRecv.lean:91`)
are not "the range's events of `[lo, d)`, once each": an event is received twice.

- In the verified model this is excluded: `watchRecvOk` says the received events are the kept
  events of deliveries whose concatenation is `watchEvents L r lo d`, each revision once. It is not
  an X because no verified run calls `Restore`.
- `notify.spec` (`watchableStore__notify.lean:23-46`) ends with `σ'.syncedAbove (ilog.length + 1)`
  and the lock invariant. For a synced watcher the invariant's `popFacts`
  (`InvWatchStore.lean:604-605`) is `lo ≤ minRev ∧ minRev ≤ d` with `evsWf γ r lo evsw d`. Pre-fix,
  a synced watcher that gets the events of `rev` moves to `d = rev + 1` with its old `minRev`:
  still `minRev ≤ d`. Every other clause is as with the fix. So the pre-fix `notify` meets its
  spec: **F−**. (The spec deliberately lets synced watchers' `minRev` lag: at the pin a synced
  watcher whose range no write touches keeps its registration `minRev`, see below.)
- Had `Restore` been verified, it would move every synced watcher into the unsynced population,
  whose clause is `d = minRev` (`:607`). That fails at the pin too for watchers whose `minRev`
  lags, so a `Restore` proof needs a relaxed unsynced clause: "the range has no event in
  `[minRev, d)`" (`watchEvents L r minRev d = []`), which `syncWatchers` can use (re-reading
  `[minRev, cur]` then yields only undelivered events). That clause holds at the pin (every
  watcher with an event of `rev` gets `minRev = rev + 1`) and fails pre-fix (a synced watcher with
  an event at `minRev ≤ rev < d`). So under `verify-watchable-restore` the bug is **F+**.

Side finding (present at the pin, reproduced): because `notify` advances `minRev` only for
watchers with events, a synced watcher on a quiet range keeps an old `minRev`; after a compaction
past it, a snapshot `Restore` moves it to the unsynced group and `chooseAll` cancels it with
`CompactRevision` although it missed nothing: `issues/etcd-watch-restore-quiet-watcher-compacted.md`.
The fix of this bug made `minRev` correct for watchers that receive events, not for quiet ones.
The same relaxed clause would not exclude it; it needs the compaction branch specified
(`watch-under-compaction`) with "a compacted cancel only for a watcher with `d ≤ compactRev`".

## Proposal: `verify-watchable-restore` (as etcd#19487)

Specify and prove `watchableStore.Restore` and the snapshot case of `store.Restore` against
`isWatchableStore`: the log model jumps to the snapshot's log, every synced watcher moves to the
unsynced population with `restore = true`, and the unsynced clause of `popFacts` becomes

```lean
(lo : Int) ≤ sint.Z st.minRev ∧ sint.nat st.minRev ≤ d ∧
  watchEvents Lc r (sint.nat st.minRev) d = [] ∧ (st.restore = false → d = sint.nat st.minRev)
```

`syncWatchers`' proof then uses the empty window to keep `evsWf` when it delivers from `minRev`.
Cost: large (the store's log model needs a jump to a snapshot, and the watch invariant's
certified-log facts must survive it), as recorded for etcd#19487. With
`watch-under-compaction` it also covers the side finding.
