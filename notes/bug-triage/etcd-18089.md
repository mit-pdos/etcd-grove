# etcd-io/etcd#18089: Watch dropping an event when compacting on delete

- URL: https://github.com/etcd-io/etcd/issues/18089 (closed 2024-10-05; labels `release/v3.5`,
  `release/v3.4`, `priority/critical-urgent`)
- Affected: v3.4, v3.5 (≤ 3.5.15, ≤ 3.4.33) and `main` before the fix; found by the robustness
  tests (a watch missing a `DELETE` event, guarantee "reliable").
- Fix: PR #18274 "*: keep tombstone if revision == compactAtRev" (commit `bbdc94181`, merge
  `1d0a6b397`, 2024-08-16; backported to 3.5/3.4). Follow-ups: #18321 (tests), #19188
  (`d8b419257`, #19179: `restore` dropping a tombstone that is a key's first revision; also an
  ancestor of the pin, a different bug). The fix's `doCompact` change is the cause of the open
  regression `issues/etcd-compaction-delete-then-put.md` (etcd-io/etcd#22376).

What goes wrong (pre-fix code): `keyIndex.doCompact` (`server/storage/mvcc/key_index.go`) skipped a
generation while its tombstone's main was `<= atRev` (`tomb > atRev` to stop). For a key deleted at
revision `c` (its generation ends with the tombstone `c`, a new empty generation follows),
compaction at `c` skips that generation, finds no revision `<= c` in the next one, and keeps
nothing for the key: `scheduleCompaction` deletes the tombstone `c` from the bucket (and
`keyIndex.compact`'s "remove any tombstone" branch dropped such tombstones too). A watcher that is
unsynced with `minRev == c` (it has received up to `c-1`) passes `choose`'s `minRev <
compactRev` test (no `ErrCompacted`), and `syncWatchers` → `rangeEvents` reads the bucket from
revision `c`: the `DELETE` at `c` is gone, the other events of `c` are delivered. The watch drops
an event silently.

## Classification

**F (fixed before the verified code); counterfactual F−, gap C-scope.** The fix `bbdc94181` is an
ancestor of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes); at the pin
`doCompact` stops at `tomb >= atRev` (`key_index.go:272`) and `compact` no longer removes the
tombstone. Counterfactually the existing specs **admit** the buggy version: the compaction
results are about the index's answers at or above `c` and the bucket keys those answers name,
and a tombstone at `c` is named by no read at or above `c`; the one statement that would see the
lost event, the watch's `rangeEvents`, has the premise `crevFrozen` (the store is never
compacted, `Spec/.../mvcc/rangeEvents.lean:30,39`). The planned unit 6b (the watchable store
under compaction) needs exactly the lemma the buggy code breaks: STATUS "Traps for 6b" already
names it, so under 6b's spec this bug would be **F+**.

Source of verification states: `verified.txt` was not yet produced; states read from the proof
files (each a `theorem … wp_proof`; the word `sorry` in `store__Compact.lean`/`store__compact.lean`
is only in their header comments) and `etc/link-lean-first-mvcc.txt`.

## The counterfactual (step 5)

Pre-fix, `compactGenIdx` (`Proof/.../mvcc/Compact.lean:68`) would skip on `tomb ≤ atRev` instead of
`tomb < atRev`, so `kiAvail c ki = none` for a key whose generation ends with the tombstone `c`
followed by another generation. Which existing statements would break?

- `keyIndex.doCompact.spec`, `keyIndex.compact.spec`, `treeIndex.Compact.spec`
  (`keepSetIs`, `InvCompact.lean:76`) and `scheduleCompaction`'s deletions (`KeyDel`,
  `Compact.lean:1634`) are all stated through `kiAvail`/`kiCompact`/`keepAt`
  (`Compact.lean:90,1625`), which mirror the code: they would be redefined with it and stay
  provable. They say *which* revisions compaction keeps, not that it keeps enough.
- The client-facing compaction results — `kiGet_avail` (`Compact.lean:1646`), `named_not_del`
  (`:1758`), `rangeAnswers_not_del` (`:1876`), and `mvcc_rangeOutcomeC_ge` (`Results.lean:366-370`,
  "a read at or above the compaction revision is unchanged by compaction") — need only that a
  revision a read at `≥ c` names is kept. A key deleted at `c` reads as absent at every revision
  `≥ c` (its last generation is empty), so it names nothing; the dropped tombstone is never named.
  These remain true of the buggy code (not re-proved; the argument is that the dropped revision is
  outside their conclusion).
- The watch statements: `rangeEvents.spec` returns `logEvents log minRev maxRev` filtered — exactly
  the property violated — but requires `mvcc.crevFrozen γ` (`rangeEvents.lean:39`; frozen: the
  compaction revision is `-1` forever, `InvStore.lean:1254`, from `newWatchableStore`'s
  `compactRight_freeze`). So no statement here covers a watch over a compacted store, and the
  observed run (compaction at 141 while a watcher at `minRev = 141` is unsynced) is outside every
  premise. Hence F−, with the gap of class **C-scope**: watch completeness is proved for a store
  that is never compacted, while etcd compacts (auto-compaction, `Compact` RPC).

STATUS.md "Traps for 6b" (lines 8867-8880) records the lemma unit 6b will need: `rangeEvents` reads
`[minRev, maxRev)` with `minRev ≥ c`, revisions above `c` are never deletable, "but at main `c`
itself a revision is deletable unless compaction at `c` keeps it", to be proved "by the revision
bound plus `kiAvail` at main `c`". Pre-fix, `kiAvail` at main `c` drops a tombstone `c` that ends a
non-last generation, so that lemma — and 6b's spec — would fail on the buggy code at that step.

## Proposal: `watch-under-compaction` (mvcc unit 6b)

Drop `crevFrozen` from the watch path: `New` returns the compaction right instead of freezing it,
the loops' readers become `storeReaderC`, `syncWatchers` reads `compactMainRev` under `s.revMu`, and
`rangeEvents.spec` takes `c ≤ minRev` (the `choose` bound) with the bucket at a compaction level
`≤ c`, concluding the same `logEvents log minRev maxRev` filter. The pure lemma it needs:

```lean
theorem keepAt_main_eq (log : Log) (hb : LogB log) (c : Int) (hc : 0 ≤ c ∧ c < log.length)
    (hnd : NoDelPutAt log c) (hone : OneChangePerKeyAt log c)   -- put-then-delete excluded
    (r : Rev) (hr : sint.Z r.main = c) (hin : r ∈ revsAt log c) : keepAt log c r
```

with the thinned-snapshot lemma `snapThin` at `[c, maxRev)`. Then a watch-stream result that the
events a watcher receives are a gap-free suffix of the log from its start revision, or
`ErrCompacted` — the robustness test's "reliable" guarantee — across compactions. Cost: medium to
large: the pure lemma (~200 lines in `Compact.lean`, from `kiGet_avail`'s structure), re-proving
`syncWatchers`, `rangeEvents`, `New`/`newWatchableStore` and the two loops over `storeReaderC`
(the existing proofs carry over, the compaction branch of `choose`/`chooseAll` becomes live), and
the premise `hone` discharged from the gRPC transaction checks (`checkIntervals`; see
`issues/etcd-txn-delete-then-ignore-put.md` for where those checks are weaker than assumed). It
would have caught this bug and guards the open regression `issues/etcd-compaction-delete-then-put.md`
from the watch side as well.
