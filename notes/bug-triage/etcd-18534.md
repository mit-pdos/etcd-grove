# etcd-io/etcd#18534: "failed to publish local member to cluster through raft" after rebooting a single-node etcd

- URL: https://github.com/etcd-io/etcd/issues/18534 (filed 2024-09-03; converted to a discussion
  by a maintainer on 2024-09-04, so it shows as closed/completed; label `type/bug`). No fix, PR or
  commit.
- Affected: 3.5.6 (bitnami image, k3s), single member.

What was reported. After a host reboot, the single member restarts from a snapshot at index
100001 with `commit 135002` (`applied: 100001`). It elects itself leader at term 19 within a
second. From then on, `publishV3` (3.5: `publish`) logs "failed to publish local member to
cluster through raft ... request timed out" every 7 s. Clearing the data directory restored
service. Maintainers pointed to #15929 and #14514 (both DNS or peer-connectivity cases, closed)
and asked for a reproduction and full logs. None came, and the issue was moved to discussions.

## Classification

**N** (a support request, undiagnosed; converted to a discussion). No cause was established and
no reproduction exists. The log is consistent with the apply loop not getting through the
replay of entries 100001..135002 within the publish timeout, or with it being stuck. A single
member that is leader commits its own proposal immediately, so the timeout means the publish
entry was not *applied* in time. If that is a real hang, it would be **C-live**: the apply loop
(`applyAll`, `applyEntries`, `apply`: verified) and the request path's wait (`publishV3`:
assumed) have partial-correctness specs only, and a loop that never applies meets every one of
them. Other candidates (a corrupt or inconsistent data directory, given that a fresh one works,
and the "found invalid file under data directory: member_id" warning) live in bootstrap, the WAL
and snapshot loading, none translated (O-pkg).

## Proposal

None specific (class N, no diagnosis). If a reproduction turns up a stuck apply loop, the safety
stand-in of the skill would apply. An example: "a proposal whose entry is applied triggers its
waiter" is already in `applyAll_model` (the waiters at the new applied index). The missing piece
would be progress of the apply loop over replayed entries, which is liveness and outside
Perennial's partial correctness.
