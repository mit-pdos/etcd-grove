# etcd-io/etcd#10566: Compare not equal operator is broken in etcd

- URL: https://github.com/etcd-io/etcd/issues/10566 (open: filed 2019-03-20 against v3.3.12,
  closed 2026-06-04 as reported against an EOL version, reopened; labels `type/bug`, `stage/tracked`)
- Affected: every version (the rule dates from v3.0); unchanged at the pin.
- Fix: none. Maintainers (jingyih, 2019) agree the rule is confusing; no PR changes it. The
  `proto: no coders for int` log lines of the report are an unrelated stringer artifact.

What happens: `Txn().If(Compare(Value(k), "!=", v)).Then(OpPut(k, v))` on a missing key `k` takes
the `Else` branch. `applyCompare` (`server/etcdserver/txn/txn.go:268-292` at the pin) answers
`false` for every `VALUE` comparison of a range with no key ("Always fail if comparing a value on
a key/keys that doesn't exist; nil == empty string in grpc"), whatever the operator, while the
other targets compare a missing key as the zero `KeyValue`. So `=` and `!=` are both false.

## Classification

**N (documentation; the behavior is the code's deliberate rule), with a spec that states it.**
The verified spec of `applyCompare` gives exactly the reported outcome: its result is
`cmpHolds (stateAfter log) c`, and `cmpHolds` returns `(c.target != .value) && ...` when the
range selects no key. The bug is that no API documentation says so: `rpc.proto`'s `Compare`
(`api/etcdserverpb/rpc.proto:606-650`) and the website's API page ("It may check for the absence
or presence of a value") suggest the opposite. Recorded as `issues/etcd-compare-value-missing-key.md`.

Source of verification states: `verified.txt` was not produced; states read from `Spec/`,
`Proof/` (each a `theorem … wp_proof`) and the txn `Link.lean`.

## The argument (step 4)

- `txn.applyCompare.spec` (`applyCompare.lean:30-35`): `RET #(cmpHolds (mvcc.stateAfter log) cm)`.
- `cmpHolds` (`Proof/go_etcd_io/etcd/cache/v3/InvEtcdTxn.lean:124-127`):
  `let sel := s.filter (inRange c.key c.rangeEnd ·.key); if sel = [] then (c.target != .value) &&
  cmpKv c (zeroKv c.key) else sel.all (cmpKv c)`. For a missing key and target `.value`, `false`
  for every operator, including `.neq` (`CmpOp.holds`, `:103`). The observed `Succeeded: false`
  is the spec's outcome, not a deviation.
- This is also the model the client contracts are stated in (`client/v3/InvCmp.lean:6`: "What a
  comparison *means* (`cmpHolds`, etcd's rule)"), so every verified client (recipes, concurrency,
  cache, leasing) is proved against this rule; none relies on `!=` holding for a missing key.
- What the user expected (a missing key's value compares as `""`, or an error) is a different
  API; no premise or axiom is involved.

Related: `issues/leasing-evalcmp-missing-key.md` (the leasing KV's cache evaluates comparisons on
missing keys differently from this rule: a value `=` holds there).

## Proposal

None for verification (N): the spec already is the precise documentation. The documentation fix
(state the rule in `rpc.proto`'s `Compare` and on the API page, with the
`ModRevision(k) > 0` / `= 0` idiom for existence) is in the `issues/` file.
