# etcd-io/etcd#13984: err is auth: revision in header is old in ETCD 3.4.16

- URL: https://github.com/etcd-io/etcd/issues/13984 (closed 2022-04-27 as a duplicate of #13976;
  label `type/bug`)
- Affected: 3.3.11 and 3.4.16. A 3-member cluster with auth, in Kubernetes. The issue appeared
  after upgrading from 3.3.11 to 3.4.16. One member's MVCC revision is 1111 against 1306 on the
  others, at the same raft and applied index (1446). Requests fail at apply with `auth: revision
  in header is old`.
- Upstream: duplicate of #13976, itself the continuation of #13503. ahrtr suspected #11651, the
  auth data-corruption bug fixed by PR #11652 (`cb633418a`, 3.3.21/3.4.8: the auth store saves
  the consistent index with its writes). mitake pointed to #13308 (`a08cc733b`, a client-side
  retry on `ErrAuthOldRevision`), backported to 3.4.19. #13976 was closed after that backport.
  No server-side cause was identified for 3.4.16.

What goes wrong, as far as known. The apply-time checks (`authStore.isOpPermitted`) reject a
request whose header's `AuthRevision` is below the member's auth revision
(`ErrAuthOldRevision`). If one member's auth revision differs from the others', the same
committed entry is applied on some members and rejected on others, and their KV states diverge.
That matches the revision gap reported. #11651 was exactly such a mechanism: a crash after an
auth write but before the consistent index was saved. On restart, the auth entry was re-applied,
which bumped the revision again. Here the members ran 3.3.11 (no fix) before the upgrade, so
the divergence may well predate 3.4.16.

## Classification

**N (duplicate, diagnosis unsettled); candidates F (#11651) with A-model, and C-other.** The
report gives no reproduction and no code-level cause, and upstream closed it as a duplicate.
Each candidate:

1. **#11651 (most likely, given the 3.3.11 history): F.** `cb633418a` is an ancestor of the pin
   `107edf7e4`. At the pin, the auth admin writes go through the backend's batch transaction,
   whose post-lock hook saves the consistent index in the same batch
   (`server.go:2448-2455`). The apply model has the matching shape: the admin methods are
   contracts taking `mvcc.csContract P f Pre Q Post` (`apply/Contracts.lean:120-125`), so they
   run the hook inside their critical section. But those are contracts, not proofs, since the
   admin side of `store.go` is not translated, and the harm needs a crash and a replay, which
   is not modeled. Counterfactual **F− (A-model, O-fn)**: the `crash-restart-model` gap.
2. **A divergence carried across the upgrade**: an operational cause, outside the code (N),
   and outside the model (no upgrade or migration path is translated).
3. **Whatever the cause, the specs do not exclude divergence by auth decisions (C-other).**
   With auth enabled, the apply model's auth layer rejects or passes by free choice:
   `chainStep`'s `.auth` case (`apply/Chain.lean:174-177`, `authMayReject on rq` true whenever
   `on`), and `alarmPut … o = .rejected .auth ∨ …` (`apply/Results.lean:85-88`) in
   `applyEntries_kv` (`etcdserver/Results.lean:292`). The auth revision is not part of the
   modeled state: `authInfoRO`'s `Revision` is opaque, and the store's `revision` is an atomic
   held in an invariant with no ghost value (`auth/InvAuth.lean`, `revInv`). So "members with the
   same applied entries have the same auth revision and make the same auth decisions" is not
   stated. A member rejecting with `ErrAuthOldRevision` what others accept is consistent with
   every result.

Not X: the run the report shows is admitted by the specs.

## Proposal: `auth-state-model` (see `etcd-14571.md`), then `crash-restart-model`

`auth-state-model` puts the auth revision in the pure `AuthState` (`σ.rev`), so the auth layer
rejects with `ErrAuthOldRevision` iff `info.rev < σ.rev`. The admin methods advance `σ.rev`
(proved over `commitRevision` inside the batch's critical section), and `σ` is part of the
applied state that `applyEntries_kv` relates across members. This closes candidate 3. Candidate
1 then needs the crash model (`crash-restart-model`): `(σ, c)` persisted atomically, which is
the invariant #11652 established and which the hook's `csContract` already has the shape of.
