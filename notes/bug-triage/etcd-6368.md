# etcd-io/etcd#6368: Possible data loss -- fsync parent directories

- URL: https://github.com/etcd-io/etcd/issues/6368 (closed 2016-09-08; `type/bug`). Found with a
  crash-testing tool (the ALICE/CORDS line of work, OSDI 2016) on a 3-node cluster.
- Affected: etcd 3.0.x and earlier.
- Fix: PR #6381 "wal: fsync directory after wal file rename", commit `bd7107bd4` (2016-09-07).

What goes wrong (pre-fix `wal/wal.go`): `Create` writes the first segment as `*.wal.tmp`, fsyncs
it, and renames it to `*.wal`, but does not fsync the directory. `cut` does the same for each new
segment. A crash after the rename lets a file system drop the rename, and on restart the WAL sees
only the `.tmp` file (and removes it), losing entries the member had acknowledged. If this happens
on a majority, a committed write is lost.

## Classification

**F (fixed before the verified code); counterfactual F−, gaps O-pkg (WAL) and A-model (crash and
file-system durability).** `bd7107bd4` is an ancestor of the etcd pin `107edf7e4`
(`git merge-base --is-ancestor`: yes). At the pin, `Create` fsyncs the parent of the renamed WAL
directory (`server/storage/wal/wal.go:224`) and `cut` fsyncs `w.dirFile` after its rename
(`wal.go:847`). The pre-fix code would not have been caught here. The WAL package is not verified,
and the server sees it only through `isRNWal`
(`Proof/go_etcd_io/etcd/server/v3/etcdserver/InvRaftNode.lean:570-578`), whose `Save` has the
postcondition `True`. There is no crash semantics (`notes/STATUS.md:1137-1141`).

## Counterfactual

The bug is that a rename was not made durable before an acknowledgement was sent. No statement
here mentions durability. `isRNWal`'s `Save` promises nothing. Raft's acknowledgements
(`isAcked`) are justified by the node's volatile log (`notes/STATUS.md:1137-1141`). No result
covers a restart from a WAL (`notes/STATUS.md` stage R8a, D11). Both the pre-fix and the fixed
WAL meet every spec in this repository: **F−**.

## Proposal: `fs-crash-model` (new)

Verify the WAL's file protocol under a crash-consistent file-system model: unsynced file data and
unsynced directory operations (create, rename, remove) may be lost at a crash, and a write may be
torn at page granularity. The statement: after `Save` with `MustSync` returns, a crash followed by
`wal.Open` + `ReadAll` returns a log that extends the saved entries. The cut/rename/fsync sequence
of `Create`/`cut` is exactly where it would fail on the pre-fix code. Building blocks: the
`raft-durable-acks` contract (the `isRNWal` `Save` postcondition becomes this durable-prefix fact),
and a file-system model in Perennial. Perennial's Rocq side has one (crash semantics, used by
GoJournal); the Lean port does not, so this is a Perennial proposal first (CLAUDE.md, "Changes to
Perennial"). Cost: large (the model, plus about 1400 lines of WAL code: `encoder`/`decoder`,
`filePipeline`, `Repair`).
