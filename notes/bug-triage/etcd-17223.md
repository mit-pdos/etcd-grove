# etcd-io/etcd#17223: UnsafeRange panicking during shutdown

- URL: https://github.com/etcd-io/etcd/issues/17223 (closed 2025-04-26, "fixed via #17757";
  labels `type/bug`, `stale`)
- Affected: `main` in 2024 (CI flake of `TestMaintenanceSnapshotCancel`; again in the robustness
  tests, etcd-io/bbolt#715).
- Fix (per the thread): not an etcd change. fuweid: grpc-go `61eab378` (v1.61.0) makes
  `GracefulStop` wait for all method handlers, and etcd's `stopServers` uses `GracefulStop`
  except in two cases; PR #17790 (graceful stop under cmux/TLS) was closed unmerged; PR #17757
  (merged, `f77fa903c`) only makes a panic during defrag fatal; PR #17235 deflaked the test.

What goes wrong: the member stops while a `Maintenance.Snapshot` RPC is running.
`EtcdServer.run`'s shutdown calls `Cleanup` (`server/etcdserver/server.go:827`, `:942-957`),
which closes the backend: `backend.Close` → `run`'s `CommitAndStop` → `unsafeCommit(stop=true)`
resets `readTx` (`tx = nil`, `read_tx.go:133-138`) and does not begin a new batch transaction;
then bbolt's `db.Close`. The still-running handler (`maintenanceServer.Snapshot`,
`api/v3rpc/maintenance.go:140-146`) calls `backend.Snapshot` → `batchTx.Commit` → the pre-commit
hook → `cindex.UnsafeSave` → `schema.UnsafeUpdateConsistentIndex` → `batchTx.UnsafeRange` on the
closed transaction: nil dereference in bbolt (`Cursor.seek`).

## Classification

**A-axiom (primary): the trust-boundary postulate `EtcdServer.Cleanup.wp_proof` is false; O-path
/ O-fn secondary. The backend's own verified specs exclude the bug.** At the pin, the bug is still
reachable in two cases (code reading, not reproduced): `stopServers`
(`server/embed/etcd.go:487-522`) calls `grpc.Server.Stop()`, which by default returns without
waiting for method handlers (grpc v1.84 `server.go:645-654`, `WaitForHandlers`, which etcd does
not set), when the gRPC server runs under the HTTP server with TLS (`ss.secure && ss.http != nil`)
and when `GracefulStop` exceeds the request timeout (a long `Snapshot` or `Watch` stream); `Close`
then calls `e.Server.Stop()`, which ends `run` and runs `Cleanup`. The backend's verified `Close`
spec requires every client's token (`bOpen γ 1`) and so could not be applied while a reader or
committer holds a share; the server's proof calls `Cleanup` through an axiom with precondition
`isPkgInit` alone, which closes that same backend without any token. That axiom is what lets the
race through the proofs, and it is false in the proofs' own terms (below).

Source of verification states: `verified.txt` was not produced; states read from `Spec/`,
`Proof/` and the `Link.lean` files (backend, etcdserver).

## The argument (step 4)

1. **The backend's specs exclude the race.** A backend client's share of "open" is
   `bOpen γ q` (`Proof/go_etcd_io/etcd/server/v3/storage/backend/InvBackend.lean:191-192`).
   `batchTxBuffered.Commit` needs and returns `bOpen γ qo`; `backend.Close` needs `bOpen γ 1`, all
   of it (`backend__Close.lean`; `InvStop.lean` header: "`Close`, with the clients' whole open
   token"). So in a verified composition, `Close` cannot run while a committer or reader holds a
   share: the issue's interleaving is unprovable. Had `Cleanup` been verified against
   `backend.Close.spec`, its proof would have needed `bOpen γ 1`.
2. **The store keeps shares forever.** The real-backend store (`γ.kb = some d`, built by
   `server_kv_backend`/`server_kv_backend_hooks`, `Proof/.../etcdserver/Results.lean:766-800`,
   `:910-…`) hands each reader slot `kbRT` = `rdTok ∗ ∃ q, bOpen q`
   (`Proof/.../storage/mvcc/InvStore.lean:1018-1022`); `store.Close` does not take them back.
   Readers use them at any time (RPC handlers: `EtcdServer.Range` serializable reads, the
   maintenance and watch paths).
3. **The axiom.** `EtcdServer.Cleanup.spec` is `{{ isPkgInit }} s.Cleanup() {{ True }}` for any
   `s` (`EtcdServer__Cleanup.lean:26-30`), postulated by `axiom EtcdServer.Cleanup.wp_proof`
   (`Proof/.../EtcdServer__Cleanup.lean:24`), used by `run`'s shutdown
   (`Proof/.../EtcdServer__run.lean:187, 263`). The real `Cleanup` closes `s.be`, the same
   backend `d.be`, physically ending what `bOpen q` promises: after it, `readTx.tx = nil`, and a
   holder of `bOpen q` doing `ConcurrentReadTx`/`UnsafeRange` (verified to return) dereferences
   nil. With the axiom, the verified specs compose into a proof that a reader holding a store
   reader slot never crashes even concurrently with `run`'s shutdown, which the Go code
   contradicts. The postulate is stronger than the callee: **A-axiom, false as stated.** (Not a
   reproduced X: no single linked theorem today composes a reader thread with `run`, and nothing
   was run; but the axiom gives a client of the specs that composition for free.)
4. Premises otherwise: none of the verified specs on the path is called against its
   precondition by verified code; the unverified callers (`stopServers`, `Snapshot` handler)
   compose them wrongly (O-path).

## Proposal: `cleanup-backend-quiescence`

1. Restate the `Cleanup` axiom honestly: its precondition takes the backend's whole open token
   (`bOpen d.γB 1` with `isStopChans`), or — closer to the code — make `Cleanup` a verified call
   of `store.Close`, the lessor's `Stop` and `backend.Close`. The `run` proof then needs `bOpen 1`
   at shutdown, i.e. the store's reader slots returned.
2. That forces the missing protocol into the proof: a server-level "RPC handlers drained" token
   (as `GoAttach`'s `wg.Wait` drains the server's own goroutines: `goAttach_shutdown`): every
   handler that reads the store holds a share obtained from a closable registry, and shutdown
   waits for them. Upstream's matching code change is grpc's `WaitForHandlers(true)` (or the
   closed PR #17790 for TLS); with neither, the obligation is unprovable, which is the bug.

Statement sketch:

```lean
abbrev EtcdServer.Cleanup.spec : Prop :=
  ∀ (s : Loc) (d : mvcc.KBReal) …,
  {{ isPkgInit … ∗ srvBackendIs s d ∗ backend.isStopChans d.γB d.be ∗ backend.bOpen d.γB 1 ∗ mvcc.storeCloser … }}
    s.Cleanup() {{ RET #(); backend.bStopped d.γB }}
```

Cost: the restatement is small; discharging it in `run` is medium to large (a handler registry
with the store's reader slots, the gRPC layer's `Stop`/`GracefulStop` as a contract, and
`maintenanceServer.Snapshot`/`backend.Snapshot` translated and specified, about 60 Go lines). Also worth a
pass over the other names-only server axioms with `True` preconditions that free or close shared
objects (`notes/STATUS.md` lists 16 at unit 4c).
