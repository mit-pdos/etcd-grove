# etcd-io/etcd#21830: in 3.7 `clientv3.New` blocks on `DialTimeout` (regression from #21282)

- URL: https://github.com/etcd-io/etcd/issues/21830 (closed 2026-06-11; labels `type/bug`,
  `priority/important-soon`, `release/v3.7`)
- Affected: `main` between PR #21282 ("grpc: replace Dial APIs with NewClient", merge `256b0c4fc`,
  2026-02-26) and the fix; never released.
- Fix: PR #21832 "Make the etcd client creation non-blocking" (merge `34c005ea0`, 2026-06-11),
  which removed the wait for a ready connection from `newClient`/`dial`.

What went wrong: #21282 replaced `grpc.DialContext` by `grpc.NewClient` in `dial` and, to keep
`DialTimeout` meaningful, added `waitForConnection` whenever `DialTimeout > 0`: a gRPC health
`Check` with `WaitForReady(true)` under a `DialTimeout` context, returning "etcdclient: failed to
connect to the etcd server" on timeout (before, `DialContext` blocked only with
`grpc.WithBlock()`). A client to one stopped member then failed in `New`
("failed to connect to the etcd server ... context deadline exceeded"), so
`etcdctl endpoint status --cluster` aborted instead of reporting the live members.

## Classification

**F (fixed before the verified code); counterfactual F− (O-fn: no spec of `New`).** `34c005ea0` is
an ancestor of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes); at the pin `dial`
(`client/v3/client.go:318-328`) ends in `grpc.NewClient(target, opts...)` with no wait, and
`newClient` (`:362-486`) blocks only in `getToken` (auth) and `checkVersion`
(`RejectOldCluster`). Counterfactually nothing here would have caught the regression: `New`,
`newClient` and `dial` are not translated (`Code/go_etcd_io/etcd/client/v3.toml` translates the
`Client` struct, not its constructor); the client-side results assume their client (`retryClientOk`,
`isEtcdClient`) instead of proving that `New` builds one.

Source of verification states: no `verified.txt`; the `.toml`, `Spec/`, `Proof/` files.

## The counterfactual (step 5)

The pre-fix `newClient` waited for readiness (bounded by `DialTimeout`) and returned an error if
the connection did not become ready. A spec of `New` of the usual partial-correctness shape
("an error, or a client meeting `isEtcdClient`") admits that: an extra error outcome is allowed.
What would exclude it is a precise-outcome spec (C-err): **`New` fails only on a configuration
error** (no endpoint, credentials or TLS setup, an invalid target) **or on the failure of the
calls it makes by configuration** (`getToken` when a username is set, `checkVersion` when
`RejectOldCluster`); in particular, not because an endpoint is unreachable. The pre-fix code
violates it on the issue's run (one stopped endpoint, no auth, no version check). Blocking itself
is a liveness/timing matter and stays out of reach.

## Proposal: `verify-client-new`

Specify and prove `clientv3.New`/`newClient`/`dial`/`dialWithBalancer`/`dialSetupOpts`
(about 200 Go lines of `client.go`, plus `NewKV`, `NewWatcher`, `NewLease`, ... already partly
verified) with: an error only in the cases above, otherwise a client meeting the predicates the
client-side results now take as premises (`retryClientOk`, `isEtcdClient` with its KV, watcher and
lease parts), and an invariant `c.endpoints ≠ []` (which also covers etcd#18090,
`client-endpoints-nonempty`). gRPC's `NewClient` at the trust boundary: it returns an error only
on a malformed target or options, never from the network (true of grpc-go's documented
`NewClient`). Cost: medium; it discharges premises every client-side result assumes today, so it
also shrinks the trust base.
