# etcd-io/etcd#22065: gRPC proxy serializable Range cache can leak protected KV data across auth contexts

- URL: https://github.com/etcd-io/etcd/issues/22065 (open, filed 2026-07-09; label `type/bug`).
  Reproduced on 3.6.12 and 3.6.13; the reporter says `main` has the same code. No fix PR yet.
- Observed: with auth enabled behind `etcd grpc-proxy`, root reads `/proxy-cache/secret` through
  the proxy. A user with an empty role, or a client with no credentials at all, then gets the value
  with `--consistency=s` through the proxy. Directly against the server, the same request is denied
  (`permission denied`, `user name is empty`). Ranges inside an authorized `Txn` fill the cache the
  same way, and `--keys-only` leaks key names.

What goes wrong (at the pin): `kvProxy.Range` (`server/proxy/grpcproxy/kv.go:47-76`) answers a
serializable request from `p.cache.Get(r)` before it forwards anything. It stores every forwarded
response, linearizable ones included, under `keyFunc(req)` with `Serializable = true`. `txnToCache`
(`:98-112`) stores the range responses of a `Txn`. The key is the marshaled `RangeRequest` alone
(`cache/store.go`), with no token, user or auth revision. On a cache hit, the server's
authorization (`authApplierV3.Range`, `checkRange`) never runs.

## Classification

**O-pkg** (O-path in kind). The code is `server/proxy/grpcproxy` (`kv.go`, `cache/store.go`), which
is not translated: no `Code/` module, and no row in the inventory
(`/shared/etcd-grove-triage/coord/verified.txt`). It is present at the pin `107edf7e4`, as quoted
above. On a cache hit no verified function runs at all. On a miss the request goes through the
verified client and the server's verified `kvServer.Range` and `authApplierV3.Range`. Those specs
are about the request that reached the server, under its own context, and they cannot speak for a
response that the proxy hands to another caller. Even if the proxy were verified, the auth specs
here have no identity (some auth info, or some error), so "the caller may read this" is not yet
statable (the proposals `inproc-client-auth-identity` and `auth-state-model`).

The same holds, by design, for the verified etcd `cache` package (`cache/v3`). It serves `Get`
from one client's watch, and its specs (`cacheGetOk`) carry no identity. That is not a bug: the
library has no auth surface. But a server that put it in front of several users would need the
check that the proxy lacks.

## Proposal: `grpcproxy-cache-auth`

Translate and verify `kvProxy` (`kv.go`, 244 Go lines) and its cache (`cache/store.go`, 174),
over the client KV specs, with the identity-carrying auth model of `inproc-client-auth-identity`
and `auth-state-model`. The statement is the server's read guarantee restated at the proxy. A
response that `kvProxy.Range` returns for context `c` is one the backend returned to a request
authorized as `authOf c` (at an auth revision not older than the entry's):

```lean
kvProxy.Range.spec : … {{ resp, RET resp; ∃ e, servedBy e resp ∧ permitted σ_auth (authOf c) (rangeOf r) }}
```

The cache invariant would map each entry to the identity and auth revision that produced it. The
pin fails it at the cache hit. A fix keys the cache on `authOf` (or disables it under auth), and
the same invariant then holds. The proof would also settle the open lead in `issues/README.md`
(the cache's invalidation intervals are built as `checkIntervals` built them, so a cached from-key
range may never be invalidated), since the cache's coherence with the backend is part of the same
invariant. Cost: medium. The code is about 420 lines; most of the work is the auth model the two
proposals above already need, plus an `lru`/`adt.IntervalTree` model (or trust-boundary specs for
them).
