# etcd-io/etcd#21128: `concurrency.Election` is not resigned if an error occurs in `Election.Campaign`

- URL: https://github.com/etcd-io/etcd/issues/21128 (closed 2026-05-11 by the stale bot; labels
  `type/bug`, `stale`). Not fixed. Candidate fix: PR #21165 "concurrency: resign election on
  campaign failure" (open, unmerged; it calls `e.Resign` on every `waitDeletes` error). Related:
  etcd-io/etcd#22123 / PR #22124 (open): `Resign` forgets the leadership when its own transaction
  fails.
- Affected: every version with the current `Campaign`. Reported on server 3.6.5, client 3.5.5.
  Present at the etcd pin `107edf7e4`.

What goes wrong: `Election.Campaign` (`client/v3/concurrency/election.go:69-107` at the pin) puts
the candidate key `pfx/<lease>` and then waits in `waitDeletes`. If `waitDeletes` fails while the
caller's context is live (a `Get` error, or a watch error such as `ErrCompacted`, which
`waitDelete` returns from `wr.Err()`), the `default:` branch (lines 96-101) sets only
`e.leaderSession = nil` and returns the error. The key stays in etcd, attached to the session's
lease, and `e.leaderKey`/`e.leaderRev` still name it. `Resign` (lines 132-145) returns `nil`
without doing anything when `leaderSession == nil`, so the caller cannot remove the key through
the `Election`. While the session lives, the orphaned key stays a candidate. Once the keys
created before it are gone it is etcd's leader (`Leader()` returns it), but no process acts as
that leader, and every later candidate waits behind it. The reporter's loop opens a new session
on each iteration, so its orphans pile up.

## Classification

**C-err (the spec is too weak), with the bug present at the pin.** `Campaign` and `Resign` are
verified (sorry-free). `Election.Campaign.spec`'s error outcome is
`⌜err ≠ nil⌝ ∗ ∃ st', electionState e s st'`
(`Spec/go_etcd_io/etcd/client/v3/concurrency/Election__Campaign.lean:53`). It allows any final
state and says nothing about the key in etcd. `Election.Resign.spec`'s first case
(`.../Election__Resign.lean:40`) states the no-op: with `st.sess = null`, it returns `nil` and
leaves the state unchanged. Together the two specs admit the observed sequence: `Campaign` fails,
the key is present, `Resign` returns `nil`, and the key is still present. Nothing stronger is
claimed anywhere (`Results.lean`'s `election_exclusion` is about leaders that `Campaign` returned
`nil` to).

## The argument (step 4)

1. Observed, in the spec's terms: from `electionState e s st` and a live context, `Campaign`
   returns `err ≠ nil` with `electionState e s ⟨key, rev, null, hdr⟩`. At the error's revision,
   `key` is present under `pfx` with create revision `rev` (the transaction put it, line 76). Then
   `Resign(ctx')` returns `nil`, the state is unchanged, and `key` is still present.
2. Premises: `isElection`, `electionState`, `context.isCancelCtxCtx ctx` and `etcdReached lo` all
   hold for the reporter's `context.Background()` (cancelable through `waitDelete`'s
   `WithCancel`). The client contract (`isEtcdMutexClient`, with the range watch of
   `InvEtcdTxn.lean`) allows a watch to end with an error (`ErrCompacted`), which is what the
   reporter's frequent compaction triggers. No premise is violated: not A-pre.
3. Assumptions: the four axioms above are not involved. Not A-axiom or A-model.
4. Postconditions: `Campaign`'s error disjunct is `∃ st', electionState e s st'`, which
   `⟨key, rev, null, hdr⟩` satisfies. `Resign`'s first disjunct, `⌜st.sess = null ∧ err = nil⌝ ∗
   electionState e s st`, is the no-op. What the user expected, "after `Campaign` fails, either
   its key is gone or `Resign` removes it", is not implied by either spec. Hence C, and C-err
   because the spec leaves the error outcome entirely open.

STATUS "Election" (`notes/STATUS.md:11374-11452`) records the spec as "Errors: some state" and
lists the error paths of `Campaign`'s doc comment. It does not flag the orphaned key.

## Proposal: `election-key-accountable`

Every way out of `Campaign`, `Proclaim` and `Resign` either leaves the key accounted for in the
`Election` (so that `Resign` can still remove it) or shows that it is gone from etcd:

```lean
-- Campaign's error disjunct (and Resign's error disjunct, likewise):
(⌜err ≠ nil⌝ ∗ ∃ st' : ElectionSt, electionState e s st' ∗
   ((⌜st'.sess = s ∧ pfx <+: st'.key⌝ ∗ ∃ R, etcdReached R)          -- Resign can still delete it
    ∨ (∃ key rev R, notLeaderAt pfx key rev R ∗ ⌜sint.Z lo ≤ sint.Z R⌝)  -- the key is gone
    ∨ ⌜st'.key = st.key ∧ st'.sess = st.sess⌝))                       -- the transaction never ran
```

The pinned code fails it in three places. `Campaign`'s `default:` branch clears the session with
the key present (#21128). `Resign`'s error disjunct (`Election__Resign.lean:45`) clears the
state although the delete may not have run (#22123). `Campaign`'s `Proclaim`-failure path ignores
`Resign`'s error, the same issue one level down. PR #21165 (`Resign` on every `waitDeletes` error)
together with PR #22124 (`Resign` keeps its state on error) would meet it. Cost: small. These are
spec changes to three methods whose proofs exist. The proofs re-run after the fixes are applied
to the fork (`.claude/skills/etcd-pr-verify`). `notLeaderAt` and the `Resign` delete reasoning
already exist (`InvElection.lean:174`). The same property for `Mutex.Lock`/`Unlock`
(`Mutex.Lock.spec`'s last disjunct is also "some state") is a natural extension.
