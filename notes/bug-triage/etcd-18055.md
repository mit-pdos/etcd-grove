# etcd-io/etcd#18055: panic when two snapshots are received in short period

- URL: https://github.com/etcd-io/etcd/issues/18055 (open; `type/bug`, `help wanted`,
  `stage/tracked`, `area/robustness-testing`). Duplicates: #20133 (Antithesis, main `3be967f`,
  default configuration), #20657 (3.5.18), both closed as duplicates or known.
- Affected: 3.5 and main (3.6, 3.7). Easiest with a low `--snapshot-count`, but Antithesis hit it at
  the default.
- Fix: none merged. PR #21082 (closed unmerged), PR #22046 "snap: keep snapshot db files until they
  have been applied" (open). Neither is an ancestor of the pin. The bug is **present at the pin**.

What goes wrong, in Go terms (pin `107edf7e4`): a slow follower receives two `MsgSnap`s, `i < j`,
in quick succession. rafthttp saves `i.snap.db` and `j.snap.db` (`Snapshotter.SaveDBFrom`), and raft
restores `i` and then `j`, in consecutive `Ready`s. Each `Ready` runs through `raftNode.start`
(`server/etcdserver/raft.go`):

1. It hands `toApply{snapshot: i}` to the apply scheduler (`:232`).
2. It saves the snapshot, sends `notifyc` (`:274`), applies it to `MemoryStorage`, and calls
   `r.storage.Release(snap i)` (`:281`) → `Snapshotter.ReleaseSnapDBs` (`api/snap/snapshotter.go:45-70`),
   which deletes every `*.snap.db` whose index is `< i`.
3. It blocks on the second `notifyc` send (`:302`, capacity 1) until `applySnapshot` has taken the
   first (`server.go:1037`). Then it advances and goes on to the next `Ready`.

`applySnapshot` then takes `s.bemu` (`:1040`) and only then calls `OpenSnapshotBackend`
(`:1048`) → `DBFilePath(i)`. If the loop has meanwhile processed `Ready` `j` and run
`ReleaseSnapDBs(j)`, `i.snap.db` is gone. `DBFilePath` returns `ErrNoDBSnapshot`, and `lg.Panic("failed
to open snapshot backend")` (`:1050`) kills the member (it recovers on restart from the newer
snapshot). The window is `server.go:1037`→`:1048`, widened by `bemu` contention.

## Classification

**A-pre (secondary O-fn).** The buggy code is translated and the two functions it races between
are verified: `raftNode.start` (112 lines) and `EtcdServer.applySnapshot` (102 lines). But the
specs assume raft's `Ready` never carries a snapshot. The server-side contract has
`⌜rd.Snapshot' = null⌝` (`rnReadyData`, `Proof/.../etcdserver/InvRaftNode.lean:190`), the
`applyc` payload `⌜ap.snapshot' = null⌝` (`rnApP`, `:682`), and `applySnapshot.spec` takes
`taSnapshotAddr ap ↦□ null` (`Spec/.../etcdserver/EtcdServer__applySnapshot.lean:30`).
So every line on the bug's path is dead code in the proofs (STATUS "Gaps, by the contract: no
snapshots … in a `Ready` (those branches are dead)"). Real followers do receive snapshots. The
snapshot-file functions (`Snapshotter.*`, `storage.Release`, `OpenSnapshotBackend`) are not
translated, names only.

Source of verification states: `verified.txt` (`etc/verified-code.py`, this batch).

## Step 4: does the spec exclude the bug?

1. **The observed behavior, as the specs see it.** Two consecutive `Ready`s with `Snapshot ≠ nil`,
   indices `i < j`. The loop interleaves its `Release(j)` between the apply goroutine's receive on
   `notifyc` and its `OpenSnapshotBackend(i)`. The apply goroutine panics.
2. **Premises.** `raftNode.start.spec` takes `isRaftNode E γ r`, whose node contract delivers
   `Ready`s satisfying `rnReadyData`, including `rd.Snapshot' = null`. The real `raft.Node` hands out
   `rd.Snapshot` whenever raft restored one (`raft.handleSnapshot` → `restore`, then
   `RawNode.readyWithoutAccept`). Raft's own specs keep the same scope: `RawNode.Step` is specified
   for `netStepTypes`, which has no `MsgSnap`. A restore makes a snapshot pending, which
   `ownRawNode` forbids (STATUS "Snapshots at the public API (stage S)", items 2-3). The bug's
   setting (a lagging follower sent `MsgSnap`) violates the premise. **A-pre**, at
   `InvRaftNode.lean:190` (server) and `InvRawnode.lean:465` / `InvRawnodeReady.lean:812` (raft).
3. **Axioms and model.** No axiom is involved on the live path, since under the premise the
   branch is not taken. The files are outside the model: Perennial has no file system in this
   repository's trust base for `api/snap`, and these functions are names-only (O-fn).
4. **With the premise lifted, would the specs as written exclude it?** There is no spec to test:
   `applySnapshot.spec` has no case for a snapshot. Any spec of that case would have to
   make `OpenSnapshotBackend` succeed, since `lg.Panic` cannot meet a postcondition. A
   separation-logic spec would do this by having `applySnapshot` own the file `i.snap.db` from
   the `toApply` it receives. Then `ReleaseSnapDBs(j)`'s precondition (ownership of every
   `.snap.db` below `j`) could not be met at `raft.go:281` while apply `i` is in flight. So a
   resource-style spec would catch the race. The present proof does not exclude it only because of the
   premise.

## Proposal: `server-apply-snapshot`

Lift the no-snapshot premise on the server's raft loop and apply path, with the snapshot files as
resources:

```lean
-- trust boundary (names-only api/snap): a .snap.db file is a resource
axiom Snapshotter.SaveDBFrom.wp_proof : … {{ … }} ss.SaveDBFrom(r, id) {{ RET (n, nil); snapDB γs id }}
axiom Snapshotter.ReleaseSnapDBs.wp_proof :
  … {{ snapDir γs D ∗ [∗ set] k ∈ D.filter (· < idx), snapDB γs k }} … {{ RET nil; snapDir γs (D.filter (idx ≤ ·)) }}
axiom OpenSnapshotBackend.wp_proof : … {{ snapDB γs (snap.index) ∗ … }} … {{ RET (be, nil); isBackend … }}
-- rnApP: a toApply with a snapshot carries snapDB γs snap.index (via notifyc), the loop keeps none
```

`raftNode.start`'s proof would then fail at `raft.go:281`: it cannot give up `snapDB i` while
`applySnapshot` holds it. That is the bug. With PR #22046's protection, it would go through.
Prerequisites: raft's stage S items 2-3 (`MsgSnap` at `RawNode.Step`, a pending snapshot through
`Ready`/`Advance`), which is the existing `raft-pending-snapshot-ready`, and the `raft.Node`
contract's `rnReadyData` widened to a snapshot. Cost: large overall, because `applySnapshot`'s body
restores lessor, mvcc, auth, alarms, membership and the consistent index (most behind trust-boundary
specs, `verify-watchable-restore` and `mvcc-restore-from-backend` for the stores). The file-ownership
part alone, with `applySnapshot`'s downstream axiomatized, is medium.

## Findings

- New: `issues/etcd-snapshot-db-released-before-apply.md`. The bug is present at the pin in
  translated, verified-but-premised code. It has a unit-level reproduction of the deletion at the
  pin. The race itself is reproduced upstream (robustness tests, Antithesis).
- No bug in this repository's specs. The premise is documented (STATUS, stage S and the server's
  raft wrapper).
