# etcd-io/etcd#21636: consistent index left behind by alarm entries, restart fails

- URL: https://github.com/etcd-io/etcd/issues/21636 (closed 2026-04-27; label `type/bug`)
- Affected: etcd 3.5.4. The reporter's cluster was upgraded 3.5.4 → 3.6.8, and the corrupt db
  dates from 3.5.4. The maintainer (ahrtr) says it was fixed in v3.5.5.
- Fix: etcd-io/etcd#14419 on `main` (merge `3dc5348d9`, 2022-09-05; issue #14382) and its 3.5
  backport #14429 (`204c0319a`). The bug itself came from #13942 (`e02ac59cf`, 2022-04), which
  made the deferred update conditional. Both commits are ancestors of the etcd pin `107edf7e4`
  (`git merge-base --is-ancestor`).

What goes wrong (pre-fix code). Before #14419, `applyEntryNormal` ran the deferred
`SetConsistentIndex(e.Index, e.Term)` only when the request was not applied to v3, or when it was
applied with an error (`!applyV3Performed || (ar != nil && ar.err != nil)`). Once the NOSPACE
alarm is raised, the server keeps proposing `Alarm{ACTIVATE, NOSPACE}`. Each of those entries finds
the alarm already set. `AlarmStore.Activate` returns the existing member without writing the
backend, so the batch lock is never taken and the post-lock hook never runs. The result has no
error, so the deferred update is skipped too. The in-memory consistent index falls behind the
applied index. A disk snapshot then commits a db whose `consistent_index` is below the snapshot's
index. On restart, bootstrap concludes the snapshot's `.snap.db` must be used, does not find it, and
panics with "failed to recover v3 backend from snapshot".

## Classification

**F+ (fixed before the verified code; the spec excludes the buggy version).** The fix is an ancestor
of the pin: at the pin the deferred update runs whenever `ConsistentIndex() < e.Index`
(`server.go:1941-1949`). Applied to the pre-fix condition, the existing specs fail. The applier's
contract does not tie "the hook ran" to "no error": `apply.Apply` returns `Post ∨ Pre` whatever
`ar.Err` is. For an alarm entry, the alarm store's `Activate` may return the existing member having
written nothing. So the proof cannot establish `applyEntryNormal`'s postcondition that `ci` equals
the entry's index.

Source of verification states: `verified.txt` (`etc/verified-code.py`, at `d606c9cac`).

## The counterfactual (step 5)

Put the pre-fix defer into the pin's `applyEntryNormal`, so the update runs only if `apply.Apply`
was not called or returned `ar.Err ≠ nil`. Then follow the `v3` case of the proof:

- `apply.Apply.spec` returns `(if v3 then iprop(Post ∨ Pre) else Pre)` and, separately,
  `apply.resultErrOk ar` (`Spec/.../apply/Apply.lean:72`). `Post` means the applier took the batch
  lock and ran the hook (`ci := i`, protocol step `hook_set_au`). `Pre` means it wrote nothing. No
  conjunct relates the disjunct to `ar.Err`.
- The `Pre` branch with `ar.Err = nil` is reachable, and it is exactly the issue's case. The alarm
  store's contract gives `Activate` the postcondition `(Post ∨ Pre) ∗ (⌜m = null⌝ ∨ alarmMemberIs
  m)` (`Contracts.lean:293-310`: "write the alarm bucket under the batch lock (or not: an alarm
  already set ...)"). `applierV3backend.Alarm` returns a response with no error either way
  (`apply/applierV3backend__Alarm.lean:30-36`: "a critical section, or none", `mPost ... Pre Post` with `applyErrIs err`; Go `backend.go:118-127`).
- In that branch the protocol state is `p := i` (`skip_done`) with `ci` unchanged. The pre-fix code
  skips `ci_advance_au`, so the postcondition `applyThread γ ⟨m.index, m.index, eff, false⟩`
  (`EtcdServer__applyEntryNormal.lean:76`, first field `k` = the consistent index) cannot be proved.
  The proof breaks at the deferred function's `if`.

So the stated spec excludes the bug, which makes this F+. One caveat about what carries the weight:
the protocol invariant itself (`eff ≤ ci ≤ p`, `InvApply.lean`) and the apply loop's `loopOk`
(`p = max(ciEff k, a)`, `InvApplier.lean:97`) would both survive `ci < p`. The bug is excluded by
`applyEntryNormal`'s exact postcondition, not by a system-level invariant. The invariant the
failure actually violates is "at a snapshot, the db's committed `ci` ≥ the snapshot index"
(`verifyConsistentIndexIsLatest`, server.go `snapshot`). That invariant lives in `EtcdServer.snapshot`,
which is an axiom. Making it a theorem is the proposal below. It would turn this F+ from "a
postcondition says so" into "the restart property says so".

## Proposal (optional, since F+): `server-snapshot-ci-latest`

Add `uint.Z a ≤ uint.Z (ciEff γ st.k)` to `loopOk`. Its docstring already claims this at start
("the applied index is the snapshot's, at most the stored consistent index"). It is kept by
`applyEntryNormal` (k = m.index) and by `applyConfChange`'s contract (`Post ∨ Adv`: hook or
`SetConsistentIndex(i)`). Then prove `EtcdServer.snapshot` (37 lines, now an axiom): its
`KV().Commit()` saves `ci` (`commit_save_au`), so `verifyConsistentIndexIsLatest(snap, ci)` is
proved never to fire, and the db committed before `SaveSnap` has stored index ≥ `ep.appliedi`.
Cost: small to medium. The loop invariant gains a conjunct, `snapshot` needs specs for
`raftStorage.CreateSnapshot` (raft's, proved) and `storage.SaveSnap` (trust boundary). See also
`etcd-17146.md`.
