# etcd-io/etcd#16693: Etcd revision decreased by 100, while the data stays the same

- URL: https://github.com/etcd-io/etcd/issues/16693 (closed 2024-04-26 "reports no longer
  available"; labels `type/bug`, `area/testing`, `priority/important-soon`).
- Affected: `main` at `6a0d2eb5c` (Oct 2023), robustness test
  `TestRobustness/Kubernetes/HighTraffic/ClusterOfSize1`, failpoint `compactBeforeSetFinishedCompact`
  (a panic between a compaction's bucket deletions and its `finishedCompact` write).
- Fix: none was attributed. PR #16695 fixed only a false "Ordered" alarm in the test's watch
  validation. The diagnosis was never settled: serathius suspected the consistent index or a
  hardware bit flip, and ahrtr argued against the consistent index.

The observation: the WAL shows `compaction:<revision:301>` (index 346). After the restart, the
single member reported revision 191 for the same key-value contents. Later writes reused
revisions 192, 193, ..., which the watch validation flagged as two different events at the same
revision. That is the signature of etcd#17780.

## Classification

**F (probable: the same mechanism as etcd#17780, whose fix is in the pin); counterfactual F−, gap
O-fn (secondary A-model). The diagnosis is unsettled.** The evidence is the same failpoint, the
same single-member topology and the same symptom: after a panic during compaction, the restored
revision is lower than the one acknowledged, and the data is unchanged. This is the failure
etcd#17780 diagnosed six months later. There, compaction at the current revision deleted the
bucket's top revisions (tail tombstones, pre-#18274), and `store.restore` recomputed `currentRev`
from the bucket's highest revision. Its fix (`dd4e35a58`, `currentRev ≥ scheduledCompact`) and
#18274 (the tombstone at the compaction revision kept) are both ancestors of the pin
`107edf7e4`. The one oddity is the size of the drop (110 revisions, all of whose surviving
effects had to be compacted away). It is unexplained but not excluded: 192–301 would have to be
deletes, or writes to keys deleted by 301. The other candidate causes are out of scope here: a
hardware fault is N; a consistent-index fault is excluded at the pin, see `etcd-13766.md`.

## Code path

As in `etcd-17780.md`: `store.Compact`/`compact`/`scheduleCompaction` and the key index's
compaction are verified; `store.restore` is a trust-boundary axiom on an **empty** `Key` bucket
only (`Spec/go_etcd_io/etcd/server/v3/storage/mvcc/store__restore.lean`); restart on a backend with
data is not verified, and crashes are not modeled.

## The counterfactual

The same as etcd#17780's. `restore`'s axiom says nothing about a non-empty bucket, and the
compaction specs (`keepAt`) say which revisions are deleted, not that the persisted state still
determines the revision. So the pre-fix code meets every statement here. **F−.**

## Proposal: `mvcc-restore-from-backend` (existing slug)

The same as for etcd#17780: `restore` on a non-empty backend with `currentRev = max(log.length - 1,
c')`, and the committed-view invariant that every commit, including the batches of
`scheduleCompaction`, persists a state `restore` recovers correctly. If that invariant had been
proved, it would also have settled this report's diagnosis: the mechanism above would be excluded
at the pin, and any remaining decrease would point to hardware or to a component outside the
proof.
