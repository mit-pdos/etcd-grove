# etcd-io/etcd#13697: v3.5.0 with #13348 still resurrects ancient members; restart fails with "member count is unequal"

- URL: https://github.com/etcd-io/etcd/issues/13697. Closed 2022-03-04 by the reporter ("it
  occurred only once and there is no further response"). Label `type/bug`.
- Affected: a patched v3.5.0 (with #13348 and other cherry-picks) in Kubernetes, rolling update of
  3 pods; `strict-reconfig-check: false`. The maintainers asked for a reproduction on official
  v3.5.2 and got none.
- Fix: none. The cause was never diagnosed.

What was observed: the three members disagree on the member list. Two report 3 members, one of them
`unstarted` with node 0's peer URL. The third reports 5 members, two of which are duplicates with
the same peer URL and new IDs. Node 0 keeps restarting. Its bootstrap as a member of an existing
cluster fails in `membership.ValidateClusterAndAssignIDs` (`cluster.go:755-759` at the pin), which
compares the local `--initial-cluster` with the member list fetched from a peer: "member count is
unequal: ems(5) lms(3)". The logs fit node 0's data being wiped and the node re-added under a new
ID while the old ID was still a member (an unstarted re-add plus duplicates). Two members with the
same peer URL should not be possible through the API. `ValidateConfigurationChange` rejects a
duplicate peer URL with `ErrPeerURLexists` at apply time (`cluster.go:340-346` at the pin), whatever
`StrictReconfigCheck` is. `StrictReconfigCheck` only governs `mayAddMember`'s quorum-readiness
check (`server.go:1406`). So the duplicates point to member stores that disagree.

## Classification

**N (undiagnosed, closed by the reporter); if it is #13196's divergence, F− (O-fn); otherwise
O-pkg.** Two candidates:

1. The v2/v3 membership stores diverged as in #13196. The members' answers differ by which store
   they read and on what each store holds. That mechanism is not in the pinned code, which has one
   membership store (`etcd-13196.md`): **F**, counterfactual **F−**, because nothing here
   specifies membership's contents.
2. An operational re-add whose duplicates came from an older version's data, and the strict join
   check then refused node 0. The failing check is in the join bootstrap
   (`bootstrapExistingClusterNoWAL` → `ValidateClusterAndAssignIDs`). It is not translated, nor is
   the code that fetches the remote member list (`GetClusterFromRemotePeers`,
   `etcdserver/cluster_util.go`): **O-pkg/O-fn**. Refusing a member list that disagrees is then the
   intended behavior, and the bug lies wherever the duplicates came from.

Source of verification states: the batch's `verified.txt`. `ValidateClusterAndAssignIDs`,
`bootstrapExistingClusterNoWAL`, `AddMember`, `mayAddMember` and the `RaftCluster` writers are not
translated. `EtcdServer.applyConfChange` is assumed (an axiom, which says nothing about the member
set: `Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__applyConfChange.lean:37-56`).
`RaftCluster.Members` is verified, but its spec returns some list of members
(`RaftCluster__Members.lean:30-34`).

## Proposal

`membership-state-model` (`etcd-13196.md`): every member's cluster and `members` buckets equal
`memOf` of its applied log. It would settle candidate 1. For candidate 2, it would also give
`ValidateClusterAndAssignIDs` a spec that can be stated: on a joining member, the fetched list is
`memOf` of some committed prefix. The thread does not show that a bug exists at all, so this bug
counts toward the proposal only weakly.

None. No `issues/` file: the report is undiagnosed and was closed for lack of a reproduction.
