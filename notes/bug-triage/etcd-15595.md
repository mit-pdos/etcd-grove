# etcd-io/etcd#15595: Etcd panic in robustness tests blackhole failpoint

- URL: https://github.com/etcd-io/etcd/issues/15595 (closed 2023-04-03; label `type/bug`)
- Affected: `main` of March 2023 (raft `eaa6808e1f7a`), only in the robustness tests' `blackhole`
  failpoint, about once in a hundred runs.
- Fix: none in etcd or raft. The cause was the test harness: `pkg/proxy`, an L4 proxy in front of
  each peer port, dropped bytes of the TCP stream (not whole packets), so the receiver's rafthttp
  decoder read a message spliced from two (#15610 "Robustness fix blackhole" changed the test;
  #15704 "Etcd should be resilient to packet manipulation" is the follow-up feature request).
  With peer TLS the panic did not reproduce, and the issue was closed on that basis.

What goes wrong: two followers panic at once in `raftLog.maybeAppend` (`index, 7, is out of range
[1]`). pav-kv's instrumented build (assertions at the sender and the receiver) showed a `MsgApp`
with `Index = 284` and `Entries[0].Index = 290`, while the leader's own assertion when building the
message never fired. So a message that no leader sent was delivered: its batch does not start at
`Index + 1`. `findConflict` returns the batch's first index, `ci - offset` exceeds `len(entries)`,
and `maybeAppend` panics.

## Classification

**N (not a bug in the Go code), secondary A-model (transport integrity).** The message was
corrupted by the test's proxy, which no real network does undetected (TCP checksums; TLS
authenticates the bytes). Raft's verified path is at the pin, and its specs exclude this panic for
every *legitimately sent* message. The premise is `isMessage γ (absMsg …)`
(`Spec/go_etcd_io/raft/v3/raft__Step.lean:446`), from which the ghost protocol gives the batch's
well-formedness `PlogWf` (`Proof/go_etcd_io/raft/v3/Plog.lean:48`). The spliced message breaks
that premise. It is the transport's integrity, assumed and not modeled.

Source of verification states: `/shared/etcd-grove-triage/coord/verified.txt` (at `d606c9cac`).

## The argument (step 4)

1. The observed run, as the spec sees it: a `MsgApp` with `m.Index = 284` and `ents = [e]`,
   where `e.Index = 290`. Then `PlogWf (entryID.mk m.LogTerm m.Index) ents` is false
   (`PlogWf` requires `e.Index = m.Index + 1`, `Plog.lean:48-50`).
2. Premises. `raft.Step.spec` takes the message with `□ isMessage γ (absMsg ty m ents ctx)`
   (`raft__Step.lean:446`, `:663`): the message is in the ghost set of messages some node sent.
   Every sent `MsgApp` is built by `maybeSendAppend` from the leader's log, so its batch is
   `PlogWf`. `stepFollower`'s spec asks for exactly that (`stepFollower.lean:232-233`), and
   `raft.Step`'s proof derives it from `isMessage`. The premise is never discharged for a real
   message: `node.Step`'s caller, `EtcdServer.Process`, and the whole of rafthttp are not
   translated. It is the documented transport assumption ("as a message the transport delivers",
   `RawNode__Step.lean:3-40`). The proxy's splicing violates it, so the outcome falls outside every
   spec. This is not X.
3. The behavior is not a weakness of the specs. For a message that meets the premise, the
   specs have `maybeAppend`'s `Panicf` unreachable (the conflict premise and `PlogWf` together),
   so the protocol-level results hold. The panic is the code's own reaction to input the protocol
   cannot produce.

Even if rafthttp were verified (`verify-rafthttp-handlers`), it would not catch this: the
spliced bytes decode to a valid `Message`. Only an integrity check on the wire (TLS, or a
checksum in the framing), or a receiver that validates the batch, would detect it.

## Proposal: `raft-step-untrusted-msg` (new, optional)

The robustness #15704 asks for, stated as a spec: `raft.Step` on a message that is only
*structurally* checked, with no `isMessage`/`PlogWf` premise for a `MsgApp`, does not panic and
leaves the state unchanged when the batch is malformed:

```lean
-- MsgApp arm, no PlogWf premise:
¬ PlogWf (entryID.mk m.LogTerm' m.Index') ents → s' = s   -- dropped (or rejected), no panic
```

This is false at the pin. Proving it would need the code change the TODO names: validate the
`logSlice` in `handleAppendEntries` (or at `Step`'s entry) and drop an invalid one. With that
change it is a small proof: the `PlogWf` test is decidable, and the valid branch is today's proof.
Cost: small for the `MsgApp` arm. Going further, it is a larger "Byzantine-shaped input" spec for
every message type, which is outside what the protocol results can say (a spliced message with a
well-formed batch but wrong terms would still break safety). Value is low while TLS is
the deployment answer. No `issues/` file: not a bug under raft's documented contract.
