# etcd-io/etcd#17502: Fouled authentication when using Concurrency/Election by multiple clients

- URL: https://github.com/etcd-io/etcd/issues/17502 (closed 2025-12-19 by the stale bot; labels
  `type/bug`, `help wanted`, `stale`). Not fixed. A maintainer (ahrtr) calls it "a design issue"
  and prefers documenting it to a fix. PR #17532 (merged) adds an election test with auth over the Go
  client. PR #22270 (documentation only, closed unmerged) and PR #22560 (open, renews tokens in
  `v3client`; it targets #17623) are related.
- Affected: 3.4.19 through 3.5.12, and `main`. Present at the etcd pin `107edf7e4`.
- Reproduction (the reporter's Docker setup, basic auth): user1 holds an election and a second
  user1 `Campaign` is blocked; user2 then calls `Campaign` (gRPC `v3election`) and gets
  `permission denied`.

What goes wrong (diagnosed by the maintainer and checked at the pin): the `v3election` server runs
`concurrency.Election.Campaign` on an in-process client, `v3client.New`
(`server/etcdserver/api/v3client/v3client.go:30`), whose watcher is
`clientv3.NewWatchFromWatchClient(adapter.WatchServerToWatchClient(...))`. The Go client puts
watchers on one gRPC watch stream per `streamKeyFromCtx(ctx)` (`client/v3/watch.go:1090`),
keyed on the *outgoing* metadata. A server handler's context carries the caller's token in its
*incoming* metadata and has no outgoing metadata, so every user's internal watch gets the key
`""` and shares one stream. That stream's context is the first watcher's
(`newWatcherGRPCStream`, `watch.go:281`, `valCtx{inctx}`). The adapter's pipe passes it as the
server stream's context (`adapter/chan_stream.go:142-154`). On the server side,
`serverWatchStream.isWatchPermitted` (`v3rpc/watch.go:237`) authorizes every watch on the stream
with `AuthInfoFromCtx(sws.gRPCStream.Context())`, that is, with user1's token. user2's watch is
therefore checked as user1. Over a real network each client has its own connection and its own
stream context, and the two keys (outgoing metadata on the client, incoming on the server)
coincide.

## Classification

**O-path (secondary C-scope).** The faulty composition runs through code nothing here translates:
`v3election` (`electionServer.Campaign`), `v3client.New` and the `grpcproxy/adapter` pipe. The
functions at either end are verified (sorry-free): the client's `watcher.Watch`/`streamKeyFromCtx`/
`newWatcherGRPCStream` (unit W-C) and the server's `isWatchPermitted`/`recvLoop` (W-S). The
verified client results assume a stub on a gRPC connection (`watchClient.Watch.spec`,
`Spec/go_etcd_io/etcd/api/v3/etcdserverpb/watchClient__Watch.lean`: `watchStubAt`, `grpcConn`).
The in-process path replaces that stub with the adapter. Even with that harness verified, no spec
here could see the bug: identity is not in any statement (C-scope).

## Why the verified parts do not exclude it (step 3)

- `streamKeyFromCtx.spec` returns *some* string (`Spec/go_etcd_io/etcd/client/v3/streamKeyFromCtx.lean`:
  postcondition `True`). Which watchers share a stream is not specified.
- `isWatchPermitted.spec` concludes only `applyErrIs err`: some error from the auth store, or
  `nil`. Its prose says "the auth info of the stream's context", but the stream context's
  identity is not a term in the spec. `AuthInfoFromCtx.spec` returns `authInfoRO a ∗ authErrIs
  err`, "an auth info": which user is not stated.
- `Results.lean` (v3rpc) says nothing about authorization. The watch results (`watch_server`) are
  about the events a watcher receives.

So even the verified client and server pieces would admit a watch authorized as another user. The
deciding fact is still the untranslated composition, because over the verified harness (one
connection per client) the mismatch between outgoing and incoming metadata cannot happen.

## Proposal: `inproc-client-auth-identity`

Verify the in-process server-side client: `v3client.New`, the `adapter` watch, KV and lease
pipes, and `v3election`/`v3lock` over the verified `concurrency` specs (about 350 Go lines:
`election.go` 108, `lock.go` 37, `v3client.go` 31, `chan_stream.go` 131, `watch_client_adapter.go`
40). Give the auth specs an identity so that the property can be stated:

- `AuthInfoFromCtx.spec`: the result is `authOf ctx` (a ghost function of the context's incoming
  token at the call; `none` without one), and `isWatchPermitted.spec` returns `nil` iff
  `permitted (authOf (stream ctx)) range`;
- the property: every internal request made on behalf of an RPC with context `c` (Txn, Range and
  each watch create) is authorized as `authOf c`. For a watch, the server stream's context, which
  the adapter takes from the client stream, must have `authOf = authOf c`. That makes the client's
  stream key a premise: watchers share a stream only if they have the same `authOf`.

The pin fails it: `streamKeyFromCtx` keys on the outgoing metadata, which no `v3election` context
has. A fix is to key on the incoming metadata too, or to give each internal request an outgoing
copy of the caller's token. Cost: medium. The adapter and `v3client` are small, and `v3election`
and `v3lock` are thin wrappers over proved specs. Most of the work is an auth model with users
(today's auth specs are "some auth info"). The same proposal covers etcd-io/etcd#17623 (the
caller's token expiring during the wait), where it needs a token-lifetime model in addition.

## Findings

- New: `issues/etcd-inproc-watch-shared-auth.md` (present at the pin; upstream known, #17502).
  No reproduction of ours: the reporter's Docker reproduction and the maintainer's analysis are
  linked there.
- No bug in this repository's specs. The auth specs are deliberately weak (identity abstracted).
