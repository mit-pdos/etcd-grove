# etcd-io/etcd#19557: [release-3.5] Learner promotion isn't persisted to v3store (bbolt)

- URL: https://github.com/etcd-io/etcd/issues/19557 (closed 2025-03-28; labels `type/bug`,
  `release/v3.5`, `release/v3.6`, `priority/critical-urgent`)
- Affected: v3.5.1 to v3.5.19. The bug was introduced on `release-3.5` by #13348, the fix for
  #13196. It shows on the upgrade to v3.6: a promoted member becomes a learner again, or, with two
  or more promoted learners, bootstrap fails with "too many learner members in cluster".
- Fix: PR #19563 (`release-3.5`, merge `2b9598b29`, v3.5.20) makes the promotion write the backend,
  and #19586/#19606 add an automatic sync of `IsLearner` from v2 to v3. #19636 (`release-3.6`) syncs
  at bootstrap. #19634 (`main`) adds an e2e upgrade test only. Follow-up: #20793 (the same wrong
  data carried by a snapshot).

What goes wrong: on `release-3.5`, `RaftCluster.PromoteMember` saves the promoted member to the
backend through `unsafeSaveMemberToBackend` (`membership/store.go:57-59` at `1810af31`). Since
#13348 that function returns `errMemberAlreadyExist` when the key exists, and for a promotion the
key always exists. The caller ignores the error. So the `members` bucket keeps `isLearner: true`,
while the v2 store, membership's source of truth in 3.5, has the promotion. v3.6 reads the members
from bbolt.

## Classification

**F (release-branch code; `main` never had it); counterfactual F−, gap O-fn.** The decisive fact:
at the etcd pin `107edf7e4`, `RaftCluster.PromoteMember` (`cluster.go:498-533`) sets
`IsLearner = false` on the cluster's member and calls `be.MustSaveMemberToBackend(m)`. That is a
plain `UnsafePut` of the marshalled member under `LockInsideApply` (`schema/membership.go:50-61`),
with no existence check. Membership has one store at the pin (v2 membership writes removed:
`fdedec1ed`, an ancestor). The existence check of #13348 was never on `main`.

Source of verification states: the batch's `verified.txt`.

## The counterfactual

Take the 3.5 behavior, where the promotion updates the in-memory member but not the bucket. It
contradicts no existing statement. The `applyConfChange` axiom (`EtcdServer__applyConfChange.lean:37-56`)
fixes only where backend writes happen (one critical section of the batch lock, or none on a failed
validation, in which case the consistent index is stored). It does not say what is written. "Writes
less than it should" fits the axiom's post. No predicate here describes the `members` bucket. The
key-value apply model (`applyEntries_kv`) does not include membership. So the buggy code would also
"verify", and the gap is unspecified code (**O-fn**), not a weak spec.

What a spec would have caught: the 3.5 code returned an error from the backend write and dropped
it, so the bucket and the in-memory cluster disagree after the apply. Under
`membership-state-model`'s invariant (both equal `memOf (applied i)`), the proof of
`PromoteMember` would fail at that write.

## Proposal: `membership-state-model`

As in `etcd-13196.md`: a pure `memOf` of the applied entries (members with `isLearner` and
attributes, removed ids). An apply-thread invariant says the cluster's in-memory state and the
`members`/`members_removed` buckets equal it. It is proved by replacing the `applyConfChange` axiom
(`verify-apply-conf-change`) and proving the `RaftCluster` writers and the schema backend. Then
`ValidateMaxLearnerConfig` at bootstrap gets the spec "the number of learners of
`memOf (applied i)`", and the 3.6 symptom becomes a statement about the log. Cost: medium to large
(about 500 Go lines). This bug is the cheapest of the group to catch: the one writer
(`PromoteMember`) plus the backend put.
