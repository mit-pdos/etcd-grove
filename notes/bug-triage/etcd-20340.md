# etcd-io/etcd#20340: etcd fails to start, with panic on 'failed to nodeToMember'

- URL: https://github.com/etcd-io/etcd/issues/20340 (closed 2025-07-24; label `type/bug`)
- Affected: 3.6.0–3.6.2. Found in Talos tests: restore from a snapshot, learners added and
  promoted, members removed and re-added, then all members restarted.
- Fix: PR #20391 on `main` (commit `0e2a4212e`, merge `c515c6acc`, 2025-07-24), backported to
  3.6 by #20387 (3.6.3).

What goes wrong (ahrtr's root cause): `RaftCluster.PromoteMember`
(`server/etcdserver/api/membership/cluster.go`) updated the **v2 store** when the member was in
the **v3** in-memory map: `if _, ok := c.members[id]; ok { m := *(c.members[id]); …;
mustUpdateMemberInStore(c.v2store, &m) }`. While replaying the WAL at bootstrap
(`shouldApplyV3 == false`, the v3 backend already ahead), `c.members` reflects the v3 state,
not the v2 store being rebuilt. A promotion of a member that the v2 store does not (or no longer)
hold writes a `raftAttributes`-less or stale node into v2. The next v2 snapshot then carries a
member without `raftAttributes`, and the next restart's `membersFromStore` → `nodeToMember`
fails and `lg.Panic("failed to nodeToMember")` (`cluster.go:729` at the pin). The fix looks up the
member in the v2 store (`membersFromStore`) when updating the v2 store.

## Classification

**F (fixed before the verified code); counterfactual F−, gap O-fn (with A-axiom).** `c515c6acc`
is an ancestor of the pin `107edf7e4` (`git merge-base --is-ancestor`: yes). By the pin `main` has
gone further: `PromoteMember` (`cluster.go:498-532`) no longer writes the v2 store at all (with
`shouldApplyV3 == false` it logs "ignore already promoted member"). The membership methods are
not translated (`verified.txt`: `RaftCluster.PromoteMember`, `Recover`,
`ValidateConfigurationChange` "not translated"; `membership` 6/71 functions verified). They are
reached from the verified apply loop only through `EtcdServer.applyConfChange`, an assumed
trust-boundary spec (`Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__applyConfChange.lean`)
that promises a return for any change and says nothing about either store. So the existing
proofs would have gone through on the buggy code.

Source of verification states: `/shared/etcd-grove-triage/coord/verified.txt`.

## The counterfactual (step 5)

On the pre-fix code the two stores diverge: after replaying a promotion the v2 store's member set
is not the fold of the applied log's membership entries. Nothing proved here mentions the v2
store or `c.members`: `applyConfChange`'s axiom has no state on either. So nothing would break,
and the result is F−. Under `membership-state-model` (`etcd-13196.md`) the invariant is "every
membership view (in-memory, the `members` bucket, and while it exists the v2 store) equals
`memOf (applied i)`". The pre-fix `PromoteMember` breaks it at the replay step whose
`shouldApplyV3 = false` branch writes `c.members[id]` (a v3-ahead value) into v2. That makes the
bug F+ under the proposal, provided the replay (`shouldApplyV3 = false`) path is in scope, i.e.
the restart half that needs `crash-restart-model` or at least a model of bootstrap's replay
from the WAL.

## Proposal: `membership-state-model` (existing), with `verify-apply-conf-change`

Replace the `applyConfChange` axiom (`verify-apply-conf-change`), and prove the `RaftCluster`
writers against a pure `memOf`, in both modes of `ShouldApplyV3`. For the `false` mode (replay
behind the backend), state that the writers leave the v3 views untouched and bring every other
view to `memOf (applied i)`. Cost as in `etcd-13196.md` (medium to large, about 500 Go lines),
plus the bootstrap replay for the restart half. At the pin the v2 writes are gone, so the proof
there is about the in-memory map and the `members` bucket only.

## Findings

None new: fixed at the pin (and the v2 write path removed). No bug in this repository's specs.
