# etcd-io/etcd#13989: Revision in response header might not reflect data in the body

- URL: https://github.com/etcd-io/etcd/issues/13989 (closed 2025-08-07 by the stale bot; labels
  `type/bug`, `stale`, `stage/tracked`, `release/v3.6`). No fix. PR #14026 (member-list header
  revision) is cross-referenced but is a different change, and it was closed.
- Affected: `main` (3.6 at the time) and the pin. `LeaseLeases` is unchanged
  (`server/etcdserver/v3_server.go:737-749` at `107edf7e4`).

The report: `LeaseLeases` reads `s.lessor.Leases()` and builds the response header
(`s.newHeader()`, which reads `s.KV().Rev()`) afterwards, with no synchronization. So the header's
revision is "later" than the body. The reporter extends this to "any other function using
newHeader". A maintainer replied that moving `newHeader` first only reverses the problem. Nobody
proposed a fix.

## Classification

**N (secondary O-fn).** The decisive fact is that the lessor's state has no revision. Granting or
revoking a lease does not advance the KV revision (`applierV3backend.LeaseGrant`/`LeaseRevoke`
write no KV entries), so "the latest revision among the returned leases" is undefined. A lease
response's header revision can only mean "the KV revision at some point during the call". That
is what the code does, and the verified `newHeader` spec says so. For the responses where a
revision does describe the body (Range, Put, DeleteRange, Txn), the header revision is the
transaction's own revision, and the specs prove it. `LeaseLeases` itself is not translated (only
its interface method signature is, `Code/go_etcd_io/etcd/server/v3/etcdserver.lean:6612`), which
is the O-fn part.

## The argument

- `newHeader.spec` returns `Revision' = log.length - 1` for a log with `mvcc.idxCert E.γ.idx log`,
  i.e. the store's revision at the moment of the read. Nothing relates it to state read earlier in
  the same handler, and nothing could for leases: the lessor's map is not indexed by revision.
- `header.fill` keeps a non-zero revision that the handler set (`hdrRevOut`: `r ≠ 0 → r' = r`).
  KV handlers set it from the mvcc transaction (`asembleRangeResponse`: `resp.Header.Revision =
  rr.Rev`). Only a zero revision is replaced by the current `rev()`. So for KV responses the
  "header vs body" mismatch the reporter generalizes to does not arise, and the specs state it.
- Maintenance responses (`Status`, `Hash`, ...) get the revision current at fill time. Those
  bodies are not KV data either.

The behavior is therefore as intended, and the issue's expectation is not expressible for leases.
Hence N, not C-obs. The verified `newHeader` spec documents the actual contract: a revision current
during the call.

## Proposal

None. The closest meaningful property ("a non-KV response's header revision lies between the
store's revision at the call and at its return") already follows from `newHeader.spec`'s
`idxCert` and the store's monotone revision. Stating it for `LeaseLeases` would need translating
`LeaseLeases`/`lessor.Leases` (small), and it would only document what is already true.
