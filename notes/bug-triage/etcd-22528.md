# etcd-io/etcd#22528: New joiner stuck in "etcdserver: too many requests" in an idle cluster

- URL: https://github.com/etcd-io/etcd/issues/22528 (open; label `type/bug`; filed 2026-10-05,
  reported on v3.7.1, also seen on v3.6.1 per the linked kubeblocks issue). Duplicate of
  etcd-io/etcd#22516 (open, "member stays unpublished after it catches up from a snapshot and no
  entry follows"); the tight retry loop is #22526 (open).
- Fix: none merged. Open PRs #22529 and #22510 (both add `s.setAppliedIndex(ep.appliedi)` and
  `s.setTerm(ep.appliedt)` at the end of `applySnapshot`), #22527 (`publishV3` waits for apply
  before retrying).

What goes wrong: a fresh member catches up from a leader snapshot (index 11476). The raft loop's
`updateCommittedIndex` raises `s.committedIndex` to the snapshot's index. `applySnapshot` sets
`ep.appliedi` to it but never calls `s.setAppliedIndex`, whose only callers are in `apply` (one per
applied entry). In an idle cluster no entry follows, so `s.appliedIndex` stays 0.
`processInternalRaftRequestOnce` then refuses every proposal with `ErrTooManyRequests`, because
`exceedsRequestLimit(0, 11476, …)` holds (gap > 5000). That includes the member's own `publishV3`,
which retries in a tight loop and never closes `readych`, so the client API never comes up. One
write anywhere in the cluster unsticks it.

## Classification

**A-pre (secondary C-live).** The buggy code is in the pin and is verified there, but only for
batches without a snapshot. `applyAll`'s and `applySnapshot`'s specs take `ap.snapshot = nil`
(`Spec/.../etcdserver/EtcdServer__applyAll.lean:51`, `EtcdServer__applySnapshot.lean:31`), carried
from the raft loop's payload invariant `rnApP` (`⌜ap.snapshot' = null⌝`,
`Proof/.../etcdserver/InvRaftNode.lean:679-683`). A joiner catching up by snapshot violates that
premise. The proof's existing loop invariant would have excluded the bug once the premise is
dropped: `applyAll`'s postcondition ties the server's atomic applied index to `ep.appliedi`
(`srvAppliedOwn γr ai'` with `epAppliedIAddr ep ↦ ai'`). The hang itself is liveness, which no
spec here states.

The bug is present at the pin and reproduced there by a Go test (below). New finding:
`issues/etcd-snapshot-applied-index-stale.md`.

Source of verification states: `/shared/etcd-grove-triage/coord/verified.txt`
(`etc/verified-code.py` at `d606c9cac`).

## The argument (step 4)

1. **Observed behavior, in the spec's terms.** The apply thread receives a payload whose
   `snapshot` is non-nil, with index 11476. Afterwards `ep.appliedi = 11476`, the atomic
   `s.appliedIndex = 0` and `s.committedIndex = 11476`. Every later
   `processInternalRaftRequestOnce` returns `ErrTooManyRequests`.
2. **Premises.** `applyAll.spec` requires `taSnapshotAddr ap ↦□ (null : Loc)` (`:51`), and
   `applySnapshot.spec` exists only for that case. `raftNode.start`'s loop promises it for every
   payload (`rnApP`), because raft's own specs keep `Ready` free of a pending snapshot (STATUS:
   "Snapshots at the public API (stage S)": carrying a snapshot to the receiver, `MsgSnap` at
   `RawNode.Step` and a pending snapshot in `Ready`/`Advance` are left). A member that joins with
   an empty data dir and is behind the leader's compaction gets `MsgSnap` and a `Ready` with a
   snapshot, so it violates the premise. **A-pre.** The premise is not a documentation issue: raft
   documents snapshots in `Ready`. It is a scope limit of the verification, recorded in STATUS.
3. **Assumptions.** None is involved: the WAL, transport and snapshotter contracts play no part in
   the stale index.
4. **Would the spec exclude it with the premise dropped?** Yes, on safety grounds. The invariant
   `srvAppliedInv` (`InvRequest.lean:1800`) holds the atomic `s.appliedIndex` at `v` together with
   half of the ghost applied index `γr.applied` at `v`. `srvAppliedOwn γr v` (`:1815`) is the
   apply thread's other half. `applyAll`'s pre has `epAppliedIAddr ep ↦ ai ∗ srvAppliedOwn γr ai`,
   and its post has `epAppliedIAddr ep ↦ ai' ∗ srvAppliedOwn γr ai'` (`:55`, `:64`), so at every
   batch boundary `s.appliedIndex = ep.appliedi`. Generalize `applyAll`'s spec to a snapshot batch
   with this shape kept (`ai'` = the snapshot index when it is larger). The buggy `applySnapshot`
   cannot establish the post: it moves `ep.appliedi` to 11476 and leaves the ghost and the atomic
   at 0. That is where the proof breaks, which makes this bug **F+-like within the future
   `server-apply-snapshot` scope**: the existing invariant catches it, and only the premise lets
   it through. A generalization that weakened the post to `srvAppliedOwn γr ai` (the old value)
   would admit it. The proposal must keep the equality.

   With the premise kept, the stale index is still safe for what the specs state. A low applied
   index makes `exceedsLimit` refuse more, and refusal is an allowed outcome of
   `processInternalRaftRequestOnce.spec` (the `err ≠ nil` disjunct, `applyErrIs err`). Reads wait
   on `applyWait`, which `applyAll` triggers at `ep.appliedi`. What the user sees, a publish that
   never succeeds, is **C-live**: `publishV3` is an axiom whose loop may run forever under any
   partial-correctness spec, and its tight retry rate (#22526) is C-perf.

## Proposal: `server-apply-snapshot` (existing slug), keeping the applied-index equality

As the slug already says (`etcd-17084.md`, `etcd-20271.md`, …): drop `rnApP`'s
`ap.snapshot = null`, prove `applySnapshot`'s non-empty branch (it depends on
`mvcc-restore-from-backend` and `raft-pending-snapshot-ready`), and keep `applyAll`'s post in the
form

```lean
{{ … ∗ epAppliedIAddr ep ↦ ai ∗ srvAppliedOwn γr ai ∗ taSnapshotAddr ap ↦□ sp ∗ snapOpt sp o … }}
  s.applyAll(ep, ap)
{{ ∃ ai' …, epAppliedIAddr ep ↦ ai' ∗ srvAppliedOwn γr ai' ∗ appliedLogAt γr ai' x'.log ∗
    ⌜uint.Z ai' = max (max (uint.Z ai) (o.map (·.index)).getD 0) lastEntryIndex⌝ }}
```

so that the snapshot branch has to call `setAppliedIndex(snapshotIndex)`. It needs the KV log at
the snapshot index for `appliedLogAt`, which is where `mvcc-restore-from-backend` comes in. This
bug adds a concrete obligation to the slug and costs nothing extra: the fixed code (PR #22510)
meets it directly. The liveness part ("publish eventually succeeds in an idle cluster") is outside
Iris-style partial correctness. Its closest safety statement is the equality above: at every batch
boundary `committedIndex − appliedIndex` is bounded by the entries not yet applied, and is 0 when
none is pending. Cost: large (the slug's cost), with the equality itself small once the branch is
proved.
