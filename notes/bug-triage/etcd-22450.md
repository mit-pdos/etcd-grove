# etcd-io/etcd#22450: Leader's apply backlog does not recover after a transient apply slowdown

- URL: https://github.com/etcd-io/etcd/issues/22450 (open; label `type/bug`). Reported on v3.5.21
  and v3.6.6 (large Kubernetes clusters). The trigger is NUMA memory pressure: the kernel reclaims
  bbolt's mmap, and the resulting major faults slow compaction under the `batchTx` lock.
- Fix: none merged. Open PRs by the reporter: #22495 "pkg/wait: avoid full map scan in
  applyWait.Trigger" (a min-heap of deadlines) and #22496 "etcdserver: decouple queued apply jobs
  from raft log lifetime" (memory). With both, the reporter's runs recover (gap back to 0, RSS a
  quarter).

What goes wrong: after a transient slowdown, the commit-apply gap grows. Linearizable reads keep
registering `applyWait` waiters for future indices (`timeList.Wait`). Each apply batch ends in
`applyAll`'s `s.applyWait.Trigger(ep.appliedi)`, and `timeList.Trigger` scans the whole waiter
map under its lock (`pkg/wait/wait_time.go`), not only the expired deadlines. The more the apply
falls behind, the more waiters there are and the slower each batch, which feeds back. Separately,
each apply job queued in the FIFO scheduler holds its `toApply` (the batch's entries), so the
queue's memory grows with the backlog until OOM. The gap above 5000 makes the member refuse
requests (`exceedsRequestLimit`), working as designed.

## Classification

**C-perf (secondary O-fn, A-model).** The quadratic feedback is in verified code present at the
pin: `timeList.Trigger`'s full scan (`pkg/wait/wait_time.go:58-67` at `107edf7e4`) and its caller
`EtcdServer.applyAll` (`server.go:984`) are verified. Their specs are partial correctness and say
nothing about cost. `wait.timeList.Trigger.spec` is
`{{ isTimeList tl P ∗ □ P d }} tl.Trigger(d) {{ True }}`
(`Spec/go_etcd_io/etcd/pkg/v3/wait/timeList__Trigger.lean`), so an O(waiters) scan is as correct
as an O(expired) one. The memory half runs through the FIFO scheduler, which is not verified
(`schedule.NewFIFOScheduler` assumed, `fifo.Schedule` not translated): O-fn. The trigger (page
reclaim, major faults) is outside the model (A-model: memory and timing). The report's diagnosis
is the reporter's; the maintainers have not confirmed it. The `Trigger` cost is a fact of the
code, reproduced at the pin (below).

New finding: `issues/etcd-wait-trigger-full-scan.md` (the verified half). Source of verification
states: `/shared/etcd-grove-triage/coord/verified.txt`.

## The argument (step 4)

The observed behavior is a rate: per-batch `Trigger` time rises from ~µs to ~1.2 ms, and the gap
grows without bound. No premise is violated: the read path and the apply thread run as etcd runs
them, and nothing assumed about `pkg/wait` is false. Every spec involved allows it. `Trigger`'s
post is `True` beyond the waiters it closes (`isTimeList`'s invariant). `applyAll`'s post
constrains state, not time. `processInternalRaftRequestOnce` may refuse. What the user expected,
"the backlog drains once the transient ends", is a throughput or liveness property, and Perennial's
Iris logic has no cost or time-credit reasoning in the Lean port. **C-perf.**

The closest property that is a safety statement does not catch this. The heap fix (#22495)
satisfies the same `timeList` spec as the map scan, so the existing spec is a regression guard for
the fix's correctness, not for its cost.

## Proposal: `apply-path-cost-bounds` (new)

- **What can be done now (small):** verify #22495's heap-based `timeList` against the existing
  `wait.timeList.{Wait,Trigger}.spec` once it is merged (the spec carries over unchanged; the heap
  needs a pure lemma that popping deadlines `≤ d` removes exactly the map's entries `≤ d`). This
  guards correctness, not cost.
- **What would catch the class (large, needs Perennial support):** a cost model, i.e. time credits
  per heap/map operation in Goose's semantics, and a spec
  `{{ isTimeList tl P ∗ £cost (k · (expired + 1)) }} tl.Trigger(d) {{ True }}`, with `expired` the
  number of deadlines `≤ d`. Then `applyAll`'s per-batch cost would be bounded by the batch and its
  released waiters, not by all pending reads. Perennial's Lean port has no time credits for Go
  steps: a Perennial proposal, not a local axiom (CLAUDE.md, "Changes to Perennial"). For the
  memory half, translate `pkg/schedule`'s FIFO (113 lines) and state a space bound on the queued
  jobs. That is likewise a resource property beyond partial correctness, so it would be stated as
  "a queued job holds only its index range" (a safety restatement of #22496's design).

## Findings

- New: `issues/etcd-wait-trigger-full-scan.md`, with
  `issues/etcd-wait-trigger-full-scan/trigger_scan_test.go`. It passes at the pin: a `Trigger`
  that releases nothing costs ~1.5 µs with 100 pending waiters and ~1.4 ms with 100 000, the
  report's ~1.2 ms.
- No bug in this repository's specs.
