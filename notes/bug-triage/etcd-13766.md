# etcd-io/etcd#13766: Inconsistent revision and data occurs

- URL: https://github.com/etcd-io/etcd/issues/13766 (closed 2022-04-07; labels `type/bug`,
  `priority/important-soon`).
- Affected: v3.5.0–v3.5.2 (the reporter ran 3.5.1; others hit it on 3.5.2). The trigger was a
  crash (OOM, SIGKILL, a full disk) under load.
- Fix: PR #13854, "Fix the data inconsistency issue by moving the SetConsistentIndex into the
  transaction lock" (merge `c83b1ad9b`, 2022-04-07). It was released in 3.5.3. The `LockWithoutHook`
  of that PR later became `LockInsideApply`/`LockOutsideApply`. The earlier attempt, #13844, was
  closed. The thread also considered #13505 (a bbolt page reference), but ruled it out as the cause.

What goes wrong (pre-fix code): `EtcdServer.applyEntryNormal` (`server/etcdserver/server.go:1799`
at `c83b1ad9b^1`) called `s.consistIndex.SetConsistentIndex(e.Index, e.Term)` *before* applying the
entry, outside the backend's batch-transaction lock. The applier then wrote the entry's effects in
its own critical section. A backend commit (the periodic one, or one at `Unlock` past the batch
limit) could run in between. Its pre-commit hook (`UnsafeSave`) then persisted consistent index `i`
without entry `i`'s writes. If the process crashed before the next commit, the restart replayed raft
only from `i + 1`, so entry `i` was lost on that member. From then on the members' revisions and
data diverged (`revision` lower on one member by ~700000, with the same raft indices).

## Classification

**F+ (fixed before the verified code; the existing specs would have excluded the buggy version).**
The fix `c83b1ad9b` is an ancestor of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`:
yes). At the pin, the index of an entry with writes is set only by the post-lock hook
(`getTxPostLockInsideApplyHook`, `server.go:2448-2455`) under the batch lock. Outside the lock it is
set only for an entry that has already been processed (`server.go:1947`, `2013`). The apply-thread
protocol in `Proof/go_etcd_io/etcd/server/v3/etcdserver/InvApply.lean` was designed against this
bug (`notes/decisions.md`, "The consistent index and the apply thread", which cites #13766). The
pre-fix `SetConsistentIndex` cannot be justified by any step of the protocol, so the proof of
`applyEntryNormal` fails at that call. No crash model is needed: the property is stated of every
commit.

Source of verification states: the proof files and `Link.lean` (`verified.txt` was not produced;
no `lake build` in this batch).

## The counterfactual (step 5)

The protocol's ghost state is `(k, p, eff, pending)` (`InvApply.lean:73-77`). Its invariant
`consInv` (`:128`) has, out of flight, `stOk`: `eff ≤ ci ≤ p` (`:102-103`). A commit, holding the
lock's token `pend`, saves `ci` and gets `commitOk s m`: `eff ≤ m ≤ p` (`:466-468`,
`commit_save_au` `:472`). "No processed-but-unsaved writes below `m`, no saved index above
what was processed" is exactly the negation of #13766's state.

In the proof, the logically atomic update of `ciIdx` to a new `i` has two justifications:

- `hook_set_au` (`:158`) needs `token γ.pend`, which only the holder of the batch lock has. It
  enters the in-flight state (`pending = true`), which a commit cannot observe, because the commit
  needs the same token;
- `ci_advance_au` (`:416`) needs `pending = false` and `i ≤ p`, so the entry must already be
  processed (`skip_done`/`writes_done` set `p := i`).

Pre-fix, `SetConsistentIndex(e.Index)` runs outside the lock with `p = e.Index - 1` (the entry is
not processed yet). Neither lemma applies, and setting `k := i > p` breaks `stOk`, which `consInv`
requires out of flight (`flightInv`, `:114-118`). So `applyEntryNormal`'s proof (which uses
`ci_advance_au` only after `skip_done`, `EtcdServer__applyEntryNormal.lean:76,401,505`) would break
at that call. If the invariant were weakened to allow it, `commit_save_au` would fail instead: a
commit in that window persists `m = i > p`. **F+.**

What the F+ rests on. The applier keeps an entry's writes in one critical section: that is
`apply.Apply`'s contract, proved, except `applyConfChange`, which is assumed. The hook contract of
the backend's constructor is a premise (`isBackend`). Crashes are not modeled. The result says what
every commit persists, which is what a crash exposes. Restart (`NewServer` replaying from the saved
index) is not verified.

## Proposal

None needed for this bug (F+). The same class is still open where an entry's writes span several
critical sections: `issues/etcd-apply-lease-checkpoint-sections.md` (present at the pin; the
proof sidesteps it by a premise of the `LeaseCheckpoint` triple, at most one checkpoint per
request). Discharging that premise, i.e. fixing or proving `lessor.Checkpoint` over one critical
section, closes the class. That issue is the existing record. No new slug.
