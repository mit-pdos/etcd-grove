# etcd-io/etcd#20418: Stale reads caused by process pausing

- URL: https://github.com/etcd-io/etcd/issues/20418 (filed 2025-07-29, closed 2026-03-04; labels
  `type/bug`, `priority/critical-urgent`, `area/robustness-testing`, backports to v3.4/3.5/3.6).
  Found by Antithesis robustness runs on `main` (container pause, slowed partitions, network
  clogging).
- Observed: a linearizable `Range` started after a `Txn` had completed (committed at raft index 11)
  got read index 10 and missed the write. Debug logs show the read loop's
  "waiting for ReadIndex response took too long, retrying" just before it, at a leader that had
  been paused.
- Fix: etcd-io/etcd#21399 (merge `5944c74e3`, 2026-03-01), "Don't reuse same ReadIndex in
  retries": every resend in `requestCurrentIndex` takes a fresh id, and a `ReadState` of any of the
  call's ids is accepted. Root-caused in etcd-io/raft#392, whose raft-side fix is etcd-io/raft#397
  (`eed49d45e`, in raft v3.7). An earlier guess, a race on `select` with the leader-change
  notifier (`ad284ef32`), did not fix it.
- Same bug as [raft-392](raft-392.md): that report has the full analysis. In short: before #397 a
  raft leader's `readOnly` queued requests by context and released every request queued before a
  context once a quorum acked that context. etcd resent `ReadIndex` with the *same* context on its
  500 ms retry timer. A paused, stale leader could therefore receive late acks for the first copy of
  a context and release a later request `B`, queued after the resend, at a stale commit index.

## Classification

**F (fixed before the verified code); counterfactual F+ (etcd half), F− with A-pre/C-scope (raft
half), as in [raft-392](raft-392.md).** Both fixes are ancestors of the pins (`5944c74e3` ⊑ etcd
`107edf7e4`, `eed49d45e` ⊑ raft `509271dac`). The decisive fact for etcd's code, the subject of this
issue: the pre-#21399 read loop cannot be verified against the current specs. A resend with the same
id needs a second `rdFresh γ (beBytes id)` (`Read.sendReadIndex.spec`'s premise,
`Spec/go_etcd_io/etcd/server/v3/etcdserver/read/Read__sendReadIndex.lean:36`). The first deposit
gave that token to raft's invariant for good, so the proof of `requestCurrentIndex` breaks at the
retry branch's call to `Read.wp_sendReadIndex`.

## The counterfactual (step 5)

As in [raft-392](raft-392.md), "The counterfactual":

- **etcd: F+.** One `rdFresh` per minted id (`srvRdFresh`, `InvRequest.lean:435`; minted by
  `NextRequestID`, `srvRdFreshInv`, `InvRequest.lean:540`). The pinned loop mints a new id on both
  resend paths (`read.go:197-199`, `211-213`) and accepts a read state of any id in `requestIDs`,
  which is what the proof needs.
- **raft: F−.** The pre-#397 queue-by-context is plausibly safe under raft's premise that a context
  is deposited once (`rdFresh`, `Spec/go_etcd_io/raft/v3/RawNode__ReadIndex.lean:73`,
  `node__ReadIndex.lean:58`). Under that premise the old raft would meet its API specs, and the bug
  needs a client that violates the premise. The premise is stronger than v3.7's documented
  `ReadIndex` contract (`node.go:218-223` does not forbid reusing `rctx`).

The guarantee the robustness test checks, a read started after a write completed sees it, is
`read_notify` (`read/Results.lean`): `LinearizableReadNotify` returns `nil` only once the applied
index reached an index at least the committed index the caller knew of (`committedAtLeast γr c`).

## Proposal

`readindex-ctx-reuse` (from [raft-392](raft-392.md)): drop `rdFresh` from raft's read-index specs, so
the guarantee holds per first deposit of a context even when a client reuses it. Small to medium,
ghost layer only. The etcd half needs nothing: it is F+.
