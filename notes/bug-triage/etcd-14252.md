# etcd-io/etcd#14252: panic due to race between wal rotation and snapshot

- URL: https://github.com/etcd-io/etcd/issues/14252 (closed as stale 2025-06-24; labels
  `type/bug`, `help wanted`, `release/v3.5`)
- Affected: 3.5.4 on Windows (Windows 10, Windows Server 2019). Restart fails with
  `failed to open WAL: wal: file not found` (`readWAL` → `restartNode`). Reproduced by a commenter:
  a single node with `max-wals: 5` and 200 KB writes, after 3000–4000 transactions.
- Fix: none. PR #14293 ("fileutil: fixed work with wal files lock on the windows") was closed
  unmerged. #14300 only improved the error message.

What goes wrong (ahrtr's diagnosis, confirmed by the reporter): the purge goroutine
(`fileutil.purgeFile`, `client/pkg/fileutil/purge.go`) may delete a WAL file only if
`TryLockFile` succeeds. The WAL keeps every file it still needs locked, and releases those locks
only up to a saved snapshot (`storage.Release` → `w.ReleaseLockTo`,
`server/storage/storage.go:78`). On Windows, `lockFile` (`client/pkg/fileutil/lock_windows.go:84`)
returns `nil` when `LockFileEx` fails with `ERROR_LOCK_VIOLATION`:

```go
} else if err.Error() == errLocked.Error() {   // "the process cannot access ..." (lower case, no period)
    return ErrLocked
} else if err != windows.ERROR_LOCK_VIOLATION {
    return err
}
return nil                                       // ERROR_LOCK_VIOLATION: reported as locked successfully
```

`errLocked`'s text does not match the system message (`"The process cannot access the file
because another process has locked a portion of the file."`), so a locked file reads as
lockable. `purgeFile` then removes WAL files the WAL still holds, and once WAL files rotate past
`max-wals` before a snapshot, the next restart cannot find the WAL that covers the snapshot's index.

## Classification

**O-pkg (secondary A-model); bug still present at the pin.** `client/pkg/fileutil` and
`server/storage/wal` are not translated (`verified.txt`: `storage/wal` 78 functions, 0
verified). The server's `EtcdServer.purgeFile` is an assumed trust boundary whose postcondition is
`True` (`Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__purgeFile.lean`), true of any
behavior. The damage shows only at a restart, which the model does not include (A-model). At the
pin (`107edf7e4`) and on upstream `main`, `lockFile` has the same three branches
(`lock_windows.go:84-97`). Windows is Tier 3 (untested) per the maintainers.

Source of verification states: `/shared/etcd-grove-triage/coord/verified.txt`.

## Code path (at the pin)

| Go function | State |
|---|---|
| `EtcdServer.purgeFile` (`server.go:601`) → `fileutil.PurgeFileWithDoneNotify` (`server.go:607`) | assumed (post `True`) / not translated |
| `fileutil.purgeFile` → `TryLockFile` → `lockFile` (Windows) | not translated (`lock_windows.go` is build-tagged `windows`) |
| `wal.WAL.ReleaseLockTo`, `storage.Release` | not translated |
| bootstrap `readWAL` / `restartNode` | not translated |

## Proposal: `wal-purge-lock-protocol` (new)

Make the file-lock protocol between the WAL and the purger an explicit contract:

- `TryLockFile path` returns `nil` → the caller holds a ghost exclusive token `fileLock path`
  (a trust-boundary spec per OS; on Windows it is false at the pin, which is exactly this bug,
  so it would surface as an A-axiom when the Windows variant is checked against the OS
  documentation);
- the WAL holds `fileLock f` for every file whose entries are above the last released snapshot
  index (`ReleaseLockTo`'s postcondition);
- `purgeFile` removes only files whose token it holds, so it never removes a WAL file above the
  released index.

The restart-time consequence ("the WAL needed by the latest snapshot exists") then needs the
`fs-crash-model`/`crash-restart-model` file-system view. The crash-free half above is medium
(purge.go about 60 lines, WAL `cut`/`ReleaseLockTo`/lock bookkeeping about 150 lines, plus the
`fileutil` lock axioms). It would not catch the Windows bug on its own: the bug lives in the
OS-level lock axiom. Its value is to name that axiom so it can be checked per platform.

## Findings

The bug is present at the pin and unfixed upstream, but in untranslated code (`client/pkg/fileutil`,
Windows only), so per this batch's rule no `issues/` file was written. It is a candidate if the
repository records bugs in untranslated code. A reproduction would be a Windows-only Go test:
`LockFile(p)` then `TryLockFile(p)` must return `ErrLocked`; at the pin it returns a
`*LockedFile`. Not run: no Windows host. No bug in this repository's specs.
