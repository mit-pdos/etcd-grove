# etcd-io/etcd#20793: Learner promotion not persisted into v3store may be propagated across multiple upgrades

- URL: https://github.com/etcd-io/etcd/issues/20793 (closed 2025-10-21; labels `type/bug`,
  `release/v3.5`, `priority/important-soon`)
- Affected: rolling replacement upgrades in the cluster-api style (add a learner, promote it,
  remove an old member) from ≤ v3.5.19 through v3.5.20–23 to v3.6. The new member
  receives a snapshot from a member running ≤ 3.5.19 whose `members` bucket still has the stale
  `isLearner: true` of #19557. The upgrade to v3.6 then fails with "too many learner members".
- Fix: PR #20797 (`release-3.5`, merge `2e24a9845`, v3.5.24). It adds
  `membership.SyncLearnerPromotionIfNeeded`, called when a snapshot is applied: v3's `IsLearner` is
  corrected from v2 (the 3.5 source of truth). The fix is on `release-3.5` only.

What goes wrong: #19557's fix (v3.5.20) repairs a member's bucket at its own bootstrap. A member that
joins later and is seeded by a snapshot (`EtcdServer.applySnapshot` → `RecoverSnapshotBackend`)
takes the sender's whole bbolt file, wrong `members` bucket included. Its v2 store is rebuilt from
the snapshot's v2 part, which is right. 3.5 uses the v2 store, so nothing shows until v3.6 makes the
bucket authoritative.

## Classification

**F (release-branch code; the mechanism is not in `main`); counterfactual F−, gap O-fn.** The
decisive fact: at the etcd pin `107edf7e4` membership has one store. A snapshot's `members` bucket
*is* the membership, so there is no second copy to disagree with. `applySnapshot`'s snapshot branch
installs the backend and calls `s.cluster.SetBackend(...)` and `s.cluster.Recover(...)`
(`server.go:1116-1120`). The bucket can only be wrong if the sender's was, and on `main` the sender's
was written by `PromoteMember`'s plain put (`etcd-19557.md`). Counterfactually, the
verified `applySnapshot` spec does not reach the snapshot branch at all.

Source of verification states: the batch's `verified.txt`.

## The counterfactual

On the buggy (3.5) code, the received snapshot carries a `members` bucket that contradicts the
member's own source of truth. Nothing here sees that. `EtcdServer.applySnapshot.spec` has the
premise that the `toApply` carries no snapshot (`taSnapshotAddr ap ↦□ (null : Loc)`, which is raft's
contract for the specified `Ready` shape, `rnApP`), and its post is `True`. The whole snapshot
branch, where #20797's sync was added, is outside every statement. Even with that branch verified, the existing predicates
say nothing about the `members` bucket's contents (see `etcd-19557.md`). So the gap is **O-fn**
twice: the snapshot branch is unverified, and the membership code is unspecified.

## Proposal: `membership-state-model`, with the snapshot branch

The statement of `etcd-13196.md`, plus the snapshot conjunct. A snapshot at index `k` that a leader
sends has buckets equal to `memOf (applied k)` (the sender's invariant at `k`, carried by the
snapshot's ghost witness, in the way `raft-pending-snapshot-ready` carries the log prefix). The
receiver's `applySnapshot` reinstates the invariant at `k` through `Recover`. Cost: on top of
`membership-state-model` (medium to large), the snapshot branch of `applySnapshot` with
`RecoverSnapshotBackend`. Large, shared with `verify-watchable-restore` and
`raft-pending-snapshot-ready`. It would catch this bug as a broken receiver invariant only if the
sender's invariant is stated per member. That is what makes the propagation visible: a wrong bucket
on one member becomes a wrong bucket on another.
