# etcd-io/etcd#20716: in-process watch (v3election Campaign) deadlocks under a storm of watch cancellations

- URL: https://github.com/etcd-io/etcd/issues/20716 (closed by the stale bot; labels `type/bug`,
  `stale`). Not fixed. PR #21064 (a reproduction test, closed) and PR #21065 (the fix, open:
  `client/v3/watch.go` sends requests from a separate `sendLoop` through bounded queues and drops
  best-effort cancels under pressure; also touches `v3rpc/watch.go`). Same root cause as
  etcd-io/etcd#18879 (open).
- Affected: 3.5.13 and 3.6.4 as reported. Present at the etcd pin `107edf7e4`.
- The report: about 500 C++ clients call the gRPC `Election.Campaign`. Killing the waiting ones all
  at once cancels about 500 internal watches on the in-process stream. The stream stops for good:
  pending-events and slow-watcher metrics stay high, new watches get no events, and a follower is
  never promoted. A goroutine dump shows the cycle.

What goes wrong (the reporter's diagnosis, checked at the pin): the cancellations reach
`watchGRPCStream.run` as `closingc` events. For each one, `run` calls `wc.Send(cancel)`
synchronously (`client/v3/watch.go:688-707`, the `Send` at 706). The adapter's pipe has an
unbuffered client-to-server channel and a one-slot server-to-client channel
(`server/proxy/grpcproxy/adapter/chan_stream.go:145`). On the server, `recvLoop` answers each
cancel by putting a response on `ctrlStream` (`v3rpc/watch.go:382-386`, buffer
`ctrlStreamBufLen = 16`, line 124). `sendLoop` drains `ctrlStream` into `gRPCStream.Send`
(`:514-519`). The client side receives through `serveWatchClient` into the unbuffered
`w.respc` (`watch.go:784`), which only `run` reads. Once `ctrlStream` is full the wait is
circular: `run` waits for `recvLoop` in `Send`, `recvLoop` waits for `sendLoop` on
`ctrlStream`, `sendLoop` waits for `serveWatchClient` in `Send`, and `serveWatchClient` waits
for `run` on `respc`. The in-process client is one long-lived `clientv3.Client` shared by every
`v3election`/`v3lock` RPC, so the stuck stream breaks all of them until the server restarts.

## Classification

**C-live (secondary O-path).** The four loops in the cycle are verified and sorry-free:
`watchGRPCStream.run` and `serveWatchClient` (client unit W-C), `serverWatchStream.recvLoop` and
`sendLoop` (W-S). The specs are partial correctness. A goroutine that blocks forever meets
`run.spec` (`Spec/go_etcd_io/etcd/client/v3/watchGRPCStream__run.lean`) and the
`recvLoop`/`sendLoop` specs, so no spec here can exclude a deadlock. The fix (PR #21065) changes
the verified functions. The reported trigger runs through the untranslated adapter, whose
unbuffered pipe removes the slack that HTTP/2 flow-control windows give a networked client: the
verified client results assume a stub on a gRPC connection
(`Spec/go_etcd_io/etcd/api/v3/etcdserverpb/watchClient__Watch.lean`). The same cycle is possible
in principle over gRPC. gRPC-go replenishes a stream's receive window only as the handler reads,
so it would take a window's worth of cancel requests (thousands). That is not demonstrated
upstream. So the composition decides the threshold, but not the existence of the cycle.

## The argument (step 4)

The observed behavior is that `run`, `serveWatchClient`, `recvLoop` and `sendLoop` all block
forever. In Iris terms, a non-terminating execution of each. Every spec on the path is a Hoare
triple `{{P}} e {{Q}}` (partial correctness): it constrains only executions that return. The
channel and stream models allow a send to block forever when nobody receives. No premise fails
and no axiom is involved (the gRPC `Send` specs are stated as their bodies). The postconditions
do not apply. The behavior is consistent with every spec, so it is C-live. No spec here
states liveness. STATUS says so explicitly for some units, e.g. the raft `node` harness
(`notes/STATUS.md:11579`: "Out of scope: liveness (an operation may wait forever)"). For the
watch loops it is implicit in the triples.

## Proposal: `watch-stream-no-cyclic-wait`

Deadlock freedom is not expressible in Perennial's Iris logic (it would need an obligations-based
logic, Jacobs-style, or a ghost wait-for graph with a termination measure, neither of which
Perennial has). The closest safety property is a structural non-blocking discipline proved as
part of each loop's spec:

- client: `run` never performs a blocking stream `Send`. Each request goes through a send queue
  owned by a separate send goroutine, and `run`'s enqueue of a best-effort request (cancel,
  progress) is a `select` with a `default` (PR #21065's shape). In the spec, `run` holds no
  `cliSendTok` (the client send token) once it has started; the send goroutine does.
- server: `recvLoop` puts on `ctrlStream` only in a `select` that can also give up. Either it is
  non-blocking with an overflow policy, or `sendLoop`'s `Send` is never waited on by `recvLoop`.

With both, every blocking wait in the cycle has a branch that drains its predecessor, which
breaks the cycle: an informal wait-for argument over proved local facts. Cost: medium after the
fix is in the fork. Re-verify `run` with the new send loop (the substream and resume invariants
carry over; the new part is the queue's ownership of the send token and the dropping of a
best-effort cancel, which needs `watch-client-cancel-reaches-server`'s conjunct weakened to
"sent or dropped under pressure") and `recvLoop`'s control sends. Verifying the adapter
(`chan_stream.go`, 131 lines) would bring the in-process path into scope, which
`inproc-client-auth-identity` (`etcd-17502.md`) also needs.
