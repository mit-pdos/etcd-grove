# etcd-io/etcd#19091: Client lease library does not check for expiration

- URL: https://github.com/etcd-io/etcd/issues/19091 (closed 2025-05-17 by the stale bot; label
  `type/bug`). Filed by upamanyus against 3.6.0-alpha.0 (`d065a4a9e`).
- Observed: with the `leasing` KV, client 1 puts and gets `k` (caching it under its session lease),
  is partitioned until the session lease expires, client 2 puts `k = "def"` (allowed: the lease key
  is gone), then client 1's `Get(k)` returns the cached `"abc"`. Expected: the package documentation
  says it "serves linearizable reads from a local cache" (`client/v3/leasing/doc.go:15`), so `"def"`.
- Fix: none merged. PR #19092 (a client-side `Lease.Unexpired()` checked by `readySession`; closed
  unmerged) and PR #21589 (the same freshness check, plus the `EvictRange` fix; closed unmerged).
  Reproduction: `TestLeasingGetChecksForExpiration` on the fork (`upamanyus/etcd` `d065a4a9e`,
  `tests/integration/clientv3/lease/leasing_test.go:419-491`).

What goes wrong, at the pin as reported: `leasingKV.get` serves a cached entry when
`readySession()` (`client/v3/leasing/kv.go:477`) is true, and `readySession` is a non-blocking
receive on `session.Done()`. `Done` is closed by the session's keep-alive goroutine when the
`KeepAlive` channel closes, which the client's lease library does only after it notices the lease
expired (its own deadline loop, after a sleep); between the server's expiry and that close, the
cache answers with a value other clients have since overwritten.

## Classification

**C-scope (the spec admits it, by a recorded choice; secondary A-model).** The leasing package is
verified at the pin (`leasingKV.Get` → `get` → `readySession`, all proved, linked in
`Proof/go_etcd_io/etcd/client/v3/leasing/Results.lean`), the premises hold, and the spec of a
cached `Get` promises only etcd's record of the key *at the entry's acquisition revision, while the
lease key existed* — not linearizability. `notes/decisions.md:2546`: "The lease-expiry window is
excluded by the statements, not the premise. … A cached answer is `k`'s record at a revision at
which the lease key existed: not linearizable, and not claimed to be." The package documentation
claims more than the code does, and the missing piece is time (when the session lease has expired),
which the model cannot express.

## The argument (step 4)

The observed run as the spec sees it: client 1's cache holds an entry `e` for `k` acquired at
revision `e.rev` with `e.acq = "abc"` and the lease key `pfx/k` present with client 1's lease. Its
session lease expires at the server; etcd deletes `pfx/k` (an `EtcdStep` changing no data key); at
revision `r3 > e.rev` client 2 writes `k = "def"`. Client 1's `Get(k)` returns `"abc"`.

- `leasingKV.Get.spec`'s postcondition is `getOutcome` (`InvLeasingKV.lean:443-449`), whose second
  case is `getCached γ pfx k o ret` (`:414-417`): an entry `e` of a state of the cache's log, with
  `entryFacts pfx k e` (etcd's record of `k` at `e.rev` is `e.acq`, the lease key present there with
  `e.lease`) and the response `getResult o e`. All of it holds of the run: the facts are about
  `e.rev`, which is in the past and unchanged.
- The theorem that connects a cached answer to etcd's *current* state,
  `leasing_cached_get_stable` (`Results.lean:180-188`), concludes `kvOf sb key = e.acq` only for a
  state `sb` in which the lease key still has its acquisition's create revision
  (`lb.createRev = lv.createRev`). In the run the lease key is gone at `r3`, so the theorem says
  nothing, by design.
- `readySession.spec` returns `sessionReady γ` on `true`: the session was not done "when it looked"
  — a fact about the `Done` channel, not about the lease at the server.

So the outcome satisfies every postcondition (no X); what the user expected — the answer is etcd's
state at some point during the call — is not implied because the spec ties the cache to the lease
key's incarnation, and nothing ties the client's view of its session (`Done`) to the server's
deletion of the lease key. That tie is a statement about time: the client can only know the lease
is live from a local clock and the TTL, which is what #19092's `Unexpired()` checks, and which is
sound only under bounded clock drift (#21589's own caveat).

## Proposal: `leasing-linearizable-with-clock` (on `lease-clock-model`)

With a fix like #19092's (serve from the cache only if the session lease's local deadline, computed
from the send time of the last keep-alive acknowledged plus the TTL, minus a drift margin, is in the
future), the statement to prove is theorem 1 strengthened to linearizability:

```lean
-- getCached, strengthened: the answer is etcd's record of k at some revision reached during the call
def getCachedLin (γ) (pfx key) (lo : w64) (o) (ret) : IProp GF :=
  ∃ (r : w64) (s : List EtcdKv), etcdState r [] s ∗ ⌜lo ≤ r⌝ ∗ etcdReached r ∗
    freshGetResp ret … (getResult o ⟨…, kvOf s key⟩)
```

proved from `leasing_cached_get_stable` plus a new trust-boundary fact of the clock model: while
the local deadline has not passed, the server has not revoked the session lease, so the lease key
keeps its incarnation (`LeasingProtocol` then gives the rest). Cost: the leasing side is small (one
case of `get`, the lemma above); the clock model is `lease-clock-model`'s (large; Perennial has no
time model: a Perennial proposal). Without a clock, the documentation fix is the honest one: say
cached reads are linearizable only while the session lease is live, and stale for up to the client's
expiry-detection delay after it expires.
