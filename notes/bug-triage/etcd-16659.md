# etcd-io/etcd#16659: etcd client can report an error after a successful write

- URL: https://github.com/etcd-io/etcd/issues/16659 (closed 2024-05-24; labels `type/bug`,
  `area/documentation`)
- Affected: v3.5.5 (embedded server), and every version since: the code is unchanged at the pin.
- Fix: none in the code. The maintainers kept the apply-side quota check on purpose and documented
  the behavior (etcd-io/website#856, "Add doc of write success with no space error returned").

What goes wrong: a compare-and-set `Txn` passes the API-side quota check
(`v3rpc.quotaKVServer.Txn` → `quotaAlarmer.check`) and is proposed. When it is applied, the
backend is over its quota. `apply.quotaApplierV3.Txn` (`server/etcdserver/apply/quota.go:45-52`)
calls `a.q.Available(rt)` first, then runs the inner applier's `Txn` anyway, which commits the
write. Only after that does it replace the `nil` error with `ErrNoSpace`. The apply loop raises the
`NOSPACE` alarm, and the client gets `mvcc: database space exceeded` for a write that was applied.
The reporter's retry of the same CAS then finds the new value and fails.

## Classification

**N (works as intended upstream, now documented). The specs document it.** The reported behavior is
the behavior the per-layer spec states. `apply.quotaApplierV3.Txn.spec` says the inner `Txn` runs,
then `ErrNoSpace` replaces its `nil` "if the quota said no (the transaction committed)"
(`Spec/go_etcd_io/etcd/server/v3/etcdserver/apply/quotaApplierV3__Txn.lean:28`). In the outcome
model this is `Outcome.applied log' true` (`Proof/.../apply/Chain.lean:120-122`, `noSpaceErrIs`
`:347`). `notes/STATUS.md` already lists it as "suspect (3) ... the client gets an error for a
committed write; the spec says so; not a bug". The client-level result agrees: an error response
says nothing about whether the write happened.

Secondary (scope, not the cause): the server's end-to-end results do not reach this case. They rest
on `isQuota`'s **`Available` returns `true`** ("the disk never fills", the user's decision,
`notes/decisions.md` "The NOSPACE alarm"). That is part of the trust-boundary axiom
`storage.NewBackendQuota.wp_proof` (`Spec/go_etcd_io/etcd/server/v3/storage/NewBackendQuota.lean:32`
→ `apply.isQuota`, `Proof/.../apply/Contracts.lean:413-424`). The reporter's deployment (a 64 MB
quota that fills) does not meet it. So `chainStep`'s quota case (`Chain.lean:178-182`) is the
inner outcome, and `ErrNoSpace` and the NOSPACE alarm are unreachable in the server model.

## The argument (step 4)

1. The per-layer spec allows the outcome and in fact names it. `kvPostF … (apply.txnAnswerIs log t
   skip resp err)` is stated over `Outcome.applied log' ns` and `noSpaceErrIs ns err`, with
   `ns = true` exactly when `Available` returned false. The observed run (the log extended by the
   CAS's put, `err = ErrNoSpace`) is that outcome with `ns = true`.
2. At the client, `client_txn_end_to_end` (`Results.lean:2192-2202`) gives "`nil` and the reply …
   with `□ Q` of the state at which the caller's **persistent** update `kvOpAu … Q` linearized …;
   or an error and no reply". The update is persistent, so it may have fired even on the error
   branch. The spec does not imply "error ⇒ not written", which is what the reporter expected.
   This holds independently of the quota axiom: the gRPC transport's contract
   (`Spec/google_golang_org/grpc/ClientConn__Invoke.lean`) already allows a failed call whose
   handler ran (see `etcd-18424.md`).
3. The quota axiom only removes the case from the server-internal results. That the server is
   "unchanged by `ErrNoSpace`" (no NOSPACE alarm proposal, no switch of the chain to `capped`,
   `kvInv`'s fixed `γk.ch0 = alarmChain false false false`, `notes/STATUS.md:3585`) is proved only
   for a disk that never fills.

## Proposal

None needed for this bug (N). A related scope direction, not new (`notes/decisions.md` "The NOSPACE
alarm" records it as deliberate) and not counted: drop `Available = true` (`isQuota`'s `Available`
returns some boolean). The chain's quota case would become `.applied l ns` with `ns` free, and the
server would have to model the NOSPACE alarm proposal (`server.go:1976`) and the switch to
`alarmChain _ true _` in `kvInv`. Cost: medium to large (the chain is fixed in `kvInv`/`kvCertInv`
and in every consumer of `chainStep_plain`).

## Findings

None: not a bug in the code (documented upstream), no `issues/` file. No bug in this repository's
specs. Note for the trust base: `storage.NewBackendQuota.wp_proof` postulates `Available = true`,
which is false once a backend reaches its quota. This is known and deliberate
(`notes/decisions.md`), and the client results do not depend on it for this behavior.
