# etcd-io/etcd#20582: cache returns a different state for the same revision (serializable validation)

<https://github.com/etcd-io/etcd/issues/20582>. Filed 2025-08-29 by serathius and closed the same
day by him. No fix and no PR. Found with the robustness tests (PR #20354, with consistent reads
disabled for the cache). The serializable validation of a `Range("key", "kez", Revision: 144)`
expected an older state than the cache returned.

**The report and its resolution.** The reporter withdrew it: "I didn't correctly implement
serializable request, forgot that range response returns latest revision. After fixing it, I got
multiple successful runs in row." The test harness had taken the response header's revision as the
revision the data is at. For the cache's `Get`, the header carries the cache's *latest* revision,
not the requested one.

## Classification

**N** (not a bug in the Go code: an error in the test harness, withdrawn by the reporter). The
spec documents the intended behavior exactly. `cacheGetOk`
(`Proof/go_etcd_io/etcd/cache/v3/InvCache.lean:1442-1454`) gives the response header as
`respHeaderVal st.latestRev` (`:1446`). The key-values are `kvRange key o.rangeEnd m` with
`isEtcdKvs r cf.pfx m` and `snapModel st o.rev = .ok r m` (`:1449-1450`). So the data is etcd's
state at the snapshot `r ≤ o.rev` that `snapModel` picks, and the header revision is the store's
latest revision `≥ r`. The two differ whenever the store has moved past the requested revision,
and nothing in the spec relates the header to `o.rev`.

## Proposal

None (N). The related strengthening `cache-get-state-at-requested-rev` (`etcd-21536.md`), "the
answer is etcd's state at `o.rev`", would let a checker compare against the requested revision
directly. The harness's mistake is the one that statement would document.
