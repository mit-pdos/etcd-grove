# etcd-io/etcd#22340: missing snapshot-directory fsync can make a member fail after a crash

- URL: https://github.com/etcd-io/etcd/issues/22340 (closed 2026-10-08; label `type/bug`)
- Affected: `main` before the fix (base `23a4e406a`), and v3.5, v3.6, v3.7.
- Fix: PR #22314 "fix: fsync snap directory when saving a received snapshot db" (merge
  `e9e56564d`, 2026-09-03). Backports were requested for 3.5/3.6/3.7.
- Sibling: etcd-io/etcd#22498 (the same missing directory fsync, at the adoption rename in
  `OpenSnapshotBackend`; open, present at the pin: `etcd-22498.md`).

What goes wrong (pre-fix code). A follower receives a leader's db snapshot over `rafthttp`.
`snap.Snapshotter.SaveDBFrom` writes it to a temp file, fsyncs the file, and renames it to
`<index>.snap.db`, but did not fsync `member/snap`. The raft message is then processed. The WAL
records the snapshot and `SaveSnap` writes the `.snap` file. After a power loss, the rename can be
lost while the WAL's snapshot record survives. On restart, bootstrap finds the snapshot record
above the db's consistent index. It asks `DBFilePath(index)` for the file, which is gone, and
panics with "failed to find database snapshot file".

## The counterfactual

No statement here mentions a file, a directory entry, or durability. `SaveDBFrom` has no spec. The
WAL's `Save`/`SaveSnap` are trust boundaries with postcondition `True` (`isRNWal`,
`Proof/.../InvRaftNode.lean`). There is no restart (`notes/STATUS.md:1137-1141`: "crashes and
durability" out of scope). The pre-fix and fixed code meet every spec: **F−**. The property the
fix restores is an ordering of durable effects: *the db file is durable before the WAL record that
refers to it*. It is of the same kind as persist-before-send (`raft-durable-acks`).

## Proposal: `fs-crash-model` (existing, from `etcd-6368.md`)

The crash-consistent file-system model that `etcd-6368.md` proposes for the WAL. Unsynced data and
unsynced directory operations (create, rename, remove) may be lost at a crash. Apply it to the
snapshot files as well. The statement for this bug, crash-free as a first step: give `os.Rename`
and `fileutil.Fsync(dir)` contracts over a ghost *durable* directory map (rename changes the
volatile map; a directory fsync copies it to the durable one). Then prove that `SaveDBFrom`
returns `nil` only with `<index>.snap.db` in the durable map. The raft wrapper's `SaveSnap`
contract then requires that fact for the snapshot it records: "durable db before durable
reference". The full statement (bootstrap after any crash finds the `.snap.db` that every durable
snapshot record above the db's consistent index names) needs crash semantics, which the Lean port
of Perennial lacks (a Perennial proposal first, CLAUDE.md "Changes to Perennial"). Cost: the
crash-free step is medium (the `snap` package's `db.go` is about 100 lines, plus the file-system
axioms). The full statement is large, and it depends on `raft-pending-snapshot-ready` for
snapshots to reach the server at all.
