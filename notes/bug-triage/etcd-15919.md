# etcd-io/etcd#15919: Incorrect hash when resuming scheduled compaction after etcd restarts

- URL: https://github.com/etcd-io/etcd/issues/15919 (closed 2023-06-08; labels `type/bug`,
  `stage/triaged`). Observed on v3.5.9 with `--experimental-compact-hash-check-enabled`: the first
  periodic compaction hash check after a rolling restart raised a false `CORRUPT` alarm.
- Fix: PR #15985 (commit `b9e30bf87`, merge `6c5fde513`, 2023-06; backported to 3.5 and 3.4):
  `store.checkPrevCompactionCompleted` (scheduled == finished compact revision in `Meta`), read
  before `updateCompactRev` in `Compact` and `compactLockfree`; `compact` stores the job's hash
  only if the previous compaction completed.

What goes wrong (pre-fix): a compaction at `c` deletes the bucket's revisions `≤ c` in batches,
committing each, and writes `finishedCompactRev` in the last. A member stopped mid-pass restarts
with `scheduledCompactRev = c > finishedCompactRev = p`; `store.restore` resumes it
(`compactLockfree(c)` → `compact` → `scheduleCompaction(c, p)`). That job's hasher sees only the
revisions the interrupted pass had not yet deleted, so the hash it stores for `(p, c]` differs
from the other members'. The leader's `CompactHashCheck` compares stored hashes at the same
`(CompactRevision, Revision)` and raises `CORRUPT` against a healthy member.

## Classification

**F− (fixed before the verified code); gaps C-obs (hashes are not modelled) and A-model (the
trigger is a crash mid-compaction), O-fn (`store.restore` on a backend with data).** The fix
`b9e30bf87` is an ancestor of the pin `107edf7e4`; at the pin `compactLockfree` and `Compact`
call `checkPrevCompactionCompleted` (`kvstore.go`). Counterfactually the specs admit the
pre-fix code: every hash is "any" (`store__scheduleCompaction.lean:32`, `kvHasher__Hash.lean`),
storing it has no effect (`hashStorage__Store.lean`: "the stored hashes are not modelled"), and
`checkPrevCompactionCompleted` itself is specified as "some boolean … which the model ignores"
(`store__checkPrevCompactionCompleted.lean:23-27`). Removing it, or storing the hash
unconditionally, leaves every proof intact. The resumed compaction itself is reached only through
`store.restore` on a backend with data, which is an axiom stated for an empty backend
(`store__restore.lean:2,35`).

Source of verification states: the `Spec/` and `Proof/…/mvcc/Link.lean` files and
`Code/go_etcd_io/etcd/server/v3/storage/mvcc.toml`; `verified.txt` was not produced.

## The counterfactual (step 5)

Pre-fix, `compactLockfree(rev)` is `updateCompactRev(rev)` then `compact(trace, rev, prev)`, and
the job calls `s.hashes.Store(hash)` unconditionally. Against the current specs:

- `store.compact.spec`'s postcondition is about the queue, the token, the channel and
  `compactDone` (`compactedAt γ rev`); the hash appears nowhere. The pre-fix job body is the
  current one with the `if prevCompactionCompleted` removed; both branches of the current proof
  already discharge `hashStorage.Store`'s `True` precondition or skip it, so the pre-fix job is
  proved by the same steps.
- No statement relates a stored hash to the store's contents, so a hash computed over a
  partially compacted bucket is indistinguishable from a correct one.
- Even with a hash model, the scenario needs a restart from a disk state in which compaction
  at `c` was scheduled, partly done and committed, and not finished. `NewStore.spec` takes a
  fresh backend (`kbView kb γb 1 ∅`), and `restore`'s axiom covers only an empty `Key` bucket, so
  no verified statement starts from such a state.

What the user relied on — *a stored compaction hash at `(p, c]` is the same on every member whose
log agrees up to `c`* — is unstated (C-obs), and its violation is reachable only across a crash
(A-model).

## Proposals

- `model-kv-hash` (new; also etcd-io/etcd#18337): a pure model of the hasher's input
  (`kvHashIn log c r`), the crc opaque; `scheduleCompaction` returns `crc (kvHashIn log p c)` *when
  it starts from a bucket compacted exactly at `p`* (`compactedAt γ p`, which the store already
  tracks), and `compact` stores only such hashes — so `checkPrevCompactionCompleted` gets a real
  spec (true ⇒ the bucket is compacted at the previous compact revision). Medium (see
  `notes/bug-triage/etcd-18337.md`).
- `mvcc-restore-from-backend` (existing), with its per-commit addition: every backend commit,
  including each of `scheduleCompaction`'s batch commits, persists a state from which `restore`
  recovers the right store, and `restore` specified on such a state (scheduled > finished: a
  partly compacted bucket). Together with `model-kv-hash` this states the resumed job's hash and
  would have failed on the pre-fix code at `compact`'s store of it, without a full crash model.
  Large (the slug's estimate).

## Findings

None new (the bug is not at the pin); no bug in this repository's specs.
