# etcd-io/etcd#20655: Fast watch creation breaks reliable watch guarantee

- URL: https://github.com/etcd-io/etcd/issues/20655 (filed and closed 2025-09-12, by its reporter
  serathius, eight minutes apart).
- Affected: reported against `main` and `release-3.5` while investigating #20349. The reproduction
  was PR #20654.
- Fix: none in the server. The reporter closed it with "Looks like a bug in robustness tests". The
  test fix is `6fd984fd6` "Fix race condition in robustness watch creation due to slices
  reallocation" (2025-09-12, `tests/robustness/client/client.go` only). It is an ancestor of the pin.

What went wrong: `RecordingClient.watch` appended a new `WatchOperation` to `c.watchOperations`
under `watchMux`. The goroutine of an earlier watch, however, wrote
`c.watchOperations[index].Responses = append(...)` without the lock. When watches were created
quickly, `append` reallocated the slice, and a goroutine's write landed in the old backing array.
Recorded responses were lost, so the validator saw the "reliable" guarantee broken. The fix keeps
a local `responses` slice and stores it under the lock.

## Classification

**N** (a bug in the test harness: no etcd code involved). The decisive fact is that the only change
is to the robustness client (`6fd984fd6`), and the reporter withdrew the server-side reading.

Source of verification states: not needed (no etcd function on the path).

## Proposal

None (class N). This race in the robustness harness is one of the candidate explanations of
etcd#20573 (`etcd-20573.md`).
