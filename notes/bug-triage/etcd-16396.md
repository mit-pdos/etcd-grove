# etcd-io/etcd#16396: myKey makes it impossible to implement distributed locks under multiple instances using concurrency

- URL: https://github.com/etcd-io/etcd/issues/16396 (closed 2025-04-26 by the stale bot; labels
  `type/bug`, `area/clientv3`, `stale`). No fix, PR or commit.
- Version: client/v3 v3.5.9 against etcd 3.4.27.
- The report: `Mutex.tryAcquire` names its key `pfx/<session lease>` (`myKey`), so two pods with
  their own sessions get different keys. The reporter reads this as "the lock is bound to one
  instance" and asks for a configurable `myKey`, so that both pods use the same key.

## Classification

**N** (not a bug: a misreading of the lock's design). The only reply (a non-member) gives the
reason. The lock is not the key `myKey`. It is "my key is the first-created key under `pfx`"
(`Get(pfx, WithFirstCreate())`). Keys of different sessions under one prefix are what make the
pods contend. The proved spec states exactly this. `lockedAt pfx key c R` holds when `key` is
present at `R` with create revision `c` and no key under `pfx` has a smaller one
(`Proof/go_etcd_io/etcd/client/v3/concurrency/InvMutex.lean:96`). `mutex_exclusion`
(`Proof/go_etcd_io/etcd/client/v3/concurrency/Results.lean:104`) proves that two holders with
different create revisions are never both present at a revision at or after both lock
revisions, whatever sessions or processes they come from. A shared `myKey` across pods would
break the lock: the second pod's `tryAcquire` would take the `Else` branch and reuse the first
pod's key, and both would "hold" it. That is the hazard `issues/mutex-lock-recreated.md` already
documents for two `Mutex` values that share one session.

## Proposal

None (class N). The intended behavior is already a theorem (`mutex_exclusion`,
`mutex_holder_unique`). The package documentation could say that a lock is shared through its
prefix and that each session holds its own key under it. That is a documentation suggestion, not
an `issues/` finding.
