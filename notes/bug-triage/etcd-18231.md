# etcd-io/etcd#18231: grpc-proxy stops sending watch events

- URL: https://github.com/etcd-io/etcd/issues/18231 (closed 2025-07-06 by the stale bot, unfixed;
  labels `type/bug`, `gRPC-proxy`, `stale`). Reported on v3.4.28 (`proxy/grpcproxy/`). The same
  code is at `server/proxy/grpcproxy/` on `main`.
- Reproduction: patch the server's `serverWatchStream` so that it ends the stream with
  `codes.Canceled` after 2 s, then watch through the proxy with `etcdctl watch`. The proxy's
  backend watch ends and the client waits for ever. No fix PR. The reporter suggests re-watching
  in a loop in `newWatchBroadcast`.

What goes wrong (at the pin): when the server cancels the backend watch or ends its stream, the
verified client closes the watch channel, sometimes after a last `Canceled` response
(`client/v3/watch.go:494-495`). `newWatchBroadcast`'s goroutine leaves its
`for wr := range wch` loop and exits (`server/proxy/grpcproxy/watch_broadcast.go:71-74`). Nothing
re-watches, and nothing tells the receivers. A cancel without a compaction revision is dropped by
`watcher.send` (`watcher.go:106-108`: no events, not `Created`, `CompactRevision == 0`). The
proxy's client stream stays open and silent. The dead broadcast then takes in new watchers as
well (etcd#21813).

## Classification

**O-pkg**. The faulty code is `server/proxy/grpcproxy`, which is not translated: no `Code/` module,
and no row in the inventory (`/shared/etcd-grove-triage/coord/verified.txt`). The bug is still at
the pin `107edf7e4` (the lines above). The verified backend client allows exactly what happens. In
`watcher.Watch.spec` the channel "may be closed" (`Spec/go_etcd_io/etcd/client/v3/watcher__Watch.lean`,
docstring and the `isSpsc … rangeWatchElem` postcondition), and a server-side cancel is one of the
ways it closes. The proxy, which is unverified, does not handle the close. It is the same defect as
etcd#21813, reached by another trigger: there the backend connection breaks, here the server
cancels.

## Proposal: `grpcproxy-watch-relay` (see `etcd-21813.md`)

The same proposal. The conjunct that catches this bug is the end of the broadcast. When its
goroutine leaves the range loop, every receiver either has had a `Canceled` response posted or has
been moved to a live broadcast that re-watches from its `nextrev`. At the pin the goroutine just
returns, so the proof of `newWatchBroadcast`'s goroutine would fail at the exit of the loop.

## Findings

None new. The bug is in an untranslated package. It is the same defect as etcd#21813 (see that
report).
