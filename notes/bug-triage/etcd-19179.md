# etcd-io/etcd#19179: Missing delete event on watch opened on same revision as compaction request

- URL: https://github.com/etcd-io/etcd/issues/19179 (filed 2025-01-13, closed 2025-01-22; labels
  `release/v3.5`, `release/v3.4`, `priority/critical-urgent`, `area/robustness-testing`).
- Affected: `main`, 3.5 and 3.4 after the fix of etcd#18089 (PR #18274). This is an edge case that
  fix missed, not a regression from it (ahrtr). Found by the robustness tests ("resumable" broken)
  with `--experimental-compaction-batch-limit=300`.
- Fix: PR #19188, "mvcc: restore tombstone index if it's first revision" (`d8b419257`, 2025-01-13;
  backports #19189/#19191 and others). It is an ancestor of the etcd pin `107edf7e4`.

What goes wrong (pre-fix code), from fuweid's reproduction. Key `a` is put at revision 2 and
deleted at 6. `Compact(6)` persists `scheduledCompact = 6` and starts the batched bucket deletion.
The first batch deletes revision 2 and keeps the tombstone 6, as #18274 intends. The process then
dies before `finishedCompact` is written (a gofail panic `compactBeforeSetFinishedCompact`). On
restart, `store.restore` rebuilds the index from the bucket. `restoreIntoIndex`
(`server/storage/mvcc/kvstore.go`) skipped any revision that is a tombstone and is the first
revision seen for its key (`else if !isTombstone(rkv.key)`). So key `a`, whose only surviving
revision is the tombstone 6, gets no `keyIndex`. `restore` then resumes the scheduled compaction at
6 (`compactLockfree(scheduledCompact)`). The index's keep set has no entry for `a`, so
`scheduleCompaction` deletes the tombstone 6 from the bucket. `compactMainRev = 6`, and a watch at
revision 6 passes `chooseAll`'s `minRev < compactRev` test, so it is not refused. `rangeEvents`
then finds no `DELETE` at 6, and the event is lost silently. The fix adds
`keyIndex.restoreTombstone`, which restores such a tombstone as a one-revision generation followed
by an empty one.

## Classification

**F (fixed before the verified code); counterfactual F−, gap O-fn (secondary A-model).** The fix
`d8b419257` is an ancestor of the pin (`git merge-base --is-ancestor`: yes). At the pin,
`restoreIntoIndex` calls `ki.restoreTombstone` (`kvstore.go:480-481`). The buggy function and its
caller are outside the verified code. `restore`, `restoreIntoIndex`, `restoreChunk` and
`keyIndex.restore`/`restoreTombstone` are names only (`Code/go_etcd_io/etcd/server/v3/storage/mvcc.toml`:
"The rest of the package (restore, compaction, hashing) is names only"). `store.restore`'s
trust-boundary spec covers only a **fresh, empty backend**
(`Spec/go_etcd_io/etcd/server/v3/storage/mvcc/store__restore.lean:24-37`, "A backend with data is
out of scope"; the premise is `bucketView γ q ∅`, `:44`; an `axiom`,
`Proof/.../mvcc/store__restore.lean`). The trigger also needs a crash in the middle of a
compaction, and crashes are not modelled (A-model). The watch specs also assume a store that is
never compacted (`crevFrozen`), as for etcd#18089.

Source of verification states: the `Spec/`/`Proof/` files, `Link.lean` and
`etc/link-lean-first-mvcc.txt`, because `verified.txt` was not produced.

## The counterfactual (step 5)

The buggy code is in untranslated functions, so the question is which statement would have to hold
of them. None does today.

- `store.restore.spec` speaks only of an empty `Key` bucket. On it, `restoreIntoIndex` reads
  nothing, so the pre-fix and post-fix versions agree, and the axiom is true of both. **F−**.
- The verified compaction (`compactLockfree` → `treeIndex.Compact` → `scheduleCompaction`) deletes
  exactly the bucket revisions that the index's `kiAvail`/`keepAt` does not keep (`KeyDel`,
  `Compact.lean`). These statements assume the index is the one the store's own writes built
  (`idxCert γ.idx log`). The bug is an index that disagrees with the bucket: `a` is missing,
  although its tombstone is in the bucket. No invariant here relates an index *rebuilt from a
  bucket* to the log, so nothing would break.
- The watch side: as in `etcd-18089.md`, the one statement that sees the lost event
  (`rangeEvents.spec`, `logEvents log minRev maxRev`) has `crevFrozen`, so it never meets a
  compacted store, let alone a restarted one.

Had restore on a backend with data been specified, the natural postcondition is "the rebuilt index
is the index of the log's surviving revisions": `idxCert γ.idx log` with the bucket a `keepAt c`
thinning of `log`, for `c` the finished compaction revision. Pre-fix `restoreIntoIndex` breaks that
postcondition for every key whose surviving revisions start with a tombstone, which is exactly the
state #18274 creates for a key deleted at `c`. So under `mvcc-restore-from-backend` this bug would
be **F+**, and that holds even without crashes. With a clean restart after a completed compaction
at 6, the rebuilt index still lacks `a`. It only shows when a compaction at 6 runs again, which
needs the interrupted compaction that is resumed on restart.

ahrtr's related concern in the thread ("a very small window that `finishedCompactRev` doesn't
match the real compacted revisions") is not present at the pin. `restore` resumes through
`compactLockfree` → `updateCompactRev`, which sets `compactMainRev = scheduledCompact`
synchronously under `revMu` before returning, and `restore` runs inside `NewStore` before any
watcher exists.

## Proposal: `mvcc-restore-from-backend`

Specify and prove `store.restore` (with `restoreIntoIndex`, `restoreChunk`, `keyIndex.restore`,
`keyIndex.restoreTombstone`) on a backend with data:

```lean
-- premise: the Key bucket is `bucketMap (thin log c)` for a log `log`, finished compaction `c`
--   (and scheduled compaction `c' ≥ c`, its batches applied to a prefix of the keys)
-- postcondition: isTreeIndex ti γ.idx ∗ idxCertThin γ.idx log c   -- index = index of log, above c
--   ∗ currentRev = max(log.length - 1, c') ∗ compactMainRev = c'
theorem restoreIndex_thin (log : Log) (c : Int) :
    indexOfBucket (bucketMap (thin log c)) ≃ₐ[≥ c] indexOf log   -- the pure core
```

Then `NewStore` on a non-empty backend, and the resumed compaction proved through the existing
`compactLockfree` spec. Cost: medium to large. The Go code is small (`restore` with its helpers is
about 150 lines, plus a goroutine and a channel). It must be translated (an addition to
`mvcc.toml`). The pure lemma that rebuilding the index from a `keepAt c`-thinned bucket gives back
the index's answers at revisions ≥ `c` is the core (several hundred lines, alongside
`Compact.lean`'s `kiGet_avail`). Proving the interrupted half (the bucket between `thin log c` and
`thin log c'`) needs `crash-restart-model` (etcd#16666, raft#197) for the crash itself. Without
crashes, a clean restart can be covered. Together with `watch-under-compaction` (etcd#18089) it
gives the watch guarantee across a restart.
