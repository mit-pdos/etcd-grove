# etcd-io/etcd#13883: AuthStore::Recover is not invalidating caches

- URL: https://github.com/etcd-io/etcd/issues/13883 (closed 2023-10-27; labels `type/bug`,
  `stage/tracked`, `release/v3.6`)
- Affected: `main` at `a08d47946` (April 2022), found by code reading. No reproduction was
  attempted. The issue's scenario: a lagging member installs a snapshot taken after a permission
  was revoked.
- Fix: closed as fixed by PR #14358 (`9c8326bb5`, `NewAuthStore` refreshes the cache). The
  `Recover` half was fixed by PR #14574 (`fbed8cb64`, `Recover` calls `refreshRangePermCache`),
  the fix of #14571. mitake's own PR #13920 for this issue was not merged.

What goes wrong (pre-fix code): `authStore.Recover(be)` (`server/auth/store.go`), called by
`EtcdServer.applySnapshot` after a snapshot install, reloaded `enabled` and `revision` but left
`rangePermCache` as it was. The cache could hold permissions that the snapshot's auth buckets no
longer grant, which are stale grants the member then honors. It could also lack users the
snapshot added: the #14571 symptom, after the cache became eagerly refreshed.

## Classification

**F (fixed before the verified code); counterfactual F−, gap O-fn and C-other**, as for
#14571 (`etcd-14571.md`, which has the full argument). Both fixes, `9c8326bb5` and `fbed8cb64`,
are ancestors of the etcd pin `107edf7e4`. At the pin, `Recover` refreshes the cache
(`store.go:396-411`). The existing specs would admit the buggy `Recover` for two reasons:

- `Recover`, `refreshRangePermCache` and the snapshot branch of `applySnapshot` are unverified
  (not translated; `applySnapshot.spec` assumes `ap.snapshot = nil`);
- `isRangeOpPermitted.spec` returns "some boolean", with no relation between the cache (`cacheP`)
  and the backend's auth state. In the apply model, the auth layer rejects or passes by free
  choice (`Chain.lean:174-177`).

The stale-grant direction is worth stating separately. Here the member *accepts* a write that
the up-to-date members reject. The spec's disjunct `chainStep B c rq log o` (accept) is as free
as the rejection, so the specs say nothing about authorization: they do not state that "a
write is committed only if the writer is permitted".

## Code path (at the pin)

The table in `etcd-14571.md` applies unchanged. The bug is in `authStore.Recover` (not
translated), reached from `EtcdServer.applySnapshot` (`server.go:1111`, outside its spec), and
seen through the verified permission checks.

## Proposal: `auth-state-model` (see `etcd-14571.md`)

The same proposal. For this bug the conjunct that matters is `cacheP st q σ`: the cache's
entries are exactly the merged permissions of `σ`. `Recover` would have to re-establish it for
the snapshot backend's `σ`. A stale entry breaks it, and so does a missing one. The
authorization half of the statement is "the auth layer passes a request iff `permitted σ …`",
and it also excludes the stale grant.
