# etcd-io/etcd#18337: HashKV should compute the hash of all MVCC keys up to a given revision

- URL: https://github.com/etcd-io/etcd/issues/18337 (closed 2025-08-28 by its author, "no
  bandwidth"; labels `type/bug`, `stale`). No fix. Maintainers: compaction and HashKV are
  coupled; changing the hash needs cross-version compatibility (a cluster-level feature, a KEP).
- Affected: every version with `kvHasher`'s keep filter, including the pin.

What goes wrong: `store.hashByRev(rev)` takes `keep := kvindex.Keep(rev)` — the revisions a
compaction *at `rev`* would keep — and `kvHasher.WriteKeyValue` skips every revision `≤
compactRevision` not in it. A revision at or below the compaction revision that compaction kept
(the key's value at the compaction revision) is skipped as soon as the key has a later revision
`≤ rev`, though it is stored and readable. The API documents HashKV as "the hash of all MVCC keys
up to a given revision" (`api/etcdserverpb/rpc.proto:243`).

## Classification

**O-fn (outside the verified code), secondary C-obs; the behaviour is a documentation mismatch
rather than an inconsistency.** The code is unchanged at the pin (`hash.go:72`, `kvstore.go:186`)
and reproduced there. Hashing is translated names-only, `hashByRev`/`HashByRev` not at all, and
the hasher is an axiom returning any value (`kvHasher__Hash.lean`: "returns some
`KeyValueHash`"; `hashStorage__Store.lean`: "the stored hashes are not modelled"), so no spec
here says what a hash covers. Every member applies the same filter, so equal stores still hash
equally; the corruption checks are not misled by this.

Source of verification states: `Code/go_etcd_io/etcd/server/v3/storage/mvcc.toml` (the translate
list) and the `Spec/` files; `verified.txt` was not produced.

## Proposal: `model-kv-hash` (new)

Model the hash as a pure function of what is fed to it, and specify both hash producers by the
committed log:

```lean
-- the crc's input, abstractly: the (key, value) pairs written, in bucket order
def kvHashIn (log : Log) (c r : Int) : List (BucketKey × KeyValue) := …   -- the filter, stated
axiom kvHasher.Hash : hasher fed `xs` returns `KeyValueHash.mk (crc xs) c r`   -- crc opaque
theorem hashByRev_spec : HashByRev rev at a store of log `log`, compaction `c`
  returns ⟨crc (kvHashIn log c rev), c, rev⟩
theorem compaction_hash_spec : a hash stored by compaction at `r` (previous `c`, *completed*)
  is ⟨crc (kvHashIn log c r), c, r⟩
```

Stating `kvHashIn` forces a choice between the documented "every stored revision `≤ r`" and the
code's filter, which is where this report's mismatch shows; and `compaction_hash_spec` is the
property the corruption check relies on (a member's stored hash equals any member's `HashKV` at
the same revisions), which etcd-io/etcd#15919 broke. Cost: medium — translate `hash.go`'s bodies
(the crc kept as an axiom over the byte sequence), `hashByRev` under `s.mu`/`revMu`, a pure lemma
that `scheduleCompaction`'s batches visit exactly the bucket's revisions `≤ r` in order (the
existing compaction proof already walks them), and `checkPrevCompactionCompleted` given a real
spec (today "some boolean").
