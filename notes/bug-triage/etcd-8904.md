# etcd-io/etcd#8904: gRPC v1.7.3 transport "panic: send on closed channel" on `*serverHandlerTransport`

- URL: https://github.com/etcd-io/etcd/issues/8904 (closed 2017-12-05; label `type/bug`).
  Reported on v3.2.10, with daily panics on all three members. It is a follow-up of #8595.
- Fix: in grpc-go, PR grpc/grpc-go#1687 "transport: fix race sending RPC status that could lead to
  a panic" (`c6b46087a`, released in v1.7.4). etcd picked it up with PR #8972 "vendor: upgrade
  grpc/grpc-go to v1.7.4" (merge `287c23c4b`, 2017-12-04).

What goes wrong: etcd serves gRPC through `grpcServer.ServeHTTP` when client and HTTP share a port
(`embed/serve.go`'s `grpcHandlerFunc`), which uses grpc's `serverHandlerTransport`.
`LeaseServer.LeaseKeepAlive` runs `leaseKeepAlive` in a goroutine and returns on
`stream.Context().Done()` while that goroutine may still be in `stream.Send`. In grpc ≤ 1.7.3,
once the handler returned, the transport closed its `writes` channel. A racing `Send`, or the
status write, then did `writes <- fn` and panicked with "send on closed channel"
(`handler_server.go:170`, in `serverHandlerTransport.do`). The stack is `leaseKeepAlive` →
`Send` → `serverStream.SendMsg` → `serverHandlerTransport.Write` → `do`.

## Classification

**F (fixed before the verified code); counterfactual F−, gap A-axiom, secondary O-fn.** The fix
is in grpc, and the pinned etcd (`107edf7e4`) builds against grpc v1.84.0 (`server/go.mod`). etcd's
vendor bump `287c23c4b` is an ancestor of the pin (`git merge-base --is-ancestor`: yes). The etcd
side of the path is not verified: `LeaseServer.LeaseKeepAlive`/`leaseKeepAlive`
(`server/etcdserver/api/v3rpc/lease.go:93,111`) are translated names-only (type only; the v3rpc
translation lists only `key.go`, `watch.go`, `header.go`, `quota.go`'s KV wrapper and the
interceptors, `Code/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc.toml`). Counterfactually, a
verified lease stream would rest on the same gRPC stream boundary as the watch: the raw
server-stream contract `srvRawStreamIs`
(`Proof/google_golang_org/grpc/InvGrpcStream.lean:313-336`), given to the handler by the axiom
`grpc.serveStream` (`:936`). That contract makes `SendMsg` return (nil or an error) with no
restriction to "before the handler returns". The header says so explicitly: "`Watch` returns
while its receive loop may be blocked". Against grpc v1.7.3's `serverHandlerTransport` that
postulate is false, since a `SendMsg` racing the handler's return panics. So the proof would have
admitted the crash by assuming it away. It would have been an A-axiom, not an F+.

Source of verification states: `/shared/etcd-grove-triage/coord/verified.txt` (no entry for
`lease.go`'s functions; `v3rpc.LeaseServer` is a type only).

## Proposal: `verify-lease-keepalive-stream` (new)

Translate `lease.go`'s `LeaseKeepAlive`/`leaseKeepAlive` (~60 lines) and prove them over the
existing stream wire (`InvGrpcStream.lean`: `srvStreamIs_of_raw`, the registration
`grpcStreamMethodOk`), as unit W-S did for `Watch`. The handler returns while its goroutine still
owns the stream's send token. The stream spec states each response's `TTL` and `ID` as
`EtcdServer.LeaseRenew`'s result, which needs `LeaseRenew` translated (shared with
`verify-lease-expiry-leadership`). Cost: medium. Alongside it, a trust-base note costing nothing:
`grpc.serveStream`'s claim that the raw stream's methods return after the handler has returned
holds for grpc's `serverHandlerTransport` only from grpc-go v1.20 (grpc/grpc-go#2695;
`etcd-9956.md`), and v1.7.4 for this race. The axiom's header should name the grpc version it is
read against, so that a grpc downgrade or a transport change is checked against it.
