# etcd-io/etcd#19487: Watch response revision can be lower than the required starting revision

- URL: https://github.com/etcd-io/etcd/issues/19487 (closed 2025-09-12)
- Affected: 3.5.18 per the report; every version before the fix (`main`, `release-3.5`, ...).
- Fix: PR #20281 (branch commit `cf0369e4a`, merge `9fb8c3685`, 2025-07-04), "Avoid lowering
  revision of watchers in the future after restore"; backported to `release-3.5` by #20290
  (`fe30a6e4f`).

What goes wrong (pre-fix code): `watchableStore.watch` puts a watcher whose `startRev` is in the
future (above `currentRev`) in the synced group with `minRev = startRev`. A snapshot install on the
member (`watchableStore.Restore`, `server/storage/mvcc/watchable_store.go`) moves every synced
watcher back to the unsynced group (`restore = true`) without touching `minRev`. The next
`syncWatchers` then set `w.minRev = curRev + 1`, *lowering* the future watcher's `minRev` below its
`startRev`, and moved it to the synced group; `notify` then delivered every later put on the range,
at revisions below `startRev`. The fix is `w.minRev = max(curRev+1, w.minRev)`.

## Classification

**F (fixed before the verified code); counterfactual F−, the gap O-fn (`watchableStore.Restore`
unverified).** The fix `cf0369e4a` (and its merge `9fb8c3685`) is an ancestor of the etcd pin
`107edf7e4` (`git merge-base --is-ancestor`: yes); the pinned `syncWatchers` has the `max`.
Counterfactually, the pre-fix `syncWatchers` still meets its spec: the lock invariant bounds an
unsynced watcher's `minRev` by the committed log (`InvWatchStore.lean:607-608`), so under it
`max(curRev+1, minRev) = curRev+1` and the two versions are the same program; the proof itself
resolves the `max` to `curRev+1` (`watchableStore__syncWatchers.lean:373-375`). The only way to an
unsynced watcher with a future `minRev` is `Restore`, which is translated but not specified, and
which the invariant excludes (`st.restore = false`, `InvWatchStore.lean:341`).

Source of verification states: `verified.txt` was not yet produced; states read directly from
`Spec/`, `Proof/` (theorems, no `sorry`) and `Proof/go_etcd_io/etcd/server/v3/storage/mvcc/Link.lean`.

## The argument (steps 4–5)

What the user observed, in the spec's terms: a response for watcher `w` with `r.startRev = 1000`
carrying an event with `modRev < 1000`. The exported result `watchRecvOk_startRev`
(`WatchRecv.lean:500-504`) says every event received for `w` has `modRev ≥ γw.lo`, and
`startLo` (`InvWatchStore.lean:237-238`) makes `γw.lo = startRev` for a nonzero start revision. So
the behavior is excluded by a proved result *in the verified model* — not an X, because the model
never runs `Restore`.

Where the invariant keeps it out:

- every live watcher has `lo ≤ minRev` in each population (`popFacts`, `InvWatchStore.lean:604-611`);
- an unsynced watcher additionally has `minRev < Lc.length` for a certified log `Lc`
  (`InvWatchStore.lean:607-608`), i.e. `minRev ≤ curRev`;
- `WsOk.st_flags` fixes `restore = false` for every watcher (`InvWatchStore.lean:340-342`).

Counterfactual on the pre-fix `syncWatchers` (`w.minRev = curRev + 1`): for a chosen unsynced
watcher, `lo ≤ minRev < Lc.length ≤ curRev + 1`, so the new `minRev = curRev + 1 ≥ lo` and every
post-state clause (`popFacts` synced: `lo ≤ minRev ≤ d`; `evsWf`) holds as with the fix — the
proof's step at line 374 already shows `minRev < curRev + 1` and takes that branch of `max`. The
existing spec therefore admits the buggy version: **F−**. The gap is not a weak postcondition of
`syncWatchers` but the scope of the watch invariant: it describes a store whose log only grows by
the store's own writes; the snapshot install that moves synced watchers back with future `minRev`
is outside it.

Had `Restore` been verified, the invariant would have to admit a restored unsynced watcher whose
`minRev` is above the log (the current unsynced clause fails for it), while keeping `lo ≤ minRev`
(which `watchRecvOk_startRev` needs). Against that invariant the pre-fix line breaks: `curRev + 1 <
lo = minRev` for a future watcher, so re-establishing `popFacts`' synced clause `lo ≤ minRev`
(`InvWatchStore.lean:605`) fails. So the bug is excluded by the existing *guarantee* once the scope
covers `Restore`: F+ conditional on the proposal below.

## Proposal

**`verify-watchable-restore`**: specify and prove `watchableStore.Restore` (and the snapshot case of
`store.Restore`) against `isWatchableStore`.

Statement sketch:

```
mvcc.watchableStore.Restore.spec :
  ∀ s st γ b L', {{ isWatchableStore s st γ ∗ watchWriter… ∗ snapshotBackend b L' ∗ ⌜σ.Lmu ≼ L'⌝ }}
    s.Restore(b)
  {{ err, RET err; err = nil → (the store's log is L') ∗ every formerly synced watcher unsynced
     with restore = true and its minRev unchanged }}
```

with the invariant generalized: `st_flags` allows `restore = true` for an unsynced watcher, whose
`popFacts` clause is `lo ≤ minRev ∧ d = minRev` without the `minRev < Lc.length` bound (and
`syncWatchers` re-proved over it, which is where the pre-fix line would fail). Cost: large. The
watcher part (the invariant clause, `Restore`'s loop over `synced.watchers`, re-proving
`syncWatchers`/`choose`) is a few hundred lines; the real cost is the store: `store.Restore` on a
backend with data (rebuilding the index, `restoreIntoIndex`, compaction state) is today a
fresh-backend-only trust boundary, and the model's log would need a "jump to a snapshot of a longer
committed log" step (the evLog/`idxCert` ghost state assumes the store's own writes). That is the
same extension a verified snapshot apply in etcdserver would need.

## Findings

None for `issues/`: the bug is fixed at the pin. No bug in this repository's specs.
