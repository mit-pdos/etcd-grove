# etcd-io/etcd#18679: Write txn shouldn't `End()` on a failure

- URL: https://github.com/etcd-io/etcd/issues/18679 (closed 2025-01-17; label `type/bug`).
  Offshoot of #18667 (`notes/bug-triage/etcd-18667.md`). No observed failure: a risk found by
  reading. Affected: `main` and 3.4/3.5 since #14149 (which added the early `End()` so that a
  read-only txn's timeout releases the locks).
- Fix: PR #18749 "Fix risk of a partial write txn being applied" (merge `38c27a4f8`,
  2024-10-24; backported).

What goes wrong (pre-fix `server/etcdserver/txn/txn.go`, `txn`): when `executeTxn` returns an
error on a write transaction, `txn` called `txnWrite.End()` and then `lg.Panic`. `End` of a write
transaction (`storeTxnWrite.End` → `watchableStoreTxnWrite.End`) bumps `currentRev` if anything
changed and unlocks the backend's batch transaction, so the operations that ran before the
failure are in the batch and may be committed to bbolt (the backend's periodic commit, or a
pending delete's commit) together with the consistent index the pre-commit hook writes. After
the panic and a restart, the member would skip the entry while holding half of it: a member
diverging from the others.

## Classification

**F− (fixed before the verified code); gap A-model (crashes), secondary C-scope.** The fix
`38c27a4f8` is an ancestor of the pin `107edf7e4` (at the pin `txn.go:84-95` panics with no
`End`). Counterfactually the spec admits the pre-fix code: `txn.spec` reaches the error branch
only for a read-only transaction (premise `nd = false → ro = true`, `Spec/.../etcdserver/txn/
txn.lean:66`; "the panicking branch is not reached", `:46`), and `Txn.specSole` (the apply
thread) requires a context that is never done (`mvcc.neverDone cd`, `Txn.lean:58`) and the run's
premises (`TxnPre`, `:60`), under which `executeTxn` cannot fail. So the early `End()` sits on a
branch the proof shows dead; and even if reached, what makes it harmful — a panic followed by a
restart that finds a partly applied entry on disk — is a crash, which nothing here models.

Source of verification states: the `Spec/`/`Proof/` files of `etcdserver/txn` (each linked
`theorem … wp_proof`); `verified.txt` was not produced.

## The counterfactual (step 5)

Pre-fix `txn`: `if err != nil { if isWrite { txnWrite.End(); lg.Panic(...) } else { lg.Error } }`.

1. *Write transaction.* `txn.spec`'s premise `(nd = false → ro = true ∧ lg ≠ null)` makes
   `nd = true` for a write, so `executeTxn.spec` gives only its success disjunct (its error
   disjunct carries `⌜nd = false⌝`, `executeTxn.lean`). The `if err != nil` branch is
   unreachable; the proof never looks at the `End()` call. The pre-fix code meets `txn.spec`
   unchanged.
2. *Where the premise comes from.* `Txn.specSole` assumes `neverDone cd` and `TxnPre log t`
   (`OpsOk`: every range of the run is at a revision the store can serve). In the real server
   the apply context is not cancelled; a range at a compacted or future revision is the one
   failure #18667 exhibited, closed at the pin by `checkTxn`'s range check, and modelled here only
   as a premise (`notes/bug-triage/etcd-18667.md`, proposal `txn-exact-check`).
3. *If the branch were reached.* The model has no outcome for a panic other than the program
   ending (`Logger.Panic` returns `PanicV`); no statement relates the backend's committed state at
   a panic to a later run. Whether `End` ran before the panic is invisible to every result,
   because results are about the running process: there is no restart to observe the partial
   entry.

So the property the fix restores — *an entry is applied to durable state entirely or not at
all, even when applying it panics* — is outside the specs (A-model: crashes; `notes/decisions.md`
and STATUS's apply units model no crash or restart).

## Proposal: `crash-restart-model` (existing), with a crash-free first step

The full statement needs a restart: after any crash, including a panic in the apply thread, the
backend's committed state equals the state after the entries up to its consistent index
(`cindex` the last entry applied *entirely*). Cost: large (the slug's existing estimate; Perennial's
Lean port has no crash semantics).

A cheaper step that would have caught this bug without crashes: give the apply path's specs a
**panic outcome** — `txn.spec`'s write case states, for the `lg.Panic` branch, that the
transaction is still pending (`txnWriteIs tw s γ trace false ilog pend'`, the batch lock held, no
`End`), i.e. "at a panic during apply nothing of the entry is committed and the consistent index
is not advanced". Under the present premises the branch is dead, so this needs the premises
weakened first (drop `OpsOk` for ranges, `txn-exact-check`), which makes the branch live. Small to
medium once `txn-exact-check` is done; it needs a way to state a postcondition at a panic (a
Perennial question: whether `wp` can carry a panic postcondition; record it if not).
