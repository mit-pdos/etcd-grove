# etcd-io/etcd#22480: rafthttp `peerStatus` latches inactive after the streams recover

- URL: https://github.com/etcd-io/etcd/issues/22480 (open; label `type/bug`; filed 2026-09-28).
  It is the root cause of #14523 (closed by the stale bot).
- Fix: none merged. Open PR #22481 "rafthttp: prevent peerStatus from latching inactive after
  stream recovery".

What goes wrong: each rafthttp `peer` shares one `*peerStatus` among its stream writers and
readers, its pipeline and its snapshot sender. All of them call `deactivate` on an I/O error, but
`activate` is called only when a stream (re)connects (`stream.go:263`, `:415`) or a pipeline or
snapshot send succeeds (`pipeline.go:118`, `snapshot_sender.go:127`). The pipeline is unused while
the stream writer works. Consider a pipeline `post` that started while the
stream was down and times out after the stream has re-attached and activated the status. It sets
`active = false` and `since = zero`, and nothing sets them back while the streams stay up.
`Transport.ActiveSince(id)` then reports the peer as never connected. As a result,
`etcd_network_active_peers` under-reports, and `mayRemoveMember`/`mayAddMember` refuse
reconfigurations with "unhealthy cluster".

## Classification

**O-pkg.** The bug is in `server/etcdserver/api/rafthttp` (`peer_status.go`, `pipeline.go`,
`snapshot_sender.go`, `stream.go`), present unchanged at the pin `107edf7e4`. rafthttp is
translated names-only (`verified.txt`: 105 functions, 0 verified, 33 translated). Its consumers
are also outside: `mayRemoveMember`/`mayAddMember` (`server.go:1602`, `:1404`) are not
translated. The verified helpers `isConnectedSince`/`numConnectedSince`/`isConnectedToQuorumSince`
(`util.go:28-90`) sit over the trust-boundary contract `rafthttp.isTransporter`
(`Proof/.../etcdserver/api/rafthttp/Defs.lean:31-35`), whose `ActiveSince` returns *some* time, so
`isConnectedSince.spec` returns any `Bool` (`Spec/.../etcdserver/isConnectedSince.lean`). Nothing
here says what "connected" means, so nothing could exclude a stale `false`.

Source of verification states: `/shared/etcd-grove-triage/coord/verified.txt`. Not in `issues/`
(the package is not translated with bodies).

## Proposal: `verify-rafthttp-peer-status` (new)

Translate `peerStatus` (`activate`/`deactivate`/`isActive`/`activeSince`, ~60 lines) and the
places that call them in `streamWriter.run`, `streamReader.run`, `pipeline.post`/`handle` and
`snapshotSender.send`. Give `peerStatus` a ghost record of the working streams and in-flight
sends, with the invariant

```lean
-- a peer whose stream writer or reader is attached is active, and `since` is no earlier than the
-- latest attachment
def peerStatusOk (σ : PeerStatusM) : Prop :=
  (σ.writerWorking ∨ σ.readerWorking) → σ.active ∧ σ.lastAttach ≤ σ.since
```

The buggy `deactivate` from a stale pipeline send breaks it (a working writer with
`active = false`). PR #22481's epoch check (ignore a failure older than `since`) restores it. Then
strengthen `rafthttp.isTransporter`'s `ActiveSince` to return the zero time only when no stream to
`id` is attached, so that `isConnectedSince` gets a meaningful post. Cost: medium to large.
`peer_status.go` itself is small, but `stream.go`'s goroutines and channels (~640 lines) need
translating to state "attached". The time comparison needs `time.Now` monotone, which is cheap.
This is related to, but not the same as, `verify-rafthttp-handlers` (the HTTP handlers,
`etcd-22440.md`).
