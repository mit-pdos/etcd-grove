# etcd-io/etcd#15498: Invalid db page layout

- URL: https://github.com/etcd-io/etcd/issues/15498 (closed as stale, not planned, 2025-06-21;
  `type/bug`, `priority/important-soon`, `stage/tracked`)
- Affected: v3.4.21. No reproduction and no db file. Maintainers' analysis of the dump
  (ahrtr): a branch item pointed to an old root page, and both meta pages pointed to the same
  root (`690`). Similar to etcd-io/bbolt#402. Hardware memory corruption was not excluded.
- Fix: none.

What goes wrong. etcd crash-loops at startup: `mvcc.restoreIntoIndex` reads the whole `key` bucket
and calls `bytesToRev` on every key. bbolt returned a key (`alarm`, 5 bytes) from another bucket's
page, because a branch page of `key` pointed into the bucket-root page. The slice of 8 bytes
panicked. At the pin, the same input makes `BytesToBucketKey` panic with "invalid revision length"
(`revision.go`, explicit check). The cause is a bbolt on-disk structure that bbolt's own invariants
forbid (a page reachable from two trees, or a stale root), from a bbolt bug, a memory stomp on the
mmap, or the disk.

## Classification

**O-pkg (bbolt internals); secondary A-model (memory and disk corruption) and A-axiom in form.**
bbolt is not translated: the backend proofs use it through the key-value axioms
`Spec/go_etcd_io/bbolt/*_kv.lean` (`Data` = bucket → key → value, `InvBbolt.lean:47-50`). Under
them, a read transaction returns exactly the committed contents of the named bucket (`rtxSnap tx D`,
`rBkt`). A key of another bucket inside `key` is a bbolt state those axioms do not allow, so the
verified etcd code above it cannot see it. The panicking reader is not verified in any case:
`restoreIntoIndex` is not translated, and `store.restore` is assumed only on an empty `key`
bucket (`Spec/.../mvcc/store__restore.lean`, `bucketView γ q ∅`). `BytesToRev.spec` requires
`revBytes r false ++ rest` with `rest.length ≤ 1`, so every verified caller must prove that the key
is well formed. The mvcc proofs do so from the ghost bucket view (`keyView`, `InvStore.lean:993`),
and that view is sound only if bbolt keeps its contract.

## Proposal: `bbolt-kv-contract` (new)

Prove the bbolt key-value axioms against bbolt's implementation, instead of assuming them. The
core is a page-level invariant: the pages reachable from the live meta page form disjoint trees
(one per bucket, inline buckets included), the freelist and pending pages are disjoint from every
page reachable from either meta page, and `Commit` writes only fresh pages before it flips the meta
page. `Tx.Bucket`/`Cursor` then return the abstract `Data` (`rBkt`), and a bucket's cursor never
yields another bucket's keys. Cost: large. bbolt's core (`tx.go`, `node.go`, `page.go`,
`freelist`, `cursor.go`, `bucket.go`) is roughly 5k lines, over mmap and `unsafe` page casts, which
Perennial's Goose cannot translate today: a Perennial proposal (an mmap/byte-array model of pages)
comes first. Memory corruption from hardware stays outside any proof. The issue's request, a
protected mode that verifies writes before they are persisted, is a runtime check, not this.

## Findings

None new. There is no confirmed bug in etcd's code, and nothing is present in translated code.
