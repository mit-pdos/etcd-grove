# etcd-io/etcd#22094: `closeRequireLeader` leaves an emptied keep-alive entry that is renewed forever

- URL: https://github.com/etcd-io/etcd/issues/22094 (open; labels `type/bug`, `stale`)
- Affected: every version with `closeRequireLeader` (2017 on); present at the pin.
- Fix: none merged. PR #22097 (closed), #22253 and #22291 (open) delete the entry when no
  subscriber remains. Companion bug in the same function: #22081 (`etcd-22081.md`).

What goes wrong: when every `KeepAlive` subscriber of a lease used `WithRequireLeader` and the
lease stream reports `ErrNoLeader`, `closeRequireLeader` (`client/v3/lease.go:383-418`) closes all
their channels and compacts `ka.chs`/`ka.ctxs` to length 0, but leaves `l.keepAlives[id]` (unlike
`keepAliveCtxCloser`, `:377`). `recvKeepAlive` refreshes `ka.deadline` on every answer (`:550`) but
advances `ka.nextKeepAlive` only inside the loop over `ka.chs` (`:563`), so `sendKeepAliveLoop`
(`:600`) sends a `LeaseKeepAliveRequest` for the lease every 500 ms, and `deadlineLoop` never
reaps it. The lease is kept alive until the client closes, with no local subscriber. Reproduced
at the pin (test in `issues/etcd-lease-requireleader-orphan-entry.md`).

## Classification

**O-fn (secondary C-perf / C-live).** The buggy code is at the pin, in `client/v3`'s lessor, which
is not translated (`Code/go_etcd_io/etcd/client/v3.toml`: no `lease.go` function), in a package
whose KV, watch and retry clients are verified. The verified caller `concurrency.Session` assumes
`isEtcdLease`, which says nothing about renewal or expiry ("Leases without liveness",
`notes/decisions.md`), so a lease renewed forever after the session's `Done` fired is admitted.

Source of verification states: as in `etcd-22081.md` (no `verified.txt`; the `.toml`, `Spec/`,
`Proof/` files).

## Does the spec exclude it?

Observed, as the verified code sees it: a session created with
`WithContext(WithRequireLeader(ctx))` loses its leader; its keep-alive channel closes, its
goroutine closes `donec` (`Done` fires), but the lease and the session's keys (a lock or election
key) stay, renewed by the client; contenders in `Mutex.Lock` wait until the client closes.

- `isEtcdLease`'s `KeepAlive` (`InvEtcdTxn.lean:1135-1140`): a channel with `isChanAny`; nothing
  about what the client does afterwards for that lease. Expiry and revocation are "a step of
  etcd's history like any other (`EtcdStep`)" (`decisions.md` "Leases without liveness"), so
  "the key is still there long after `Done`" is a history the model allows.
- `Session.Done`'s documentation ("closes when the lease is orphaned, expires, or is otherwise no
  longer being refreshed", `session.go:95-96`) is contradicted, but no spec states it:
  `sessionDone`/`sessionDoneChan` only say `donec` is closed.
- `mutex_exclusion`/`election_exclusion` hold (the stale key keeps excluding others, which is the
  safe direction); the observed harm is progress (contenders wait) and resources (a keep-alive
  stream per orphaned lease): C-live / C-perf, out of reach of partial correctness.

## Proposal: `verify-client-lessor`

The same as `etcd-22081.md`. The conjunct of the lessor's lock invariant that catches this bug:
`l.keepAlives[id] = some ka → ka.chs ≠ []` (with `len ka.chs = len ka.ctxs`), broken at the end
of `closeRequireLeader` when every subscriber required a leader. As a safety stand-in for "the
client stops renewing a lease nobody keeps alive", `sendKeepAliveLoop`'s spec: every id it sends
has a live registration (a `kaReg` token in the ghost map). Making `Session.Done` match its
documentation additionally needs a `Done → no live registration for the session's lease`
statement in `isSession` (small once the lessor is verified). Cost: as for #22081 (medium to
large, shared).
