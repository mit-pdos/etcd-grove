# etcd-io/etcd#16380: `checkIntervals` will not validate correctly in certain nested txn scenarios

- URL: https://github.com/etcd-io/etcd/issues/16380 (closed 2025-07-17, not planned/stale;
  labels `type/bug`, `backport/v3.4`, `backport/v3.5`, `stale`)
- Affected: `main` and the release branches; present at the pin.
- Fix: none merged. PR #16395 (closed unmerged); ahrtr confirmed the bug, then found the fix too
  costly and questioned the expected semantics.

What goes wrong: `v3rpc.checkIntervals` (`server/etcdserver/api/v3rpc/key.go`, lines 258-297 at
the pin) checks each nested transaction's puts against `dels` *as collected so far*, and unions
that nested transaction's deletes into `dels` only afterwards. A put in a nested transaction is
therefore never checked against the delete of a *later* sibling nested transaction:
`Then(Txn(Then(Put(k))), Txn(Then(Delete(k))))` passes, the reversed order and the flat
`Then(Put(k), Delete(k))` are rejected with `ErrGRPCDuplicateKey`. The accepted transaction writes
`k` twice in one revision (a put, then a tombstone).

## Classification

**A-pre (premise of the verified check's result), found by the proof.** This is our finding
`issues/etcd-txn-check-intervals-sibling.md` (it already links #16380). `checkIntervals` is
verified with an exact functional spec (`ivCheck`), which states the code's order and so admits
the behavior; the property the rest of the proof uses, "a branch that passes the checks writes
each key at most once" (`intervalsOkCheckStmt`, `checkIntervals_nodup`), is proved only under the
premise `ReqOp.siblingSafeL` (no nested put deleted by a later sibling), which the issue's request
violates. Nothing discharges the premise for an arbitrary client: the clients that rely on
one-write-per-key (the client watch's `srvNoDupKeys`) take it as a premise about other writers.

Source of verification states: `verified.txt` was not produced; states read from `Spec/`,
`Proof/` and the v3rpc `Link.lean`.

## The argument (step 4)

1. Observed: request `ops = [txn([put k]), txn([del k])]`; `checkIntervals` returns `nil`; the
   apply writes `(R,0)` put `k` and `(R,1)` tombstone `k`.
2. `checkIntervals.spec` returns whatever `ivCheck us` computes; `ivCheck` is the code's
   algorithm, so `some (puts, ds)` for this `ops`: the spec admits it (it is meant to: an exact
   spec of a check).
3. The guarantee is `v3rpc.intervalsOkCheckStmt` (`Proof/.../v3rpc/Defs.lean:353-358`) and its
   exported form `checkIntervals_nodup` (`Proof/.../v3rpc/Results.lean:68-75`): distinct put keys
   and no put key deleted, under `ReqOp.noFromKeyDelL ops` and **`ReqOp.siblingSafeL ops`**
   (`Defs.lean:333-339`; `sibOk u v`: a nested transaction `u`'s puts are not in a later sibling
   `v`'s deletes). The issue's `ops` has `sibOk (txn [put k]) (txn [del k]) = False`: the premise
   fails, so the guarantee says nothing (and is false without it, the reason it is there).
4. Downstream: the double write is modeled faithfully by `txn.Txn`'s spec, so the server's specs
   hold; the visible consequence is the watch (a PUT event of `k` at `R` whose value is not in the
   state at `R`), which the client watch excludes only by its premise `srvNoDupKeys`
   (`Proof/go_etcd_io/etcd/client/v3/InvWatch.lean:258`): another A-pre, on other writers.

## Proposal: `check-intervals-final-dels`

Fix the check in the fork (check every nested transaction's puts against the level's final
`dels`: a second pass after the unions, as the level's own puts already are; ahrtr's or bsbds'
diff in the thread), re-translate, and drop `siblingSafeL` from `intervalsOkCheckStmt` /
`check_gives_nodup`:

```lean
theorem check_gives_nodup' (n : Int) (ops : List ReqOp) (tops : List TxnOp) (s0 s : List EtcdKv) (r : w64) :
    ReqOp.toTxnOps ops = some tops → opsCheck n ops = none → ReqOp.noFromKeyDelL ops →
    intervalsOk ops → Good (txn.srvOps s0 r s tops).1 ...   -- no siblingSafeL
```

Cost: small. `ivCheck` and `checkIntervals.wp_proof` change by one loop; `CheckNodup.lean`'s
sibling case (`:544`, "a later sibling's delete: `siblingSafe`") becomes the level-deletes case
already proved for the level's own puts. Without an upstream fix, the alternative is to weaken
what the watch consumers assume (`srvNoDupKeys` → events of a revision applied in order), larger.
