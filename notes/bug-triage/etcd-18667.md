# etcd-io/etcd#18667: Specifying a revision for a range request in a transaction may cause data inconsistency

- URL: https://github.com/etcd-io/etcd/issues/18667 (closed 2026-05-23)
- Affected: every version up to the fix (3.4.x, 3.5.x, `main`), per the report.
- Fix: PR #21432 (merge `bb5725264`, branch commit `fbba4f46e`), "Fix data inconsistency when a
  transaction includes a range request with a specified revision". Related: #18674 (the apply
  context never done), #18679 (txn side-effect symmetry, opened from this thread), #20454 (e2e test).

What goes wrong (pre-fix code): `apply.Apply` (`server/etcdserver/apply/apply.go`) called
`removeNeedlessRangeReqs(raftReq.Txn)` when no waiter was registered for the entry
(`needResult == false`, i.e. on every member but the one the client is connected to), deleting the
range operations from the transaction's `Success`/`Failure` before dispatch. `txn.checkTxn` runs
`checkRange` on each range of the path, which fails for a revision that is compacted
(`ErrCompacted`) or in the future (`ErrFutureRev`). So for `Then(Put(k2,foo), Get(k1, rev=10))`
after compaction at 21, the proposer's check fails and it rejects the transaction, while the other
members check the stripped transaction, pass, and commit the put: the members' stores diverge.

## Classification

**F (fixed before the verified code); counterfactual F−.** The fix `bb5725264` is an ancestor of
the etcd pin `107edf7e4` (`git merge-base --is-ancestor`: yes; fork point `f061acd09`, 2026-10-08):
the pinned `apply.Apply` no longer strips ranges, it sets `SkipRangeExecution` and `executeTxn`
skips only the range's execution, never `checkTxn`. Counterfactually the existing specs **admit**
the buggy version: the apply relation's transaction case lets a non-plain transaction be rejected
unconditionally, and the transactions that trigger the bug (a get at a revision ≠ 0) are exactly
the non-plain ones, which the server's and client's `Txn` specs exclude by the premise `txnPlain`.
The gap is therefore a scope choice (C-scope: determinism of the apply step proved for plain
transactions only), not an unsound proof.

Source of verification states: the inventory `verified.txt` was not yet produced; states read
directly from `Proof/**` (each a `theorem … wp_proof`, no `sorry`, no `axiom`) and
`Proof/go_etcd_io/etcd/server/v3/etcdserver/apply/Link.lean`.

## The counterfactual (step 5)

Take the pre-fix `apply.Apply`: on a member with `needResult = false`, dispatch sees `t'` = `t`
with every get removed (nested ones too, `removeNeedlessRangeReqs` only strips the top level of
each branch; nested `RequestTxn` keep theirs). Would `apply.Apply.spec` (`Spec/…/apply/Apply.lean`)
still be provable?

- Its KV conclusion is `applyStep rq v3 x x' out` of the *decoded* request `rq` (with `t`), via
  `dispatchStep` → `chainStep backendStep` (`apply/InvUber.lean:68-71, 113-118`).
- `backendStep`'s `.txn` case (`apply/Chain.lean:198-218`) has two disjuncts:
  - rejected, with only `txn.txnPlain t → ¬ PathsIgnOk …` (lines 210-212): for a **non-plain** `t`
    a rejection is allowed whatever the state;
  - applied, committing `srvRunTxn … t` with `PathsIgnOk` of the path (lines 213-218). It does not
    require `checkTxn` to pass.
- The proposer (full `t`, `checkRange` fails, `checkRangeErr`'s `ErrCompacted`/`ErrFutureRev`
  case, `txn/InvRange.lean:86-93`) is in the first disjunct. The followers (`t'`) commit
  `srvRunTxn … t'`, whose changes equal `t`'s (gets write nothing and do not change the compare
  verdicts or the puts' previous key-values), with `PathsIgnOk` unchanged (it is about puts): the
  second disjunct. Both satisfy `applyStep rq`; the divergence is admitted.
- For a **plain** `t` (`txnPlain`, `txn/TxnRun.lean:543-558`: every get at revision `0`)
  `checkRange` cannot fail (`checkRangeErr`'s first case), so stripping gets changes neither
  outcome: the buggy code is correct there, and the determinism lemmas (`applyStep_plain` etc.,
  `notes/decisions.md` "Making the apply relation exact") would still hold.
- The only place the trigger could matter end to end, the abstract state `etcdKV γ σ` stepped by
  `kvOpStep` from the committed log, is reached only by requests with `reqPropOk`/`txnPermit`
  (`etcdserver/InvRequest.lean:1085-1086`, `KVModelDefs.lean:56-63`: `plainReq` of a txn is
  `txnPlain`), so a writing transaction with a get at a revision ≠ 0 has no server or client spec
  at all.

Also out of the model: compaction (`dispatchOk`; mvcc's first revision is `-1`, so `ErrCompacted`
is unreachable in `checkRangeErr`). The report's compaction trigger is thus doubly outside; but a
get at a *future* revision (`ErrFutureRev`) triggers the same divergence with no compaction, and
the specs admit that too, for the reason above. (Pre-fix provability in detail, e.g. the
response-shape clause `dispatchResult … skip` on a response with the ranges removed, would need a
proof attempt; it bears on the waived response, not on the KV divergence.)

So: **F−**. The spec that would have caught it is a per-entry determinism for *all* transactions.

## Proposal: `txn-exact-check` (with `kv-compaction-model` for the reported trigger)

Statement sketch (`apply/Chain.lean`, `KVModelDefs.lean`):

```lean
-- a pure check, from checkRangeErr / checkPut / checkLease along the path
def txn.checkTxnOk (log : mvcc.Log) (t : TxnModel) : Prop := …
-- backendStep's .txn case made exact for every transaction
| .txn => ∃ t, rq.txn = some t ∧
    ((o = .rejected .backend ∧ ¬ txn.checkTxnOk log t) ∨
     (o = .applied (mvcc.commitLog log (txn.srvRunTxn … t).2.1) false ∧ txn.checkTxnOk log t ∧ …))
-- and txnPlain widened: gets at any revision (checkRange is a function of rev and log)
```

Then `applyStep_plain`'s determinism (the member's step a function of the entry and the state,
independent of `needResult`/`SkipRangeExecution`) covers transactions with revisioned gets, and the
pre-fix `apply.Apply` fails it (follower applies, proposer rejects, same state). Cost: moderate —
`checkTxn.spec` and `checkRange.spec` are already exact per operation (`checkRangeErr`), so it is a
pure `checkTxnOk` with its lemma from `checkTxn.spec`, the `backendStep` case, and re-running the
T2 consumers (≈15 proofs: `txn.Txn.specSole`, backend/auth `Txn`, `InvApplier`, `InvRequest`,
`ServerKVTxn`, …), plus widening `txnPlain`/`txnPermit` for the client contracts. For the
compaction trigger itself, `kv-compaction-model`: a compacted revision in `KVState` and
`checkRangeErr`'s `ErrCompacted` iff `rev < compactRev`, with compaction requests in `kvOpStep` —
larger (the mvcc `Compact` spec, and the open `NoDelPutAt` gap, `notes/STATUS.md` "The compaction
premise `NoDelPutAt` is not met by the gRPC checks").

A cluster-level statement (all members' stores equal at equal applied indices) is implied today
only through the shared σ, which is a function of the committed log for plain requests; it is not
stated, which is why the per-member gap is only visible in `backendStep`.
