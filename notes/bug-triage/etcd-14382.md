# etcd-io/etcd#14382: etcd fails to start after `alarm list` and a power off/on

- URL: https://github.com/etcd-io/etcd/issues/14382 (closed 2022-09-05; label `type/bug`)
- Affected: etcd 3.5.3–3.5.4 and `main` of that time. The regression came from #13854/#13908
  (3.5.3), which made the deferred consistent-index update conditional.
- Fix: PR #14419 "Move consistent_index forward when executing alarmList operation" (commit
  `cc840336f`, merge `3dc5348d9`, 2022-09-05); backported to 3.5 as #14429.
- Same root cause as etcd-io/etcd#21636 (its report: `etcd-21636.md`; there the no-write entry is
  a repeated `Alarm{ACTIVATE, NOSPACE}`, here `Alarm{GET}`).

What goes wrong (pre-fix code). `etcdctl endpoint health` (3.5) runs `alarm list`, which goes
through raft as an `Alarm{GET}` entry. Pre-fix `applyEntryNormal` ran its deferred
`SetConsistentIndex(e.Index, e.Term)` only if the request was not applied to v3, or was applied
with an error (`!applyV3Performed || (ar != nil && ar.Err != nil)`). `applierV3backend.Alarm`'s
`GET` reads `AlarmStore.Get` (an in-memory map). It never takes the batch lock, so the post-lock
hook does not run either. The consistent index stays behind the applied index. A disk snapshot
(`snapshot-count`) is then taken at the applied index. It commits a db whose `consistent_index`
is below the snapshot index. After `kill -9`, bootstrap sees `snapshot index > consistent_index`.
It concludes the member crashed while receiving a leader snapshot, looks for `<index>.snap.db`,
and panics because the file is missing.

## Classification

**F+ (fixed before the verified code; the spec excludes the buggy version). Secondary:
O-fn/A-model for the restart.** The fix is an ancestor of the pin `107edf7e4` (`git
merge-base --is-ancestor 3dc5348d9 107edf7e4`: yes). At the pin the deferred update runs whenever
`ConsistentIndex() < e.Index` (`server/etcdserver/server.go:1941-1949`). The pre-fix condition
cannot establish `applyEntryNormal.spec`'s postcondition that `ci` is the entry's index. That
postcondition, though, is the only thing excluding the bug. The loop-level relation `loopOk` and
the snapshot contract admit `ci < applied`.

Source of verification states: `verified.txt` (`etc/verified-code.py`, at `d606c9cac`).

## The counterfactual (step 5)

Put the pre-fix defer into the pin's `applyEntryNormal` and follow its `v3` case:

- `apply.Apply.spec` returns `(if v3 then iprop(Post ∨ Pre) else Pre)` together with
  `resultErrOk ar` (`Spec/.../apply/Apply.lean:72`). `Post`: the hook ran (`ci := i`,
  `hook_set_au`, `InvApply.lean`). `Pre`: no backend write. Nothing ties the disjunct to `ar.Err`.
  For `GET`, `applierV3backend.Alarm` returns `mPost … Pre Post` with no error
  (`applierV3backend__Alarm.lean`). Its `GET` branch writes nothing, so the `Pre` branch with
  `ar.Err = nil` is reachable: exactly this bug.
- In that branch the protocol state becomes `p := i` (`skip_done`) with `k` unchanged. The pre-fix
  defer skips `ci_advance_au`, so the postcondition `applyThread γ ⟨m.index, m.index, eff, false⟩`
  (`EtcdServer__applyEntryNormal.lean`, the `v3` case; first field `k` = the consistent index)
  cannot be proved. The proof breaks at the deferred function's `if`. **F+.**

What carries the weight (the same caveat as `etcd-21636.md`): `consInv`'s `eff ≤ ci ≤ p` and
`loopOk` (`p = max(ciEff k, a)`, `InvApplier.lean:97`) both hold with `ci < p`. The post of
`applyEntries`/`applyAll` allows `ciEff γ st'.k = ciEff γ st.k` as one disjunct
(`EtcdServer__applyEntries.lean:71-72`). The assumed `EtcdServer.snapshot.spec` needs only
`loopOk` and promises nothing about the committed `ci`. So the property the restart depends on is
not stated anywhere: "the db committed before `SaveSnap` stores `ci ≥` the snapshot index", which
`RecoverSnapshotBackend`'s comment calls the invariant. A re-proof on the buggy code could weaken
`applyEntryNormal`'s postcondition and still go through every consumer. The restart failure itself
also needs crashes (A-model) and the untranslated bootstrap (O-fn).

## Proposal: `server-snapshot-ci-latest` (existing, from `etcd-21636.md`)

Add `uint.Z a ≤ uint.Z (ciEff γ st.k)` to `loopOk`. Then prove `EtcdServer.snapshot` (37 lines,
now an axiom): its `KV().Commit()` saves `ci` (`commit_save_au`), so
`verifyConsistentIndexIsLatest` never fires, and the db committed before `SaveSnap` stores an
index `≥ ep.appliedi`. With that conjunct the `ci = ci` disjunct of `applyEntries`'s post goes,
and the buggy defer fails at the loop level, not only in one postcondition. Cost: small to
medium. It needs specs for `raftStorage.CreateSnapshot` (raft's, proved) and `storage.SaveSnap`
(trust boundary).

None new: the bug is not in the pinned code, and there is no bug in this repository's specs.
