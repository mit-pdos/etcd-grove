# etcd-io/etcd#9956: 3.3.7 "panic: send on closed channel"

- URL: https://github.com/etcd-io/etcd/issues/9956 (closed 2019-08-12; label `type/bug`).
  Reported on v3.3.7, later also on 3.2.17 (Ubuntu's package).
- Fix: in grpc-go, PR grpc/grpc-go#2695 "transport: do not close channel that can lead to panic"
  (`272a4b69f`, 2019-03-19, released in v1.20.0). etcd picked it up via PR #10624 (closed) and the
  release-3.3 bumps #10952/#10984 (grpc 1.23, released in v3.3.17). `main` has used grpc ≥ 1.20
  since 2019, and the pin uses v1.84.0.

What goes wrong: the same family as `etcd-8904.md`, a different race in grpc's
`serverHandlerTransport` (used by etcd's `grpcServer.ServeHTTP` path). After a stream handler
returns, grpc ≤ 1.19 closed the transport's `writes` channel, and a later `do(fn)` from a goroutine
the handler left running panicked. There are two traces in the thread. The original is
`LeaseServer.leaseKeepAlive` → `Send` → `serverHandlerTransport.Write` → `do`. A later comment has
`serverWatchStream.recvLoop` → `Recv` → `serverStream.RecvMsg`, whose error path calls
`WriteStatus` → `do`. In both, the handler (`LeaseKeepAlive`, `watchServer.Watch`) had already
returned while its goroutine still used the stream.

## Classification

**F (fixed before the verified code); counterfactual F−, gap A-axiom.** The buggy code is
grpc ≤ 1.19, and the pin builds against grpc v1.84.0 (`server/go.mod`), so it is not in the
verified setting. The etcd pattern is unchanged at the pin: `watchServer.Watch` returns while
`recvLoop` may still call `Recv` (`watch.go:163`ff), and `LeaseKeepAlive` returns on context
cancellation while `leaseKeepAlive` may still `Send` (`lease.go:93-108`). It is correct only
because grpc ≥ 1.20 tolerates it. The watch half of the path is verified: `watchServer.Watch`,
`serverWatchStream.recvLoop`/`sendLoop` (`verified.txt`, sorry-free). They rest on the raw
server-stream contract `srvRawStreamIs` (`Proof/google_golang_org/grpc/InvGrpcStream.lean:313-336`,
from the axiom `grpc.serveStream`, `:936`): `RecvMsg`/`SendMsg` return nil, EOF or a stream error,
at any time, including after the handler returned ("`Watch` returns while its receive loop may be
blocked"). Against grpc ≤ 1.19's `serverHandlerTransport`, that postulate is false, so the
verified watch server would have admitted this panic through a false axiom. **A-axiom**, not F+.
The lease half is O-fn (`lease.go` not translated), as in `etcd-8904.md`.

At the pinned grpc the postulate is not known to be false. This is not a soundness alert, but the
axiom's truth depends on the grpc version, which nothing here records.

Source of verification states: `/shared/etcd-grove-triage/coord/verified.txt`.

## Proposal: `verify-lease-keepalive-stream` (as `etcd-8904.md`), plus the axiom's version

- The lease half: translate and prove `LeaseKeepAlive`/`leaseKeepAlive` over the stream wire
  (medium).
- The watch half is already verified. The remaining action is in the trust base: record in
  `InvGrpcStream.lean`'s header (the transport's claims) and in `notes/decisions.md` that
  "a stream's methods return after the handler has returned" is read against grpc ≥ 1.20
  (grpc/grpc-go#2695) for the `ServeHTTP` transport, and ≥ 1.7.4 (#1687) for the status race.
  A check in `etc/` could compare `server/go.mod`'s grpc version with that bound. Cost: small.
