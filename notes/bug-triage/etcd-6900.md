# etcd-io/etcd#6900: Panic (nil pointer dereference) in gRPCWatcher

- URL: https://github.com/etcd-io/etcd/issues/6900 (closed 2016-12-07; labels `type/bug`,
  `area/clientv3`).
- Affected: `clientv3/naming` (the grpc-v1 naming resolver) of etcd 3.1-rc, running against an
  etcd 3.0.9 server. A 3.0 server ignores `prev_kv`.
- Fix: none. Closed once the reporter confirmed that a ≥ 3.0.15 server returns `PrevKv`. The
  resolver was "alpha/mostly broken for 3.0". The dereference stayed in the code until the package
  was deleted in `a836a8045` ("Get rid of legacy client/v3/naming API", 2021-01-21).

What goes wrong. `gRPCWatcher.Next` (`clientv3/naming/grpc.go:96`) watches its target with
`WithPrevKV` and, for a `DELETE` event, reads `e.PrevKv.Value`. A server that does not fill
`PrevKv` sends `nil` there, so service B panics when service A deregisters.

## Classification

**F (the code was replaced before the pin), O-pkg.** `a836a8045`, which deleted `gRPCWatcher`, is
an ancestor of the etcd pin `107edf7e4`. Its replacement, `client/v3/naming/endpoints`
(`endpoints_impl.go:159-161`), does not read `PrevKv` for a delete. Neither the old nor the new
naming package is translated (`Code/go_etcd_io/etcd/client/v3/` has no `naming`). Counterfactually
the specs could not have excluded it. The panic is in an untranslated caller, and the server half
(whether `PrevKv` is filled) is excluded from the watch server's proof by a premise: `watchReqOk`
requires `c.prevKv = false` for every create request
(`Proof/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/InvWatchStream.lean:154-155`; the header
`:143-145`: "the send loop's `PrevKv` write and the store read behind it are not modeled").

## Code path

| Go function | State |
|---|---|
| `clientv3/naming.gRPCWatcher.Next` | removed before the pin (`a836a8045`), never translated |
| `client/v3.watcher.Watch` with `WithPrevKV` → `watchRequest.toPB` | verified (W-C), but with `prevKV` the server side is outside the proof |
| server `serverWatchStream.sendLoop`, the `needPrevKV` block (`v3rpc/watch.go:446-456` at the pin) | translated; verified only under `watchReqOk` (`prevKv = false`), so this block is dead in the proof |

## Note on the class at the pin

`PrevKv` can still be `nil` on a modern server. `sendLoop` fills it only `if err == nil &&
len(r.KVs) != 0` after a `Range` at `ModRevision - 1` (`watch.go:451-455`). If that revision is
compacted between the event and the send, the event goes out with `PrevKv == nil` and no error. Any
client that dereferences `PrevKv` on a delete (the pattern of this bug) can therefore still panic.
This is documented: `rpc.proto:809-810` says "If the previous KV is already compacted, nothing will
be returned". So it is a caller's obligation, not an etcd bug, and no `issues/` file.

## Proposal: `watch-prevkv`

Lift the `prevKv = false` restriction of `watchReqOk`. The send loop's spec would state that, for a
watch created with `prev_kv`, each non-create event's `PrevKv` is the key's value at
`ModRevision - 1` in the log, or `nil` only when that revision is at or below the compaction
revision (or the key did not exist). That turns `rpc.proto`'s sentence into a stated outcome,
which client-side proofs must then handle. Cost: medium. It needs the `Range` call of `sendLoop` under `watchReader`, the
per-watch `prevKV` map in `swsMu`'s invariant (now empty by premise), and the store under compaction
(`watch-under-compaction`) for the `nil` case. This bug's own code (the resolver) is gone, so the
proposal guards the class, not this instance.
