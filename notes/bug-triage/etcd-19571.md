# etcd-io/etcd#19571: [release-3.4] consistent index not persisted when committing a member deletion

- URL: https://github.com/etcd-io/etcd/issues/19571 (closed 2025-05-05, won't fix; labels
  `type/bug`, `help wanted`)
- Affected: release-3.4 only (the report says so). It was introduced by #17238 ("[3.4] Fix delete
  inconsistencies in read buffer", `6caef6ca4`, release-3.4), which force-commits the backend
  after deleting a member. There is no fix: the maintainer left it because 3.4 is near its end of
  support and the impact is minor.
- What goes wrong (3.4). In 3.4 the consistent index reaches the backend only through mvcc's write
  transaction (`saveIndex` at the end of a `TxnWrite`, and `KV().Commit()`). A conf-change removal
  deletes the member from the membership bucket and `ForceCommit`s. That persists the deletion
  without the entry's index. After a restart (or an upgrade to 3.5) the conf change is
  re-applied to v3, although it was already applied. The membership data is not mvcc data, so this
  is mostly harmless. It broke 3.5's `TestDowngradeUpgradeClusterOf3` once a v2/v3 membership
  check was added (#19563).

## Classification

**F (release-branch-only; `main` replaced the code). Counterfactual: the violated property is a
trust-boundary contract here (`applyConfChange.spec`), so F+ once that axiom is proved; at the pin
it is assumed, not checked.** On `main` (and at the pin `107edf7e4`), every backend commit runs the
pre-commit hook `BackendHooks.OnPreCommitUnsafe`, and the hook saves the consistent index
(`ci.UnsafeSave`, proved: STATUS units 7–8). Membership writes take `LockInsideApply`
(`server/storage/schema/membership.go:58,77`), so the post-lock hook sets `ci := i` before the
write. A commit therefore cannot persist the deletion without the index.

Source of verification states: `verified.txt`.

## The counterfactual (step 5)

The property 3.4 breaks is the apply protocol's commit rule: a commit persists no entry's effects
above the index it saves (`commit_save_au`, `InvApply.lean:472`; "eff ≤ ci" at every commit).
3.4's `ForceCommit` persists entry `i`'s membership write while the stored index is `< i`.

In this repository that rule is discharged for conf changes by an axiom.
`EtcdServer.applyConfChange.spec` says that with `v3` "its writes to the backend happen in one
critical section of the batch lock, after the hook", or else none happen and it calls
`SetConsistentIndex(i, t)`; its postcondition is `Post ∨ Adv` (`EtcdServer__applyConfChange.lean:
26-38, 55`). 3.4's code does not meet that contract: the write happens outside the hook protocol.
Had 3.4 been the verified code, then:

- the proved part (the apply loop, the hook, the commit) would still go through, because it trusts
  the contract. In that sense this is **F−** at the pin as it stands. An axiom falsified by the
  code is the A-axiom case, and the bug would have been missed;
- a proof of `applyConfChange` and of membership's backend writers would fail at the delete. That
  is the **F+** the proposal buys.

The same axiom also states the fix of the related 3.5 bug class: the validation-failure branch's
direct `SetConsistentIndex` (server.go:2009-2014), which is its `Adv` case.

## Proposal: `verify-apply-conf-change`

Replace the axiom `EtcdServer.applyConfChange.wp_proof` with a proof. Translate
`membership.RaftCluster`'s `ValidateConfigurationChange`, `AddMember`, `RemoveMember`,
`PromoteMember`, `UpdateRaftAttributes` and `membershipBackend`'s writers
(`MustSaveMemberToBackend`, `MustDeleteMemberFromBackend`: `LockInsideApply`, then puts or deletes
on the `members`/`members_removed` buckets) with bodies. Each writer then meets
`cPre b P f Pre Q Post` (the shape `isCluster`'s `SetVersion` already has,
`apply/Contracts.lean`), and `applyConfChange.spec` follows. Cost: medium. About 300 Go lines
(`membership/cluster.go` and `schema/membership.go`), plus the v2 store's membership mirror as a
names-only boundary and `json.Unmarshal` of the context as an axiom. It is the same work that
`transport-tracks-confstate` and any membership-consistency result would need.
