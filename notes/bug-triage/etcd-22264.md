# etcd-io/etcd#22264: syncWatchers rescans the whole backlog on every pass, stalling the apply loop

- URL: https://github.com/etcd-io/etcd/issues/22264 (open; label `type/bug`).
- Affected: 3.5.21, and still present in 3.6.14, 3.7.1 and `main` (`ee043b3`). The reporter's
  reproduction is a unit test of package `mvcc` that drives `syncWatchers` by hand. Recovering one
  watcher that is 20,000 revisions behind reads 210,001 revisions to deliver 20,000.
- Fix: none merged. Open PRs: #22265 ("mvcc: bound syncWatchers scan to deliverable revisions"),
  #22304 ("storage/mvcc: bound the syncWatchers scan to watchBatchMaxRevs"), #22594 ("server:
  bound syncWatchers backend scan by entry count"). A comment reports that on 3.6.13 with a bounded
  scan, the per-pass quota of 1000 revisions still caps catch-up at about 10k rev/s. Earlier related
  reports: #16839 and #18109, and a reverted cache, `562f4af`.

What goes wrong. On every pass, `watchableStore.syncWatchers` (`server/storage/mvcc/
watchable_store.go:347-416` at the pin) holds `s.mu` and reads the backend from the chosen
watchers' least `minRev` to `curRev+1` (`rangeEvents`, `:366`, a full `UnsafeRange` of the key
bucket, `:432`). It then hands each watcher at most `watchBatchMaxRevs = 1000` distinct revisions
(`eventBatch.add`, `watcher_group.go:39-62`, `moreRev`), and the watcher stays unsynced from
`moreRev` (`:386-402`). A watcher `N` revisions behind therefore costs about `N/1000` passes, each
reading the whole remaining backlog: `O(N²/1000)` revisions read. Each pass holds `s.mu`, which
`watchableStoreTxnWrite.End` needs to publish its events, so writes stall during recovery (more
than 90% of the time in the reporter's Kubernetes incident).

## Classification

**C-perf (secondary C-live: a watcher whose backlog grows faster than 1000 revisions per pass
never catches up).** The buggy code is in the pin (no fix merged; lines quoted above) and is
verified with no `sorry` or `axiom`. The premises hold: the reproduction uses an uncompacted store,
which is the specs' `crevFrozen` setting. Every spec on the path is a partial-correctness statement
about *which* events are returned and delivered, and none about how much is read or how long `s.mu`
is held. The quadratic read is not merely admitted by the spec, it is *required* by it:
`rangeEvents.spec` returns all events of `[minRev, maxRev)`, and `syncWatchers` calls it with
`maxRev = curRev + 1`.

Source of the verification states: the proof files and
`Proof/go_etcd_io/etcd/server/v3/storage/mvcc/Link.lean` (`verified.txt` was not produced; no
`sorry` or `axiom` in the files below).

## The argument (step 4)

1. Observed. There is one unsynced watcher with `minRev = m` and `curRev = c ≫ m + 1000`, and the
   store is not compacted. Pass `k` calls `rangeEvents(m_k, c+1)`, which reads `c + 1 - m_k`
   revisions, and leaves the watcher unsynced with `m_{k+1} = moreRev ≈ m_k + 1000`. Nothing else
   goes wrong: the events delivered are right and in order, and none is lost.
2. Premises. `syncWatchers.spec` needs `isWatchableStore` and `watchReader` (the loop's reader
   slots, which `syncWatchersLoop` owns), and `rangeEvents.spec` needs `crevFrozen` and `0 ≤ minRev
   ≤ maxRev ≤ log.length`. All hold in the reproduction (a fresh `newWatchableStore`, no
   compaction).
3. Assumptions. The backend read is `isKeyBackendG`'s `UnsafeRange`. Its cost is not modeled, and
   no axiom is involved in the behavior.
4. Postcondition. `rangeEvents.spec` (`rangeEvents.lean:32-53`) returns exactly
   `(logEvents log minRev maxRev).filter (wgCovers W ·.kv.key)`. The full window is in the
   postcondition. `syncWatchers.spec` (`watchableStore__syncWatchers.lean`, docstring) says that a
   watcher with events "gets them in one response (all of them, or under the cap of
   `watchBatchMaxRevs` revisions those below the first revision left out, staying unsynced from
   there)". That is exactly the observed delivery. The spec says nothing about the size of the
   window read or the time `s.mu` is held, and neither does any spec in Perennial's model, which has
   no notion of cost. A watcher that stays behind forever is not excluded either:
   `syncWatchersLoop` is specified as partial correctness, and the watcher stays in `unsynced`,
   which is a legal state. So the spec admits the behavior → **C-perf**.

The fix PRs change the window. #22304 and #22265 shrink `maxRev`, so `rangeEvents` would be called
on a smaller window and the existing `syncWatchers` spec would stay provable (each watcher's
`moreRev` becomes the window's end when the window is cut). The existing proofs would therefore
accept both the buggy and the fixed code. #22594 bounds the read by entry count (`UnsafeRange`'s
`limit`), which needs `rangeEvents.spec` for a limited read: a new case of the backend spec.

## Proposal: `watch-sync-bounded-scan`

This is a safety statement that stands in for the cost bound: the window a pass reads is bounded.
Add a ghost read counter to the backend reader token. `isKeyBackendG`'s `UnsafeRange` would consume
one credit per bucket key returned, through a ghost `£`-like token `readCredit n`, which Perennial
can express as an ordinary ghost resource without time credits. Then strengthen `syncWatchers.spec`
to be given `readCredit (B · |chosen|)` with `B` a fixed bound (`watchBatchMaxRevs` times a
constant, or the entry limit of #22594):

```lean
-- syncWatchers reads at most B revisions per pass, and each chosen watcher that is not
-- victimized advances its minRev or becomes synced
{{ ... ∗ readCredit B }} s.syncWatchers() {{ (n : w64), RET #n; ... ∗ ⌜∀ w ∈ chosen, ...⌝ }}
```

The code at the pin fails this statement (it reads `curRev + 1 - minRev`, which is unbounded). Any
of the three PRs would meet it, with the first-mile caveat that a window may hold no events for the
watcher, and the spec must then still advance `minRev` to the window's end, as #22304 does. A
companion "progress per pass" conjunct (every chosen watcher's `minRev` strictly increases unless
it is synced or a victim) is a safety property too, and rules out a pass that does nothing. The
reporter's second regime (writes faster than 1000 revisions per 100 ms) is a throughput limit by
design and stays out of scope. Cost: small to medium. The counter threads through
`isKeyBackendG`'s read specs (one new resource, defaulting to an unbounded supply for existing
callers), plus `rangeEvents` and `syncWatchers` re-proved for a bounded window. It is only provable
after one of the fixes is translated.
