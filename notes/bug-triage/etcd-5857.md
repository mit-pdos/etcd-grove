# etcd-io/etcd#5857: cannot restart after shutdown (database file does not match with snapshot)

- URL: https://github.com/etcd-io/etcd/issues/5857 (closed 2016-07-03; label `type/bug`)
- Affected: etcd 3.0.0 (3-member cluster). A member restarts with `database file (... db index
  140014) does not match with snapshot (index 141365)`. Its raft snapshot file is ahead of its
  bolt db's `consistent_index`.
- Fix: PR #5862 "etcdserver: commit before sending snapshot" (commit `8a8a8253f`, merge
  `df61322e5`, 2016-07-03). It adds `s.KV().Commit()` before `s.be.Snapshot()` in
  `createMergedSnapshotMessage` (`etcdserver/snapshot_merge.go`). The change to `server.go` is to a
  comment only.

What goes wrong (pre-fix code). A leader sends a lagging follower a merged snapshot: a raft
snapshot at the applied index `snapi`, plus a stream of the bolt db file (`be.Snapshot()`). The
db snapshot reads the *committed* bolt file, but the leader's batch transaction still buffers
the writes and the `consistent_index` of the entries applied since its last commit (the backend
commits on an interval). So the follower installs a db at index 140014 whose raft snapshot says
141365. The entries in `(140014, 141365]` are in neither the follower's db nor its raft log. That
is a silent divergence. It surfaced at the next restart: the 3.0 startup check in `NewServer`
(`kvindex < snapshot.Metadata.Index`) refused the data directory.

## Classification

**F (fixed before the verified code); counterfactual F−, gap O-fn (secondary: scope, no snapshot in
a `Ready`).** The fix is an ancestor of the etcd pin `107edf7e4` (`git merge-base --is-ancestor
df61322e5 107edf7e4`: yes). At the pin, `createMergedSnapshotMessage` commits first
(`server/etcdserver/snapshot_merge.go:35-36`). The buggy function is a trust-boundary axiom here,
with postcondition `True`. On the follower, the snapshot-install branch of `applySnapshot` is
excluded by the raft wrapper's contract `ap.snapshot = nil`. So neither side of the bug is stated.
No crash is needed for the divergence itself: the restart only exposed it.

Source of verification states: `verified.txt` (`etc/verified-code.py`, at `d606c9cac`).

## The counterfactual (step 5)

- The leader side: `EtcdServer.createMergedSnapshotMessage.spec` is
  `{{ isPkgInit … }} … {{ (merged : Loc), RET #merged; True }}`
  (`EtcdServer__createMergedSnapshotMessage.lean`, an `axiom` in
  `Proof/.../EtcdServer__createMergedSnapshotMessage.lean`). It says nothing about how the db
  stream relates to `snapi`. The pre-fix body meets it.
- The follower side: `applySnapshot.spec` requires `taSnapshotAddr ap ↦□ (null : Loc)`, which
  `rnApP` provides (`Proof/.../InvRaftNode.lean:682`, `⌜ap.snapshot' = null⌝`). That holds because
  `ownRawNode` requires `snap = none` (STATUS "S2": `MsgSnap` is not admitted at `RawNode.Step`).
  No verified result describes a follower installing a snapshot.
- The apply protocol (`InvApply.lean`, `consInv`: `eff ≤ ci ≤ p`) is exactly the right vocabulary
  for this bug. A commit persists `ci` together with the effects through `ci`. But it governs the
  local backend's commits only. `be.Snapshot()` outside a commit is not one of its steps.

The pre-fix code meets every stated spec: **F−**.

## Proposal: `server-apply-snapshot` (new)

Specify both ends of a snapshot transfer.

- **Leader.** `createMergedSnapshotMessage(m, t, i, cs)` takes the apply thread's resources with
  `loopOk γ st i`. It returns a message whose db stream is a bolt image whose stored meta index is
  `ciEff γ st.k ≥ i` and whose KV is the state after the entries `≤` that index (`kvApplied`). Its
  proof needs `KV().Commit()` → `commit_save_au` and a `backend.Snapshot` contract: "the image is
  the last commit".
- **Follower.** `applySnapshot` with a non-nil snapshot at index `i` returns the apply thread with
  `applyThread γ' ⟨i, i, i, false⟩`, `srvApplyKV` at the snapshot's state, and `appliedLogAt γr i`.

Statement sketch for the leader:
`{{ applyThread γ st ∗ applyBackend γ ci b ∗ srvApplyKV s E w x ∗ ⌜loopOk γ st i⌝ }}
createMergedSnapshotMessage … {{ m, RET m; dbImage m (ciEff γ st.k) x.log ∗ ⌜uint.Z i ≤
uint.Z (ciEff γ st.k)⌝ ∗ … }}`.

Cost: medium to large. The leader half is small (15 lines of Go, plus a backend-snapshot axiom).
The follower half needs the raft side to admit snapshots first (`raft-pending-snapshot-ready`,
STATUS stage S items 2-3). It also needs specs for `lessor.Recover`, `store.Restore` (see
`verify-watchable-restore`, `mvcc-restore-from-backend`), the auth and alarm restores, and
`OpenSnapshotBackend`. The restart check itself also needs `crash-restart-model`.
