# etcd-io/etcd#14370: Durability API guarantee broken in single node cluster

- URL: https://github.com/etcd-io/etcd/issues/14370 (closed 2022-09-22; `type/bug`,
  `priority/important-soon`).
- Affected: every release up to 3.5.4 and 3.4.20, single-member clusters. Fixed in 3.5.5 and 3.4.21.
  Reproduced with gofail failpoints (`raftBeforeLeaderSend` sleep, `raftBeforeSave` panic,
  `backend/beforeCommit` sleep).
- Fix, in three steps, all ancestors of the etcd pin `107edf7e4` (`git merge-base --is-ancestor`):
  - PR #14400 (`73029fe89`): etcd-side. `raftNode.start` saves the WAL before `applyc` when
    `shouldWaitWALSync`.
  - PR #14413 (`31d9664cb`, tbg, "raft: don't emit unstable CommittedEntries"): the raft fix. The
    leader no longer self-acks in `appendEntry`. It steps an `MsgAppResp` to itself from
    `advance`, after the entries of the `Ready` were persisted.
  - PR #14505 (`ea3d78faa`): reverts the etcd-side change, because the raft fix makes it
    unnecessary.

  In etcd-io/raft, the self-ack was later reworked into `msgsAfterAppend` (async storage writes).
  At the raft pin `509271dac`, `appendEntry` sends `MsgAppResp{To: r.id, Index: li}`
  (`raft.go:835-846`), which `send` routes to `msgsAfterAppend` (`raft.go:592`). In synchronous
  mode, `acceptReady` queues it on `stepsOnAdvance` (`rawnode.go:414-416`), and it is stepped by
  `Advance` (`rawnode.go:477-490`).

What goes wrong (pre-fix): raft's `appendEntry` did `r.prs.Progress[r.id].MaybeUpdate(li);
r.maybeCommit()` (`raft/raft.go:637-640` at `026794495`). In a one-voter configuration, a
proposal was therefore committed the moment the leader appended it, and it appeared in the
same `Ready` as both `Entries` (to persist) and `CommittedEntries` (to apply). etcd's `raftNode.start`
sends the committed entries to `applyc` (`server/etcdserver/raft.go:213` at `73029fe89^`)
before `r.storage.Save` (`:237`). The apply thread can apply the put and answer the client
before the WAL write. A crash at that point loses the entry from both the WAL and bbolt (its batch
not yet committed), although the client was told OK.

## Classification

**F (fixed before the verified code); counterfactual F−, gap A-model (durability: no stable vs
volatile state, no crashes).** All three commits are ancestors of the pins. At the raft pin, the
leader's self-ack is stepped only from `Advance`. The server calls `Advance` after `Save` and
`raftStorage.Append` (`raft.go:256,287,331` at `107edf7e4`), so a one-voter commit implies the entries are
in the WAL. The pinned specs would also have admitted the buggy pair:

- The server's WAL contract `isRNWal` gives `Save` the postcondition `True`
  (`Proof/go_etcd_io/etcd/server/v3/etcdserver/InvRaftNode.lean:570-578`).
- Raft's acknowledgements, the leader's own included, are justified by the volatile log
  (`notes/STATUS.md:1137-1141`).

So neither the early `applyc` nor an immediate self-ack breaks any statement. The reported loss
needs a crash, which the model does not have.

## Argument (step 5)

1. **The bad behavior in spec terms.** A put is acknowledged: its entry is in
   `isCommitted γ L` (`RawNode__Ready.lean:89`, handed to the apply thread). Then a crash and a
   restart leave a server whose state lacks the entry. The second half has no representation. There
   is a single execution of fresh nodes (`notes/STATUS.md:2239`, "no crash-restart"), and
   `isCommitted` is a ghost fact about that execution. No predicate relates it to what the WAL
   holds.
2. **The raft half, counterfactually.** The pre-fix `appendEntry` updates the leader's own `Match`
   and commits at once. The protocol model already treats the self-ack as a message, `pselfAck`
   (`Protocol/Model.lean:1428-1431`), stepped later. Its pending-queue fact asks only for a term
   bound: `PendingOk (.self pv t)` (`InvRawnode.lean:298-302`). Nothing ties the acked index to
   the stored entries, unlike the `MsgStorageAppendResp`, which needs `StableOk`
   (`InvReadylog.lean:115-119`). An immediate self-ack is the same protocol step with the
   delivery folded in. It preserves the invariants (Log Matching, Leader Completeness, commit
   monotonicity), because they hold of volatile logs. So `appendEntry`'s and `Step`'s specs would
   be re-provable on the old code. This is argued, not re-proved: no proof attempt was made.
   `Ready`'s postcondition asks that `CommittedEntries` be committed (`isCommitted`), not that
   they be stable. Since `applyUnstableEntries()` is true in synchronous mode
   (`rawnode.go:443-445`), committed-but-unstable entries are legitimate on a follower, so the spec
   cannot forbid them in general.
3. **The etcd half.** `raftNode.start.spec` would be just as provable with `applyc` and `Save` in
   either order, because `Save`'s contract is `True → True`. The ordering that makes the pin
   durable (`Save` → `raftStorage.Append` → `Advance`, and only then the self-ack) is a fact of
   the code the proof walks through, but no postcondition states it.
4. Hence **F−**, gap **A-model**. Durability of acknowledged writes is outside the stated
   properties. This is the same gap as `raft-197.md` and `etcd-16666.md`.

## Proposal: `raft-durable-acks` (existing; first step of `crash-restart-model`)

Make "acknowledged implies durable on a quorum" a ghost fact, without crash semantics:

- Strengthen the trust boundary `isRNWal`. `Save(hs, es)` with `MustSync` (or always, since etcd
  syncs on non-empty entries, `wal.go:1015`) updates a ghost `walDurable γ id L` to the log
  with `es` appended at their indices.
- Add a conjunct to `PendingOk`. A self `MsgAppResp` at index `i` is steppable only when
  `plogLast s.logst.prev s.logst.stored ≥ i`, the same shape as the `.appendAck` case. Prove that
  `raftNode.start` calls `raftStorage.Append` only after `Save`, so `stored` ⊆ `walDurable`.
- Then `isAcked γ id t i → walDurable γ id ⊒ log[..i]`, and
  `isCommitted γ L → ∃ Q quorum, ∀ q ∈ Q, walDurable γ q ⊒ L`. For one voter, the applied
  entries are in its own WAL. The pre-fix raft fails at the new `PendingOk` conjunct, because the
  self-ack is taken at append time, and the pre-fix etcd-side ordering would have been caught
  as well if the follower's `MsgAppResp` were required to come after `Save` (the `!islead`
  branch, `raft.go:297-324`).

Cost: medium. The work is `isRNWal` and its users, `PendingOk`/`StepsOk` in `InvRawnode`, the
`isAcked` producers, and `raftNode.start`'s invariant. It needs no crash semantics. The restart
half (`walDurable` survives a crash and is what `RestartNode` gets) is `crash-restart-model`.

## Findings

None new: the bug is fixed at both pins. No bug in this repository's specs. The durability gap
is already recorded (`notes/STATUS.md:1137-1141`).
