# etcd-io/etcd#16687: `/members` peer handler is not guarded with linearizable check

- URL: https://github.com/etcd-io/etcd/issues/16687 (filed 2023-10-03, closed 2025-06-13 by the
  stale bot; labels `type/bug`, `stage/tracked`). Split out of etcd-io/etcd#16666.
- Affected: every version; reproduced on a v3.4.20 branch (an integration test on the reporter's
  fork). No fix. Draft PRs #17100/#17119 were not merged.
- What happens: the peer HTTP handler `peerMembersHandler.ServeHTTP`
  (`server/etcdserver/api/etcdhttp/peer.go:107-122` at the pin) returns `h.cluster.Members()`, the
  local member's view of the membership, without a linearizable read barrier. Right after a restart,
  while the WAL is still being replayed, a member serves a stale member list. The consumer is a
  joining member's bootstrap (`GetClusterFromRemotePeers`, `server/etcdserver/cluster_util.go:64`),
  which checks the cluster ID and takes its own ID and the peer names from it. The maintainers doubt
  that this does any harm, since the joining member then replays raft, and nobody showed a failure
  caused by it. Related: #14174 (a joining member seeing a membership change not yet applied
  everywhere; the workaround is to retry on the client side).

## Classification

**O-pkg (secondary N: not shown to be a bug).** The handler's package,
`server/etcdserver/api/etcdhttp`, is not translated (no `Code/` module), and neither is the
bootstrap's consumer (`cluster_util.go` is not in the inventory; `bootstrapExistingClusterNoWAL`,
`bootstrap.go:343`, is "not translated"). The one verified function on the path,
`membership.RaftCluster.Members` (`Spec/go_etcd_io/etcd/server/v3/etcdserver/api/membership/RaftCluster__Members.lean`),
promises only fresh clones of the cluster object's members (`membersAt sl ms`). It says nothing
about how current that object is relative to the cluster's committed membership. So no spec here
states or excludes the behavior. The code is unchanged at the pin.

## Proposal: `membership-read-barrier` (low priority)

Specify and prove the joining member's view of the membership. (1) `RaftCluster`'s member set,
after apply, equals the configuration of the applied prefix of the raft log (membership is mostly
unverified: 6 of 71 functions verified, 37 of 934 lines; `etc/verified-code.py --package
.../api/membership`). (2) The `/members` handler either waits for `LinearizableReadNotify` (then
`read_notify` gives "at least the committed membership the caller knew of") or is documented as a
possibly stale view. (3) The bootstrap uses only fields that cannot change under it (cluster ID,
the joiner's own ID). Cost: medium to large; it needs the membership store, the v2/v3 membership
backends and an HTTP-handler boundary. It would decide whether #14174-like failures are possible,
which the issue left open.
