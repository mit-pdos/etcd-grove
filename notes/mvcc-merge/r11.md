# Track R11: every gRPC handler run holds its goroutine's thread token (2026-11-07)

The user's decision (2026-11-07): this repository's trusted gRPC model gives each handler run the
thread token of the goroutine grpc runs it on, given back at its return. Until then a run held only
its slot `S`, so a handler that needs `threadTok` (every read over mvcc's API: `threadTok ∗
mvcc.api.mvccReaders γ 1`) had it in the slot (`client.etcdRunSlot`, `v3rpc.watchRunSlot`), and a
server could stock no slot (no one can make `n` thread tokens out of nothing): the examples served
one request at a time.

Scope: `Proof/google_golang_org/grpc/{InvGrpc,InvGrpcStream}.lean`, and the generated Watch handler
(`{Spec,Proof}/go_etcd_io/etcd/api/v3/etcdserverpb/_Watch_Watch_Handler.lean`), whose spec passes the
stream contract's token through. v3rpc, client/v3 (R7) and the examples (R9) are not touched.

## Why it is true of grpc-go (v1.84.0, `examples/go.mod`'s pin)

Every call's handler runs on a goroutine of its own, from its start to its return:

- `server.go:1090-1106` (`serveStreams`): the transport's `HandleStreams` callback builds
  `f := func() { …; s.handleStream(st, stream) }` and runs it with `go f()` (`:1106`); with the
  option `NumStreamWorkers` (etcd sets none: `v3rpc.Server`'s options, and no `NumStreamWorkers` in
  etcd v3.7's server), it may instead hand `f` to a worker (`:1099-1104`), a goroutine
  (`serverWorker`, `:687-696`) that runs one `f` at a time to its end, so the run still has the
  goroutine to itself while it lasts.
- `handleStream` (`:1537`; its comment, `:1540`: "This method always runs in its own goroutine")
  dispatches a registered method to `processRPC` (`:1594`), which calls `sd.Handler(server,
  wrappedStream)`, or the stream interceptor over it (`:1450-1458`), in that goroutine; a unary
  method's `sd.Handler` is `wrapUnaryHandler`'s closure (`:812`, `:1281-1289`), which calls
  `md.Handler(srv, stream.Context(), df, s.opts.unaryInt)`, the generated handler `grpcMethodOk`
  speaks of, in the same goroutine.

In Perennial a `go` statement gives the new goroutine a fresh thread token that it holds until it
exits (`wp_fork_tok_body`); a run of grpc's runtime is such a goroutine, so it holds one, and
gives it back when the run returns (the goroutine then ends, `ThreadExit`). The tokens bound the
live threads of the executions the adequacy theorem speaks of (`threadBound`); grpc's handler
goroutines are live threads of the real program, as any goroutine the program starts, so they are
counted as `go` statements' would be (the stream slots' pool already assumes the runtime starts a
run only when it can give it what the axiom promises). A run that does not return (a stream
handler blocked forever) keeps its token, as a goroutine that does not exit keeps its own.

## Changed axioms and trusted definitions (old → new)

### `grpc.serve` (axiom, `InvGrpc.lean`): the method contracts at `threadTok ∗ S`

Old:
```lean
axiom grpc.serve (addr ics regs) (ms : List (GrpcMethod GF)) (S : IProp GF) (n : Nat) :
  (ms.map GrpcMethod.name).Nodup → (∀ m ∈ ms, (m.name, m.handler, m.srv) ∈ regs) →
  (grpcServerAt addr ics regs ∗ ([∗list] _x ∈ List.replicate n (), S) ∗
    [∗list] m ∈ ms, grpcMethodOkMd m.handler m.srv ics S m.spec) ⊢
  |={⊤}=> [∗list] m ∈ ms, grpcServes addr m.name m.handler m.srv ics S
```
New:
```lean
  (grpcServerAt addr ics regs ∗ ([∗list] _x ∈ List.replicate n (), S) ∗
    [∗list] m ∈ ms, grpcMethodOkMd m.handler m.srv ics iprop(threadTok ∗ S) m.spec) ⊢
  |={⊤}=> [∗list] m ∈ ms, grpcServes addr m.name m.handler m.srv ics iprop(threadTok ∗ S)
```
The runtime is handed `n` copies of `S` (the slots, no token); a run holds one copy and its
goroutine's token, and gives both back (`grpcMethodOkMd`'s post returns its resource). The
definitions `grpcMethodOk(Md)` and the unary handler contracts `grpcHandlerOk`, `grpcHandlerOkMd`,
`grpcHandlerOwnOk`, `grpcHandlerOwnOkMd` are unchanged (they are generic in the run's resource,
which is now `threadTok ∗ S`). Its corollary `grpc_serve_rpcs` (a theorem) takes the methods'
`grpcMethodOkMd … iprop(threadTok ∗ S) …` in place of `… S …`; its conclusion is unchanged.

### `grpcStreamMethodOk`, `grpcStreamMethodOkR` (definitions in `grpc.serveStream`'s statement, `InvGrpcStream.lean`)

Old (the run's part of both; `R` has `grpcSlotPool S -∗` after `S -∗`):
```lean
      Spec (metadata.incomingOf (GoInterface.ok ci)) γ Dn -∗ S -∗ srvRawStreamIs st γ Req Rep Up Dn ci cd -∗
      srvRecvTok (Req := Req) γ [] -∗ srvSendTok (Rep := Rep) γ [] -∗ streamAuxTok γ -∗
      srvStreamInfoIs info -∗
      srvStreamChainWP #info ics mh #srv #st (fun _ => iprop(True))
```
New:
```lean
      Spec (metadata.incomingOf (GoInterface.ok ci)) γ Dn -∗ S -∗ threadTok -∗
      srvRawStreamIs st γ Req Rep Up Dn ci cd -∗
      srvRecvTok (Req := Req) γ [] -∗ srvSendTok (Rep := Rep) γ [] -∗ streamAuxTok γ -∗
      srvStreamInfoIs info -∗
      srvStreamChainWP #info ics mh #srv #st (fun _ => threadTok)
```
(`grpcStreamMethodOkR`: `… S -∗ grpcSlotPool S -∗ threadTok -∗ srvRawStreamIs …`, the same post.)
The axiom `grpc.serveStream`'s text is unchanged (its docstring says where the token comes from);
the pool still holds only the slots `S`. A stream run returns the token if it returns, and still
need not return `S` (it may give it to the pool later, `grpcSlotPool`). `grpcStreamMethodOk_R`'s
proof passes the token on.

### `grpcStreamHandlerOk` (the stream handler contract, `InvGrpcStream.lean`)

Old:
```lean
    Spec (metadata.incomingOf (GoInterface.ok ci)) γ Dn -∗ S -∗ srvStreamIs st γ Req Rep Up Dn ci cd -∗ …
    srvSendTok (Rep := Rep) γ [] -∗ streamAuxTok γ -∗ ▷ (∀ err : GoInterface, Φ #err) -∗
    WP (App (Val h) (Val #st)) {{ Φ }}
```
New:
```lean
    Spec (metadata.incomingOf (GoInterface.ok ci)) γ Dn -∗ S -∗ threadTok -∗
    srvStreamIs st γ Req Rep Up Dn ci cd -∗ …
    srvSendTok (Rep := Rep) γ [] -∗ streamAuxTok γ -∗ ▷ (∀ err : GoInterface, threadTok -∗ Φ #err) -∗
    WP (App (Val h) (Val #st)) {{ Φ }}
```

### `etcdserverpb._Watch_Watch_Handler.spec` (`Spec/go_etcd_io/etcd/api/v3/etcdserverpb/`)

Pre `… ∗ S ∗ srvRawStreamIs …` → `… ∗ S ∗ threadTok ∗ srvRawStreamIs …`; post `True` → `threadTok`.
Its proof passes the token to `grpcStreamHandlerOk` and back.

## What changes for the handlers' implementers (R7, R9)

Unary methods (`grpc_serve_rpcs`, `grpc.serve`):
- A served method's contract is at `iprop(threadTok ∗ S)` where `S` is what the server stocks `n`
  copies of. A handler proved today with the token inside its slot (`client.etcdRunSlot`'s
  `(threadTok ∗ mvccReaders E.γ 1)`) keeps its proof once the slot is split: drop `threadTok` from
  the slot (`etcdRunSlot`: `… ∗ mvccReaders E.γ 1 ∗ …`), and state the method contracts handed to
  `grpc_serve_rpcs` at `iprop(threadTok ∗ etcdGrpcSlot …)` (or the slot used there); the handler
  contracts (`grpcHandlerOk(Md)`, `grpcHandlerOwnOk(Md)`) and the generated handlers' specs are
  generic in the run's resource and do not change. Obligation: the run's post gives the token back
  (it is part of the resource `grpcMethodOkMd` returns).
- The `n` copies stocked (`([∗list] _x ∈ List.replicate n (), S)`) no longer contain a token: a server
  can stock any number of them (the examples' one-request-at-a-time limitation goes).
- `isGrpcRpc(Md)`, `grpcServes` and the client side are unchanged in form (the existential run
  resource is `threadTok ∗ S`).

Stream methods (`grpc_serveStream_rpcs`, `grpc.serveStream`):
- `grpcStreamHandlerOk h S Up Spec` now gives the handler `threadTok` and requires it back at its
  return: the continuation is `▷ ∀ err, threadTok -∗ Φ #err`. `v3rpc.watch_streamHandlerOk`: take
  the token from the contract (not from `watchRunSlot`), pass it to `watch_server`, and give
  `watchServer.Watch.spec`'s returned `threadTok` to the continuation (now `iintro %err -` drops it).
- `grpcStreamMethodOk` / `grpcStreamMethodOkR`: the run takes `threadTok` after `S` (after
  `grpcSlotPool S` for `R`), and the chain's post is `fun _ => threadTok`. `v3rpc.etcd_watchMethodOk`:
  `srvStreamChainWP_of_ok … (fun _ => threadTok)`, the handler `watch_handler` given the token and
  its post's token returned through the interceptors' continuation; the early-error branch
  (`R -∗ ∀ err, ⌜err ≠ nil⌝ -∗ Ψ #err`) must now give `threadTok`: keep the token aside and frame it
  (it is not passed through the interceptors).
- `v3rpc.watchRunSlot R W`: drop `threadTok` (now `R.E.RD ∗ mvcc.api.mvccReaders W.γm 2 ∗
  ⌜threadBound …⌝`), as planned (`r7.md`).
- `etcdserverpb._Watch_Watch_Handler.spec` (above): `watch_handler` is its linked proof; callers
  give `threadTok` and get it back.

Examples (R9): the stocks of run slots (`kvServeStocks`, `grpcUp*`, `ServedLease`'s "the KV's
run resources and a thread token") lose their tokens, following R7's restated slots. The committed
interfaces `interface/Proof/github_com/mit_pdos/etcd_grove/examples/lib/etcdstart/Served*.txt`
reach these definitions and need regenerating once those build.
