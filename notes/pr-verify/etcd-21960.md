## Verdict

**The PR should not be merged as it is. It removes the only thing that told an idle
require-leader keep-alive stream that its member had lost its leader, and it fixes no actual
leak.**

**The regression.** etcd's stream interceptor gives a `WithRequireLeader` stream a context of its
own. `monitorLeader` cancels that context with `ErrGRPCNoLeader` when the member has had no
leader for a while. The `select` the PR deletes is what turned that cancellation into the RPC's
result. Its own comment listed this as case 2.
- `Recv` and `Send` go to grpc's transport stream, which does not watch that context. So with
  the PR, the handler stays blocked until the client's next request.
- The client's lessor opens its keep-alive stream with `WithRequireLeader`
  (`client/v3/lease.go`), so every clientv3 lease user is affected.
- When the next request does arrive, `LeaseRenew` fails on the canceled context with `Canceled`.
  The client then never sees `ErrNoLeader`, and never closes its require-leader keep-alive
  channels.
- Two of upstream's own integration tests fail at the PR head and pass at its base (F1).

**The leak.** The leak the PR describes does not exist.
- When a stream handler returns, grpc cancels the transport stream. The old goroutine's `Recv`
  or `Send` then fails at once.
- The PR's test passes on the old code too (F2).

**What is proved.** Of the new code, with no new axiom and no `sorry`:
- every response `LeaseKeepAlive` sends answers the request at the same position, with the
  request's lease id, the server's header ids, and a TTL that is `0` or the lessor's;
- if the handler returns, it hands back the stream's receive and send tokens, so nothing it
  started still uses the stream.

The new spec implies the old one. These are partial-correctness specs: that the handler *returns*
when the stream's context is canceled, the property the PR breaks, is outside them. The tests
found that.

## The specs

Vocabulary: `Proof/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/InvLease.lean`. It reuses grpc's
generic server stream end (`srvStreamIs`, `google_golang_org/grpc/InvGrpcStream.lean`) and the KV
server's header (`hdrIs`).

**Message models** (trusted wire models, like the watch service's):
- a request's model is its lease id;
- a response's model is its id, its TTL, and its header's cluster and member ids.

**The lessor**: `lessorOk le Ren`, a premise and not an axiom. `LeaseRenew(ctx, id)` returns
either a TTL with `Ren id ttl`, or an error `errors.Is` and `togRPCError` can take (`srvErrIs`).

**The specs** (paths under `Spec/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/`):
- **`LeaseServer.leaseKeepAlive.spec`** (`LeaseServer__leaseKeepAlive.lean`).
  - Premises: the server end of the stream; the receive token at the `Lq` requests received and
    the send token at the `Lr` responses sent, with `|Lr| = |Lq|`; the header's resources.
  - The stream's content `Dn` of responses is implied by `lkDn`. `lkDn` says the `j`th response
    answers the `j`th request (`upAt`): same id, the server's cluster and member ids, a TTL that
    is `0` or a renewal's.
  - It returns `lkDone`: both tokens and the header's resources.
- **`LeaseServer.LeaseKeepAlive.spec`** (`LeaseServer__LeaseKeepAlive.lean`): the same pre- and
  postconditions.
- **`LeaseServer.LeaseKeepAlive.spec_old`**, in the same file: the handler's shape before the PR,
  as in `watchServer.Watch.spec`. Same premises; it returns, with nothing given back.
  - The new spec implies it (`spec_implies_old`, in the Proof file).
  - Why the old code could not give the tokens back: they belonged to its goroutine, possibly
    still in `Recv`, `LeaseRenew` or `Send`. This is argued, not proved, since the old body is not
    translated.
  - The difference is the model's: there `Recv`/`Send` may succeed after the handler returned. In
    real grpc they fail at once (F2).
- **Exported results**: `v3rpc.lease_keep_alive` and `v3rpc.lease_keep_alive_old`, in
  `v3rpc/Results.lean`'s lease section.

Two things the specs do not say:
- **"A `nil` return means every request received was answered."** Proving it needs
  `errors.Is(nil, io.EOF) = false`. Perennial's `errors.Is.spec` returns some boolean, so it was
  dropped (`notes/STATUS.md`).
- **"It returns once the stream's context is canceled."** This is liveness. Also, the stream
  model's `Recv`/`Send` are not tied to the context.

Neither the PR's test nor these proofs would have caught F1. The verified stream interceptor
(`newStreamInterceptor`) excludes the require-leader branch by a premise (`runsNoRequireLeader`).

## Findings

Each test is in `notes/pr-verify/etcd-21960/`; the `README.md` there gives the revisions and
commands.

**F1. Regression: an idle require-leader keep-alive stream is no longer ended with
`ErrGRPCNoLeader`.**
- `newStreamInterceptor` wraps a `WithRequireLeader` stream in `serverStreamWithCtx` and registers
  it with `monitorLeader`. After `maxNoLeaderCnt` election timeouts with no leader,
  `monitorLeader` calls `ctx.Cancel(rpctypes.ErrGRPCNoLeader)` and waits for
  `<-ss.Context().Done()`.
- The old `select` returned that error to the client. With the PR, the handler stays in `Recv()`:
  - `RecvMsg` goes to the embedded transport stream, which selects on its own `ctxDone` (grpc
    v1.81.0 `internal/transport`), not the wrapper's.
  - When the client's next keep-alive request arrives, `LeaseRenew` gets the canceled context and
    returns `ErrCanceled`. The RPC ends with `Canceled`, not `Unavailable`/`no leader`.
  - The clientv3 lessor's `recvKeepAliveLoop` therefore never calls `closeRequireLeader`.
- The same hang happens while the handler is blocked in `Send` on flow control (F1b, the
  reviewer's `TestReviewNoLeaderSendBlocked`): the write quota is tied to the transport's
  `ctxDone`.
- **Evidence**:
  - upstream's `TestV3LeaseKeepAliveForwardingCatchError/catches_NoLeader_error_with_WithRequireLeader`
    hangs at the PR head until the 2-minute test timeout, at `v3_lease_test.go:426`;
  - upstream's `TestLeaseWithRequireLeader` fails at the PR head at `lease_test.go:780`
    ("Canceled metric should not change, expected 0, got 1");
  - both pass at the base (`base-tests.log`, `pr-head-tests.log`);
  - `lease_keepalive_noleader_test.go` (unit) and `lease_keepalive_grpc_review_test.go` (over a
    real grpc server) pass at the base and fail at the PR head. The unit test also fails on the
    fork branch.

**F2. The leak the PR describes does not exist, and its test does not show one.**
- grpc's `processStreamingRPC` calls `WriteStatus` after the handler returns. That reaches
  `finishStream`, which calls `s.cancel()` first, "to interrupt Recv/Send in other goroutines".
- So the old goroutine's pending `RecvMsg`/`SendMsg` returns `Canceled` right after the handler
  returns. Its `LeaseRenew` is bounded by the wrapper context, which the interceptor's
  `defer ctx.Cancel(nil)` cancels, and by `ReqTimeout`.
- The reviewer's tests check this on the base: no `leaseKeepAlive` goroutine outlives the handler
  by more than 3s.
- `TestLeaseKeepAlive_GoroutineLeakOnDisconnect` passes on the unchanged base code (3 of 3 runs),
  because its mock `Recv` itself watches the context.
- The old code's only real wart: its goroutine could finish a `LeaseRenew`, or a failing `Send`,
  briefly after the handler returned, and log it.

**F3. The PR's test file.**
- It is not `gofmt`-clean (`struct{`, field alignment).
- On current `main`, its `mockRaftStatusGetter` embeds a nil `apply.RaftStatusGetter` and lacks
  `Leader()`, which `header.fillWithoutRevision` calls since `ee374bdc1`. The test then panics
  with a nil dereference: seen on the fork, and read from the code for `main`.

**Other behavior differences** (the reviewer's; none harmful):
- on client cancellation both versions end the RPC with `codes.Canceled`, with the same logs and
  metrics;
- on server shutdown, no difference;
- with a `LeaseRenew` in flight when the context is canceled, the old handler answered at once.
  The new one waits for `LeaseRenew`, which is bounded.

**No bug in the existing (pinned) code was found.** Nothing was added to `issues/`.

**Reviewer**: a fresh subagent reviewed the specs, the premises and F1 to F3 against grpc's
source. Its points on wording are folded in: `Results.lean` and `spec_old`'s doc now say the
token result holds only if the handler returns, and that the old code's "leak" is a property of
the model. No point is left open.

> Thanks for looking into this. I don't think this change is safe, and I don't think the leak it
> describes happens.
>
> The `select` on `stream.Context().Done()` is what ends a `WithRequireLeader` keep-alive stream

> client gets `Canceled` instead of `no leader`. clientv3's lessor always uses
> `WithRequireLeader` for this stream. Two existing integration tests fail with this PR and pass

> - `TestV3LeaseKeepAliveForwardingCatchError/catches_NoLeader_error_with_WithRequireLeader` hangs;
> - `TestLeaseWithRequireLeader` fails at `lease_test.go:780` (Canceled instead of Unavailable).
>
> On the leak: when a stream handler returns, grpc finishes the stream and cancels the transport
> stream's context (`finishStream` → `s.cancel()`), so the old goroutine's pending `Recv`/`Send`
> returns right away. The new test also passes on the current code, since its mock `Recv`
> watches the context itself. If you have a goroutine dump showing goroutines stuck in
> `leaseKeepAlive` after their RPC ended, that would help find the real cause.
>
> (Minor: the test file isn't gofmt'ed. On current main, `mockRaftStatusGetter` also needs
> `Leader()`, since `header.fill` now sets `LeaderId`.)
