## Verdict

The PR is sound and does what it says, with one gap.

- **`currentRev` race: fixed, and proved.** `hash` now reads `currentRev` under `revMu`. The
  proof of `store.hash` shows this read is race-free, and that the revision returned is the last
  revision of a committed log extending the caller's. The old code reads `currentRev` with no
  lock, which the store invariant does not allow. That race is wider than the PR says: it also
  races with every ordinary write transaction, without `Restore`
  (`issues/etcd-mvcc-hash-currentrev-unlocked.md`, with a race-detector test that fails on the
  base and passes with the PR).
- **`s.b` race with `Restore`: fixed, checked by reading the code, not proved.** The store
  invariant treats `s.b` as never changing (`Restore` is outside the verified code), so the proof
  cannot see this race. Read by hand, with the reviewer agreeing: with the PR, every access to
  `s.b` is ordered with `Restore`'s write. Committing under `s.mu.RLock` also stops the old code's
  `ForceCommit` on a backend that `applySnapshot` has closed. That case is a `lg.Fatal` in
  production, not just a race report. After `Close`, `CommitAndStop` leaves the batch
  transaction's `tx` set to the committed bolt transaction (`batch_tx.go:281-308`), and a
  `ForceCommit` then runs the backend's `OnPreCommitUnsafe` hook (`batch_tx.go:384`). The
  server's hook writes the consistent index through `UnsafePut` on that closed transaction, whose
  error is fatal. Without hooks (unit tests) it returns early, since nothing is pending. `Hash` on a closed
  backend returns bbolt's `ErrDatabaseNotOpen`.
- **No deadlock.** Holding `s.mu.RLock` across `ForceCommit` follows the existing lock order
  (`s.mu`, then the batch transaction's lock, as in `Write` and `Commit`), and no holder of the
  batch lock takes `s.mu`.
- **Gap: a wrong revision around `Restore`.** The PR reads `currentRev` after releasing `s.mu`. A
  `Restore` in that window makes `hash` return the old backend's hash with `Restore`'s transient
  revision 1, or with the new store's revision. The base code does the same, so this is not a
  regression (`issues/etcd-mvcc-hash-restore-transient-rev.md`; the reviewer's test fails on both
  the base and the PR). Reading `currentRev` before `s.mu.RUnlock()`, as `hashByRev` does, fixes
  it. This is worth a review comment, below.
- **Not covered:**
  - `Restore` itself, as above.
  - The backend's `Hash`, which is a premise (`storeHashOk`).
  - The connection from the `Maintenance.Hash` RPC to `hashStorage.Hash`. The server's
    `maintenanceServer` is not translated, and `store.HashStorage`'s spec does not name the store
    the hash storage belongs to.

## The spec

`Spec/go_etcd_io/etcd/server/v3/storage/mvcc/store__hash.lean`, `mvcc.store.hash.spec`:

- **Takes:** the store (`isStore`), a reader's tokens (`storeReaderC`), a write session's token
  (`storeWT`, which `ForceCommit` spends, as the backend's contract requires), and a certificate
  `idxCert γ.idx log₀` of a committed log. It also takes `storeHashOk s`, the backend's
  `Hash(schema.DefaultIgnores)` returning (`HashDefs.lean`).
- **Gives back:** the reader's tokens, and a hash, an error and a revision. The revision is
  `len(log) - 1` for a certified committed log `log` extending `log₀` (at least the caller's
  revision). The hash, the error, and how the hash relates to the revision are unconstrained (the
  code's TODO).

There was no old spec (not translated). The old code cannot meet this one: it reads `currentRev`
with no lock. The invariant holds `currentRev`'s points-to in halves, one in `s.revMu`'s resource
(`revMuInv`) and one with the writer under the batch lock, so an unlocked read has no part of it
to read with. No proof attempt against the old translation was needed to see this. A load needs
a fraction of the points-to, and none is reachable without the lock.

What the spec does not say: anything about `s.b` and `s.mu`. `isStore` keeps `s.b` read-only,
`s.[store, "b"] ↦□ b` (`InvStore.lean`, `isStore`), so the proof would go through with `s.b` read
outside `s.mu` too. Stating the PR's main point needs a store whose backend `Restore` replaces:
`s.b` owned by `s.mu`'s resource, with every store proof that reads `s.b` (all the transactions,
the compaction, `NewStore`) adapted. That is a change to the store invariant across the whole
package, not done here (the next step if `Restore` is verified).

## Findings

1. **Existing bug, fixed by the PR**: `issues/etcd-mvcc-hash-currentrev-unlocked.md`. `hash`
   races with every write transaction on `currentRev`. Test:
   `notes/pr-verify/etcd-22609/kvstore_hash_put_race_test.go`. It fails under `-race` on
   `b25719d10` and passes 50 runs of 50 on the PR head.
2. **Existing bug, left by the PR**: `issues/etcd-mvcc-hash-restore-transient-rev.md`. `hash` can
   return the old backend's hash with `Restore`'s transient revision 1. Test:
   `notes/pr-verify/etcd-22609/kvstore_hash_restore_rev_test.go` (the reviewer's). It fails on
   `b25719d10` and on the PR head; with `currentRev` read before `s.mu.RUnlock()` it passes under
   `-race` (the reviewer's run).
3. **A bug in this run's spec, fixed**: the premise `storeHashOk` took any function argument
   (above).

The reviewer's other points were all checked and found OK:

- the spec captures the `currentRev` half and the old code cannot meet it;
- spending `storeWT` is the backend contract's own requirement, as for `store.Write`, not
  vacuous;
- `hashSec_init` is sound;
- every access to `s.b` and to the other fields `Restore` writes is ordered with `Restore`
  (`watchableStore.syncWatchers` reads `s.store.b` under `watchableStore.mu`, which
  `watchableStore.Restore` holds);
- no deadlock.

Open points:

- `Restore`, and so the `s.b` half of the PR, is outside the verified code.
- `store.HashStorage`'s spec returns `True`. It does not say the hash storage's `store` field is
  the store (`NewHashStorage` sets it), so `hashStorage.Hash`'s spec takes that as a premise.

>    s.revMu.RLock()
>    revision = s.currentRev
>    s.revMu.RUnlock()
>    s.mu.RUnlock()
>
>    h, err := b.Hash(schema.DefaultIgnores)
>    ```
>
>    The TODO still applies (writes can land between the commit and the hash), but the revision
>    is then always the hashed backend's store's revision as of the commit, never `Restore`'s
>    placeholder or another backend's. Happy to leave this for a follow-up if you'd rather keep
>    this PR minimal.
