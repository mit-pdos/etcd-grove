## Verdict

The PR is safe as far as it was verified, but it does only part of what it says.
- **What is proved**: the new code runs without panicking and leaves the request path's behavior
  unchanged. The re-proved log interceptor stores the client's address in the context it passes
  on (`v3rpc.logIcStoresIP`), and `ClientIPFromContext` downstream returns that address. The
  auth store's invalid-token path is re-proved with the extra field. The server's KV results
  (`etcd_kv_served`, the handlers) still go through with the interceptor passing a derived
  context.
- **What it rests on**: two new trust-boundary axioms (a `context.WithValue` triple at the new
  key, and "a request-path context answers `Value(ClientIPContextKey{})`"). Two trusted
  definitions are also strengthened: the run context `grpcRunCtx` now carries the run's peer,
  whose `Addr` is non-nil.
- **What does not work as described** (a Go test shows both):
  - "authenticated a user" always logs `remote=""`. `authStore.Authenticate` runs in the apply
    path with a context made from `context.Background()`.
  - The invalid-token warning, and `AuthInfoFromTLS`'s new fields, log `remote=""` for stream
    RPCs (Watch, LeaseKeepAlive), because only the unary interceptor stores the IP.
- **Not covered**: the JWT provider's `info`, `authStore.Authenticate`,
  `EtcdServer.Authenticate`, `AuthInfoFromTLS` and `logUnaryRequestStats` and its two helpers.
  Those are names-only or trust-boundary axioms. Log contents are not modeled beyond "the field is
  computed without panicking".

### The behavior changes, old and new specs

- **`authStore.AuthInfoFromCtx`**
  (`Spec/go_etcd_io/etcd/server/v3/auth/authStore__AuthInfoFromCtx.lean`). Old: any `ctx`.
  New: `ctx` answers `Value(ClientIPContextKey{})`, which is `auth.ctxClientIPOk` in
  `Proof/go_etcd_io/etcd/server/v3/auth/ClientIP.lean`. The postcondition is unchanged.
  `authInfoFromToken`'s spec gains the same premise and passes it to the token provider.
- **`newLogUnaryInterceptor`**
  (`Spec/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/newLogUnaryInterceptor.lean`). Old: the
  closure is `srvInterceptorOk`, meaning it calls the handler on the same context or fails early.
  New, in two parts:
  - `srvInterceptorOk` in its generalized form: it calls the handler on some run context.
  - `v3rpc.logIcStoresIP`: on a run context whose peer is at address `addr` (`grpcRunPeerIs ci
    (some addr)`), the handler's context carries `addr` as its client IP (`ctxClientIPIs ci'
    (some addr)`).

  The second part is the PR's purpose, stated so that a version which stored nothing or the wrong
  value would fail.
- **`srvInterceptorOk`** (`Proof/google_golang_org/grpc/InvGrpc.lean`). Old: the handler
  continuation is at the same context `ci`. New: it is for any run context `ci'`
  (`isContext ci' cd' ∗ grpcRunCtx ci'`). Every interceptor that met the old contract meets the
  new one (`srvKont_here`), so the assumption about grpc-prometheus's interceptor in
  `etcd_kv_served` is weaker, not stronger. The cost is in `srvChainWP_of_ok` and the four
  generated KV handlers' proofs, which now take the continuation for any context. Their
  `grpcHandlerOk` premise already quantifies over the context.
- **`grpcRunCtx`** (trusted: what grpc's runtime gives a run), in three parts:
  - The old definition said `Value` at every etcd key returns `nil`, which the PR makes false past
    the log interceptor. Now `ClientIPContextKey` is excepted.
  - Its value there is some IP or none (`∃ o, ctxClientIPIs ci o`).
  - It includes the run's peer (`grpcRunPeer`: `Value(peerKey{})` is nil or a non-nil `*Peer`
    with `grpcPeerIs p addr`, an `Addr` field that is a non-nil `net.Addr` whose `String()`
    returns `addr`).

  The context the interceptor derives satisfies it again (`grpcRunCtx_withClientIP` in the
  interceptor's proof).

## Trust base

New axioms, both in this repository:

1. **`context.WithValueClientIP.wp_proof`** (`Spec/context/WithValueClientIP.lean`). It is a
   triple of `WithValue(parent, ClientIPContextKey{}, s)`:
   - `isContext` passes to the child at the same descriptor;
   - `Value` at the key returns `s`;
   - at a key of any other dynamic type, `Value` is the parent's.

   It is believed because it is Go's `valueCtx`. The key is an empty struct, so it is comparable
   and `WithValue` does not panic. Interface `==` against a key of another type is false. `value()`
   then returns what `parent.Value(key)` would, for every context type. `Deadline`, `Done` and
   `Err` are promoted from the parent, and `parentCancelCtx` reads only those. It sits beside the
   existing `WithValue` axiom (`Spec/context/WithValue.lean`), whose keys do not overlap with this
   one. Perennial has no model of `WithValue`.
2. **`auth.ctxClientIPOk_of_txnCtx`** (`Proof/go_etcd_io/etcd/server/v3/etcdserver/ClientIPCtx.lean`).
   It says a context described by `mvcc.txnCtx` answers `Value(ClientIPContextKey{})`. It is true
   of every context that reaches `AuthInfoFromCtx` and `AuthInfoFromTLS`: all of them are standard
   library contexts over grpc's. It is not true of an arbitrary context with a nil `Done()`. The
   same assumption is already implicit in `metadata.FromIncomingContext.spec`, an axiom over any
   context, nil included, which `AuthInfoFromCtx` called before the PR.
   - **A cleaner way**, not done here: carry `ctxClientIPOk` along the request path the way
     `traceutil.ctxTraceIs` is carried, from `grpcRunCtx` through the `WithValue`/`WithTimeout`
     specs. The general fix is in Perennial: give `isContext` a `Value` clause for every
     comparable key (`notes/STATUS.md`).

Trusted definitions strengthened (part of the trusted runtime, used by the existing axioms
`grpc.serve`, `grpc.serveStream`, `srvStreamIs`):
- `grpcRunCtx` now includes `grpcRunPeer`.
- `grpcPeerIs` says the peer's `Addr` is non-nil.

grpc v1.84 meets both. `serveStreams` calls `peer.NewContext(ctx, st.Peer())` for every stream.
`http2Server` sets `Addr` to `conn.RemoteAddr()`, and etcd's listener wrappers pass that through.
The `ServeHTTP` transport sets it to `strAddr(r.RemoteAddr)`. A unix socket's remote address is a
non-nil `*net.UnixAddr` (`notes/pr-verify/etcd-22259/unixaddr.log`). The PR widens the exposure:
`Addr.String()` used to run only when request stats were logged and now runs on every unary
request. A hand-built peer with a nil `Addr` panics the interceptor
(`notes/pr-verify/etcd-22259/peer_nil_addr_test.go`), which grpc's own transports never build.

## Findings

These are in the PR. None is a bug in the pinned code, so `issues/` gets nothing.

1. **"authenticated a user" never carries the client IP** (Medium: the PR does not do what it
   says).
   - `authStore.Authenticate` is called from the apply path, `applierV3backend.Authenticate` in
     `server/etcdserver/apply/backend.go`, with
     `context.WithValue(context.WithValue(context.Background(), ...))`. So
     `clientIPFromContext(ctx)` is always `""`, on the leader and on followers alike.
   - Test: `notes/pr-verify/etcd-22259/client_ip_log_test.go`; output at the PR head:
     `client_ip_log_test-pr-head.log`.
   - The request's address would have to go into the `InternalAuthenticateRequest`. Otherwise
     only the member that served the RPC can log it, in `EtcdServer.Authenticate`, which the PR
     already does for failures.
2. **Stream RPCs carry no client IP** (Medium). The IP is stored only by the unary interceptor
   (`newLogUnaryInterceptor`). So the "invalid auth token" warning from a Watch or LeaseKeepAlive
   (`isWatchPermitted` → `AuthInfoFromCtx` on the stream's context) logs `remote=""`, and so do
   `AuthInfoFromTLS`'s fields on those streams. Same test: the watch's line carries `""`.
3. **The defaults are inconsistent** (Low).
   - "request stats" without a peer logged `"No remote client info."` before and logs `""` now.
   - `EtcdServer.Authenticate` looks the peer up itself, logs `"unknown"` when there is none, and
     does not check `p != nil`.
   - The value is `ip:port` (`"@"` for a unix-socket client), not an IP as the key's name says.
4. **Gateway and in-process clients** (Info). Requests through the gRPC gateway are logged with the
   gateway's loopback address, since it dials the server over gRPC. v3client and in-process
   adapters bypass the interceptors, so they log `""`.
5. **Cost on every unary request** (Low): `peer.FromContext`, `Addr.String()` (a string format) and
   a `WithValue` allocation, even when nothing is logged.

Repository side: the trusted definitions and the axioms above are recorded in `notes/STATUS.md`.
Also there: `metadata.FromIncomingContext.spec` and `tokenProviderOk`, before this branch, claimed
behavior for a nil context, on which Go panics.

## Reviewer

A fresh reviewer read the specs, the axioms and the PR. It raised these points:
- The specs did not capture the PR's intent. Addressed: `logIcStoresIP`.
- `tokenProviderOk` was false for JWT on a nil context. Addressed: it is now premised on
  `ctxClientIPOk`.
- The `AuthInfoFromTLS` and `logUnaryRequestStats` axioms were left over any context.
  Addressed: both are now premised on `ctxClientIPOk`.
- `ctxClientIPOk_of_txnCtx` is broader than needed. Still open, as above.

It confirmed that the `srvInterceptorOk` generalization and `WithValueClientIP` are sound, and
that `grpcRunCtx` holds of grpc v1.84's contexts. It also found findings 1–5 and wrote
`peer_nil_addr_test.go` and `unixaddr/`.
