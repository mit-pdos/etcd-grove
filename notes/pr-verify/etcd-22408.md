## Verdict

The change does what it says and is safe as far as verified. It fixes a real bug in the pinned code
(`issues/etcd-cache-config-retry-unread.md`): the three `Config` fields were never read. With the
PR, `newCache` rejects exactly the three new bad configurations. Every retry timer of the watch
loop is in `[InitialBackoff, MaxBackoff]`, and its schedule is `min(InitialBackoff·2^k,
MaxBackoff)`. The bootstrap `Get` runs on a `GetTimeout` context that is cancelled on return, with
all existing guarantees of the cache kept (full `lake build`, unchanged trust base). The proof
needs one premise, `MaxBackoff < 2^62`, because the PR's `backoff *= 2` wraps above it.

Three behaviors are worth raising with the author, none a safety bug:
- (a) the doubling overflow (theoretical with a real clock);
- (b) `GetTimeout` applies to every bootstrap attempt, so a prefix whose full `Get` takes longer than `GetTimeout` (5s by default) never bootstraps, where it used to;
- (c) the backoff is never reset after a healthy watch (the PR says this is deliberate).

All three are shown by Go tests. Not covered: liveness (that the timeout actually ends a hung `Get`, that the cache becomes ready), which this logic cannot state.

### The specs, old and new

- **`newCache`** (`Spec/go_etcd_io/etcd/cache/v3/newCache.lean`, result `newCacheResult` in
  `InvNew.lean`).
  - Old: it rejects `HistoryWindowSize ≤ 0` or `BTreeDegree < 2`, and otherwise returns a cache.
  - New: it also rejects `InitialBackoff ≤ 0`, `MaxBackoff < InitialBackoff` and `GetTimeout ≤ 0` (`CfgValid`). An accepted configuration must satisfy `CfgBounded`, which now also requires `MaxBackoff < 2^62`.
  - The new spec does not hold of the old code, which returns a cache for `InitialBackoff = 0` (argued from the code; not proved against the `lean` translation).
  - The proof now takes the existing trust-boundary `fmt.Errorf` spec (`Spec/fmt/Errorf.lean`), because the error messages format `time.Duration`s with `%v` (`Duration.String`). Perennial's own `fmt.Errorf` spec only admits basic-typed arguments.
- **`Cache.getWatchLoop`** (`Spec/go_etcd_io/etcd/cache/v3/Cache__getWatchLoop.lean`). The triple's text is unchanged: it keeps the writer and the wait-group token and returns once the internal context is done. What changed is `isCacheFields`, in its precondition:
  - The cache's clock is now `isClockFor cf.clock (cacheClockOk cf.cfg)`. `NewTimer(d)` is only specified for `d ∈ [InitialBackoff, MaxBackoff]` or `d = ProgressNotifyInterval` (`Cache.Watch`'s timer).
  - It also carries `BackoffOk cf.cfg`: `0 < InitialBackoff ≤ MaxBackoff < 2^62`.
  - The proof therefore has to show that every retry timer is in range. A loop that retried without waiting (`d = 0`, or a negative `d`) fails to verify. Before, `isClock` allowed any `d`, and the old constant `time.After(50ms)` was not tied to the configuration at all.
  - The loop invariant ties the Go `backoff` variable to `backoffAt cfg k`. `backoffAt_eq_min` shows that this schedule is `min(InitialBackoff·2^k, MaxBackoff)` under `BackoffOk`.
  - The schedule itself is not in the triple, because the model has no time.
  - `realClock` still meets the stronger requirement: any `isClock` is an `isClockFor` for every predicate (`isClock_isClockFor`), so `newCache` passes it through from `isClock clk`.
- **`Cache.get`** (`Spec/go_etcd_io/etcd/cache/v3/Cache__get.lean`).
  - Unchanged: either the client's error and nothing changed, or a response at or above the revision bound, restored into the store.
  - The client `Get` now runs on `context.WithTimeout(ctx, c.cfg.GetTimeout)` (Perennial's proved `context.WithTimeout`). The derived context is a valid context for the client's linearizable `Get` (`isEtcdKVE` is quantified over every context), and the deferred `cancel()` is run on both returns.
  - What the PR is for, that a hung `Get` now ends, is a liveness property and outside this logic.

## Findings

In the PR. None breaks a guarantee the cache had. Each comes with a Go test in `notes/pr-verify/etcd-22408/` (see its README).

1. **The doubling overflows** (low; theoretical with a real clock). `New` accepts any `InitialBackoff ≤ MaxBackoff`.
   - With `MaxBackoff ≥ 2^62` ns (about 146 years), `backoff *= 2` wraps to `math.MinInt64`. That is not above `MaxBackoff`, so the next timer is negative and every later one is 0: the loop retries without waiting.
   - Lean: `backoffAt_wraps`, for `InitialBackoff = MaxBackoff = 2^62`, which `CfgValid` accepts.
   - Go: `TestCacheBackoffStaysPositiveWithLargeMaxBackoff` (`backoff_probe_test.go`, with a fake clock). At the PR head the timers are `[1281023h53m38s, -2562047h47m16s, 0s]` (`backoff_probe-head.log`).
   - With a real clock, one wait of at least 146 years comes first, so it is unreachable in practice. A user writing `WithMaxBackoff(math.MaxInt64)` for "no cap" would still hit it in tests with a fake clock.
   - The proof records it as `CfgBounded`'s `MaxBackoff < 2^62`.
   - Fix: `if backoff > c.cfg.MaxBackoff/2 { backoff = c.cfg.MaxBackoff } else { backoff *= 2 }`, or reject `MaxBackoff > math.MaxInt64/2` in `newCache`.
2. **`GetTimeout` bounds every bootstrap attempt, so a slow but healthy `Get` never completes** (medium).
   - `Config` documents `GetTimeout` as "the timeout applied to the first Get() used to bootstrap". The PR applies it to each retry's `Get`, with the default of 5s. A prefix whose full `Get` takes longer (a large keyspace, a loaded server) now never bootstraps: every attempt hits the deadline, and the cache re-issues a full-prefix `Get` about every 7s, each costing the server its range work. Before the PR, the first attempt completed.
   - `TestCacheBootstrapsWithSlowGet` (`backoff_probe_test.go`, `synctest`): with a 6s `Get` and default options, the PR head starts 10 `Get`s in a minute and completes none (`backoff_probe-head.log`). The base completes the first (`backoff_probe-base.log`).
   - This is the documented behavior, and the only escape is `WithGetTimeout`, so it is a question of defaults and documentation rather than a bug. Worth saying in the doc comment, or growing the timeout with the backoff.
3. **The backoff is never reset after a healthy watch** (medium; the PR says this is deliberate).
   - After a few disconnects over the cache's lifetime, every later reconnect waits `MaxBackoff`, even after hours of healthy watching. The cache is not ready during that wait (`ready.Reset()`), so `Get`/`Watch` block in `WaitReady` for `MaxBackoff` instead of `InitialBackoff`.
   - This reads against `InitialBackoff`'s doc ("the first delay to wait before retrying an upstream etcd Watch after it ends with an error") and is a regression from the base's constant 50ms.
   - `TestReviewBackoffNeverResetsAfterHealthyWatch` (`backoff_reset_test.go`, by the reviewer; `synctest`, a watch healthy for 1h and then cancelled, ten times). At the PR head the downtimes are `[50ms 100ms 200ms 400ms 800ms 1.6s 2s 2s 2s 2s]` (`backoff_reset-head.log`); at the base the test passes (`backoff_reset-base.log`).
   - Possible fix: reset `backoff` to `InitialBackoff` once a retried watch has made the cache ready.

In the existing (pinned) code, recorded in `issues/`: `issues/etcd-cache-config-retry-unread.md`. `InitialBackoff`, `MaxBackoff` and `GetTimeout` are documented and settable but never read. This PR fixes it: the PR's own tests fail at the base (`base-pr-tests.log`), and the proof shows the PR's code uses all three as documented (safety part).

The reviewer's other points were resolved:
- Its main critique, that the first version of the `getWatchLoop` triple did not constrain the backoff at all, is fixed by `isClockFor` and `BackoffOk` above.
- The postulates are sound (above).
- The fork's `watch_retry_test.go` change is needed and not flaky in principle.
- `Close` during the timer is handled: `ctx.Done`, then `Stop` and return; a simultaneous ready timer is caught by the `ctx.Err()` check at the top of the loop.
