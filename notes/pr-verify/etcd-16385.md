# etcd-io/etcd#16385: client: Added new session option to set timeout for session creation

- **PR**: https://github.com/etcd-io/etcd/pull/16385, head `524448aa21033724a48d9e6f36d98d097574fbe9`
  (one commit, open, approved by fuweid, jmhbnz and lhmzhou, waiting on ahrtr/serathius). It was
  opened in 2023 and rebased onto `main` at `d3c8a1559` on 2026-10-13. It addresses
  etcd-io/etcd#14631: `concurrency.NewSession` hangs while no member is reachable, because the
  client's calls use gRPC's `WaitForReady`. The stale bot closed the issue in 2025 as not planned,
  with no fix. **The PR is not superseded**: upstream `main` (`b25719d10`, 2026-10-16) has no
  creation timeout for sessions.
- **Verified at**: `mit-pdos/etcd-grove` branch `pr-etcd-16385-goose-lean`, commit `bd46a46e5`.
  That is the fork's `goose-lean` at the pin `09669450f`, plus the PR's diff (`session.go`,

  the PR's code.
- **Fork checks**: `go build ./...` passes. `go test ./concurrency/` of `client/v3` passes. The
  PR's integration tests `TestCreationTimeout` and `TestTimeoutDoesntAffectSubsequentConnections`

- **This repository's branch**: `pr-verify/etcd-16385`.

## Verdict

The change is sound as far as it was verified, and it does what it says:

- `WithCreationTimeout(d)` sets the timeout when `d > 0`. Otherwise it logs a warning and keeps the
  current value.
- `NewSession` derives a context with that timeout from the options' context. It uses it only for
  the lease `Grant`, and cancels it on return.
- The session's own context, and the keep-alive, are still derived from the options' context.
  This is the property the maintainer asked for: the timeout does not affect the session after
  creation.

Both functions are proved, with no new axiom and no `sorry`. `NewSession`'s new spec implies the
old one, so its callers are unaffected (`leasingKV.monitorSession` was rebuilt).

What is not covered:

- The timeout's purpose is liveness ("returns instead of hanging"), which Hoare triples do not
  state. The probes and the PR's tests show it.
- The spec does not pin down that the keep-alive gets the options' context rather than the
  creation context (open spec gap 1 below).

Findings on the PR are documentation-level:

- the option's doc comment is wrong for `d <= 0`;
- the doc does not say that the timeout covers only the lease grant, and does nothing with
  `WithLease`;
- small nits in the log field, the CHANGELOG entry and the test.

No bug was found in the pinned code.

## The specs

- **`WithCreationTimeout(d)`** (`Spec/go_etcd_io/etcd/client/v3/concurrency/WithCreationTimeout.lean`,
  proof `Proof/.../WithCreationTimeout.lean`): it returns an option with transformer
  `withCreationTimeoutM d`, defined in `Proof/.../InvSession.lean`.
  - The transformer sets `creationTimeout := d` if `0 < sint.Z d`. That is Go's signed
    `timeout > 0` on `time.Duration`, so negative durations keep the value.
  - Otherwise the options are unchanged; the warning goes through the `zap` trust-boundary
    axioms, as for `WithTTL`.
- **`NewSession`, old spec** (`lean`'s `Spec/.../NewSession.lean`, restated as `NewSession.spec_old`
  in `Proof/.../NewSession.lean` over the extended options):
  - `nil` with an error, or
  - a session (`isSession`) whose lease is the options' lease if they name one, or a granted one.
- **`NewSession`, new spec** (`Spec/.../NewSession.lean`): the same, and the session's context has
  the **values and deadline of the options' context** (`sessionCtxOf s pcs`, `InvSession.lean`).
  - The difference is one conjunct: the session's context is not derived from the creation
    timeout's context.
  - Perennial's `context.WithTimeout` spec gives that context a fresh deadline `some d`, which the
    proof cannot choose. So a version that derived the session's context from it, directly or
    through `WithCancel`, would fail this spec. That would be the regression the maintainer warned
    about in review.
  - `NewSession.spec_implies_old` (new ⇒ old) is proved. The old code also meets the new spec:
    the conjunct pins down that the PR kept the session's context where it was, not what it
    changed.
- **What the proof covers**:
  - `context.WithTimeout` (Perennial's proved spec) and the deferred cancel. The `defer` slot holds
    "runs and returns" (`deferOk`), joined over the two branches of `if ops.creationTimeout > 0`
    with `wp_join`. The deferred cancel is run before every one of the five returns.
  - `Grant` with the creation context, for any context descriptor.

## Findings

All of these are in the PR, at documentation level. None is a bug in the pinned code, so
`issues/` is unchanged. The probes are in `notes/pr-verify/etcd-16385/` (see its `README.md`); all
pass at the PR head and on the fork branch.

1. **The doc comment is wrong for `timeout <= 0`.** It says "If timeout is <= 0, no timeout will be
   used". The code keeps the current value, as its log message says ("preserving current
   timeout"), so `WithCreationTimeout(500ms), WithCreationTimeout(0)` still times out after
   500ms (`TestNewSessionCreationTimeoutNonPositiveKeepsEarlier`). The proved spec models the code.
   `WithTTL`'s comment has the same shape, but there it is accurate, since its default is 60s.
2. **The timeout covers only the lease grant; the doc should say so.**
   - With `WithLease`, `Grant` is skipped and the option does nothing. That is harmless today,
     since `KeepAlive` does not wait for the server (`TestNewSessionCreationTimeoutWithLease`
     returns at once against an unreachable endpoint).
   - If the deadline fires after the server granted the lease but before the response arrives,
     `NewSession` returns `DeadlineExceeded` and the lease lives until its TTL. This could already
     happen with a canceled `WithContext` context; a short creation timeout makes it likelier.
   - The timeout is derived from the options' context, so an earlier deadline there still wins.
     That is correct, but undocumented.
3. **Nits.**
   - The warning logs the current timeout as raw nanoseconds (`zap.Int64(...,
     int64(so.creationTimeout))`); `zap.Duration` would be readable, and the rejected value is not
     logged.
   - The CHANGELOG line has no PR link, unlike its neighbor, and says "concurrent session" rather
     than naming `WithCreationTimeout`.
   - In `TestTimeoutDoesntAffectSubsequentConnections`, `defer close(errorc)` can race with the
     `Put` goroutine's send if the second `select` times out (send on a closed channel). A buffered
     channel without the close avoids it.

### Reviewer, and open spec gaps

A fresh reviewer subagent found no soundness problem.

- It confirmed that the options model is faithful (signed comparison, zero value, other options
  keep the field).
- It confirmed that the deferred cancel is handled at every return, and that `spec_implies_old`
  and the caller's rebuild are sound.
- It raised findings 1 to 3 above.

It also raised two gaps, recorded as open in the spec's docstring:

1. **The spec does not exclude passing the creation context to `KeepAlive`.** The lease client's
   `KeepAlive` triple (`isEtcdLease`, `Proof/go_etcd_io/etcd/cache/v3/InvEtcdTxn.lean`) takes any
   context and promises nothing of the stream. So a version calling `KeepAlive(sessionCreationCtx,
   id)` would still verify, although the deferred cancel would end the keep-alive at return. That
   is exactly the regression the maintainer warned about; the PR's
   `TestTimeoutDoesntAffectSubsequentConnections` catches it in Go.
   - Likewise, a creation context made with `WithCancel` alone, with the session's context derived
     from it, would keep values and deadline, and so would pass.
   - Closing this needs a `KeepAlive` spec that ties the stream's life to its context, a change to
     the shared lease-client spec that is outside this PR's scope.
2. **The spec does not say that `Grant` gets the creation context.** `Grant`'s triple accepts any
   context, so a version that never used the timeout would also verify. This is the liveness part,
   which Hoare triples do not state; the probes `TestNewSessionNoCreationTimeoutBlocks` and
   `TestNewSessionCreationTimeout` show it in Go.
