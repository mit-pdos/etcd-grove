## Verdict

**The change is correct, and redundant on current `main`.**

- **What is proved**: the PR's code meets the existing spec of `AuthInfoFromCtx`, re-proved
  unchanged.
  - The proof shows that in both branches of the new `if`, the token passed to
    `authInfoFromToken` is `strings.TrimPrefix(ts[0], "Bearer ")`, which is the code on `main`
    (#21910).
  - No new panic: the slice's bounds are guaranteed by the `HasPrefix` before it.
- **Tested**:
  - The probe tests show the same accepted and rejected forms at the PR head, on the fork and on
    `main`.
  - The reviewer's test shows that the PR fixes #19752's websocket path end to end:
    `wsproxy` → `Authorization: Bearer <tok>` → `authorization` metadata → `AuthInfoFromCtx`. The
    test fails at the PR's base.
- **Not covered**: the spec does not say which token is checked. Its postcondition is
  "nil/nil, `authInfoFromToken`'s result, or nil/`ErrInvalidAuthToken`", and `authInfoFromToken`'s
  spec ignores the token. So the bearer behaviour itself is shown by the proof's intermediate step
  and by the tests, not by the spec (open point 1).
- **Recommendation**: rebased onto `main`, the PR would change only the form of the strip
  (`HasPrefix` and slice instead of `TrimPrefix`) and add tests. It could be closed as superseded
  by #21910, and #19752, still open, could be closed as fixed by #21910.

## Findings

- **Bugs in the PR**: none.
  - No panic: the slice is guarded by `HasPrefix`, so its length is at least 7. The existing
    `ts[0]` on an empty metadata slice is unchanged and already recorded in
    `issues/etcd-auth-token-md-empty.md`.
  - No token confusion: simple tokens and JWTs contain no space, so no valid token starts with
    `"Bearer "`. `X` and `Bearer X` are the same token, and only one prefix is stripped.
  - No concurrency change: the strip works on immutable strings.
- **A design point, shared with #21910**:
  - The scheme is matched case-sensitively, with exactly one space. RFC 7235 makes the
    auth-scheme case-insensitive, so `bearer <tok>` (which some proxies send) is still rejected,
    as are `Bearer  <tok>` and a tab. See `notes/pr-verify/etcd-19775/server/auth/bearer_scheme_test.go`.
  - etcd's own paths (the websocket proxy, the grpc-gateway, the client) send exactly
    `"Bearer "` or a raw token.
- **Existing code, recorded in `issues/`**: `issues/etcd-auth-simple-token-delete-logs-token.md`.
  The simple-token keeper still logs an expired token in plaintext at Debug level
  (`simple_token.go:175`), which #20934's fingerprinting missed. The reviewer found it. It is not
  in the verified code.
- **Reviewer's open points**:
  1. The spec is token-agnostic. The reviewer's cheap way to state "`authInfoFromToken` receives
     the header's first value with one leading `Bearer ` removed" has two steps. It is not done
     here, since on `main` the PR is a no-op.
     - (a) An opaque `incomingMD ctx` in the trust-boundary spec of grpc's
       `metadata.FromIncomingContext`, relating the returned map to the context.
     - (b) An `AuthInfoFromCtx` spec that is higher-order in its callee's postcondition
       `Q token a ok`. The existing `authInfoFromToken` spec would be its instance, so
       `Link.lean` still closes.
     - Saying which *user* comes back would also need a token-validity relation in
       `tokenProviderOk` (`InvAuth.lean`).
  2. grpcproxy's `getAuthTokenFromClient` forwards only the `token` key, not `authorization`. This
     predates the PR and is outside the verified code.
