## Verdict

The four helpers are correct for the uses they are meant for, and all four are verified with no
`sorry` and no new axiom:
- `Len` returns the number of items.
- `ReplaceLatest` replaces the newest item.
- `RemoveLess(rv)` keeps exactly the items with revision `≥ rv`, in order.
- `ensureCapacity` keeps the items and doubles the capacity to the least `cap·2^k ≥ minCapacity`.

All four are proved against the ring buffer's existing representation predicate, whose invariant
(slots, head/tail/size, strictly increasing revisions) is unchanged and preserved by each of them.

Two findings, neither reachable in etcd today since nothing calls these methods:
1. **`ReplaceLatest`'s doc gap.** `ReplaceLatest` does not check, and its doc comment does not
   state, that the new item's revision must be above the second-newest one's. A lower revision
   silently breaks the ordering that every lookup's binary search relies on.
2. **`ensureCapacity` overflow.** The doubling loop in `ensureCapacity` overflows `int` for
   `minCapacity > 2^62`. With a power-of-two length it never terminates.

Not covered:
- **Slot zeroing.** The specs do not say that `RemoveLess` and `RebaseHistory` zero the slots
  they free (unused slots may hold anything in the predicate). The zeroing only affects memory
  retention.
- **Future callers.** If a caller of `ensureCapacity` appears, the cache's invariants, which fix
  the ring's capacity, would need to change (see "Callers").

### The specs

All four are over `ownRingBuffer r cap isItem revOf items` (`InvRingBuffer.lean`): the ring has
`cap` slots and holds `items`, oldest first, with strictly increasing revisions.

- **`Len`** (`Spec/go_etcd_io/etcd/cache/v3/ringBuffer__Len.lean:26`).
  - Precondition: any fraction of the ring (a reader's).
  - Returns `items.length`.
- **`ReplaceLatest(item)`** (`ringBuffer__ReplaceLatest.lean:30`).
  - Preconditions:
    - `items ≠ []`. Go panics on an empty ring; the spec excludes it.
    - `item` models `v`.
    - `RevAbove revOf items.dropLast v`: `v`'s revision is above the item before the newest.
  - Postcondition: the ring holds `items.dropLast ++ [v]`.
  - The premise is exactly what keeps the revisions sorted, and it is as weak as possible. It
    allows the k8s use: there, a same-revision `add` replaces the last element, and an older one
    panics.
- **`RemoveLess(rv)`** (`ringBuffer__RemoveLess.lean:32`).
  - Postcondition: the ring holds `removeLessItems revOf rv items`, that is
    `items.filter (rv ≤ revision)`, which is what the doc comment says.
  - The proof shows that under sortedness this is `items.drop (ltCount …)`
    (`removeLessItems_eq_drop`, `Proof/.../ringBuffer__RemoveLess.lean:31`): the index
    `findFirstIndexGreaterOrEqual` returns is where the kept items start.
  - All three exits are proved: the empty ring, nothing below `rv`, and everything below `rv`
    (through `RebaseHistory`).
- **`ensureCapacity(minCapacity)`** (`ringBuffer__ensureCapacity.lean:30`).
  - Precondition: `minCapacity ≤ 2^60`.
  - Postcondition: for some `k`, the ring holds the same items with capacity `cap·2^k`, where
    `minCapacity ≤ cap·2^k` and `cap·2^j < minCapacity` for every `j < k`. So `k` is the least
    such exponent, and `k = 0` (nothing changes) when the ring is already big enough.
  - The bound `2^60` keeps the result within the predicate's `2^61` slots. Nothing allocatable
    lies above it, and Go's arithmetic is safe up to `2^62`.
  - The new layout (`tail = 0`, `head = size`), which the PR's test checks, is internal: the
    predicate abstracts it away, and no method can observe it.
- `ReplaceLatest` and `ensureCapacity` require `isItem` to be persistent, as `Append` already
  does. The cache's two instances, `batchAt` and `snapCert`, are.

Since the functions are new, there is no old spec to compare with and no `spec_implies_old`
lemma.

## Callers (step 6)

`ringBuffer` is unexported, and none of the four methods is called outside tests, in the
fork or upstream (`grep` over `cache/`). So no caller graph needed exploring.

The existing proofs of the cache package all rebuild against the new translation:
`Proof.go_etcd_io.etcd.cache.v3.{Link,Results}`, and the full `lake build`.

One consequence for the future: `ensureCapacity` is the only method that changes the
capacity. The cache's invariants fix the capacity: `DemuxInv cap c` and the demux's lock
(`InvDemux.lean`), and the store lock (`InvStore.lean`). A caller of `ensureCapacity`, such as
a grow-on-full policy like k8s's, would have to make `cap` existential there and re-prove
`demux__updateStoreLocked` and `demux__resyncLaggingWatchers`, which read `full()`.

## Findings

### Findings about the PR

Both findings are in the PR's code, which is not merged, so they are recorded here and not in
`issues/`. Their tests are in `notes/pr-verify/etcd-21676/` (`README.md` lists each).

1. **`ReplaceLatest` accepts a revision that breaks the ordering (doc gap).**
   - Its doc comment says only "overwrites the most recently appended entry". With stored
     revisions 5, 10, `ReplaceLatest` of revision 3 leaves 5, 3.
   - After that, `AscendGreaterOrEqual(4)` visits revision 3, and `RemoveLess(4)` keeps it:
     `TestReplaceLatestBreaksOrdering`, which fails on the PR head.
   - The verified spec needs `RevAbove items.dropLast v` (`v`'s revision above the second
     newest).
   - k8s's equivalent checks the revision (it panics on an older one). `Append` has the same
     unstated requirement, but its only callers in the cache guarantee it.
   - Suggested fix: document the requirement (newer than the second-newest entry, typically
     the same revision as the replaced one) or check it.
2. **`ensureCapacity` loops forever for `minCapacity > 2^62` (bug, unreachable today).**
   - `newCap *= 2` overflows `int`. With a power-of-two length, `newCap` goes from `2^62` to
     `-2^63` to `0` and stays `0`, so the loop never ends: `TestEnsureCapacityOverflowHangs`,
     which fails on the PR head.
   - With another length the doubling ends above `minCapacity`, and `make` panics
     (`makeslice: len out of range`): the reviewer's `TestReviewEnsureCapacityHugeNonPow2`.
   - Such sizes cannot be allocated anyway, so this is a robustness point for an unexported,
     unused helper. A bound check, or `newCap <<= 1` guarded by `newCap <= maxInt/2`, would
     make it panic cleanly.

### Other results

- **No bug in the existing code.** Nothing was found in the existing ring buffer, and nothing
  was added to `issues/`.
- **A randomized test passes.** The reviewer's `TestReviewRingBufferModel` runs 2000 random
  runs of `Append` and the four new methods against a list model, with callers keeping the
  verified premises, and passes.

### Reviewer's points

A fresh reviewer read the PR and the specs; none of its points is open:
- The specs match the PR's doc comments and tests.
- Each postcondition determines the result. The `∀ j < k` clause fixes `k` because `cap > 0`.
- The premises are as weak as the invariant allows.
- `minCapacity ≤ 0` is a no-op, which is right.
- A capacity-0 ring is excluded by the predicate (`RingOk.cap_pos`). Go would grow it to 1.

The reviewer also raised:
- **Slot zeroing.** Not specified, as noted above. This is a deliberate abstraction of the
  existing predicate, not a gap in this PR's verification.
- **`issues/` entries.** The reviewer suggested `issues/` entries for the two findings. Per the
  skill, findings about unmerged PR code go in the report, not `issues/`.
