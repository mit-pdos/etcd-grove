## Verdict

The change is sound and does what it says. `resyncDelay` is proved to return the documented delay,
and that delay is always positive, whatever the measured `syncDuration` (zero or negative
included). When `syncDuration > 0` the delay is the same as before. Over the PR,
`syncWatchersLoop`'s spec (it returns, with no panic) is re-proved unchanged with Perennial's
`time.Since`, which may return any duration. So this repository's clock assumption, that
`time.Since` is positive, is no longer needed and is deleted from the trust base. That assumption
was how the proof recorded the open finding `issues/etcd-watch-sync-ticker-reset-zero.md` (the
same bug as etcd#22296), so the proof confirms the fix. Nothing in the PR is left unverified: the
whole change is the helper and its one call.

### The specs

- `resyncDelay`: `Spec/go_etcd_io/etcd/server/v3/storage/mvcc/resyncDelay.lean`, proved in
  `Proof/go_etcd_io/etcd/server/v3/storage/mvcc/resyncDelay.lean`. It returns
  `mvcc.resyncDelayOf sd last un`, which is `sd` if `un ≠ 0 ∧ last > un ∧ sd > 0` (all signed) and
  `100ms` otherwise, together with `0 < d` (`resyncDelayOf_pos`).
- `syncWatchersLoop`: `Spec/go_etcd_io/etcd/server/v3/storage/mvcc/watchableStore__syncWatchersLoop.lean`,
  unchanged. Its proof (`Proof/.../watchableStore__syncWatchersLoop.lean`) takes `resyncDelay`'s spec
  as a hypothesis instead of the local `time.Since` spec, and discharges `Ticker.Reset`'s premise
  (`0 < d`, `Spec/time/Ticker__Reset.lean`) from `resyncDelay`'s postcondition.
- **Against the old code**: the old proof discharged `Reset(syncDuration)`'s premise only through
  the positivity axiom. With Perennial's `time.Since` (any `w64`), the progress branch's
  `Reset(syncDuration)` cannot be proved: that is the `Reset(0)` panic. So the unchanged spec, over
  the honest clock spec, is what pins down the PR's change.

## Findings

- No bug in the PR. The reviewer (a fresh subagent) checked: the signed comparisons; the fallback
  value; that no other proof relied on the deleted axiom (every other `time.wp_Since` user already
  used Perennial's); that the base code cannot meet the spec without it; and that the behavior is
  identical for `syncDuration > 0`. A very small positive `syncDuration` (say 1ns) still re-arms the
  ticker that fast. That was already so before the PR, it is not a regression, and the branch
  runs only while the unsynced set shrinks.
- A probe, `notes/pr-verify/etcd-22297/resync_delay_probe_test.go`, checks `resyncDelay` against
  its doc comment over edge values (`math.MinInt64` to `math.MaxInt64` durations, `math.MinInt` to
  `math.MaxInt` counts) and passes each value to `Ticker.Reset`. It passes at the PR head and on the
  fork branch (`notes/pr-verify/etcd-22297/README.md`).
- The existing finding `issues/etcd-watch-sync-ticker-reset-zero.md` is fixed by this PR, and the
  proof confirms it. The branch's copy of the issue records that.
- No new bug in the existing code.
