## Verdict

**The change does what its first sentence says: a `NewCtxClient` client now carries exactly the
call options a `New` client gets, proved. But it is not the harmless default the PR presents.
Every call through such a client now passes `WaitForReady(true)`, a 2 MiB send limit and an
unlimited receive limit, and these override whatever the caller configured on its own gRPC
connection. Requests over 2 MiB that worked before now fail, a caller's lower receive limit and
fail-fast setting are silently lost, and the caller still cannot change any of it.** For etcd's
own embedded client (`v3client.New`) the change is a no-op: its in-process adapters ignore call
options.

- **Proved** (no `sorry` of this work, no new axiom): `NewCtxClient` returns a non-nil client
  whose `callOpts` is the package's `defaultCallOpts` slice, which holds `options.go`'s three
  options (`FailFast: false`, send 2 MiB, receive `MaxInt32`), full and read-only (`callOptsAt`,
  what the client's KV-path proofs need of a client's call options). Its logger is non-nil (the
  options' or `zap.NewNop()`), its context a child of the caller's, its service interfaces nil.
  `WithZapLogger`'s option writes only the logger. `NewKVFromKVClient(remote, c)` gives a `KV`
  whose every call passes `c.callOpts`.
- **The old code does not meet the new spec**: it stores the nil slice (length 0) where the spec
  says `dsl`, of length 3. The spec pins down what the PR changed.
- **Shown by tests, not proved** (the gRPC transport is a trust boundary here, its option handling
  not modeled): grpc applies a call's options after the connection's
  (`combine(cc.dopts.callOptions, opts)`, grpc v1.80.0 `call.go`/`stream.go`), so the per-call
  defaults win. Probes at the upstream base and the PR head (`notes/pr-verify/etcd-21809/`):

  | probe (`KV` from `NewKVFromKVClient` over a `NewCtxClient` client, caller's own connection) | base | head |
  |---|---|---|
  | get a 5 MiB value (the PR's case) | fails (4 MiB) | passes |
  | put a 3 MiB value | passes | **fails** (2 MiB) |
  | put 3 MiB over a connection whose default send limit is 64 MiB | passes | **fails** |
  | get 5 MiB over a connection limiting receives to 1 MiB (reviewer) | refused, as configured | **accepted** |
  | put to an unreachable server, connection `WaitForReady(false)` (reviewer) | `Unavailable` at once | **blocks until the deadline** |
  | put to an unreachable server, grpc's defaults | `Unavailable` at once | **blocks until the deadline** |
  | put 3 MiB with an interceptor appending `MaxCallSendMsgSize(64 MiB)` (reviewer) | passes | passes |

- **The PR's premise is not right either**: before the PR, a ctx client's calls passed no
  options, so `grpc.WithDefaultCallOptions(grpc.MaxCallRecvMsgSize(...))` on the caller's own
  connection already lifted the 4 MiB limit (reviewer's `TestReviewDialRecvLimit`, which passes at
  the base). After the PR, connection-level options no longer work for these three settings; only
  an interceptor does.
- **Not covered**: the gRPC library itself (how options combine is read from its source and
  tested, not proved); the other `New*FromXClient` constructors (`Lease`, `Watcher`,
  `Maintenance`, `Cluster`, `Auth`), which copy `c.callOpts` the same way as `NewKVFromKVClient`
  (read, not translated); options other than `WithZapLogger` (the spec assumes an option writes
  only the logger).

### The spec of the behavior change

- **Old** (no Lean statement: the function was not translated): the client's `callOpts` is the

## Findings

1. **PR behavior: a 2 MiB send limit nobody can raise.** At the PR head, a ctx client's calls
   carry `MaxCallSendMsgSize(2 MiB)`. They override the connection's default (grpc's
   `MaxInt32`, or what the caller set), so requests over 2 MiB fail with `ResourceExhausted`,
   where they succeeded before. `callOpts` is unexported and no `Option` sets it: only a client
   interceptor can undo it. Tests: `TestCtxClientLargeRequest`,
   `TestCtxClientLargeRequestDialLimit` (`notes/pr-verify/etcd-21809/ctx_client_call_opts_test.go`,
   output in `probe-upstream.log`).
2. **PR behavior: `WaitForReady(true)` and the receive limit override the caller's connection.**
   - A call to an unreachable server used to fail at once with `Unavailable`. Now it blocks until
     the caller's deadline, or forever with `context.Background()`: a caller-built connection has
     neither etcd's retry interceptor nor its health checking.
   - A caller's lower receive limit is replaced by `MaxInt32`.
   - Tests: `TestCtxClientUnreachableFailsFast`, and the reviewer's `TestReviewDialFailFast` and
     `TestReviewDialRecvLimitLowered` (`review_ctx_client_test.go`, `review.log`).
3. **PR premise**: connection-level `grpc.WithDefaultCallOptions` already solved the 4 MiB problem
   before the PR (`TestReviewDialRecvLimit` passes at the base). The PR makes that way stop working
   for these three settings.
4. **No bug in the existing (pinned) code was found**; nothing added to `issues/`. (The reviewer
   noted that `NewKV(c)` on a ctx client builds over a nil connection and would fail on first use.
   That is what "no underlying grpc connection" documents, so it is not recorded.)
5. **Reviewer's points on the specs, resolved**:
   - The spec's header misstated the old behavior as grpc's defaults (it is the connection's).
     Fixed.
   - `defaultCallOptsVar` first recorded only "three scalar options". It now pins their values
     (`defaultCallOptVals`), so the spec records the send-limit change.
   - `ctxClientOptOk` is narrower than Go's contract. Recorded as a limit of coverage, above.

## Draft review comment

> The change makes a `NewCtxClient` client match `New`'s call options, but for callers that pass
> their own gRPC clients (the case this PR is for) it also changes behavior in ways the
> description doesn't mention. grpc applies per-call options after the connection's
> `WithDefaultCallOptions`, so `defaultCallOpts` now overrides whatever the caller configured:
>
> - the send limit drops from grpc's default `MaxInt32` to 2 MiB, so a 3 MiB put that works today
>   fails with `ResourceExhausted`, even over a connection created with
>   `grpc.WithDefaultCallOptions(grpc.MaxCallSendMsgSize(64<<20))`;
> - `WaitForReady(true)`: a call to an unreachable server used to fail right away with
>   `Unavailable`, now it blocks until the context deadline (forever without one), since the
>   caller's connection has no etcd retry interceptor;
> - a caller's own lower `MaxCallRecvMsgSize` is replaced by `MaxInt32`.
>
> Since `callOpts` is unexported and there is no `Option` for it, a caller can't change any of
> these, except by a client interceptor that appends options after the per-call ones. Also, before
> this change the 4 MiB receive limit could already be raised with
> `grpc.WithDefaultCallOptions(grpc.MaxCallRecvMsgSize(...))` on the caller's connection, because
> ctx clients passed no per-call options.
>
> Would an option like `WithCallOptions(opts ...grpc.CallOption) Option` (or documenting
> `WithDefaultCallOptions`) fit better than applying `defaultCallOpts` unconditionally? If the
> defaults stay, it would be worth a CHANGELOG line about the 2 MiB send limit and `WaitForReady`.
> I have tests for each case if useful. (For `v3client.New` the change is a no-op: the
> grpcproxy adapters ignore call options.)
