## Verdict

The PR is not correct as written.
- Its new `shouldSnapshotToDisk` returns true whenever anything was applied since the last disk
  snapshot. The flag was removed, but its disjunct was kept.
- So the apply loop takes a disk snapshot after every applied batch: a backend commit with fsync,
  plus a WAL snapshot record with fsync. `--snapshot-count` is ignored.
- This is proved exactly (`shouldSnapshotToDisk.spec`, `pr_ne_intended`) and shown by tests: 24 WAL
  snapshot records after 20 puts.
- The same change makes the unit-test servers, which have no KV, crash in `snapshot()`. That explains
  the failing CI.

The obvious one-line repair is not safe either. That repair drops the disjunct, leaving the
snapshot-count rule alone, which is also what the removed TODO suggests. It loses the WAL snapshot
record that the old forced snapshot wrote after a downgrade. A v3.6 member restarted on the downgraded
data then replays the earlier `ClusterVersionSet{3.7}` entry and panics in `MustDetectDowngrade`.
etcd's own e2e test `TestDowngradeUpgradeClusterOf1`, run with a v3.6.15 binary, shows this.

The other half of the PR is sound as far as it was checked:
- `ForceSnapshot` committing the backend is proved under the backend's commit contract.
- It cannot deadlock where it is called.
- It persists a consistent index that matches the batch's contents.

But it does not replace what the forced snapshot did. A correct cleanup has to keep a forced WAL
snapshot on downgrade.

Not covered by the proofs:
- crash and restart;
- the WAL;
- other binaries' versions (the downgrade finding rests on the e2e test and on reading v3.6's code);
- performance;
- the apply package's view of `ForceSnapshot` (`isSnapshotServer`), which is still an undischarged
  premise, as before the PR.

## Specs, old and new

- **`shouldSnapshotToDisk`** (`Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__shouldSnapshotToDisk.lean`;
  the proof, `spec_old`, `intended` and `pr_ne_intended` are in
  `Proof/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__shouldSnapshotToDisk.lean`).
  - **Old**: it returns some boolean and gives back the applied index, the disk snapshot index and
    the force flag.
  - **New**: it returns exactly `decide (ai ≠ d) || decide (sc < ai - d)`.
    - The old spec, without the removed field, follows from it.
    - The rule the PR appears to intend, `intended ai d sc = decide (sc < ai - d)`, differs from it
      whenever `d < ai ≤ d + sc`: the PR says true, the rule says false (`pr_ne_intended`).
    - On the old code, the result with the flag false is exactly `intended`.
- **`ForceSnapshot`** (`Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__ForceSnapshot.lean`).
  - **Old**: it was not translated. The code set `s.forceDiskSnapshot = true`, a field the apply
    thread owns, which made the next `snapshotIfNeededAndCompactRaftLog` take a disk snapshot.
  - **New**: given a reader slot of `s.bemu` (given back), it calls `ForceCommit` on the current
    backend, under the backend's contract `srvBackendCommits`, and returns. It no longer touches the
    apply loop's snapshot state.

## Trust base

`etc/tcb-report.py --check` matches `etc/tcb-baseline.txt` (229 axioms, 12 `sorry`s). The collections
`server`, `v3rpc`, `apply` and `read` match their baselines. The new collection
`etc/tcb-collections/pr-etcd-21574.txt` covers the changed functions and checked callers: 55 axioms,
0 `sorry`s, all already on `lean`. `EtcdServer.wp_ForceSnapshot` and `EtcdServer.wp_shouldSnapshotToDisk`
rest on no axiom of this repository.

One new **premise**, not an axiom: `srvBackendCommits b`
(`Proof/go_etcd_io/etcd/server/v3/etcdserver/InvApplyAll.lean`). It is part of `s.bemu`'s invariant
`bemuP` and says the server's backend's `ForceCommit` returns, `□ {{ True }} ForceCommit {{ True }}`.
It enters with the construction premise (`srvBemuReader`), as `isMetaBackend`'s `ReadTx` contract does.
- It cannot be derived from `backend.ForceCommit.spec`. That spec needs the backend open and spends a
  write-back budget token, and the server's view tracks neither.
- It is **false of a closed backend**. The reviewer's `forcecommit_after_close_test.go` panics on a nil
  transaction in the pre-commit hook.
- It holds for the server as modelled, for two reasons:
  - the apply loop's scheduler stops before `Cleanup` closes `s.be`;
  - `applySnapshot`, which closes the old backend asynchronously after swapping in the new one, is not
    modelled (raft's contract hands over no snapshot).
- Modelling the snapshot path needs a backend-open condition here (recorded in the file's header).

## Findings

1. **The PR takes a disk snapshot after every applied batch (bug in the PR).**
   - Where: `shouldSnapshotToDisk` keeps `ep.appliedi != ep.diskSnapshotIndex` without the flag.
   - Proof: `pr_ne_intended`.
   - Tests:
     - `notes/pr-verify/etcd-21574/shouldsnapshot_test.go` fails on the fork+PR and on the upstream
       PR head, and passes on the base.
     - `snapshot_count_test.go` (one member, 20 puts, `--snapshot-count` 10000) finds 24 WAL snapshot
       records on the PR, against 1 on the base.
   - Each extra snapshot costs:
     - `KV().Commit()`, a bbolt commit with fsync that holds the batch transaction's lock;
     - a WAL `SaveSnapshot` record with fsync;
     - `Release`;
     - on the upstream head, also a `.snap` file.
   - Raft-log compaction is not a new cost: it already ran every 100 entries.
   - Existing unit tests (`TestApplyRepeat` and many after it) build servers with no KV. They now reach
     `snapshot()` and panic at `s.KV().Commit()` (`probes.log`, `fork-tests.log`), which is why every
     CI job fails.
   - The reviewer noted one more consequence, not tested: after a restart, raft's in-memory log starts
     at the latest WAL snapshot, so a member restarted after this change keeps almost no entries for
     lagging followers.
2. **The obvious repair breaks downgrades (latent in the PR's design).**
   - The repair is `shouldSnapshotToDisk-fix.patch`, the snapshot-count rule alone. With it, the
     package tests pass (`fixed-tests.log`).
   - But after a downgrade no WAL snapshot record follows the downgrade entry. The reviewer's
     `downgrade_wal_test.go` shows `ClusterVersionSet{3.7.0}` at index 4 left after the latest snapshot
     record, which is at 0 (`review-probes.log`).
   - etcd's e2e `TestDowngradeUpgradeClusterOf1`, with `bin/etcd-last-release` = v3.6.15, gives:
     - pass on the upstream base and on the PR head;
     - fail with the repair. The restarted v3.6 member panics in `MustDetectDowngrade`, from
       `RaftCluster.SetVersion`, from `applyInternalRaftRequest`, while replaying `ClusterVersionSet`
       (`e2e-downgrade.log`).
   - The PR's own `ForceSnapshot` change, a backend flush, therefore does not replace the forced
     snapshot. The PR as written avoids the panic only because it snapshots after every batch.
3. **`ForceSnapshot`'s backend commit is safe where it runs** (the reviewer's check).
   - `ClusterVersionSet` calls it after `Cluster.SetVersion` has released the batch transaction, so
     `ForceCommit` cannot deadlock.
   - The consistent index it persists (index i) comes with all of entry i's backend writes. This is
     no worse than the backend's own periodic commit.
4. **Existing code (recorded): `issues/etcd-forcesnapshot-todo-v36-replay.md`.** The TODO on
   `forceDiskSnapshot` ("Replace with flush db in v3.7 assuming v3.6 bootstraps from db file") rests
   on a false assumption: v3.6 loads the version from the db but still replays the WAL from the latest
   snapshot record (finding 2).
5. **Spec-level notes, open.**
   - `srvBackendCommits` is false of a closed backend (see the trust base).
   - `isSnapshotServer` is undischarged. It was before the PR too.

The reviewer's remaining points were resolved in the specs' text:
- the cost list (compaction is not new);
- the `intended` rule being unsafe, now said in its docstring.

## Draft review comment (for the user to edit and post)

> Two things in `shouldSnapshotToDisk`:
>
> 1. Dropping only `s.forceDiskSnapshot &&` leaves `ep.appliedi != ep.diskSnapshotIndex` as a
>    disjunct of its own. So a disk snapshot (backend commit plus WAL snapshot record, both fsynced)
>    is now taken after every applied batch, whatever `--snapshot-count` is. With a single member and
>    the default count, 20 puts leave 24 snapshot records in the WAL, against 1 on `main`. This is
>    also what breaks the unit tests: servers built without a KV now reach `snapshot()` and panic at
>    `s.KV().Commit()`, e.g. `TestApplyRepeat`.
>
> 2. Going back to `ep.appliedi-ep.diskSnapshotIndex > s.Cfg.SnapshotCount` alone fixes the tests, but
>    then `TestDowngradeUpgradeClusterOf1` (e2e, with a v3.6 binary as `etcd-last-release`) fails. The
>    v3.6 member panics with "invalid downgrade; server version is lower than determined cluster
>    version" on restart.
>    - The forced snapshot is what moved the WAL snapshot past the downgrade's `ClusterVersionSet`
>      entry. Without it, v3.6 replays the earlier `ClusterVersionSet{3.7}` entry.
>    - v3.6 applies `ClusterVersionSet` regardless of `shouldApplyV3`, and its `SetVersion` calls
>      `MustDetectDowngrade`.
>    - Flushing the backend does not help there: v3.6 does read the version from the db first, but it
>      still replays the WAL from the last snapshot record.
>
> So the TODO's assumption ("v3.6 bootstraps from db file") doesn't quite hold. I think the forced
> disk snapshot on downgrade has to stay, at least while v3.6 is a supported downgrade target.
