## Verdict

The change is sound as far as it was verified. Every function the PR adds or changes is proved,
with no `sorry`: the hand-rolled heap's `push` and `pop`, `Wait`, `Trigger` and `NewTimeList`
against their existing specs (the PR is a refactor of them), the new `Pending`, and the server's
`applyAll`, `start` and `ApplyWait` over them. The proof establishes a new lock invariant: the heap
holds exactly the map's deadlines, each once, in heap order, and after `Trigger(d)` no deadline
`≤ d` is left in the map. So `Trigger` never panics (no nil-channel close, no double close, no index
out of range), the heap and map never fall out of sync, and only deadlines `≤ d` are released.

What is not covered:
- **That the removed channels are actually closed.** The specs don't state it, though the proof
  does close each channel it removes (open point 1 below; the gap predates the PR).
- **`pop`'s length bound.** It rests on one new trust-boundary axiom: Go's `append` never builds
  a `[]uint64` of `2^62` elements (`pop`'s `2*i + 1` would overflow beyond that).
- **Performance.** The complexity claims and the metric's value were not verified.

The PR also changes an exported interface (`WaitTime` gains `Pending`), and the new metric's help
text says "waiters" where it counts deadlines.

### The specs

- `Trigger`, `Wait`, `NewTimeList`: unchanged statements (`Trigger(d)` takes `□ P d`, returns;
  `Wait(d)` returns a broadcast channel whose close gives `P d`). The PR is a refactor of them.
- **The lock invariant** (`timeListR`, `Proof/go_etcd_io/etcd/pkg/v3/wait/TimeList.lean`) now also
  owns `tl.h`, a slice holding a min-heap (`waitHeap.heapOk`, `Proof/go_etcd_io/etcd/pkg/v3/wait/Heap.lean`)
  of exactly the map's deadlines, each once (`heapMatch`), fewer than `2^62` of them, and states
  that **every deadline still in the map is above the last trigger's deadline** (`tlHeapOk`). The
  last conjunct is new with this work and is the content of the PR's claim: `Trigger(d)` closes
  and removes every waiter at most `d` (the loop ends only when the heap is empty or its root, its
  least element, is above `d`). The contract's postcondition for `Trigger` is `True`, so this
  property is internal to the invariant (a client cannot cite it), but it is proved for the new
  code: a heap bug that left a releasable waiter behind would fail the proof. Whether the old
  map-scan `Trigger` meets the same strengthened invariant was not attempted (it does by
  inspection: it deletes every key at most `d`).
- `deadlineHeap.push(d)`: from a slice of a heap `xs` (with its capacity), a slice of a heap
  `xs' ≡ₚ xs ++ [d]` with `xs'.length < 2^62`.
- `deadlineHeap.pop()`: from a non-empty heap `xs` with `xs.length ≤ 2^62`, returns `t = xs[0]`,
  `t ≤` every element, and leaves a heap `xs'` with `t :: xs' ≡ₚ xs`.
- `Pending()`: `0 ≤ n`; it is `len(tl.m)` under the lock, a snapshot of what other threads change,
  so the contract says no more.

## Trust base (step 7)

- **New axiom (one):** `wait.deadlineHeap.append_len_bound`
  (`Proof/go_etcd_io/etcd/pkg/v3/wait/HeapAppend.lean`). It is Perennial's `wp_slice_append` at
  `deadlineHeap.ty`, with "the result has fewer than `2^62` elements" added. Why it is believed:
  Go's `growslice` panics beyond `maxAlloc` bytes (`2^48` on 64-bit platforms), so a `[]uint64`
  has at most `2^45` elements. It is false of Perennial's model, which only assumes the length
  fits an `int`. It is needed because `pop`'s `2*i + 1` overflows for slices over `2^62` long
  (Perennial's `slices.siftDownOrdered` takes `len ≤ 2^62` as a premise for the same code). The
  general fix, a model assumption of the allocation bound in Perennial, is recorded in
  `notes/STATUS.md`, not made here.
- **New package fact:** the server's `applyWaitPending` holds a gauge whose `Set` returns
  (`srvApplyLoopInit`), like the existing `proposalsApplied`. Package facts are assumed for the
  package's `init`, as for every other metric.
- **No `sorry` added.**

## Findings (step 8)

- **No bug found in the PR.** The proof covers the Go code's safety and heap/map consistency.
  Two randomized tests against a reference model also pass on the PR head: mine,
  `notes/pr-verify/etcd-22495/wait_time_model_test.go`, and the reviewer's,
  `wait_time_review_test.go`, 2000 seeds plus an 8-goroutine `-race` stress test. Both include
  triggers below the last one and repeated deadlines. Logs are beside them.
- **No bug in the pinned code**, so nothing goes in `issues/`.
- **PR nit, compatibility:** `WaitTime` is an exported interface of the public module
  `go.etcd.io/etcd/pkg/v3`. Adding `Pending()` breaks any implementation or mock outside etcd.
  Inside etcd's modules only `*timeList` implements it. A separate optional interface, or calling
  `Pending` on the concrete type, would avoid the break.
- **PR nit, metric text:** the help text of `etcd_debugging_server_apply_wait_pending` ("The
  number of outstanding waiters …") is inaccurate. It counts distinct pending deadlines, and
  waiters on the same index share one channel, as the PR's own test says ("a duplicate deadline
  shares a channel and must not be counted twice").
- **PR nits, minor:** `Pending()` takes the lock a second time per apply batch, separately from
  `Trigger`. The heap's backing array never shrinks after a spike, as the map's doesn't either.
- **Open point 1 (spec, predates the PR):** the contract's `Trigger` postcondition is `True`, and
  the new invariant says no deadline `≤ d` stays in the map. In this affine logic a `Trigger` that
  removed deadlines without closing their channels would still verify, so "the waiters are
  released" is a property of the proof script (each removed channel is closed with
  `wp_broadcast_chan_close`), not of a statement. Stating it needs a ghost record of the channels
  `Wait` handed out, each pending in the map or closed. That is future work; the doc comments say
  so (`TimeList.lean`, "The heap").
- **Reviewer:** a fresh reviewer subagent checked the specs, the axiom, the invariant (including
  concurrency) and the Go code. Its findings are the points above. It also flagged the TCB
  baseline, since updated.
