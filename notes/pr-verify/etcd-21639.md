# etcd-io/etcd#21639: "fix: resolve transaction data inconsistency on followers"

- PR: https://github.com/etcd-io/etcd/pull/21639, open, head `cb56c8ad050d5418760d4102a2808f1f1a592f44`
  (one commit), base `3401a41e5` (upstream `main`, 2026-04-13). GitHub reports it as conflicting
  ("PR needs rebase").
- Fixes (per its description) etcd-io/etcd#18667: a follower strips a transaction's range operations
  before applying it (`removeNeedlessRangeReqs`), so a `Get` at a compacted revision that fails the
  transaction on the member serving the client is not seen on the other members, which apply the
  writes.
- Change: `removeNeedlessRangeReqs` (`server/etcdserver/apply/apply.go`) no longer removes range
  operations from `Success`/`Failure`; it rewrites each top-level one in place to
  `Get("\x00", Limit 1, KeysOnly, CountOnly)`, keeping its `Revision`, so that `checkTxn`'s revision
  check still runs on every member. Plus an e2e test change (`TestReproduce18667` asserts all members agree).
- Fork: `mit-pdos/etcd-grove` branch `pr-etcd-21639-goose-lean` (local `~/etcd-pr/etcd-21639`),
  commit `45afb08e9` onto the pin `09669450f`: an **empty** commit, see "Applying the PR".
- This branch: `pr-verify/etcd-21639` (worktree `/shared/etcd-grove-pr/etcd-21639`): this report and
  `notes/pr-verify/etcd-21639/` (tests and logs). No Lean changes.

## Verdict

The PR is **superseded**: upstream already fixed #18667 differently, in #21432 (commit `fbba4f46e`,
merged 2026-05-23), which deleted `removeNeedlessRangeReqs` and instead passes a
`SkipRangeExecution` flag down to `txn.executeTxn`, so every member applies the same, unmodified
request and only the range's execution is skipped. The fork's pin contains #21432, and that code is
the verified code; there is nothing of this PR left to apply or verify on it.

On its own base the PR does fix the compacted-revision case (#21432's regression test passes at its
head, fails at its base), but it **introduces a new divergence between members when auth is
enabled**: the apply-time permission check (`authApplierV3.Txn` → `CheckTxnAuth`) runs on the
rewritten request, so the members with no waiting client check read permission on `"\x00"` instead
of the original key. A user allowed to read `k1` and write `k2` runs `Then(Put(k2), Get(k1))`:
applied on the member serving the client, rejected with permission denied on the other two (Go
test below). The base had the mirror-image divergence (ranges stripped: a range the user may not read
rejects the transaction on one member only); #21432 fixes both, and both tests pass at upstream `main`
and at the pin.

## Applying the PR

`git apply -3` of the PR's non-test diff onto the pin conflicts in `apply.go`: the PR edits
`removeNeedlessRangeReqs`, which the pin no longer has (removed by #21432). Re-adding it would add a
function with no caller, and re-wiring `apply.Apply` to call it would undo #21432 (17 files) and
re-verify the whole apply chain against code that upstream has already discarded. Resolution: keep the
pin's `apply.go`; the fork branch's only commit is empty and records this. Nothing was re-translated
and no Lean module changed; `etc/goose.py`, the link files and the trust base are as on `lean`.

Old/new spec, in a sentence each (not formalized, since the function is not in the verified code):

## What the existing proofs say about the merged fix (#21432)

At the pin, the proved specs show that `SkipRangeExecution` affects only responses:
`txn.Txn.specSole` (`Spec/go_etcd_io/etcd/server/v3/etcdserver/txn/Txn.lean`) commits
`srvRunTxn … t` on the state after `log` whatever `skip` is, `skip` appearing only in
`txnResponseIs skip resp`; `CheckTxnAuth` and `checkTxn` are applied to the request as decoded. But two
points of the specs mean the proofs do not by themselves exclude the #18667 class:

- `txn.checkTxn.spec` constrains its error only for a plain transaction (`txnPlain`: gets at revision
  0); for a get at a non-zero revision (the compacted case) either outcome is allowed. The KV model
  (`Proof/go_etcd_io/etcd/server/v3/etcdserver/KVModelDefs.lean`, `plainReq`) excludes such
  transactions.
- The auth layer's rejection is modeled as not determined by the log (`kvExact` false with auth
  enabled), so agreement of members on a permission decision is not stated.

What would catch the class: a spec of `checkTxn` whose error is a function of the log and the request
(compacted / future revision), a deterministic model of `CheckTxnAuth` over the auth store's state, and
a lemma that `apply.Apply`'s effect on the store is the same with and without a registered waiter.

   `["v2" "foo" "foo"]`), passes at upstream `main` and the pin. Not recorded in `issues/`: the pinned

   `nested-compare-snapshot`) and `etcd-max-txn-ops-nested`: the PR addresses none of them; they are about
