# etcd-io/etcd#22115: concurrency: stale Mutex.Unlock retry can delete a newer same-session lock

- **PR**: https://github.com/etcd-io/etcd/pull/22115, head `06eca942caa6d18e12d5caa8a73d4244130e1891`
  (one commit, open), base `main` at `6006f4058`. It fixes etcd-io/etcd#22082. Before the PR,
  `Mutex.Unlock` deleted its key by name. A stale retry of `Unlock`, after a lost response, could
  therefore delete a later incarnation of the same key: the same session and prefix give the same
  key name. The PR fences the delete:
  `Txn(ctx).If(m.IsOwner()).Then(OpDelete(m.myKey)).Commit()`, where `IsOwner()` is
  `CreateRevision(myKey) == myRev`.
- **Verified at**: `mit-pdos/etcd-grove` branch `pr-etcd-22115-goose-lean` (`0ab4ed980`, worktree
  `~/etcd-pr/etcd-22115`). That is the fork's `goose-lean` (`09669450f`) plus the PR's non-test
  diff. The PR's base is an ancestor of the fork's base, so no upstream commits are missing.
  - **One conflict**, resolved in the fork's style without changing behavior: the fork writes
    `client.KV.Delete` where upstream writes `client.Delete`, so the PR's line became
    `client.KV.Txn(ctx).If(m.IsOwner()).Then(v3.OpDelete(m.myKey)).Commit()`.
  - `go build ./...`, `go vet ./concurrency` and `go test ./concurrency` (in `client/v3`) pass on
    the fork branch. So does `go test ./integration/clientv3/concurrency` (in `tests/`), with the
    PR's test file copied in (`notes/pr-verify/etcd-22115/fork-tests.log`).
- **This branch**: `pr-verify/etcd-22115` (worktree `/shared/etcd-grove-pr/etcd-22115`), off `lean`
  `51547df02`. The translation was regenerated from the fork worktree

  `Mutex.Unlock.impl` in `Code/go_etcd_io/etcd/client/v3/concurrency.lean`. The package was

## Verdict

**The PR is correct and does what it says: it should be merged, ideally with `TryLock`'s cleanup
delete fenced the same way.** The fenced `Mutex.Unlock` is proved, with no `sorry` and no new axiom:
- on `nil`, the incarnation the mutex acquired, `(myKey, myRev)`, is gone at some revision at or
  after the call;
- the transaction it commits leaves a later incarnation of the key untouched
  (`mutex_unlock_txn_fenced`), where the old delete removed it (`mutex_unlock_old_txn_unfenced`).

The PR's regression test fails at the upstream base and passes at the head. Its callers (`Lock`,
`NewLocker`'s `Unlock`, `etcdctl lock`) are unaffected.

**One limit of the verification, not of the PR.** The fence is a property of the transaction the
code commits, not of `Unlock`'s Hoare triple. The client's model records knowledge only, so a
triple cannot say "this call did not delete the later incarnation": the unfenced delete meets
every state-based postcondition the fenced one does. The first version of the spec claimed more.
The reviewer refuted it, and it was corrected (see "The spec").

**Not covered by the PR, recorded in `issues/etcd-mutex-unlock-unfenced.md`:**
- `TryLock`'s cleanup delete (`mutex.go:65`) still deletes by name (probe at the PR head);
- the server's `v3lock` `Unlock` RPC is still unfenced too.

**Two user-visible changes, neither documented:**
- a stale handle's `Unlock` now silently returns `nil` without deleting;
- `Unlock` now needs read permission on the key.

### The spec, old and new

`Spec/go_etcd_io/etcd/client/v3/concurrency/Mutex__Unlock.lean`; the predicates are in
`Proof/go_etcd_io/etcd/client/v3/concurrency/InvMutex.lean`.

- **Old** (`Mutex.Unlock.spec_old`, kept in the same file): `nil` means `myKey` is absent at some
  `R ≥ lo` (`etcdAbsent`), whatever incarnation of it was there.
- **New** (`Mutex.Unlock.spec`): `nil` means `unlockedAt pfx myKey myRev R` at some `R ≥ lo`.
  That is, etcd's state at `R` does not have `myKey` with create revision `myRev`: the key is
  absent, or a later incarnation of it is there. The mutex is released, as before. The error cases
  (`ErrLockReleased` for a mutex without a key; any other error, state unchanged) are as before.
- **Old implies new** (`etcdAbsent_unlockedAt`, and the other cases are the same), and the fenced
  code does not meet the old spec: a failed guard leaves a later incarnation present. So the `nil`
  case is weaker, and the callers were re-checked (below).

**What the triple cannot say: the fence.** The fence means `Unlock` never deletes a later
incarnation. Since the old spec implies the new one, the unfenced code meets the new spec too.
This is the reviewer's finding (point 1 below). The client's model (`EtcdModel`,
`txnCommitResultTok`) records knowledge only: etcd's state at each revision, and a token for a
revision a commit wrote. A commit that writes nothing yields no fact. A delete by this call and
another client's delete at the same revision therefore look the same, and no postcondition stated
over states can exclude the first.

My first spec had a disjunct, "it deleted `(myKey, myRev)` (with the revision's token), or it wrote
nothing (the state lacks `(myKey, myRev)`)". Its documentation and a `mutex_stale_unlock` theorem
claimed the fence. Both were vacuous as guarantees about `Unlock`, and they were replaced.
Stating the fence as a triple would need ownership of key incarnations in the client contract, a
model change this PR does not justify (`notes/decisions.md`, "Unlock's fence and the
knowledge-only client model").

**The fence, as proved.** The proof runs `Unlock`'s commit through the contract as the transaction
`unlockTxn` (`If(CreateRevision(myKey) = myRev).Then(OpDelete(myKey))`). About that transaction
(`Proof/.../concurrency/Mutex__Unlock.lean`, restated in `Results.lean`):

- `mutex_unlock_txn_fenced` (`unlockTxn_keeps_later`): on a sorted state where `myKey` has create
  revision `c' ≠ myRev` (and `myRev > 0`), the guard fails and the state is unchanged. This is
  #22082's schedule: the stale retry runs against the newer incarnation.
- `mutex_unlock_old_txn_unfenced` (`deleteTxn_drops_key`): the old delete removes every incarnation
  of the key.
- `unlockTxn_deletes`: when the guard holds, the transaction deletes exactly `myKey`, whose
  incarnation is then `(myKey, myRev)`.
- `unlock_guard_iff`: the guard holds iff `(myKey, myRev)` is in the state. This uses `myRev > 0`:
  a missing key compares as create revision 0.

That the code commits `unlockTxn` is checked by the proof. It is not exported as a fact about a
call, for the reason above.

The proof (`Proof/go_etcd_io/etcd/client/v3/concurrency/Mutex__Unlock.lean`, no `sorry`) uses two
callees with existing specs, `Mutex.IsOwner` (the comparison `CreateRevision(myKey) = myRev`) and
`OpDelete`, besides `Session.Client`. `Link.lean` (from `etc/link-lean-first-concurrency.txt`) now
links `Mutex.Unlock` to `Mutex.wp_IsOwner` and `v3.wp_OpDelete`.

## Findings

Tests and logs are in `notes/pr-verify/etcd-22115/` (see its `README.md`).

1. **The PR fixes #22082, and the proof confirms it.** The PR's regression test fails at the
   upstream base `6006f4058` (`up-base.log`: the newer key is gone, `mutex_test.go:162`) and passes
   at the head (`up-head.log`). `mutex_unlock_txn_fenced` is the general statement, about the
   committed transaction: on a state with a later incarnation, the fenced delete changes nothing.
2. **The bug the PR fixes was in the verified code, and was not recorded.** The old `Unlock` spec
   met by it, and no triple over the client model could exclude it (see "The spec"). It is now
   recorded as `issues/etcd-mutex-unlock-unfenced.md`
   (upstream: known, #22082 and #22115).
3. **`TryLock`'s cleanup delete is still unfenced** (not changed by the PR; existing code,
   recorded in the same issue file). When `TryLock` is not the owner, it deletes `myKey` by name
   (`mutex.go:65`). If the key is deleted and re-created by another `Mutex` of the same session
   between `TryLock`'s transaction and its delete, the delete removes that newer incarnation. The
   other mutex's waiting `Lock` then returns `ErrSessionExpired`.
   - `TestProbeTryLockDeleteUnfenced` (`mutex_trylock_unfenced_probe_test.go`, at the PR head)
     shows it: `probe.log`.
   - The window is narrow, and it needs a second handle on the same session.
   - The same one-line fence would close it. Worth suggesting in the review, or as a follow-up.
4. **The server's `v3lock` `Unlock` RPC is unfenced too** (`v3lock/lock.go:53`, `Delete(req.Key)`).
   A client that retries a lost `Unlock` RPC, while the same lease has locked again, deletes the new
   incarnation. `UnlockRequest` carries no revision, so the fix needs an API change. It is outside
   this PR and recorded in the issue file.

### Reviewer

A fresh reviewer subagent checked the specs, the proof, the translation and the PR's behavior. Its
probes are in `mutex_unlock_review_probe_test.go`, with output in `review-probe.log`.

1. **Spec issue (major, resolved).** The first spec's `nil` case was implied by the old one, so it
   did not express the fence, and `mutex_stale_unlock` was vacuous as a guarantee about `Unlock`.
   The spec now claims only that the incarnation is gone. The fence is stated about the committed
   transaction, and the model limitation is recorded (`notes/STATUS.md`, `notes/decisions.md`).
2. **Callers: no issue.**
3. **Proof soundness: no issue.** One translator note: Goose evaluates the method chain's
   arguments, `OpDelete(myKey)` then `IsOwner()`, before `KV.Txn(ctx)`, while Go evaluates
   left to right. None of these calls touches etcd or `m`, so the difference is unobservable here.
4. **Behavior changes users can notice:**
   - **Stale handle (doc).** Two handles on one session share a key. When the stale one unlocks
     after the other has re-locked, `Unlock` returns `nil` and the key stays, at create revision 4
     against the stale 2 (`TestReviewProbeSameSessionStaleHandle`). This is intended, and an
     improvement in the `issues/mutex-lock-recreated.md` schedule, but it is not documented, and
     callers cannot tell a no-op from a delete.
   - **Auth (minor).** The guard needs read permission on the key; `DeleteRange` needed only
     write. With a write-only user, the fenced `Unlock` fails with `permission denied`, the plain
     `Delete` succeeds, and `Lock` already fails (`TestReviewProbeUnlockNeedsRead`). This is
     visible only if permissions are narrowed between `Lock` and `Unlock`.
   - **Retries: no issue.** The client's retry interceptor treats `Txn` and `DeleteRange` alike, and
     the fence makes a retry harmless.

No open points.

## Draft review comment

> Thanks, the fix looks right to me: fencing the delete with `IsOwner()` means a retried `Unlock`
> from an old `Mutex` can no longer remove a later acquisition of the same key, and the
> regression test fails before the change and passes after it. A few suggestions:
>
> 1. `TryLock` has the same pattern on its "cannot lock, so delete the key" path
>    (`client.Delete(ctx, m.myKey)`). If another `Mutex` on the same session deletes and re-creates
>    the key between `TryLock`'s transaction and that delete, the delete removes the newer key, and
>    that mutex's pending `Lock` returns `ErrSessionExpired`. I could reproduce this with an
>    interceptor that runs the other mutex's steps just before the `DeleteRange`. The same
>    one-line fence would close it; would you consider including it here?
> 2. `Unlock` now returns `nil` without deleting anything when the key's create revision no longer
>    matches (for example, a stale handle on a session whose key was re-acquired). That is the
>    intended behavior, but it might be worth a doc comment on `Unlock`, since callers cannot tell
>    the two cases apart.
> 3. Minor: the compare in the transaction needs read permission on the key, where `DeleteRange`
>    needed only write. `Lock` already needs read, so this only matters if permissions change
>    between `Lock` and `Unlock`, but it may deserve a mention in the PR description.
> 4. For completeness, the server-side lock service (`v3lock`'s `Unlock`) still deletes by key
>    name, and `UnlockRequest` carries no revision to fence with. That is out of scope here, but
>    may be worth a follow-up issue.
