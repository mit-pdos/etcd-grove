## Verdict

The change is correct as far as verified: the new `processMessages` returns exactly the messages
the old filter keeps (not to a removed member, not a `MsgSnap`, and of the `MsgAppResp`s only the
last one to a member not removed), **in the `Ready`'s order**, as a fresh slice, reading the
`Ready`'s slice and messages without writing them. This is proved in Lean of the PR's code with
no `sorry` and no new axiom. The new spec implies the old one, so the caller `raftNode.start` is
unaffected (re-proved). The code before the PR does not meet the new spec: it returns the same
messages reversed. That bug, which the PR fixes, is now recorded in
`issues/etcd-processmessages-reverse-order.md`. What is not covered is why order matters: the
effect on followers (rejected `MsgApp`s, resends, throughput) is liveness and performance, outside
what the proofs state. rafthttp's `Send` is a contract with no ordering.

## Old and new spec

- **Old** (`lean`, kept as `raftNode.processMessages.spec_old` in
  `Proof/go_etcd_io/etcd/server/v3/etcdserver/raftNode__processMessages.lean`): the result is a
  slice `out ↦* outL` whose messages are each valid (`rnMsgOk`). It said nothing about which
  messages or their order; its comment recorded "in reverse order". That is how the pinned code's
  bug got through.
- **New** (`Spec/go_etcd_io/etcd/server/v3/etcdserver/raftNode__processMessages.lean`): the
  result is exactly `rnKept msL tys rm`. That is `msL`'s messages at the indices where `rnKeepAt
  tys rm i` holds, in `msL`'s order, for the messages' types `tys` (tied to the messages by
  `msgAt`) and some per-index answers `rm` of `isIDRemoved`. `rnKeepAt` holds when:
  - `rm[i] = false`;
  - the type is not `MsgSnap` (7);
  - if the message is a `MsgAppResp` (4), every later `MsgAppResp` has `rm = true`.

  The answers are existential because `isIDRemoved`'s contract (`isRNIDRemoved`) returns any
  boolean: membership changes concurrently, so two messages to one member may get different
  answers within one call. The precondition is the old one: the `Ready`'s slice read-only (`↦*□`),
  the messages persistent read-only (`msgAt`'s discarded fraction). So the PR's "does not modify
  the Ready messages" is enforced by the proof, not stated as a postcondition.
- **Difference**: the new spec determines the output given `isIDRemoved`'s answers; the old one
  allowed any valid messages. `raftNode.processMessages.spec_implies_old` (new implies old) and
  `rnKept_sublist` (the output is a sublist of the input, i.e. the order) are proved in the Proof
  file.
- **Against the old code**: the old code returns `rnKept` reversed. For two or more distinct kept
  messages this differs, so it does not meet the new spec. `notes/pr-verify/etcd-22485/base.log`
  shows the PR's test failing on it. This was not attempted as a Lean proof: the counterexample is
  the test.

The proof (complete) has two loop invariants:
- `pmL1`: the first, backward loop's marks are `rnKeepAt`'s above the counter, and `sentAppResp`
  is true iff a later `MsgAppResp` to a member not removed exists.
- `pmOut`: the second, forward loop's output is the marked messages among the first `j`.

It also needs `count = 0 → no marks`, for the `return nil` path, and a bound on `count`, for
`make`'s capacity. The `MsgSnap` nonblocking send and the heartbeat paths are reused from the
`lean` proof.

## Findings

- **The PR**: no bug found.
  - `count == 0` returns `nil` as before (the old code appended to a nil slice).
  - `Transport.Send` ranges over the result, so `nil` is fine.
  - Heartbeats are still observed in reverse order (unchanged, harmless).
  - A `MsgSnap` still leaves through `msgSnapC`, out of band, as in v3.6.
- **Bug fixed by the PR, in the pinned code**: `issues/etcd-processmessages-reverse-order.md`
  (upstream: etcd-io/etcd#22483). The proof confirms the fix: the new spec, which states the
  `Ready` order, holds of the PR's code. Tests: `notes/pr-verify/etcd-22485/` (`raft_order_test.go`,
  failing on 09669450f in `base.log`, passing on the fork branch in `fork.log`).
- **Proof-side gap found by the reviewer (pre-existing, not the PR's)**, in `notes/STATUS.md`: the
  trust-boundary axiom `EtcdServer.createMergedSnapshotMessage.wp_proof` has precondition `True`.
  But the Go function writes `m.Snapshot` (`snapshot_merge.go:51`), and its caller holds only a
  read-only fraction of the `MsgSnap` from `msgSnapC`. The axiom should require ownership of the
  message; the Go code is fine.
- **Reviewer's open points**: none for this PR. The reviewer's suggestion to state the filter
  exactly (per-index removal answers) was adopted. It replaced a first version of the spec that
  stated only the order, no `MsgSnap`, and at most one `MsgAppResp`, which a `return nil` would
  also have met.
