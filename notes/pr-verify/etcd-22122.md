## 1. Summary of the PR

Prior to PR `#22122`, `(*txnOrdering).Commit()` in `client/v3/ordering/kv.go` executed `txn.KV.Do(txn.ctx, opTxn)` inside an unconditional `for` loop:

```go
for {
    opResp, err := txn.KV.Do(txn.ctx, opTxn)
    if err != nil {
        return nil, err
    }
    txnResp := opResp.Txn()
    if txnResp.Header.Revision >= prevRev {
        txn.setPrevRev(txnResp.Header.Revision)
        return txnResp, nil
    }
    err = txn.orderViolationFunc(opTxn, opResp, prevRev)
    if err != nil {
        return nil, err
    }
}
```

Whenever `txnResp.Header.Revision < prevRev` and `txn.orderViolationFunc` returned `nil` (for example, `NewOrderViolationSwitchEndpointClosure` in `client/v3/ordering/util.go`, which switches the client's endpoint and returns `nil` for the first `5 * len(c.Endpoints()) + 1` violations), `Commit()` looped and resubmitted `opTxn` to the new endpoint. For any mutable transaction (containing `OpPut` or `OpDelete` at the top level or inside a nested `OpTxn`), automatic resubmission after a successful `Do` response can apply the mutation a second time or take a different `If`/`Then`/`Else` branch on the new endpoint.

PR `#22122`:
1. Adds `isReadOnly(op clientv3.Op) bool` (`client/v3/ordering/kv.go:165-182`), which returns `true` for `op.IsGet()`, `false` for `!op.IsTxn()`, and for a transaction recursively checks that every operation in both `thenOps` and `elseOps` satisfies `isReadOnly`.
2. Computes `canRetry := isReadOnly(opTxn)` before the loop in `(*txnOrdering).Commit()` (`client/v3/ordering/kv.go:138`).
3. If `txnResp.Header.Revision < prevRev` and `txn.orderViolationFunc(opTxn, opResp, prevRev)` returns `nil`, checks `if !canRetry { return txnResp, nil }` (`client/v3/ordering/kv.go:158-160`), returning without resubmitting the mutable transaction.

### How Separation Logic Proves At-Most-Once Execution for Mutable Transactions

In [`Spec/go_etcd_io/etcd/client/v3/ordering/txnOrdering__Commit.lean`](../../Spec/go_etcd_io/etcd/client/v3/ordering/txnOrdering__Commit.lean), `kvDoTxnSpec kv ctx st.ms st.ts st.es R P PostOk PostErr` consumes an execution token `P : IProp GF` on each call to `txn.KV.Do(txn.ctx, opTxn)` (`{{ P ∗ opTAtC false opv (.txn OpFull.txnInit ms ts es) }} ...`), and the precondition of `txnOrdering.Commit` is conditioned on `isReadOnlyM (.txn OpFull.txnInit st.ms st.ts st.es)`:

```lean
(if isReadOnlyM (.txn OpFull.txnInit st.ms st.ts st.es) then □ P else P) ∗
kvDoTxnSpec kv ctx st.ms st.ts st.es R P PostOk PostErr
```

- When `isReadOnlyM = false` ([`wp_txnOrdering_Commit_mutable_at_most_once`](../../Proof/go_etcd_io/etcd/client/v3/ordering/Results.lean)), the caller supplies only a **single linear** (non-persistent) execution token `P : IProp GF`. That linear resource `P` is consumed on the first call to `txn.KV.Do(txn.ctx, opTxn)`. Because Iris separation logic forbids duplicating a non-persistent resource `P`, the proof of `txnOrdering.Commit` can only go through because every execution path after the first `txn.KV.Do` call exits the `for` loop and returns without re-entering the loop body.
- When `isReadOnlyM = true` ([`wp_txnOrdering_Commit_readOnly_monotonic`](../../Proof/go_etcd_io/etcd/client/v3/ordering/Results.lean)), the caller supplies persistent `□ P`, and the postcondition guarantees `sint.Z prevRev ≤ sint.Z rev` on any `nil`-error return.

## 3. Caveats and Findings in `client/v3/ordering`

While PR `#22122` is a sound fix for automatic resubmission of mutable transactions in `txnOrdering.Commit()`, our formalization and code audit identified 4 architectural caveats in `client/v3/ordering`:

### Caveat 1: Interaction of `txnOrdering.Commit()` with `OrderViolationFunc` on Mutable Transactions (`kv.go:154-160`, `util.go:28-40`, `doc.go:36`)

In `txnOrdering.Commit()`:

```go
err = txn.orderViolationFunc(opTxn, opResp, prevRev)
if err != nil {
    return nil, err
}
if !canRetry {
    return txnResp, nil
}
```

Because `txn.KV.Do(txn.ctx, opTxn)` has **already executed** before `txnResp.Header.Revision` can be inspected:
1. **When `orderViolationFunc` returns `nil`** (for example, `NewOrderViolationSwitchEndpointClosure` in `util.go:28-40` during the first `5 * len(c.Endpoints()) + 1` violations, which is used by `server/etcdmain/grpc_proxy.go:468`):
   - `NewOrderViolationSwitchEndpointClosure` increments its lifetime `violationCount` (which is never reset on success), calls `c.SwitchEndpoint()`, and returns `nil`.
   - `Commit()` then hits `if !canRetry { return txnResp, nil }` and returns `(txnResp, nil)` — silently returning a response with `txnResp.Header.Revision < prevRev` and `err == nil`.
   - Note that our formal specification in [`Spec/go_etcd_io/etcd/client/v3/ordering/txnOrdering__Commit.lean`](../../Spec/go_etcd_io/etcd/client/v3/ordering/txnOrdering__Commit.lean) explicitly reflects this: `sint.Z prevRev ≤ sint.Z rev` is guaranteed only when `isReadOnlyM (.txn OpFull.txnInit st.ms st.ts st.es) = true`.
2. **When `orderViolationFunc` returns a non-nil `err`** (as recommended in the new `doc.go:36` comment, or after `NewOrderViolationSwitchEndpointClosure` exceeds `5 * len(c.Endpoints())` lifetime violations):
   - The mutable transaction has **already been executed and committed on the server** (assuming it went through Raft or modified state), yet `Commit()` discards `txnResp` and returns `(nil, err)`. Callers that treat a non-nil error from `Commit()` as meaning the transaction was not applied (or that retry the transaction at the application layer on error) can still re-apply the mutation.

### Caveat 2: `kvOrdering` Does Not Override `Put`, `Delete`, or `Do` (`kv.go:30-35`)

`kvOrdering` embeds `clientv3.KV` and only overrides `Get`, `GetStream`, and `Txn`:
- Calling `kv.Put(ctx, key, val, opts...)` or `kv.Delete(ctx, key, opts...)` on `ordering.NewKV(...)` delegates directly to the embedded `kv.KV.Put` / `kv.KV.Delete` without calling `kv.setPrevRev(resp.Header.Revision)`. Consequently, a client that writes via `kv.Put` at revision `R = 100` and then issues a serializable `kv.Get` or `kv.Txn` that lands on a lagging member at revision `50 < 100` will not detect the read-your-writes ordering violation if `prevRev` was `< 50`.
- Calling `kv.Do(ctx, op)` on `ordering.NewKV(...)` delegates directly to the embedded `kv.KV.Do`, bypassing `kvOrdering` completely for `OpGet`, `OpPut`, `OpDelete`, and `OpTxn`.

### Caveat 3: Client `ordering.isReadOnly` vs Server `txn.IsTxnReadonly` Mismatch on Nested Read-Only Transactions (`client/v3/ordering/kv.go:165-182` vs `server/etcdserver/txn/txn.go:352-364`)

- In `client/v3/ordering/kv.go`, `isReadOnly` recursively traverses nested `OpTxn`s: a transaction containing a nested `OpTxn` whose leaves are all `OpGet` (or empty) has `isReadOnly == true` and will be retried by `txnOrdering.Commit()`.
- On the server side (`server/etcdserver/txn/txn.go:352-364`), `IsTxnReadonly(r *pb.TxnRequest)` is non-recursive: it checks `u.GetRequestRange() != nil` only at the top level and returns `false` whenever any operation is a nested `RequestTxn` (`u.GetRequestTxn() != nil`). Thus the server (`server/etcdserver/v3_server.go:326`) routes nested read-only transactions through Raft consensus (`s.raftRequest`) rather than the read-only path.

### Caveat 4: Redundant `txnOrdering.Txn` Allocation and `If`/`Then`/`Else` Behavior (`kv.go:86-133`)

- `kvOrdering.Txn(ctx)` calls `kv.KV.Txn(ctx)` to allocate an underlying `*clientv3.txn` and stores it in the embedded `txnOrdering.Txn` field, and `txnOrdering.If`/`Then`/`Else` forward to `txn.Txn.If`/`Then`/`Else` (which clone `Cmp`s and allocate `*pb.RequestOp`s).
- However, `txnOrdering.Commit()` never uses `txn.Txn`: it constructs a fresh `opTxn := clientv3.OpTxn(txn.cmps, txn.thenOps, txn.elseOps)` and calls `txn.KV.Do(txn.ctx, opTxn)`.
