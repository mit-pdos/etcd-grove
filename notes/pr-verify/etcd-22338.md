# etcd-io/etcd#22338: verification report

- **PR**: etcd-io/etcd#22338, "auth: add etcd_debugging_auth_simple_tokens metric",
  https://github.com/etcd-io/etcd/pull/22338, head `6b04e70c31aff45994f6f4cc0d77a1d9782ae34a`
  (one commit, base `main` `a2b3d9fe8`). Open. It says it fixes etcd-io/etcd#22337: with a 10-year
  `--auth-token-ttl` and clients that re-authenticate on every stream, the in-memory simple token
  map grew without bound, and `simpleTokenTTLKeeper.run` held `simpleTokensMu` for long sweeps. The
  PR does not bound the map. It makes the growth visible: a gauge
  `etcd_debugging_auth_simple_tokens`, and a warning each time the count reaches a multiple of
  10000.
- **Verified at**: `mit-pdos/etcd-grove` branch `pr-etcd-22338-goose-lean` (`7087d21f4`, worktree
  `~/etcd-pr/etcd-22338`). That is the fork's `goose-lean` (`09669450f`) plus the PR's non-test
  diff. It applied with `git apply -3` with no conflicts and no rewrites, so the verified code is
  the PR's. The PR's e2e test change (`tests/e2e/metrics_test.go`) is not in the fork commit, since
  test files are excluded. `go build ./...` and `go test ./auth/` pass in the fork worktree.
- **This branch**: `pr-verify/etcd-22338` (worktree `/shared/etcd-grove-pr/etcd-22338`), off `lean`
  `51547df02`. The translation was regenerated from the fork worktree. `auth.toml` now translates
  `simple_token.go`'s keeper (`addSimpleToken`, `deleteSimpleToken`, `resetSimpleToken`, `run`,
  `stop`) and table methods (`assignSimpleTokenToUser`, `invalidateUser`, `enable`, `disable`), the
  two types, the gauge variable and the TTL globals, all with bodies. It also imports `time` and
  prometheus. The etcd pin in `etc/goose.py` is unchanged, so `etc/goose.py --check` fails on this
  branch by design.

## Verdict

**The PR is sound as far as it was verified, and it does what it says for one server per
process.**
- The proofs show the keeper's `addSimpleToken` and `deleteSimpleToken` set the gauge to exactly
  `float64(len(tokens))` of the new deadline map.
- `enable` (the new `lg` field), `disable` (the new `Set(0)` after `stop`, without the lock),
  `assignSimpleTokenToUser` and `invalidateUser` are proved race-free and panic-free against the
  provider's lock invariant. The warning's guard `n > 0 && n%10000 == 0 && lg != nil` is proved to
  never panic or divide by zero.

**Not covered.**
- The keeper goroutine `run` (the PR's per-sweep `Set`) and `stop` are unfinished (`sorry`).
- No spec above the keeper states the gauge's value. The gauge is one per process and `disable`
  writes it outside the lock, so no lock-level statement can.
- That the warning fires is in no postcondition; a Go test checks it instead.

**Minor behaviour notes, for the review comment (no bugs).**
- Several providers in one process (embedded or integration-test clusters) overwrite each other's
  gauge value.
- The warning repeats each time the count returns to a multiple of 10000, not once per 10000 new
  tokens.
- `WithRoot` (`/health`, lease revoke) also creates simple tokens, which the gauge now makes
  visible.

A pre-existing bug was found along the way, unrelated to the PR: `Recover` with auth disabled leaves
the old simple tokens valid after the next `AuthEnable`
(`issues/etcd-auth-recover-disabled-keeps-tokens.md`).

### The new specs

- `addSimpleToken` (`Spec/go_etcd_io/etcd/server/v3/auth/simpleTokenTTLKeeper__addSimpleToken.lean`).
  The caller holds `tokens ↦$ m`, the gauge state `G x` and `gaugeModel G` (whose `Set(y)` takes
  `G x` to `G y`). Afterwards, `∃ e, tokens ↦$ m[token := e] ∗ G (tokenCount m[token := e])`.
  Before the PR the function had no spec. Its old code satisfies the map half but not the gauge
  half, so the gauge conjunct pins down exactly what the PR adds.
- `deleteSimpleToken` (`…__deleteSimpleToken.lean`): afterwards,
  `tokens ↦$ delete token m ∗ G (tokenCount (delete token m))`.
- `G` is a parameter, so the only way the proof can produce `G (tokenCount m')` is the code's
  final `Set(float64(len(m')))`.
- prometheus is translated names-only, so what the gauge is lives in the caller's choice of `G`, a
  ghost variable for the last value set. At the lock level the proofs take `G := True`
  (`gaugeTrivial`, from `authInit`'s value-less gauge).
- The specs of `enable`, `disable`, `assignSimpleTokenToUser`, `invalidateUser`, `run` and `stop`
  are pr-verify/etcd-22560's, minus that PR's `expiredTokens`. With the PR, `disable`'s proof also
  covers the `Set(0)` after `stop`.

## The lock invariant

`Proof/go_etcd_io/etcd/server/v3/auth/InvSimpleToken.lean` (`stLockP`, `isTS`, `tsAdmin`) is copied
from pr-verify/etcd-22560 and simplified.
- `simpleTokensMu` guards the token table (below a ghost table `A` of allowed tokens), the TTL,
  half of `simpleTokenKeeper`, and the deadline map of every keeper ever created. An old keeper's
  `run` may still sweep its map after `disable` dropped it, until `stop` returns.
- The other half of `simpleTokenKeeper` is the admin's (the apply goroutine), for
  `invalidateUser`'s unlocked read.
- The PR's change to the invariant: `keeperRO` gains the keeper's read-only `lg`. The deadline map's
  field `tokens` becomes read-only (`↦□`), which is what `addSimpleToken` reads.
- No conjunct relates the gauge to anything. The value at lock level is not stated (see Verdict).

## Findings

1. **No bug in the PR.** The race detector is clean on the PR's tests and ours (`-race`).
2. **Several providers per process share one gauge** (minor). Each provider's 1-second sweep sets
   the gauge to its own count, and one provider's `disable` zeroes it while another still holds
   tokens. `TestSimpleTokenGaugeSharedAcrossProviders`
   (`notes/pr-verify/etcd-22338/server/auth/simple_token_gauge_test.go`) sees it alternate between
   3 and 1. This matters only for embedded or test clusters. It is the usual pattern for etcd's
   process-global metrics; `etcd_debugging_auth_revision` is also last-writer-wins.
3. **The warning repeats at the threshold** (minor). It is logged whenever an add brings the count
   to a multiple of 10000, also after deletions brought it below. `TestSimpleTokenWarnAtEveryCrossing`
   logs 6 warnings after 5 delete/add cycles at 10000.
   - This matches the CHANGELOG ("whenever the count reaches a multiple of 10000"). The PR
     description says "warn every 10000 tokens".
   - Removals come mostly from the 1-second sweep, so it is at most about one warning per sweep in
     practice. `invalidateUser` churn can add more.
   - The warning is logged while holding `simpleTokensMu`, on the apply path.
4. **A transient stale value in `disable`** (note). Between `disable`'s `Unlock` and `stop`, the old
   keeper's `run` may sweep and set the gauge to its old map's size. `stop` waits for `run` to exit
   and `Set(0)` comes after it, so the value ends at 0. No `assign` can add in that window, because
   the keeper is nil.
5. **`WithRoot` creates simple tokens** (note; reviewer). Every `/health` probe and lease-revoke
   with auth on assigns a fresh root token that lives for the TTL; with a 10-year TTL that is
   forever. `TestReviewWithRootCountsTokens` (`server/auth/simple_token_review_test.go`): 50 calls add 50 to the
   gauge. This bears on the issue the PR addresses: client re-authentication is not the only source
   of growth. It also means the provider's specs, which assume the apply goroutine as the only
   admin, do not describe that caller.
6. **Pre-existing bug: `Recover` with auth disabled keeps the simple tokens**
   (`issues/etcd-auth-recover-disabled-keeps-tokens.md`). `Recover` sets `enabled = false` but never
   calls `tokenProvider.disable()`. A later `AuthEnable`'s `enable()` is then a no-op, so tokens
   issued before the disable are accepted again on a member that caught up by snapshot.
   `TestRecoverAuthDisabledKeepsSimpleTokens`
   (`notes/pr-verify/etcd-22338/server/auth/recover_disabled_tokens_test.go`) fails at the fork pin
   `09669450f`; the code is the same on upstream `main`.
7. **The e2e change is fine** (note). The gauge is registered in `init()` with no labels, so it is
   always exported, at 0 with JWT or no auth. The PR's failing `pull-etcd-e2e-amd64` and
   `pull-etcd-govulncheck` CI jobs were not investigated.

Reviewer's open points, recorded rather than fixed:
- The gauge's value is stated only for the two leaf operations.
- The warning is in no postcondition.
- `run`'s and `stop`'s specs are unprovable as stated (above).

Tests and logs: `notes/pr-verify/etcd-22338/README.md`.

## Draft review comment (for the user to edit and post)

> Thanks, this looks correct to me. The count is updated under `simpleTokensMu` on add, delete and
> each TTL sweep, and `disable` resets it to 0 only after `stop()` has waited for the sweeper to
> exit, so a single server's gauge settles on the right value. `go test -race ./server/auth/` is
> clean with some extra tests for this (assign/invalidate/expiry/disable). A few small points:
>
> 1. The gauge is process-global. With several members in one process (embed, integration tests),
>    each member's sweep overwrites it every second, and one member's disable zeroes it. That is
>    probably acceptable for a debugging metric, but worth a comment.
> 2. The warning fires every time the count comes back to a multiple of 10000. With churn around
>    10000 (expiry plus new logins) it can repeat about once per sweep. The CHANGELOG wording
>    matches this. If you meant "once per 10000 new tokens", you would need to remember the last
>    multiple you warned at.
> 3. `WithRoot` (health checks, lease revoke) also mints a simple token per call, which lives for
>    the TTL. With a very long `--auth-token-ttl` these add up too, so the new metric may be the
>    first place people see them.
>
> Unrelated to this PR, but noticed while reading the code: `authStore.Recover` doesn't call
> `tokenProvider.disable()` when the restored backend has auth disabled. So on a member that catches
> up by snapshot after an `AuthDisable`, old simple tokens survive, and they are valid again after
> the next `AuthEnable`. Happy to open a separate issue.
