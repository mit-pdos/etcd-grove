## Verdict

**The PR is unsound: it loses watch events.** `syncWatchers` caps the backend scan at
`watchBatchMaxRevs * maxWatchersPerSync * 2` = 1,024,000 entries. That cap counts the entries
of every key, not just the watched ones. The rest of `syncWatchers` is unchanged, and it still
treats the scan as complete:

- A chosen watcher with no events in the scanned part, or with events but no `moreRev`, is
  moved to the synced group at `currentRev + 1`.
- The events of its key past the cut are never delivered.

On top of that, the backend's limited range is not a prefix of the range (finding 2). So even a
watcher whose batch overflows (`moreRev` set) can skip the events in the gap.

In the proof, everything goes through except one obligation: that the cap does not cut the
range. That obligation is false in exactly the case the PR is for, and three Go tests that fail
on the PR head show it. The PR also does not reduce the work for backlogs under 1,024,000
entries, which includes the 500K-revision case of #22264. A fix that bounds the scan by
revision range keeps the guarantee (draft comment below). That fix is not verified here.

### `rangeEvents`: old and new spec

- **Old** (`lean`, `Spec/go_etcd_io/etcd/server/v3/storage/mvcc/rangeEvents.lean`): for
  `0 ≤ minRev ≤ maxRev ≤ |log|`, the result is the events of revisions `[minRev, maxRev)` whose
  key the group covers, in revision order.
- **New** (same file on this branch): the same result, given a `limit` with
  `limit ≤ 0 ∨ |logEnts log minRev maxRev| ≤ limit`. Here `|logEnts …|` is the number of bucket
  entries in the range: one per change of each revision, sub-revisions and tombstones included,
  before any filtering by watcher.
  - With `limit ≤ 0` the new spec is the old one, which is what `TestRangeEvents`' `0` relies on.
  - For a limit that cuts the range, nothing is promised. The backend returns no prefix of the
    range then (finding 2), so the natural "the first `limit` events" spec would be false.
  - Proof: `Proof/go_etcd_io/etcd/server/v3/storage/mvcc/rangeEvents.lean`.
- **What it rests on.** mvcc's contract for the backend's range read of the `Key` bucket
  (`keyRangeReadSpec`, `Proof/go_etcd_io/etcd/server/v3/storage/mvcc/InvStore.lean`) now takes a
  limit, under the same premise. It is proved of the real backend in `BackendBridge.lean`
  (`rtRange_safe_lim`, from the backend's proved model `backend.rtRange`, plus `rt_rangeRead`).
  It is not a new assumption. The reviewer checked it against `baseReadTx.UnsafeRange`, including
  concurrent commits and writebacks, which all take `readTx.Lock` and so cannot run while the
  range holds `RLock`.

### `syncWatchers`

The spec is unchanged (`Spec/go_etcd_io/etcd/server/v3/storage/mvcc/watchableStore__syncWatchers.lean`).
It keeps the watchable store's lock invariant, which records that every synced watcher has
received every event of its key up to the current revision.

The proof (`Proof/go_etcd_io/etcd/server/v3/storage/mvcc/watchableStore__syncWatchers.lean`)
is the old one plus:

- the two global loads (`HmaxB`);
- the call to `rangeEvents` with the limit, whose premise is discharged by
  `mvcc.syncWatchers_scanLimit_uncut` (same file): `|logEnts C minRev |C|| ≤ 1000*512*2`.

That lemma is a `sorry` and is false. It fails whenever the chosen watchers are more than
1,024,000 entries behind. Everything after the call is unchanged, because when the limit does
not cut the range the code behaves exactly as before. So the proof shows the PR is correct
exactly when its limit has no effect.

## Findings

1. **The PR loses watch events: a cut scan moves watchers to synced past events they never
   received.**
   - `notes/pr-verify/etcd-22594/watchable_store_scanlimit_test.go`
     (`TestSyncWatchersScanLimitDeliversAll`): `watchBatchMaxRevs = 1`, so the cap is 1024.
     There are 1100 puts of `b` and one of `a`, and the watch on `a` starts at revision 1.
   - On the PR head and on the fork branch the watcher gets `[]` instead of `[1102]`, and `[12]`
     instead of `[12 1102]` with one more `a` inside the scan.
   - It passes on the base: `head-test.log`, `base-test.log`.
   - At the default values the same happens with 1,024,000 puts of other keys.
2. **The backend's limited range is not a prefix.** `ReadTx.UnsafeRange` returns the read
   buffer's range first:
   - if the buffer holds fewer than `limit` entries of the range, the result is bbolt's first
     `limit - n` entries followed by all `n` of the buffer's;
   - otherwise it is the buffer's first `limit` entries and nothing from bbolt.

   `notes/pr-verify/etcd-22594/watchable_store_rangeevents_limit_test.go`: `rangeEvents(2, 27,
   limit 10)` returns `[2 3 4 5 6 22 23 24 25 26]`. This is a property of the existing code that
   its API does not document. It is recorded as
   `issues/etcd-backend-readtx-range-limit-not-prefix.md`, with no reachable bug in the pinned
   callers (`restore` reads with an empty buffer, compaction uses the batch transaction).
3. **Lost events even when `moreRev` is set** (reviewer).
   `notes/pr-verify/etcd-22594/watchable_store_review_gap_test.go`: revisions 2..1101 are
   committed, with `a` at 1052, and `a` at 1102 and 1103 are buffered. With cap 1024, the
   watcher's batch overflows on the buffered events after the gap, so its `moreRev` points past
   the gap. It gets `[1102 1103]`, not `[1052 1102 1103]`. The test drives `syncWatchers` by
   hand, so it is deterministic. It fails on the head and passes on the base (`gap-*.log`).
4. **The performance goal is not met.** For a backlog under 1,024,000 entries, the 500K-revision
   case of #22264 included, each pass does the same scan as before. Above that, it still scans
   about 1M entries under `s.mu` and `revMu`.

Reviewer's open point (low confidence, not filed): `syncWatchers` sends `Revision: curRev` with
a batch cut at `moreRev`, while `moveVictims` uses `w.minRev - 1`. This would matter only to a
client that reads an event response's header revision as "complete through here".

The PR fixes nothing recorded in `issues/`.

## Draft review comment

> Thanks for looking at this. As written, the change can drop watch events. The entry limit
> counts every key's revisions in `[minRev, curRev]`, but the rest of `syncWatchers` still
> treats the scan as complete. A chosen watcher with no events in the scanned prefix, or with
> fewer than `watchBatchMaxRevs` revisions there, gets `w.minRev = curRev+1` and moves to
> `synced`, so its events past the cut are never sent.
>
> Reproduction: set `watchBatchMaxRevs = 1` (limit 1024), put `b` 1100 times and `a` once,
> `ForceCommit`, then watch `a` from revision 1. The watcher never receives the `a` event. It
> does on `main`.
>
> A second problem: `readTx.UnsafeRange` with a limit returns the read buffer's entries after
> bbolt's first `limit - n`, so the result is not a prefix of the range. Even a watcher whose
> batch fills up (`moreRev` set) can skip the events in between.
>
> Also, for backlogs under ~1M entries, including the 500K case in #22264, the scan is the same
> as before.
>
> Bounding the scan by revision instead keeps the guarantee:
>
> - scan `[minRev, end)` with `end = min(curRev+1, minRev+N)` and no entry limit;
> - set each watcher's `minRev` to `max(end, w.minRev)` (or `moreRev`);
> - move a watcher to `synced` only when its `minRev > curRev`.
>
> A test along the lines of the reproduction above would guard it.
