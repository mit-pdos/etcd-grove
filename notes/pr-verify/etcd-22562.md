## Verdict

The one-line change does what the PR says, and the proofs show why it is right: with the guard
gone, `HashKV`'s hash of a revision and the hash the compaction job stores for it are the same
filter of the bucket (`hashIncl_keep_compact`), and that filter never hashes a revision the
compaction may delete, so the hash no longer depends on how far a compaction has gone
(`hashIncl_not_del`, given that the compaction revision does not delete a key and put it again,
the separate known bug `issues/etcd-compaction-delete-then-put.md`). Both mismatches it removes
are real bugs at the pin (`issues/etcd-hash-empty-keep.md`, reproduced). **But the PR also changes
the hash that a finished compaction gives when no key is live at the hashed revision**
(`hashInclOld_empty_ne`; #22515's test case "every key deleted after the compact revision" fails
on this PR): in a cluster mixing members with and without the change, `HashKV` differs on
identical data, which `PeriodicCheck`/`InitialCheck`/`CompactHashCheck` report as corruption. The
PR says so ("Empty-keep-set hashes intentionally change ... mixed-version hash compatibility was
not exercised"); its CHANGELOG line does not. Not covered: the hasher's crc32 writes (the trust
boundary, as before), `hashByRev`/`unsafeHashByRev`/the corruption checker (not specified), and
the link from the pure theorems to the Go loops (stated over the model's kept sets, not proved of
`scheduleCompaction`'s or `hashByRev`'s code).

## The behavior change

- **Old** (`hashInclOld`, `Proof/go_etcd_io/etcd/server/v3/storage/mvcc/HashFilter.lean`): a pair of
  revision `r` is hashed when `r.main ≤ rev`, and, if `r.main ≤ c`, `keep` keeps `r` **or `keep`
  is empty**, and `r` is not a tombstone at `c`.
- **New** (`hashIncl`, same file; the spec of `kvHashIncludes`): the same without "or `keep` is
  empty".
- Incompatible by design: the new filter skips, with an empty `keep`, what the old one hashed
  (`hashInclOld_empty_ne`). The callers are checked below; the change is visible at the exported
  API (`HashKV`'s `hash`).

What the new filter is for, as theorems over the model of the key index (`Compact.lean`,
`CompactIdx.lean`: `kiKeep` is `keyIndex.keep`, `kiAvail` what `keyIndex.compact` keeps;
`keepOfIs`/`keepSetIs` the proved results of `treeIndex.Keep`/`treeIndex.Compact`):

- `keepOf_iff_keepAt` / `hashIncl_keep_compact`: below `rev`, `Keep(rev)` and `Compact(rev)` keep the
  same revisions (they differ only at a tombstone at `rev` ending a generation,
  `kiKeep_of_kiAvail_lt`), so for a compaction revision `c < rev` the two kept sets give the same
  filter: `HashKV(rev)` before the compaction at `rev` and the hash that compaction stores agree.
- `hashIncl_not_del`, `hashIncl_not_del_compact`, `hash_filter_del`: a revision compaction at `c`
  may delete (`KeyDel`) is never hashed, with either kept set at `rev ≥ c`, so the filtered
  sequence of a bucket is the same with any part of those revisions deleted; premise
  `NoDelPutAt log c` (`kiKeep_avail`). Without it the theorem is false: a txn that deletes and
  puts a key at `c` makes compaction delete the live put, which `Keep(rev)` keeps
  (`issues/etcd-compaction-delete-then-put.md`); the hash then still depends on the progress.
- `hashInclOld_keep_compact_differ`: the old filter fails the first property, on a key put at 2 and
  deleted at 3 (`kiPutDel`, evaluated: `Keep(3)` empty, `Compact(3)` = the tombstone).
- All of them rest on `propext`, `Classical.choice`, `Quot.sound` only (`Results.lean`).

`HashKV` and the compaction job run at different times, so their kept sets are of different logs
(the reader's `kn.log` in `treeIndex.Keep`'s spec, the job's in `treeIndex.Compact`'s), one a
prefix of the other, both past `rev`: `hashIncl_keep_compact_logs` states the agreement for that
case (via `kiAvail_prefix`). The case of two compactions queued (the job for `c0` still deleting
while the compaction revision is already `c1`) needs `NoDelPutAt` at `c0` as well; it follows from
`kiKeep_avail` at `c0` but is not stated. These are theorems about the filter: the hasher is
opaque, so no proved function's result says what is hashed; `hashByRev` and the job's loop are not
linked to them.

## Findings

1. **Bug at the pin, fixed by the PR** (`issues/etcd-hash-empty-keep.md`): with an empty kept set
   the hasher filters nothing, so (a) `HashKV(rev)` and the compaction's stored hash of `rev`
   disagree when `Keep(rev)` is empty and `Compact(rev)` is not
   (`notes/pr-verify/etcd-22562/hash_empty_keep_test.go`: fails at the pin and at #22515, passes
   with this PR), and (b) `HashKV` depends on the progress of a running compaction (#22517;
   #22515's test, `notes/pr-verify/etcd-22562/hash_physical_compaction_22515_test.go`, fails at the
   pin). The proof confirms the fix of both (above).
2. **The PR changes the hash after a finished compaction** when no key is live at the hashed
   revision and some revision at or below the compaction revision is stored (a key live at the
   compaction revision, deleted after it): #22515's case "every key deleted after the compact
   revision" fails on this PR (`0xa934d75d`, older versions `0x4803ce7`). In a mixed-version
   cluster (a rolling upgrade, a downgrade), members disagree on identical data and the
   corruption checks raise `CORRUPT` alarms. The PR knows; its CHANGELOG entry presents it as a
   plain fix. #22515 avoids this but leaves finding 1(a); no filter can keep every value older
   versions compute, since at the pin `HashKV` and the stored hash already disagree there.
3. **Restart.** A restart mid-compaction (a prefix of the deletions done, what the job's ascending
   committed batches leave) gives the same `HashKV` before, after, and after the resumed
   compaction (reviewer's `TestReviewHashRestartMidCompaction`, 0 of 3000 failures). Not covered by
   any proof: `store.restore` is specified on an empty backend only. A non-prefix deletion state
   (not reachable) resurrects a deleted revision on restore.
4. **Delete-then-put.** With txns that delete and put a key in the compaction revision the PR's
   hashes still disagree (69 of 3000 trials), because compaction then deletes the live value
   (`issues/etcd-compaction-delete-then-put.md`; `hashIncl_not_del`'s premise). Neither caused nor
   fixed by this PR.
5. **#22515 vs this PR** (reviewer's `TestReviewHashProgressAndRestart`): no failure on this PR
   without delete-then-put; 164 of 3000 on #22515, all "stored hash of `c1` ≠ `HashKV(c1)` at
   `c0`" (finding 1(a), `CompactHashCheck`'s comparison).
6. **The PR's fuzz test** compacts synchronously and only compares `HashByRev(rev)` before with the
   stored hash after: it cannot see the progress dependence or a hash change across versions.
7. Reviewer's open points: none against the formalisation; the opaque `WriteKeyValue` axiom
   (already on `lean`) promises a return for any key, though the Go code panics on a malformed
   one, and does not tie its `keep` to the hasher's. Unchanged by this PR.

The reviewer also qualified the mixed-version impact: all three corruption checks are opt-in
(`--corrupt-check-time`, default off; gate `InitialCorruptCheck`, default off: a mismatch keeps a
restarted member from starting; gate `CompactHashCheck`, alpha: affected only when `Compact(rev)`
is empty too), and the trigger needs a nearly empty keyspace. The tests and their log:
`notes/pr-verify/etcd-22562/` (README).

## Draft review comment

> Thanks, this fixes a real inconsistency. With an empty `Keep(rev)` the hasher filters nothing, so
> `HashKV(rev)` and the hash the compaction at `rev` stores (same `Revision` and
> `CompactRevision`) can differ — e.g. put `k` at 2, compact 2, delete `k` at 3: `HashKV(3)` before
> compacting at 3 hashes the put at 2, the compaction at 3 does not (`Compact(3)` keeps the
> tombstone, so its keep set is not empty). Dropping the `len(h.keep) > 0` guard makes both use the
> same rule, and since nothing compaction deletes is in `Keep(rev)`, the result also no longer
> depends on how far a running compaction has got (the issue in #22517).
>
> One concern, which the description mentions: the change also alters the hash after a finished
> compaction when no key is live at `rev` and some revision at or below the compact revision is
> still stored (a key live at the compact revision, deleted after it). #22515's test case "every
> key deleted after the compact revision" fails with this change (`0xa934d75d`, where earlier
> versions return `0x4803ce7`). During a rolling upgrade, members on either side would then report
> different hashes for the same data, which `PeriodicCheck` reports as corruption and
> `InitialCheck` turns into a failed start (both opt-in). Could the CHANGELOG entry say that the
> `HashKV` value changes for this case, or could the change keep the old value there? Note that
> #22515 keeps it but does not fix the first mismatch above, so the two PRs are not alternatives
> for the same cases.
>
> Separately, the fuzz test compacts synchronously and compares only `HashByRev(rev)` before with the
> stored hash after, so it does not exercise hashing while a compaction is still deleting.
