# etcd#22215: etcdserver: refactor baseReadTx

- PR: https://github.com/etcd-io/etcd/pull/22215, head `1fe4029cd2d1c448f1d7bec9bf0709b63f47cbac`
  (one commit, by conanoc), against `main` (merge base `14bd0caac`). Open; prow says it needs a
  rebase. There are no review comments.
- What it says it does: it groups `baseReadTx`'s `{txMu, tx, buckets, txWg}` into a type that
  "share[s] the same lifecycle" and is shared among `concurrentReadTx`s. This removes a TODO in
  `read_tx.go`. The PR says nothing about a behavior change, so it is a refactor.
- Verified at: `mit-pdos/etcd-grove` branch `pr-etcd-22215-goose-lean`, commit `5d716ccc3`. That is
  the PR's diff (non-test files) applied onto the etcd pin `09669450f` (fork `goose-lean`).
  - `read_tx.go` and `batch_tx.go` applied cleanly. `read_tx.go` is byte-identical to the PR head.
  - `backend.go` had one conflict. Since the PR's base, upstream `d6af8028d` ("Support
    non-blocking defragmentation") split `defrag` into `defragBlocking`, `defragNonBlocking` and
    `finishDefrag`. I applied the PR's defrag edits where that code now lives:
    - `finishDefrag` gets `readTx.reset(b.lg)`, `tx := b.unsafeBegin(false)`,
      `readTx.tx.setTx(tx)`, and its size computation from `tx`;
    - `defragBlocking`'s error path gets `readTx.tx.setTx(...)`;
    - `defragNonBlocking`'s error path also gets `readTx.tx.setTx(...)`. The PR does not have that

    touch verified code.
  - No other rewrites. `go build ./...`, `go vet` and `go test -race ./storage/backend/

- Proofs: branch `pr-verify/etcd-22215` of this repository, off `lean` (`51547df02`).
  `etc/goose.py --check` fails on this branch, as expected: the translation is of the PR, and the
  pin is unchanged. `Code/go_etcd_io/etcd/server/v3/storage/backend.toml` gains the new functions.

## Verdict

The refactor is sound, as far as it was verified, and it keeps the behavior. Every verified
function it touches was re-proved against its spec:

- the shared and concurrent `UnsafeRange`;
- `ConcurrentReadTx`;
- `concurrentReadTx.RUnlock`;
- the batch commit `unsafeCommit`.

All their downstream users rebuild with no new axiom or `sorry`: the rest of the backend, mvcc,
the server, apply and v3rpc. The spec texts did not change. Only the representation predicates
changed: the fields moved into the `sharedBoltTx` behind the interface. The new
`sharedBoltTx` methods and `newSharedTx` are all proved.

Not covered:

- `UnsafeForEach`, in its three variants, was not specified before the PR and is not specified
  now;
- the defrag functions are names-only;
- `newBackend` is unproved, because bbolt's `Options` is axiomatized.

These rest on reading the code and a race-detector stress test, not on proof.

### The specs

- **The refactored functions keep their statements.** These spec files are unchanged:
  - `Spec/go_etcd_io/etcd/server/v3/storage/backend/baseReadTx__UnsafeRange.lean`;
  - `backend__ConcurrentReadTx.lean`;
  - `concurrentReadTx__RUnlock.lean`;
  - `batchTxBuffered__unsafeCommit.lean`.

  What changed is the definitions they are stated in, in `InvBackend.lean`:
  - `RdSt` gains `st`, the shared read transaction's `*sharedBoltTx`. It is fixed for the
    backend's life, and its agreement comes for free through `γ.rd`.
  - `rtCore` holds `rstOf (baseOf rt) ↦□ stIf st`, persistently. That is `readTx.baseReadTx.tx`,
    which `newBackend` writes once and nothing assigns again. It also holds `rtxOf st`/`rwgOf st`
    at `q`. `rtResAt` holds `rbktOf st`.
  - `isBackend` and `crTok` hold `rtmuAt rt tm` (new, persistent) instead of `rtmuOf (baseOf rt)
    ↦□ tm`.
  - `baseRd` is split. The read buffer stays in it, the `sharedBoltTx` part is the new `stRd`,
    and they are linked by `rstOf base ↦□ stIf st`.
  - `crtSnap` gets the concurrent transaction's own clone `cst`, with its four fields read-only.

  `ReadSide.lean` threads `st` through the commit's lemmas: `rtCm` takes `st`, and so do
  `rtRes_cm_open`/`close` and `new_intv`. `ReadLemmas.lean` adds `stIf_agree` and `rtmuAt_agree`,
  and `wp_rdDone` moved there from `concurrentReadTx__RUnlock.lean`. One client proof unfolds
  `crtSnap` and needed its pattern updated: mvcc's `crtSnap_wf` in `BackendBridge.lean`.
- **`readTx.reset`** (`Spec/.../readTx__reset.lean`).
  - Old: it took the fields of `baseReadTx` and returned them reset.
  - New: it takes `lg` and the fields of its `sharedBoltTx` `st`, plus `rollbackRes γ tx wg ∨
    tx = null`. It returns the same reset fields. Before the PR, the rollback goroutine was
    `unsafeCommit`'s; it now runs inside the reset.
  - Its only caller is `unsafeCommit`, which was re-proved. `finishDefrag` also calls it but is
    not verified.
- **New**, in `Spec/.../backend/`:
  - `sharedBoltTx__lock`, `__unlock`: `txMu`'s guard.
  - `__setTx`.
  - `__addWait`, `__finishWait`, `__wait`: the interval's `WaitGroup` protocol. These are
    `wp_rdAdd`/`wp_rdDone`/`wp_rollback_Wait` behind the method.
  - `__bucket`: the bucket of the interval's snapshot, a handle or nil (`bktFact`).
  - `__reset`, `__clone`.
  - `newSharedTx`.

## Findings

No bug in the PR. No new issue in the existing code.

The behavior differences, all checked unobservable:

1. **`unsafeCommit` now resets the read side unconditionally.** Before, it did so only when
   `readTx.tx != nil`. The difference shows only with no open read transaction: at the first
   `Commit()` in `newBatchTxBuffered`, where the buffer is empty, and after `CommitAndStop`,
   where a further commit is fatal in both versions (`begin` on a closed DB). No goroutine
   starts in either case. The proof's spec excludes the stopped backend, and `newBackend` is
   unproved.
2. **`UnsafeForEach` now goes through the buckets cache** instead of calling `tx.Bucket` under
   `txMu.Lock`. A read transaction is a fixed snapshot, so the cached handle (or nil) is what
   `tx.Bucket` returns. Not verified.
3. **`UnsafeRange`'s cache miss releases `txMu`** between caching the bucket and taking it again
   for `Cursor()`. This is covered by the proof: the bucket's handle (`bktFact`, persistent)
   stays valid while the reader holds its `txLive` share.
4. **`finishDefrag`'s `readTx.reset(lg)` would now start a rollback goroutine if `readTx.tx` were
   non-nil.** Before, it dropped the transaction. It is always nil there: both defrag variants
   call `unsafeCommit(true)` first, under `readTx.Lock`, which they hold until the end. Not
   verified (names-only).
5. **`sharedTx.wait()` is never called.**

The reviewer, a fresh subagent, found no unsound spec or proof step. It confirmed by grep that no
code, test or non-test, assigns `readTx.baseReadTx.tx` after `newBackend`, which is what the
persistent `↦□` in `rtCore` rests on. It noted two items:

- `rtRes`'s fractionality, which `isBackend`'s `RWMutex` guard needs, is still not proved
  (because `newBackend` is unproved), as before the PR. The new conjuncts keep it provable.
- `UnsafeForEach` and defrag remain the uncovered parts.

Its stress test `notes/pr-verify/etcd-22215/review22215_test.go` passes under `-race` against the
PR head. It runs concurrent readers (`UnsafeRange`/`UnsafeForEach`, present and missing buckets),
writers and 1 ms commits against five defrags. Output: `review22215-pr-1fe4029cd.log`. See
`notes/pr-verify/etcd-22215/README.md`.

## Draft review comment

> This looks behavior-preserving to me. `clone()` hands each `concurrentReadTx` the same
> `txMu`, bbolt transaction, buckets map and `WaitGroup` that the old field copies did, and
> `reset` swaps in fresh ones only on `readTx`'s own `sharedBoltTx`, under `readTx.Lock`, as
> before.
>
> A few small points:
> - `unsafeCommit` now calls `readTx.reset` even when `readTx.tx` is nil (the first commit in
>   `newBatchTxBuffered`, or after `CommitAndStop`), where the old code skipped it. It is
>   harmless (no rollback goroutine starts, and the buffer is empty or the backend is stopped),
>   but worth a word in the commit message, or keep the old guard.
> - `finishDefrag`'s `readTx.reset(lg)` would now roll back a still-open read transaction where
>   the old `reset()` dropped it. It is nil there today because `unsafeCommit(true)` ran first;
>   a comment saying so would help.
> - `sharedTx.wait()` has no caller.
> - `UnsafeForEach` now uses (and fills) the bucket cache. That is fine, since a read
>   transaction is a fixed snapshot.
> - The PR needs a rebase onto the non-blocking defrag change: `defragNonBlocking`'s error path
>   also assigns `b.readTx.tx` and needs `setTx`.
