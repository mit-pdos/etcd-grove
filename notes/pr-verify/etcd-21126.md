## Verdict

The change is sound as far as it was verified. The proof is complete, with no `sorry` and no new
axiom. It shows that `closeRequireLeader` at the PR head keeps the lessor's lock invariant:
- every entry of `l.keepAlives` has at least one subscription, which fixes etcd#22094 (an orphaned
  entry kept being renewed);
- every kept channel stays paired with its own subscriber's context, which fixes etcd#22081, the
  `ctxs[newIdx]` bug the PR description calls "the bug of `newIdx`".

It also shows that the function closes a channel only through its own subscriber's close right,
and only when that subscriber's context requires a leader, with no double close, nil close or
out-of-range index.

The PR fixes both bugs, and it is the same fix as #22291 and #22087 together.

What is not covered:
- The spec is a safety spec. Its postcondition is `True`, so it says neither that the
  require-leader channels *are* closed nor that plain subscribers are *kept*: Iris can drop a
  resource. The reviewer's Go tests check those behaviors.
- The PR's claim that keep-alive requests stop rests on `sendKeepAliveLoop` (it reads
  `l.keepAlives` under `l.mu` each round), which was checked by reading, not proved.
- The PR's own integration test exercises only the delete, not the `ctxs[i]` fix (finding 2).

## The spec

`Spec/go_etcd_io/etcd/client/v3/lessor__closeRequireLeader.lean`, over `lessor.muInv R l`
(`Proof/go_etcd_io/etcd/client/v3/InvLease.lean`). Both files are unchanged from
`pr-verify/etcd-22087` commit dc2bb0753, except for a header comment.

- **Pre**:
  - the mutex `l.mu` with the invariant `muInv`: each `keepAlives` entry holds a **non-empty** list
    of subscriptions `(ch, ctx)`, with `chs` and `ctxs` index-aligned, no nil channel, each context
    `metadata.outgoingStable`, and one close right `R ch ctx` each;
  - `lessor.closeOk R` (with `R ch c`, `close(ch)` succeeds when `c` requires a leader);
  - package init and the two `rpctypes` metadata globals.
- **Post**: `True`.

There is no old spec, since the function was not translated on `lean`. The spec does not hold of
the pinned code, for two reasons:
- an all-require-leader entry is left with `subs = []`;
- re-establishing the pairing would need `R chB ctxA` from `R chB ctxB`.

#22291's earlier version of the spec needed the premise `□ ∀ ch c c', R ch c -∗ R ch c'` because of
the second reason. This PR, like #22087, makes it unnecessary.

**Proof changes**: the Go local `id` is now `leaseID`, so two hypothesis names changed
(`"leaseID" ∷ leaseID_ptr`). Nothing else changed.

## Callers and shared state

These are as for #22291 and #22087 (`notes/pr-verify/etcd-22291.md` and
`notes/pr-verify/etcd-22087.md`, "Callers and shared state"). The rest of `lease.go` at the PR head
is the same as at the fork pin, and the reviewer re-read it.

- **Caller**: the only caller is `recvKeepAliveLoop`, on `ErrNoLeader`. It is untranslated and
  unexported, and no exported API changes.
- **`sendKeepAliveLoop`**: it collects due ids under `l.mu`. At most one batch collected before the
  delete can still be sent, which is harmless. After that, the deleted lease is not renewed, which
  is the PR's intent.
- **`recvKeepAlive`**: it ignores a response for a deleted id.
- **`deadlineLoop` and the teardown**: they see only entries still in the map, so `ka.close()`
  never double-closes.
- **A later `KeepAlive` for the same id** makes a fresh entry. The old subscription's
  `keepAliveCtxCloser` matches by context pointer, so it neither touches nor deletes that entry
  (`TestReview21126DeletedThenResubscribe`).

## Findings

1. **In the PR's code: nothing wrong.** The reviewer found no input or interleaving that breaks it,
   and nothing that differs from #22087+#22291:
   - everything runs under `l.mu`;
   - the delete happens only after every channel of the entry has been closed;
   - the gRPC proxy's keep-alive contexts carry no outgoing metadata, so this path does not touch
     them.
2. **(Low/Medium, PR's test) The PR's integration test does not exercise the `ctxs[i]` fix.** At
   the base with the PR's `lease_test.go`:
   - the "lease expires when both keepAlives require leader" subtest fails (TTL=8 instead of -1);
   - "lease stays alive with mixed keepAlives" passes even with the bug (`tests.log`).

   The mispairing shows only on a second leader loss, or when the plain subscriber's context ends.
   The reviewer's `TestReview21126MixedSecondLeaderLoss` and `TestReview21126MixedCancelPlain` show
   it: both fail at the base and pass at the head. They would make good regression tests for that
   half of the PR. (#22087's own test, `TestLessorCloseRequireLeaderKeepsSurvivorsPairedWithOwnContext`,
   covers the same case.)
3. **(Low, doc) The new `ctx.go` comment names `newUnaryInterceptor` and `newStreamInterceptor`.**
   - Both are unexported and server-side (`server/etcdserver/api/v3rpc/interceptor.go`), in another
     module, which the comment does not say.
   - The gRPC proxy does its own check (`server/proxy/grpcproxy/lease.go:159`, `watch.go:110`).

   Suggested wording: "The check is done by the server (etcd's gRPC interceptors, or the gRPC
   proxy), which fails the request with ErrNoLeader."
4. **(Low; pre-existing, also in #22291) `ka.donec` stays open on the delete path.** The deleted
   subscriptions' `keepAliveCtxCloser` goroutines stay blocked until their contexts end or the
   lessor closes. At the base, `deadlineLoop` would reap the emptied entry and close `donec`, so
   this is a longer goroutine lifetime, not an unbounded leak. Adding `close(ka.donec)` before the
   `delete` would be safe, since nothing else can close it once the entry is out of the map.
5. **The bugs the PR fixes**, both already in `issues/`, now list this PR:
   - etcd#22094, `issues/etcd-lease-closerequireleader-orphan.md`;
   - etcd#22081, `issues/etcd-lease-closerequireleader-ctx-misaligned.md`.

   The proof confirms both fixes. #22291's test, #22087's pairing test and #22087's reviewer tests
   all fail at the base 34141c24b and pass at the head 15e720e9c and on the fork branch (`tests.log`).
6. **Overlap**: this PR, #22291 (or the equivalent #22253) and #22087 do the same thing.
   - Merging this PR alone fixes both bugs.
   - Merging #22291 alone leaves etcd#22081, and makes it a little worse: a plain subscriber's lease
     stops being renewed at a second leader loss.
