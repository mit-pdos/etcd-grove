## Verdict

The change is sound and does what it says. With it, every entry of the leasing KV's cache
caches at most one key-value and its `Count` is the number it caches. This is the invariant
`LeaseEntry.countOk`, now part of the cache's lock invariant, and it is proved for every function
that touches the cache. A `Get` (and a `Txn`'s get) served from the cache therefore returns
`Count == 0` after this client deleted the key, through either `Delete` or a transaction. That is
etcd's count, since etcd counts before revision filters, count-only and limits. Without the PR the
invariant is false: an integration test on upstream `main` shows `Count == 1` with no key-values
on both paths, and it passes with the PR.

Not covered:
- Whether the cached key-value itself is etcd's after this client's own writes. That is a
  separate, already-recorded matter (`issues/leasing-update-stale.md`). `countOk` only relates
  `Count` to the cached key-values.
- The PR's tests, as Go tests (they are tests).

### The behavior change

- **Old spec.** `delete` at a header not older than the entry's response drops the cached
  key-values and replaces the header. The count is unchanged.
- **New spec.** The same, and the count becomes 0 (`LeaseEntry.del`, `InvLeaseCache.lean:193`).
- **What the new spec pins down.** The new spec does not hold of the old code: its body never
  writes `Count`, and the count can be 1. The invariant
  `LeaseEntry.countOk e := e.kvs.length ≤ 1 ∧ e.count = W64 e.kvs.length`
  (`InvLeaseCache.lean:203`) is what makes the difference observable, and the old `delete`
  breaks it.
- **Where the invariant comes from.**
  - It is established at acquisition: `keyGet_count` (`InvLeasingGetLemmas.lean:166`) says the
    single-key `OpGet(key)` lists as many key-values as etcd's count, and `keyGet_kvs` says at
    most one.
  - It is preserved by `Update`, which sets the count to 1 with a fresh key-value or keeps both,
    and by `delete`.

## Findings (step 8)

- **The bug the PR fixes is in the verified (pinned) code.** It is recorded as
  `issues/leasing-delete-stale-count.md` (upstream `known`: #22417, #22585). This repository's
  proofs had not caught it: the specs carried the cached `Count` through unchanged and related it
  to nothing. The invariant added here closes that.
  - Reproduction: `notes/pr-verify/etcd-22585/leasing_count_test.go`. `TestLeasingDeleteCount`
    and `TestLeasingTxnDeleteCount` fail on upstream `d3c8a1559` (`.../leasing_count_test-upstream-base.log`)
    and pass on the PR head (`.../leasing_count_test-pr-head.log`) and on the fork branch.
- **No bug in the PR.** The reviewer subagent checked several things and found no problem:
  - Count semantics against etcd's server. `txn/range.go` sets `Count` before pruning by revision
    filters. `withTotalCount` is set for `Range`/`Txn`.
  - Every other path that writes a cached response: `Update`, the Txn path, evict/revoke, and an
    entry created from a response whose `Count` differs from `len(Kvs)`. The last is not
    reachable: the cache is filled only from the option-free `OpGet(key)` of `acquire`, and
    `Add`'s only caller is `leasingKV.get`.
  - Concurrency. `delete` always runs under the cache's write lock, and every read of the cached
    response, `copyGetResponseMetadataOnly` included, runs under the read or write lock. Users get
    copies.
- **Reviewer suggestions, both adopted.** `countOk` was strengthened with `kvs.length ≤ 1`, and
  exported through the Txn path (`respOpFresh`).
- **The PR's tests (low; for the PR author).**
  - `TestLeaseCacheDeleteClearsCount` is a real regression test: it fails on the base
    (`.../cache_test-upstream-base.log`).
  - `TestLeaseCacheDeleteDoesNotClearCountWhenRevisionOlder` also passes on the base: it guards the
    existing older-revision no-op, not the fix.
  - Both read `lk.response` directly, though a comment says "via leaseKey.get". Neither checks
    what a user's `Get` returns, nor the transaction delete path (`commitToCache`), which the fix
    also covers.

> always equals the number of key-values it caches (0 or 1), so a `Get` served from the cache
