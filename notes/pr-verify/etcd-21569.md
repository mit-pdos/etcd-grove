## Verdict

**The PR should not be merged as is.**
- It does not compile.
- Once it compiles, it removes the only check that a snapshot's database stream is as long as
  declared. That check is what produced the "ioutil: short read" in #21418, and it was right to
  fail there: the stream was truncated.

In #21418, bbolt's `Tx.WriteTo` stopped early with `io.EOF`. `io.CopyN` returns `io.EOF` when the file
it copies is shorter than the transaction's size. `newSnapshotReaderCloser` then calls
`pw.CloseWithError(io.EOF)`, and the reader sees a normal end of stream. The sender streams the
body chunked, with no `Content-Length`. The receiver's `SaveDBFrom` copies until EOF, with no
size or hash check anywhere.

With the PR, such a truncated database is reported as sent (`SnapshotFinish`) and saved by the
follower. The follower's `applySnapshot` then renames it over its live `db` and opens it. With
etcd's options, bbolt dies with SIGBUS in `loadFreelist`, a fatal fault rather than a panic.
Because the live db is already replaced, the member crash-loops on restart. This is reproduced
by the tests below.

The PR's one gain is narrow. A WriteTo error other than `io.EOF` is no longer reported as
"short read" but as itself. That is better done by fixing the error mapping (Draft review).

The `snapshot_merge.go` change (`closeErr`) is a pure refactor. The old `err` is local to the
goroutine and dead after `pw.CloseWithError(err)`.

Proved here:
- The exact reader's three functions (`NewExactReadCloser`, `exactReadCloser.Read` and `Close`),
  verified with no `sorry`.
- The base's `NewMessage` (its `ReadCloser` is an exact reader over `rc` of `rcSize` bytes) and the
  PR's (its `ReadCloser` is `rc` itself), each against its own translation.

Not proved:
- Anything about the sender/receiver protocol. The findings rest on Go tests.
- `newSnapshotReaderCloser`, which is not translated (it needs `io.Pipe` and the backend's snapshot
  interface).

## The behavior change

Statements: `Spec/go_etcd_io/etcd/server/v3/etcdserver/api/snap/NewMessage.lean`.

- **Old** (`snap.NewMessage.spec_old`, proved at `6fda2bba0`). The message holds `rs`, a new
  `*exactReadCloser` `e` over `rc` (`e ↦ {rc, br := 0, totalBytes := rcSize}`), the total size
  `proto.Size(rs) + rcSize` and a new channel of capacity 1. Every read of `e`
  (`Spec/go_etcd_io/etcd/pkg/v3/ioutil/exactReadCloser__Read.lean`, `exactReadResult` in
  `Proof/go_etcd_io/etcd/pkg/v3/ioutil/Defs.lean`) behaves as follows:
  - past `rcSize`, it returns `(0, ErrExpectEOF)`;
  - short of it on an empty underlying read, it returns `(0, ErrShortRead)`;
  - otherwise it returns the underlying result.

  `exact_end` follows: a pass-through end of stream from an empty underlying read (how `io.Pipe`
  ends) comes after exactly `rcSize` bytes.
- **New** (`snap.NewMessage.spec`). The same, but the `ReadCloser` is `rc` itself. Nothing relates
  the stream's length to `rcSize`, which the sender only logs and counts in metrics.
- **Difference**: the new spec drops the guarantee that the stream ends only after exactly `rcSize`
  bytes. It does not imply the old spec, so the change is incompatible.
  - "The PR's code does not meet `spec_old`" is argued, not proved in Lean: for every `rc`, the
    returned `ReadCloser` is `rc` and not a `*exactReadCloser`.
  - The Go tests show the consequence.

## Callers (step 6)

`snap.NewMessage` has one caller, `(*EtcdServer).createMergedSnapshotMessage`
(`snapshot_merge.go`), called from `EtcdServer.sendMergedSnap` (`server.go`). The message goes to
rafthttp's `snapshotSender.send` (`snapshot_sender.go`) and the peer's `snapshotHandler.ServeHTTP`
(`http.go`), which calls `Snapshotter.SaveDBFrom`. The follower then runs
`applySnapshot` → `storage.OpenSnapshotBackend`, then `os.Rename` onto `db` and `bolt.Open`.

None of these is translated with a proof on `lean`; `applySnapshot` is verified only for an empty
snapshot. So the path was checked by reading the code and by the Go tests below, not by proof. The
caller graph explored:

| Caller | Outcome |
|---|---|
| `createMergedSnapshotMessage` | read: passes `dbsnap.Size()` as `rcSize` and the pipe of `newSnapshotReaderCloser` as `rc` |
| `snapshotSender.send` / `createSnapBody` | read: chunked body (`io.MultiReader(buf, merged.ReadCloser)`, no `ContentLength`). It reports `SnapshotFinish` whenever the POST succeeds; a later `Close` error only flips `CloseNotify` to `false`. |
| `snapshotHandler.ServeHTTP` / `SaveDBFrom` | read: copies to EOF, fsyncs, renames to `<index>.snap.db`; no size check |
| `applySnapshot` / `OpenSnapshotBackend` | read: renames the file over the live `db` and opens it. bbolt v1.5.0 does not check the meta's high-water page against the file size, and the meta pages, written first, are intact (the reviewer's reading, confirmed by `bolttrunc/`). |

This is an exported behavior change: a truncated transfer now succeeds. The PR does not say so,
and it has no CHANGELOG entry.

## Trust base

`etc/tcb-report.py --collection etc/tcb-collections/pr-etcd-21569.txt` covers 4 roots (`NewMessage`
and the three `ioutil` results). It reports 1 axiom and 0 `sorry`s:

- **`proto.SizeMessage.wp_proof`** (new; `Spec/google_golang_org/protobuf/proto/SizeMessage.lean`).
  `proto.Size` of a `*raftpb.Message` returns some non-negative `int` and leaves the message's
  ownership (`msgOwn`) intact. It is believed for the same reason as the existing `SizeEntry`:
  protobuf-go's `Size` is the length of the wire encoding and writes only the atomic size caches,
  which the hidden-field invariant in `msgOwn` owns.

Two more assumptions:

- **`ioutilInit`** (`Proof/go_etcd_io/etcd/pkg/v3/ioutil/Base.lean`), a package-initialization
  assumption like the others: `ErrShortRead` and `ErrExpectEOF` hold fixed non-nil pointer errors.
  `fmt.Errorf` without `%w` returns `errors.New`'s `*errorString`, and nothing in etcd reassigns
  them.
- **`readerSpec`/`closerSpec`** (`ioutil/Defs.lean`) are premises on the underlying reader, not
  axioms. `Read` returns `0 ≤ n ≤ len(p)` and some error; nothing is said about the error.

The global baseline (`etc/tcb-baseline.txt`) and the `server` collection gain the one new axiom
(`--check --update`). Every other collection is unchanged (each `--check` passes); a full `lake
build` of the branch succeeds.

## Findings

Tests and logs are in `notes/pr-verify/etcd-21569/` (see its `README.md`).

1. **The PR does not compile**: `rs.Size()` on a protobuf-go v2 message (`pr-head-build.log`).
2. **The PR removes the only length check, and a truncated database is installed on the follower.**
   - The existing `TestSnapshotSend` fails with the PR (`rafthttp-pr.log`; it passes at the base,
     `rafthttp-base.log`). Case #2 is a stream shorter than declared: "snapshot expected false, got
     true" and "expected 0 files, got 1 files".
   - `snapshot_truncated_test.go` reproduces #21418's mechanism: a pipe closed with `io.EOF` after a
     quarter of the declared bytes. The snapshot is reported sent and the receiver keeps
     `0000000000000000.snap.db`. It passes at the base.
   - The reviewer's `bolttrunc/` opens such a truncated bbolt file as etcd does: SIGBUS in
     `bolt.Open` (`bolttrunc.log`).
   - `snapshot_long_test.go` (case #3: more bytes than declared) is a regression in the test only,
     since `Tx.WriteTo` never writes more than `tx.Size()`.
3. **#21418's cause is probably not fixed by anything etcd-side.** The log shows WriteTo returning
   `EOF` and the on-disk db smaller than the reported size, which fits `Tx.WriteTo` reading a file
   shorter than the transaction.
   - Up to bbolt v1.3.11, `Tx.WriteTo` reopened the db by path. The reporter's 3.5.11 uses v1.3.8.
     If the path names a different, shorter file than the one open, `io.CopyN` hits EOF.
   - bbolt#1057/#1058/#1059 (v1.3.12, v1.4.3) reuse the open file when `WriteFlag` is unset, which
     etcd never sets, so etcd v3.5.23+ and release-3.6 already avoid this.
   - With the PR, that scenario would send the wrong file's pages as a successful snapshot.

   (The reviewer's analysis, from the bbolt history; not reproduced here.)
4. **Existing code** (`issues/etcd-exactreadcloser-eof-with-data.md`, latent): `exactReadCloser.Read`
   passes `(n > 0, io.EOF)` through when the stream is short; only `Close` reports
   `ErrShortRead`. `io.Reader` allows this shape, but etcd's one reader (`io.Pipe`) never produces
   it. Test: `readcloser_eof_test.go`, which fails at the base.

The reviewer (a fresh subagent) found nothing wrong in the specs. Its open points are recorded
above:
- `spec_old`'s failure for the new code is argued, not proved.
- `exactReadCloser.Close`'s spec is weak. Its `err' ≠ nil` case also covers `ErrShortRead`; it
  says exactly that `nil` means `br ≥ total`.
- The base code reads `e.br` unsynchronized if the transport is still reading the body when the
  sender's deferred close runs after an early response. No proof here covers or needs that.

## Draft review comment (for the user to edit and post)

> Thanks for looking into #21418. I don't think removing the exact-length wrapper is the right fix,
> and the PR currently doesn't build: `rs.Size()` doesn't exist on the protobuf-go v2
> `*raftpb.Message` (`message.go:42`); it needs to stay `proto.Size(rs)`.
>
> More importantly, the "ioutil: short read" in #21418 is the wrapper doing its job. bbolt's
> `Tx.WriteTo` copies the data pages with `io.CopyN`, which returns `io.EOF` when the file is
> shorter than `tx.Size()`. `newSnapshotReaderCloser` then calls `pw.CloseWithError(io.EOF)`, so
> the reader sees an ordinary end of stream. The snapshot is sent chunked with no Content-Length,
> and the receiver's `SaveDBFrom` copies to EOF without any size check. Without the wrapper, a
> truncated database is reported as sent, saved by the follower, renamed over its db by
> `OpenSnapshotBackend` and opened. With etcd's backend options, bbolt then faults (SIGBUS in
> `loadFreelist`).
>
> With this change the existing `TestSnapshotSend` in `rafthttp` fails (the "sends less than the
> given snapshot length" case). A test closing the pipe with `io.EOF` after part of the declared
> size shows the receiver keeping the truncated `.snap.db`.
>
> If the goal is to report the real error instead of "short read", how about keeping the wrapper
> and mapping `io.EOF` from `WriteTo` to `io.ErrUnexpectedEOF` in `newSnapshotReaderCloser`?
> `exactReadCloser.Read` could also return the underlying error when it is neither nil nor
> `io.EOF`. As for #21418 itself, the 3.5.11 reporter's bbolt (v1.3.8) reopened the db file by path in
> `Tx.WriteTo`, which bbolt v1.3.12 / v1.4.3 changed to reuse the open file; that seems the more
> likely cause of the short copy.
