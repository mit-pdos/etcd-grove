## Summary

PR `#22650` fixes the lease `Checkpointer` closure wired in `NewServer` (`server/etcdserver/server.go:398-407`) so that it returns the `error` from `srv.raftRequest(ctx, &pb.InternalRaftRequest{LeaseCheckpoint: cp})` instead of discarding both return values and returning `nil`. We translated the change via Goose, specified the checkpointer closure's full contract (`newServerCkptFn`) over `srv.ensureLeadership` and `srv.raftRequest`, strengthened `lessorCkptOk`'s `SetCheckpointer` precondition to require `newServerCkptFn`, and mechanically verified both the closure (`newServer_ckptFn_of` / `server_checkpointer_spec`) and `NewServer` (`NewServer.wp_proof` / `wp_NewServer`) with zero new axioms or `sorry`s. However, inspecting the caller `lessor.Renew` (`server/lease/lessor.go:396-456`) revealed a remaining concurrency race with scheduled `Checkpoint` applications that can still cause `Renew` to shorten a lease's expiry to a stale `remainingTTL` while returning `(l.ttl, nil)` to the caller.

## Findings

### Caveat: Remaining race between `lessor.Renew` and concurrent `lessor.Checkpoint` can still shorten lease expiry to a stale `remainingTTL`

PR `#22650` ensures that when `lessor.Renew` calls `le.cp(context.Background(), &pb.LeaseCheckpointRequest{Checkpoints: []*pb.LeaseCheckpoint{{ID: int64(l.ID), Remaining_TTL: 0}}})` (`server/lease/lessor.go:436-440`), any error from `srv.raftRequest` aborts `Renew` instead of letting `Renew` proceed to `l.refresh(0)` (`server/lease/lessor.go:449`) with a stale `l.remainingTTL > 0`.

However, `lessor.Renew` (`server/lease/lessor.go:396-456`) still has a lock-split window around `le.cp`:
```go
// server/lease/lessor.go:412-455
clearRemainingTTL := le.cp != nil && l.remainingTTL > 0
le.mu.RUnlock()
if l.expired() { ... }

if clearRemainingTTL {
    if err := le.cp(context.Background(), &pb.LeaseCheckpointRequest{Checkpoints: []*pb.LeaseCheckpoint{{ID: int64(l.ID), Remaining_TTL: 0}}}); err != nil {
        return 0, err
    }
}

le.mu.Lock()
if !le.isPrimary() {
    le.mu.Unlock()
    return -1, ErrNotPrimary
}
l = le.leaseMap[id]
if l == nil {
    le.mu.Unlock()
    return -1, ErrLeaseNotFound
}
l.refresh(0)
le.initAndPush(l)
le.mu.Unlock()
return l.ttl, nil
```
Because `l.refresh(0)` (`server/lease/lease.go:84-89`) computes `newExpiry := time.Now().Add(extend + time.Duration(l.getRemainingTTL())*time.Second)` where `l.getRemainingTTL()` (`server/lease/lease.go:76-81`) returns `l.remainingTTL` whenever `l.remainingTTL > 0`, and `Renew` does **not** clear `l.remainingTTL` under `le.mu.Lock()` before calling `l.refresh(0)`, any scheduled `Checkpoint(id, r)` (`0 < r < l.ttl`) that applies on the Raft apply goroutine before `Renew` acquires `le.mu.Lock()` at line 442 causes the exact same symptom described in `#22649` / `#22650`:

1. **`clearRemainingTTL == true` (`l.remainingTTL > 0` at line 412)**:
   - A periodic `LeaseCheckpoint` entry `Checkpoint(id, r)` (`0 < r < l.ttl`) has already been proposed by `checkpointScheduledLeases` (`server/lease/lessor.go:356-380`).
   - `Renew(id)` observes `clearRemainingTTL == true`, releases `le.mu.RUnlock()`, and calls `le.cp` with `Remaining_TTL: 0`.
   - Suppose `Checkpoint(id, 0)` applies first (setting `l.remainingTTL = 0`) and `le.cp` returns `nil`, and before `Renew`'s goroutine acquires `le.mu.Lock()` at line 442, the apply goroutine applies another scheduled `Checkpoint(id, r)` (setting `l.remainingTTL = r` and persisting `RemainingTTL: r` in bbolt).
   - `Renew` acquires `le.mu.Lock()` at line 442 and calls `l.refresh(0)` at line 449, which uses `l.getRemainingTTL() == r` to set `l.expiry = now + r`, leaves `l.remainingTTL = r` in memory and in bbolt, and returns `(l.ttl, nil)` to the client.
2. **`clearRemainingTTL == false` (`l.remainingTTL == 0` at line 412)**:
   - When `Renew(id)` enters, `l.remainingTTL` is `0` (for example, before the first periodic checkpoint after `Grant` or after a prior `Renew`), so `clearRemainingTTL` is `false` at line 412.
   - `Renew` releases `le.mu.RUnlock()` at line 414 and skips `if clearRemainingTTL` (proposing no `Remaining_TTL: 0` Raft entry at all).
   - Before `Renew` acquires `le.mu.Lock()` at line 442, the apply goroutine applies a periodic `Checkpoint(id, r)` (`0 < r < l.ttl`), setting `l.remainingTTL = r` and persisting `RemainingTTL: r` in bbolt.
   - `Renew` acquires `le.mu.Lock()` at line 442, calls `l.refresh(0)` (setting `l.expiry = now + r`), leaves `l.remainingTTL = r` in memory and in bbolt (and on followers, since no `Remaining_TTL: 0` entry was proposed), and returns `(l.ttl, nil)` to the client.

Both cases are deterministically reproduced in [`notes/pr-verify/etcd-22650/renew_checkpoint_race_test.go`](etcd-22650/renew_checkpoint_race_test.go) (log in [`notes/pr-verify/etcd-22650/test-renew-checkpoint-race.log`](etcd-22650/test-renew-checkpoint-race.log)), and the PR's `NewServer` checkpointer fix is unit-tested in [`notes/pr-verify/etcd-22650/checkpointer_error_test.go`](etcd-22650/checkpointer_error_test.go) ([`test-base.log`](etcd-22650/test-base.log) vs. [`test-pr.log`](etcd-22650/test-pr.log)).

## Draft Review Comment

> This change to `NewServer`'s `SetCheckpointer` closure (`server/etcdserver/server.go:405-406`) is right: propagating the `error` from `srv.raftRequest(ctx, &pb.InternalRaftRequest{LeaseCheckpoint: cp})` ensures that when `lessor.Renew` calls `le.cp` to clear `remainingTTL`, a failed Raft proposal/apply returns `0, err` instead of silently falling through to `l.refresh(0)` while `l.remainingTTL > 0`.
>
> While reviewing `lessor.Renew` (`server/lease/lessor.go:396-456`), we noticed a related concurrency window with `lessor.Checkpoint` (`server/lease/lessor.go:492-508`) that can still produce the same symptom (shortening `l.expiry` to a stale `remainingTTL` while returning `l.ttl, nil` to the client) even with this fix:
>
> 1. In `lessor.Renew` (`server/lease/lessor.go:412-455`), `clearRemainingTTL := le.cp != nil && l.remainingTTL > 0` is read under `le.mu.RLock()`, which is released at line 414 before `le.mu.Lock()` is acquired at line 442.
> 2. If `l.remainingTTL == 0` when `Renew` checks line 412 (`clearRemainingTTL == false`), and an in-flight periodic `Checkpoint(id, r)` (`0 < r < l.ttl`) applies on the Raft apply goroutine after `le.mu.RUnlock()` (line 414) and before `le.mu.Lock()` (line 442), `Checkpoint` sets `l.remainingTTL = r` (and persists `RemainingTTL: r` in bbolt). `Renew` skips `le.cp`, acquires `le.mu.Lock()`, and calls `l.refresh(0)` (`server/lease/lease.go:84-89`), which uses `l.getRemainingTTL() == r` to set `l.expiry = now + r` while returning `(l.ttl, nil)` and leaving `l.remainingTTL = r` in memory, bbolt, and followers.
> 3. Similarly, even when `clearRemainingTTL == true`, if a periodic `Checkpoint(id, r)` applies after `Renew`'s `Checkpoint(id, 0)` applies and before `Renew` re-acquires `le.mu.Lock()` at line 442, `l.refresh(0)` again sees `l.remainingTTL == r` and sets `l.expiry = now + r` while returning `(l.ttl, nil)`.
>
