## Verdict

**The PR fixes etcd-io/etcd#21128 as it says, and `Campaign` is proved against a stronger spec with
no `sorry` and no new assumption.** On an error, either nothing was recorded in the election (the
first transaction failed), or `Resign` ran. In that case the election's leader key and session are
cleared, and the campaign's key is gone from etcd unless `Resign`'s own delete failed. That spec
does not hold of the code before the PR. The old spec follows from the new one, so callers are
unaffected.

**The PR has two side effects, both reproduced by tests that fail at the PR head and pass at its
base.**
- `Campaign` can now block past the caller's canceled context: the cleanup uses `client.Ctx()`,
  which is canceled only by `Close`.
- A failing `Campaign` now deletes a key that another `Election` on the same session and prefix
  shares. A concurrent `v3election` Campaign RPC with the same lease and name shares it too.

Both were already possible on the canceled-context path; the PR extends them to every wait error.
Not covered: liveness (the spec cannot express the blocking), and the case where `Resign`'s delete
fails. In that case the key can still stay behind, with no way left for the caller to retry.

### The spec change

`Spec/go_etcd_io/etcd/client/v3/concurrency/Election__Campaign.lean`, `Election.Campaign.spec`.
The old spec is kept as `Election.Campaign.spec_old` in
`Proof/go_etcd_io/etcd/client/v3/concurrency/Election__Campaign.lean`.

- **Old**: the `nil` case, and on an error "some state" (`∃ st', electionState e s st'`).
- **New**: the same `nil` case. On an error, `∃ st', electionState e s st' ∗ X`, where `X` is one
  of three outcomes:
  - `st' = st`: the transaction failed;
  - `s = null`: a degenerate case the predicates do not exclude, in which `Resign` does nothing;
  - `Resign` ran, so `st'.key = []`, `st'.sess = null` and `st'.rev = rev`. In addition, for the
    campaign's key `key` (under the prefix, created at `rev`), either `notLeaderAt pfx key rev R`
    at some `R ≥ lo`, meaning the key is gone, or `True`, meaning `Resign`'s delete failed.

The new spec does not hold of the old code. From `ElectionSt.init` with a live context, the old
code's `default` branch leaves `⟨key, rev, null, hdr⟩` with a non-empty `key` (the prefix is
non-empty), which matches none of the three outcomes. This was argued, not proved in Lean.

The proof is the old one with the `select` replaced by the direct `Client.Ctx` and `Resign` calls.
Two lemmas turn `Resign`'s three outcomes into the error case:
- `campaign_resign_key`: `Resign` of the campaign's own key.
- `campaign_resign_cleared`: `Resign` after `Proclaim` found the key gone. There, `Proclaim`'s
  `notLeaderAt` already gives the "gone" outcome.

`Resign` is now given the transaction's revision as its `lo`, instead of 0, so the "gone" revision
is at least `lo`.

**The `True` outcome** is where the spec admits a key left in etcd. `Campaign` discards `Resign`'s
error and returns the wait's error. `Resign` clears the state even when its delete fails (on
`lean`; etcd-io/etcd#22211 changes that). So the caller has no way to retry the cleanup. The spec
states this rather than hiding it.

## Findings

0. **The bug the PR fixes**, in the pinned code, is now recorded as
   `issues/election-campaign-wait-error-key-left.md` (upstream etcd-io/etcd#21128). The proof
   confirms the fix. Every error path after the transaction runs `Resign`, and the key is gone
   unless the delete fails. The PR's test shows the bug at the base and the fix at the head.

1. **Medium (regression): `Campaign` can block past a canceled caller context.**
   - The cleanup now runs `Resign(client.Ctx())` after any wait error. `client.Ctx()` is canceled
     only by `Client.Close`, and the client's requests wait for a ready connection.
   - So a wait error that is not the context's (`ErrCompacted`, a `Get` error, a lost watch),
     followed by the cluster becoming unreachable, keeps `Campaign` from returning until the
     connection comes back. Canceling the caller's context does not help.
   - Before the PR this path returned at once. The canceled-context path already had the hazard.
   - Test `TestReviewCampaignCleanupIgnoresCallerDeadline`
     (`notes/pr-verify/etcd-21165/review_21165_test.go`):
     - PR head: `Campaign` had not returned 6 s after the cancel, and returned only after the
       server restarted (`review_tests.pr-head.log`).
     - Base: it returns in 46 µs (`review_tests.base.log`).
   - A fix is to bound the cleanup, for example with `context.WithTimeout(context.WithoutCancel(ctx), …)`.
   - The proofs are partial-correctness and cannot show this.

2. **Low to medium (regression): the cleanup deletes a key that another `Election` shares.**
   - Two `Election`s on the same session and prefix use the same key
     (`keyPrefix/<lease>`), and `Resign`'s guard (its create revision) is the same for both. So
     are two concurrent `v3election` Campaign RPCs with the same lease and name.
   - With the PR, a wait error in one deletes the shared key while the other is waiting. That
     one then returns nil without a key, while a third candidate also wins.
   - This is the known gap that `Campaign` does not look at its key after the wait
     (`issues/election-campaign-key-check.md`; `campaignLost` in the spec). The PR makes it
     reachable by a compaction, where before it took a canceled context or a failed `Proclaim`.
   - Test `TestReviewCampaignCleanupDeletesSharedKey`:
     - PR head: the key is deleted, and both `e1` and `e3` win.
     - Base: the key is kept and `e3` waits.
   - etcd-io/etcd#22387 (final `Get` of the key; `pr-verify/etcd-22387`) would turn the false win
     into an error.

3. **Note: interaction with etcd-io/etcd#22211** (`pr-verify/etcd-22211`: `Resign` keeps its
   state when the delete fails).
   - With both PRs, a failed cleanup leaves `⟨key, rev, s, hdr⟩`. The new `Campaign` spec, which
     requires `st'.sess = null` after `Resign`, no longer holds, so whichever PR merges second
     needs this spec redone.
   - The behavior gets better, though: the caller's deferred `Resign` can retry, which closes the
     `True` gap above.

4. **Open, pre-existing, out of the PR's scope**: if the first transaction's `Commit` returns an
   error after etcd applied it, the key exists but `Campaign` recorded nothing (the spec's
   `st' = st` case). A later `Campaign` on the same session reuses the key, so this is
   recoverable. Not recorded in `issues/`: an ambiguous commit is inherent to the client.

5. **Reviewer's suggestion, not done**: say in the "Resign ran" case that `key` is exactly
   `pfx ++ hex(lease)`. That needs `SprintfNamed`'s output fully, where the proof uses only its
   prefix. `st'.rev = rev` was added.

## Draft review comment

> The change fixes #21128: with it, a failed `Campaign` always tries to delete its key, and the
> new test fails without the fix. Two side effects are worth considering:
>
> 1. `Resign(client.Ctx())` now runs after any wait error, not only after the caller's context is
>    done. `client.Ctx()` is only canceled by `Close`. If the cluster becomes unreachable right
>    after, for example, a compacted watch, `Campaign` blocks in the cleanup and canceling `ctx`
>    no longer makes it return. Before, this path returned immediately. Bounding the cleanup, for
>    example with `context.WithTimeout(context.WithoutCancel(ctx), ...)`, would keep the old
>    latency.
> 2. Two `Election`s on the same session and prefix share one key (`prefix/<lease>`). The same
>    holds for two v3election `Campaign` RPCs with the same lease and name. A wait error in one of
>    them now deletes the key the other is still waiting on, and that one later returns nil
>    without a key while another candidate also becomes leader. This was already possible when
>    the context was canceled; the PR makes it reachable by a compaction. Re-checking the key
>    after the wait (#22387) would make the second `Campaign` return an error instead.
>
> Also, `Resign`'s error is dropped. If its delete fails, the key stays and `leaderSession` is
> cleared, so the caller cannot retry. Combining this with #22211 (keep the state on a failed
> delete) would let the caller's `Resign` clean up.
>
> Tests for both are at <link to `notes/pr-verify/etcd-21165/review_21165_test.go`>.
