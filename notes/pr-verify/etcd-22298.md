- Proofs: branch `pr-verify/etcd-22298` of this repository. `etc/goose.py --check` fails on this

## Verdict

The change is sound and does what it says. With `wb.dedupe()` in both branches,
`txWriteBuffer.writeback` is proved over any keys in a bucket written by `UnsafePut`. Before, the
proof needed the keys distinct wherever the read buffer already had the bucket. That premise was
the open finding `issues/etcd-backend-duplicate-put-stale-read.md` (etcd#21986), and the PR
removes it. The proof follows the weaker premise up through `UnsafePut`, the backend's session
invariant and the server's pre-commit hooks:

- `UnsafePut` no longer needs a key to be new in its lock session;
- the consistent index's hook and the `confState` save no longer have to show that they do not
  repeat a key;
- every backend, mvcc, server and apply result rebuilds over the new specs, with no new axiom or
  `sorry`.

So `ReadTx`/`ConcurrentReadTx` read a key's newest buffered value for any sequence of puts in a
session. Two things are not covered:

- the performance remark in the PR (`sort.Stable` instead of `sort.Sort`);
- the separate `ConcurrentReadTx` cache bug, which the PR does not touch and which still shows
  up in one of the reviewer's checks (see Findings).

### The spec, old and new

`Spec/go_etcd_io/etcd/server/v3/storage/backend/txWriteBuffer__writeback.lean`. The
postcondition is the same in both: every write-buffer bucket is merged into the read buffer as
`canon (old ++ new)`, sorted with the newest value of each key, and the write buffer is reset.

- **Old** (kept as `backend.txWriteBuffer.writeback.spec_old` in
  `Proof/go_etcd_io/etcd/server/v3/storage/backend/txWriteBuffer__writeback.lean`): the premise is
  `W.WfR (fun id => R.bks.lookup id = none)`. A bucket written by `put` may repeat a key only if
  the read buffer has no such bucket.
- **New**: the premise is `W.WfR (fun _ => True)`. A bucket written by `put` may hold anything; a
  bucket written only by `putSeq` must still be strictly increasing, since `writeback` neither
  sorts nor dedupes it, as before.
- The proof's merge branch calls `dedupe`, so the bucket becomes `canon es`. Two new pure lemmas
  in `ModelLemmas.lean` close it:
  - `canon_append_canon`: `canon (a ++ canon b) = canon (a ++ b)`;
  - `canon_isEmpty`: needed because `reset` only looks at which buckets are empty.

  `lastVal_append` is a helper.

## Callers (step 6)

The writeback spec changed compatibly, so `batchTxBuffered.Unlock` (its only caller) would have
gone through unchanged; it now passes the weaker premise directly instead of `wfR_closed`.
Because the PR's point is that a repeated put is now harmless, the premise was also removed where
it had been threaded up:

| Node | Change | Outcome |
|---|---|---|
| `sessWf` (`Proof/.../backend/Model2.lean`), the backend's invariant on a batch session | `st.W.WfR (wbDupOk st)` became `st.W.WfR (fun _ => True)`; `wbDupOk` was deleted | `sessWf_put`, `sessWf_setHw`, `commit`'s reset and `sessWf_writeback` re-proved, each simpler (`wfR_reset` and `wfR_closed` deleted) |
| `batchTxBuffered.Unlock` | none to its spec | re-proved |
| `batchTxBuffered.UnsafePut` (`Spec/.../backend/batchTxBuffered__UnsafePut.lean`) | premise `kb ∉ keys of the write-buffer bucket ∨ wbDupOk st id` dropped | weaker precondition, re-proved |
| `storage.hookSaveStep` (`Proof/go_etcd_io/etcd/server/v3/storage/InvHooks.lean`) | conjunct `csDupOk` (the `confState` key may be put) dropped | `BackendHooks.OnPreCommitUnsafe` re-proved |
| `CindexBackend.lean` (the consistent index's hook over the backend) | `hookRun_dup` deleted; the two puts and `hookSaveStep_of_run` no longer prove the premise | re-proved; the server's `Link`/`Results` rebuild |
| `batchTxBuffered.UnsafeSeqPut` | none (its premise is that the key is above the bucket's keys, `putSeq`'s documented contract) | unchanged |

Every other caller of `UnsafePut` in the verified code (mvcc's `store`, schema's savers) goes
through these specs. They all rebuild: a full `lake build` of the branch succeeds.

These are now unused, left in place:

- the third conjunct of `hookPre` (`Model2.lean`: every write-buffer bucket empty or with an empty
  read-buffer bucket);
- the last conjunct of `hookRun` (`CindexBackend.lean`).

Both only served the deleted premise and could be removed in a cleanup. The doc comment of
`hooksSpec` (`InvBackend.lean`) still says the hook "may re-put a key of a bucket whose
read-buffer bucket is empty". It is left unchanged, because editing it would rebuild every
module downstream of `InvBackend`.

## Findings

- **The PR fixes `issues/etcd-backend-duplicate-put-stale-read.md`** (etcd#21986; also etcd#21987,
  a PR for the same fix). The proof confirms it, as above. The issue's reproduction,
  `notes/pr-verify/etcd-22298/stale_read_test.go`, fails at the base and passes at the PR.
  The issue file records the verified fix.
- **No bug in the PR.** The reviewer checked several cases by reading the code, and none breaks
  it:
  - mixed `UnsafeSeqPut`/`UnsafePut` of one key in one session (the flag ends `false`, so the
    bucket is deduped);
  - the `bucket2seq` flag reset to `true`;
  - an empty write-buffer bucket at write-back (`merge` compares against a stale `buf[0]`;
    harmless);
  - deletes;
  - safe-range buckets.

  Its test `notes/pr-verify/etcd-22298/review_dup_put_test.go` shows the base failing in three
  cases: the older value after a duplicate put, the older value after a seq-then-plain put of one
  key, and a range returning a key twice. All three pass at the PR. Logs: `test-base-09669450f.log`,
  `test-pr-01a459f07.log`.
- **Still failing at the PR, not caused by it:** the test's last check (after `ForceCommit`, a
  `ConcurrentReadTx` range returns `a=1 b=2 c=3 b=2 c=3`). That is
  `issues/etcd-backend-read-buffer-cache-stale-after-commit.md` (the `ConcurrentReadTx` cache is
  keyed by `bufVersion`, which a commit's reset does not bump), which is already recorded.
- The PR's description says this is "not reachable from etcd itself". That agrees with the
  issue: no etcd caller is known to put a key twice into a bucket whose read-buffer entry
  survived. The consistent-index hook's re-puts were proved harmless even before the PR.

## Draft review comment

> This change makes `writeback`'s two branches agree. Without it, `UnsafePut` has an unstated
> precondition: a key must not be put twice in one lock session into a non-sequential bucket that
> the read buffer already holds, including a bucket whose read-buffer entry was emptied by the
> last commit's reset and kept. With it, any sequence of `UnsafePut`s in a session leaves the
> read buffer sorted and holding only the newest value of each key, so `ReadTx` and
> `ConcurrentReadTx` agree with the batch transaction.
>
> A small end-to-end reproduction through the public API may be worth adding beside the unit
> test: commit once so the bucket's read-buffer entry survives, then put `foo` twice in one
> session. At `main`, `ReadTx` returns the older value while `BatchTx` returns the newer one.
>
> Unrelated to this PR: `ConcurrentReadTx` can still return stale entries after a commit, because
> its buffer cache is keyed by `bufVersion`, which `reset` does not bump.
