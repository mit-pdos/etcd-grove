### Finding 1 (HIGH): `snapshotDefragmented` holds `b.mu.RLock()` across the entire `bolt.Compact` copy and disk syncs, stalling `batchTx` writes and `Snapshot()`/`Hash()` when `Defrag()` runs concurrently

- **Location**: `server/storage/backend/backend.go:444-445` (`(*backend).snapshotDefragmented`).
- **Root Cause**:
  In `(*backend).Snapshot()` (`backend.go:386-388`), `b.mu.RLock()` is held only across `b.db.Begin(false)` (a microsecond-scale pointer/freelock operation). Similarly, `(*backend).defragNonBlocking()` (`backend.go:804-810`) explicitly documents:
  ```go
  // Phase 1: bulk-copy the live db using only a read-only bbolt transaction, mirroring
  // Snapshot()'s locking (b.mu.RLock() only around Begin, not held for the copy itself), so
  // live reads/writes keep flowing through the normal batchTx/readTx path throughout.
  ```
  By contrast, `(*backend).snapshotDefragmented` (`backend.go:444-504`) acquires `b.mu.RLock()` with `defer b.mu.RUnlock()` and holds it across:
  1. `os.CreateTemp(dir, "db.tmp.snap.*")`,
  2. `bolt.Open(tdbp, 0o600, &options)`,
  3. `bolt.Compact(tmpdb, b.db, defragTxMaxBytes)` (which copies the entire multi-GB database and performs hundreds of `fdatasync`s), and
  4. `tmpdb.Begin(false)`.
- **Impact**:
  1. Both `defragBlocking()` (`backend.go:716-720`) and `defragNonBlocking()` Phase 2 (`backend.go:828-831`) acquire `b.batchTx.LockOutsideApply()` **first** and then call `b.mu.Lock()`. If a defragmentation enters that lock sequence while `snapshotDefragmented` is running `bolt.Compact`, `Defrag()` blocks on `b.mu.Lock()` **while holding `b.batchTx` lock**, stalling all Raft apply writes (`b.batchTx.LockInsideApply()`) and periodic `b.run()` commits for the entire duration of `bolt.Compact`.
  2. Because Go's `sync.RWMutex` blocks new `RLock()` acquisitions as soon as a writer (`b.mu.Lock()`) is queued, all concurrent `b.Snapshot()`, `b.Hash()`, `b.begin()`, and `b.SnapshotDefragmented()` calls also block until `bolt.Compact` finishes.
- **Reproduction**: `TestPR21776Finding1_SnapshotDefragmentedHoldsBMuRLockAndStallsBatchTxDuringDefrag` in [`notes/pr-verify/etcd-21776/repro_pr21776_test.go`](etcd-21776/repro_pr21776_test.go).

### Finding 2 (MEDIUM): `snapshotDefragmented` ignores `b.bopts` and leaves `options.NoSync = false` on the throwaway temporary database

- **Location**: `server/storage/backend/backend.go:465-475` (`(*backend).snapshotDefragmented`).
- **Root Cause**:
  Compare `snapshotDefragmented` (`backend.go:465-475`) with `createDefragTmpDB` (`backend.go:602-613`) in the same file:
  - `createDefragTmpDB` starts from `options := *b.bopts`, sets `options.Mlock = false`, and sets `options.NoSync = true` (*"Skip fsync on intermediate commits to avoid contending with the live db's own fsyncs"*).
  - `snapshotDefragmented` starts from `options := bolt.Options{}` (copying `*boltOpenOptions` only if non-nil, which is `nil` outside tests) and sets only `options.OpenFile` and `options.Mlock = false`.
- **Impact**:
  1. `options.NoSync` and `options.NoGrowSync` remain `false` (even if the backend was configured with `UnsafeNoFsync: true`!). Because `bolt.Compact(tmpdb, b.db, 16MB)` commits a write transaction every 16MB, bbolt executes an `fdatasync` on every 16MB chunk (e.g., ~500 `fdatasync`s on an 8GB database) on a throwaway temporary file (`db.tmp.snap.*`) that is unlinked in `Close()` and never used for crash recovery (`tx.WriteTo` reads from `tmpdb`'s mmap/page cache).
  2. `options.InitialMmapSize` is `0` instead of `b.bopts.InitialMmapSize` (10GB default in etcd), forcing `tmpdb` to repeatedly `munmap`/`mmap` as it grows from 32KB to multi-GB during `bolt.Compact`.
  3. `options.FreelistType` and `options.Logger` are reset to zero values instead of inheriting `b.bopts.FreelistType` and `b.bopts.Logger`.
- **Reproduction**: `TestPR21776Finding2_SnapshotDefragmentedIgnoresBoptsAndRunsWithNoSyncFalse` in [`notes/pr-verify/etcd-21776/repro_pr21776_test.go`](etcd-21776/repro_pr21776_test.go).

### Finding 3 (LOW/MEDIUM): `defragmentedSnapshot.Close()` discards `closer()` errors and `removeTemp()` double-closes `temp`

- **Location**: `server/storage/backend/backend.go:455-486, 1221-1224`.
- **Root Cause**:
  - `defragmentedSnapshot.closer` has type `func()` rather than `func() error`, and `(*defragmentedSnapshot).Close()` runs `defer s.closer(); return s.snapshot.Close()`, so any error from `tmpdb.Close()` or `os.Remove(tdbp)` is logged at `Warn` level and never returned from `Close()`.
  - Once `bolt.Open` succeeds, `tmpdb` owns `temp` (returned by `options.OpenFile`) and closes `temp` in `tmpdb.Close()`, after which `removeTemp()` calls `temp.Close()` a second time.
- **Reproduction**: `TestPR21776Finding3_DefragmentedSnapshotCloseSwallowsCloserErrors` in [`notes/pr-verify/etcd-21776/repro_pr21776_test.go`](etcd-21776/repro_pr21776_test.go).

## Draft Upstream Review Comment

1. **`snapshotDefragmented` holds `b.mu.RLock()` across the entire `bolt.Compact` copy (`server/storage/backend/backend.go:444-445`)**:
   Holding `b.mu.RLock()` while `bolt.Compact(tmpdb, b.db, defragTxMaxBytes)` copies the database causes a severe lock-order stall if `Defrag()` (`defragBlocking` or `defragNonBlocking` Phase 2) runs concurrently: `Defrag()` acquires `b.batchTx.LockOutsideApply()` first and then blocks on `b.mu.Lock()`, which stalls all `b.batchTx` writes/commits (and blocks any subsequent `b.mu.RLock()` callers such as `Snapshot()` and `Hash()`) for the entire duration of `bolt.Compact`.

2. **Temporary database options in `snapshotDefragmented` (`server/storage/backend/backend.go:465-475`)**:
   Unlike `createDefragTmpDB()` (`backend.go:602-613`), `snapshotDefragmented` initializes `options := bolt.Options{}` instead of copying `*b.bopts` and setting `options.NoSync = true` / `options.NoGrowSync = true`. Because `tmpdb` is a short-lived temporary file that is unlinked when the snapshot closes and is never used for crash recovery, leaving `NoSync: false` causes `bolt.Compact` to `fdatasync` on every 16MB intermediate commit (hundreds of fsyncs on a multi-GB DB, contending with the live DB's disk I/O), and leaving `InitialMmapSize: 0` instead of `b.bopts.InitialMmapSize` forces repeated `mmap` remaps as `tmpdb` grows.
