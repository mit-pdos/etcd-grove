## Verdict

**The change is sound as far as it was verified.** `publishV3` and the new
`waitApplyWithinRequestLimit` are translated and proved, with no `sorry`, against specs of what
the PR intends. The proofs show the following:

- Every publish attempt meets `raftRequest`'s precondition.
- The wait's deadline `ci - maxNormalGap` does not underflow.
- When the wait ends through `applyWait`, the applied index has reached `ci - 5000`, so a proposal
  checked at that committed index passes the request limit.
- The timer is always stopped.
- `readych` is closed at most once.
- The caller `Start` still verifies.

**What the proofs cannot show.** The point of the PR, that there is no tight retry loop, is a
progress property, and a partial-correctness triple cannot state it. The Go tests cover it: with
a 20 ms publish timeout, the base logs 5632 rejections in 200 ms and the PR head logs 10.

**The PR alone does not fix #22526's reproduction.** That reproduction catches up from a
snapshot. After a snapshot, `applyWait` is triggered at the snapshot's index while
`s.appliedIndex` lags (#22516). The wait then ends at once, and the PR head still spins, with
thousands of rejections in 100 ms. The PR's description says #22510 is needed for that case. The
verified result does not cover snapshots either: it rests on raft's no-snapshot contract.

## Specs

- **`waitApplyWithinRequestLimit`** (new;
  `Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__waitApplyWithinRequestLimit.lean`).
  - **Pre:** the server's reader view `isServerRead`. This gives the committed index's invariant,
    `applyWait` as a `WaitTime` for `appliedAtLeast γr`, and `stopping`.
  - **Post:** some `c` that the committed index has reached (`committedAtLeast`), with
    `waitApplyExit c`. That is one of:
    - `c ≤ 5000`, so there is no wait;
    - `5000 < c` and `appliedAtLeast (c - 5000)`;
    - the timer fired or the server stopped. This case carries no fact, so the disjunction is as
      strong as `True`, and the spec says so.
  - **Lemma `waitApply_within_limit`:** the second exit puts `c` within `exceedsRequestLimit`'s
    normal gap.
  - **Proof:** `Proof/.../EtcdServer__waitApplyWithinRequestLimit.lean`. It uses
    `getCommittedIndex`'s spec, Perennial's `NewTimer` and `Timer.Stop`, the broadcast channel
    from `Wait`, the timer's bag channel, and `stopping`'s stop channel in a blocking three-way
    `select`.
- **`publishV3`** (`Spec/.../EtcdServer__publishV3.lean`).
  - **Old spec:** `{{ isPkgInit }} s.publishV3(d) {{ True }}`, an axiom.
  - **New spec, pre:** `isServerReq`, `isServerRead` and the publisher's resources
    (`srvPublishRes`):
    - `s.attributes`, read-only, and its `ClientURLs` slice;
    - `s.ctx`, which is a context;
    - `s.readych`, as a pending broadcast channel that only the publisher closes;
    - a reader slot of `s.leadTimeMu`, `E.RD` and a reader slot of `s.lgMu`;
    - the server's id-credit supply `□ |==> idCred ρ.ids 1`, one credit per attempt;
    - a certified log, the proposer's floor.
  - **New spec, post:** `readych` is `Done` or still `Pending`.
  - The new spec is incompatible with the old one only through its precondition: it asks for
    resources the old one did not. Its content is in the proof. Each attempt allocates a fresh
    `InternalRaftRequest{ClusterMemberAttrSet: req}` with `irrNoHdrIs` for
    `irrMemberAttr ⟨memberID, Name, ClientURLs⟩`, takes the context from `WithTimeout`, and calls
    `raftRequest`. On `nil` it closes `readych` and returns. Otherwise it warns, and on
    `errors.Is(err, ErrTooManyRequests)` calls `waitApplyWithinRequestLimit` under its spec.
  - The old code (without the wait) also satisfies the new spec, because a partial-correctness
    triple cannot tell "retry at once" from "wait, then retry". So the difference the PR makes is
    visible in the proof, not in the statement.

## Callers (step 6)

- `Start` → `GoAttach(func() { s.publishV3(s.Cfg.ReqTimeout()) })`. This is the only caller,
  per `grep publishV3` over the fork. Its proof was re-proved. Start now passes `srvPublishRes`
  to the goroutine as `GoAttach`'s `P` (`Proof/.../EtcdServer__Start.lean`). Its spec is
  unchanged in form, but its precondition `isServerBuilt` grows; see below.
- `start` hands the new resources on: `srvStarted` gains `Hpub` and `Hctxp` (the context `start`
  made) and now takes `E`. Its proof is adapted. Its spec changes only by `srvStarted`'s new
  argument and conjuncts, a strictly stronger postcondition.
- `Results.lean`'s `start_gives_views` and every other user of `srvStarted` or `isServerBuilt`
  rebuild unchanged: the full `lake build` passes, 5108 jobs.
- The path stops at `Start`, whose callers are outside the translated code.

**The construction premise.** `isServerBuilt` (`Proof/.../InvStart.lean`) gains
`"Hpub" ∷ srvPublishBuilt s E`: `NewServer`'s `attributes` and `readych`, plus the publisher's own
reader slots and `E.RD`. These are true of the Go code:

- `attributes` is written only in `NewServer` (`server.go:326`).
- `readych` is made in `NewServer` (`:318`), closed only by `publishV3`, and only handed out to
  receivers (`ReadyNotify`).
- The reader slots are one more of a bounded pool, as for any request goroutine.

## Trust base

Measured by `etc/tcb-report.py --check` after a full `lake build`:

- **Gone:** `axiom EtcdServer.publishV3.wp_proof`.
- **New:** `axiom fmt.SprintfStruct.wp_proof` (`Spec/fmt/SprintfStruct.lean`,
  `Proof/fmt/SprintfStruct.lean`). `publishV3` logs `fmt.Sprintf("%+v", s.attributes)`.
  Perennial's `fmt.wp_Sprintf` admits only arguments of predeclared basic types, and
  `fmt.SprintfNamed` admits only named basic types. The new axiom is specialized to one
  `membership.Attributes` argument whose `ClientURLs` the caller holds read-only. It says only
  that `Sprintf` returns some string and gives the argument slice back.

  This is true of Go: `Attributes` has no methods, so `fmt` formats it by reflection, reading
  `Name` and `ClientURLs`' backing array. It is also true of Perennial's model, which reads only
  the slice.

  The reviewer flagged that an earlier, broader version omitted the read-only premise on the
  slice. The current version has it.

  This is recorded as a Perennial limitation in `notes/STATUS.md`. The general fix is a Perennial
  `Sprintf` spec for methodless structs.
- **`sorry`s:** none new, and none reached.

`etc/tcb-baseline.txt` was updated with `--check --update`. The new collection
`etc/tcb-collections/pr-etcd-22527.txt` has roots `waitApplyWithinRequestLimit`, `publishV3` and
`Start`. It lists 63 axioms and 0 `sorry`s.

Compared with `lean` on the same roots, the axioms differ only by the swap above. Every other
axiom was already in the server's trust base. That includes the logging leaves (`zap.*`,
`types.ID.String`), and `context.WithTimeout` is Perennial's, proved.

What the verified result also rests on: the server proof's standing scope. Above all that is
raft's no-snapshot contract (`applySnapshot` is proved only with no snapshot), under which
`applyWait`'s `appliedAtLeast` is `s.appliedIndex`.

## Findings

Tests, logs and commands are in `notes/pr-verify/etcd-22527/` (see its `README.md`).

1. **The PR alone still spins after a snapshot.** Medium; the PR's description acknowledges it.
   - After `applySnapshot`, `applyWait` has been triggered at the snapshot index but
     `s.appliedIndex` is stale (#22516, fixed by #22510). `Wait(ci - 5000)` then returns the
     closed `closec` at once and the loop retries without delay.
   - `TestPublishV3ProbeApplyWaitAheadOfAppliedIndex` logs 2519 and 22275 rejections in 100 ms in
     two runs on the PR head. The reviewer's `TestReviewerPublishV3SpinsAfterSnapshotTrigger`
     shows the same.
   - This is #22526's own scenario, a new member installing a snapshot. So #22526 is fixed only
     by this PR together with #22510.
   - Recorded for the pinned code in `issues/etcd-applied-index-stale-after-snapshot.md`
     (upstream known).
2. **The wait can end with the limit still exceeded.** Low.
   - The wait targets the committed index read after the rejection. If commit advances during
     the wait, the retry is rejected again.
   - The reviewer's `TestReviewerPublishV3RejectedOncePerApplyBatch` logs 20 rejections over 200
     apply batches, with commit staying 6000 ahead.
   - The retries are bounded by apply progress, one per wakeup, so this is not a tight loop.
   - Waiting until `exceedsRequestLimit` no longer holds would remove these warnings.
3. **No other problems found.**
   - The timer is stopped on every path.
   - A stop during the wait ends the publish without a proposal
     (`TestPublishV3ProbeStopDuringWait`).
   - `ErrTooManyRequests` is returned unwrapped, so `errors.Is` matches.
   - Publish is never a priority request, so the normal gap is the right bound.
   - No other user of `applyWait` changes.
   - The PR's test passes. Its 100 ms negative check can only miss a regression, never fail a
     correct build. Its `Eventually(logs.Len() > 0)` counts any warning, not the rejection itself.
4. **A bug in the existing code.** The tight loop the PR fixes is present at the pinned revision.
   It is recorded in `issues/etcd-publish-too-many-requests-tight-loop.md` (upstream known:
   #22526). `TestPublishV3ProbeTimeoutRetries` logs 5632 rejections in 200 ms on the base and 10
   on the PR head.

Reviewer's points and how they were resolved:

- Specs too weak for the progress claim: stated in the specs' docstrings and above.
- The no-snapshot scope: added to `waitApplyExit`'s docstring.
- `publishV3`'s docstring overstated its post: reworded.
- The `Sprintf` axiom was too broad: narrowed.
- None remain open.

## Draft review comment (for the user to edit and post)

> I looked at this change in detail and it does what it says for a member that catches up
> from log entries: after a "too many requests" rejection, `publishV3` makes no further attempt
> until the applied index is within 5000 of the committed index it read, or the publish timeout
> or the stop comes first. With the apply stuck and a 20 ms publish timeout, `main` logs about
> 5,600 rejections in 200 ms and this branch logs 10. The deadline cannot underflow
> (`ci <= maxNormalGap` returns first), the timer is always stopped, and a stop during the wait
> ends the publish without proposing.
>
> One thing worth making explicit: on its own, this does not fix the reproduction in #22526,
> which catches up from a snapshot. After `applySnapshot`, `applyWait` has been triggered at the
> snapshot index while `s.appliedIndex` is still behind (#22516), so `applyWait.Wait(ci-5000)`
> returns an already-closed channel and the loop spins as before (thousands of rejections in
> 100 ms in a unit test that triggers `applyWait` without moving `s.appliedIndex`). It may be worth
> saying in the description that #22526 needs both this and #22510, or landing them together.
>
> A smaller point: the wait targets the committed index read after the rejection, so if the
> committed index keeps moving during catch-up, each wakeup can be rejected once more (one warning
> per apply batch, not a tight loop). Waiting until `exceedsRequestLimit` no longer holds would
> avoid those. In the test, `require.Eventually(... logs.Len() > 0 ...)` could filter on the
> rejection message so it does not count an unrelated warning.
