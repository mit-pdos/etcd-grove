## Verdict

The PR's code change is correct as far as it is verified. The proof is #22550's, rebuilt against this
PR's translation. The key index now stores, with each revision, the lease of the key-value written at
that revision. A keys-only range at the current or any past revision then returns exactly the lease a
full read returns, which fixes #22209. It is proved end to end, from `keyIndex.put`/`get` through
`treeIndex.Range` and mvcc's fast keys-only read to the server's range and the client-level results.
No axiom or `sorry` was added.

The PR's own new tests are wrong. `TestKeyIndexPut` fails on the PR head. The new "after update"
cases of `TestKVGet` fail there too, for full reads as well as keys-only reads. Those are bugs in the
tests, not in the server: with a three-line test fix, everything passes on the PR head, and the
keys-only cases fail on the base. They are likely among the reasons for the PR's red prow jobs; the
other is that it needs a rebase. #22550 has the corrected `TestKeyIndexPut`.

Not covered, as for #22550:
- the untranslated restore path (`restoreIntoIndex`, `keyIndex.restore`, `restoreTombstone`), which
  #22550's randomized Go tests cover;
- memory, +8 bytes per indexed revision;
- mixed-version clusters.

## Findings

The tests are in `notes/pr-verify/etcd-22245/`; its README gives the revisions and commands.

**No bug in the PR's code.** The fresh reviewer re-checked the restore, tombstone, compaction,
same-key multi-put and locking cases and found nothing beyond #22550's review.

**Bugs in the PR's tests** (they fail on the PR head):
1. `TestKeyIndexPut` (`server/storage/mvcc/key_index_test.go`) expects revision 5's lease to become 1
   after a later put at revision 7 with lease 1. The code correctly keeps lease 0 for revision 5, which
   is the point of the PR. Log: `keyindexput-pr-head.log`. #22550 expects `lease.NoLease` there.
2. `testKVGet`'s update loop (`tests/common/kv_test.go`) puts `inputs[i].Value` and `inputs[i].Lease`
   instead of `updates[i]`'s. It writes `a` with no lease, and `fop` with value `"a"` and no lease. The
   "at the current rev, expect lease" cases therefore fail for full reads too.
3. `kvWithLease.ModRevision, kvWithLease.Lease = firstRev+10, newLease` mutates the struct that is then
   the expectation of "before the update, expect the original lease". The server correctly returns
   mod revision `firstRev+8` with the original lease.

   Bugs 2 and 3 make 18 subtests fail: 6 cases in each of the 3 TLS variants. Log: `kvget-pr-head.log`.

With `pr-test-fixes.patch` (3 lines), mvcc's tests and `TestKVGet`/`TestKVGetStream`/`TestKVGetNoQuorum`
(integration) pass on the PR head (`fixed-tests-pr-head.log`). On the base's mvcc code, the same
patched tests fail exactly in the `--keys-only` cases (`fixed-tests-base-code.log`), so the fixed tests
do test the fix.

Minor points, from the review:
- the import grouping (`lease` beside zap/btree) is probably flagged by etcd's import-order lint;
  #22550 groups it separately;
- a stray `1.` in `generation.walk` (also in #22550);
- `restoreTombstone` is passed `rkv.kv.Lease`, which is always 0 for a tombstone;
- the comment typo "Update Leae";
- a `CountOnly` filter in the after-update loop that never applies.

**The issue the PR fixes**: the proof confirms the fix, as for #22550. `issues/etcd-range-keys-only-lease.md`
stays open on `lean` until a pin includes it. No bug was found in the existing code, so nothing is new in `issues/`.

**Relation to #22550**: #22550 has the same code with a corrected `TestKeyIndexPut` and no e2e changes,
and is the one to review. This PR's remaining value is the after-update e2e cases, once they are fixed
and rebased onto #22477's version of `kv_test.go`.

## Draft review comment (for the user to edit and post)

> The mvcc change here is the same as in #22550, and I checked it against a model of the key index and
> the range path. The lease stored beside each revision is always the lease of the key-value written
> at that revision, so a keys-only range returns the same lease as a full read at any revision.
>
> The new tests have a few bugs, which I think explain the unit and integration failures:
> - `TestKeyIndexPut` expects revision 5's lease to become `1` after the put at revision 7. It should
>   stay `lease.NoLease`, since each revision keeps its own lease (#22550 has this fixed).
> - In `testKVGet`'s update loop, `cc.Put(ctx, string(updates[i].Key), string(inputs[i].Value), config.PutOptions{LeaseID: clientv3.LeaseID(inputs[i].Lease)})`
>   uses `inputs[i]` instead of `updates[i]`, so `a` and `fop` are written without the new lease (and
>   `fop` with value `"a"`).
> - `kvWithLease.ModRevision, kvWithLease.Lease = firstRev+10, ...` changes the expectation used for
>   the "before the update" reads, which should still see mod revision `firstRev+8` and the original lease.
>
> With those three fixed, `TestKVGet` and `TestKVGetStream` pass with this change and fail without it
> only in the `--keys-only` cases. Since #22477 already landed a version of the first commit,
> this needs a rebase, and the after-update cases could perhaps go on top of #22550 instead.
