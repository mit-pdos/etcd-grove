## Verdict

The PR is correct. `Int64Comparable.Compare` now gives the signed three-way order for every pair
of int64s, and `NewInt64Point` returns `[a, a+1)` below `MaxInt64` and the empty `[MaxInt64,
MaxInt64)` at the top. Either way `Begin <= End`, and a query with that top point overlaps no
interval. Both functions are fully proved: no `sorry`, no new axiom. Neither had a spec before;
the old code is shown to be wrong at the extremes, by a pure model and by a Go probe.

Not covered:
- the interval tree's own proof (`ownIvt`) is over string-affine intervals only, so `Stab` and
  `Intersects` on int64 trees are not verified. The lemmas about `Interval.Compare` on int64
  intervals use a pure model of its Go body.
- no production code in etcd uses the int64 intervals.

## The specs

The pure part is in `Proof/go_etcd_io/etcd/pkg/v3/adt/Int64Ivl.lean`.

- **`Int64Comparable.Compare`**: `v.Compare(Int64Comparable(w))` returns `int64Cmp v w`, for
  every `v` and `w`, with no premise. `int64Cmp` is `-1`/`0`/`1` by the signed order
  (`int64Cmp_spec`: `-1` iff `v < w`, `0` iff `v = w`, `1` iff `w < v`).
  - Before the PR the result was the sign of the wrapping difference `v - w` (`int64CmpOld`).
    `int64CmpOld_wrong`: it gives `-1` for `MaxInt64` vs `MinInt64` and for `MaxInt64` vs `-1`,
    where the spec gives `1`.
- **`NewInt64Point(a)`**: returns `[a, int64PointEnd a)`, where `int64PointEnd a` is `a + 1`,
  or `a` at `MaxInt64`. `int64PointEnd_spec` gives `Begin <= End` (signed), `End = a + 1` as an
  integer below `MaxInt64`, and the empty interval at `MaxInt64`.
  - Before the PR the result was `[a, a + 1)` with wrapping. `int64PointOld_wrong`: at `MaxInt64`
    its End (`MinInt64`) is below its Begin.
- **The point used as a query.** `int64IvlCmp` copies `Interval.Compare`'s Go body over int64
  comparables. The query is the receiver, as in `intervalNode.visit` (line 155) and
  `intervalTree.Intersects` (line 732).
  - `int64IvlCmp_maxPoint`: the query `NewInt64Point(MaxInt64)` is right of every interval
    `[b, e)`, so it overlaps none. This is what the PR means by "matches no keys": no half-open
    int64 interval contains `MaxInt64`.
  - `int64IvlCmp_point`: below `MaxInt64`, the point overlaps exactly the intervals with
    `b <= a < e`, is left of those with `a < b`, and right of those with `e <= a`.

None of these is an old spec weakened: the functions had no spec, so there are no callers in the
proofs to re-check.

## Findings

1. **The bug the PR fixes is confirmed.** It is recorded as
   `issues/etcd-adt-int64-compare-overflow.md` (upstream: known, #22357).
   - On the base, the random probe `TestProbeInt64ExtremesRandom`
     (`notes/pr-verify/etcd-22358/int64_extremes_probe_test.go`) has `Stab` miss intervals: with
     `[MinInt64+1, 1)`, `[MinInt64+1, 2^62)` and `[-2^62, 2)`, `Stab(1)` finds 0 of 2
     (`probe-base.log`). The PR's own test also fails there (`pr-tests-base.log`).
   - On the PR head both pass (`probe-head.log`). The proofs confirm the fix.
2. **No bug in the PR.**
3. **Reviewer, minor: the code comment overstates.** It says the degenerate interval "is empty
   ([a, a)) and matches no keys". That holds at `MaxInt64`, the only place the code builds it
   (`int64IvlCmp_maxPoint`). Empty intervals `[a, a)` below `MaxInt64` do overlap in this tree:
   the query `[5, 5)` matches a stored `[0, 10)` (`review-probe-head.log`). Wording only.
4. **Reviewer, minor: an asymmetry at `MaxInt64`.** After `Insert(NewInt64Point(MaxInt64))`,
   `Find` finds it but `Stab` and `Intersects` with the same point do not; for every other value,
   `Stab` of the point finds the stored point. This follows from `MaxInt64` having no point
   interval, but the PR does not mention it.
5. **The same class in existing code: `NewStringAffinePoint("")` and `NewBytesAffinePoint(nil)`.**
   They build `["", "\x00")`, and since `""` is `+inf` in the affine order, `Begin > End`.
   - Recorded as `issues/etcd-adt-affine-point-empty-key.md`, with the reviewer's probe.
   - It is unreachable from etcd's callers, which reject empty keys first. The existing specs
     claim no order between the ends, so they stay true.
   - The PR does not touch it.

The related PR etcd-io/etcd#22252 fixes the same `Compare` overflow, but not `NewInt64Point`.
Its verification is queued and starts from this branch, so the specs here apply to it unchanged
if its `Compare` is the same direct comparison.
