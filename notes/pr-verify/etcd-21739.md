- **Branch**: `pr-verify/etcd-21739` (worktree `/shared/etcd-grove-pr/etcd-21739`).

## Verdict

The unary half is right. The PR moves the `isContextError` check before the "retrying of unary
invoker failed" warning. This is proved: over an invoker that fails only with `Canceled` or
`DeadlineExceeded` statuses, the interceptor never calls `Warn`. The interceptor's existing
contract is re-proved unchanged, and the stream interceptor (newly translated) is proved to return.

The getToken half does not fix the issue. `getToken`'s error on a canceled context is the bare
`context.Canceled`: `authClient.Authenticate` passes grpc's `Canceled` status through
`ContextError`, which replaces it with `ctx.Err()`. `isContextError(context.Canceled)` is false
(`status.Code` gives `Unknown`), so the guard `!isContextError(err) || ctx.Err() == nil` still logs
"getToken failed" at Error, which is the issue's second log line, verbatim. A unit test and an
end-to-end test (real grpc server, `clientv3.New` with user/password, `Close()` during a watch
reconnect, 10 of 10 runs) show it on the PR head.

The third guard ("streamer failed to create ClientStream") is correct, but the issue's watch path
never reaches it: the client installs the stream interceptor with `withMax(0)`.

## Findings

1. **The PR does not stop "clientv3/retry_interceptor: getToken failed" on `Close()`** (the issue's
   second line):
   - The mechanism:
     - `getToken` returns `c.Auth.Authenticate`'s error, and `authClient.Authenticate`
       (`auth.go:138`) returns `ContextError(ctx, err)`.
     - On a `Canceled`/`DeadlineExceeded` status with `ctx.Err() != nil`, `ContextError`
       (`client.go:615-623`) returns `ctx.Err()`, the bare `context.Canceled`.
     - `isContextError` tests `status.Code(err)`, which is `Unknown` for that error, so the guard
       logs.
   - No path gets a status error out of `getToken` on a done context. The unary interceptor's
     `return lastErr` and `waitRetryBackoff`'s `contextErrToGRPCErr` both go through the same
     `ContextError`.
   - The guard holds back the log only in a race: a server-sent `Canceled` while the context is
     live, with the context canceled between `ContextError` and the guard.
   - Tests, against the PR head:
     - `TestStreamInterceptorGetTokenCanceledLogs` in
       `notes/pr-verify/etcd-21739/retry_interceptor_shutdown_test.go` fails (log `*.head.log`).
     - The reviewer's end-to-end `TestReviewerE2EShutdownLogs` in
       `notes/pr-verify/etcd-21739/retry_interceptor_shutdown_e2e_test.go` logs the issue's exact
       line in 10 of 10 runs.
   - Fix: guard on `ctx.Err() != nil` alone. Alternatively, also test
     `errors.Is(err, context.Canceled) || errors.Is(err, context.DeadlineExceeded)`.
2. **The "streamer failed to create ClientStream" guard does not apply to the watch path** (info,
   from the reviewer):
   - `client.go:269` installs `streamClientInterceptor(withMax(0), ...)`, and `Watch` passes no
     retry option, so `callOpts.max == 0` returns `streamer(...)` before that log.
   - The log is reachable only from calls passing `withMax(n > 0)`, i.e. `Maintenance.Snapshot`
     (`maintenance.go:231,274`). There the guard is correct (see the premise above).
3. **On a live context, a `Canceled`/`DeadlineExceeded` status is now retried silently** (low):
   - Up to `max` attempts, previously one Warn per attempt
     (`TestUnaryInterceptorLiveCtxCanceledStatusSilent`: 5 silent attempts on the head, 5 warnings
     on the base).
   - The PR's description says so: "continue retrying without logging".
   - This path is the existing `issues/etcd-client-retry-put-ctx-error.md`: a non-repeatable `Put`
     re-sent after a server-sent `Canceled`. The PR removes its only trace. A note was added to that
     issue file (on this branch).
4. **Open (the reviewer's, low): the stream `spec_quiet` assumes the context is done on entry.** In
   the issue the context is canceled during the call. The Go code handles that, since it reads
   `ctx.Err()` after the error, but this spec does not state it.

No bug was found in the existing (pinned) code beyond what `issues/` already records.

## Draft review comment (for the user to edit and post)

> Thanks for this. The unary-interceptor change looks right to me: with the context check moved
> before the warning, a canceled or timed-out attempt no longer logs "retrying of unary invoker
> failed".
>
> I don't think the `getToken` change silences the second line from #21643, though. `getToken`
> returns the error of `c.Auth.Authenticate`, and `authClient.Authenticate` passes it through
> `ContextError(ctx, err)`. Once `ctx` is done, that turns the `Canceled` status into
> `ctx.Err()`, the plain `context.Canceled`. `status.Code(context.Canceled)` is `Unknown`, so
> `isContextError(err)` is false and the `Error` log still fires. That matches the issue's log,
> which shows `error="context canceled"` rather than `rpc error: code = Canceled ...`. A test that
> sets `Username`/`Password`, gives `Auth` an `AuthClient` whose `Authenticate` returns
> `status.Error(codes.Canceled, "context canceled")`, and calls the stream interceptor with a
> canceled context reproduces it. So does an end-to-end run that calls `Close()` while a watch
> reconnects with auth enabled. Checking `ctx.Err() != nil` alone, or adding
> `errors.Is(err, context.Canceled) || errors.Is(err, context.DeadlineExceeded)` to the check,
> would cover it.
>
> Two smaller notes:
> - The "streamer failed to create ClientStream" log isn't reached by `Watch`, because the stream
>   interceptor is installed with `withMax(0)` and returns before that branch. The guard only
>   matters for calls that enable stream retries, such as `Snapshot`.
> - With the reorder, a `Canceled`/`DeadlineExceeded` status from the server while the caller's
>   context is still live is now retried with no log at all, up to the retry limit.
