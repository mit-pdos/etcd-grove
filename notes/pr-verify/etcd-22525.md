# etcd-io/etcd#22525: finish publishV3 when a leader snapshot already carries it

- PR: https://github.com/etcd-io/etcd/pull/22525, "etcdserver: finish publishV3 when a leader
  snapshot already carries it", one commit, head `429b52576ed06213ea8008acac3b039024e5d754`, open
  and not yet reviewed upstream. It fixes etcd-io/etcd#22524: a member that joins with an empty data
  directory and catches up from the leader's snapshot becomes ready only after its first publish
  request times out (7 s by default). The merge base with `main` is `91703b3d4`.
- Verified at: `mit-pdos/etcd-grove` branch `pr-etcd-22525-goose-lean`, commit `cd4d431d1` ("pr
  etcd#22525 at 429b52576…, onto goose-lean"), on top of the pinned fork commit `09669450f`. The
  PR's diff (`server/etcdserver/server.go`, and its tests in `server_test.go`) applied cleanly, with
  no conflicts and no rewrites, so the verified Go code is the PR's code. `go build ./...` passes, and
  so do `go test ./etcdserver/...` and `go test -race -run 'TestPublishV3|TestApplySnapshot|TestSnapshot'
  ./etcdserver/` in `server/`.
- The Lean side is on branch `pr-verify/etcd-22525` (this file), worktree `/shared/etcd-grove-pr/etcd-22525`.

## Verdict

The change is sound as far as it was verified. `publishV3` was previously a trust-boundary axiom
that said only "it returns". It is now translated with its body and proved, including the PR's
per-attempt goroutine, the `publishedBySnapshot` flag and the error override. The proof shows four
things:

- `s.readych` is closed at most once.
- It is closed only with evidence that the member's attributes are published: either the apply
  thread dispatched the member's own `ClusterMemberAttrSet` entry, or `RaftCluster.Member` returned
  exactly this member's name and client URLs.
- The only other way out of the loop is the stopping path, and on that path `readych` stays open.
- The goroutine is memory-safe and never blocks the loop.

The new `hasPublishedAttributes` is proved too. `start` is re-proved over the new field, and so is its
caller `Start` over `publishV3`'s new spec.

Some things are not covered:

- **Liveness.** The PR's whole point is that the attempt returns early. A Hoare triple can't
  express that, so only the PR's tests cover it.
- **Committed membership.** The proof doesn't show that what `Member` returns after a snapshot is
  committed membership. That is the trust boundary `membership.attrsHeld`.
- **The new `Notify` in `applySnapshot`.** `applySnapshot` is verified only for raft's no-snapshot
  case.

The review found no bug in the PR itself, but one interaction matters. The existing code doesn't
advance `s.appliedIndex` when it applies a snapshot, which is upstream's #22528, fixed by the open
#22529/#22510. So with this PR alone, a new member in an idle cluster can become ready on the
snapshot and then reject every write with "too many requests". The PR should land with or after
that fix. The review also made three small observations (under Findings).

## The behavior changes

**`publishV3`**:

- **Old spec** (`git show lean:Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__publishV3.lean`,
  an axiom): `{{ isPkgInit }} s.publishV3(d) {{ RET (); True }}`.
- **New spec** (`Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__publishV3.lean`; the vocabulary
  is in `Proof/go_etcd_io/etcd/server/v3/etcdserver/InvPublish.lean`):
  - Precondition: the request path's view `isServerReq`, the fields it reads (`srvPubFields`: the
    member id, cluster, attributes and their URLs, logger, context, `stopping`, the snapshot
    notifier, a certified log, the id budget, and `threadBound GF < actualMaxReaders`), a request
    goroutine's resources (a `leadTimeMu` reader slot, `E.RD`, an `lgMu` slot), all the notifier's
    reader slots, and the closer's view of `s.readych`. `s.readych` is a broadcast channel whose
    close carries `pubDone`.
  - Postcondition: the resources come back, and either `readych` is still open (the stopping
    path) or it is closed and `pubDone c id a cus` holds.
  - `pubDone` means one of two things. Either `RaftCluster.Member(id)` was seen to hold
    `(a.Name, cus)` (`membership.attrsHeld`). Or `raftRequest` succeeded, so the wire form of
    `&pb.InternalRaftRequest{ClusterMemberAttrSet: req}` went through `apply.applyStep` as
    dispatched.
- **Difference**: the old spec says nothing. The new one ties readiness to a published-attributes
  fact, and the second disjunct is the PR's new path.
- **The flag**: `publishedBySnapshot` has an invariant (`pubFlagInv`) saying it is set only with
  `attrsHeld`. That is why `err != nil && publishedBySnapshot.Load()` sets `err = nil` only with
  evidence.

**`hasPublishedAttributes`** (new, `Spec/.../EtcdServer__hasPublishedAttributes.lean`): with the
member id, cluster and attributes read-only (`srvMemberAttrs`), it returns `true` only if
`membership.attrsHeld c id a.Name cus`.

**`start`**: the spec text is unchanged. `isServerBuilt` (`InvStart.lean`) gains three things:

- `Hsnapa`: the field, any value.
- `Hrdbound`: `threadBound GF < actualMaxReaders`.
- `Hpub` (`srvPubBuilt`): the member's id, cluster and attributes as `NewServer` set them, and
  `readych`'s closer view.

`srvStarted` gains four things:

- `Hsas`: the notifier `start` made, with its writer guard and all its reader slots.
- `Hrdbound`.
- `Hpub`.
- `Hctxs`: `s.ctx` and its `isContext`.

**`Start`** (`Spec/.../EtcdServer__Start.lean`): its precondition gains a third `lgMu` reader slot,
a `leadTimeMu` slot and `E.RD`, which are the publish goroutine's request resources. Before, they
were hidden behind the `publishV3` axiom.

## Trust base

(The tables below come from `etc/tcb-report.py --collection etc/tcb-collections/pr-etcd-22525.txt`
after a full `lake build` of the worktree; see "Trust base, measured".)

New postulates (`axiom … .wp_proof`), each with why it is believed:

- `membership.RaftCluster.Member` (`Spec/go_etcd_io/etcd/server/v3/etcdserver/api/membership/RaftCluster__Member.lean`):
  - It returns `nil`, or a fresh, owned clone with name `nm` and URLs `cus`, and
    `membership.attrsHeld c id nm cus` holds.
  - The body is `c.Lock(); defer c.Unlock(); return c.members[id].Clone()`, and `Clone` deep-copies
    `ClientURLs`, so the ownership part is right.
  - `attrsHeld` is an uninterpreted `opaque` predicate, so the axiom is consistent: `True`
    satisfies it. It means only "`Member` observed these attributes".
  - The reviewer pointed out that it doesn't mean "committed". At a new cluster's bootstrap,
    `c.members` comes from `--initial-cluster`, and `newMember` sets the name with no client URLs.
    The doc comment says so.
- `slices.EqualString` (`Spec/slices/EqualString.lean`): `slices.Equal` on `[]string` returns
  whether the two lists are equal. Go's body compares lengths and then the elements with `==`.
- `fmt.SprintfAttrs` (`Spec/fmt/SprintfAttrs.lean`): `Sprintf` of one `membership.Attributes`
  returns some string, reading the argument slice and the URL slice's elements, both owned by the
  precondition. `Attributes` has no methods, so `fmt` calls no etcd code. The reviewer's point that
  the first draft didn't own the URL slice is fixed.

New premises, in the construction premise, not axioms:

- `threadBound GF < actualMaxReaders` (2^30 - 1) bounds how many threads can be live. This is
  stronger than `isServerBuilt`'s existing `≤ 2^31`. Adequacy chooses `threadBound`, so it can be
  met.
- `srvPubBuilt`: `NewServer` sets `memberID`, `cluster` and `attributes` once, and `readych` is a
  fresh channel.

No `sorry` was added. The results here rest on the axioms they rested on before, with the old
`EtcdServer.publishV3.wp_proof` axiom replaced by the three above.

Why a pool of reader slots (`PublishPool.lean`):

- Each attempt's goroutine calls `Receive` on `s.snapshotApplied`, which read-locks the notifier's
  `RWMutex`. Perennial bounds the reader slots (`notifyReader`), as Go's `rwmutexMaxReaders` does.
- The goroutines aren't joined, and an attempt may start before the previous goroutine has exited.
- So a goroutine draws a slot from an invariant by depositing its thread token, and gives the slot
  back when it exits. With fewer live threads than slots, the pool is never empty.

## Findings

**An interaction with a known bug in the existing code.** `applySnapshot` doesn't advance
`s.appliedIndex`, while raft raises `s.committedIndex` to the snapshot's index. This is
`issues/etcd-snapshot-applied-index-stale.md`, recorded by the verification of
etcd-io/etcd#22529 and copied to this branch. It is upstream's etcd-io/etcd#22528 and #22516,
fixed by the open PRs #22529 and #22510.

On a new member in an idle cluster, the gap between the two indices exceeds 5000, so
`exceedsRequestLimit` rejects every proposal through that member with `ErrTooManyRequests` until
another member's write is applied. That includes `publishV3`'s retries, so without #22525 the
member stays unready.

With #22525, if the member's first proposal is covered by the snapshot, the member becomes ready
on the snapshot, but its applied index is still stale. It then reports ready (`ReadyNotify`, the
readiness probes) while rejecting every client write with "too many requests". The symptom
changes from "never ready" to "ready but rejecting writes".

`notes/pr-verify/etcd-22525/server_publish_stale_applied_test.go` shows that state on the fork
with the PR (it passes: ready, `AppliedIndex()` 0, a `Put` rejected). It simulates the snapshot
through the same three effects `applySnapshot` and raft have. #22525 should land with or after
#22529/#22510, which set `s.appliedIndex` in `applySnapshot`. With them, the member made ready by
the snapshot has an applied index equal to the snapshot's.

No other bug was found in the PR or in the existing code. The reviewer (a fresh subagent, given the PR, the specs, the postulates and the invariants) checked the
interleavings on `publishedBySnapshot`, `ctx` and `cancel`, a nil `snapshotApplied` (impossible: it
is set in `start` before `go s.run()` and before `Start`'s `GoAttach(publishV3)`, and the PR's tests
set it for their direct `publishV3` calls), a snapshot applied between `Receive()` and the proposal
(covered: the argument is evaluated before the proposal), and `readych` closing twice (impossible).
It made three observations, none of them a bug:

1. **The PR text overstates one claim.** It says that a member that restarts with its attributes
   already in its own store still publishes through raft, and the `hasPublishedAttributes` comment
   repeats this. That holds only while no snapshot is applied during the attempt. If a restarting
   member that is far behind installs a leader snapshot during its first attempt, it becomes ready
   on the snapshot, without its own entry. That is correct, because its attributes are the ones
   already held. Probe: `notes/pr-verify/etcd-22525/server_publish_restart_test.go`
   (`TestPublishV3RestartWaitsWithoutSnapshot` and `TestPublishV3RestartCompletedBySnapshot` both
   pass; output in `test-fork-pr.log`).
2. **Ready during shutdown.** If `raftRequest` returns `ErrStopped` while the snapshot check has set
   the flag, `publishV3` now closes `readych` and logs "published" during shutdown. Before the PR,
   it looped and left on `stopping`. The spec allows both. The attributes are published, so this
   is harmless.
3. **The applied index lags** (the reviewer's version of the interaction above). `applySnapshot`
   doesn't call `setAppliedIndex`, and its `Notify` runs before `applyAll`'s `applyWait.Trigger`.
   So a member made ready through the snapshot path reports an applied index below the snapshot's.
   Linearizable reads still wait on `applyWait`, so they are unaffected. Writes are not, as shown
   above.

Open points:

- The PR's argument that an observation made after an applied leader snapshot reflects committed
  membership isn't in the spec. `attrsHeld` is only an observation, and `pubDone` would hold just
  as well if the check ran without any snapshot. Stating it would take an invariant on the
  members map tying it to committed state, and the map's writers are names-only.
- `applySnapshot`'s snapshot path, including the new `Notify`, is unverified (existing scope).
- `start` hands `run` no writer guard of `snapshotApplied`, because `applySnapshot`'s verified case
  doesn't notify. A proof of the snapshot path would take it from `srvStarted`'s `Hsas`, which
  `Start` currently drops.

## Related PRs

- etcd-io/etcd#22527 ("wait for apply before retrying a rejected publish", head `6d1df10c5`)

  verification (`pr-verify/etcd-22527`) had no commits when this report was written.
  `publishV3`'s spec here is unaffected by it: its postcondition says nothing about the failure
  branch beyond looping. A combined proof would add `waitApplyWithinRequestLimit` (with
  `applyWait`'s `isWaitTime` from `isServerRead`) to the failure branch.
