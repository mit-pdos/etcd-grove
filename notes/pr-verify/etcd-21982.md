# etcd-io/etcd#21982: verification report

- **PR**: etcd-io/etcd#21982, "server: commit compaction deletes after unlocking batch tx" (xigang), open,
  one commit, head `9f62dc886b4a5ef248ee993e3a9ef87ed474342a`, base `main` at `61d518f55`. No linked issue; no
  review comments.
- **What it says it does**: compaction deletes no longer force a bbolt commit (an fsync) while the batch-tx
  lock is held. The lock is released first, and then the batch is committed, so queued apply operations are not
  blocked behind compaction's fsync. Ordinary client deletes keep their immediate commit.

    upstream, non-blocking defrag), which the PR does not touch. **The verified code is the PR's code.**
  - One test-only addition: `fakeBatchTx.UnsafeDeleteForCompaction` in `server/storage/mvcc/kvstore_test.go`.
    Without it, mvcc's tests do not compile, at the PR head too (finding 1).
  - `go build ./...`, `go vet ./storage/...` and `go test ./storage/{backend,mvcc,schema}/` pass in `server/`.
- **Proofs**: branch `pr-verify/etcd-21982` of this repository (worktree `/shared/etcd-grove-pr/etcd-21982`).

## Verdict

The change is sound as far as it is verified, and it does what it says. It also has two defects in its test and
CI surface that should be fixed before merge: mvcc's tests do not compile, and a robustness failpoint silently
disappears (findings 1 and 2).

- **`scheduleCompaction`.** Its existing spec is re-proved, unchanged, over the PR's control flow: unlock, then
  commit, for every batch, the last one included. Under mvcc's backend contract a compaction delete never had
  to be visible at any particular time (reads may miss deletable keys), so this is a refactor at that level.
- **The new backend methods.** Both are proved. But the buffered one, the PR's point, is proved only for a hook's
  bucket. The backend's model says that a free batch lock means the readers see the writer's contents. The PR
  deliberately breaks that for schema's `Key`: until the next commit, readers keep seeing the revision keys
  compaction deleted (`notes/pr-verify/etcd-21982/compaction_delete_visibility_test.go`).
- **Why that is safe.** No reader looks those keys up. This rests on mvcc's proved result that the index never
  names a compacted revision, and, for the hash, the watchers and restore, on code reading by me and the
  reviewer. It is not a proof over the real backend: that would need the backend's view redesigned to be one
  "up to deletable keys", which the real backend also lacked before the PR (compaction is verified only
  against mvcc's assumed backend contract).
- **What is new for readers.** Their view now lags the writer's contents while the lock is free, which is a
  longer window of the state a `ConcurrentReadTx` taken just before a commit already saw. Nothing observable
  to clients changes. The PR also commits the final batch (and `finishedCompactRev`) before the job returns,
  where before a final batch with no deletes stayed uncommitted until the periodic commit; this repository's
  models have no durability, so that improvement is not stated.

### The specs

- **`batchTx.UnsafeDeleteForCompaction`**: `Spec/go_etcd_io/etcd/server/v3/storage/backend/batchTx__UnsafeDeleteForCompaction.lean`.
  bbolt's writer deletes the entry and `pending` goes up by one. It is `batchTx.UnsafeDelete`'s statement for the
  new method. The proof calls that spec.
- **`batchTxBuffered.UnsafeDeleteForCompaction`**:
  `Spec/go_etcd_io/etcd/server/v3/storage/backend/batchTxBuffered__UnsafeDeleteForCompaction.lean`.
  - It moves the session to `BSess.delC` (`Proof/.../backend/LateDel.lean`): the writer's contents lose the key,
    `pending` goes up by one, and `pendingDeleteOperations` is unchanged. So the `Unlock` that follows does not
    commit, and readers keep seeing the key until some later commit.
  - It is stated and proved for a key of one of the pre-commit hook's buckets only (premise
    `P.HB bi.name = true`), and not for one of the hook's own keys. `UnsafeDelete`'s spec is the opposite: any
    bucket except a safe-range one.
  - `sessWf_delC` (`LateDel.lean`) is the invariant step.
- **`store.scheduleCompaction`**: `Spec/go_etcd_io/etcd/server/v3/storage/mvcc/store__scheduleCompaction.lean`.
  The statement is unchanged; only its doc comment now says that each batch is unlocked and then committed,
  the last one too. The proof (`Proof/.../mvcc/store__scheduleCompaction.lean`) follows the new control flow:
  - the `finished` flag;
  - the meta put and the job's ghost update (`compactedAt`) before the `Unlock`;
  - `Unlock`, `ForceCommit` and the pause metric on both paths;
  - then either the hash and return, or `RevToBytes` and the sleep/stop `select`.
- **mvcc's backend contract**: `batchTxSpecG`, `Proof/.../mvcc/InvStore.lean`. The compaction-only clause
  (under `Cmp`) of `UnsafeDelete(schema.Key, k)` is now one of `UnsafeDeleteForCompaction`, with the same
  statement. Deleting a key that compaction may delete (`Del k`) leaves the logical bucket as it is, and reads
  may miss such keys (`snapThin`). That statement never said *when* a delete becomes visible to readers, so it
  fits the PR's late visibility as well as it fitted the old immediate commit. No other clause or proof uses the
  method.

### What the backend's model would need (why `Key` is not covered)

The backend's model (`Model2.lean`, `InvBackend.lean`) keeps three facts:
- whenever no *counted* delete is pending, the readers' view (committed data overlaid with the read buffer)
  agrees with the writer's contents off the hook's buckets (`sessWf`);
- when the batch lock is free, no delete is pending (`freeOk`);
- a commit, which the `run` goroutine or any other session's `Unlock` may make, therefore leaves the clients'
  view `vData` unchanged. The committer does not hold that view.

The PR breaks all three for a non-hook bucket, by design:
- after the compaction batch's `Unlock`, the lock is free;
- readers still see the deleted revision keys, and the writer does not
  (`notes/pr-verify/etcd-21982/compaction_delete_visibility_test.go`);
- the next commit, whoever makes it, removes them from what readers see.

So no spec of `batchTxBuffered.UnsafeDeleteForCompaction` on `Key` holds in this model. What the PR relies on is
that no reader looks up a compacted revision. That needs the backend's view to be one "up to deletable keys":
- the clients' view keeps a key that compaction deleted;
- readers' snapshots may miss such a key at any time, as mvcc's contract already says (`snapThin`);
- deletes carry the client's evidence that the key is deletable (mvcc's `delKey`).

That is the redesign `notes/decisions.md` ("The compaction over the real backend") already names as the reason the
real backend does not support mvcc's compaction (`Cmp` false in `BackendBridge.lean`). Two of the obstacles listed
there change with this PR:
- *A compaction `Unlock` changes the clients' view*: no longer. That `Unlock` now commits only at the batch limit,
  and the meta put is in a hook's bucket.
- The obstacle moves to the commits: every commit (`ForceCommit`, the periodic commit, another session's) may now
  change the readers' view. The model must allow that without the clients' view, which only the "up to deletable
  keys" view does.

The other obstacles are unchanged: deletion from a safe-range bucket, the `Meta` reads, the budgets.

## Findings (step 8)

Every test, probe and log is in `notes/pr-verify/etcd-21982/`; its `README.md` gives the revision and command for each.

**Bugs in the PR:**

1. **mvcc's tests do not compile at the PR head.** `go vet ./storage/mvcc/` (and `go test`) fails:
   `kvstore_test.go:996: *fakeBatchTx does not implement backend.BatchTx (missing method
   UnsafeDeleteForCompaction)` (`notes/pr-verify/etcd-21982/vet-mvcc-pr-head.log`). The fake is the only other
   `BatchTx` implementation in the tree. Its new method has to record a `"delete"` action (delegate to its
   `UnsafeDelete`), or `TestStoreCompact`'s expected actions fail. The fork branch adds exactly that, and mvcc's
   tests pass there.
2. **A robustness failpoint silently disappears.** `tests/robustness/failpoint/gofail.go` still lists
   `CompactBeforeCommitBatchPanic` (`"compactBeforeCommitBatch"`), and `failpoint.go` still includes it. The PR
   removes that gofail point. `goPanicFailpoint.Available` asks the member whether the point exists, so the
   failpoint just drops out of random selection, with no error
   (`notes/pr-verify/etcd-21982/check_failpoints.sh`, logs `check_failpoints-{pr-head,base}.log`).
   - Keeping `// gofail: var compactBeforeCommitBatch struct{}` between the new `tx.Unlock()` and
     `s.b.ForceCommit()` fixes the list.
   - It also exercises the window this PR creates: a crash with the batch's deletes uncommitted while the lock
     is free. Before the PR, that point came after a commit had already happened.
   - A smaller change: `compactAfterCommitBatch` now also fires on the final batch, before the hash is stored.
     With the multi-batch trigger it still fires on a non-final batch first.
3. **The new interface method is undocumented** (low). `BatchTx.UnsafeDeleteForCompaction` is exported and has
   no doc comment. Its contract is weaker than `UnsafeDelete`'s: `ReadTx` and `ConcurrentReadTx` keep returning
   the key until the next commit, so it is safe only for keys no reader will look up. The comment in
   `batchTxBuffered.Unlock` explains why ordinary deletes must commit at once (the linearizability argument);
   it should say that this method is the exception and why.

**Checked and found harmless** (the reviewer and I, by reading the code): readers that run between a batch's
`Unlock` and its `ForceCommit`.
- `rangeKeys` looks revisions up through the index, which is compacted before the first batch, so it never asks
  for a deletable key (the proved `named_not_del`).
- `HashByRev` skips deletable keys through `keep`, except as below. The reviewer's test shows the same hash
  during and after a compaction when a key is live.
- Watchers with `minRev < compactRev` are cancelled as compacted. Every deletable key has a main revision of
  at most the compaction revision. A deletable key exactly at it (such as the tombstone of a key deleted and put
  again in that revision, after #22377) would be seen or missed by a watcher at `minRev = compactRev` depending
  on timing. That was already so before the PR, through the pause between batches and snapshots taken before
  a commit.
- `finishedCompactRev` is visible in the read buffer while the final batch's deletes are not committed, but
  nothing reads both. `checkPrevCompactionCompleted` reads only `Meta`, and restore and `Close` wait for the
  running job (`fifoSched.Stop`).
- Other commits only commit the deletes earlier: another session's `Unlock`, the periodic commit, `Snapshot`,
  defrag. bbolt's write transaction is atomic.
- The fork's non-blocking defrag is excluded for the whole pass by `LockForSafeRangeDelete`, which covers each
  `ForceCommit`.
- A crash between `Unlock` and `ForceCommit` loses the batch's deletes and `finishedCompactRev` together.
  `scheduledCompactRev` is already committed, so the compaction is redone at restart.
- At the batch limit, the compaction's `Unlock` still commits under the lock, and the `ForceCommit` after it
  commits the consistent-index hook's re-put. That is two commits, as every batch with deletes had before the
  PR. Otherwise the PR removes one of the two commits per batch.

**Bug in the existing code** (older than the PR, which neither causes nor fixes it): with no key live, `HashByRev`
differs between a member mid-compaction and one that has finished. That is symptom 2 of
`issues/etcd-hash-empty-keep.md`, copied from `pr-verify/etcd-22515`, with this run's reproduction added. The
reviewer's test is `notes/pr-verify/etcd-21982/review_compaction_hash_test.go` (log
`review_compaction_hash_test.log`): 1555807101 during the compaction, 1084519789 after it, at revision 8 with
compaction revision 8. The PR makes the window between batches no longer than before.

**Reviewer's open points:** none beyond the findings above. The reviewer confirmed the claim about the backend's
model: the restricted spec is sound, and its doc says it does not cover `Key`.
