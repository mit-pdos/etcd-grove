## Verdict

The change is sound as far as it was verified. The proof is complete, with no `sorry`.

- **No orphans**: `closeRequireLeader` keeps the lessor's lock invariant, including that every
  entry of `l.keepAlives` has at least one subscription. That is exactly what etcd#22094 found
  broken. The pinned code compacts such an entry to zero channels and leaves it in the map, so it
  does not keep the invariant.
- **No panics or double closes**: the function closes each channel at most once, through the close
  right its subscription holds, and never closes a nil channel or indexes out of range.
- **Mixed entries are compacted as before.** The PR does not touch the compaction, which still
  pairs a kept channel with another subscription's context (the pre-existing etcd#22081).

The PR makes that older bug a little worse. When a plain subscriber's channel is wrongly closed at
a second leader loss, the entry is now deleted as well, so that subscriber's lease stops being
renewed.

What is not covered:

- The spec is a safety spec. Its postcondition is `True`, so it does not say that the
  require-leader channels *are* closed. A function that does nothing would also meet it.
- It does not say that a subscription leaves the map only with its channel closed.
- The other functions that touch `keepAlives` are not translated. By reading the code, they keep
  the invariant (see "Callers and shared state").

## The spec

`Spec/go_etcd_io/etcd/client/v3/lessor__closeRequireLeader.lean`, over the lock invariant
`lessor.muInv R l` of `Proof/go_etcd_io/etcd/client/v3/InvLease.lean`.

**The invariant** covers what `l.mu` protects, which is the `keepAlives` map:

- each entry is a `*keepAlive` whose `chs` and `ctxs` slices hold one list `subs` of subscriptions,
  each a channel with its subscriber's context;
- the two slices have the same length, and the list is **non-empty**;
- no channel is nil;
- every context is "stable" (see the axiom below);
- there is one resource `R ch ctx` per subscription, the caller's right to close `ch`.

**The spec**:

- **Pre**: the mutex has that invariant. Package init gives the two `rpctypes` metadata variables.
  It also takes `lessor.closeOk R` (with `R ch c`, `close(ch)` succeeds when `c` asks for a
  leader) and the premise `□ ∀ ch c c', R ch c -∗ R ch c'`.
- **Post**: `True`.

There is no old spec to compare with: the function was not translated.

The new spec does not hold of the old code. In the branch where every subscription required a
leader, the old code leaves the entry with `subs = []`, which the invariant forbids. The PR's test
`TestLessorCloseRequireLeaderRemovesOrphanedKeepAlive` shows the same thing in Go: it fails on
upstream f744d457f and passes at the head.

**The premise `R ch c -∗ R ch c'` is the pre-existing bug etcd#22081**
(`issues/etcd-lease-closerequireleader-ctx-misaligned.md`). The proof uses it only where a mixed
entry is compacted (`newCtxs[newIdx] = ka.ctxs[newIdx]`), which pairs the kept channel with another
subscription's context. Because of it, `closeOk`'s condition is about the context stored at the
channel's index, not the subscriber's own. So the spec does not exclude closing a plain
subscriber's channel at a later leader loss.

A fix of etcd#22081 such as etcd-io/etcd#22087 (`ka.ctxs[i]`, queued) should let the spec drop
the premise. Then `closeOk` would mean what it says: only channels whose own context asks for a
leader are closed. The proof's compaction loop would carry the pairs instead of re-pairing them
(`lessor.repair`).

## Callers and shared state

- **Callers**: the only one is `recvKeepAliveLoop` (`lease.go:494` at the fork commit), on
  `ErrNoLeader`. It is unexported and not translated: not specified, and it has no other callers.
  Nothing outside `lease.go` calls `closeRequireLeader` in any of etcd's modules.
- **Exported API**: none of it changes. A client sees the change only as a lease no longer kept
  alive after all its require-leader subscriptions closed, which is the documented intent
  (`WithRequireLeader`).
- **Shared state**: the invariant is new and covers `l.keepAlives`, so every function touching it
  under `l.mu` is a "caller". The reviewer read each of them at the PR head. None is translated.
  - `NewLeaseFromLeaseClient` makes an empty map.
  - `KeepAlive` adds a one-subscription entry with a fresh channel, or appends to `ctxs` and `chs`
    together.
  - `keepAliveCtxCloser` removes one index from both slices, closes that channel, and deletes the
    entry when it is empty.
  - `recvKeepAlive` either deletes the entry and calls `ka.close()` (TTL ≤ 0), or only sends.
  - `deadlineLoop` calls `ka.close()` and deletes the entry.
  - `recvKeepAliveLoop`'s teardown closes every entry and replaces the map.
  - `sendKeepAliveLoop` only reads; `Close` does not touch the map.

  All of them keep non-emptiness, equal lengths and non-nil channels. Each removal closes exactly
  one channel, so nothing is closed twice. Before the PR, `closeRequireLeader` was the only
  function that broke non-emptiness. These are unchecked by proof: specifying them means modeling
  the channels' protocol (what `R` is) and the stream goroutines.

## Trust base

`etc/tcb-report.py --roots lessor__closeRequireLeader`, and the new collection
`etc/tcb-collections/pr-etcd-22291.txt`: the result rests on one axiom of this repository and no
`sorry`. `etc/tcb-baseline.txt` and `etc/tcb-collections/client.txt` are updated (`--check
--update`) with that axiom.

- **New axiom: `metadata.FromOutgoingContext.wp_proof`**
  (`Spec/google_golang_org/grpc/metadata/FromOutgoingContext.lean`). For a context with
  `metadata.outgoingStable ctx`, the call returns `(md, ok)`: `ok` is false when there is no
  outgoing metadata, and otherwise `md` is a fresh map of fresh slices with the contents
  `metadata.outgoingMD ctx`. Both of these are uninterpreted. This matches grpc v1.84.0's code:
  `out := make(MD, ...)`, `copyOf`, an `append` onto a fresh slice, and `ok` false exactly when
  there is no `rawMD`.
  - The premise is needed because the reviewer showed that grpc's result is not a function of the
    context value:
    - `NewOutgoingContext` keeps the caller's `MD`, so mutating it changes later results;
    - keys equal up to case merge in map-iteration order
      (`TestReviewFromOutgoingContextNotDeterministic`).
  - `outgoingStable` stands for "non-nil, `Value` does not panic, metadata never mutated, no keys
    equal up to case". The lessor's invariant demands it of every subscription's context. That is a
    premise about the contexts users pass to `KeepAlive`: `WithRequireLeader` builds a fresh `MD`
    no one else holds.
- Already there: the types Goose does not translate (Perennial's axiomatized types) and Perennial's
  models (`sync.Mutex`, channels through `closeOk`).
- No `sorry` was added.

## Findings

1. **In the PR: nothing wrong with what it changes.**
   - The delete branch is reached only when `reqIdxs == len(ka.chs)`, that is, when every channel
     was just closed. Deleting while ranging over the map is safe.
   - Not calling `ka.close()` is right, since it would close the channels twice.
   - An in-flight response for the deleted id is ignored. A later `KeepAlive` for the same lease
     makes a fresh entry.
   - A deleted subscription's `keepAliveCtxCloser`, waking later, finds no entry, or a new entry
     without its `&ctx` key, and does nothing.
2. **(Low; in the PR, also in #22253) `ka.donec` stays open on the delete path.**
   - The `keepAliveCtxCloser` goroutines of the deleted subscriptions stay blocked until their
     contexts end or the lessor closes (`TestReviewDeletedEntryDonecNotClosed`).
   - This is not a regression: before the PR they were blocked behind the orphan entry.
   - `close(ka.donec)` before the `delete` would release them. It is safe because `ka.close()` is
     only called on entries still in the map.
3. **(Medium; pre-existing, recorded) etcd#22081** (`issues/etcd-lease-closerequireleader-ctx-misaligned.md`).
   - The compaction pairs a kept channel with another subscription's context.
   - A plain subscriber can have its channel closed at a second leader loss. Canceling its own
     context no longer closes its channel, and canceling the require-leader subscriber's context
     closes it instead.
   - Tests: `notes/pr-verify/etcd-22291/lease_requireleader_pairing_internal_test.go` (fails on the
     pin, upstream and the PR head; `pairing-fork-pin.log`), and `TestReviewMixedCase`
     (`review-tests.log`).
   - The PR does not cause it. With the PR, the second loss also deletes the entry, so that
     subscriber's lease silently stops being renewed.
   - etcd-io/etcd#22087 fixes it and should be merged first or together.
4. **(Pre-existing, the bug the PR fixes) etcd#22094** (`issues/etcd-lease-closerequireleader-orphan.md`).
   The proof confirms the fix: the invariant's non-emptiness holds after `closeRequireLeader` at the
   PR head, and it is false of the pinned code.
5. **Comparison with etcd-io/etcd#22253**, the competing fix: it compacts first, then deletes when
   `len(ka.chs) == 0`. It behaves the same: the entry is deleted in exactly the same cases, with
   the same open `donec`. It would meet the same spec, with the same proof outline except that the
   delete comes after the compaction loop.

**Reviewer's points**:

- **Resolved**:
  - The spec's docstring overclaimed "only require-leader channels"; it now states what is and is
    not guaranteed.
  - The `FromOutgoingContext` axiom was false for mutable or case-colliding metadata; the
    `outgoingStable` premise was added.
- **Open, recorded above**:
  - The spec is safety-only: no guarantee that the closes happen, and rights can be dropped.
  - `closeOk` and the premise are not discharged by any verified caller.
  - Finding 2.

## Draft review comment (for the user to edit and post)

> The change looks right to me. Deleting the entry only when `reqIdxs == len(ka.chs)` means every
> channel of the entry was just closed, so skipping `ka.close()` is correct (it would double-close),
> and nothing else holds the entry: a later response for that lease ID is ignored, and a later
> `KeepAlive` builds a fresh entry.
>
> Two small things:
>
> 1. On the delete path `ka.donec` is never closed. So the `keepAliveCtxCloser` goroutines of
>    those subscriptions stay blocked until their contexts are canceled or the lessor is closed.
>    This was already true before the change, when they waited behind the orphaned entry. Closing
>    `ka.donec` before the `delete` releases them and is safe, since `ka.close()` is only ever
>    called on entries still in the map.
> 2. The compaction a few lines below still pairs the kept channel with `ka.ctxs[newIdx]` rather
>    than `ka.ctxs[i]` (#22081, fixed by #22087).
>    - With subscriptions `[A (require leader), B (plain)]`, after one leader loss the entry is
>      `chs=[B]`, `ctxs=[ctxA]`. Canceling B's context then no longer closes B, and a second leader
>      loss closes B.
>    - With this change, that second loss also deletes the entry, so B's lease silently stops being
>      renewed.
>    - It would be good to land #22087 first, or together, and to add a mixed-case test: one
>      require-leader and one plain subscription, then check that the plain channel stays open and
>      the entry stays, across two leader losses.
