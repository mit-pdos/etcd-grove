## Verdict

The change is sound and does what the PR says, as far as it was verified. `ServeHTTP` is now
proved against a spec. The handler reads at most 64 KiB + 1 bytes of the request body, whatever
the client sends. (When net/http closes the body, it may still read and discard up to 256 KiB
more to reuse the connection. That was already so before the PR, and none of it is kept in
memory.) A body longer than 64 KiB gets `413 request body too large`, and the handler
neither decodes it nor computes a hash. Every other outcome (405, bad path, 412, a read error,
a decode error, a `HashByRev` error, a marshal error, 200 with the hash) is as before. The spec
does not hold of the old code: the Go probe on the base reads a 16 MiB body whole and answers 200.

The PR's own description is accurate. The one visible behavior change is the status for a body
over 64 KiB: before, it was 200 or 400 depending on the JSON; now it is 413. The only caller in
etcd is the peer client `HashByRev`, which sends `{"revision":N}`, a few bytes, so it is not
affected.

Not covered by the proof (the trust boundary, below): what `net/http`, `io.ReadAll`,
`encoding/json` and `errors.As` do is postulated, not proved. The postulate that carries the bound
(`io.ReadAllMaxBytes`) was checked against Go 1.27's `maxBytesReader.Read` and `io.ReadAll`, and
the Go probe confirms it at the edge (65536 bytes accepted, 65537 rejected, 65537 read of 16 MiB).

## The spec

`Spec/go_etcd_io/etcd/server/v3/etcdserver/hashKVHandler__ServeHTTP.lean`, over the model in
`Proof/go_etcd_io/etcd/server/v3/etcdserver/InvHashKV.lean`. There is no old spec: the function
was not translated before.

- **Precondition.** The server's facts are persistent (`hashKVHandlerOk h cid R`): the handler's
  logger (not nil) and server, the server's cluster and its id `cid`, and the KV, whose
  `HashStorage().HashByRev(rev)` returns a hash related to `rev` by a relation `R` or an error
  (`hashKVOk kv R`). The response writer is a `ResponseWriter` whose `Header` and `Write` act on
  an owned response log `respLog w evs`. The request's fields are read-only. The body has content
  `c` (bytes, then end of stream or a read error that is not `io.EOF`) and is owned (`bodyR`);
  its `Close` closes it. Its read error, if any, has an error tree `errors.As` can walk
  (`bodyErrOk c`).
- **Postcondition.** The handler appends `evs'` to the response, and one of these holds:
  1. the method is not `GET`: `Allow: GET`, then 405; the body is untouched;
  2. the path is wrong: 400 `bad path`; the body is untouched;
  3. the `X-Etcd-Cluster-ID` header is neither empty nor the server's id string
     `types.idStr cid`: 412; the body is untouched;
  4. the header is empty or the server's id, and the body is read and closed with
     `c.drop (min (len c.data) (65536 + 1))` left unread by the handler. This is the bound: the
     handler reads at most 65537 bytes. The response is
     `hashKVBodyServed c R (types.idStr cid) evs'`:
     - over 65536 bytes: exactly `[error 413 "request body too large"]`;
     - a read error within the bound: 413 or 400 (`errors.As` decides; 413 only if the body's
       error is itself a `MaxBytesError`);
     - the whole body read: 400 if it does not decode (`json.hashKVReqOf`); else, for the
       decoded revision `rev`, 400 on a `HashByRev` error, or, for a hash `kvh` and revision
       `crev` with `R rev kvh crev`, 500 on a marshal error, or the headers
       `X-Etcd-Cluster-ID: idStr cid` and `Content-Type`, then the body
       `json.hashKVRespJSON crev kvh...`.

  For a body over the bound, the spec says the response is exactly the 413. It does not say that
  the body is not decoded and no hash is computed. Those calls leave no trace in the
  postcondition, although the code makes neither.

## Callers (step 6)

The function had no spec before, so no caller's proof depended on one. Its callers:

- `net/http`'s `ServeMux`, through the handler `etcdhttp.newPeerHandler` registers at
  `/members/hashkv` (`server/etcdserver/api/etcdhttp/peer.go`, from `s.HashKVHandler()`). This is
  an exported API, the peer HTTP endpoint. Its spec change is the 413 for a body over 64 KiB,
  which the PR describes. The PR adds no CHANGELOG entry; the change is visible only to a client
  sending more than 64 KiB, which etcd's own client never does.
- The peer client `HashByRev` (same file) is a client of the endpoint, not a Go caller. Its
  request body is `json.Marshal(&HashKVRequest{Revision: rev})`, at most about 40 bytes.
- No other Go code calls `ServeHTTP` (tests only).

## Findings

- **Bugs in the PR**: none found, by the proof or by the reviewer, who checked the PR's code
  against short reads, data returned with an error, chunked bodies, a nil body (net/http never
  passes one), HTTP/2 (no `requestTooLarge` hook: the connection stays open, harmlessly) and the
  only client.
- **The reviewer's points** (a fresh subagent over the PR, the spec, the model and the
  postulates; a second pass confirmed the fixes). Resolved:
  - `maxBytesR` was persistent, though the Go reader keeps a budget and a sticky error. It is now
    owned and consumed by `ReadAll`.
  - The `ReadAll` postulate read a negative limit as 2^64 − 1. It now takes `0 ≤ n`.
  - The body error's error tree came from the `ReadAll` postulate. It is now a premise about the
    body (`bodyErrOk`).
  - The 412 case allowed any non-empty header, because `ID.String` returned an unconstrained
    string. `ID.String` now returns `types.idStr id`: 412 iff the header is neither empty nor
    `idStr cid`, and the served response carries `idStr cid`.
  - Docs now say what is not modelled: the doc of `bodyR` excludes `io.EOF` as a read error;
    `Connection: close` on a 413 and `Close`'s drain are not recorded; the "not decoded, not
    hashed" claim of a 413 is the code's, not the spec's.
  - A duplicated `open` line was removed.
- **Open (minor)**: the 400 after a `HashByRev` error and the 412 carry some message (`∃ msg`).
  The peer client matches on `ErrCompacted`, `ErrFutureRev` and `ErrClusterIDMismatch` in the
  body text, so tying the message to `err.Error()` would be more faithful. The status codes are
  exact. The Go probe calls `ServeHTTP` directly with a counting body, so it does not exercise
  net/http's drain on `Close`.
- **Bugs in the existing code**: none recorded. The old code's unbounded `io.ReadAll` is what
  the PR fixes. etcd's threat model calls it a robustness defect, not a vulnerability, since only
  an authenticated peer can reach the endpoint. It is not recorded in `issues/` because the PR
  fixes it and the verified pin does not yet have the fix; the report is where it is described.
- **Perennial limitations met** (worked around here, `notes/STATUS.md`): Goose emits no Lean
  import for a package the Go file does not import (`net/url` for `r.URL.Path`; the blank import
  above). Instance search for an axiomatized named type's `TypeRepr` prefers the generated `sorry`
  instance to the package's type assumption (local instances in the proof).
