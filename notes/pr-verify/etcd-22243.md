## Verdict

The change is sound and does what the PR says, as far as it was verified. `ServeHTTP` is now
proved against a spec. The handler reads at most 64 KiB + 1 bytes of the request body, whatever
the client sends. A body longer than 64 KiB gets `413 request body too large`, and the handler
neither decodes it nor computes a hash. Every other outcome (405, bad path, 412, a read error,
a decode error, a `HashByRev` error, a marshal error, 200 with the hash) is as before. The spec
does not hold of the old code: the Go probe on the base reads a 16 MiB body whole and answers 200.

The PR's own description is accurate. The one visible behavior change is the status for a body
over 64 KiB: before, it was 200 or 400 depending on the JSON; now it is 413. The only caller in
etcd is the peer client `HashByRev`, which sends `{"revision":N}`, a few bytes, so it is not
affected.

Not covered by the proof (the trust boundary, below): what `net/http`, `io.ReadAll`,
`encoding/json` and `errors.As` do is postulated, not proved. The postulate that carries the bound
(`io.ReadAllMaxBytes`) was checked against Go 1.27's `maxBytesReader.Read` and `io.ReadAll`, and
the Go probe confirms it at the edge (65536 bytes accepted, 65537 rejected, 65537 read of 16 MiB).

## The spec

`Spec/go_etcd_io/etcd/server/v3/etcdserver/hashKVHandler__ServeHTTP.lean`, over the model in
`Proof/go_etcd_io/etcd/server/v3/etcdserver/InvHashKV.lean`. There is no old spec: the function
was not translated before.

- **Precondition.** The server's facts are persistent: the handler's logger (not nil) and server,
  the server's cluster and its id, and the KV, whose `HashStorage().HashByRev(rev)` returns a
  hash related to `rev` by a relation `R` or an error (`hashKVOk kv R`). The response writer is a
  `ResponseWriter` whose `Header` and `Write` act on an owned response log `respLog w evs`. The
  request's fields are read-only. The body has content `c` (bytes, then end of stream or a read
  error), is owned (`bodyR`), and its `Close` closes it.
- **Postcondition.** The handler appends `evs'` to the response, and one of these holds:
  1. the method is not `GET`: `Allow: GET`, then 405; the body is untouched;
  2. the path is wrong: 400 `bad path`; the body is untouched;
  3. the `X-Etcd-Cluster-ID` header is not empty: 412 (ID.String's result is unspecified, so the
     spec does not say it differs from the server's id); the body is untouched;
  4. the body is read and closed with `c.drop (min (len c.data) (65536 + 1))` left. This is the
     bound: at most 65537 bytes consumed. The response is `hashKVBodyServed c R evs'`:
     - over 65536 bytes: exactly `[error 413 "request body too large"]`;
     - a read error within the bound: 413 or 400 (`errors.As` decides; 413 only if the body's
       error is itself a `MaxBytesError`);
     - the whole body read: 400 if it does not decode (`json.hashKVReqOf`); else, for the
       decoded revision `rev`, 400 on a `HashByRev` error, or, for a hash `kvh` and revision
       `crev` with `R rev kvh crev`, 500 on a marshal error, or the headers
       `X-Etcd-Cluster-ID`/`Content-Type` and the body `json.hashKVRespJSON crev kvh...`.

## Callers (step 6)

The function had no spec before, so no caller's proof depended on one. Its callers:

- `net/http`'s `ServeMux`, through the handler `etcdhttp.newPeerHandler` registers at
  `/members/hashkv` (`server/etcdserver/api/etcdhttp/peer.go`, from `s.HashKVHandler()`). This is
  an exported API, the peer HTTP endpoint. Its spec change is the 413 for a body over 64 KiB,
  which the PR describes. The PR adds no CHANGELOG entry; the change is visible only to a client
  sending more than 64 KiB, which etcd's own client never does.
- The peer client `HashByRev` (same file) is a client of the endpoint, not a Go caller. Its
  request body is `json.Marshal(&HashKVRequest{Revision: rev})`, at most about 40 bytes.
- No other Go code calls `ServeHTTP` (tests only).

## Trust base

`etc/tcb-report.py` was not run: it needs the whole tree built. Instead, `#print axioms` of
the linked result `hashKVHandler.wp_ServeHTTP` gives the list
(`notes/pr-verify/etcd-22243/axioms-hashKVHandler.wp_ServeHTTP.txt`). It has **no `sorryAx`**.
The proof uses `net/http`'s type assumption for `http.Request`'s fields
(`Request.TypeAssumptions`), not the generated `sorry` instance of the axiomatized type, which
instance search otherwise picks first. `etc/tcb-baseline.txt`, `etc/tcb-collections/server.txt` and
the new collection `etc/tcb-collections/pr-etcd-22243.txt` are updated by hand with the list below,
not by `--check --update`.

Already on `lean`: `zap.Logger.Warn`, `zap.Error`, `zap.Int64`, `types.ID.String` (names-only
packages), and Perennial's `errors.As.wp_proof`. The callees `EtcdServer.KV`, `EtcdServer.Cluster`
and `membership.RaftCluster.ID` are proved.

Added here (20 axioms, all at the trust boundary of names-only standard-library code):

| Axiom | Why it is believed |
|---|---|
| `http.MaxBytesReader.wp_proof` | `MaxBytesReader` only builds the reader; what reading it does is the next postulate's. |
| `io.ReadAllMaxBytes.wp_proof` | Go 1.27 `maxBytesReader.Read` asks the body for at most `n + 1` bytes; once more than `n` arrive it returns `n` of them and `&MaxBytesError{n}`, then nothing more; a body error before that passes through. `io.ReadAll` turns `EOF` into `nil` and returns everything read. So `min(len, n + 1)` bytes are consumed. The Go probe checks the edge. |
| `http.Error.wp_proof` | `http.Error` writes headers, the status and the message: one `.error code msg` event. |
| `http.Header.Get.wp_proof`, `http.Header.Set.wp_proof` | `Get` returns the header's first value; `Set` on the writer's header map sets a response header. |
| `json.UnmarshalHashKVRequest.wp_proof`, `json.hashKVReqOf` | `Unmarshal` into a zero `HashKVRequest` is a function of the bytes: an uninterpreted one here. |
| `json.MarshalHashKVResponse.wp_proof`, `json.hashKVRespJSON` | `Marshal` of the response the handler builds is a function of its four numbers (or an error whose `Error()` returns). |
| `errors.AsExact.wp_proof` | Go's `As` first checks `TypeOf(err).AssignableTo(targetType)`; an error of exactly the target's element type is assignable, so `As` stores it and returns true. Perennial's `errors.As.spec` only says that some boolean is returned. |
| `http.maxBytesError_asTarget` | `*MaxBytesError` has `Error() string`, so it can be `As`'s target type (method sets are uninterpreted in the model). |
| `http.respLog`, `http.respHdr`(+`_persistent`), `http.reqHdrGet`(+`_persistent`), `http.bodyR`, `http.bodyClosed`, `http.maxBytesR`(+`_persistent`) | Abstract state of the response writer, the request header and the body. Only the postulates above and the caller's premises (net/http's server) introduce or change them. |

## Findings

- **Bugs in the PR**: none found. REVIEWER-PLACEHOLDER
- **Bugs in the existing code**: none recorded. The old code's unbounded `io.ReadAll` is what
  the PR fixes. etcd's threat model calls it a robustness defect, not a vulnerability, since only
  an authenticated peer can reach the endpoint. It is not recorded in `issues/` because the PR
  fixes it and the verified pin does not yet have the fix; the report is where it is described.
- **Perennial limitations met** (worked around here, `notes/STATUS.md`): Goose emits no Lean
  import for a package the Go file does not import (`net/url` for `r.URL.Path`; the blank import
  above). Instance search for an axiomatized named type's `TypeRepr` prefers the generated `sorry`
  instance to the package's type assumption (local instances in the proof).
