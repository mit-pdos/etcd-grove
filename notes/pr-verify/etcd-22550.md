## Verdict

The PR is correct as far as it is verified. The key index now records, beside each revision, the
lease of the change at that revision. Every keys-only read at the current or a past revision
then returns the same lease as a full read, and so as v3.6. This was proved end to end:
- the index's `Put`/`get`/`Range` (`treeIndex.Range` returns each key's lease at its mod revision);
- mvcc's fast keys-only read, whose key-values now carry the lease of the state at the revision read;
- the server's `executeRange` and the client-level results. The server's range is now exactly the
  client model's: the "up to `leaseZ`" exception that `issues/etcd-range-keys-only-lease.md` caused is gone.
  The client's `getExact` no longer excludes keys-only gets, so the cache/recipes results now cover them.

All 16 changed functions that were verified before are verified again. Every one that is only a
refactor keeps its spec, modulo the representation's new lease function.

Not covered by the proof:
- **Restore**: rebuilding the index from a backend with data (`restoreIntoIndex`, `keyIndex.restore`,
  `restoreTombstone`) is untranslated. The `store.restore` axiom covers an empty backend only. That
  path is checked by Go tests: randomized histories, compaction, restart and snapshot restore.
- **Memory**: each index revision grows from 16 to 24 bytes.
- **Mixed-version clusters**: during a rolling upgrade from an unfixed v3.7.x, a keys-only answer
  depends on which member serves it. This is why the PR's upgrade e2e tests fail.

The PR's design (ahrtr's objection) is a maintainers' decision. The verification only shows that the
index's lease is exactly the backend key-value's at every revision, so the index adds no new semantics.

## How leases are modelled

The model key index (`Model.lean`'s `Gen`/`KeyIndex`, `kiPut`, compaction) is unchanged. A
lease is a function of the revision, the lease of the change at that revision. The
representation predicates (`ownGen`/`ownGens`/`ownKi`/`ownEntry`/`ownTree`, `Defs.lean` and
`InvIndex.lean`) take a lease function `lf`: the slice `g.revs` holds `rlVal lf r =
{revision: r, leaseID: lf r}` for each model revision `r`.

The index lock invariant `idxLockInv` uses `lf := evLease (evsOf (ilog ++ [pend]))`
(`Model.lean`), the lease of the event with that revision: a put's lease, or `0` for a delete. Compaction
only drops revisions, and `lf` matters only at the index's revisions (`ownTree_congr`), so the
compaction proofs needed no change beyond the parameter.

New lemmas, all in `InvIndex.lean`:
- `evLease_append_of_mem` and `IdxCRep.evLease_next`: a writer's next change leaves the tree's leases unchanged.
- `evLease_next`: the new revision's lease is the change's.
- `rangeAnswers_rev_mem` and `rangeTaken_leases`: a reader's answers' leases are its own certified log's.
- `mem_evsOf_of_get` and `BucketHas_lease`: the index's lease at a key's mod revision is the backend key-value's `Lease`. A tombstone's revision is never an answer.

The two halves of the read lock may carry different `ilog`/`pend`. `ownGen_combine` combines them at
the first half's `lf`, from the slices' agreement.

## Specs that changed (old, new)

- `keyIndex.put` (`Spec/.../mvcc/keyIndex__put.lean`): before, the revision is appended (`kiPut`).
  Now, the revision is appended with `leaseID`, which must be the representation's lease for it.
- `keyIndex.get` (`keyIndex__get.lean`, `Defs.lean` `kiGetVal`): before, `(mod, created, ver, err)`.
  Now, `(mod, created, ver, lf mod, err)`, with `NoLease` on `ErrRevisionNotFound`.
- `treeIndex.Put` (`treeIndex__Put.lean`): before, `Put(key, rev)` for a change `.put k v l` with any `l`.
  Now, `Put(key, l, rev)`: the index records the change's own lease.
- `treeIndex.Range` (`treeIndex__Range.lean`): before, keys, modifies, creates, versions, total. Now
  also `leases`, `evLease (evsOf kn.log)` of each answer's mod revision.
- `storeTxnCommon.rangeKeys` (`storeTxnCommon__rangeKeys.lean`, `InvStore.lean` `kvPtrIs false`):
  before, a `FastKeysOnly` key-value had `Lease: 0`. Now it has `Lease: kv.lease` of the state's
  key-value at the revision read, which is what a full read returns.
- txn (`etcdserver/txn/RangeModel.lean`): `kvRead true` no longer zeroes the lease, and `leaseZ` is
  deleted. Before, `srvRangeOk_rangeKvsOk` (and `rangeResultClient`, `rangeResult_txn`, `executeTxn`'s
  and `InvTxn`'s range responses) gave `kvs = kvs'.map (leaseZ (fastKeysOnly o))`. Now it gives `kvs = kvs'`,
  the client model's `rangeKvsOk` exactly.
- client (`cache/v3/InvEtcdTxn.lean` `OpFull.getExact`, `client/v3/ServerKVGet.lean`): `getExact`
  loses its `keysOnly = false` conjunct, and `wire_fastKeysOnly` is deleted. Every result stated over
  `getExact` gets (the cache's, the recipes', `ServerKVTxn`'s) now holds for keys-only gets too.

## Findings

No bug in the PR's code was found. The tests are in `notes/pr-verify/etcd-22550/` (README there):

- `kvstore_fastkeysonly_lease_test.go` (`TestFastKeysOnlyLeaseRestore`): 20 random histories with
  leases, deletes and an optional compaction. At every uncompacted revision, the fast keys-only read
  equals the full read, on the live store and after a restart. It passes on the PR head and fails
  on the base (lease 0). This test covers the unverified restore path.
- `kvstore_review_lease_test.go` and `txn_review_lease_test.go` (the reviewer's) cover several cases,
  and all pass on the PR head:
  - sub-revisions in one write transaction, a key deleted and re-created with a new lease, reads at
    the compaction revision, and after a restart and a snapshot `Restore`;
  - `IgnoreLease` puts;
  - a put then a keys-only range in one txn.

  The txn test fails on the base. The mvcc test does not build there, because it measures `revisionLease`.
- The tests of `issues/etcd-range-keys-only-lease.md` (`range-keys-only-lease-tests.patch`) pass on the PR head, including the past-revision cases.
- **The issue the PR fixes**: the proof confirms the fix. The server-side difference that
  `issues/etcd-range-keys-only-lease.md` describes (`leaseZ`) is gone. The issue stays open on `lean`
  until a pin includes the fix.

Reviewer's open points, none a correctness bug in the code:
1. **Mixed versions**: unfixed members (released v3.7.x) omit leases while fixed members return them.
   This is why the PR's e2e `TestKVGet*/…LastVersion…--keys-only` cases fail on prow.
2. **Memory**: +8 bytes per indexed revision. There is no benchmark in the PR.
3. **`restoreTombstone`** gets a `leaseID` argument, `rkv.kv.Lease`, which is always 0 for a
   tombstone. Passing `lease.NoLease`, as `ki.tombstone` does, would say so.
4. **Nit**: `g.revs[l-i-1.]` in `generation.walk` has a stray `.` (an untyped float constant `1.`). It compiles, but should be `1`.

No bug was found in the existing code, so there is nothing new in `issues/`.
