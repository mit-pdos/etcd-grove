## Summary

PR `#22634` restores WAL replay support in `apply.Apply` (`server/etcdserver/apply/apply.go`, `server/etcdserver/apply/legacy_request.go`) for legacy v2 metadata `PUT` entries (`/0/version` and `/0/members/<hex>/attributes`) that were written by etcd ≤ 3.5 before commit `073d46a558de734e5e86ff2f84cd2f54f990f75d` removed `etcdserverpb.Request`. We translated the PR via Goose, defined pure wire-format and request-conversion models (`v2UnmarshalLoop`, `v2Decode`, `legacyClusterVersionIRR`, `legacyMemberAttrIRR`, `legacyToIRR`, `entryDecode`), extended `RestM` / `restOut` to track `clusterVersionSet` and `clusterMemberAttrSet`, and mechanically verified `requestV2.String`, `requestV2.Unmarshal`, `requestV2.toInternalRaftRequest`, `pbutil.MustUnmarshal`, `apply.Apply`, and `EtcdServer.applyEntryNormal` with zero `sorry`s.

During formal modeling and edge-case analysis, we found **three bugs** in the PR:
1. **Unanchored `memberAttributePathRegexp` (`legacy_request.go:32`) combined with `path.Dir(r.Path)` in `MustParseMemberIDFromKey` (`legacy_request.go:103`)**:
   - `memberAttributePathRegexp` is compiled from `path.Join(membership.StoreMembersPrefix, "[[:xdigit:]]{1,16}", "attributes")` without `^` or `$` anchors.
   - Disallowed v2 `PUT` paths with a prefix or suffix (e.g. `"/prefix/0/members/1a2b/attributes"` or `"/0/members/1a2b/attributes_extra"`) match `memberAttributePathRegexp` and have `path.Base(path.Dir(r.Path)) == "1a2b"`, so `toInternalRaftRequest` **silently accepts them and converts them into `ClusterMemberAttrSetRequest{Member_ID: 0x1a2b}`** instead of panicking with `"detected disallowed v2 WAL for stage --v2-deprecation=write-only"`.
   - Worse, a disallowed v2 `PUT` path with two trailing segments where the parent segment is hex (e.g. `"/0/members/1a2b/attributes/deadbeef/subkey"`) matches `memberAttributePathRegexp`, has `path.Base(path.Dir(r.Path)) == "deadbeef"`, and **mutates the wrong member ID (`0xdeadbeef` instead of `0x1a2b`)**.
   - A disallowed v2 `PUT` path with one trailing segment (e.g. `"/0/members/1a2b/attributes/extra"`) matches `memberAttributePathRegexp` and panics inside `MustParseMemberIDFromKey` (`strconv.ParseUint: parsing "attributes": invalid syntax`) instead of the expected `"detected disallowed v2 WAL"` panic.
2. **Protobuf wire-format overlap between `InternalRaftRequest` (`reserved 2; reserved "v2";`) and legacy v2 entries (`apply.go:31`)**:
   - `apply.Apply` only enters the legacy v2 fallback when `proto.Unmarshal(e.Data, &raftReq)` returns a non-nil error.
   - Because field 2 of `InternalRaftRequest` (`raft_internal.proto:40`) is `reserved 2;`, `proto.Unmarshal` silently skips tag 2 (`Method` in a bare v2 `Request`, or `V2` in an `InternalRaftRequest` that wrapped a v2 `Request` in field 2).
   - Consequently:
     - Any v2 `Request` wire encoding that omits field 5 (`Dir`) (such as the PR's own `legacyRequestBytes(id, method, "", "")` helper in `apply_test.go`, e.g. `legacyRequestBytes(42, "DELETE", "", "")`) succeeds in `proto.Unmarshal(e.Data, &raftReq)` with `err == nil` (`ID: 42`, `Range: &RangeRequest{}`, `Put: &PutRequest{}`, unknown field `2: "DELETE"`), bypassing the `if err != nil` legacy fallback and executing as a v3 request instead of panicking on the disallowed v2 method.
     - Any `InternalRaftRequest` that wrapped a v2 request in field 2 (`InternalRaftRequest{Header: &RequestHeader{ID: 77}, V2: &Request{...}}`, which etcd 3.6 handled via `if raftReq.V2 != nil`) succeeds in `proto.Unmarshal(e.Data, &raftReq)` with `err == nil` and drops field 2 as an unknown field, leaving `ClusterVersionSet == nil` and `ClusterMemberAttrSet == nil`.
3. **`wal.MinimalEtcdVersion` (`server/storage/wal/version.go:108`) was not updated alongside `apply.Apply`**:
   - Commit `073d46a558de734e5e86ff2f84cd2f54f990f75d` (`Remove the v2 Request message`) removed the v2 `Request` fallback in both `server/etcdserver/apply/apply.go` and `server/storage/wal/version.go` (`visitEntryData`).
   - PR `#22634` restores the fallback in `apply.go` but does not update `visitEntryData` in `server/storage/wal/version.go`, so `wal.MinimalEtcdVersion(ents)` / `wal.ReadWALVersion(w)` panics (`proto: cannot parse invalid wire-format data`) on a WAL containing the very legacy v2 `/0/version` or `/0/members/<id>/attributes` entries that PR `#22634` replays.

## Findings

### Finding 1: Unanchored `memberAttributePathRegexp` (`legacy_request.go:32`) accepts malformed paths and can parse the wrong `Member_ID`

In [`server/etcdserver/apply/legacy_request.go:32`](file:///root/etcd-pr/etcd-22634/server/etcdserver/apply/legacy_request.go#L32):
```go
var memberAttributePathRegexp = regexp.MustCompile(path.Join(membership.StoreMembersPrefix, "[[:xdigit:]]{1,16}", "attributes"))
```
Because `path.Join(membership.StoreMembersPrefix, "[[:xdigit:]]{1,16}", "attributes")` evaluates to `"/0/members/[[:xdigit:]]{1,16}/attributes"` **without `^` or `$` anchors**, `memberAttributePathRegexp.MatchString(r.Path)` returns `true` for any `r.Path` that merely contains `"/0/members/<1..16 hex chars>/attributes"` as a substring.

Then, at [`legacy_request.go:102-103`](file:///root/etcd-pr/etcd-22634/server/etcdserver/apply/legacy_request.go#L102-L103):
```go
if memberAttributePathRegexp.MatchString(r.Path) {
    id := membership.MustParseMemberIDFromKey(lg, path.Dir(r.Path))
```
where [`membership.MustParseMemberIDFromKey`](file:///root/etcd-pr/etcd-22634/server/etcdserver/api/membership/store.go#L51-L56) computes `types.IDFromString(path.Base(key))` (parsing the last path component of `path.Dir(r.Path)` as a base-16 `uint64`):
1. **Prefix or filename suffix (`1a` in [`repro_test.go`](etcd-22634/repro_test.go))**:
   - If `r.Path` has an arbitrary prefix (e.g. `"/prefix/0/members/1a2b/attributes"`) or a suffix on the final segment (e.g. `"/0/members/1a2b/attributes_extra"`), `memberAttributePathRegexp.MatchString(r.Path)` is `true`, and `path.Base(path.Dir(r.Path))` is still `"1a2b"`.
   - Instead of panicking with `"detected disallowed v2 WAL for stage --v2-deprecation=write-only"`, `toInternalRaftRequest` **silently accepts the disallowed path** and returns `ClusterMemberAttrSetRequest{Member_ID: 0x1a2b, ...}`.
2. **Two trailing segments with a hex parent (`1b` in [`repro_test.go`](etcd-22634/repro_test.go))**:
   - If `r.Path` has two trailing segments where the parent segment is hex (e.g. `"/0/members/1a2b/attributes/deadbeef/subkey"`), `memberAttributePathRegexp.MatchString(r.Path)` is `true`, and `path.Dir(r.Path)` is `"/0/members/1a2b/attributes/deadbeef"`, whose `path.Base` is `"deadbeef"`.
   - `MustParseMemberIDFromKey` **parses `0xdeadbeef` instead of `0x1a2b` as `Member_ID`**, silently mutating the wrong cluster member's attributes.
3. **Single trailing segment (`1c` in [`repro_test.go`](etcd-22634/repro_test.go))**:
   - If `r.Path` has one trailing segment (e.g. `"/0/members/1a2b/attributes/extra"`), `path.Base(path.Dir(r.Path))` is `"attributes"`, causing `MustParseMemberIDFromKey` to panic with `failed to parse member id from key: strconv.ParseUint: parsing "attributes": invalid syntax` instead of the expected `"detected disallowed v2 WAL for stage --v2-deprecation=write-only"` panic.

**Fix**: Anchor the regular expression at both ends:
```go
var memberAttributePathRegexp = regexp.MustCompile("^" + path.Join(membership.StoreMembersPrefix, "[[:xdigit:]]{1,16}", "attributes") + "$")
```

### Finding 2: Wire-format overlap with `InternalRaftRequest` (`reserved 2; reserved "v2";`) bypasses the `err != nil` legacy fallback

In [`server/etcdserver/apply/apply.go:31`](file:///root/etcd-pr/etcd-22634/server/etcdserver/apply/apply.go#L31):
```go
var raftReq pb.InternalRaftRequest
if err := proto.Unmarshal(e.Data, &raftReq); err != nil {
    var legacyReq requestV2
    pbutil.MustUnmarshal(&legacyReq, e.Data)
    raftReq = legacyReq.toInternalRaftRequest(lg)
}
```
In `etcdserverpb.InternalRaftRequest` (`api/etcdserverpb/raft_internal.proto:40`), field 2 was changed in commit `073d46a558de` from `Request v2 = 2;` to `reserved 2; reserved "v2";`. In protobuf wire decoding, **reserved field numbers are treated as unknown fields and silently skipped without error**.

Comparing the wire tags of a bare legacy v2 `Request` against `InternalRaftRequest`:
- Tag 1 (`VarintType`): `Request.ID` (`uint64`) $\leftrightarrow$ `InternalRaftRequest.ID` (`uint64`, same wire type!).
- Tag 2 (`BytesType`): `Request.Method` (`string`) $\leftrightarrow$ `reserved 2` in `InternalRaftRequest` (**silently skipped as an unknown field!**).
- Tag 3 (`BytesType`): `Request.Path` (`string`) $\leftrightarrow$ `InternalRaftRequest.Range` (`RangeRequest` submessage, same wire type!).
- Tag 4 (`BytesType`): `Request.Val` (`string`) $\leftrightarrow$ `InternalRaftRequest.Put` (`PutRequest` submessage, same wire type!).
- Tag 5 (`VarintType`): `Request.Dir` (`bool`) $\leftrightarrow$ `InternalRaftRequest.DeleteRange` (`DeleteRangeRequest` submessage, wire type mismatch: varint vs bytes).

This has two consequences (demonstrated in `TestFinding2_ProtoUnmarshalWireOverlapBypass` in [`repro_test.go`](etcd-22634/repro_test.go)):
1. **Bare v2 `Request` encodings without field 5 (`Dir`) (`2a` in [`repro_test.go`](etcd-22634/repro_test.go))**:
   - For a 3.5 `pbutil.MustMarshal(&etcdserverpb.Request{...})`, `gogoproto` always emits tag 5 (`Dir`, wire type 0 = varint), which collides with `InternalRaftRequest.DeleteRange` (tag 5, wire type 2 = bytes) and causes `proto.Unmarshal` to fail when `Path` and `Val` happen to be valid (or empty) submessage bytes.
   - However, when `Dir` is omitted (as in standard proto3 encoding or in the PR's own `legacyRequestBytes(id, method, p, val)` helper in `server/etcdserver/apply/apply_test.go`) and `p` and `val` are empty (e.g. `legacyRequestBytes(42, "DELETE", "", "")` or `legacyRequestBytes(42, "SYNC", "", "")`), `proto.Unmarshal(e.Data, &raftReq)` **returns `err == nil`** with `raftReq.ID = 42`, `raftReq.Range = &RangeRequest{}`, `raftReq.Put = &PutRequest{}`, and unknown field `2: "DELETE"`. `apply.Apply` never enters the `if err != nil` branch and instead dispatches a v3 `Range` request!
2. **`InternalRaftRequest` entries that wrapped a v2 `Request` in field 2 (`V2`) (`2b` in [`repro_test.go`](etcd-22634/repro_test.go))**:
   - In etcd 3.6 (before `073d46a558de`), `apply.Apply` handled both bare v2 `Request` entries (`if !pbutil.MaybeUnmarshal(&raftReq, e.Data)`) and `InternalRaftRequest` entries with field 2 (`V2`) populated (`if raftReq.V2 != nil`).
   - With `reserved 2;` in `InternalRaftRequest`, `proto.Unmarshal(e.Data, &raftReq)` on an `InternalRaftRequest{Header: &RequestHeader{ID: 77}, V2: &Request{...}}` **returns `err == nil`** and stores field 2 in `raftReq`'s unknown fields, leaving all v3 request pointers `nil` (which then panics in `uberApplier.dispatch` with `"not implemented apply"`).

### Finding 3: `wal.MinimalEtcdVersion` (`server/storage/wal/version.go:108`) still panics on legacy v2 WAL entries

Commit `073d46a558de734e5e86ff2f84cd2f54f990f75d` (`Remove the v2 Request message`) removed the v2 `Request` unmarshal fallback in **two** places:
1. `server/etcdserver/apply/apply.go` (`Apply`)
2. [`server/storage/wal/version.go:107-111`](file:///root/etcd-pr/etcd-22634/server/storage/wal/version.go#L107-L111) (`visitEntryData`):
   ```go
   func visitEntryData(data []byte, visitor entryVisitor) error {
       var raftReq etcdserverpb.InternalRaftRequest
       if err := proto.Unmarshal(data, &raftReq); err == nil {
           return visitSubMessages(raftReq.ProtoReflect(), visitor)
       } else {
           return err
       }
   }
   ```
   (Before `073d46a558de`, the `else` branch unmarshaled into `etcdserverpb.Request` via `pbutil.MaybeUnmarshal(&req, data)` and returned `nil`.)

PR `#22634` restores the legacy v2 fallback in `server/etcdserver/apply/apply.go`, but does not update `visitEntryData` in `server/storage/wal/version.go`. As demonstrated in `TestFinding3_WALMinimalEtcdVersionPanicsOnLegacyV2Entries` in [`repro_test.go`](etcd-22634/repro_test.go) ([`test.log`](etcd-22634/test.log)), calling `wal.MinimalEtcdVersion(ents)` (called by `wal.ReadWALVersion`) on a WAL containing a valid legacy v2 `/0/version` or `/0/members/<id>/attributes` entry causes `visitEntryData` to return `proto: cannot parse invalid wire-format data` and `MinimalEtcdVersion` to panic.
