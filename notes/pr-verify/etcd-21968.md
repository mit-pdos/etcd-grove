## Verdict

The change is sound as far as it is verified. `store.Compact` returns `nil` exactly when the requested
revision is already the compaction revision and is still the store's head. It still returns
`ErrCompacted` when a write has moved the head past the revision. This decision is made under `s.mu`
(exclusive) and `s.revMu`, so the head cannot move while it is taken. The state is untouched in both
cases. Releasing `s.mu` earlier is harmless, because the check after it reads only local values.

The PR does have a gap: it does not update the robustness tests' model. `tests/robustness/model`
still answers `ErrCompacted` to a repeated compaction at the head, so it rejects the server's new
answer. That can make a robustness run fail falsely (finding 1).

It is a user-visible API change (exported `KV.Compact` and the `Compact` RPC), and it has no CHANGELOG entry.

Not covered by the proof:
- The server's apply path above `store.Compact` (`applierV3backend.Compaction`, `EtcdServer.Compact`) is
  not verified. I checked it by reading the code, and the reviewer checked it too.
- The no-op's channel is specified only as the barrier's `compactChan ch True` (finding 2).

### `store.Compact`
File: `Spec/go_etcd_io/etcd/server/v3/storage/mvcc/store__Compact.lean`; the old spec is
`git show lean:<same path>`.

- **Old**: for `rev ≤ c` (`c` is the compaction right's revision), the result is `ErrCompacted`, the
  barrier's channel, and `Pre` back.
- **New**: the case `rev ≤ c` splits in two:
  - `err = nil`, `rev = c`, and the caller's certified log has length `rev + 1`. That is, the caller
    knows of no write after `rev`, and the head was `rev`. The barrier's channel and `Pre` come back.
  - `ErrCompacted`, with a certificate of a committed log longer than `rev + 1`: a write at a revision
    above `rev` had happened when `Compact` ran. The barrier's channel and `Pre` come back.
- The success and `ErrFutureRev` cases are unchanged.

The old spec does not hold of the new code, and the new spec does not hold of the old code: when
`rev = c = head`, the old code returns `ErrCompacted` (`kvstore_compact_latest_test.go` fails on the base).
So the new spec pins down exactly what the PR changes.

`idxCert` is only a lower bound on the committed log, so "the head was exactly `rev`" cannot be stated
directly. The statement above is the strongest form available. For the server's apply thread, the
only compactor and the only writer, it decides the outcome: the two cases contradict each other for a
caller that knows its log exactly.

### `store.updateCompactRev`
File: `Spec/.../mvcc/store__updateCompactRev.lean`.

The result is `(ch, prev, cur, err)`, where `cur` is `currentRev` read under `s.revMu`.

| Case | Before | Now |
|---|---|---|
| success | — | adds `rev ≤ cur` |
| `ErrCompacted` | `prev = 0` | `prev = c`, `c ≤ cur`, and a certificate `logh` with `cur = |logh| - 1` that extends the caller's certified log |
| `ErrFutureRev` | `prev = 0` | `prev = c`, and the existing certificate has length `cur + 1` |

The `ErrCompacted` facts come from the invariant `revMuInv`: `currentRev = |log| - 1` and `-1 ≤ c < |log|`
(`InvStore.lean`). They also use `idxLogAuth_cert_prefix`.

## Findings (step 8)

**Bugs in the PR's code: none found.** The reviewer's edge probes all pass on the PR head
(`notes/pr-verify/etcd-21968/kvstore_compact_noop_edges_test.go`, log `review-probe.log`):
- negative revisions and revision `0` on a fresh store;
- after a restore that raises `currentRev` to the compaction revision;
- a delete at the head.

**1. Medium: the robustness model is not updated** (`deterministic_compact_test.go`, `probe.log`).
- `tests/robustness/model/deterministic.go` `stepCompact` still answers `ErrCompacted` for
  `rev ≤ CompactRevision`. The model therefore rejects the server's new success answer to a second
  compaction at the head, and that history fails to linearize.
- The etcd traffic can produce this: `RunCompactLoop` (`tests/robustness/traffic/etcd.go:190`) draws `compactRev`
  from `[lastRev, head+5)`, which includes the last compacted revision. When no write lands between two
  ticks, it re-compacts the head. That case is rare, so expect a rare false failure, not a systematic one.
- The kubernetes traffic always writes before it compacts, so it cannot hit this.
- Fix: in `stepCompact`, answer success with the state unchanged when
  `rev == CompactRevision && rev == Revision`.

**2. Low, the spec's gap**: the no-op's channel is specified as `compactChan ch True`. The code does
better: the barrier job runs after the earlier compaction job on the FIFO scheduler, so once the
channel closes, that compaction is done (the reviewer's `TestProbeNoopBarrierAfterJob`).
- Before the PR this did not matter, since the caller got an error. Now `EtcdServer.Compact` with `Physical`
  reports success after waiting on it.
- Strengthening it to `compactDone s γ c` needs the barrier to take over the queue's last job's
  postcondition (`compactQueue`, `store.compactBarrier`'s spec), and that was not done. Open.

**3. Low**:
- no CHANGELOG entry;
- in the no-op the log field `previous-compact-revision` always equals `compact-revision`.

**Bugs in the existing code**: none found. Nothing was added to `issues/`, and no `issues/` entry concerns this function.

## Draft review comment (for the user to edit and post)

> The change looks right to me. The decision is taken with `s.mu` held exclusively and `currentRev`
> read under `revMu`, so no write can slip in between, and both outcomes leave the store untouched;
> moving `s.mu.Unlock()` up is fine since only locals are used afterwards. I also checked a restarted
> store (where `currentRev` is raised to the compaction revision), a delete at the head, and
> negative/zero revisions; all behave as described.
>
> One thing the PR misses: the robustness model in `tests/robustness/model/deterministic.go`
> (`stepCompact`) still returns `ErrCompacted` for `rev <= CompactRevision`, so it rejects the new
> success response. `RunCompactLoop` picks `compactRev` from `[lastRev, head+5)`, so whenever no write
> lands between two compaction ticks it can compact the head again, and the linearizability check
> would then fail spuriously. Could the model return success when `rev == CompactRevision &&
> rev == Revision`? A small model test along these lines fails on this branch:
> put at rev 2, compact(2) → ok, compact(2) → ok.
>
> Since this changes what clients see from `Compact`, it probably deserves a CHANGELOG line too.
