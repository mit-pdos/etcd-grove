# etcd-io/etcd#22211: concurrency: retain leader state in Resign when the delete transaction fails

- **PR**: https://github.com/etcd-io/etcd/pull/22211, head `02ea797798b275a281fa61b5b5dc6b7ea97a9207`
  (one commit, open), base `main` at `3602ea922`. It fixes etcd-io/etcd#22123: `Election.Resign`

## Verdict

**The PR fixes etcd-io/etcd#22123 as it says, but it adds a regression.** `Resign` is proved
against a new spec, with no `sorry`: on an error the election's state is unchanged, so `Resign`
can be retried. The spec's success and no-session cases are the same as before. The guarded
delete makes a retry safe: whether or not the first attempt was applied, a retry deletes only the
same incarnation of the key. `Campaign`, the only caller in the package, keeps its spec, and its
proof rebuilds unchanged.

**The regression** (found by the reviewer, reproduced by a test). When `Proclaim` finds the key
gone, it clears `leaderKey` but not `leaderSession`. With the PR, every later `Resign` then sends a
delete of the empty key, etcd rejects it ("key is not provided"), and the state is kept. So
`Resign` fails until the next successful `Campaign`. Before the PR, the first such `Resign` failed
and the second returned nil. `Campaign` can reach this state itself, when its key disappears
between its transaction and its `Proclaim`. A complete fix also clears `leaderSession` in
`Proclaim`'s not-leader branch, or has `Resign` treat an empty `leaderKey` as nothing to delete.

Not covered: the proof models the client's contract, not the server's rejection of the empty key.
So the spec allows the regression's behavior, and only the test shows it (see "Findings").

## The spec change

`Spec/go_etcd_io/etcd/client/v3/concurrency/Election__Resign.lean`, `Election.Resign.spec`:

- **Old** (`lean`): with a leader session, an error leaves `electionState e s ⟨[], st.rev, null,
  st.hdr⟩`: the key and session are cleared, the header is kept.
- **New**: an error leaves `electionState e s st`, the state unchanged. The no-session case (nil,
  unchanged) and the nil case (state `⟨[], st.rev, null, hdr⟩` with the transaction's header; for
  a key under the prefix, `notLeaderAt pfx st.key st.rev R` at the header's revision `R ≥ lo`) are
  textually the same.

Neither error postcondition implies the other: the fields hold different values. So the change is
incompatible, and the callers were checked (below). The new spec does not hold of the old code:
there, on the error path, `leaderSession` is `nil` while `st.sess ≠ null`. It pins down exactly
what the PR changes.

The proof (`Proof/go_etcd_io/etcd/client/v3/concurrency/Election__Resign.lean`) is the old one,
changed in two lines: each error branch now gives back the original state (`exact Hsess`).

```
│     translated) builds a fresh ResumeElection per request and discards it: unaffected.
└── etcdctl elect  (etcdctl/ctlv3/command/elect_command.go:136; not translated) calls
      Resign(context.TODO()) once at exit and returns its error: unaffected.
```

`Resign` is exported: its error behavior changes for users, which is the PR's point. The PR adds
no CHANGELOG entry.

Seen from users, `Campaign` behaves differently after a failed cleanup `Resign`. The election then
keeps `leaderKey`, `leaderRev` and `leaderSession`, though `Campaign` returned an error. `Key()`
returns the key, and `Resign` can retry the delete. That is the improvement: before, the key
stayed in etcd until the lease ended, with no handle to delete it. But `Proclaim` can now succeed
on a key that never became leader, since its guard checks only the key's create revision; before,
it returned `ErrElectionNotLeader`. `Campaign`'s spec hides this (`∃ st'`). This is a consequence
of the PR rather than a bug, worth a sentence in `Campaign`'s documentation.

## Findings

1. **A bug the PR introduces: `Resign` fails forever after `Proclaim` loses the key** (medium).
   Test: `notes/pr-verify/etcd-22211/election_resign_lost_proclaim_test.go`. It passes at
   `09669450f` and fails at the PR head `02ea79779` and on `pr-etcd-22211-goose-lean`; logs in
   `lost_proclaim.{pinned,prhead}.log`. The sequence:
   - campaign;
   - delete the key from another client;
   - `Proclaim` returns `ErrElectionNotLeader`, `Key()` is `""`;
   - three `Resign`s all return "etcdserver: key is not provided" (before the PR: an error, then
     nil, nil).

   A later `Proclaim` returns the same server error instead of `ErrElectionNotLeader`. `Campaign`
   can produce the same state itself: its key is deleted, or its lease expires, between its
   transaction (which found an existing key with another value) and its `Proclaim`, and its cleanup
   `Resign(ctx)` hits the empty key. Fixes: in `Proclaim`'s `!tresp.Succeeded` branch also set
   `e.leaderSession = nil`, or in `Resign` treat `e.leaderKey == ""` as nothing to delete (clear
   the session, return nil).
2. **The bug the PR fixes is now in `issues/`**:
   `issues/etcd-election-resign-forgets-on-error.md` (upstream `known`: #22123, #22211, #22124).
   The `lean` spec stated the old behavior without flagging it. The PR's test, renamed
   (`notes/pr-verify/etcd-22211/election_resign_retry_test.go`), fails at `09669450f`
   (`pinned-09669450f.log`) and passes with the PR (`fork-pr.log`). **The proof confirms the fix:**
   an error leaves the state unchanged, and a retry from that state is again covered by the spec.
3. **Spec weakness (this repository; reviewer's F2).** With `st.key = []` and a session set, the
   new spec allows a nil result, through its `¬ pfx <+: st.key` disjunct. That is sound, since the
   client contract does not model the server's empty-key rejection. But it means the proof cannot
   tell finding 1 from correct behavior. Possible tightenings: an `electionState` invariant
   "session set ⇒ key under the prefix" (`Proclaim` breaks it today), or an empty-key error in the
   transaction contract. Neither is done here.
4. **Retry safety (reviewer's F5): no bug.** Suppose the first delete was applied but reported as
   an error. The retry's guard fails, because the key is gone or was re-created with a new create
   revision. The retry returns nil, clears the state, and gives `notLeaderAt` at `R ≥ lo`. Two
   `Election`s on one session and prefix share the key `pfx/<lease>`. If one's failed `Resign` was
   not applied and the other then campaigned over the same key (same create revision), the stale
   handle's retry deletes the other's key. That comes from the shared key, which predates the PR
   (`issues/election-campaign-key-check.md` discusses the shared key).
