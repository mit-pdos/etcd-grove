## Verdict

The change is correct for what it says. Assuming a role's permissions are sorted by key (every
writer keeps them that way, and the proof shows `RoleGrantPermission` does too), the PR's scan from
the binary-search position finds the first permission with the request's key *and* range end
whenever the role has one. It updates that permission's type, or appends and sorts when there is
none. The proof covers the whole function (no `sorry`), and a lemma shows that when the role had no
two permissions on one range, the role afterwards holds exactly its old permissions on other ranges
plus the granted one. So a grant creates no duplicate and a downgrade takes effect. The old code
fails this spec (Go test).

What it does not cover:
1. **Duplicates already stored are not repaired**: a role written by an etcd without the fix can
   already hold two permissions on one range. The PR updates only the first, so a downgrade can
   still leave a stale `WRITE` in place (finding F1, reproduced on the PR head).
2. The backend's batch transaction, `commitRevision`, `refreshRangePermCache` and
   `isValidPermissionRange` are contracts or postulates, not proofs.
3. The apply package's call through the `AuthStore` interface is checked against its own contract
   (`authReqContract`), which this result does not discharge (unchanged by the PR).

## The spec (behavior change)

- **Old**: none. Informally, the old code updates the permission only if the *first* permission
  with the request's key also has its range end, and otherwise appends.
- **New** (`Spec/go_etcd_io/etcd/server/v3/auth/authStore__RoleGrantPermission.lean`, the pure
  part `GrantSpec` in `Proof/go_etcd_io/etcd/server/v3/auth/RolePerms.lean`):
  - Premises: the backend's roles `m` (the caller's abstract `Roles m`) are all sorted by key, and
    the role has fewer than `2^62` permissions (`sort.Sort`'s bound).
  - Success (`err = nil`): the request had a permission, the role existed, and its new
    permissions `ps'` satisfy `GrantSpec ps ps' p`. Either the first permission on `p`'s key and
    range end becomes `p` and nothing else changes, or, if there is none, `ps'` is a permutation of
    `ps ++ [p]` sorted by key.
  - Error: the roles are unchanged. A missing role is an error.
  - Always: all roles stay sorted.
- Consequences (`RolePerms.lean`): `grantSpec_sorted` (sortedness kept); `grantSpec_nodup` (no two
  permissions on one range stays true); `grantSpec_mem` (with no duplicates: `q ∈ ps' ↔ (q ∈ ps ∧ q
  not on p's range) ∨ q = p`, the "set the permission on the range" meaning).
- The old code fails `GrantSpec`: with `[W foo..fop, W foo..foq]`, granting `R foo..foq` appends
  (`notes/pr-verify/etcd-21845/store_grant_downgrade_test.go`, failing at `09669450f`).

## Findings

- **F1 (the PR, not a bug it introduces): duplicates already stored are not repaired.** Before the
  fix, a role can end up with two permissions on one range. For example, write `[foo, fop)`, read
  `[foo, foq)`, then write `[foo, foq)` (an upgrade) gives `[W fop, R foq, W foq]`. With the PR,
  downgrading `[foo, foq)` to read updates only the first permission on the range (already read).
  The stale write stays, so the user can still write `fop`. Test:
  `notes/pr-verify/etcd-21845/store_grant_existing_duplicate_test.go`, failing on the PR head and
  the fork branch (`pr-head.log`). The spec records it: `GrantSpec` updates the first match, and
  `grantSpec_mem` needs `NoDupRanges`. Fix: update every permission on the range, or drop the later
  duplicates, in the same loop. Workaround today: revoke the range (removes all), then grant.
- **The bug the PR fixes, in the pinned code**: recorded as
  `issues/etcd-auth-grant-permission-same-key.md` (a downgrade has no effect; test
  `store_grant_downgrade_test.go`, failing at `09669450f`, `downgrade-base.log`). The proof
  confirms the fix for roles without duplicates.

## Review (a fresh reviewer subagent)

No soundness problem found; nothing vacuous (premises satisfiable, contracts are hypotheses tying
`UnsafeGetRole`/`UnsafePutRole` to `m name`/`rolesSet`). Points, all recorded:
- F1 confirmed fair (low to medium: not a regression; needs pre-fix data; revoke + grant repairs).
  Added to the spec's doc comment.
- **Scope**: the PR's claim ("a downgrade takes effect") is about permission checks; the spec stops at
  the stored role, since `refreshRangePermCache` is postulated without a cache spec. Linking would
  need a spec of the cache rebuild and `NoDupRanges` as an invariant (`grantSpec_nodup` keeps it).
  Open.
- The exclusive ownership of `Roles m` is justified: every role writer (`RoleAdd`,
  `RoleGrantPermission`, `RoleRevokePermission`, `RoleDelete`, `Recover` from `applySnapshot`)
  runs on the apply goroutine; the batch commits do not change data. `Recover` rewrites `as.be`,
  which `authWriteInv` treats as read-only (as `InvAuth.lean` already does): sound per call.
- `SortedByKey` holds of etcd's own writes since v3.0 (grant sorts with the same key-only order;
  revoke filters in order; restore copies); a hand-edited, unsorted role defeats the scan (probe D),
  so the premise is needed.
- The three axioms are true of the real code (pure check; atomic add plus a save to the auth
  bucket; the cache rebuild under its own lock).
- Smaller: `isValidPermissionRange`'s result is unconstrained (the spec does not say invalid ranges
  are rejected); `PermType` is unvalidated (pre-existing, modelled faithfully); nothing about `resp`;
  two spellings of one range (`[a]` and `[a, "a\x00")`) are distinct, so a downgrade through the
  other spelling keeps write (pre-existing, probe C; the spec's textual `sameRange` models it).
- Probes: `notes/pr-verify/etcd-21845/store_grant_reviewer_test.go` (`reviewer-pr-head.log`); the
  random-vs-model test (3000 steps, up to 46 permissions) found no sort-instability effect.

> permission with `r.Perm.Key` is in the run starting at `idx`, so the loop finds the matching
