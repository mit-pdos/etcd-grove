## 1. Summary of the Change

When a surviving etcd node restarts with `--force-new-cluster` (`cfg.ForceNewCluster == true`) after an abrupt crash where the bbolt backend's `consistent_index` (`ci.ConsistentIndex()`) is ahead of the last entry persisted in the WAL (`lastIndex`), `bootstrapWALFromSnapshot` (`server/etcdserver/bootstrap.go`) previously executed:

1. `bwal.st.Commit = new(max(oldCommitIndex, consistentIndex))`
2. `bwal.ents = bwal.CommitedEntries()`
3. `entries := bwal.NewConfigChangeEntries()` — which calls `serverstorage.CreateConfigChangeEnts(..., bwal.st.GetTerm(), bwal.st.GetCommit())`, numbering the synthetic `EntryConfChange` entries starting at `bwal.st.GetCommit() + 1` (`consistentIndex + 1`).
4. `bwal.AppendAndCommitEntries(entries)` — which appended `entries` directly after `bwal.ents` (ending at `lastIndex < consistentIndex`), persisted `entries` to the WAL on disk (`wal.w.Save(&raftpb.HardState{}, entries)`), and set `bwal.st.Commit = bwal.ents[len(bwal.ents)-1].Index`.

When `consistentIndex > lastIndex`, this created an index gap `(lastIndex, consistentIndex]` between the existing WAL entries and the newly appended `EntryConfChange` entries, causing two cascading failures (`etcd-io/etcd#22646`):

- **First boot (`--force-new-cluster`)**: `bwal.MemoryStorage()` appends `bwal.ents` into a `raft.MemoryStorage`. Because `MemoryStorage.lastIndex()` is computed by position (`ms.ents[0].GetIndex() + uint64(len(ms.ents)) - 1`), `ms.LastIndex()` is smaller than `bwal.st.GetCommit()` by `consistentIndex - lastIndex`, causing `raft.RestartNode` (`raft.loadState`) to panic with `state.commit <N> is out of range [<first>, <last>]`.
- **Every subsequent boot (with or without `--force-new-cluster`)**: Because `AppendAndCommitEntries` already wrote the gapped `EntryConfChange` entries to the WAL on disk before `MemoryStorage()` ran, `wal.ReadAll()` fails fatally with `wal: slice bounds out of range` (`wal.ErrSliceOutOfRange`), permanently bricking the data directory.

PR `etcd-io/etcd#22655` adds `(*bootstrappedWAL).fillBackendAheadGap()` and calls it between `bwal.ents = bwal.CommitedEntries()` and `entries := bwal.NewConfigChangeEntries()`:

```go
func (wal *bootstrappedWAL) fillBackendAheadGap() {
	var lastIndex uint64
	if len(wal.ents) > 0 {
		lastIndex = wal.ents[len(wal.ents)-1].GetIndex()
	} else {
		lastIndex = wal.snapshot.GetMetadata().GetIndex()
	}
	commit := wal.st.GetCommit()
	if commit <= lastIndex {
		return
	}
...
	var gapEnts []*raftpb.Entry
	for idx := lastIndex + 1; idx <= commit; idx++ {
		gapEnts = append(gapEnts, &raftpb.Entry{
			Type:  raftpb.EntryNormal.Enum(),
			Term:  new(wal.st.GetTerm()),
			Index: new(idx),
		})
	}
	wal.AppendAndCommitEntries(gapEnts)
}
```

## 3. Findings and Architectural Caveats

While `fillBackendAheadGap()` is verified to restore `PlogWf (snapId sv) esFinal` and prevent the `raft.loadState` panic and `wal: slice bounds out of range` corruption in `etcd-io/etcd#22646`, the formalization and code inspection identified three notable edge cases/caveats:

1. **Loop bound `commit < math.MaxUint64` (`uint.Z hs.Commit' + 1 < 2 ^ 64`)**:
   - In `fillBackendAheadGap`, the loop `for idx := lastIndex + 1; idx <= commit; idx++` increments `idx` in 64-bit unsigned arithmetic before checking `idx <= commit`. If `commit == math.MaxUint64`, `idx++` wraps around to `0` and loops forever. Our specification records this explicitly as `uint.Z hs.Commit' + 1 < 2 ^ 64` (never reached in practice by Raft log indices, which are bounded below `2 ^ 61`).
2. **Membership changes inside the backend-ahead gap (`bootstrap.go:89` vs `bootstrap.go:112-115`)**:
   - In `bootstrap(cfg)` (`server/etcdserver/bootstrap.go`), `bootstrapWALFromSnapshot` runs at line 89 *before* `cs := buildConfStateFromV3store(cfg.Logger, backend.be); sn.Metadata.ConfState = &cs` runs at lines 112-115.
   - If a membership change (e.g., `ConfChangeAddNode` adding a voter `M`) was committed and applied to the backend at an index inside the missing WAL gap `(lastIndex, consistentIndex]`, `fillBackendAheadGap()` replaces that gap with empty `EntryNormal` entries.
   - Consequently, `bwal.NewConfigChangeEntries()` (which calls `serverstorage.GetEffectiveNodeIDsFromWALEntries(wal.lg, wal.snapshot, wal.ents)`) only sees the pre-gap `wal.snapshot.Metadata.ConfState` and `wal.ents`, and does **not** emit a `ConfChangeRemoveNode(M)`.
   - Immediately afterward at lines 112-115, `bootstrap()` overwrites `s.wal.snapshot.Metadata.ConfState` with `buildConfStateFromV3store(cfg.Logger, backend.be)` (which *does* include `M` from the backend's `members` bucket). When `bwal.MemoryStorage()` then applies `s.wal.snapshot` and appends `s.wal.ents`, `M` remains in Raft's voter set because no `ConfChangeRemoveNode(M)` was generated for it (`TestProbeMembershipChangeInBackendAheadGap` in [`notes/pr-verify/etcd-22655/bootstrap_pr22655_probe_test.go`](./etcd-22655/bootstrap_pr22655_probe_test.go)).
3. **`AppendAndCommitEntries` does not persist the updated `HardState.Commit` to disk (`bootstrap.go:793-801`)**:
   - Pre-existing behavior in `AppendAndCommitEntries`: `wal.w.Save(&raftpb.HardState{}, ents)` passes an empty `HardState` (which `wal.Save` skips writing because `raft.IsEmptyHardState` is true) and only updates `wal.st.Commit` in memory. As shown in `TestBootstrapWALFromSnapshotBackendAheadOfWAL` ([`notes/pr-verify/etcd-22655/probe-test.log`](./etcd-22655/probe-test.log)), in-memory `bwal.st.GetCommit()` is `51` while on-disk `st2.GetCommit()` read back via `w2.ReadAll()` remains `28` until Raft later persists a new `HardState`.
