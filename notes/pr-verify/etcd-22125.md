## Verdict

The `maintenance.go` change is a real fix, but only a partial one. Before the PR, a backend snapshot
whose `WriteTo` stops short makes `Snapshot`'s send loop spin, sending empty messages, until the client
goes away. With the PR, the loop now ends with the error when `WriteTo` fails with a non-EOF error,
such as a disk read error. It still spins when `WriteTo` stops short with `io.EOF`. bbolt's `Tx.WriteTo`
does exactly that when the database file is shorter than the transaction's size: its `io.CopyN`
returns `io.EOF`.

The `register.go` change is harmless, but it fixes no leak. An expired `concurrency.Session` has
already cancelled its context and its goroutine has already exited. A 20-expiry integration probe shows
the goroutine count flat both before and after the PR. The added `ss.Close()` only revokes the old lease.

What was verified is a pure model of the send loop and when it terminates, proved in Lean. It rests on
no axioms. No Hoare triple of `Snapshot` was attempted: termination is a liveness property, and a
partial-correctness spec holds of the loop both before and after the PR. `Register` was checked by
code reading and a Go test only, not in Lean.

### `Snapshot`: old and new behavior

- **Old**: the writer goroutine runs `snap.WriteTo(pw)` and drops its error, then calls `snap.Close()`
  and `pw.Close()`. The reader loop ignores `io.EOF` and `io.ErrUnexpectedEOF` and runs while
  `total-sent > 0`. A short write therefore leaves the loop reading `(0, io.EOF)` forever
  (`snapshot_old_hangs`).
- **New (PR)**: if `WriteTo` returns `err != nil`, the goroutine calls `pw.CloseWithError(err)`;
  otherwise it calls `pw.Close()`. Then it calls `snap.Close()`, which used to run before the pipe
  was closed. The loop now returns the write's error, unless that error is EOF-like
  (`snapshot_new_terminates`, `snapshot_new_hangs_on_eof`).
- The Lean statements are in `Proof/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/SnapshotLoop.lean`,
  restated as `snapshot_*` in `.../v3rpc/Results.lean`. The model takes a few inputs:
  - the bytes written and whether the close's error is EOF-like;
  - `io.ReadFull` over `io.Pipe`, which depends only on the writer's final state, since reads block
    until data or close;
  - `WriteTo`'s contract: at most `total` bytes, and `nil` exactly when it wrote all of them. This is
    bbolt's contract through `io.CopyN`. It holds for etcd, which never sets `WriteFlag`; with
    `WriteFlag`, an `f.Close` error could follow a complete write.
  - `srv.Send` assumed to succeed. So "runs forever" means "while the client keeps receiving".

  The reviewer checked the model against `io.ReadAtLeast`, the `io.Pipe` semantics and the loop. It
  also checked the edge cases: `B` is the constant 32 KiB, `total = 0`, int64 vs Nat, and no overshoot
  of `total` under the contract.

## Findings

1. **The PR leaves the `io.EOF` case looping.** Evidence: `TestSnapshotWriteToEOFReturns`, which fails
   at both the base and the PR head, and `snapshot_new_hangs_on_eof`. The case is reachable from the
   real backend: `TestBoltWriteToShortFileReturnsEOF` gets bbolt v1.5.0's `Tx.WriteTo` to return
   `io.EOF` after 12288 of 233472 bytes on a truncated file. A file that short takes external
   truncation or corruption; defrag cannot cause it. `CloseWithError(io.EOF)` looks to the reader
   exactly like a normal end. The suggested fix is a loop that fails on a read of no bytes
   (`guarded-loop.patch`):
   - proved to terminate for every writer: `snapshot_guarded_terminates`;
   - all three tests and the package's tests pass with it.
2. **The goroutine leak `register.go` claims to fix does not occur.** `ss.Done()` is the session
   goroutine's own `donec`. It closes only after that goroutine has called `cancel()` and exited. The
   client's lessor also drops the lease from its keepalives on every path that closes the channel.
   The probe `TestRegisterSessionExpiryNoGoroutineLeak` shows the same result before and after the
   PR: 39 goroutines after 3 and after 20 expiries, and 1 lease alive.
   - In the old code an orphaned server-side lease just expires, and the endpoint key, re-`Put`
     with the new lease, survives.
   - Where the client gave up but the server-side lease is still alive (a partition, where the
     client-side keepalive deadline fired), the new `ss.Close()` has two effects (reasoned by the
     reviewer, not tested). Its `Revoke` blocks up to `ttl` seconds. Once it succeeds, it deletes the
     endpoint key, which is still attached to the old lease. Endpoint watchers then see the proxy
     disappear until the next registration, at least one rate-limiter tick later.
   - So the change trades a lingering lease, which would expire soon anyway, for a brief delete/put
     flap of the endpoint.
3. **Smaller points about the PR** (confirmed by the reviewer):
   - The pipe is now closed before `snap.Close()`, so the RPC can return before the read transaction
     rolls back. That was already possible when `total` is a multiple of 32 KiB, and nothing depends
     on the order. Calling `snap.Close()` first and then `pw.CloseWithError(err)` keeps the old order
     with less code, since `CloseWithError(nil)` is `Close()`.
   - "failed to send snapshot" is now logged at Warn on every client-aborted snapshot: `WriteTo` fails
     with `io.ErrClosedPipe` once the reader has gone. It is log noise.
4. **Existing code** (pinned fork `09669450f`, which has the old `Snapshot`): recorded as
   `issues/etcd-snapshot-short-write-busy-loop.md`, with `upstream: known` (this PR).
5. **Reviewer**: a fresh subagent reviewed the model, the tests and the PR. It had no open
   disagreements; its two caveats (the "until the client disconnects" wording, the endpoint flap) are
   folded in above. It wrote no tests of its own.

## Draft review comment (for the user to edit and post)

> Thanks, the maintenance.go change fixes a real hang: when `snap.WriteTo` fails partway, the old code
> closes the pipe normally, every following `io.ReadFull` returns `(0, io.EOF)`, which the loop
> ignores, and the handler keeps sending empty `SnapshotResponse`s until the client goes away.
>
> One case is still open: if `WriteTo` stops short and returns `io.EOF` itself, `pw.CloseWithError(io.EOF)`
> looks to the reader exactly like a normal close, and the loop spins as before. bbolt's `Tx.WriteTo`
> does this when the db file is shorter than `tx.Size()` (its `io.CopyN` returns `io.EOF`). A unit
> test with a fake `backend.Snapshot` whose `WriteTo` writes 4 KiB of 96 KiB and returns `io.EOF`
> times out with this PR. Failing the loop when a read returns no data covers every case:
>
> ```go
> n, err := io.ReadFull(pr, buf)
> if err != nil && !errorspkg.Is(err, io.EOF) && !errorspkg.Is(err, io.ErrUnexpectedEOF) {
>     return togRPCError(err)
> }
> if n == 0 {
>     return togRPCError(fmt.Errorf("snapshot ended after %d of %d bytes: %w", sent, total, io.ErrUnexpectedEOF))
> }
> ```
>
> Small thing: `_, err := snap.WriteTo(pw)`, then `snap.Close()`, then `pw.CloseWithError(err)` keeps the
> old order (the RPC finishes after the read transaction is closed), since `CloseWithError(nil)` is `Close()`.
>
> About register.go: I don't think there is a leak to fix. `ss.Done()` is closed by the session's own
> goroutine after it calls `cancel()` and returns, and the lessor drops the lease from its keepalives
> when it closes the channel. In an integration test that expires the session 20 times by revoking its
> lease, the goroutine count stays flat with and without the change. The added `ss.Close()` revokes the
> old lease, which can block up to `ttl` seconds during a partition, and if that lease is still alive
> on the server it deletes the endpoint key until the next registration puts it back. Could you say what
> you observed that pointed to a leak? Otherwise I'd suggest dropping this part, or describing it as
> revoking the stale lease.
