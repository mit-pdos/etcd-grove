## 2. Detailed Findings & Formal Witnesses

### Finding 1 (HIGH): `SetEndpoints` in `newClient` Executes 0 Loop Iterations and Never Updates `c.resolver`

#### Root Cause in Go Code
In `client/v3/client.go:195–203`, PR `#21765` replaces the direct `c.resolver.SetEndpoints(eps)` call in `(*Client).SetEndpoints` with a loop over `c.channels`:
```go
func (c *Client) SetEndpoints(eps ...string) {
	c.epMu.Lock()
	defer c.epMu.Unlock()
	c.endpoints = eps

	for _, ch := range c.channels {
		ch.resolver.SetEndpoints(eps)
	}
}
```
However, look at the initialization order in `newClient` (`client/v3/client.go:415, 456, 471, 483`):
1. Line 415: `client.channels = make(map[string]channel)` (initialized to an **empty map** `∅`).
2. Line 456: `client.resolver, err = resolver.New(cfg.Endpoints...)`.
3. Line 471: `client.SetEndpoints(cfg.Endpoints...)` is called **while `client.channels` is still empty (`len(client.channels) == 0`)**!
4. Line 483: `client.channels[defaultChannelKey] = channel{conn: conn, resolver: client.resolver}` is populated **after** `SetEndpoints` and `dialWithBalancer` have already run.

Because `client.channels` is empty at line 471, the `for _, ch := range c.channels` loop inside `client.SetEndpoints(cfg.Endpoints...)` executes **0 iterations** and does **not** call `client.resolver.SetEndpoints(eps)`. (In `newClient`, `resolver.New(cfg.Endpoints...)` happened to seed `client.resolver` at line 456, making the resolver update in `SetEndpoints` at line 471 dead code; furthermore, any caller that invokes `SetEndpoints` before `c.channels` is populated only mutates `c.endpoints` while leaving `c.resolver` stale.)

#### Formal Witness in Lean
In [`Spec/go_etcd_io/etcd/client/v3/Client__SetEndpoints.lean`](../../Spec/go_etcd_io/etcd/client/v3/Client__SetEndpoints.lean) and [`Proof/go_etcd_io/etcd/client/v3/Client__SetEndpoints.lean`](../../Proof/go_etcd_io/etcd/client/v3/Client__SetEndpoints.lean):
- `Client.SetEndpoints.spec` (when `mref ↦$ (∅ : GMap GoString clientv3.channel.t)`) requires **no `etcdResolverOwn` resource at all** in its precondition or postcondition!
- In `Client.SetEndpoints.wp_proof` (lines 38–48), the `map.forRange` loop body is proved unreachable via `exfalso; simp at Hvv` because `∅ !! key = none`.
- Conversely, `Client.SetEndpoints_singleton.spec` (when `mref ↦$ {[k₀ := channel.mk conn r]}`) proves that `etcdResolverOwn r eps0` is updated to `etcdResolverOwn r eps` only when the channel entry is already present in `c.channels`.

#### Reproduction
Reproduced by `TestVerify_Finding1_SetEndpointsEmptyChannelsInNewClient` in [`notes/pr-verify/etcd-21765/channel_pool_verify_test.go`](etcd-21765/channel_pool_verify_test.go).

### Finding 2 (HIGH): `RetryKVClient` Breaks `NewCtxClient` / Direct `c.conn` Clients, Panics on `c.epMu == nil`, and Acquires `c.epMu.RLock()` on Every KV RPC

#### Root Cause in Go Code
In `client/v3/retry.go:100–104`, PR `#21765` changes `RetryKVClient`:
```go
func RetryKVClient(c *Client) pb.KVClient {
	return &retryKVClient{
		kc: pb.NewKVClient(&routingClientConn{client: c}),
	}
}
```
And `(*routingClientConn).Invoke` / `NewStream` (`client/v3/channel_pool.go:90–108`) call `c.connectionForContext(ctx)` on every unary RPC and stream:
```go
func (c *Client) connectionForContext(ctx context.Context) (*grpc.ClientConn, error) {
	key, err := channelKeyForRequest(ctx)
	if err != nil {
		return nil, err
	}
	c.epMu.RLock()
	ch, ok := c.channels[key]
	channelsNil := c.channels == nil
	c.epMu.RUnlock()
	if channelsNil {
		return nil, c.connectionPoolClosedError()
	}
	if !ok || ch.conn == nil {
		return nil, fmt.Errorf("%w: %q", ErrChannelKeyNotFound, key)
	}
	return ch.conn, nil
}
```
This has three consequences:
1. **Nil-pointer panic when `c.epMu == nil`**: Any test or caller constructing `&Client{conn: conn}` without `epMu: new(sync.RWMutex)` now panics with a nil-pointer dereference at `c.epMu.RLock()` on the first KV RPC (`TestVerify_Finding2a_RetryKVClientNilEpMuPanic`).
2. **`NewCtxClient` + `c.conn` broken**: `NewCtxClient(ctx)` initializes `epMu: new(sync.RWMutex)` but leaves `c.channels == nil`. Previously, setting `c.conn = conn; c.KV = NewKV(c)` worked because `RetryKVClient(c)` used `c.conn`. Now `c.channels == nil` causes every KV RPC to fail with `c.connectionPoolClosedError()` instead of falling back to `c.conn` when `key == defaultChannelKey` (`TestVerify_Finding2b_NewCtxClientDirectConnBroken`).
3. **Per-RPC `RWMutex` contention and reader-slot requirement**: Every KV RPC (`Put`, `Get`/`Range`, `DeleteRange`, `Txn`) now acquires and releases `c.epMu.RLock()` on the hot path, adding shared cache-line contention on `c.epMu` across all concurrent KV goroutines and requiring a `sync.RWMutex` reader slot (`ownRWMutex`) in the formal precondition of every KV RPC.

#### Formal Witness in Lean
- [`Proof/go_etcd_io/etcd/client/v3/InvKVConn.lean`](../../Proof/go_etcd_io/etcd/client/v3/InvKVConn.lean) defines `clientPoolInv` and `kvRoutingStubAt`, which require `c.epMu ↦□ mu`, `ownRWMutex (1/2) mu (clientPoolInv c mref chs)`, and `poolConnFor chs o ≠ null`.
- [`Spec/go_etcd_io/etcd/client/v3/routingClientConn__Invoke.lean`](../../Spec/go_etcd_io/etcd/client/v3/routingClientConn__Invoke.lean) and [`Spec/go_etcd_io/etcd/api/v3/etcdserverpb/kVClient__Put.lean`](../../Spec/go_etcd_io/etcd/api/v3/etcdserverpb/kVClient__Put.lean) (`kVClient.Put_routing.wp_proof`) formally thread the `ownRWMutex` reader permission through `(*kVClient).Put` -> `(*routingClientConn).Invoke` -> `(*Client).connectionForContext` -> `(*grpc.ClientConn).Invoke`.

### Finding 3 (MEDIUM/HIGH): `connectionPoolClosedError()` Fallback Branch Is Dead Code After `Client.Close()`, and Post-`Close()` RPCs Regress from `codes.Canceled` to `codes.Unknown`

#### Root Cause in Go Code
In `client/v3/channel_pool.go:83–88`:
```go
func (c *Client) connectionPoolClosedError() error {
	if err := c.ctx.Err(); err != nil {
		return err
	}
	return status.Error(codes.Canceled, "etcdclient: client connection is closing")
}
```
And in `client/v3/client.go:151–163`:
```go
func (c *Client) Close() error {
	c.cancel()
	...
	c.epMu.Lock()
	channels := c.channels
	c.channels = nil
	c.epMu.Unlock()
```
Because `c.Close()` calls `c.cancel()` **before** setting `c.channels = nil`:
1. Whenever `c.channels == nil` as a result of `c.Close()`, `c.ctx.Err()` is **already non-nil (`context.Canceled`)**. Therefore, the `return status.Error(codes.Canceled, "etcdclient: client connection is closing")` branch in `connectionPoolClosedError()` is **dead code** for closed clients!
2. Worse, before this PR, calling `c.Get(context.Background(), "k")` after `c.Close()` (with an uncanceled request context `reqCtx`) hit the closed `grpc.ClientConn`, which returned a gRPC status error with `status.Code(err) == codes.Canceled`. With this PR, `connectionForContext` intercepts the call and returns `c.connectionPoolClosedError()`, which returns raw `context.Canceled` (`*errors.errorString`), for which `status.Code(err) == codes.Unknown`! Any caller checking `status.Code(err) == codes.Canceled` (or `rpctypes.Error`) after `c.Close()` experiences an error-classification regression.

#### Formal Witness in Lean
In [`Spec/go_etcd_io/etcd/client/v3/Client__connectionPoolClosedError.lean`](../../Spec/go_etcd_io/etcd/client/v3/Client__connectionPoolClosedError.lean) and [`Proof/go_etcd_io/etcd/client/v3/Client__connectionPoolClosedError.lean`](../../Proof/go_etcd_io/etcd/client/v3/Client__connectionPoolClosedError.lean):
- When `st = .Done` (the state of `c.ctx` after `c.cancel()` in `Close()`), `Client.connectionPoolClosedError.wp_proof` takes the `if err != nil` branch and returns `c.ctx.Err()` (`st.err`) directly without ever reaching `status.Error(codes.Canceled, ...)`.
- `Client.connectionPoolClosedError.wp_proof` reaches `status.Error(codes.Canceled, ...)` **only** when `st = .Active` (i.e., `c.channels == nil` on an uninitialized client whose `c.ctx` has not been canceled).

#### Reproduction
Reproduced by `TestVerify_Finding3_ClosedClientErrorTypeRegressionAndDeadCode` in [`notes/pr-verify/etcd-21765/channel_pool_verify_test.go`](etcd-21765/channel_pool_verify_test.go).

### Finding 4 (MEDIUM): Non-Idempotent `Client.Close()` and `errors.Join` Error Masking in `IsConnCanceled`

#### Root Cause in Go Code
In `client/v3/client.go:151–177`:
```go
	c.epMu.Lock()
	channels := c.channels
	c.channels = nil
	c.epMu.Unlock()
	for _, ch := range channels {
		if ch.resolver != nil {
			ch.resolver.Close()
		}
		if ch.conn != nil {
			if err := ch.conn.Close(); err != nil && !IsConnCanceled(err) {
				errs = append(errs, err)
			}
		}
	}
	if len(errs) > 0 {
		return errors.Join(errs...)
	}
	if len(channels) > 0 {
		return nil
	}
	return c.ctx.Err()
```
1. **On the 1st call to `c.Close()`**: `len(channels) >= 1` (at least `"default"`), so `if len(channels) > 0 { return nil }` returns `nil`.
2. **On a 2nd call to `c.Close()`**: `c.channels` was set to `nil` by the 1st call, so `len(channels) == 0`, and `c.Close()` falls through to `return c.ctx.Err()`, returning `context.Canceled`!
3. **Multi-channel `errors.Join` masking in `IsConnCanceled`**: If `errs` contains multiple errors joined via `errors.Join(errs...)`, gRPC's `status.FromError(err)` uses `errors.As(err, &gs)`, which stops at the **first** error in the joined tree implementing `GRPCStatus() *Status`. If the first error is a non-`Canceled` gRPC status error and the second is `codes.Canceled`, `status.FromError` inspects only the first error.

#### Reproduction
Reproduced by `TestVerify_Finding4_CloseNotIdempotentAndErrorsJoinMasksIsConnCanceled` in [`notes/pr-verify/etcd-21765/channel_pool_verify_test.go`](etcd-21765/channel_pool_verify_test.go).

### Finding 5 (MEDIUM): Incomplete Service Coverage (`Watch`, `Lease`, `Cluster`, `Auth`, `Maintenance` Ignore `WithChannelKey`)

#### Root Cause in Go Code
In `client/v3/retry.go` and `client/v3/watch.go`:
- Only `RetryKVClient(c)` (`retry.go:103`) was changed to pass `&routingClientConn{client: c}` to `pb.NewKVClient`.
- `RetryLeaseClient(c)` (`retry.go:118`), `RetryClusterClient(c)` (`retry.go:136`), `RetryMaintenanceClient(c)` (`retry.go:153`), `RetryAuthClient(c)` (`retry.go:177`), and `NewWatcher(c)` (`watch.go`) still pass `c.conn` directly to `pb.New*Client(c.conn)`!
- Although `routingClientConn` implements `NewStream` (`channel_pool.go:99–108`), no streaming client (`Watch`, `LeaseKeepAlive`, `Maintenance.Snapshot`) actually uses `routingClientConn` in `client/v3` production code. Callers passing `WithChannelKey(ctx, "ch-1")` to `client.Watch`, `client.Grant`, `client.KeepAlive`, etc. will have their requests silently sent over the `"default"` channel (`c.conn`).

### Finding 6 (MEDIUM): Wrapped `ErrChannelKeyNotFound` Violates Leaf-Error Contract (`errors.isLeafError`)

#### Root Cause in Go Code
In `client/v3/channel_pool.go:79`:
```go
	if !ok || ch.conn == nil {
		return nil, fmt.Errorf("%w: %q", ErrChannelKeyNotFound, key)
	}
```
Whereas `ErrEmptyChannelKey` and `ErrReservedChannelKey` are returned directly as `*errors.errorString` values (leaf errors with no `Unwrap()` method), `connectionForContext` wraps `ErrChannelKeyNotFound` using `fmt.Errorf("%w: %q", ...)`, producing a `*fmt.wrapError` whose `Unwrap()` returns `ErrChannelKeyNotFound` (`errors.Unwrap(err) != nil`).
In `client/v3`'s formal specification of `ContextError` (`Spec/go_etcd_io/etcd/client/v3/ContextError.lean`), non-status errors returned by the transport are required to satisfy `errors.isLeafError` so `errors.Is(err, context.Canceled)` and `errors.Is(err, context.DeadlineExceeded)` do not traverse arbitrary unwrap chains.

#### Formal Witness & Reproduction
- In [`Spec/go_etcd_io/etcd/client/v3/Client__connectionForContext.lean`](../../Spec/go_etcd_io/etcd/client/v3/Client__connectionForContext.lean), the missing-key postcondition (`poolConnFor chs o = null`) yields `go_etcd_io.etcd.cache.v3.errorStringSpec err` (from `fmt.Errorf.spec`) rather than `errors.isLeafError`.
- Reproduced by `TestVerify_Finding6_ErrChannelKeyNotFoundWrappedIsNotLeaf` in [`notes/pr-verify/etcd-21765/channel_pool_verify_test.go`](etcd-21765/channel_pool_verify_test.go).

### Finding 7 (MEDIUM): `initChannelKey` Holds Exclusive `c.epMu.Lock()` Across Dial, and `dialWithContext` Ignores `ctx`

#### Root Cause in Go Code
1. **`c.epMu.Lock()` held across `dialWithBalancerForKey` (`channel_pool.go:44–61`)**:
   `initChannelKey` acquires `c.epMu.Lock()` (`defer c.epMu.Unlock()`) and holds it across `resolver.New(endpoints...)` and `c.dialWithBalancerForKey(ctx, key, r, endpoints)`. Because `routingClientConn.Invoke` and `routingClientConn.NewStream` acquire `c.epMu.RLock()` on every RPC, holding `c.epMu.Lock()` across dial blocks all concurrent RPCs and `c.Endpoints()` / `c.SetEndpoints()` calls, and will deadlock if any synchronous dial option / callback invokes `c.Endpoints()`.
2. **`ctx` parameter in `initChannelKey` -> `dialWithBalancerForKey` -> `dialWithContext` is completely unused (`channel_pool.go:41–53`, `client.go:322, 344`)**:
   `initChannelKey(ctx, key)` normalizes `if ctx == nil { ctx = c.ctx }` and threads `ctx` through `dialWithBalancerForKey(ctx, ...)` to `dialWithContext(ctx, channelKey, ep, creds, dopts...)`. However, `dialWithContext` (`client.go:344–364`) **never references `ctx` at all**! Even if `ctx` is already canceled, `initChannelKey` ignores `ctx.Err()` and creates the channel anyway.
