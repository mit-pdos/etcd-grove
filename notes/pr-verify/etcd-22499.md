## Verdict

The PR does what it says. The proof shows that `OpenSnapshotBackend` returns success only after
the rename of `<index>.snap.db` onto `db` has been followed by a successful `fsync` of the
directory holding `db`, and that a failed sync returns a nil backend and an error that wraps the
sync error. This is the same result, under the same spec, as for #22518. The two PRs differ only in
how the sync helper is defined (a package variable here, so tests can stub it), the error text, and
#22518's extra log line.

Reading the caller, `applySnapshot`, shows the fix is enough for #22498. The consistent index
picks up the snapshot's index only at `consistIndex.SetBackend(newbe)`, which runs after
`OpenSnapshotBackend` returns. So the old backend can write that index into the old file only after
the rename is durable.

What is not covered:
- **Crash semantics.** There is no crash model; durability is an abstract resource that only the
  trust-boundary `Fsync` spec produces.
- **The caller's ordering.** It was checked by reading the code, not proved.
- **The package variable is assumed read-only.** The proof assumes that after package
  initialization `syncSnapDir` holds its declared literal and is not written again. This holds for
  the production code; only the PR's tests write the variable.

### The spec and how the proof differs from #22518's

`Spec/go_etcd_io/etcd/server/v3/storage/OpenSnapshotBackend.lean` is #22518's, as refined after
its review: on `(be, nil)`, `fs.entryDurable (snapDBPath ss idx) (cfgBackendPath cfg.DataDir)`
(the entry `db` is durable and names `<idx>.snap.db`); otherwise `be = nil` and an error. The
durability vocabulary (`fs.renamePending src dst`, `fs.entryDurable src dst`, `fs.dirOf`,
`snapDBPath`, ...) and the eight trust-boundary specs are #22518's.

What is new here comes from the variable:
- `Proof/go_etcd_io/etcd/server/v3/storage/Fs.lean`. The part of the vocabulary the package fact
  needs moved here from `InvSnapshotBackend.lean`, because `apply/Base.lean` (which defines the
  instance) cannot import that file. This file also holds:
  - `syncSnapDir.litBody`: the literal's translated body, copied.
  - `syncSnapDir.lit_in_initialize`: a kernel check (`rfl`) of the copy against the generated
    `storage.initialize'`. The initializer's first `let` binds `$r0` to a literal with parameter
    `dir` and that body, and the first pair `(GlobalVarAddr g _, $r0)` in its scope (the
    `GoStore`'s operands) names `syncSnapDir`. A deliberately wrong body fails the check.
  - `storageInit := globalAddr syncSnapDir ↦□ syncSnapDir.lit`: **the package fact**, now
    `server/v3/storage`'s `isPkgInit` (`etcdserver/apply/Base.lean`; it was `True`).
- `Proof/.../storage/syncSnapDirLit.lean`: `syncSnapDirFn f` is #22518's `syncSnapDir.spec`
  stated for a function value: with `renamePending src dst` and `dirOf dst = dir`, `f(dir)`
  returns `nil` with `entryDurable src dst`, or an error. `syncSnapDir.wp_lit` proves that
  `syncSnapDir.lit` meets it, from the specs of `OpenDir`, `Fsync` and `Close`. The proof is
  #22518's proof of `syncSnapDir`; the bodies are the same expression.
- `Proof/.../storage/OpenSnapshotBackend.lean`: #22518's proof, except at the sync. Here it gets
  `storageInit` from `isPkgInit`, loads the variable (`↦□`), and applies `syncSnapDir.wp_lit`. It
  drops #22518's `zap.String`/`Logger.Info` callees (no log line).
- `etc/link-lean-first-server.txt`: `storage_OpenSnapshotBackend` now lists `fileutil_OpenDir
  fileutil_Fsync os_File__Close` in place of `storage_syncSnapDir zap_String zap_Logger__Info`.
  There is no `storage_syncSnapDir` entry: it is a variable, not a function.

The package fact is an assumption, as the other etcd packages' facts are (`v3rpcInit`, the error
variables). `storage`'s initializer cannot be proved, because it also runs the names-only
initializers of `quotaBackendBytes`, `DefaultQuotaSize` and `maxQuotaSize`, which are opaque axioms.
`↦□` (read-only) is what the production code gives: `syncSnapDir` is unexported, and outside the
initializer only the PR's `backend_test.go` writes it. The fact is part of an instance, not an
`axiom`, so `etc/tcb-report.py` does not list it; it is listed here.

## Findings

- **No bug in the PR.** The fresh reviewer found no input or interleaving where it goes wrong. A
  sync failure after a successful rename leaves a consistent state on restart: if the rename
  reached disk, `db` is the snapshot's database with its own index; if not, the old db is below the
  snapshot index next to `<index>.snap.db`, and `RecoverSnapshotBackend` redoes the swap.
- **Design (minor).** The package variable exists only so tests can stub the sync.
  - It is mutable global state: harmless today (no `t.Parallel` in `server/storage`, and the tests
    restore it with `t.Cleanup`), but a future parallel test would race on it.
  - Upstream `main` already has the same helper as `fsyncSnapDir` in
    `server/etcdserver/api/snap/db.go` (from #22314), injected through a `Snapshotter.fsyncDir`
    field rather than a global; both PRs duplicate it.
  - For verification, the variable costs one assumption (that it is read-only) that #22518's
    plain function does not need.
- **No bug in the existing code** was found; nothing was added to `issues/`.
- **Reviewer's points on the model** (shared with #22518, recorded there, open):
  - `entryDurable` is not exclusive per directory entry, so a later rename onto `db` would leave
    an earlier fact in place. Nothing verified here renames onto `db` twice.
  - No verified caller uses the new guarantee yet.

## Draft review comment

> The change looks correct to me: after the rename, `OpenSnapshotBackend` now returns only once
> `member/snap` has been fsynced, and a sync failure returns an error before the caller switches
> the consistent index to the new backend. Since `SetBackend` is what makes the old backend start
> writing the snapshot's index into the old file, this ordering closes the window described in
> #22498.
>
> Two small suggestions:
> - `server/etcdserver/api/snap/db.go` already has the same helper (`fsyncSnapDir`, from #22314),
>   and `Snapshotter` injects it through its `fsyncDir` field. Reusing that (or the same
>   field-injection pattern) would avoid a second copy and a mutable package-level variable that
>   parallel tests could race on.
> - #22518 makes the same fix; it may be worth consolidating the two.
