## Verdict

As far as it was verified, the change is safe on the request path, but it does less than its
description says.
- **What is proved**: the new entry function `logLightweightRequestInfo` does not panic for any
  decoded request of any size. It never dereferences nil, never indexes out of range (at most
  `maxLogKeys` comparisons are read) and writes nothing of the request. The log interceptor still
  meets its old contract (transparent, calls the handler once, logs after it) with the request logger
  passed in. `EtcdServer.RequestLogger` returns the field.
- **What it rests on**: one new trust-boundary axiom, `zap.Strings`. The interceptor's call
  `logUnaryRequestStats` is still a names-only axiom, now with the extra parameter. Its new branch
  (`peer.FromContext`, `Addr.String()`, then the proved function) is trusted, not proved.
- **What does not work as described** (a Go test shows each, `notes/pr-verify/etcd-21764/`):
  - **Writes inside a Txn are not logged.** The log records only a Txn's compare keys, never the keys of
    its `Success`/`Failure` operations. A Txn that deletes a key with no comparison (`clientv3`'s
    `Txn().Then(OpDelete(k))`, `etcdctl txn`) logs no key. So the log cannot answer "who deleted this
    key", its first stated goal, for transactions.
  - **The request path can block on the log file.** `BufferedWriteSyncer.Write` flushes synchronously,
    under the mutex every request's write and the 1 s flush loop share, whenever the 256 KB buffer is
    full. A slow disk then stalls requests, contradicting "ensures log writes never block the gRPC
    request path".
  - `compare_range_ends` lists only the non-empty range ends, so it does not line up with
    `compare_keys`: two different transactions give the same entry.
  - Entries logged after `Cleanup` has stopped the syncer stay in the buffer and are never written.
    That is requests the gRPC server still serves after the server's run loop ended (the server
    stopping itself; `embed.Close` stops gRPC first, so a normal shutdown loses nothing).
  - The reviewer found more, each with a test (findings 7 to 12). The main ones:
    - `Cleanup` never closes the lumberjack file, which leaks it and a goroutine per server stop.
    - A bad rotation JSON (`maxsize: -1`) silently drops every entry.
    - Binary keys collide in the JSON output (invalid UTF-8 becomes U+FFFD).
- **Not covered**: `NewServer`'s construction of the logger (lumberjack, the rotation JSON), `Cleanup`,
  the flags and config plumbing, and what is logged. Logging has no effect in the model, so the specs
  say nothing about entry contents; the content findings above come from tests.

### The behavior changes, old and new specs

- **`newLogUnaryInterceptor`**
  (`Spec/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/newLogUnaryInterceptor.lean`).
  - Old: given `s.lg ↦□ lg` (non-nil) and `s.Cfg.WarningUnaryRequestDuration ↦□ wd`, the closure is
    `srvInterceptorOk`.
  - New: the same, plus `s.requestLogger ↦□ rl` for some `rl`, nil or not.

  The extra premise is incompatible in form only. `requestLogger` is written once, in `NewServer`,
  before the server is shared, and never again, so a read-only points-to is what its callers hold.
- **`logUnaryRequestStats`** (`Spec/.../v3rpc/logUnaryRequestStats.lean`, axiom). Old: 7 arguments,
  `lg ≠ null`, returns. New: 8 arguments; the request logger `rl` is any pointer; same pre/post.
- **`logLightweightRequestInfo`** (`Spec/.../v3rpc/logLightweightRequestInfo.lean`, new). With
  `lg ≠ null` and `v3rpc.lwReqIs req u`, it returns. `lwReqIs`
  (`Proof/.../v3rpc/InvRequestLog.lean`) says `req` is one of the switch's six request types with
  its read fields read-only, or anything else, nil included.
- **`EtcdServer.RequestLogger`** (`Spec/.../etcdserver/EtcdServer__RequestLogger.lean`, new). With
  `s.requestLogger ↦□ rl`, it returns `rl`.

## Trust base

New axiom: **`zap.Strings.wp_proof`** (`Proof/go_uber_org/zap/Strings.lean`). It says
`zap.Strings(k, ss)` returns a field, as the existing `zap.ByteString`, `zap.String` and `zap.Int64`
axioms do. zap's `Strings` builds a `Field` around `stringArray(ss)` and does not read the slice until
encoding, which, like all logging here, has no effect in the model.

Trusted more widely (no new axiom): the `logUnaryRequestStats` axiom now also covers the request
logger's branch. That branch calls `peer.FromContext(ctx)` and `peerInfo.Addr.String()` on every
unary request when request logging is on (before the PR, only for slow or debug-logged requests), and
then `logLightweightRequestInfo`, whose precondition `lwReqIs` the axiom trusts of the decoded request.
- `lwReqIs` holds of what grpc decodes: protobuf-go never decodes a nil message or a nil repeated
  element.
- `Addr` is non-nil for grpc's own transports (`notes/pr-verify/etcd-22259.md`, whose
  `grpcPeerIs` makes that a premise). A hand-built peer with a nil `Addr` would panic the
  interceptor here too.

## Findings

These are about the PR. None is a bug in the pinned code, so `issues/` gets nothing.

1. **Transaction operations are not logged** (Medium: the PR misses its main goal for Txn).
   `logLightweightRequestInfo` logs only `r.Compare[i].Key`/`RangeEnd`, never the keys in
   `r.Success`/`r.Failure`. Kubernetes' writes compare and write the same key, so they show it. A Txn
   whose operations differ from its comparisons, or has none, shows only the comparisons or nothing.
   Test: `TestRequestLogTxnOpKeysNotLogged`; the entry has method, remote and time only.
2. **The request path can block on the log file** (Medium: contradicts the description).
   `zapcore.BufferedWriteSyncer.Write` holds its mutex while it flushes a full buffer to lumberjack,
   which writes and may rotate (rename, open) the file. The 1 s flush loop holds the same mutex
   during its write. Under load, or with a slow or stalled disk, every unary request waits behind the
   log file. Test: `TestRequestLogBlocksOnSlowSink`, with a sink taking 300 ms per write; the slowest
   `logLightweightRequestInfo` call took 300 ms.
3. **`compare_range_ends` is ambiguous** (Low). Only non-empty range ends are appended, so the list
   does not line up with `compare_keys`. Test: `TestRequestLogCompareRangeEndsAmbiguous`;
   `[{a,z},{b}]` and `[{a},{b,z}]` give the same entry.
4. **Entries after `Stop` are lost** (Low).
   - `Cleanup` stops the syncer. Later writes go into the buffer, which nothing flushes, since the
     flush loop has exited.
   - The lumberjack file is never closed.
   - Requests the gRPC server serves after the server's run loop has ended (a member stopping itself
     while gRPC still serves) are dropped.

   Test: `TestRequestLogLostAfterStop`.
5. **No outcome or identity in the entry** (design). The entry has no gRPC status or error, and no
   authenticated user. A denied or failed delete looks the same as a successful one, and "who" is
   only a client address. Behind a proxy (grpc-proxy, a load balancer) that address is the proxy's.
6. `server/embed/etcd.go` is not gofmt-clean in the PR (`make verify` would flag it).

### The reviewer's points

A fresh reviewer checked the specs, the axioms and the code. It found the specs sound and not
vacuous, but proving safety only: no content claim of the PR is stated, since logging has no effect
in the model. That is the gap findings 1 to 5 fill with tests.
- **The interceptor's old meaning is preserved.** The postcondition is unchanged; the new premise is
  true of the code, since `requestLogger` is written only in `NewServer`, before the server is shared.
- **The axioms are sound.** `zap.Strings` is a pure constructor.
- **The `logUnaryRequestStats` axiom over-generalizes as before.** It allows any non-nil `rl`, such as
  a `&zap.Logger{}` with a nil core, on which `Info` would panic. The `lg` premise and the
  `zap.Logger.Info` spec already do the same; in the code `rl` is nil or `zap.New(core)`.
- **No data race.** Tested under `-race` with requests during `Close`
  (`TestReviewRequestLogConcurrentCloseRace`, passes).

Its new findings, each with a passing test in `notes/pr-verify/etcd-21764/`:

7. **The lumberjack file is never closed** (Low to Medium, for embedders and in-process tests).
   `Cleanup` stops the syncer but never closes `ljCfg`. After each start/`Close` cycle the file
   descriptor and one `millRun` goroutine leak (`TestReviewRequestLogFileLeakAfterClose`: 2 open fds
   and 2 goroutines after 2 cycles).
8. **The rotation JSON is not validated** (Low).
   - `{"maxsize": -1}` is accepted; lumberjack then rejects every write and the flush loop drops the
     error, so nothing is ever logged (`TestReviewRotationNegativeMaxSizeDropsAll`).
   - Misspelled keys are ignored silently (`TestReviewRotationUnknownKeyIgnored`).
   - A syntax error is caught only in `NewServer`, after bootstrap. That error path is clean: the
     deferred `b.Close()` runs, and the syncer has no goroutine yet.
9. **Binary keys collide** (Low to Medium for an audit use). zap's JSON encoder replaces invalid UTF-8
   with U+FFFD, so keys `0xff01` and `0xfe01` give the same entry (`TestReviewBinaryKeysCollide`).
10. **Entry size grows with key size** (Low). Keys are logged whole, so a 1 MiB key gives a 1 MiB
    entry. The "O(1)" is per field, not per byte, and large entries make finding 2 worse
    (`TestReviewEntrySizeUnboundedInKeySize`).
11. **The gateway hides the client** (Low). HTTP/JSON requests through the gRPC gateway are logged with
    the gateway's loopback connection, not the HTTP client (`TestReviewGatewayRemoteIsServerItself`).
    The slow-request log already behaves the same way.
12. **Cosmetic.** `help.go` shows a JSON default for `--experimental-log-request-rotation-config-json`,
    but the flag's default is `""`, which means the same values. The PR also adds a new
    `--experimental-*` flag while etcd is retiring that prefix.

None of these is a panic, and none concerns the pinned code.

## Relation to etcd#22259

etcd#22259 (`pr-verify/etcd-22259`) changes the same interceptor: it stores the client IP in the
handler's context and generalizes `srvInterceptorOk`. The two changes are independent, so a merge of
both would need this branch's `rl` premise added to 22259's spec of `newLogUnaryInterceptor`. Both add
an `Addr.String()` on the request path; 22259 does it unconditionally, this PR only when request
logging is on. 22259 established the premise that grpc's transports give a non-nil `Addr`.
