## Verdict

**The code change is correct and adds no risk: it exposes an existing field, and the fencing property it advertises holds, with one exception the PR inherits.**

- **Proved** (no `sorry`, no new axiom):
  - `Mutex.Rev` returns `myRev`.
  - `NewDLocker` builds the same `lockerMutex` as `NewLocker`, and its `Rev` is the mutex's.
  - **Fencing tokens increase**: take a holder whose `Rev()` is `c1`, observed at revision `R1`, and a later holder with an ownership fact `lockedAt` at `R2 ≥ R1` and create revision `c2`. Then `c1 ≤ c2`, and `c1 < c2` when the two differ. Here "holder" means `Lock`'s or `TryLock`'s `nil`, and `c2` is also the later holder's `Rev()`. This follows from etcd's history laws (a key lives from its creation; revisions are well formed), so tokens follow the order in which etcd granted the lock.
- **The exception**: the doc's "monotonically incremental" fails in one case, when the later holder's `Lock` returned in the case `issues/mutex-lock-recreated.md` records. There, another `Mutex` of the same session deleted and re-created the shared key, and `Lock` returns nil without re-checking the key's create revision. The later caller's `Rev()` is then the stale, smaller revision (probe: `B.Rev()=3 < D.Rev()=5`, with B's `Lock` returning after D's).
  - A storage that rejects tokens below the largest it has seen, as the new demo does, stays safe: it rejects the stale holder once the real holder has written.
  - The fix proposed in that issue restores monotonicity.
- **Not covered by the proof**: the `contrib/lock` demo programs (`main` packages, not translated). They were checked by reading only. Their README is now inconsistent with their output (Findings).

## The specs and results

All files are under `Spec/go_etcd_io/etcd/client/v3/concurrency/` and `Proof/go_etcd_io/etcd/client/v3/concurrency/`.

- `Mutex__Rev.lean`: `{mutexState m st} m.Rev() {RET st.rev; mutexState m st}`.
  - Like `Mutex.Key`, it needs exclusive ownership of the mutex's fields: `Rev` is not synchronized.
  - The docstring lists what `myRev` is in each state: `-1` before any `Lock`, and after `Unlock` or `TryLock`'s `ErrLocked`. After an error of `Lock` it may be a positive, stale revision.
- `lockerMutex__Rev.lean`: the same, through `lm.Mutex`.
- `NewDLocker.lean`: identical to `NewLocker.spec`, for the function `NewDLocker`. The result is `interface.mkOk (*lockerMutex) lm`, with `isMutex` and `mutexState m MutexSt.init`.
- `InvMutex.lean`, "Fencing tokens":
  - `lockFloor pfx c R`: at `R`, `c ≤ R` and no key under `pfx` has a create revision below `c`.
  - `lockedAt_floor`, `keyRecreated_floor`: both of `Lock`'s `nil` outcomes give `lockFloor` for the `rev` they leave in `myRev`.
  - `lockFloor_later`: every key present at a revision `a ≥ R` has a create revision at least `c`.
  - `lockFloor_fence`: the same for a later holder's `lockedAt`.
- `Results.lean`: `mutex_Rev`, `dlocker_NewDLocker`, `dlocker_Rev`, `mutex_fence` (`(lockedAt ∨ keyRecreated) pfx k1 c1 R1 ∗ lockedAt pfx k2 c2 R2 ⊢ c1 ≤ c2` for `R1 ≤ R2`) and `mutex_fence_strict` (`c1 ≠ c2 → c1 < c2`).
  - The premise `R1 ≤ R2` is reachable from real-time order: give holder 1's `etcdReached R1` to holder 2's `Lock` as `lo`, and `Lock`'s postcondition gives `lo ≤ R2`.
  - Equal tokens from different keys need one transaction that creates two lock keys, which no `Mutex` does. The model does not record who wrote a key, so it does not exclude this (as for `mutex_exclusion`).

These properties also held of the code before the PR: `myRev` and the ownership facts are unchanged. The PR only makes the token readable. This is the gap the etcd#22384 report noted ("`Mutex` gives the caller no way to learn the `myRev`"), and `Rev()` closes it.

## Findings

No bug in the PR's library code.

1. **"Monotonically incremental" fails while the `Mutex.Lock` bug of `issues/mutex-lock-recreated.md` is unfixed** (medium). That bug is in existing code.
   - In its schedule, B's `Lock` returns nil after D's, while D holds the lock, and `B.Rev()` (r1) is below `D.Rev()` (r2). The storage remains safe: B's writes are rejected once D has written.
   - Probe: `TestDLockerRevKeyRecreated` in `notes/pr-verify/etcd-18779/dlocker_fence_test.go`. It passes on the fork and on the PR head, which confirms the behaviour.
   - Recorded as a new section of `issues/mutex-lock-recreated.md` (on this branch).
   - The proof's `mutex_fence` covers only later holders with `lockedAt` for this reason.
2. **`DLocker` invites use from several goroutines, as `sync.Locker` does, but gives no exclusion between them** (medium, documentation).
   - A `lockerMutex` shared by two goroutines lets both `Lock`s return with the same `Rev()`. After one `Unlock`, the other sees `Rev()` = `-1`, which a storage with no entry for the key would accept.
   - This is pre-existing for `NewLocker`. The specs exclude it by requiring exclusive `mutexState`, and concurrent `Rev`/`Lock` is a data race.
   - Probe: `TestReviewSharedLockerGoroutines` in `notes/pr-verify/etcd-18779/dlocker_review_test.go`.
3. **`Rev()` after a failed `Lock` is a stale positive value** (low, documentation).
   - For example, after `ErrSessionExpired`, `Rev()` returns 3 with no lock held (`TestReviewSessionExpiredStaleRev`).
   - For a `DLocker` this is reachable only by recovering `Lock`'s panic. `DLocker.Lock` panics on any error and takes no context, which is limiting for exactly the lease-expiry situations fencing is for.
4. **Two DLockers on one session both hold with equal tokens** (low). This is by design: the same session's key is reused. The storage's `<` check accepts both (`TestReviewSameSessionEqualTokens`).
5. **contrib/lock README is inconsistent with the new client** (low).
   - It still shows lease IDs as "acquired lock, version: 694d82254d5fa305" (README lines 37, 59).
   - It still says "expected fail to write to storage with old lease version:" (line 67), but the client now prints "old version".
   - The client logs the version in hex (`%x`) and the storage in decimal (`%d`), so revision 10 shows as `a` and `(10)`.
6. Pre-existing, out of scope: `contrib/lock/storage`'s `data` map is accessed by concurrent HTTP handlers with no lock.

The reviewer subagent checked the specs, the soundness and non-vacuity of the fence theorems, interleavings, the demo and the conflict resolution. It found no soundness problem. Its docstring points (the fence's scope, `Rev` after errors) are fixed on this branch. Its open points are findings 2–5. All probes and logs are in `notes/pr-verify/etcd-18779/` (`README.md`).

## Draft review comment (for the user to edit and post)

> Thanks — exposing the mutex's create revision as a fencing token looks right to me, and `<` (rather than `!=`) is the correct check on the storage side. A few points:
>
> 1. "monotonically incremental" doesn't hold in one case today. When two `Mutex`es share a session and prefix and one of them is canceled while waiting and then locks again, the other one's `Lock` can return nil while another session holds the lock (`Lock` only checks that its key exists, not that its create revision is still `myRev`). Its `Rev()` is then the old, smaller revision, even though it returned later. A fenced resource still rejects it once the real holder has written, but the doc comment overpromises. Maybe say "a later holder's revision is larger" with that caveat, or fix `Lock` to re-check the create revision.
> 2. `DLocker` embeds `sync.Locker`, so people may share one locker across goroutines. That gives no exclusion between them (both `Lock` calls return, with the same `Rev()`), and `Rev()` races with `Lock`/`Unlock`. Worth a sentence in the doc that a `DLocker` must be used by one goroutine at a time, as with `Mutex`.
> 3. `Rev()` returns -1 before `Lock` and after `Unlock`, and a stale value after a failed `Lock`; the doc could say it's only meaningful while the lock is held.
> 4. The README's sample output still shows lease IDs as the version and the "old lease version" message; the client now prints the revision in hex while the storage prints it in decimal.
