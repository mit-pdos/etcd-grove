## Verdict

**UNSOUND (BUGGY — 5 bugs identified; 3 reproduced deterministically in unit tests, 1 triggered a `SIGSEGV` in existing `mvcc` tests, and 2 mechanized as counterexample theorems in Lean).**

PR `#21397` rewrites `(*store).scheduleCompaction` (`server/storage/mvcc/kvstore_compaction.go`) to move the batched `UnsafeRange` scan and `kvHasher.WriteKeyValue` hashing into a background producer goroutine that reads via `s.b.ReadTx()`, sending unkept revisions over a buffered channel `toDelRevsChan := make(chan Revision, batchNum)` to the consumer loop in `scheduleCompaction`, which deletes keys under `tx := s.b.BatchTx(); tx.LockOutsideApply()`.

Attempting to re-prove [`mvcc.store.scheduleCompaction.wp_proof`](../../Proof/go_etcd_io/etcd/server/v3/storage/mvcc/store__scheduleCompaction.lean) against the translated PR immediately fails at multiple separation-logic obligations in our existing `mvcc` and `backend` contracts ([`InvStore.lean`](../../Proof/go_etcd_io/etcd/server/v3/storage/mvcc/InvStore.lean), [`Model2.lean`](../../Proof/go_etcd_io/etcd/server/v3/storage/backend/Model2.lean)), exposing five distinct bugs:

1. **Tombstone keys (`<rev>t`, 18 bytes) are never deleted from bbolt (`tx.UnsafeDelete` called with 17-byte non-tombstone key)**:
   - In the `key` bucket (`schema.Key`), normal updates use 17-byte keys (`mvcc.revBytes r false`) while tombstones written by `store.delete` use 18-byte keys ending in `'t'` (`mvcc.revBytes r true = mvcc.revBytes r false ++ [W8 116]`).
   - In PR `#21397`, the producer goroutine calls `rev = BytesToRev(keys[i])` (which parses only bytes `0..8` and `9..17`, discarding the 18th tombstone byte `'t'`) and sends `rev` (`Revision`) on `toDelRevsChan`.
   - The consumer loop then calls `tx.UnsafeDelete(schema.Key, RevToBytes(rev, make([]byte, 8+1+8)))`, which always constructs a 17-byte key (`mvcc.revBytes r false`).
   - As mechanized in [`mvcc.sc_pr21397_tombstone_key_ne`](../../Proof/go_etcd_io/etcd/server/v3/storage/mvcc/store__scheduleCompaction.lean) and [`mvcc.sc_pr21397_tombstone_not_deleted`](../../Proof/go_etcd_io/etcd/server/v3/storage/mvcc/store__scheduleCompaction.lean), and reproduced in `TestPR21397TombstoneKeyNeverDeleted` ([`compaction_pr21397_bug_test.go`](etcd-21397/compaction_pr21397_bug_test.go)), **every superseded tombstone key in `schema.Key` is leaked in bbolt forever**, while `keyCompactions` still increments as if it had been deleted.

2. **`ReadTx.UnsafeRange` with a positive limit skips committed bbolt keys and corrupts `KeyValueHash` when `txReadBuffer` is non-empty**:
   - Replacing `BatchTx.UnsafeRange` with `ReadTx.UnsafeRange(schema.Key, last, end, int64(batchNum))` hits the exact hazard documented in [`issues/etcd-unsafe-range-limit-buffer.md`](../../issues/etcd-unsafe-range-limit-buffer.md) and [`backend.rtRange`](../../Proof/go_etcd_io/etcd/server/v3/storage/backend/Model2.lean): `baseReadTx.UnsafeRange` first takes up to `batchNum` entries in `[last, end)` from `readTx.buf` (`txReadBuffer`, which holds the newest uncommitted revisions) and, if `n < batchNum`, prepends `batchNum - n` entries from bbolt (`readTx.tx`, which holds older committed revisions starting at `last`), returning `append(k2, keys...)`.
   - When bbolt has more than `batchNum - n` entries in `[last, end)` and `readTx.buf` has `n > 0` entries in `[last, end)`, the last element of the returned batch `keys[len(keys)-1]` is the newest entry from `readTx.buf`.
   - Advancing `last = RevToBytes(Revision{Main: rev.Main, Sub: rev.Sub + 1}, last)` jumps straight past `readTx.buf`'s newest entry, **completely skipping all committed bbolt keys between `k2[len(k2)-1]` and `keys[0]`**.
   - As mechanized in [`mvcc.sc_pr21397_rtRange_skips_committed`](../../Proof/go_etcd_io/etcd/server/v3/storage/mvcc/store__scheduleCompaction.lean) and reproduced in `TestPR21397ReadBufferSkipsCommittedKeysAndCorruptsHash` ([`compaction_pr21397_bug_test.go`](etcd-21397/compaction_pr21397_bug_test.go)), those skipped revisions are neither deleted from bbolt nor fed to `h.WriteKeyValue`, producing a corrupted `KeyValueHash` (`3562080347` instead of `1968211745`) that mismatches `HashByRev` and causes false-positive `CORRUPT` alarms across cluster members.

3. **Use-after-`RUnlock` on zero-copy bbolt mmap slices (`keys[i]`, `values[i]`)**:
   - In the producer goroutine (`kvstore_compaction.go:51-62`):
     ```go
     rtx := s.b.ReadTx()
     rtx.RLock()
     keys, values := rtx.UnsafeRange(schema.Key, last, end, int64(batchNum))
     rtx.RUnlock()

     for i := range keys {
         rev = BytesToRev(keys[i])
         ...
         h.WriteKeyValue(keys[i], values[i])
     }
     ```
   - `rtx.UnsafeRange` returns byte slices pointing directly into bbolt's mmap'd pages owned by `rtx.tx` (`*bolt.Tx`). In [`InvStore.lean`](../../Proof/go_etcd_io/etcd/server/v3/storage/mvcc/InvStore.lean) (`keyReadLocked` and `rdCap Rd Tok`), those slices (`Rd ksl k`, `Rd vsl v`) can only be dereferenced while holding the reader token `Tok`, which `rtx.RUnlock()` consumes (`store.restore` avoids this by holding `rtx.RLock()` until `<-revc` confirms `restoreIntoIndex`'s goroutine has finished reading every slice; see [`restoreIntoIndex.lean`](../../Proof/go_etcd_io/etcd/server/v3/storage/mvcc/restoreIntoIndex.lean)).
   - Because PR `#21397` calls `rtx.RUnlock()` *before* reading `keys[i]` and `values[i]`, a concurrent `BatchTx` commit (either by the consumer goroutine at `tx.Unlock()` / `s.b.ForceCommit()` or by normal writes) can acquire `readTx.Lock()`, roll back `rtx.tx`, and commit a write transaction that frees/rebalances/remaps those bbolt pages while the producer goroutine is reading `keys[i]` and `values[i]`.

4. **Producer goroutine leak and post-close `SIGSEGV` when interrupted or closed (`<-s.stopc`)**:
   - When `<-s.stopc` is selected in the consumer loop (`kvstore_compaction.go:108-109`), `scheduleCompaction` returns immediately (and runs `defer s.b.UnlockForSafeRangeDelete()`) without stopping or waiting for the background producer goroutine.
   - If more than `batchNum` unkept keys remain, the producer goroutine blocks forever on `toDelRevsChan <- rev` (`TestPR21397StopcGoroutineLeak` in [`compaction_pr21397_bug_test.go`](etcd-21397/compaction_pr21397_bug_test.go)).
   - If `s.Close()` and `b.Close()` run while the untracked producer goroutine is still looping (which happens in existing `mvcc` tests that call `s.Compact(...)` without waiting on the returned channel before `cleanup(s, b)`), `b.Close()` calls `CommitAndStop()`, which sets `baseReadTx.tx = nil` (`batch_tx.go:397`), causing the producer goroutine to panic with a nil-pointer `SIGSEGV` at `bbolt.(*Tx).Bucket` inside `baseReadTx.UnsafeRange` (`read_tx.go:103`).

5. **`BatchTx` lock (`tx.LockOutsideApply()`) held across channel wait and across arbitrary numbers of kept keys**:
   - The consumer acquires `tx.LockOutsideApply()` *before* entering `for !completed` (`kvstore_compaction.go:81-82`) and only unlocks when `keyCompactions%batchNum == 0` (`kvstore_compaction.go:97`, i.e., every `batchNum` *deleted* keys rather than every `batchNum` *scanned* keys) or when `toDelRevsChan` closes.
   - As a result, `tx.LockOutsideApply()` is held while waiting for the producer goroutine to scan and hash keys; if `< batchNum` keys are deleted across the entire compaction (e.g., when most or all keys are in `keep`), `tx.LockOutsideApply()` is never released or slept on for the entire multi-batch scan and hash computation. Conversely, when total deleted keys is a positive multiple of `batchNum`, `keyCompactions%batchNum == 0` performs an extra unnecessary `ForceCommit()` and `CompactionSleepInterval` sleep after the final deleted key before observing `!ok` on `toDelRevsChan`.

## Draft Review Comment for Upstream

Below is a self-contained review comment in etcd's terminology (not posted upstream):

> There are several correctness and concurrency bugs in this approach:
>
> 1. **Tombstone keys (`<rev>t`) are never deleted from bbolt**:
>    In the `key` bucket, tombstones written by `deleteKey` are 18 bytes (`8` main + `1` `'_'` + `8` sub + `1` `'t'`, via `markTombstone`). `BytesToRev(keys[i])` only parses the first 17 bytes (`Main` and `Sub`), dropping the `'t'` suffix. When the consumer calls `tx.UnsafeDelete(schema.Key, RevToBytes(rev, make([]byte, 8+1+8)))`, it always constructs a 17-byte non-tombstone key, so `bucket.Delete` is a no-op for every tombstone key. All superseded tombstones remain in the `key` bucket forever.
>
> 2. **`ReadTx.UnsafeRange` with a limit skips committed bbolt keys and corrupts `KeyValueHash` when `txReadBuffer` is non-empty**:
>    `baseReadTx.UnsafeRange(bucket, key, endKey, limit)` (`server/storage/backend/read_tx.go:78-122`) first takes `n <= limit` matching entries from `baseReadTx.buf` (`txReadBuffer`, which holds the newest uncommitted revisions) and then takes `limit - n` entries from bbolt (`baseReadTx.tx`, which holds older committed revisions starting at `key`), returning `append(k2, keys...)`.
>    When `txReadBuffer` has uncommitted keys `<= compactMainRev` and bbolt has more than `batchNum - n` keys in `[last, end)`, the last element `keys[len(keys)-1]` of the returned batch is the newest revision in `txReadBuffer`. Setting `last = RevToBytes(Revision{Main: rev.Main, Sub: rev.Sub + 1}, last)` jumps past all committed bbolt keys between `k2[len(k2)-1]` and `keys[0]`, skipping both their deletion and their `h.WriteKeyValue` hash contribution (so the returned `KeyValueHash` does not match `HashByRev`).
>
> 3. **Use-after-`RUnlock` on bbolt mmap slices (`keys[i]`, `values[i]`)**:
>    `rtx.UnsafeRange` returns zero-copy byte slices pointing directly into bbolt's mmap'd pages for `rtx.tx`. Calling `rtx.RUnlock()` at line 54 *before* iterating over `keys[i]` and `values[i]` in `BytesToRev(keys[i])` and `h.WriteKeyValue(keys[i], values[i])` allows a concurrent `BatchTx` commit (`tx.Unlock()` / `ForceCommit()`) to acquire `readTx.Lock()`, roll back `rtx.tx`, and reuse/remap those bbolt pages while the goroutine is still reading `keys[i]` and `values[i]`.
>
> 4. **Goroutine leak and post-close `SIGSEGV` when interrupted via `s.stopc`**:
>    When `<-s.stopc` fires at line 108, `scheduleCompaction` returns without stopping or waiting for the producer goroutine. If more than `batchNum` keys remain to be deleted, the producer goroutine blocks permanently on `toDelRevsChan <- rev`. If `b.Close()` runs right after `s.Close()` (as in tests that call `cleanup(s, b)` while a background compaction is in flight), `CommitAndStop()` sets `readTx.tx = nil` while the producer goroutine is still running, causing a `SIGSEGV` in `baseReadTx.UnsafeRange` at `baseReadTx.tx.Bucket(...)`.
>
> 5. **`tx.LockOutsideApply()` is held while waiting on `toDelRevsChan` and across all kept keys**:
>    Because `tx.LockOutsideApply()` is acquired before the `for !completed` loop and only unlocked when `keyCompactions%batchNum == 0` (every `batchNum` *deleted* keys rather than every `batchNum` *scanned* keys), the `BatchTx` lock is held while waiting for the producer goroutine's `UnsafeRange` and `WriteKeyValue`, and is held continuously without ever unlocking or sleeping if `< batchNum` keys are deleted across a large key space.
