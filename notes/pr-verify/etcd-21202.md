## Verdict

The server side is unchanged, and the proof shows why. `HashByRev`, which the corruption checks
and `HashKV` call, goes through `hashByRevWithCompactRev(rev, 0)`. With `compactRev = 0`,
`prepareHashParams` does exactly what the pin's `hashByRev` did: the same checks, revision,
compaction revision and kept set (`store__hashByRev.lean`, proved, no `sorry`). The filter moved into
`shouldWriteKeyValue` is the pin's (`hashInclF_size_old`).

**`--compact-rev` does not do what it is for.** The PR says the flag is for comparing snapshots, but a
positive compaction revision replaces the store's compaction revision in the `rev < compactRev`
check, so nothing refuses a value below what the snapshot has already compacted. The proof of
`prepareHashParams` goes through only under the premise that the custom value is at or above the
store's (`hashCrevOk`); without it, the code calls `kvindex.Keep` on a revision the store
compacted. The cost is wrong hashes with no error: a revision the snapshot has compacted is hashed
instead of refused (finding 1), and two snapshots of one history give different hashes. The
comparison the PR describes does work when the custom revision is the compacted snapshot's own
compaction revision and some key is live at the hashed revision. With every key deleted, it fails
because of the existing empty-kept-set bug (finding 3, `issues/etcd-hash-empty-keep.md`).

**Other problems.** `--detailed` drops values that do not decode from the total hash (finding 5).
With `-w json`, `--detailed` prints two JSON documents (finding 9). The PR also needs a rebase: it
does not compile on current `main` (protobuf-go v2).

**Not covered.** The crc32 hashing and the backend's `UnsafeForEach` (two new axioms), the hash
cache in `hashStorage`, and etcdutl (not translated). These were reviewed and tested instead.

## The specs

All in `Spec/go_etcd_io/etcd/server/v3/storage/mvcc/`, over `Proof/.../mvcc/HashParams.lean`
(`hashCrev compactRev cm`: the caller's compaction revision if positive, else the store's `cm`;
`hashRev rev cur`: `rev`, or the last revision `cur` for `0`).

- **`prepareHashParams(rev, compactRev)`**, by a store reader (`storeReaderC`, given back), for
  `rev ≥ 0`: under `s.mu` and `s.revMu` it reads the committed log (last revision `cur`) and the
  compaction revision `cm`; `0 < rev < hashCrev compactRev cm`: `ErrCompacted`; `cur < rev`:
  `ErrFutureRev`; otherwise `nil`, the revision `prev = hashRev rev cur` with `cm ≤ prev ≤ cur`,
  the compaction revision `hashCrev compactRev cm`, the map of what `treeIndex.Keep(prev)` keeps
  (`keepOfIs`), a locked read transaction and the function that unlocks it. Premise
  `hashCrevOk γ compactRev`: `compactRev ≤ 0`, or the caller holds the compaction right at some
  `c ≤ compactRev` (it fixes the store's compaction revision). That premise is what makes
  `cm ≤ prev` hold — `treeIndex.Keep`'s spec needs it — and it is exactly what the code fails
  without (finding 1).
- **`hashByRevWithCompactRev`**: the same outcomes; on success the hash of `unsafeHashByRev` with
  `Revision = hashRev rev cur` and `CompactRevision = hashCrev compactRev cm` (value opaque), the
  read transaction unlocked by the deferred cleanup.
- **`hashByRevDetailed`**: the same, of the detailed result's total hash and own fields.
- **`hashByRev`** (the refactor): with `compactRev = 0`, `hashCrevOk` holds and `hashCrev 0 cm =
  cm` (`hashCrev_zero`): `0 < rev < cm`: `ErrCompacted`; `cur < rev`: `ErrFutureRev`; otherwise the
  hash at `hashRev rev cur` with the store's compaction revision. This is the pin's `hashByRev`
  (`kvstore.go:167-195` at 09669450f) read off its code: same checks, same order, same results.
  The pin's `hashByRev` is not translated on `lean`, so the spec was not re-proved of the old
  translation; the old code is the new one with `compactRev = 0` inlined.
- **`kvHashIncludes`**: returns the filter at the pin (`hashInclF … (len(keep) > 0)` ↔ `hashInclOld`,
  `HashFilter.lean` `hashInclF_size_old`): `shouldWriteKeyValue` is a refactor. Proof from
  pr-verify/etcd-22515's (its `exactKeep = false` case).

Premises shared by the store's specs: `storeCmp γ` (the backend supports compaction: its
view-less `ReadTx`, `metaReadTx`, the one the specs use; the backend contract's ordinary `ReadTx`
needs the bucket's view, which `hashByRev` does not hold when it calls `ReadTx` after releasing
`s.revMu` — before and after the PR — and the hash is opaque anyway) and, for the three hash
functions, `hashRevSecOk` (the histogram `hashRevSec`'s `Observe` returns; not in the package's
facts).

## Findings

Findings about the PR are listed first. The tests are in `notes/pr-verify/etcd-21202/` (see its README).
Unless a finding says otherwise, each one reproduces at the PR head and on the fork branch.

1. **`--compact-rev` below the store's compaction revision is not refused** (medium). With
   `0 < compactRev ≤ rev`, `prepareHashParams` checks only `rev < compactRev`, so the store's own
   compaction revision is never checked.
   - A snapshot compacted at 10 answers `HashByRevWithCompactRev(5, 3)` with a hash of what
     compaction left, where `HashByRev(5)` is `ErrCompacted`
     (`TestHashByRevWithCompactRevBelowStoreCompaction`).
   - `(15, 3)` hashes differently on a snapshot compacted at 10 and an uncompacted one of the same
     history, and neither reports an error (`…BelowStoreCompactionDiffers`).
   - This is the case the PR's comparison is meant for. The fix is to refuse `compactRev` (and
     `rev`) below `s.compactMainRev` with `ErrCompacted`.
   - In the proof: `prepareHashParams` is proved only under the premise `hashCrevOk` (a positive
     `compactRev` is at least the store's compaction revision). `treeIndex.Keep`'s spec needs the
     store's compaction revision to be at or below the revision it keeps at, which the code does
     not ensure.
2. **`--compact-rev` above the hashed revision** (low). With `rev = 0` it is accepted, because the
   check runs before `rev` is resolved to the current revision. With `rev` set explicitly to the
   current revision it is `ErrCompacted`. The result reports `CompactRevision` greater than
   `Revision` (`TestHashByRevWithCompactRevAboveRev`). The spec states this: nothing bounds `pc` by
   `prev` when `rev = 0`.
3. **No key live at the hashed revision** (existing bug, made reachable by the PR). An uncompacted
   snapshot hashed with `--compact-rev C` and one compacted at `C` disagree
   (`…EmptyKeepDisagrees`). The cause is the hasher's `len(keep) > 0` guard at the pin:
   `issues/etcd-hash-empty-keep.md`, added to here. They agree with #22562's change applied, and
   agree when a key is live at the hashed revision (`…AtStoreCompactionAgrees`).
4. **Negative revision** (existing). `HashByRev(-5)` returns the hash of nothing, with no error:
   `issues/etcd-hashkv-negative-revision.md`. The specs take `0 ≤ rev` as a premise.
5. **`--detailed` drops undecodable values** (medium, reviewer). `kvHasherDetailed.WriteKeyValue`
   returns on an `Unmarshal` error before writing to the total hash. The detailed total then
   differs from the plain hash, and the per-key list omits the pair, which hides exactly the
   corruption the tool is for (`TestReviewDetailedDropsUndecodableValue`). The fix is to write the
   pair to the total first, or to report the error.
6. **`--compact-rev 9223372036854775807`** (low, reviewer). `compactRevision + 1` wraps around, so
   the kept-set filter is off and the hash is the same as with `compactRev` 0
   (`TestReviewCompactRevMaxInt64Overflow`). `kvHashIncludes`'s spec excludes this case with a
   premise.
7. **The flag's help text is not what is hashed** (low, reviewer). The help says "revisions less
   than or equal to this value will be ignored". In fact, a revision at or below `compactRev` that
   is live at `rev` is hashed, and when nothing is live, nothing is skipped
   (`TestReviewCompactRevNotIgnored`). The help should say "as if compacted at this revision".
8. **The per-key entries are ambiguous** (low, reviewer). They have no sub-revision and no tombstone
   flag, so a transaction that deletes and puts a key gives two equal `{key, modRevision}` entries
   (`TestReviewDetailedTombstoneAmbiguous`).
9. **`hashkv --detailed -w json` writes two JSON documents to stdout** (low-medium, reviewer):
   first the per-key array, then the printer's object (`TestReviewDetailedStdoutMixed`).
10. **`--output`** (low, reviewer). The file is written with mode 0644 (key names readable by every
    user), an existing file is replaced, and the flag is ignored without `--detailed`
    (`TestReviewOutputFile`).
11. **The PR needs a rebase**:
    - It does not compile on current `main`: `rkv.kv.Unmarshal` is gone since the switch to
      protobuf-go v2.
    - Its deferred `st.Close(); b.Close()` would duplicate `main`'s `defer` calls.
    - Both are resolved on the fork branch (see "Conflicts").
12. **API.** The exported `HashStorage` interface gains `HashByRevWithCompactRev` and
    `HashByRevDetailed`, so every implementation outside `mvcc` breaks. Inside etcd, only the test
    fake in `etcdserver/corrupt_test.go` (updated by the PR) implements it. This is not in the PR
    description.
13. Reviewed and correct:
    - The hash cache's new condition (`rev == h.Revision && (compactRev <= 0 || compactRev ==
      h.CompactRevision)`, `TestReviewHashCache`).
    - The server and corruption checks, unchanged (the PR's own tests pass:
      `existing-hash-tests.pr-head.log`).
    - The detailed total hash, which equals the plain one on decodable data
      (`TestHashByRevDetailedTotalMatches`).

Bugs in this run's own statements, found by the reviewer and fixed:
- The first `unsafeHashByRevDetailed` axiom claimed the result's revision fields on any error. The
  code returns `DetailedHashResult{}` on an error (`TestReviewUnsafeHashErrorFields`), so the claim
  is now made only for a `nil` error, and so is `hashByRevDetailed`'s.
- Both hashing axioms assume that the read transaction's `UnsafeForEach` returns, which
  `metaReadTx` does not specify. This is now stated in their documentation.

Open: none against the formalisation. The premises `storeCmp` and `hashRevSecOk` are the
modeling limits described under "The specs".
