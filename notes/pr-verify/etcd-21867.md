## Verdict

The PR does what its code says: the proof of `bootstrappedCluster.Finalize` over the PR's code
shows that, with a WAL and `--force-new-cluster`, the cluster is left with this node as its only
member and every other member in the removed set (in memory and in the backend). That fixes a
real, pre-existing bug the PR does not quite describe: a member that is in the backend but unknown
to the WAL gets no removal entry and becomes a raft voter, so the force-new-cluster node can never
elect itself (reproduced; `issues/etcd-force-new-cluster-stale-backend-member.md`).

**But the change breaks the normal path.** `--force-new-cluster` already appends a
`ConfChangeRemoveNode` entry for every member the WAL knows. With the PR those members are
already in the removed set when the entries are applied, so each fails validation with
`ErrIDRemoved` (proved on a model of `ValidateConfigurationChange`: `finalize_force_rejects_removal`),
logs an ERROR, and `applyConfChange` returns before `transport.RemovePeer`. When the members'
`ConfChangeAddNode` entries are still in the WAL after its last snapshot, their replay has
re-added the peers to the transport, and with the PR nothing removes them: the node keeps dialing
the dropped members (80 connections in 2 s in a 3-member test; 0 on the base) until its next plain
restart. Not merge-ready as is; a fix that keeps every removal in the log is sketched below.

Not covered: `bootstrap`, `bootstrapWALFromSnapshot`, `buildConfStateFromV3store`, the cluster's
methods and `applyConfChange` are not translated (their behavior enters as contracts, or as Go
tests); the proof depends on Goose's placeholder instances for `config.ServerConfig`'s axiomatized
field types (see the trust base).

### The spec

`Spec/go_etcd_io/etcd/server/v3/etcdserver/bootstrappedCluster__Finalize.lean`, over
`Proof/go_etcd_io/etcd/server/v3/etcdserver/InvFinalize.lean`. The membership is a record of ids,
`ClusterSt` (members, removed), held by a predicate `P` the spec quantifies over. `Finalize`
returns some error, and the membership `σ'`:
- without a WAL: unchanged;
- with a WAL: `FinalizedSt cfg.ForceNewCluster c.nodeID σrec σ'`, where `σrec` is what `Recover`
  loads from the backend: `σ' = σrec` without the flag; with it, `x ∈ σ'.members ↔ x ∈
  σrec.members ∧ x = nodeID` and `x ∈ σ'.removed ↔ x ∈ σrec.removed ∨ (x ∈ σrec.members ∧ x ≠
  nodeID)`.

There was no old spec. On the old code the post with the flag would be `σ' = σrec`, so the spec
pins exactly what the PR adds. The loop is modelled by `removeOthers` (in the order `Members()`
returns), and `removeOthers_finalized` turns it into `FinalizedSt` given that the ids are a
permutation of the members.

The consequences, pure lemmas in `InvFinalize.lean`, on `validateRemove`, a transcription of the
`ConfChangeRemoveNode` case of `ValidateConfigurationChange` with `ApplyBoth` (`cluster.go:306-389`):
- `finalize_force_rejects_removal`, `finalize_force_rejects_removal_later`: after `Finalize`
  (and at any later membership whose removed ids include those), the removal entry of a member
  other than this node is `ErrIDRemoved`;
- `base_accepts_removal`: without the PR it is valid for a member not already removed;
- `finalize_force_only_self`: with the PR the backend's members are this node at most (what fixes
  the stale-member bug, since raft's voters are built from them).

## Findings

1. **The PR leaves the transport dialing the removed members** (a regression). After
   `Finalize` puts the other members in the removed set, the force-new-cluster removal entries fail
   validation with `ErrIDRemoved` (ERROR "Validation on configuration change failed" for each), and
   `applyConfChange` returns before `s.r.transport.RemovePeer` (`server.go:2004-2016`). If the
   members' `ConfChangeAddNode` entries are after the WAL's last snapshot, their replay (with
   `shouldApplyV3 = false`, validation skipped) has called `transport.AddPeer` for them
   (`server.go:2045`): with the PR those peers stay. Tests in `notes/pr-verify/etcd-21867/`:
   - `force_new_cluster_transport_test.go`, `TestForceNewClusterStopsDialingRemovedPeers`: PR head
     fails (80 connections in 2 s to the removed members' peer addresses, 3 runs of 3); base passes.
     `...AfterSnapshot` (a snapshot covers the membership entries): both pass.
   - `force_new_cluster_restart_test.go` (the reviewer's), `TestForceNewClusterThenPlainRestartDials`:
     with the PR, 80 dials after the force restart, 0 after a following plain restart (the removal
     entries are then at or below the consistent index: validation is skipped and `RemovePeer`
     runs); base 0 and 0.
   - The existing `TestForceNewCluster` passes on both; its logs show the difference
     (`*-TestForceNewCluster-transport.log`).
   Raft itself is not affected: its `ConfState` comes from the backend (`{self}` with the PR) and
   the rejected changes are applied as no-ops.
2. **Pre-existing, fixed by the PR**: a member in the backend but not in the WAL makes
   `--force-new-cluster` unable to elect. `issues/etcd-force-new-cluster-stale-backend-member.md`;
   test `force_new_cluster_stale_member_test.go` (base: times out with raft voters `(42 self)`; PR:
   passes).
3. **The PR's description misattributes the cause.** On the base, `AddPeer` for the old members
   at startup (`server.go:437-441`, from `cl.Members()`) is normal: the removal entries undo it a few milliseconds later.
   What actually fails is only finding 2's case. The PR's unit test checks `Members()` after
   `Finalize` with an empty WAL; it exercises neither raft's voters, nor the replay, nor the
   transport.

Reviewer's open points (not reproduced):
- a crash after the PR's backend deletions are committed (the backend's periodic commit) but
  before the removal entries are applied: the backend is then ahead of the consistent index; a
  plain restart replays the removal entries above it, which fail validation as in finding 1, with
  the same transport effect until they are applied (the removal entries are in the WAL: they were
  saved before `Finalize`);
- a committed-but-unapplied `RemoveNode` of a member, above the consistent index, is rejected the
  same way (same class as finding 1);
- learners behave as voters here; a returning removed member is refused (410) with or without
  the PR, but with it this node's leaked peer keeps sending to it.

## A draft review comment (for the user to edit and post)

> Thanks for the fix. The case it addresses is real: if the backend's members bucket has a member
> that is in neither the WAL's snapshot nor its entries (the v2/v3 store inconsistency of #20967),
> `--force-new-cluster` appends no removal entry for it, `buildConfStateFromV3store` makes it a
> voter, and the node never becomes leader. An integration test that writes an extra member into
> the stopped member's backend before the force restart times out on main and passes with this PR.
>
> But removing the members in `Finalize` also changes the normal case. `--force-new-cluster`
> already appends a `ConfChangeRemoveNode` for every member the WAL knows; with this change those
> ids are already in `members_removed` when the entries are applied, so each one fails
> `ValidateConfigurationChange` with `ErrIDRemoved` ("Validation on configuration change failed"
> at ERROR) and `applyConfChange` returns before `transport.RemovePeer`. When the members'
> `ConfChangeAddNode` entries are still in the WAL after the last snapshot, replaying them has
> already called `transport.AddPeer`, so the restarted member keeps dialing the removed members'
> peer URLs until it is restarted again. In a 3-member integration test (put one key, stop member
> 0, terminate the others, restart member 0 with `ForceNewCluster`, then listen on the removed
> members' peer addresses), member 0 makes about 80 connection attempts in 2 seconds with this PR
> and none on main. The existing `TestForceNewCluster` passes either way, which is why CI would
> not catch it.
>
> Would it work to keep every removal in the log instead: pass the union of the WAL's ids and the
> backend's members to `CreateConfigChangeEnts` in `bootstrapWALFromSnapshot`? The stale member
> then gets a removal entry like the others, and raft, the backend and the transport are all
> updated by the usual apply path. (Alternatively, remove in `Finalize` only the members that will
> not get a removal entry.) A regression test along the lines above, plus one with an extra
> backend-only member, would cover both cases; the current unit test only checks `Members()` after
> `Finalize`.
