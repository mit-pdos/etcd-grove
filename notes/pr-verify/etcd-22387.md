# etcd-io/etcd#22387: client/v3: stop concurrency waits when session expires

- **PR**: https://github.com/etcd-io/etcd/pull/22387, head `31197665285b7fc8b150684868adec32fbbee02b`
  (one commit, open), base `main` at `e9e56564d`. It fixes etcd-io/etcd#19597: a `Mutex.Lock` or
  `Election.Campaign` waiting behind an older key keeps waiting after its own session's key is gone.
  `waitDeletes` now also watches the waiter's own key and returns `errWaitKeyDeleted` when that key is
  deleted. `Lock` maps that to `ErrSessionExpired` and `Campaign` maps it to `ErrElectionNotLeader`.
  `Campaign` also gains a final `Get` of its key before it returns nil.

  - `client.KV.Get` and `client.Watcher.Watch` instead of `client.Get` and `client.Watch`;

    loops.
  `Campaign`'s new `client.Get` became `client.KV.Get` in the same way.

## Verdict

**The PR does what it says, but it should not be merged as it is.** All four changed functions
are proved against specs written from the PR's intent, with no `sorry`:
- `waitDelete` and `waitDeletes` return `errWaitKeyDeleted` only when the waiter's key is absent
  from etcd at a revision at or after the start of the wait.
- `Mutex.Lock` still meets its spec from before the PR.
- `Campaign`'s spec gets stronger. It returns nil only if its key is present at the end; it can
  no longer return nil after its key was deleted (the `issues/election-campaign-key-check.md`
  bug).

**One new bug.** `Campaign`'s new existence check has an error path that leaves a phantom leader.
If the final `Get` fails (for example, the context is canceled just after the wait succeeded),
`Campaign` clears the leader session and returns the error, but it does not resign. Its key, which
has just become the leader, stays alive with the session. `Resign` then deletes nothing, and every
other candidate blocks until the session ends. A test shows this at the PR head.

**One bug only narrowed.** When another `Mutex` or `Election` on the same session deletes and
re-creates the shared key, the bug is only narrowed (`issues/mutex-lock-recreated.md`, and its
`Campaign` analogue): the wait checks only that the key exists, not its create revision. The specs
keep their `keyRecreated` case.

Not covered: liveness. The client's watch contract promises no event, so the proofs cannot show
that the wait actually ends early, which is the PR's point. Only its own tests show that.

### The specs, old and new

- **`waitDelete`** (`Spec/go_etcd_io/etcd/client/v3/concurrency/waitDelete.lean`).
  - Old: nil only after a delete event of `key` at a revision `r ≥ rev`, so `key` is absent at `r`;
    otherwise an error.
  - New: the same, with a second outcome. The function also gets `waitCh`, the channel of a
    watch of `waitKey` from `wrev`, and its consumer (`waitKeyWatch`, `InvMutex.lean`). It returns
    `errWaitKeyDeleted` only after a delete event of `waitKey` on that channel, at a revision
    `r ≥ wrev`, so `waitKey` is absent at `r`. On nil it gives the consumer back.
- **`waitDeletes`** (`.../waitDeletes.lean`).
  - Old: nil only when, at some `R ≥ lo`, no key under the prefix was created at or before
    `maxCreateRev`; otherwise an error.
  - New: the same, plus `errWaitKeyDeleted` only when `waitKey` is absent at some `r ≥ lo`. That
    absence is seen either by the first `Get` or by the watch, which starts at that `Get`'s
    revision.
- **`Mutex.Lock`** (`.../Mutex__Lock.lean`): unchanged. Its `ErrSessionExpired` case still
  promises that the key is absent at some `R ≥ lo`. The early return is proved to satisfy that
  case when `waitDeletes` returned the sentinel, and otherwise falls under "some error".
- **`Election.Campaign`** (`.../Election__Campaign.lean`).
  - Old: nil means `leaderAt` or `campaignLost` at `waitDeletes`' revision. `campaignLost` covers
    a key that is deleted, or deleted and re-created.
  - New: nil means `leaderAt`, or `keyRecreated` together with `campaignLost`, at the final `Get`'s
    revision. So a nil return now implies the key is present. It is the leader unless another
    `Election` of the same session re-created it.
  - The old spec is kept as `Election.Campaign.spec_old`. Its implication from the new one is
    proved in `Proof/.../Election__Campaign.lean` (`recreated_lost`: a re-created key of a
    well-formed state is not there with its old create revision).

## Trust base (step 7)

New, from this work:
- `errors.IsAnyErr.wp_proof` (`Spec/errors/IsAnyErr.lean`, `Proof/errors/IsAnyErr.lean`): Go's
  `errors.Is(err, target)`, for a pointer-error target and any `err`, returns some boolean. Its
  result is unconstrained, and the proofs do not depend on it.
  - Why it is needed: Perennial's `errors.wp_Is` needs the error tree of `err`, that is, specs of
    its `Is` and `Unwrap` methods. The client's contract gives no such facts about its errors, and
    neither do contexts.
  - Why it is believed: `Is` compares, then walks `Unwrap`, calling `Is` methods. It returns as
    long as those methods return. That holds for context errors, `errors.New` errors, gRPC status
    errors and `rpctypes.EtcdError`. A caller-supplied context whose `Err()` returns an error with a
    diverging `Is` or `Unwrap` method is outside the assumption.
- The package-init assumption (`concurrencyInit`, `Base.lean`, an assumption like its existing
  entries): `errLostWatcher` and `errWaitKeyDeleted` hold fixed non-nil errors, and
  `errWaitKeyDeleted`'s is a pointer error (`errors.New`).
- No new `sorry`.

Already there: the collection `etc/tcb-collections/concurrency.txt` (`fmt.SprintfNamed`,
`proto.Clone`, `status.Error`, `status.FromError`, zap). The new collection
`etc/tcb-collections/pr-etcd-22387.txt` records the PR's roots. They rest on the axioms `errors.IsAnyErr` (new), `fmt.SprintfNamed`,
`proto.Clone`, `status.Error` and `status.FromError`, and on no `sorry`. This is from
`etc/tcb-report.py` after a full `lake build` of the branch. On `lean` the same functions rest on
the same set without `errors.IsAnyErr`. `etc/tcb-baseline.txt` and the `concurrency` collection gain
that one axiom, and every other collection is unchanged. All four functions were verified before
and are verified after, so `etc/verified-code.py`'s counts for the package do not change (not
rerun).

**A limit of the specs.** `errors.Is(werr, errWaitKeyDeleted)` cannot be shown to be false for
the client's own errors: the contract allows any error value, including the unexported sentinel.
So `Lock`'s early `ErrSessionExpired` carries the key's absence only on the sentinel path, and
otherwise counts as some error. That is enough for `Lock`'s unchanged spec. A stronger spec, where
`ErrSessionExpired` is returned only when the key is gone, would need a client contract saying that
its errors are not this package's sentinel.

## Findings

1. **Bug in the PR: `Campaign`'s failed existence check leaves a phantom leader.**
   - The trigger: the new `client.Get(ctx, e.leaderKey)` after a successful `waitDeletes` fails,
     for example because the context was canceled just then, or the network failed.
   - What happens: `Campaign` sets `e.leaderSession = nil` and returns the error, but the key it
     confirmed by waiting is the oldest one under the prefix, so it is the leader. The session
     keeps it alive. The caller sees a failure. `Resign()` returns nil without deleting anything
     (`leaderSession == nil`). Every other candidate's `Campaign` blocks until the session ends.
   - Compare the other error paths. The `waitDeletes` error path resigns when the context is
     done, and `Mutex.Lock` unlocks on the same `Get`'s failure.
   - The test: `notes/pr-verify/etcd-22387/election_campaign_getfail_test.go` cancels the context
     at the second single-key `Get`. Both of its tests fail at the PR head
     (`campaign_canceled_after_wait.pr-head.log`). They skip on the base, where `Campaign` returns
     nil at that point (`.base.log`).
   - The fix: on a `Get` error, clean up as the `waitDeletes` error path does (resign if the
     context is done).
   - The proof does not exclude this, because the spec's error case is "some state". The test
     shows the consequence.
2. **Not fixed by the PR: a deleted and re-created key of the same session**
   (`issues/mutex-lock-recreated.md`, and the `Campaign` part of
   `issues/election-campaign-key-check.md`). Two `Mutex` or `Election` values on one session share
   the key `pfx/<lease>`.
   - If the key is deleted and re-created after the wait has started, the new watch on `waitKey`
     sees the delete, and the waiter returns `ErrSessionExpired` or `ErrElectionNotLeader`. That is
     an improvement: before the PR, `Lock` could return nil while another session held the lock.
     But the error is reported although the session is alive.
   - If the re-creation happens before `waitDeletes`' first `Get` (after `tryAcquire`, or after
     `Proclaim`), the `Get` finds the new key and nothing checks its create revision. The waiter
     then waits only for the keys created before its old revision and can return nil without the
     lock.
   - The specs keep the `keyRecreated` case. The issue files are unchanged; they describe the
     pinned code.
3. **Observation: a new long-lived watch.** The watch of `waitKey` lives for the whole wait and
   stays at its start revision, because the key does not change. If the watch stream reconnects
   after a compaction past that revision, it fails with `ErrCompacted`, and `Lock` and `Campaign`
   fail. The existing watch of the older key has the same exposure, so this is not new in kind.

4. **Also not fixed (reviewer): re-creation after the wait.** Mutexes A and B share session S,
   and they and C wait behind each other. When C unlocks, B's `waitDeletes` returns nil and its
   watch of `waitKey` is canceled. If, before B's final `Get`, A deletes the shared key and locks
   again (re-creating it after D's key, where D is on session U), then D gets the lock and B's
   existence-only `Get` also returns nil.
   - The same can happen inside `waitDelete`: when the predecessor's delete and the `waitKey`
     delete are both ready, `select` picks one at random, and nothing drains `waitCh` first.
   - `notes/pr-verify/etcd-22387/mutex_recreated_after_wait_test.go` fails at the PR head *and* at
     the base: this is the pinned code's `issues/mutex-lock-recreated.md`, in another schedule,
     which that issue now lists.
   - The fix there (check the create revision after the final `Get`) closes all of these windows.
5. **Behavior change (reviewer): `ErrSessionExpired` while the session is alive, now
   immediately.** A and B are on one session behind C. A's context is canceled, so its `Lock`
   unlocks and deletes the shared key. B returns `ErrSessionExpired` at once, with the lease still
   at TTL 59.
   - Before the PR, B kept waiting. It then failed the same way after C left, or returned nil if
     the key had been re-created.
   - `notes/pr-verify/etcd-22387/mutex_sibling_cancel_test.go` fails at the PR head and passes at
     the base.
   - `issues/mutex-lock-recreated.md`'s proposed fix argued for re-adopting the key instead of
     failing. Severity: low, since it is an error rather than a safety violation.
6. **The long-lived `waitKey` watch and compaction (reviewer), extending observation 3.** The
   client advances a watch's resume revision only on events or progress notifications, and none
   are requested. After a compaction and a stream reconnect, `waitCh` fails with `ErrCompacted`
   even when the current predecessor's watch is fresh. This matters when `waitDeletes` loops over
   several predecessors. `WithProgressNotify` on that watch would avoid it. No test.

Reviewer's open points on the proof itself:
- **`errors.IsAnyErr` is an assumption about the errors that reach it, not a fact of Go's
  semantics.** Like the existing `errors.IsCtxErr`, it drops two premises of Perennial's
  `errors.Is.spec`:
  - Go's typing of interface values (`TreeTyped`);
  - the error tree, whose `Is` and `Unwrap` methods must return.

  So it is false in a model where some error type's `Is` or `Unwrap` method panics. The axiom is
  quantified over every such model, which in principle threatens consistency.

  The sound fix is in the client contract: error trees for the errors that `isEtcdKV`,
  `isEtcdRangeWatcher` and the contexts return (the recipes' `clientErrIs` at `context.TODO()`
  is the precedent). Then Perennial's `errors.wp_Is` applies with no axiom. That fix is left open:
  it changes shared contract definitions that many proofs use (`notes/decisions.md`, "`errors.Is`
  of a client error").
- **The `errWaitKeyDeleted` and `ErrSessionExpired` cases promise less than they appear to.** Both
  specs have a catch-all "some error" disjunct, and `IsAnyErr` says nothing of its result. A caller
  therefore cannot conclude "the error is the sentinel, so the key is gone". The PR's claim that
  `ErrSessionExpired`/`ErrElectionNotLeader` means the key is gone lives in the doc comments, not
  in the specs (see "A limit of the specs").

## Draft review comment

> Thanks, the early exit looks right to me: `waitDeletes` returns `errWaitKeyDeleted` only after
> it has seen the waiter's own key gone, and `Lock`'s and `Campaign`'s other paths behave as before.
>
> One problem with the new check in `Campaign`. When `client.Get(ctx, e.leaderKey)` fails after
> `waitDeletes` succeeded (for instance, the context is canceled at that moment), `Campaign` clears
> `leaderSession` and returns the error, but it does not resign. At that point the key is the
> oldest under the prefix, so it is the leader, and the session keeps it alive. A later `Resign()`
> is a no-op (`leaderSession == nil`), and every other candidate blocks until the session ends. A
> test that cancels the context just before that `Get` shows both effects. Could this path clean up
> the way the `waitDeletes` error path does, resigning when the context is done (or always, as
> `Mutex.Lock` unlocks on the same failure)?
>
> A smaller point: two `Mutex`es (or `Election`s) on the same session share a key, and if it is
> deleted and re-created before `waitDeletes` takes its first `Get`, the `Get` finds the new key
> and the wait goes on as if it were the waiter's own. Checking the create revision there
> (`CreateRevision == myRev` / `leaderRev`) would close that, and would also avoid reporting
> `ErrSessionExpired` while the session is alive.
