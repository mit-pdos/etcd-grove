## Verdict

The two changes that were verified are sound, but they make no observable difference.
`syncVictimsLoop`'s spec was re-proved unchanged over the reusable timer. `Compaction` got a new
spec, and the same spec holds of the code before the PR: `KV.Range` at `RangeOptions{}` under the
trace's never-canceled context cannot fail or return nil, so the "nil pointer dereference" the PR
fixes cannot happen. The `ClientConfig` nil check guards a path that real use cannot reach either
(finding 4). The timer-leak rationale is false for this module: since Go 1.23, a `time.After`
timer that nothing references is garbage-collected (finding 2). The one real effect is a regression:
`time.NewTicker` panics on a non-positive period. A negative `--downgrade-check-time`, or a
negative gateway `--retry-delay`, now crashes etcd or the gateway at startup; before the PR it made
a loop spin (finding 1). The four untranslated functions were checked by reading the code and by
Go tests, not by proofs.

## The two verified functions

### `syncVictimsLoop`: the old spec, re-proved

Spec (`Spec/go_etcd_io/etcd/server/v3/storage/mvcc/watchableStore__syncVictimsLoop.lean`, unchanged):
with a reader slot of the store and a done token of its wait group, the loop resends the victims'
batches, waits for a tick, a new victim or the stop channel, until the latter, then calls
`s.wg.Done()`; it does not panic. The proof now goes through `time.NewTimer`, `(*Timer).Stop` and
`(*Timer).Reset` (Perennial's specs; `isTimer`: the timer's channel is a bag of times, with nothing
said about when a value arrives), the initial `if !retryTimer.Stop() { <-retryTimer.C }` (both
branches), the `Reset` on each pass with victims, and the deferred `Stop` before `wg.Done()`. No new
axiom: `time.After`'s axiom is replaced by `NewTimer`/`Stop`/`Reset`'s, all Perennial's.

What the spec does not say: it is partial correctness, and Perennial's timer model allows a timer
channel to deliver nothing, so it cannot tell a loop that waits 10 ms from one that blocks forever.
The drain `<-retryTimer.C` is such a place (see "Findings", 3): under Go 1.27's timer semantics it is
never executed, but it would block forever if it were.

### `Compaction`: a new spec, which holds of both versions

The applier's `Compaction` is outside the apply chain's model (`uberApplier.dispatch`'s premise
`dispatchOk`), so it had no spec. The new one
(`Spec/go_etcd_io/etcd/server/v3/etcdserver/apply/applierV3backend__Compaction.lean`) is stated over
`store.Compact`'s premises (the compaction right at the store's compaction revision `c`, `storeStop`,
a certified log of which the request's revision is a revision, the batch lock's hook and the
caller's critical-section contract) and a reader slot of the store. It has two outcomes:

- the compaction is scheduled (`c < rev`): no error, the right at `rev` and the caller's `Post`, the
  compaction's channel, and a fresh response whose `Header.Revision` is the store's current revision
  (the last revision of a certified log, at least `rev`), with a non-nil trace;
- `store.Compact`'s error (`ErrCompacted`, `ErrFutureRev`): that error, a nil response and trace,
  the right and `Pre` unchanged.

There is no third outcome: the range read that takes the current revision cannot fail. The proof
(`Proof/.../apply/applierV3backend__Compaction.lean`) re-proves `readView.Range` at a context never
canceled (`readView_Range_todoNow`: `EnsureTrace(context.TODO(), ...)`'s context, whose `Done()` is
`nil`; `readView.Range`'s spec takes an `isContext`, which that context is not), and shows
(`rangeOutcomeC_now`) that at `RangeOptions{}` (`Rev: 0`, the transaction's revision) with a result
the outcome is no error: `ErrFutureRev` needs `ro.Rev > rev`, `ErrCompacted` needs the read revision
below the compaction revision, which the read transaction sees as a revision of its log
(`storeTxnReadIs`: `crev < log.length`), and the context error needs a canceled context. So the
error check the PR adds is dead code, and the nil dereference it guards against cannot happen with
etcd's store (whose error returns, but for the context one, all carry a non-nil result anyway:
`kvstore_txn.go` `rangeKeys`).

The same spec was proved of the code before the PR, with the same proof file, on a worktree of
`lean` (`notes/pr-verify/etcd-22476/compaction-old-code.log`). The spec therefore does not pin down
the PR's change: nothing observable changed. Linked as `apply.applierV3backend.wp_Compaction`
(`Proof/.../apply/Link.lean`, `etc/link-lean-first-apply.txt`), printed in `apply/Results.lean`.

## Findings

1. **Regression: a negative interval now panics at startup** (the PR's bug; not in `issues/`). `time.NewTicker(d)` panics for `d <= 0`. `monitorDowngrade` special-cases only `0` (`server.go:2336`), and `--downgrade-check-time` is not validated. `embed.Config.Validate` checks only `--compact-hash-check-time`, at `config.go:1022`, so `monitorCompactHash` is safe. `runMonitor` defaults only `0` (`userspace.go:74`), and `etcd gateway start --retry-delay` is not validated (`gateway.go:77`). With a negative value, the goroutine panics and takes down the process. Before the PR, `time.After(negative)` fires at once and the loop spins, which is the existing bug recorded in `issues/etcd-negative-check-interval-busy-loop.md`. Tests: `notes/pr-verify/etcd-22476/monitor_interval_test.go` and `userspace_monitor_test.go`. Both fail at the PR head (`non-positive interval for NewTicker`) and pass at the base (`negative-interval.log`). This repository's `time.NewTicker` spec (`Spec/time/NewTicker.lean`) has `0 < d` as its premise, which is where a proof of these loops would have stopped.
2. **The timer-leak premise is false.** The module's `go` directive is 1.27. Since Go 1.23, an unreferenced timer is collected before it fires, and Go 1.27 removed `GODEBUG=asynctimerchan`. 10^6 `time.After(time.Hour)` timers abandoned in a `select` leave the heap unchanged: `time_after_gc_test.go` shows -96 KiB. The reviewer's `aftergc/` (`output.txt`) shows 96 KiB abandoned and 255 MiB kept referenced. The four `time.After` replacements fix nothing.
3. **`syncVictimsLoop`'s drain is dead code, and the spec could not tell.** Under Go 1.27, `Stop()` on the fresh `NewTimer(0)` returns true. `runtime/time.go` `timer.stop` counts a fired value it drains as pending, so `<-retryTimer.C` never runs (`timer_stop_probe/output.txt`: 0 of 100000). If it did run, it would block forever, because no value arrives after `Stop`. The reviewer also confirmed that `Reset` drains a stale value, so each pass waits a fresh 10 ms. One goroutine owns the timer, so no interleaving goes wrong. The spec is partial correctness over a timer model that says nothing about delivery. `t.Stop(); <-t.C`, which hangs forever, would pass the same proof. A spec that rules out such a hang (liveness of the victims' retry) is beyond what this repository's timer model can state.
4. **The `ClientConfig` nil check is correct but practically unreachable.** With `EmptyCN` and non-empty TLS info, `ClientConfig` first calls `baseConfig` (`listener.go:567`). Its `tlsutil.NewCert` with `tls.X509KeyPair` already fails on a file with no PEM block. The closure sees such a file only through the test-only `parseFunc`, or if the file changes between the two reads. Reviewer's test: `listener_emptycn_test.go`. With the default parser it returns `tls: failed to find any PEM data in certificate input`. With an accepting `parseFunc` it panics at the base.
5. **`Compaction`'s new error branch is dead.** Every return of `rangeKeys` carries a non-nil result except the canceled-context one, and the context here is never canceled. `compactMainRev <= currentRev` always holds (`Compact` rejects future revisions; restore raises `currentRev`, `kvstore.go:372-385`). The proof makes this argument formally. The KV is always the store: production's `*watchableStore` embeds `*store` and overrides none of `Compact`, `Range` or `Read`. Had the branch been reachable, the client would get an error for a compaction already committed and scheduled (`v3_server.go:402-420` waits on `Physc`, then returns the error).
6. **Ticker versus After: a small timing change.** A `Ticker` is fixed-rate. When the work takes longer than the period, the next check starts at once instead of one period later. This is plausible for `monitorDowngrade`: its default period is 5 s, and `CancelDowngradeIfNeeded`'s raft request can take up to the request timeout, about 7 s. It is negligible for `monitorCompactHash` (1 min). It is not a bug, but it is not "no behavioral change" either.

Bugs in existing code: `issues/etcd-negative-check-interval-busy-loop.md` (new, minor, the busy loop of finding 1; not in the verified code). No bug was found in this repository's specs or proofs. The reviewer (a fresh subagent) agreed with every claim above and has no open points.
