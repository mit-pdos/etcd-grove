## Verdict

`EnqueueUint64` does what `Enqueue` does, with a `uint64` priority. It meets `Enqueue`'s proved
spec unchanged, with no new trust assumption. For priorities below 100000 it writes exactly the
keys `Enqueue` writes, and every proved ordering result of the priority queue holds of it.

But the PR's purpose is priorities of 100000 and more, and there the key format `%05d` is no
longer fixed-width. The proof shows that both facts the queue's correctness rests on are false
from that point on, and integration tests on the PR head confirm the consequences:

1. **Wrong dequeue order.** `Dequeue` takes the lexicographically least key, so priority 100000
   comes out before 99999.
2. **Lost items.** One priority's prefix is a prefix of another's (`prq/10000` of `prq/100000/…`).
   `newSequentialKV` then computes the sequence number from the other priority's last key, and its
   put overwrites an item already in the queue. This also hits the old `uint16` `Enqueue` on a queue
   where `EnqueueUint64` was used.

The PR's own tests use priorities 0 to 2 only, so they never exercise the new range. The
nanosecond-timestamp use case works only as long as every priority on the queue has the same
number of digits, which nanosecond timestamps do between 2001 and 2286. The PR should not be
merged as is: see the draft comment below.

Not covered: the fixes suggested below are tested in Go but not verified.

### The spec, and what it does not say

- **The spec.** On `nil`, a key under `key/ ++ padZeros 5 (decimal pr) ++ "/"` was put with value
  `val` at a revision etcd has reached, computed from the state at a get revision `g ≥ lo`
  (`seqKeyPutAt`). This is `Enqueue`'s spec word for word, except for the method name and the
  type. Like `Enqueue`'s, it does not state that the key is fresh or ordered. Those facts are in
  the order results, which rest on a premise about the keys present.
- **Same keys as `Enqueue` below 2^16.** `pqPrefix_uint64_uint16` (`Results.lean:598`): equal
  values give equal prefixes.
- **Order for `pr < 10^5`.** `pqueue_enqueueUint64_order` (`Results.lean:678`) is
  `pqueue_enqueue_order`'s statement. The key is a `pqKey` with `p < 10^5`, the shape `PQKeysWf`
  requires, so the dequeue's order result `pqueue_order` covers queues filled by either function.
- **No order from 10^5 on.** It cannot be proved, because it is false:
  - `pqKey_100000_lt_99999` (`Results.lean:622`): every key of priority 100000 sorts before every
    key of priority 99999.
  - `pqPrefix_10000_prefix_100000` and `pqKey_100000_ne_seqKey_10000` (`:632`, `:640`), and from
    them `seqKeysBelow_10000_false` (`:656`): once priority 100000 has an item, the premise of the
    enqueue's order result (`SeqKeysBelow (pqPrefix key 10000) …`) is false for priority 10000. So
    nothing is proved about where that enqueue's key goes. The Go test shows it lands on an
    existing key.

The local fmt lemmas `SprintfOut_str_05d_uint64` and `IntArgValue_uniq_uint64` (in the proof file)
are proved from Perennial's `Sprintf` model in the same way as its `uint16` versions. Perennial has
only the `uint16` case. Adding the `uint64` case upstream would be a general Perennial change, not
needed here.

## Caller graph

The function is new and nothing in etcd calls it (searched across all modules of the fork
worktree), so there are no callers to re-check. The shared state is the queue's key space under
`key/`. The new function writes keys that `Dequeue` (unchanged spec; its order result needs
`PQKeysWf`) and `Enqueue` (via `newSequentialKV`'s lookup) read. Both are covered by the
counterexample lemmas above. Their specs are unchanged: they promise nothing at priorities of
10^5 and more.

## Findings

All tests are in `notes/pr-verify/etcd-18557/`; its `README.md` gives the revisions and commands.

1. **Order breaks at six digits** (PR bug).
   - `TestUint64PrQueueOrderAtSixDigits` (`v3_queue_uint64_test.go`) fails on the PR head and on the
     fork branch: after `EnqueueUint64` at 99999 and at 100000, `Dequeue` returns priority 100000.
   - The general condition is priorities `a < b` with different digit counts, `b ≥ 10^5`, where
     `decimal(a)` is not a prefix of `decimal(b)`. Examples are 20000 against 100000, or a seconds
     timestamp against a nanosecond one.
2. **Enqueued items are overwritten** (PR bug).
   - Mechanism: `newSequentialKV` looks up the last key with `Get(prefix, WithLastKey())`, a prefix
     range without the trailing `/`. For a priority `p ≥ 10^4`, the range `key/<p>` also covers
     every priority whose decimal extends `p`'s (10000 covers 100000–100009, 1000000…). Those keys
     sort last, because `/` < `0`. The new sequence number is that key's plus one. The transaction
     guards only `__key/<p>`, so the put overwrites whatever item of priority `p` has that number.
   - `TestUint64PrQueueEnqueueOverwrites`: 4 items after 5 enqueues.
   - Reviewer probes (`v3_queue_uint64_probe_test.go`): every later enqueue at that priority takes
     the same key (4 items after 6 enqueues). The old `Enqueue(val, 10000)` loses items in the same
     way on a queue where `EnqueueUint64(.., 100001)` was used.
   - Before the PR this is unreachable through priorities, because every `uint16` of 10^4 or more
     has exactly 5 digits. It is reachable only through overlapping queue names (`q` and
     `q/12345`), a misuse in which `q`'s `Dequeue` already consumes the other queue's items. Not
     recorded in `issues/`.
3. **The PR's tests** do not test the new range: they use priorities 0–2 only. Their order check
   is vacuous, because `lastPr` is never updated. The same is true of the existing
   `TestPrQueueOneReaderOneWriter` it copies (`tests/integration/.../v3_queue_test.go:108`), a
   test bug upstream (not verified code).
4. **Fixes, tested, not verified.**
   - (a) `newSequentialKV` looks up `prefix + "/"` (`newSequentialKV-slash.patch`). This finds the
     same keys of its own prefix and is backward compatible. It removes the overwrite for every
     caller and every width. The overwrite tests and the probes pass, and the existing queue tests
     still pass. The order test still fails.
   - (b) `EnqueueUint64` prints `%020d` (`enqueueuint64-020d.patch`). All four `TestUint64PrQueue*`
     tests pass. This holds only on a queue that uses `EnqueueUint64` alone: `%05d` and `%020d`
     keys neither sort by priority against each other nor, without (a), avoid the prefix
     collision.
   - Re-expressing `Enqueue` through a 20-digit format would reorder items already stored under
     5-digit keys.

The reviewer's other points are resolved above. Its open point is that neither fix is verified.
With (a), `SeqKeysBelow` would only need to constrain keys under `prefix/`, and
`seqKeysBelow_10000_false` would no longer apply.

## Draft review comment

> Thanks for this. One problem with keeping the `%05d` format for a `uint64`: it only pads to five
> digits, so priorities of 100000 and more have different widths, and the queue relies on its
> keys having one width in two places.
>
> 1. `Dequeue` takes the lexicographically first key, so `prq/100000/...` comes out before
>    `prq/99999/...`: priority 100000 is dequeued before 99999.
> 2. `newSequentialKV` finds the last sequence number with `Get(prefix, WithLastKey())`, where
>    `prefix` has no trailing `/`. For priority 10000 that range also covers priority 100000's
>    keys, which sort after its own. The new key reuses a sequence number already taken at
>    priority 10000, and the put overwrites that item. For example, enqueue three items at
>    10000, one at 100000, then one more at 10000: the queue holds four items, not five. This also
>    affects `Enqueue(val, 10000)` on a queue where `EnqueueUint64` was used with a 6-digit
>    priority.
>
> The tests in the PR use priorities 0 to 2, so they do not reach this. (Also, `lastPr` is never
> updated in `TestUint64PrQueueOneReaderOneWriter`, nor in the existing
> `TestPrQueueOneReaderOneWriter`, so the order check never fails.)
>
> Nanosecond timestamps are all 19 digits until 2286, so a queue that holds only those works. A
> fixed width would make the new function safe in general: `%020d` holds every `uint64`. The
> catch is that `%020d` keys don't sort against `Enqueue`'s 5-digit keys, so the doc comment
> should say not to mix the two on one queue. Separately, looking up `prefix + "/"` in
> `newSequentialKV` would make the sequence numbers independent of other priorities' keys, which
> is backward compatible. I have integration tests for both cases if useful.
