## Verdict

**The server change is sound and does what the PR says. The new client method does not: it is
not safe to call concurrently, contrary to its doc comment, and it panics on clients built
without credentials. Both are easy to fix.**

- **Server, proved.** The proof shows that `tokenJWT.info`, in the PR's version:
  - returns `(nil, false)`, or `(a, true)` with a read-only, non-nil auth info `a`;
  - for a verify-only provider, sets `a.Revision` to the revision it was passed, whatever the
    token's claim says;
  - meets the contract the auth store calls it through (`tokenProviderOk`). So the store's
    existing proofs (`authInfoFromToken`, `AuthInfoFromCtx`, ...) hold unchanged with a JWT
    provider of either kind.
- **Server, checked by reading the code (not proved).** The guard against auth changes between
  the token check and the request's apply is kept, exactly as for TLS common-name
  authentication (`AuthInfoFromTLS`):
  - **Writes and txns.** The request header carries the revision the token was checked at.
    `isOpPermitted` rejects the request at apply time when an auth change committed in between.
  - **Reads.** `doSerialize` compares the request's revision with the current one.
  - **Permissions.** The user's permissions are re-read from the store on every check, so
    revoked roles and deleted users are denied. The PR's `TestAuthJWTOnlySkipRevision` shows
    this end to end.
- **Server, a consequence of the design.** Auth changes now revoke nothing. A token stays valid
  until its `exp`, or forever if it has none: golang-jwt does not require `exp`. That includes a
  user deleted and re-created under the same name: the old token works again, with the new
  user's roles (finding 3).
  - This is what the PR intends: revocation moves to the token issuer.
  - It deserves a line in the documentation of `--auth-token` and in the changelog.
  - Requiring `exp` for verify-only providers (`jwt.WithExpirationRequired()`) would be worth
    considering.
- **Not covered by the proofs.**
  - What `jwt.Parse` checks (signature, `exp`) is a postulate that says nothing about either.
  - The apply-time argument above was read from the code.
  - That later RPCs use the token `UpdateAuthToken` stores is not covered: the credentials
    bundle is a contract.

## The specs

- **`tokenJWT.info`** (`Spec/go_etcd_io/etcd/server/v3/auth/tokenJWT__info.lean`, over
  `Proof/go_etcd_io/etcd/server/v3/auth/InvJWT.lean`).
  - **Precondition** (`jwtProviderRO t vo`): the provider's logger (not nil), `signMethod`,
    `key` and `verifyOnly = vo`, all read-only.
  - **Postcondition**: `authInfoRO a ∗ jwtInfoOk vo rev a ok`, that is:
    - either `ok = false` and `a = nil`;
    - or `ok = true`, `a` is not nil, and when `vo` is true, `a.Revision ↦□ rev`.
  - **The old behavior** had no spec: `jwt.go` was not translated. Its only constraint was the
    store's contract `tokenProviderOk`: some auth info, read-only.
  - **Compatibility**: the new spec implies that contract (`tokenJWT.tokenProviderOk_of`), so
    the change is compatible for the store's proofs.
  - **What pins the change down**: the revision clause. The old code returns the token's
    claim, so it does not satisfy the clause.
- **`Client.UpdateAuthToken`** (`Spec/go_etcd_io/etcd/client/v3/Client__UpdateAuthToken.lean`,
  over `Proof/go_etcd_io/etcd/client/v3/InvAuthToken.lean`).
  - **Precondition**:
    - the field `c.Token ↦ old`, owned;
    - `c.authTokenBundle ↦□ atb`;
    - `tokenBundleOk atb`: the bundle is not nil, and its `UpdateAuthToken` returns.
  - **Postcondition**: `c.Token ↦ token`.
  - **Why it cannot hold alongside the interceptor.** The verified retry interceptor holds
    `c.Token` read-only (`retryClientOk`, `InvRetry.lean`). The lemma
    `retryClientOk_excl_token` proves that the two cannot hold at once. So `UpdateAuthToken`
    cannot be called on a client with requests in flight. That is finding 1, as a theorem.

## Callers (step 6)

- **`tokenJWT.info`.** It is called only through the `TokenProvider` interface, by
  `authStore.authInfoFromToken`. Its contract there (`tokenProviderOk`) is unchanged and is met
  (`tokenProviderOk_of`), so the path stops there. The callers further up, which consume the
  revision, were read rather than proved:
  - the server's `AuthInfoFromCtx` → `processInternalRaftRequestOnce` (the header's
    `AuthRevision`) → apply (`isOpPermitted`, the lease checks in `apply/auth.go`);
  - `doSerialize` (Range, RangeStream, read-only Txn);
  - `IsAdminPermitted`, which ignores the revision.
  No change is needed in any of them.
- **`Client.UpdateAuthToken`.** It is a new exported API with no callers in etcd besides the
  test framework. It shares `c.Token` with the verified `shouldRefreshToken` (and the
  unverified `getToken`); that is finding 1.

## Trust base

`etc/tcb-report.py --collection etc/tcb-collections/pr-etcd-21909.txt`, with the roots
`tokenJWT__info` and `Client__UpdateAuthToken`.
- **`UpdateAuthToken`** rests on none of this repository's axioms and on no `sorry`.
- **`info`** rests on five axioms. Two were there already: `zap.Error` and `zap.Logger.Warn`.
  Three are new to this work:
  - `jwt.Parse.wp_proof`
    (`Proof/github_com/golang_jwt/jwt/v5/Parse.lean`).
    - **Premise**: a key function whose calls return.
    - **Result**: an error, or a token with `Claims` and `Valid` read-only. When the claims are
      a `MapClaims`, they are a read-only map of the values `encoding/json` decodes into `any`:
      nil, a string, a float64, or another type.
    - **Why it is believed**: this is golang-jwt's default parser, which decodes the claims
      with `encoding/json`. It states nothing about the signature or `exp`.
  - `auth.tokenJWT.keyFunc.wp_proof`.
    - **Statement**: the key function returns a key and an error. The function itself is a
      method comparison and a type switch on `t.key`.
    - **Why it is believed**: it cannot panic. `signMethod` is set by the constructor, and
      `Parse` fails before calling the key function on an unknown algorithm.
  - `auth.wp_convert_float64_uint64`.
    - **Statement**: `uint64(f)` of a `float64` returns.
    - **Why it is believed**: Go's conversion never panics; its value is
      implementation-defined when out of range.
    - **Why it is an axiom**: Perennial's model has no step for float-to-integer conversions.
      This is recorded as a Perennial limitation (`notes/STATUS.md`, `notes/decisions.md`),
      with the general fix to propose there.

On `lean`, these roots did not exist (`info` was not translated). `etc/tcb-baseline.txt` and
the `server` collection gain the three new axioms, and no other collection changes.

## Findings

Tests and logs: `notes/pr-verify/etcd-21909/` (README there).

1. **`UpdateAuthToken` is a data race with in-flight requests**, contrary to its doc comment.
   - **The race.** It writes the plain field `c.Token`. The retry interceptor reads that field
     on every failed RPC: `shouldRefreshToken`, retry_interceptor.go:153. `getToken` reads it
     too.
   - **Shown.** The race detector reports it at the PR head
     (`client/v3/client_update_token_test.go`, `TestUpdateAuthTokenRacesWithRetry`,
     `client-update-token-pr.log`). The proof shows the same thing as
     `retryClientOk_excl_token`.
   - **Impact.** The read only tests `Token != ""`, so in practice the race is benign. It is
     still a race the race detector flags in users' tests.
   - **The fix needs a lock or an atomic.** Simply dropping the write of `c.Token` would turn
     re-authentication back on for user/password clients (finding 2c).
2. **`UpdateAuthToken`'s unstated preconditions.**
   - **a. Panic without credentials.** It panics on a client built without a token or a user
     name and password, for example a TLS-certificate client: `authTokenBundle` is nil
     (`TestUpdateAuthTokenNoCredentialsPanics`). Such a client also dials without per-RPC
     credentials, so a token could not take effect anyway. The method should return an error,
     or document the precondition.
   - **b. Clearing the token.** `UpdateAuthToken("")` on a token client turns the token
     refresh path back on with no user name, so requests then go out unauthenticated
     (`ErrUserEmpty`). Found by the reviewer, by reading the code.
   - **c. User/password clients.** On a user/password client it sets `Token`, after which the
     client never re-authenticates on `ErrInvalidAuthToken`/`ErrAuthOldRevision`
     (`TestUpdateAuthTokenDisablesPasswordRefresh`). This is worth documenting as "for clients
     configured with `Config.Token`".
3. **A re-created user name revives old tokens.** With a verify-only provider, a token minted
   for a user (with the then-current revision and no `exp`) keeps working after the user is
   deleted and a new user of the same name is created, and it then carries the new user's
   roles.
   - **Shown.** `tests/common/auth_jwt_recreated_user_test.go`: the token gains root and can
     `RoleAdd`. The test passes at the PR head; at the base it fails, because the token is
     rejected with `revision of auth store is old`.
   - **Nature.** This follows from the design and is not a code bug, but the PR should
     document it: revocation is now only by `exp` (or rotating the key).
4. **The `revision` claim is still required.** It must be a JSON number, or `info` fails, even
   though its value is now ignored. The PR description's "hardcode 1 (or any value)" should say
   "any number".
5. **In-flight requests across an auth change still fail once.** A request in flight across any
   auth change, even one unrelated to its user, still gets `ErrAuthOldRevision` at apply time.
   Static-token clients do not retry it (`shouldRefreshToken` is false when `Token != ""`).
   - This is the same as for TLS clients, and far better than before.
   - It qualifies the PR's "prevents sudden client disconnections": the errors become
     transient but can still reach the caller.
6. **Before the PR (existing behavior, not a bug).** A verify-only token whose revision claim is
   above the current revision passes `isOpPermitted`'s `<` check, so its writes never go stale.
   Its reads still fail, because `doSerialize` checks `!=`. Issuers therefore could not already
   get the PR's behavior that way. No issue is recorded.

No bug in the pinned code was found, so nothing was added to `issues/`.

### Open points from the review

- **`info`'s spec is partial.** It does not say that the user name comes from the token, or
  that a token with a stale claim is accepted. `Parse`'s postulate says nothing about the
  claims' contents, so neither can be stated without strengthening it.
- **The new property is not used downstream.** No proof downstream uses the new revision
  property: `tokenProviderOk` mentions no revision, and the apply-time check is unproved.
- **The bundle is a contract.** `tokenBundleOk` is a contract: `client/v3/credentials` is
  translated names only.

## Draft review comment

> The server change looks right to me. Using `as.Revision()` for verify-only tokens keeps the
> apply-time check (`isOpPermitted` still compares the header's revision with the store's, and
> `doSerialize` does the same for reads), so it matches TLS common-name auth. Two things worth
> stating in the docs/changelog: auth changes no longer invalidate verify-only tokens at all, so
> revocation is only by `exp` (and golang-jwt does not require one: maybe use
> `jwt.WithExpirationRequired()` for verify-only), and a token for a deleted user works again if
> a user of the same name is re-created, with that user's roles. Also, the `revision` claim
> still has to be present and numeric.
>
> On `Client.UpdateAuthToken`: it is not safe to call concurrently as the comment says. It
> writes `c.Token` while `shouldRefreshToken` (retry_interceptor.go) and `getToken` read it, and
> `go test -race` reports it. It also panics when the client was created without `Token` or
> `Username`/`Password` (`authTokenBundle` is nil), and on a username/password client it
> silently disables re-authentication. Maybe guard `Token` with a mutex (or an atomic), return
> an error when there is no bundle, and document that it is meant for clients configured with
> `Config.Token`. A test that reproduces the race is easy to write (call `UpdateAuthToken` in
> one goroutine and `shouldRefreshToken` in another).
