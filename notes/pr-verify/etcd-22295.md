## Verdict

The fix is correct. Whatever members `chooseAll` retires from the temporary group, `choose` now
also retires from the group it chose from, exactly those and no others. A member whose
compaction response could not be sent (full channel) stays in the unsynced group and is retried
on the next sync. This is proved in Lean of the PR's `choose` (`mvcc_watcherGroup_choose_compact`):
no new axioms and no `sorry`s. The Go tests (the PR's, and the reviewer's mixed test) fail at the
pinned base and pass with the PR.

Two limits on what is proved:
- The result is relative to an abstract statement of what `chooseAll` retires
  (`chooseAll.specG`, a hypothesis of the theorem, not an axiom). The only proved instance of it
  retires nothing. The compaction branch of `chooseAll` (the response send, the `compacted` flag)
  stays outside the verified store, which is verified as never compacted (`notes/decisions.md`).
- So the store-level effect (no duplicate compaction responses through `syncWatchers`) is shown
  by tests, not by the proof.

One small behaviour change, not reachable: with a negative `maxWatchers`,
`make([]*watcher, 0, maxWatchers)` now panics, where the old code returned an empty group. The
only caller passes `maxWatchersPerSync` (512).

### The specs

- **Old** (`Spec/go_etcd_io/etcd/server/v3/storage/mvcc/watcherGroup__choose.lean`,
  `mvcc.watcherGroup.choose.spec`): of a group `W` none of whose members is below `compactRev`,
  `choose` returns the group itself (`len < maxWatchers`) or a fresh group of `max 0 maxWatchers`
  members, `wg` unchanged, with their least `minRev`. On this branch it gains the premise
  `0 ≤ sint.Z maxWatchers`, and that is its only change. It is needed because the PR's
  `make(..., 0, maxWatchers)` panics on a negative capacity
  (`notes/pr-verify/etcd-22295/watcher_group_choose_negative_test.go`).
- **New** (same file, `mvcc.watcherGroup.choose.specC`): for any `Ok`/`P`/`Q` for which `chooseAll`
  meets `chooseAll.specG curRev compactRev Ok P Q`:
  - `specG` says: from a group `W` with `Ok W`, holding `P`, `chooseAll` keeps some `K ⊆ W` and
    gives `Q W K m` (`Spec/.../watcherGroup__chooseAll.lean`).
  - In the uncapped branch, `wg` ends at the `K` that `chooseAll` kept.
  - In the capped branch, the fresh group of `maxWatchers` members `W' ⊆ W` ends at `K ⊆ W'`, and
    `wg` ends at `retireChosen W W' K`: `W` without the members of `W'` that `K` lacks
    (`Proof/.../mvcc/InvWatchBatch.lean`).

  The old code meets this only when `K = W'`, that is, when nothing was retired. The Go tests show
  the difference: at the base, the retired watchers stay in the unsynced group.

  `wp_proof` derives the old spec from `specC`, instantiated at `chooseAll.spec_G`, where nothing
  is retired, so `retireChosen W W' W' = W`.

## Findings

1. **The bug the PR fixes, in the pinned code**: recorded as
   `issues/etcd-watch-choose-capped-compacted-stays-unsynced.md`. In `choose`'s capped branch, a
   watcher that `chooseAll` retires with a compaction response stays in the unsynced group, and
   every later resync sends it the response again. The PR's test fails at `09669450f` (expected 0
   unsynced, actual 2) and passes with the PR
   (`notes/pr-verify/etcd-22295/watchable_store_test.go`, `base-09669450f-compacted-capped.log`,
   `prhead-2219f4914.log`). The proof confirms the fix at the `choose` level, as above.
2. **Negative `maxWatchers` now panics (remark, not reachable)**:
   `notes/pr-verify/etcd-22295/watcher_group_choose_negative_test.go` passes at the base and panics
   at the PR head (`makeslice: cap out of range`). The only caller passes 512, and the variable is
   changed only by tests.
3. **Reviewer, no bug found.** I asked a fresh reviewer to look for a case where the PR goes wrong.
   It checked these cases:
   - `selected` has no duplicates (it comes from a map range);
   - every `wg.delete` is of a member;
   - full-channel watchers are retried;
   - `syncWatchers` no longer sees retired watchers;
   - `cancelWatcher` cannot interleave (both hold `s.mu`); for a retired watcher it takes the
     `wa.compacted` branch and decrements `watcherGauge` once;
   - `slowWatcherGauge` is reset by `Set` on every sync.

   Its test `notes/pr-verify/etcd-22295/watcher_group_choose_capped_mix_test.go` (capped,
   compacted, live and full-channel watchers mixed) passes at the PR head and fails at the base.
4. **Open (reviewer)**: as the verdict says, `specC` adds something over the old spec only through
   a `chooseAll.specG` instance that retires watchers, and none is proved yet. Proving one needs a
   statement of the compaction send on the watcher's channel. That is the next step if the
   watchable store is ever verified with compaction.

## Draft review comment

> The change looks right to me. After `ret.chooseAll`, every watcher in `selected` that is no longer
> in `ret.watchers` is one `chooseAll` retired: it sent the compaction response and deleted it from
> `ret`. Deleting exactly those from `wg` makes the capped branch behave like the uncapped one.
> Watchers whose send hit a full channel stay in both groups and are retried, as before.
> `selected` comes from a map range, so there are no duplicates, and each `wg.delete` is of a
> current member. I also tried a mix in the capped branch (compacted, live, and a compacted watcher
> with a full channel, then cancelling all). Every compacted watcher gets exactly one response, and
> `watcherGauge` and `slowWatcherGauge` end where they started; before the change the compacted
> watchers stay unsynced.
>
> One small thing: `make([]*watcher, 0, maxWatchers)` panics if `maxWatchers` is negative, where
> `choose` used to return an empty group. Nothing passes a negative value today
> (`maxWatchersPerSync` is 512), so this is only a note. `make([]*watcher, 0, max(maxWatchers, 0))`
> would keep the old behaviour, if you care.
