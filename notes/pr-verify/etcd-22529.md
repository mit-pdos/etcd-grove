## Verdict

The change is correct and safe as far as it was checked. In Go the store comes after the KV,
lessor, auth store and cluster have been restored, and before `applyAll` triggers `applyWait`.
Neither value can go backwards: the code panics unless the snapshot index is above
`ep.appliedi`, and the snapshot's term is at least the term of any entry already applied. So a
reader that sees the new `AppliedIndex()` and skips waiting reads an already-restored KV.

In the proof, the applied index's invariant, which every linearizable read relies on, was
generalized to allow the jump. The PR's store was proved to preserve it and to bring the apply
thread's ghost index back in line with `ep.appliedi`. The old code leaves the two apart, which is
exactly the bug. All of the server's existing results re-build unchanged.

What is **not** proved:
- the rest of `applySnapshot`'s snapshot path (backend open, restores, transport). The verified
  apply loop still assumes raft hands it no snapshot.
- liveness, i.e. that proposals stop being rejected, which no spec here states.
- the term (`setTerm`'s spec says nothing about the value stored).

The PR misses the same gap on restart: `run()` sets `ep.appliedi` from the stored snapshot but
leaves `s.appliedIndex` at 0. There it is only transient.

### The spec change

- **Old** `srvAppliedPre γr v v' L` (`setAppliedIndex`'s precondition): the apply thread holds the
  ghost index at `v`, has deposited `L` as the log applied through `v'`, and `v' = v + 1`.
  **New**: the same, with `v < v'`. The invariant's `appliedKeysOk` (InvRequest.lean) changes
  with it: while a deposit is pending, its key is the unique key above `v` (instead of "is
  `v + 1`").
- Statements: `Proof/go_etcd_io/etcd/server/v3/etcdserver/InvRequest.lean` (`appliedKeysOk`,
  `appliedMonoMap_insert`, `srvAppliedPre`, `srvAppliedPre_of_succ`, `applied_predeposit_gt`,
  `applied_predeposit` now its `v + 1` corollary), and
  `Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__setAppliedIndex.lean` (the statement is
  unchanged; only its predicate weakened).
- **Readers are not weakened.** The invariant never said "every index up to `v` has a log", and
  no reader assumes it:
  - the read loop and `KVRead` take the log at the current index, with mvcc's certificate;
  - `getAppliedIndex` gives only a lower bound;
  - monotonicity looks up only keys that exist.

  Indices inside the jump simply never get a log. Publishing still requires mvcc's certificate
  for the published log and `kvLogAt` (the KV model of the committed raft log through that
  index), so a proof still cannot publish an index whose KV is not there.

### The PR's store: `EtcdServer.applySnapshot.publish_ok`

In `Proof/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__applySnapshot.lean`.

- **Premises**:
  - `s.setAppliedIndex(si)` with `ai < si`;
  - the apply thread's half at `ai` with its log `L₀`;
  - `kvLogAt γr si Ls` and `L₀ <+: Ls`;
  - `mvcc.idxCert E.γ.idx Ls`, the KV restored to the snapshot's log.
- **Conclusion**: `srvAppliedOwn γr si ∗ appliedAtLeast γr si ∗ appliedLogAt γr si Ls`.

That conclusion is what `srvApplyRes` (InvApplyAll.lean) and the next `applyEntries` require
alongside `ep.appliedi ↦ si`. The old code leaves the half at `ai` while `ep.appliedi = si`. It
cannot satisfy the next entry's `applied_predeposit` (`m.index = ai + 1` fails at `si + 1`), so
the apply loop's invariant `s.appliedIndex = ep.appliedi` breaks after a snapshot.

`publish_ok` is not linked (no linked spec covers the snapshot path). Its premises are what the
unverified code before the store must establish; that it does is argued from the Go order, not
proved.

## Findings

1. **The bug the PR fixes is in the pinned code.** Recorded in
   `issues/etcd-snapshot-applied-index-stale.md`. The PR's test fails without the fix
   (`notes/pr-verify/etcd-22529/base.log`) and passes with it (`pr-head.log`). The proof confirms
   the fix restores the apply loop's `s.appliedIndex = ep.appliedi` (`publish_ok`), modulo the
   unverified restore premises.
2. **Restart, not covered by the PR.** `run()` initializes `ep.appliedi`/`ep.appliedt` from the
   raft storage snapshot but leaves `s.appliedIndex`/`s.term` at 0 until the first entry after
   it is applied. The reviewer's `notes/pr-verify/etcd-22529/review_restart_test.go` shows the
   zeros, and that the first applied entry repairs them.
   - In that window the first `Ready` raises `committedIndex`, so proposals can be rejected and
     `Status` reports 0.
   - It is transient (publish retries), so it is a suggestion for the PR, not a blocker. Recorded
     in the same `issues/` file.
3. **"Forever" is slightly overstated.** Any write applied through another member un-sticks the
   new member. The state persists only while all writes go through it.
4. **For this repository's notes** (`notes/STATUS.md`, "etcd-io/etcd#22529"): a future spec of
   the snapshot path will need `kv.Restore` to keep mvcc's index ghost (`E.γ.idx`) growing from
   `L₀` to `Ls`, although Restore rebuilds the tree index. The modelled start (`isServerBuilt`)
   holds only for an applied index of 0, i.e. not for restarts.

The reviewer (a fresh subagent) agreed the ghost generalization is sound and that readers are not
weakened. It found no bug in the PR's two lines. Its other points are findings 2–4 and the
not-proved items in the verdict.

## Draft review comment

> The change looks right to me. The new stores come after `kv.Restore`, the auth/cluster
> recovery and the `bemu` unlock, and before `applyAll` triggers `applyWait`. So a linearizable
> read that sees `AppliedIndex() >= readIndex` and skips the wait already reads the restored KV.
> Neither value can go backwards: a snapshot at or below `ep.appliedi` panics earlier, and the
> snapshot's term is at least the last applied entry's.
>
> Two small things you may want to consider:
> - The same gap exists on restart. `run()` initializes `ep.appliedi`/`ep.appliedt` from the
>   raft storage snapshot, but `s.appliedIndex`/`s.term` stay 0 until the first entry after it
>   is applied. In that window `Status` reports 0, and once the first `Ready` raises the
>   committed index, proposals (including `publishV3`'s first attempts) can be rejected with
>   "too many requests". It is transient, but setting both in `run()` after building `ep` would
>   make the invariant "appliedIndex == ep.appliedi" hold everywhere.
> - #22510 makes the same change; the two could be merged into one PR with both tests.
>   Release-3.6 and release-3.5 have the same code, if a backport is wanted.
