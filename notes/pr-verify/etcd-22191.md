## Verdict

The PR fixes the panic it is about: no response is sent on the `recvc` of a substream the server
canceled, so a progress broadcast can no longer panic with "send on closed channel". This is
machine-checked: `run`'s complete proof (no `sorry`) covers exactly this code, since the
translation of the PR is byte-identical to that of the pinned code, which already had the same
fix. But that proof assumes that the gRPC stream never fails with a retryable error, so it does
not cover reconnecting. On that path the change introduces a new bug: the removed substream keeps
its watch id, and after a reconnect it deletes another watch that the new stream gave the same id.
That watch then loses its events or has its channel closed silently, and `Close()` can hang.
Reproduced with an etcd-like fake server (8 of 300 trials) and a scripted one (23 of 200); a one-line
addition fixes it. The PR's unit test also does not test the fix: it passes
without it.

## Findings

1. **New bug on the reconnect path, introduced by the change, also in the pinned fork code**:
   `issues/etcd-watch-canceled-substream-stale-id.md`. After the `Canceled` case removes watch A
   from `substreams`, A keeps its `id`. A retryable stream error before `run` takes A from
   `closingc` makes `newWatchClient` resume the other watches, and their ids restart at 0 on the new
   server stream. Watch B can then get A's id. `closeSubstream(A)` then deletes
   `substreams[A.id]`, which is now B, and the `closingc` case either sends a cancel for B's id or,
   B being the last watch, returns. In the second case `run`'s teardown waits on B's goroutine,
   which blocks on `closingc`: `Close()` hangs. In the first, a stale cancel request that reaches the
   new stream after B's create makes the server cancel B: B's channel closes silently. Tests:
   `notes/pr-verify/etcd-22191/watch_stale_id_etcdlike_test.go` (the reviewer's, an etcd-like fake
   server and the realistic trigger: the user cancels A with an event in flight; at the PR head 6
   of 300 trials lose B's event and hang `Close()`, 2 close B silently, `etcdlike-at-pr-head.log`;
   with the fix 0, `etcdlike-with-suggested-fix.log`) and
   `notes/pr-verify/etcd-22191/watch_cancel_reconnect_test.go` (a scripted server; 23 of 200 trials
   lose B's event and hang `Close()`, `reconnect-at-pr-head.log`). With
   `notes/pr-verify/etcd-22191/suggested-fix.diff` (`ws.id = InvalidWatchID` after the `delete`)
   0 of 200, and the package's tests pass (`reconnect-with-suggested-fix.log`). Without the PR,
   the same scenario panics instead (`reconnect-at-base.log`,
   `issues/etcd-watch-resume-closing-substream.md`, which the PR's change also removes, without
   saying so).
2. **The PR's test does not cover the fix**: `TestBroadcastResponseSkipsRemovedSubstream` builds a
   `watchGRPCStream` whose map never held the canceled substream and calls `broadcastResponse`. It
   never runs `run`'s `Canceled` case, and passes at the base without the fix
   (`notes/pr-verify/etcd-22191/pr-test-at-base.log`). A regression test that does fail without the
   fix is the fork's `TestWatchProgressBroadcastAfterServerCancel`
   (`notes/pr-verify/etcd-22191/watch_progress_cancel_test.go`: panics at the base,
   `progress-cancel-at-base.log`, passes at the PR head). The test file also adds a second blank
   line before the test, which `gofmt` rejects.
3. **Bug the PR fixes, recorded in `issues/`**: `etcd-watch-progress-closed-substream.md`. Confirmed:
   the proof of `run` over this exact code establishes that nothing is sent on a closed `recvc`,
   under the premise above.

## Reviewer

A fresh reviewer subagent checked the PR, the coverage claim and the findings. Its conclusions:
- the fix removes the broadcast panic; the teardown still collects the canceled substream through
  `closing`. The coverage claim holds: the pin differs from the PR's `watch.go` only in that
  comment and two existing Goose rewrites.
- finding 1 is confirmed against an etcd-like server. The reviewer's
  `watch_stale_id_etcdlike_test.go` corrected the scripted test's unfaithful parts: etcd sends no
  unsolicited `Canceled`, and no event for an id that was never created. It found the
  silent-close variant. The suggested fix is correct and complete for it: with the id invalid,
  `closeSubstream` scans `resuming`, where the substream is not, and `serveSubstream` never reads
  `ws.id`.
- refuted as problems: the early `return` while the canceled substream is still in `closing`
  (the teardown drains it); the redundant cancel request without a reconnect (harmless, as at the
  base); a `Canceled` for an id in `resuming` (not in the map).
- **open, not reproduced**: a narrower hang the suggested fix does not cover. It needs a
  `Canceled` for a substream whose goroutine is still alive. etcd's server never sends that; the
  gRPC proxy forwards backend cancels and may. `run` closes `recvc` and drops the substream; a
  stream failure then closes `resumec`; the goroutine may take that case and exit as resuming,
  without the `closingc` send. It is never restarted, and the teardown's `closing` drain waits
  forever. Recorded under "Related" in `issues/etcd-watch-canceled-substream-stale-id.md`.

>    with a retryable error (`Unavailable`) before `run` takes the substream from `closingc`,
>    `newWatchClient` resumes the remaining watches on a new stream, where watch ids start again at
>    0, so another watch can get the canceled one's id. When `run` then takes the canceled substream
>    from `closingc`, `closeSubstream` does `delete(w.substreams, ws.id)` and removes the *other*
>    watch. Either it sends a cancel request for that id, so the watch stops getting events and its
>    channel is never closed, or, if that was the last watch, `run` returns and its teardown blocks
>    in `w.wg.Wait()` forever, so `Close()` hangs. With a fake `WatchClient` that numbers watches
>    per stream from 0 and answers cancel requests the way etcd does, I reproduce it in a few
>    percent of trials. The setup: cancel watch A's context while an event for it is in flight, then
>    fail the stream with `Unavailable` after the server's `Canceled`. Watch B resumes with id 0
>    and either loses its events, or has its channel closed by the stale cancel, and `Close()`
>    can hang. Clearing the id as well fixes it:
>
>    ```go
>    delete(w.substreams, pbresp.WatchId)
>    ws.id = InvalidWatchID
