## Verdict

The change is correct and safe as far as it was checked, for the same reasons as #22529. The
store comes after the KV, auth and cluster restores and before `applyAll` triggers `applyWait`.
Neither value can go backwards. The proof shows the store restores the apply loop's invariant
`s.appliedIndex = ep.appliedi`, which the old code breaks after a snapshot. Not proved, as for
#22529:

- the rest of the snapshot path (the restore premises of `publish_ok`);
- liveness, i.e. that proposals stop being rejected;
- the value of the term.

The PR also leaves the restart gap open.

## Differences from #22529 (outside the code)

- **Test.** `TestApplySnapshotUpdatesAppliedIndex` writes a real snapshot DB with
  `snapshotter.SaveDBFrom` at index `2*maxGap+1` (10001). It feeds raft a `Ready` with that
  snapshot and waits on `ApplyWait`. Then it checks `AppliedIndex()`/`Term()`, and that a `Put`
  is *proposed to raft* rather than rejected with `ErrTooManyRequests`.
  - #22529's test instead gets its snapshot through `newSnapTransporter` and renames the file.
    It checks `getAppliedIndex`, `getTerm` and `getCommittedIndex` (term 7 rather than 1).
  - #22510's test checks the symptom users see, the rejected proposal, directly; #22529's does
    not. #22529's also checks the committed index, and uses a term other than 1, which tells
    the snapshot's term apart from a default.
  - Both fail on the pinned base and pass with the fix. For #22510: `base.log` (index 0 vs
    10001, term 0 vs 1, and `ErrTooManyRequests`) and `pr-head.log`. The whole `etcdserver`
    package's tests pass on the fork branch with the PR's test.
- **Comment.** #22510's comment ("Proposals are admitted against appliedIndex. Leaving it at the
  pre-snapshot value rejects them until a later entry is applied.") is accurate and
  understated. #22529's says the rejection can last "forever", which overstates it: a write
  applied through another member clears it.
- **Description.** It says the index never moves backwards because "applySnapshot returns early
  for a snapshot at or below the current applied index". In fact it **panics** there
  (`lg.Panic("unexpected leader snapshot from outdated index")`, server.go:1026). The
  conclusion stands. The claim that linearizable reads are unaffected (they fall back to
  `applyWait`) agrees with the proof: readers take only a lower bound from `getAppliedIndex`.
- **CHANGELOG.** Neither PR adds an entry. The bug is also on `release-3.6` and `release-3.5`.
- **#22527** (`publishV3` retry, branch `pr-verify/etcd-22527`) depends on this fix in the same
  way as on #22529's, since the code is the same.

## Draft review comment

> The change looks right to me. The two stores come after the KV/auth/cluster restores, and
> before `applyAll` triggers `applyWait`. So a read that sees the new `AppliedIndex()` and skips
> the wait already reads the restored KV.
>
> Small things:
> - The description says `applySnapshot` returns early for a snapshot at or below the applied
>   index. It panics there (`unexpected leader snapshot from outdated index`). The conclusion,
>   that the index never moves backwards, still holds.
> - The same gap exists on restart. `run()` sets `ep.appliedi`/`ep.appliedt` from the raft
>   storage snapshot, but `s.appliedIndex`/`s.term` stay 0 until the first entry after it is
>   applied. In that window `Status` reports 0, and proposals can be rejected once the first
>   `Ready` raises the committed index. It is transient, but setting both in `run()` would close it.
> - #22529 makes the identical change. Its test also checks the committed index and a term other
>   than 1, and this one checks that the proposal reaches raft, so the two could be combined into
>   one PR with both tests.
