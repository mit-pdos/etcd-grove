## Verdict

The change does what the PR says, and the proofs show it: with the fallback to `Keep(compactRev)`,
`HashKV` never hashes a revision the running compaction may delete, so its value no longer depends
on how far the compaction has gone (`hashIncl22515_not_del`, given that the compaction revision does
not delete a key and put it again, which the API forbids: `issues/etcd-compaction-delete-then-put.md`),
and on what a finished compaction leaves in the bucket the new filter is the pin's
(`hashIncl22515_compat`), so the hash after a compaction is unchanged and members of mixed versions
agree. Both code-level steps (`kvHashIncludes` with `exactKeep`, `hashByRevKeep`) are proved with no
new axioms or `sorry`s, and their composition is the filter the theorems are about
(`hashByRevKeep_filter`). The reviewer's randomized tests agree: finished-compaction hashes
identical to the pin's over 3000 histories, no progress dependence (0/3000, and 0/300 under a real
concurrent compaction, where the pin fails 1037/3000 and 78/300). **What the PR does not fix**:
`HashKV(rev)` and the hash the compaction at `rev` stores for the same revision and compact revision
still differ when `Keep(rev)` is empty and `Compact(rev)` is not (`hashIncl22515_keep_compact_differ`;
symptom 1 of `issues/etcd-hash-empty-keep.md`, which `CompactHashCheck` compares). That is not a
regression (same at the pin) and the PR does not claim it; #22562 fixes it but changes the
finished-compaction hash instead, so the two PRs trade one property for the other. Not covered:
the crc32 hasher (trust boundary, as before), `hashByRev`'s locking and loop, `unsafeHashByRev` and
the compaction job's loop (not linked to the filter theorems), and two compactions queued at once
(argued and tested, not stated).

## The behavior change

All in `Proof/go_etcd_io/etcd/server/v3/storage/mvcc/HashFilter.lean`, last section, over the model
of the key index (`kiKeep` = `keyIndex.keep`, `kiAvail` = what `keyIndex.compact` keeps;
`keepOfIs`/`keepSetIs` the proved results of `treeIndex.Keep`/`treeIndex.Compact`):

- **Old** (`hashInclOld`): a pair of revision `r` is hashed when `r.main ≤ rev`, and, if `r.main ≤ c`,
  `keep` keeps `r` **or `keep` is empty**, and `r` is not a tombstone at `c`; `hashByRev` passes
  `Keep(rev)`.
- **New**: the hasher's filter is `hashInclF` (the old one, but with the flag
  `exactKeep || len(keep) > 0` in place of "keep not empty"), and `HashKV` hashes with
  `hashIncl22515`: `Keep(rev)` if it keeps something (the old filter); otherwise, if `c > 0`,
  `Keep(c)` applied though empty; otherwise the old filter. `hashByRevKeep_filter` proves that
  `hashByRevKeep`'s spec followed by `kvHashIncludes`'s computes exactly this.
- Incompatible as a filter (it differs from the old one while a compaction is running), but by
  design not at the exported API after a compaction finishes:
  - `hashIncl22515_not_del` (and its lifting to a bucket, `hash22515_filter_del`): no pair that
    compaction at `c` may delete (`KeyDel`) is hashed, so `HashKV` does not depend on how far the
    compaction has gone. Premises: `NoDelPutAt log c` (revision `c` does not delete a key and put it
    again; without it compaction deletes a live revision, `issues/etcd-compaction-delete-then-put.md`),
    and `0 < c` or `Keep(rev)` non-empty (with `c ≤ 0` and nothing kept the PR changes nothing; etcd
    stores nothing at revision 0). The proof generalises #22562's `hashIncl_not_del` to a kept set
    taken at any revision at or above `c` (`hashIncl_not_del_at`).
  - `hashIncl22515_compat`: on every pair a finished compaction leaves in the bucket (at or below `c`,
    a revision compaction kept, `keepAt log c`; each pair the log's event of that revision with its
    tombstone mark), the new filter is the old one. So a member with the PR and one without agree
    after the compaction. The one case that needs care, a revision with main `c` that `Compact(c)`
    keeps but `Keep(c)` does not, is a tombstone ending a generation (`kiKeep_of_kiAvail_ntomb`), which
    both filters skip.
  - When `Keep(rev)` is not empty, or `c ≤ 0`, the filter is the old one by definition.

What it does not do (`hashIncl22515_keep_compact_differ`): `HashKV(rev)` and the hash the
compaction job at `rev` stores for the same `Revision` and `CompactRevision` still differ when
`Keep(rev)` is empty and `Compact(rev)` is not (a key put at 2, compact 2, deleted at 3:
`HashKV(3)` falls back to `Keep(2)`, which keeps the put at 2, and hashes it; the job at 3, with the
flag unset and `Compact(3)` = the tombstone, does not). This is symptom 1 of
`issues/etcd-hash-empty-keep.md`, which #22562 fixes and this PR does not claim to.

The theorems are about the filter: the hasher is opaque, so no proved function's result says what
is hashed, and `hashByRev`'s and the compaction job's loops over the bucket are not linked to them.

## Findings

1. **Bug at the pin, symptom 2 fixed by the PR** (`issues/etcd-hash-empty-keep.md`, #22517): `HashKV`
   depends on a running compaction's progress when `Keep(rev)` is empty. The PR's
   `TestHashByRevAcrossPhysicalCompaction` (`notes/pr-verify/etcd-22515/hash_physical_compaction_22515_test.go`)
   fails at the pin and passes with the PR; the reviewer's `TestR22515Progress` and
   `TestR22515Concurrent` (`notes/pr-verify/etcd-22515/hash_review_22515_test.go`) fail 1037/3000 and
   78/300 at the pin and 0 with the PR. The proof confirms the fix (`hashIncl22515_not_del`).
2. **Symptom 1 not fixed** (not a regression, not claimed): `HashKV(rev)` vs the compaction job's
   stored hash of `rev` (`hash_empty_keep_test.go`, `TestR22515Symptom1`: `0x53cd23ab` vs
   `0xb08e9997`, same at the pin; the #22562 reviewer's `TestReviewHashProgressAndRestart` fails
   164/3000 at the PR head, every failure this one). `CompactHashCheck` (gate, alpha) compares
   exactly these, so a follower that has not applied the compaction at `rev` yet can still be
   reported as corrupt.
3. **The hash after a finished compaction is unchanged** (the PR's claim): proved
   (`hashIncl22515_compat`) and tested (`TestR22515Dump`: pin and PR dumps byte-identical over
   3000 random histories, `hash_review_22515.log`). This is what #22562 gives up.
4. **Concurrency** (reviewer, from the code; not proved): the premise of `hashByRevKeep`'s spec (the
   index compaction revision at or below `compactRev`, at or below `rev`) holds: `hashByRev` holds
   `s.mu.RLock` across both `Keep` calls, `store.Compact`/`Restore` take `s.mu.Lock`, and a job only
   compacts the index at a revision `updateCompactRev` already recorded. A job running concurrently
   on the index does not change `Keep` at or above its revision (`treeIndex.Keep`'s spec). Restart
   mid-compaction: 0/3000 failures (`TestReviewHashRestartMidCompaction`).
5. **Two compactions queued** (the job for `c0` still deleting while `compactRev` is `c1`): not stated
   as a theorem; it follows from `hashIncl_not_del_at` at `c0` with the kept set at `c1 ≥ c0` and
   `NoDelPutAt` at `c0`. Tested: no progress failures in `TestReviewHashProgressAndRestart` at the PR.
6. **#22515 vs #22562.** Both fix symptom 2. #22562 also fixes symptom 1 but changes `HashKV`'s value
   after a finished compaction when nothing is kept at `rev` and something at or below the compact
   revision is stored (#22515's test case "every key deleted after the compact revision" fails on
   #22562), a false-corruption risk for the opt-in checks during a rolling upgrade. #22515 keeps
   that value and leaves symptom 1. No filter keeps every value older versions compute and fixes
   symptom 1, since at the pin the two hashes already disagree there; one option (untested, in the
   issue file) is to change only the compaction job's stored hash to `HashKV`'s, on top of #22515.
7. **The PR's test** compares the hash after `scheduleCompaction` with hard-coded values from older
   versions and the hash between `updateCompactRev` and the deletion; it does not exercise a
   partial deletion (some batches done) or a concurrent compaction, which the reviewer's tests add.
8. Reviewer's open points: none against the formalisation. As for #22562, `hashByRev`,
   `unsafeHashByRev`, the opaque `WriteKeyValue` axiom and the job's loop are not linked to the
   filter theorems, so the step from "the filter" to "the hash" is by reading the code.

No bug in the existing code was found beyond `issues/etcd-hash-empty-keep.md` (copied from
`pr-verify/etcd-22562` and extended with this branch's results).

## Draft review comment

> Thanks, this looks right to me. With an empty `Keep(rev)` the hasher filters nothing, so the
> revisions a running compaction has not deleted yet are hashed; falling back to
> `Keep(compactRev)` filters exactly what the compaction will delete, and nothing it keeps (below
> `compactRev`, `Keep(compactRev)` and what `Compact(compactRev)` keeps are the same set, except a
> tombstone at `compactRev` ending a generation, which the hasher skips anyway), so the hash during
> the compaction equals the hash after it, and after it equals the hash of older versions. We
> checked this with randomized tests beyond the PR's: over 3000 random histories the hashes after
> a finished compaction are identical to those without the PR, and with a random part of the deletions done
> (or a real `Compact` running with `CompactionBatchLimit: 1` while other goroutines call
> `hashByRev`) `HashKV` never changed, where the code without the PR fails about a third of the histories.
>
> One related case remains, which the PR does not claim to fix: `HashKV(rev)` and the hash the
> compaction at `rev` stores (same `Revision`/`CompactRevision`) can still differ, e.g. put `k` at
> 2, compact 2, delete `k` at 3: `HashKV(3)` falls back to `Keep(2)` and hashes the put at 2, while
> the compaction at 3 uses `Compact(3)` (the tombstone) with `exactKeep` false and does not.
> `CompactHashCheck` compares those two values. #22562 fixes that case but changes the hash after a
> finished compaction (your test case "every key deleted after the compact revision" fails there),
> so the two PRs are not interchangeable; it may be worth a follow-up that changes only the hash
> the compaction stores.
>
> Small thing: the test could also hash after only some of the compaction's batches have run, which
> is the state the issue describes (the current test goes from no deletion to all of them).
