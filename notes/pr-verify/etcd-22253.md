## Verdict

The change is sound as far as it was verified, with the same guarantees as etcd#22291 and no
`sorry`: `closeRequireLeader` at the PR head meets etcd#22291's spec unchanged (the lessor's lock
invariant, in particular that no `keepAlives` entry is left without a subscription, which the pinned
code breaks), with no double close, nil close or out-of-range index. The two PRs behave identically:
etcd#22291 deletes when `reqIdxs == len(ka.chs)` before compacting, this PR compacts and deletes when
`len(ka.chs) == 0`, which is the same condition; the only difference is that this PR first stores two
empty slices into the `keepAlive` it then drops, which nothing else can see (every other access to a
`keepAlive` goes through `l.keepAlives` under `l.mu`). What is not covered is as for etcd#22291: the
spec is safety-only (postcondition `True`), and the other functions over `keepAlives` are checked by
reading, not proved.

## The spec and the proof

Unchanged from etcd#22291: `Spec/go_etcd_io/etcd/client/v3/lessor__closeRequireLeader.lean`, over
`lessor.muInv` (`Proof/go_etcd_io/etcd/client/v3/InvLease.lean`); see `notes/pr-verify/etcd-22291.md`,
"The spec", for its statement, its premise `R ch c -∗ R ch c'` (the pre-existing etcd#22081,
`issues/etcd-lease-closerequireleader-ctx-misaligned.md`) and why it fails of the old code.

The proof changed only in its shape: etcd#22291's early `reqIdxs == len(ka.chs)` branch (delete,
`continue`) is gone; the compaction now runs for every entry with `reqIdxs > 0`, including when it
leaves zero subscriptions (zero-length `make`s, a loop that skips every nil channel), and after the
`ka.chs, ka.ctxs = newChs, newCtxs` stores a new `len(ka.chs) == 0` branch deletes the map entry,
dropping the emptied `keepAlive`'s ownership; otherwise the non-emptiness of the kept entry comes
from that branch's condition instead of from the earlier one. The lemmas of `InvLease.lean` were
reused as they are.

## Findings

1. **In the PR: nothing wrong with what it changes.** Deleting during the `range` over the map is
   safe in Go; the closed channels are not closed again (no `ka.close()`); a late response or
   `keepAliveCtxCloser` for the deleted id finds no entry.
2. **(Low; also in etcd#22291) `ka.donec` stays open on the delete path**, so the deleted
   subscriptions' `keepAliveCtxCloser` goroutines stay blocked until their contexts end or the
   lessor closes (`TestReviewDeletedEntryDonecNotClosed` at this head, `notes/pr-verify/etcd-22253/tests.log`).
   Not a regression. `close(ka.donec)` before the `delete` would release them.
3. **(Medium; pre-existing, recorded) etcd#22081**: the compaction pairs a kept channel with
   `ka.ctxs[newIdx]`; with this PR, as with etcd#22291, a second leader loss closes a plain
   subscriber's channel and now also deletes its entry (`TestLessorCloseRequireLeaderKeepsPairing`
   fails at this head; `TestReviewMixedCase`). etcd-io/etcd#22087 fixes it.
4. **The bug the PR fixes**, etcd#22094 (`issues/etcd-lease-closerequireleader-orphan.md`): the
   proof confirms the fix; the PR's own test fails on the upstream base and passes at the head.
5. **Comparison with etcd#22291**: identical behavior, confirmed both by the proof (one spec) and by
   the tests: each PR's test passes on the other's head, and the review tests print the same at
   both heads. Choosing between them is a matter of style: etcd#22291's early delete skips the
   useless allocation; this PR keeps the compaction uniform. Either should land with or after
   etcd#22087.

No reviewer subagent was run for this PR: the spec, invariant and axiom are etcd#22291's, already
reviewed there, and the one new artifact is a machine-checked proof of the same statement.

Tests and logs: `notes/pr-verify/etcd-22253/` (see its `README.md`).

## Draft review comment (for the user to edit and post)

> This looks correct to me: `len(ka.chs) == 0` after the compaction holds exactly when every channel
> of the entry was just closed, so skipping `ka.close()` is right, and a later response or
> `KeepAlive` for that lease ID behaves as for a fresh lease. It is equivalent to #22291, which fixes
> the same issue by deleting before the compaction.
>
> Two small things, shared with #22291:
>
> 1. `ka.donec` is not closed on the delete path, so those subscriptions' `keepAliveCtxCloser`
>    goroutines stay blocked until their contexts are done or the lessor is closed (as before, behind
>    the stale entry). Closing `ka.donec` before the `delete` would release them.
> 2. The compaction still pairs the kept channel with `ka.ctxs[newIdx]` instead of `ka.ctxs[i]`
>    (#22081, fixed by #22087). With subscriptions `[A (require leader), B (plain)]`, a second leader
>    loss now closes B and also deletes the entry, so B's lease silently stops being renewed. It would
>    be good to land #22087 first or together, with a mixed-case test.
