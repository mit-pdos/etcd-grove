## Verdict

**The PR makes `Snapshot` loop forever.** It raises the loop bound to `total + 32`, but the
pipe the loop reads from carries only the database's `total` bytes. Once those are read,
`io.ReadFull` returns `(0, io.EOF)`, which the loop tolerates, so `sent` stays at `total`. The
server then sends an empty response with `RemainingBytes = 32` per iteration until the client
cancels; the checksum is never sent.
- The Lean model of the loop proves this for every database size (`pr_spins`, `pr_spin_msg`).
- The integration test shows it on a real cluster: 466,443 empty responses in 10 s.
- `etcdctl snapshot save` without `--command-timeout` would hang forever.

**The intended change is right, and one line fixes the PR.** Keep the loop bound at
`total-sent > 0` and report `RemainingBytes = total + 32 - sent`. The stream then meets
`rpc.proto`'s "number of blob bytes to be sent after this message" for every response, the
checksum included (`fixed_remainingOk`). The base does not meet it (`base_not_remainingOk`), so
the bug the PR targets is real. Both tests pass with this fix (`suggested-fix.patch`).

**The PR's own e2e test would not have caught this, and its check is wrong.**
- At the PR head it fails only by hitting its 30 s deadline.
- Its per-response check `len(Blob) + RemainingBytes == totalByteToSend` holds only for the
  first response. It passes on the test cluster's database only because that fits in one 32 KiB
  buffer; with several buffers it fails from the second response on, even with the fix.

**Not covered:**
- `Snapshot` itself is not verified as code. Goose translates it, but the translation needs
  `crypto/sha256` and `hash`, which Perennial does not model (see "Translation"). The model
  covers the loop's arithmetic and its pipe reads, not the rest of the function.
- A Hoare triple would not catch the bug either: partial correctness is met by a loop that never
  ends, and each response the spinning loop sends has `RemainingBytes` correctly equal to
  `total + 32 - sent`. Only a bound on the number of `Send`s (or a termination argument) excludes
  it; the model proves termination directly.
- The log-field renames (`total-bytes` → `total-bytes-to-send`/`total-bytes-sent`, `size` →
  `database-size`) were checked only by grepping `tests/`, where nothing matches them.

**Overlap with etcd#22125**, which changes the same function (the writer goroutine:
`pw.CloseWithError` on a `WriteTo` error) and is verified on `pr-verify/etcd-22125`, uncommitted
when this run looked.
- The two PRs touch different lines and compose.
- #22125 does not stop #22066's spin. That spin happens on the success path, where `WriteTo`
  returns `nil` and the pipe ends with `EOF`.

### The specs (the model)

`Proof/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/SnapshotLoopModel.lean` models the loop by
four numbers:
- `avail`: the bytes the pipe yields before `EOF`;
- `bound`: the loop runs while `bound - sent > 0`;
- `rep`: data responses carry `RemainingBytes = rep - sent`;
- the 32 KiB buffer.

Each read adds `min 32768 (avail - sent)`, which is `io.ReadFull` on an `io.Pipe` with
`ErrUnexpectedEOF`/`EOF` tolerated. So `sent` after `k` iterations is `min (32768 k) avail`
(`sentAfter_eq`).

- **Old behavior** (`base D`: `avail = bound = rep = D`): the loop ends after `⌈D/32768⌉`
  iterations (`base_exits`). Every data response's `RemainingBytes` is 32 short of the bytes sent
  after it (`base_not_remainingOk`).
- **The PR** (`pr D`: `bound = rep = D + 32`): the loop never ends as long as `Send` succeeds
  (`pr_spins`). From iteration `⌈D/32768⌉` on, each response is empty with `RemainingBytes = 32`
  (`pr_spin_msg`).
- **The intended behavior** (`fixed D`: `bound = D`, `rep = D + 32`): the loop ends after
  `⌈D/32768⌉` iterations (`fixed_exits`). Every response of the stream, the checksum included,
  carries exactly the blob bytes sent after it (`RemainingOk`, `fixed_remainingOk`).
- General: the loop ends iff `bound ≤ avail` (`exits_iff`). Before the PR, a snapshot that
  yields fewer than `snap.Size()` bytes also never ends (`base_spins_on_writeTo_error`).

The model is pure arithmetic and leaves out three things:
- `Send`'s failure, the loop's only other exit;
- int64 overflow of `total + 32` (a file size);
- the SHA-256 value itself.

The reviewer checked it against the Go code. `avail = snap.Size()` on success holds because
bbolt v1.5.0's `Tx.WriteTo` writes exactly `Size()` bytes.

### Translation

Adding `maintenanceServer.Snapshot` and `snapshotSendBufferSize` to `v3rpc.toml`'s `translate`,
and `crypto/sha256`, `github.com/dustin/go-humanize`, `storage/backend` and `storage/schema` to
its imports, makes Goose translate the body. The output, however, imports
`Perennial.Code.crypto.sha256` and names `Perennial.hash.Hash`, and Perennial has neither, so
the module does not build. The translation was therefore reverted on this branch, and
`v3rpc.toml` is unchanged.

This is recorded as a Perennial limitation in `notes/STATUS.md`, section "pr-verify etcd#22066".
The local workaround is the one the etcd#22125 run tried: names-only translations of
`crypto/sha256` and `hash` under the empty root (`-lean-root crypto/sha256= -lean-root hash=`).
It would let a later proof of `Snapshot` start.

## Callers (step 6)

`Snapshot` is a gRPC handler; nothing in etcd calls it directly. It is reached through:
- `authMaintenanceServer.Snapshot` (an auth check, then delegation);
- the grpc-proxy's maintenance server (`server/proxy/grpcproxy/maintenance.go`) and the
  in-process adapter, which forward the stream as is and so inherit the endless stream.

On the client side, `client/v3/maintenance.go`'s `Snapshot` reads `Blob` until `EOF` and never
reads `RemainingBytes`, and nothing outside the generated `*.pb.go` files does (the reviewer's
grep). So the change to `RemainingBytes` itself affects only third-party gRPC clients, and the
loop bound affects every client. None is verified, so there are no proofs to rebuild. This is an
exported API change (the value of a wire field), and the PR does not mention a CHANGELOG entry.

## Findings

1. **The PR's loop never terminates** (a bug the PR introduces). Evidence:
   - `logs/unit-pr.log`, from `maintenance_snapshot_test.go`'s `TestSnapshotStream`: the fake
     stream refuses the 1001st response, the last one being empty with `remaining_bytes:32`;
   - `logs/integration-pr.log`, from `maintenance_snapshot_remaining_test.go`: 466,443 empty
     responses in 10 s on a real cluster, then `DeadlineExceeded`.

   Fix: `suggested-fix.patch` (`logs/unit-fix.log`, `logs/integration-fix.log` pass).
2. **The PR's e2e test checks the wrong invariant.** `len(Blob) + RemainingBytes` equals
   `size + 32` only for the first data response. `logs/unit-fix.log` logs it per response over a
   224 KiB database: 229408, 196640, 163872, ... The right check is cumulative: each response's
   `RemainingBytes` is the total minus the blob bytes received so far, including its own. With
   the PR's code the test fails only by timing out after 30 s.
3. **Existing code: `RemainingBytes` leaves out the digest** (the PR's target). Recorded in
   `issues/etcd-snapshot-remainingbytes-sha.md` (`upstream: known`, #18340, #22066). Shown by
   `logs/unit-base.log` and `logs/integration-base.log`: the count is 32 short.
4. **Existing code: a snapshot that ends early spins forever.**
   - Cause: `snap.WriteTo`'s error is dropped and the pipe closed with `EOF`.
   - Recorded in `issues/etcd-snapshot-writeto-error-spin.md` (`upstream: known`, #22125's fix
     covers a `WriteTo` error but not a `WriteTo` that returns `io.EOF`, per that run's tests).
   - Shown by `TestSnapshotWriteToError`, which fails at the base, at the PR head and with the
     fix.
   - Reachable only through a read error of the database file (the reviewer).
5. Cosmetic: the PR leaves the checksum's log call with `zap.Int64("total-bytes", total)` while
   renaming the other two, and the comment above the response ("it is possible that
   resp.RemainingBytes == 0, resp.Blob == zero byte") is stale before and after: with the bound
   at `total`, the loop stops at `sent == total` without an empty response.

Reviewer (a fresh subagent; it re-ran the tests in its own worktree):
- It confirmed every point above.
- Its three nits are resolved:
  - `pr_spins` is now stated as "while `Send` succeeds";
  - the tests no longer index an empty response list;
  - the WriteTo issue now says why a read error is the only route.
- It added no findings, and no review points remain open.
