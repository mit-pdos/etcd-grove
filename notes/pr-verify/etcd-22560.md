## Verdict

**The PR should not be merged as it is.** It does fix the two scenarios it tests. But it breaks
token expiry and token revocation for the whole v3lock/v3election gRPC API:
- **Every request is renewed, not just blocked ones.** `kvServerWrapper` renews the token whenever
  a call fails with an auth-token error, not only when the call had been blocked.
- **Expired JWTs are renewed.** JWT `renew` parses with `jwt.WithoutClaimsValidation()`, so a JWT
  of any age is renewed, including one revoked by a password change or by deleting and re-creating
  the user.
- **Expired simple tokens come back.** Simple-token `renew` puts TTL-expired tokens back in the
  live table, where they work on every API again.

So a leaked token that the KV API correctly rejects can still delete keys through `Lock.Unlock`.
The integration test shows this at the PR head, and the same test passes on `main`.

The fix is also incomplete. A waiter that must create a new watch after the auth revision moves
still fails.

`RenewToken` also adds a data race, which the race detector reports: it calls the admin-only
`invalidateUser` from a request goroutine, concurrently with `disable`.

**What the proofs establish.** Among the simple provider's table operations, `renew`, `assign`,
`invalidateUser`, `disable`, `enable` (including the PR's change to the keeper's callback) and the
constructor are proved race-free and panic-free against a lock invariant, with no `sorry`. Their
verified callees in the same file (`addSimpleToken`, `resetSimpleToken`, `deleteSimpleToken`) are
also proved. They rest on two new postulates: the keeper goroutine `run` and its `stop`.

The invariant says that what `renew` accepts is a token the admin has assigned and has not
invalidated or disabled since. That rules out revoked users. It also makes precise that the TTL is
no bound: nothing in the invariant mentions expiry.

**What is not covered.**
- `RenewToken` has one `sorry`, the race.
- The JWT `renew` is not translated, because `golang-jwt` is not translated.
- The v3client wrappers are translated but not specified. That is where the policy findings live,
  and the Go tests carry them.

### The specs

The files are in `Spec/go_etcd_io/etcd/server/v3/auth/`. The invariant is
`Proof/go_etcd_io/etcd/server/v3/auth/InvSimpleToken.lean`.

**The lock invariant `stLockP`.** `t.simpleTokensMu` guards:
- `simpleTokens` and the PR's `expiredTokens`, both below a ghost table `A` (token → user, the
  tokens the admin allows);
- `simpleTokenTTL`;
- half of `simpleTokenKeeper` (the admin, `tsAdmin`, holds the other half);
- the deadline map of every keeper ever created, old keepers included. The goroutine of a keeper
  that `disable` has dropped may still sweep its map under the lock until `stop` returns.

**`tokenSimple.renew`** returns one of three results:
- `(token, nil)`;
- `("", ErrAuthFailed)` when the provider is disabled;
- `("", ErrInvalidAuthToken)`.

The invariant gives what it accepts: a token of either map, hence in `A`.

**The admin operations** each change `A`:
- **`assignSimpleTokenToUser`**: inserts `tk ↦ u` if the provider is enabled. Its premise is
  `A !! tk = none`; otherwise the Go code panics if the token is live.
- **`invalidateUser`**: filters `u` out of `A`.
- **`disable`**: sets `A` to empty and the keeper to `nil`.
- **`enable`**: keeps `A`, and installs a non-nil keeper and its goroutine.

**`authStore.RenewToken`** keeps the caller's reader resources: a slot of `enabledMu` and the
backend's `R`. It returns `err = nil` or the token `""`.

**The admin discipline.** `enable`, `disable`, `invalidateUser` and `assign` take `tsAdmin`.
In etcd the admin is the apply goroutine. `invalidateUser` reads `simpleTokenKeeper` before it
takes the lock, which is safe only for the admin.

**What the specs do not state.** No spec states the PR's own intent ("an authentic token, the user
still exists") as a contract its callers could use (reviewer, point 4). `renewable_allowed` is a
lemma about the invariant, not part of `renew`'s postcondition. A spec that bounded renewal by the
TTL could not be proved of this code, and the tests show it does not hold.

## Trust base

`etc/tcb-collections/pr-etcd-22560.txt` covers 13 roots (`tokenSimple__*`,
`simpleTokenTTLKeeper__*`, `newTokenProviderSimple`, `tokenNop__renew`, `authStore__RenewToken`).
- 12 of the roots reach no `sorry`. `auth.authStore.wp_RenewToken` reaches one.
- The new postulates are `auth.simpleTokenTTLKeeper.run.wp_proof` and
  `auth.simpleTokenTTLKeeper.stop.wp_proof`. The others they rest on (`zap.String`,
  `zap.Logger.Debug`, `zap.NewNop`) were already there.
- `etc/tcb-baseline.txt` (now 244 entries) and the `server` collection were updated: they gain
  these two axioms and the `sorry`.

Why the new postulates and contract changes are believed:
- **`run`** gets its lock (`keeperRO`: `mu = &t.simpleTokensMu`), its deadline map (in the lock,
  found through the persistent membership `k ↪[γk]□ ()`), its callback (`delfOk`, proved) and its
  two channels. The Go code only locks, sweeps and calls back. The reviewer notes that it also reads
  the mutable global `simpleTokenTTLResolution`, which `authInit` does not cover.
- **`stop`** is not derivable as stated: `stop` takes only the persistent `keeperRO`, while the
  channels' exclusive ownership went to `run` (reviewer, point 8). The Go code never panics there,
  it only blocks. A sound restatement would put the channels in a stop/done invariant shared by
  `run` and `stop`. **Open.**
- **`authInit`** gains `ErrAuthFailed` and a read-only `simpleTokenTTLDefault`. That variable is a
  mutable `var` that only tests write.
- **`tokenProviderOk`** gains two contracts:
  - `renew` returns, with the token `""` on an error. All three providers do.
  - `invalidateUser` needs a provider resource `Adm`. For the simple provider that is `tsAdmin`;
    for JWT it is trivially met.

## Findings

All tests are in `notes/pr-verify/etcd-22560/`; its `README.md` gives the revisions and commands.

1. **Bug in the PR (security): fresh v3lock/v3election requests with revoked or expired tokens
   succeed.**
   - Test: `tests/integration/v3lock_auth_renew_test.go`, `TestV3LockUnlockRejectsRevokedAndExpiredJWT`.
   - Result: FAIL at the PR head, PASS on `main`.
   - The KV API rejects the leaked token (`revision of auth store is old`). `Lock.Unlock` with the
     same token deletes `foo1`. After the JWT has expired too, it deletes `foo2`.
   - Cause: `kvServerWrapper` renews whenever a call fails with an auth-token error.
2. **Bug in the PR (security): JWT renewal ignores `exp` and undoes revocation by auth revision.**
   - Tests: `server/auth/renew_token_finding_test.go`, `TestRenewTokenJWTIgnoresExpiry`,
     `…SurvivesPasswordChange` and `…DeletedUserRecreated`.
   - What they show:
     - An expired JWT is renewed.
     - A JWT issued before a password change passes `IsPutPermitted` again after renewal.
     - A deleted user's JWT is renewed for a new user of the same name.
   - etcd revokes JWTs (which carry no server state) through the auth revision. `RenewToken` only
     checks that a user of that name exists.
3. **Bug in the PR (security): expired simple tokens come back to life everywhere.**
   - Tests: `TestRenewTokenResurrectsExpiredSimpleToken`, and the reviewer's
     `server/auth/revive_reviewer_test.go`, `TestReviewerRenewRevivesExpiredSimpleTokenForAllAPIs`.
   - `renew` moves the token from `expiredTokens` back to `simpleTokens`. After one renewal through
     the in-process client, the client's own expired token authenticates on every API of that
     member again.
   - Entries leave `expiredTokens` only by eviction past 10000, `invalidateUser` or `disable`.
4. **Bug in the PR (concurrency): a data race between `RenewToken` and `AuthDisable`.**
   - Test: `TestRenewTokenInvalidateUserRacesDisable`, run with `-race`. The race detector reports
     it (`race.log`).
   - `RenewToken` calls `tokenProvider.invalidateUser` on a request goroutine. `invalidateUser`
     reads `simpleTokenKeeper` without the lock, and `disable` writes it under the lock.
   - This is the proof's `sorry`. The effect is benign today: after `disable` the table is empty.
   - The call is redundant: `UserDelete` already invalidates, and for JWT `invalidateUser` does
     nothing. Dropping the call, or taking the lock before the nil check, fixes it.
5. **Incomplete fix: a waiter that re-watches after an auth revision bump still fails.**
   - Test: `tests/integration/v3lock_auth_revision_rewatch_test.go`.
   - Result: FAIL at the PR head and on `main`. On `main` the KV call fails first.
   - `watchWrapper.Watch` renews only if `AuthInfoFromCtx` fails. A JWT with a stale revision
     passes that check and is then refused by the watch's permission check. The PR's own
     revision-bump test passes only because its watch already exists before the bump.
6. **Notes.**
   - **Retries.** The retry of `Put`/`Txn`/`DeleteRange` cannot apply twice: invalid tokens are
     rejected before proposal, and a stale revision is rejected at apply before execution
     (reviewer, point 10). But the renewed context is used only for the one retry, so every later
     call on the session fails once and renews again. For a stale-revision write that is two raft
     proposals per call.
   - **String fallbacks.** `isInvalidAuthToken` looks for "revision of auth is old", but the
     message is "revision of auth store is old". The fallback is dead code, since `errors.Is`
     matches.
   - **Admin discipline vs. `WithRoot`.** The spec of `assignSimpleTokenToUser` (admin only) is too
     strong for `WithRoot`, which calls `assign` from the lease-revoke goroutine and the health
     handlers (reviewer, point 5). The Go code takes the lock there, so it is safe. **Open** spec
     gap; no bug.
   - **The premise `A !! tk = none`** makes the PR's `delete(expiredTokens, tk)` in `assign` dead in
     the proof. It holds for `Authenticate` (raft indices are unique). For `WithRoot` it holds only
     with high probability (index 0, random prefix).

The PR's own tests pass at the head (`pr-own-tests.log`). This work found no bug in the existing,
pinned code, so there is no new entry in `issues/`.

### Draft review comment (for the user to edit and post)

> Thanks for working on #17623. I tried this out and I think the renewal is too broad as it
> stands:
>
> - `kvServerWrapper` renews on any invalid-token or old-revision error, not only for calls that
>   were blocked when the token went stale. So every v3lock/v3election request with an expired or
>   revoked token now succeeds. For example, after `UserChangePassword`, the old token is rejected by
>   KV but `Lock.Unlock` with it still deletes keys. Three seconds after its `exp`, too.
> - `tokenJWT.renew` parses with `jwt.WithoutClaimsValidation()`, so a JWT of any age is
>   re-issued as long as a user of that name exists. That also defeats revocation through the
>   auth revision (password change, delete and re-create of a user).
> - For simple tokens, `renew` moves the token from `expiredTokens` back into `simpleTokens`, so
>   the client's own expired token becomes valid again on every API.
> - `RenewToken` calls `invalidateUser` from a request goroutine. It reads `simpleTokenKeeper`
>   without the mutex while `AuthDisable` writes it, and `go test -race` reports it. `UserDelete`
>   already invalidates, so the call can go.
> - `watchWrapper.Watch` only renews when `AuthInfoFromCtx` fails, which a stale-revision JWT does
>   not trigger. A waiter that has to start a new watch after a revision bump still fails.
>
> A narrower design might capture the caller's authenticated identity when `Campaign`/`Lock`
> starts, after the token has been validated once, and let only that in-flight call continue.
> I have tests for each point and can share them.
