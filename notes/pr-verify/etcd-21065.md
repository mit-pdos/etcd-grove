## Verdict

**The PR fixes the deadlock, but it should not be merged as it is.** Dropping "best-effort"
requests loses cancel requests for good, and with them server watchers. It also loses progress
requests that `RequestProgress` has already reported as sent.

- **The deadlock is fixed.** `run` no longer sends, so it always reads responses. With 2000
  watches closed at once over the in-process client, the stream keeps working at the PR head; at
  the base and at the pin it stops (`integ-*.log`).
- **But the closed watches leak on the server.**
  - The extra cancels are dropped when the 128-slot queue is full.
  - `run` puts each id in `cancelSet` before it enqueues the cancel, so a later event for a
    dropped id is ignored and no new cancel is sent. The server keeps that watcher for the
    stream's lifetime and keeps sending it events.
  - In the PR's own scenario, 1400 to 1560 of the 2000 closed watches stay registered on the
    server.
  - Over an ordinary gRPC connection, where the base cancels all 2000, the PR leaks 500 to 1000.
    That is a regression for every client, not only the in-process one.
  - The same queue drops `RequestProgress`'s request after `RequestProgress` has returned `nil`.
- **The proofs.**
  - Proved, with no `sorry`: the new `sendLoop`, `enqueueCreateReq` and `enqueueBestEffortReq`,
    the renamed `recvLoop`, and `newWatchClient` and `newWatcherGRPCStream` under their new specs.
    Every request `sendLoop` sends is one `run` enqueued, with the server's obligations met. A
    queue is never sent on after it is closed.
  - **Not proved**: `run`'s own proof is now a `sorry`. Its `lean` proof matched each `Created`
    to the head of `resuming` through the stream's sender token, and that token is now
    `sendLoop`'s. Re-proving it needs a stronger (logically atomic) model of the gRPC stream's
    `Send` ("Why `run`'s proof is open").
  - So the end-to-end watch results (`watcher.Watch` and the recipes' watch vertical) now rest
    on that `sorry`.

### Old and new specs

- **`run`** (`Spec/go_etcd_io/etcd/client/v3/watchGRPCStream__run.lean`). The postcondition is
  the same: the thread token back. The precondition also takes:
  - the fields `sendCreatec` and `sendBestEffortc`;
  - the adder of `sendWg` (`wgsWgAdder`, the thread-token wait group of `InvWatchWg.lean`).
- **`newWatchClient`** (`Spec/.../watchGRPCStream__newWatchClient.lean`).
  - Old: returned the stream's client end, its sender token and `respc`'s consumer side.
  - New: returns only the error. On success it gives the caller the two queues (`sendQIs`: the
    fields read-only, two SPSC channels of `sendElem`) and their producer sides, with the
    stream's specification and `respc`'s consumer side.
  - The sender token goes to `sendLoop`, started on `sendWg`: its `Add(1)` deposits the
    caller's thread token, and the `go` gives the caller a fresh one.
  - This is incompatible with the old spec. Its only caller, `run`, was re-specified.
- **`sendElem`** (`Proof/go_etcd_io/etcd/client/v3/InvWatchSend.lean`), what a queue element
  carries:
  - the request message (`watchReqSend`);
  - the server's requirement on a request (`v3rpc.watchUp`: restricted, and a watch token for a
    create). It does not depend on the request's position, so `run` can meet it without knowing
    where `sendLoop` will put the request.
- **`sendLoop`**: with the sender token and the consumer sides of both queues, it sends each
  request it takes, meeting the server's requirement, until a queue is closed, a `Send` fails, or
  the stream is done.
- **`enqueueCreateReq`**: with the create queue's producer side and an element, it enqueues the
  request (`sent ++ [req]`) or gives up on `donec` or the context (`sent`).
- **`enqueueBestEffortReq`**: the same over the best-effort queue, never blocking: it also gives
  up when the queue is full. The spec states the drop; nothing in a safety spec forbids it.
  The findings are about what the drop does to the protocol.

### Why `run`'s proof is open

- `run`'s `lean` proof keeps the gRPC stream's sender token, `cliSendTok γs S.L`, so it knows the
  whole up queue `S.L`. The proof depends on that knowledge:
  - Its model (`WatchClientModel.lean`, `gOk`) says that every create in `S.L` is answered or is
    the pending one (`pend = some i`).
  - So when the server's `Created` answers up position `i`, the create at `i` is the head of
    `resuming`. That gives the substream the server's registration facts (`regFacts`), and with
    them the contract of its events.
- With the PR the token is `sendLoop`'s, which sends what it takes from two queues in an order
  `run` does not see.
- This repository's model of a client stream's `Send` (`cliBidiStreamIs`,
  `Proof/google_golang_org/grpc/InvGrpcStream.lean`, trust boundary) is a Hoare triple, not a
  logically atomic one.
  - When the server's answer for position `i` reaches `run`, `sendLoop` may still be inside the
    `Send` that put a request at `i`.
  - Nothing `run` can hold at that point ties position `i` to the request it enqueued.
  - A ghost record that `sendLoop` makes before or after each `Send` does not close the gap. A
    record made before cannot exclude positions beyond it. A record made after can be overtaken
    by the answer.
- One fact helps, but not enough. Under the verified premises `run` keeps at most one create in
  flight per stream, and creates travel through one FIFO queue. But identifying the answered
  create still needs a tie between the stream's actual up queue and the queue, at the moment of
  the send.
- What would close it: a logically atomic `Send` (an atomic update of `cliSendTok` at the
  linearization point, inside `SendMsg`). This is a change to the gRPC model, to be designed on
  its own (`notes/STATUS.md`). With it, `sendLoop` could publish "position `i` holds the request
  of queue element `k`" atomically, and `run`'s model could keep `S.L` as before.
- All of `run`'s callees are proved. The helper lemmas of `lean`'s proof are kept in the file.

## Findings

Tests and logs are in `notes/pr-verify/etcd-21065/` (README there).

1. **Dropped cancel requests are never sent again, so the server keeps the closed watches.** (A
   bug the PR introduces.)
   - When more than 128 cancels are pending, `enqueueBestEffortReq` drops the rest.
   - Both places that send a cancel put the id in `cancelSet` first:
     - the `closingc` case (`cancelSet[ws.id] = struct{}{}`);
     - the unknown-id case.
   - So when the server later sends an event for a dropped id, `run` sees the id in `cancelSet`
     and sends nothing. The server watcher lives as long as the stream: it is matched against
     every write and its events are sent and discarded.
   - Evidence:
     - `watch_send_queue_test.go`, `TestWatchCancelStormLeaksServerWatchers`: a fake stream whose
       `Send` is held while 300 watches close. At the PR head 171 stay registered, even after one
       more event each. At the base, 0 (`unit-up-head.log`, `unit-up-base.log`;
       `unit-fork-pr.log` at the fork branch).
     - `v3_watch_inprocess_cancel_storm_test.go`: a real one-member cluster, 2000 watches closed
       at once. The mvcc watcher gauge counts the server's watchers afterwards; each closed
       watch's key is then written once more, and the gauge is read again.
       - Over the in-process client, the PR leaks 1393 to 1560. At the base and the pin the
         stream deadlocks instead (the bug the PR fixes).
       - Over a gRPC connection, the PR leaks 496 to 1033. The base leaks none and does not
         deadlock.
       - Logs: `integ-up-head.log`, `integ-up-base.log`, `integ-fork-pin.log`,
         `integ-fork-pr.log`.
2. **`RequestProgress` reports success for a request it drops.** (A bug the PR introduces.)
   - Its request goes on the same best-effort queue.
   - When the queue is full, the request is dropped after `RequestProgress` has returned `nil`.
     No progress notification comes.
   - Callers that wait for one, such as Kubernetes' consistent reads from its watch cache, wait
     until their own timeout.
   - Evidence: `TestWatchRequestProgressDroppedWhenQueueFull`. At the PR head the server gets 0
     progress requests and no notification arrives. At the base, 1 request and the notification.
3. **The bug the PR fixes, recorded in `issues/`**: `etcd-watch-cancel-storm-deadlock.md`. The
   integration test reproduces it at the pin and at the base over the in-process client. The PR's
   code does not deadlock in that test.
   - The proof does not confirm the fix: the specs are partial correctness, and a deadlock meets
     them.
   - What the proofs do show of the new code: `sendLoop` is the only sender; `run` never sends on
     a closed queue; at most one goroutine sends on a stream.
   - Under the premise that no stream error is retryable, a queue is closed only on the way out.
4. **The PR's description and its head disagree.** The description cites
   `TestV3WatchCancellationStorm` and a reproduction in #21064 (closed, not merged), but the head
   adds no test.
