## Verdict

In the **revision** mode the PR does what it says, and that is proved:
- `--auto-compaction-interval` reaches the compactor;
- `0` (the default) is still 5 minutes;
- the compactor waits exactly that interval between rounds, and only that;
- every compaction is still at a positive revision that keeps the last `retention` revisions.

In the **periodic** mode, `getCompactInterval` returns the interval when it is non-zero and the
old value otherwise (proved, with a compatibility lemma). The compactions stay safe. But the
interval's effect on *when* compaction happens is not verified, because Perennial's `Time.Sub` is
opaque. Tests show the interval is only a lower bound on the sampling grid of
`min(retention, 1h)/10`: an interval below that grid has no effect, and other values are rounded
up to a multiple of it.

The PR has three problems:
1. it accepts negative and tiny intervals, and these make the revision compactor busy-loop;
2. its e2e test cannot pass;
3. the documentation of the periodic default is wrong.

Every proof is finished, with no `sorry` and no new axiom.

## The specs

All are in `Spec/go_etcd_io/etcd/server/v3/etcdserver/api/v3compactor/`, over
`Proof/.../v3compactor/Defs.lean`:

- **`isRevision rc P`** (persistent) holds:
  - the read-only fields `lg`, `clock`, `retention`, `interval`, `rg` and `c` at `↦□`;
  - a cancellable context;
  - `sync.isMutex` over `paused`.
- **`isPeriodic pc P`** (persistent) holds:
  - the read-only fields `lg`, `clock`, `period`, `interval`, `rg` and `c`;
  - the context;
  - the `RWMutex`'s writer guard over `paused` (`pdLockInv`, fractional).

  Two resources go to `Run`'s goroutine:
  - **`pdRevs pc xs`**, the sample window `pc.revs` (owned, and touched only by the goroutine
    after `newPeriodic`);
  - **`pdReader pc`**, one reader token of the lock.
- **Durations**: `rvInterval i = if i = 0 then 5 min else i`;
  `pdCompactInterval p i = if i = 0 then min(p, 1h) else i`; `pdRetry p = min(p, 1h) / 10`;
  `pdRetentions p = p / pdRetry p + 1`. `pdRetentions_pos` proves this is at least 1 once
  `10 ≤ |p|`, by integer arithmetic in the kernel.
- **The callee contracts** are premises of the `Run` specs, not axioms:
  - **`clockwork.isClockFor clk D`**: `Now()` returns a time, and `After(d)`, for `D d`, a channel
    of times. A real clock (`isClock`, the `NewRealClock` axiom) satisfies it for every `D`
    (`isClock_isClockFor`).
  - **`v3cRevOk rg R`**: `Rev()` returns `v ≥ 0` with a persistent `R v`.
  - **`rvCompactOk c R T retention`**: `Compact` at a non-physical revision `r` with `0 < r`,
    `r ≠ p` for the last success `p` recorded by `T`, and `r + retention = v` for some `R v`. It
    returns an error `errors.Is` can classify, and `T p ∧ |==> T r`.
  - **`pdCompactOk c R T`**: the same with `R r` and `r ≠ p`.
- **`Revision.Run.spec`** assumes the contracts, `T 0`, a non-nil logger and `0 ≤ retention`. It
  takes the clock at `isClockFor P.clock (· = P.interval)`, so **every wait is
  `After(rc.interval)`** (etcd#18472's change). The goroutine does not panic, and every compaction
  meets `rvCompactOk`. Before the PR the wait was the constant 5 minutes. The new spec at
  `interval = 5 min` is that behavior, and `New`/`newRevision` give `5 min` for `0`.
- **`Periodic.Run.spec`** assumes `pdRevs pc []`, `pdReader pc`, the contracts, `T 0`, a non-nil
  logger and `10 ≤ |period|`. Every wait is `After(pdRetry period)`, and every compaction is at a
  sampled revision other than the last success. The spec states **nothing about the time between
  compactions**, which is where `interval` acts (`clock.Now().Sub(lastSuccess) < baseInterval`).
  Perennial's `Time.Sub` returns an unspecified duration, so that comparison cannot be related
  to the clock (`notes/STATUS.md`). The verified facts about `interval` in this mode are
  `getCompactInterval`'s value and that it does not change the sampling.
- **`getCompactInterval.spec`**: `pdCompactInterval p i`, compared with the old
  `pdCompactIntervalOld p = min(p, 1h)`. The difference is one sentence: a non-zero interval
  replaces `min(period, 1h)`. **Compatible**: at `i = 0` it is the old value
  (`spec_implies_old`; `Results.getCompactInterval_compat`).
- **`New.spec`**: `newResult`. The periodic mode has the premise `10 ≤ |retention|`, because below
  that `getRetentions` divides by zero (`issues/etcd-compaction-retention-duration.md`).
  etcd#22095's `New.spec` said only "some compactor" for these two modes, and this one is
  stronger. (The two PRs change `New` incompatibly with each other: different new arguments.)

## Findings

**In the PR** (tests in `notes/pr-verify/etcd-18472/`; `README.md` there has the commands):

1. **A negative or tiny interval is accepted and makes the revision compactor busy-loop** (medium).
   - `parseCompactionInterval` returns `time.ParseDuration`'s value unchecked, and
     `Config.Validate` ignores the field. `-1s` and `1ns` are accepted from the flag and from
     the config file (`reviewer/reviewer_interval_yaml_test.go`).
   - `newRevision` replaces only `0`. `clock.After(≤ 0)` fires at once, so the goroutine calls
     `Rev()`, and `Compact` whenever the revision moved, with no sleep: about 4,500 iterations
     per 100 ms (`pr-head/interval_probe_test.go`, `TestProbeRevisionNegativeIntervalSpins`,
     `…TinyIntervalNearSpins`). Under write load that is one compaction proposal per new
     revision.
   - In the periodic mode a negative interval only disables the gate.
   - `Revision.Run`'s spec holds for any interval: it is a safety spec, and the spin is a
     liveness and performance problem. Suggested fix: reject `interval < 0` (and maybe tiny
     values) in `parseCompactionInterval` or `Validate`.
2. **In the periodic mode the interval is a lower bound on a fixed sampling grid** (medium,
   documentation). The goroutine samples every `min(retention, 1h)/10` and can only compact on a
   sample, so the effective delay is the interval rounded up to a multiple of that.
   - Retention 1 h with interval 1 m compacts every 6 minutes (20 compactions in 3 h,
     `TestProbePeriodicIntervalBelowSamplingIsIneffective`).
   - Retention 1 h with interval 15 m compacts every 18 minutes.
   - The first compaction still waits a full retention period.

   The flag's documentation ("the delay between compaction runs") does not say this. This is
   the part of the PR the proof does not cover.
3. **The e2e test `TestConfigurableCompactionInterval` cannot pass** (medium; by reading, not run).
   - It watches a key that only receives puts, but requires 100 `DELETE` events
     (`expectedCompactCount := totalRev`).
   - `fromRev` is never advanced, so a re-watch starts at revision 0 (the current revision) and
     cannot observe `ErrCompacted`.
   - It either times out or fails `require.Equal(100, 0)`. The PR's e2e CI jobs are failing.
4. **The new documentation of the periodic default is wrong** (low). `embed/config.go` says
   "'periodic' defaults to retention". The default is `min(retention, 1h)`.
5. Low:
   - the interval is silently ignored when `--auto-compaction-retention` is 0;
   - a unit-less interval (`5`) is an error, while a unit-less retention means hours;
   - `etcd.conf.yml.sample` does not list the key;
   - the new unit test `TestPeriodicMinutesWithInterval` does not check the 2-minute cadence;
   - the revision tests no longer exercise the `0 → 5 min` default (the spec covers it).

**In existing code**:
- `issues/etcd-startup-log-compaction-interval.md` (new, from the review): `embed/etcd.go:367`
  logs `auto-compaction-interval` with the *retention's* value. The PR leaves this line, so with
  the PR the log would show the wrong value under the new flag's name.
- `issues/etcd-compaction-retention-duration.md` (from etcd#22095's verification, extended here)
  covers three problems: a duration retention in the revision mode, a negative retention, and a
  1–9 ns periodic retention, which panics `New`. The specs carry the premises
  `10 ≤ |retention|` and `0 ≤ retention`.

**Reviewer's points** (all resolved or recorded above): the periodic timing gap (stated in the
verdict and the specs), the e2e test, validation, the documentation, and the startup log. The
reviewer found the contracts, the `RWMutex` invariant and its `Fractional` instance, and the
ownership of `pc.revs` sound. `Run` consuming `pdRevs` also rules out a second `Run`. The
reviewer found no concurrency issue.

## Draft review comment (for the user to edit and post)

> Thanks for this, a configurable interval for the revision mode is useful. A few things I
> noticed while testing it:
>
> 1. Negative or very small values are accepted: `parseCompactionInterval` returns whatever
>    `time.ParseDuration` gives and `Validate` doesn't check it. In revision mode
>    `newRevision` only replaces `0`, and `clock.After(-1s)` (or `1ns`) fires immediately, so the
>    goroutine spins calling `Rev()` and `Compact` with no sleep (thousands of iterations per
>    100ms in a unit test). Could we reject `interval < 0` (and perhaps values below some
>    minimum)?
> 2. In periodic mode the interval can only take effect on the sampling grid
>    (`getRetryInterval()`, i.e. `min(retention, 1h)/10`), so e.g. retention 1h with interval 1m
>    still compacts only every 6 minutes, and 15m becomes 18m. It may be worth documenting that,
>    or tying the sampling interval to the configured interval. Also the doc comment says
>    "'periodic' defaults to retention"; the default is `min(retention, 1h)`.
> 3. `TestConfigurableCompactionInterval` expects `totalRev` DELETE events, but the watched key
>    only ever gets puts, and `fromRev` is never updated after a compacted watch, so I don't
>    think it can pass as written (the e2e jobs are red).
> 4. Unrelated to the change itself, but now confusing: `embed/etcd.go` already logs a field
>    named `auto-compaction-interval` whose value is `sc.AutoCompactionRetention.String()`.
>    With this PR it should probably log `sc.AutoCompactionInterval`.
