- **PR**: etcd-io/etcd#21203, "client/v3: Add configurable buffer limit for watch streams to prevent

- **Verified at**: `mit-pdos/etcd-grove` branch `pr-etcd-21203-goose-lean`, two commits onto the

  - `09c251583`: the PR's diff, with its test file;
  - `2ec6703e3`: a rewrite to make one line translatable (below).
- **Conflicts and divergences** (places where the verified code differs from the PR):
  1. *Conflict in `watcherStream`'s fields.* The base has upstream's newer `bufLogger` and
     `bufWaitStartTime` (upstream `312d7262d`, "print info log when watcher stream buffer is
     backlogged", which the PR's base `ab9157da2` predates). Both sets of fields are kept.
  2. *Rebased onto that buffer-wait logging.* The PR adds a second `select`, used when the buffer
     is full. In the fork, its `outc` send case also calls `w.recordBufWait(ws)` and its `resumec`
     case calls `ws.resetBufWait()`, as the outer select's cases do. A rebase of the PR onto
     upstream main has to do the same, or the wait timer stays set after the head is sent. This
     changes only logging.
  3. *Translatable rewrite of the threshold.* The PR computes `int(float64(ws.maxBufferSize) * 0.8)`.
     Perennial has no semantics for a float64-to-int conversion, so the fork computes
     `ws.maxBufferSize * 4 / 5` instead. The two agree for every limit in 1..1e8
     (`notes/pr-verify/etcd-21203/threshold_equiv.go`). They can differ only beyond 2^61, where
     `*4` overflows. The threshold only decides when a warning is logged. The Perennial limitation
     is recorded in `notes/STATUS.md`.

  `go build ./...` and `go test` of `client/v3` pass in the fork worktree.

## Verdict

The change does not do what it promises, and with a limit set it makes the watch client wrong in
three ways. The proofs establish the following:

- **What holds.** Whatever the limit, each watch still publishes exactly the responses it
  receives, in order, with the same content guarantees as before. A substream's buffer never
  holds more than `MaxWatcherBufferSize` responses. All of this is machine-checked, with no
  `sorry` in `serveSubstream`'s or `run`'s proofs.
- **What the proofs cannot see.** Those proofs are about safety, and they exclude reconnection.
  The PR's real effects are on progress and on the reconnect path, and Go tests at the PR head
  show them:
  1. A full buffer blocks `run()`, which is shared by every watch on the gRPC stream. One slow
     consumer stalls all the other watches on that stream. It can also deadlock its own goroutine
     (`Watch()` from the consumer).
  2. On reconnect, the response that was waiting is dropped, but the resume revision has already
     moved past it, so an event is lost.
  3. The full-buffer path forgets to stop after delivering an error (compacted) response, so the
     watch channel stays open after the error.
- **Smaller points.** The PR's tests exercise none of this: they only read struct fields. The
  limit counts responses, not events, so it does not bound memory by itself.

## Old and new specs

- **`serveSubstream`** (`Spec/go_etcd_io/etcd/client/v3/watchGRPCStream__serveSubstream.lean`).
  - *Old:* given a fresh substream, it forwards `run`'s responses on `recvc` to `outc` in order,
    sending its channel on `retc` at the created response, until `recvc` is closed or a context is
    done.
  - *New:* the same postcondition. It additionally takes `wsF ws "maxBufferSize" ↦□ mb`,
    `wsF ws "bufferWarningThreshold" ↦□ th` and `wsF ws "bufferWarningLogged" ↦ wl`. Its `recvc`
    protocol (`recvElem`, `Proof/go_etcd_io/etcd/client/v3/InvWatch.lean`) now hands a read-only
    copy of `ws.id` with the created response, which the PR's log calls read.
  - *The bound:* the proof's loop invariant keeps `0 < mb → len(buf) ≤ mb`. It is maintained
    through the PR's two paths. When the buffer is not full, the buffer grows by one. When it is
    full, the goroutine waits on `outc`, pops the head, then appends.
  - *Not covered:* the bound is internal (not in the postcondition). Waiting is not a safety
    property, so the specs cannot express the stall.
- **`run`** (`Proof/go_etcd_io/etcd/client/v3/watchGRPCStream__run.lean`). The spec text is
  unchanged. The invariant `wsElem` now holds the substream's `id` field according to its phase
  (`idFr`): in full while the substream is queued, since `addSubstream` writes it; read-only after
  creation, when `run` persists it and passes a copy with the created response.
  - In the covered behavior, `run` never writes `id` after creation. The only other write is
    `newWatchClient`'s, on the resume path, which the premise `noRetryableStreamErr` excludes.
  - `run` reads the owner's `maxBufferSize` through `isWGS`, which now carries
    `∃ mb, watcherF w "maxBufferSize" ↦□ mb`.
- **`closeSubstream`**: takes `wsF ws "id" ↦{dq0} id` for any `dq0`. The old spec is the instance
  `dq0 = 1`.
- **`NewWatchFromWatchClient` / `NewWatcher`** (their Spec files, and
  `client_newWatcher_rangeWatcher` in `Proof/go_etcd_io/etcd/client/v3/Results.lean`).
  - *New premise:* `structFieldRef Config "MaxWatcherBufferSize" (structFieldRef Client "cfg" c) ↦□ mb`.
  - *New postcondition:* `watcherF w "maxBufferSize" ↦□ mb`.
  - *Why the premise is believable:* `Client.cfg` is written only by `newClient`'s composite
    literal (`client.go:384`), before `NewWatcher(client)`.

## Findings (step 8)

All are bugs in the PR's code, not in the pinned code, so none goes in `issues/`. Tests are in
`notes/pr-verify/etcd-21203/` (see its README). All four fail at the PR head with a limit set and
behave correctly with the limit 0 (`probe-at-pr-head.log`).

1. **One slow watcher stalls every watcher on the stream** (`TestWatchBufferLimitStallsOtherWatchers`).
   - Watches opened with the same context share one gRPC stream and one `run()` goroutine, which
     hands each response to the target substream over the unbuffered `recvc`.
   - When a substream is backpressured it stops receiving, so `run()` blocks in `unicastResponse`.
     Responses for other watches, new `Watch()` requests, `RequestProgress` and cancellations all
     wait until the slow consumer reads.
   - The doc ("the watcher will be paused") says otherwise.
2. **Deadlock from the consumer** (`TestReviewerWatchFromConsumerDeadlocks`, by the reviewer). A
   consumer of watch A that calls `Watch()` on the same context while A is full blocks forever:
   `run()` is waiting for A to be drained.
3. **Event lost on reconnect** (`TestWatchBufferLimitResumeLosesEvent`).
   - In the full-buffer `select`, the response `wr` was already taken from `recvc`, and
     `ws.initReq.rev` was already moved past it.
   - The `resumec` case returns without buffering `wr`, so the resumed watch starts after it. With
     limit 1 the consumer sees revisions 2, 3, 5 and loses 4.
   - The proofs do not cover this: their premise excludes reconnects, the same premise that
     covers `issues/etcd-watch-resume-closing-substream.md`.
4. **Error response does not end the watch** (`TestReviewerCompactedThenProgressKeepsChannelOpen`,
   by the reviewer).
   - The outer send returns after delivering a response with `Err() != nil`; the full-buffer send
     only pops it.
   - After a compacted response (which `run` does not remove from `substreams`), a later progress
     notification is delivered after the error and the channel stays open. A `for range` loop
     never ends.
   - The proofs do not see this, because `recvElem` excludes error responses: canceled/compacted
     responses are outside the verified watch contract.
5. **The limit counts responses, not events or bytes** (no test). One response can carry any
   number of events, and beyond `buf` there are `outc`'s slot, the response in hand, and `run`'s
   and `serveWatchClient`'s. Memory is bounded only per response count.
6. **Log edge cases** (no test).
   - With `MaxWatcherBufferSize = 1` the threshold is 0. The "approaching limit" warning fires on
     the first response and never resets.
   - The "buffer full" warning is logged on every response while full.
   - Negative values silently mean unlimited.

Reviewer points that are not findings:

- The new premises are satisfiable, and the `id` and `maxBufferSize` ownership is sound in the
  covered behavior.
- The read-only `id` relies on the excluded resume path. A proof covering resume would have to
  rework it.
- `Close()` and cancelling the blocked watch itself work.

## Draft review comment (for the user to edit and post)

> Thanks for looking at this. I tried the change against a fake watch server (tests below) and
> found a few problems with the backpressure approach.
>
> 1. All watches created with the same context share one gRPC stream and one `run()` goroutine,
>    which hands each response to its watcher over an unbuffered channel. When one watcher's
>    buffer is full, `serveSubstream` stops receiving, so `run()` blocks: other watchers on the
>    stream get no events, and new `Watch()` calls, `RequestProgress` and cancellations wait too.
>    A consumer that calls `Watch()` on the same context while handling events deadlocks. So the
>    limit is per stream, not per watcher.
> 2. In the full-buffer `select`, the response `wr` has already been taken and
>    `ws.initReq.rev` already advanced past it. When `resumec` fires (reconnect), the function
>    returns without keeping `wr`, so the resumed watch skips it. With a limit of 1 a watcher sees
>    revisions 2, 3, 5.
> 3. The full-buffer send doesn't check `ws.buf[0].Err()` the way the main send does, so after a
>    compacted response the watch channel can stay open and receive a progress notification after
>    the error.
> 4. The limit counts `WatchResponse`s, each of which can hold many events, so the docs' "events"
>    is misleading and memory isn't bounded by it alone.
>
> The added tests only check the config field, not the behavior. Tests reproducing 1 to 3 against
> this branch: [attach `watch_buffer_limit_probe_test.go` and
> `watch_buffer_limit_reviewer_probe_test.go`].
