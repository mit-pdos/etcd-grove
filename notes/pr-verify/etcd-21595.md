## Verdict

**The change is sound and does what the PR says.** The proof shows that `doSerialize` now
returns a non-nil error from `get` unchanged. An auth error is returned only when `get` did not
run, or when it ran and returned `nil`. So a read error such as `ErrCompacted` can no longer be
replaced by `ErrAuthOldRevision`. On the current code it can be: the probe in
`notes/pr-verify/etcd-21595/base/` reproduces exactly the race the PR describes.

`Range` and `Txn` meet their existing specs unchanged. Every caller's proof rebuilds, including
the gRPC layer's (`v3rpc`).

Not covered:
- `RangeStream`, which is not translated. Its converted closure was checked by reading the code.
- The PR as written does not compile on upstream `main` until `RangeStream`'s closure is
  converted.
- The PR's unit test runs with auth disabled, so it never reaches the stale-token check it is
  about.

## The behavior change: `doSerialize`

- **Old spec** (`lean`): `get` is `{G} get() {Q}`. On success the result is `Q`. On failure it
  is an error the gRPC layer can take (`applyErrIs`), with `get` either not run (`G`) or run
  (`Q`). The old spec says nothing about which error is returned: an auth error after a failed
  read is allowed.
- **New spec**
  (`Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__doSerialize.lean:36`): `get` is
  `{G} get() {e. Q e}`. The postcondition (line 51) has three cases:
  - `err = nil` with `Q nil`;
  - `err ≠ nil` with `Q err`: `get` ran and this is its error, as is;
  - `err ≠ nil` with `applyErrIs err` and either `G` or `Q nil`: an auth failure, with `get` not
    run or run and returned `nil` (the stale-token check).
  
  The "error as is" property comes from `Q`: a caller states `get`'s error inside `Q`.
  `Range` and `Txn` do this with `⌜errv = gerr⌝`.
- The two specs are not comparable, because `get`'s type changed, so there is no
  `spec_implies_old`. The callers had to change anyway, so they were re-checked.
- The new spec does not hold of the old code. There, after a failed read the stale-token check
  can return `ErrAuthOldRevision`, which is neither `get`'s error nor an auth failure after a
  successful `get`. The probe shows this case.
- Proof: `Proof/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__doSerialize.lean` (the new
  branch at line 116).

## Callers

- `EtcdServer.Range` (`Proof/.../EtcdServer__Range.lean`, `Spec/...` unchanged):
  - `Q gerr` is the existing read result with `⌜errv = gerr⌝`.
  - The new case at line 322 is the read's error, returned as `(nil, err)`. It is an error the
    gRPC layer can take, by `rangeResult_errIs`.
  - The success case loses its old "read failed but `doSerialize` returned `nil`" sub-case,
    which can no longer happen.
  - Spec unchanged, so the path stops here.
- `EtcdServer.Txn`, read-only branch (`Proof/.../EtcdServer__Txn.lean:321`): the same change.
  - The read's error is returned as `(nil, err)`. Before, the read's error could come back
    together with a partly filled response.
  - The spec allows either (a read-only failure says nothing of `resp`), so it is unchanged.
  - No caller uses the response on error: `v3rpc`'s `kvServer.Range` and `kvServer.Txn` return
    `nil, togRPCError(err)`, and so do the proxy adapters and v3client over them.
  - Spec unchanged, so the path stops here.
- `EtcdServer.RangeStream`: not translated. The converted closure returns the same `err` it
  stores, and `RangeStream` returns `doSerialize`'s error as before. Checked by reading.
- Above these: `Proof/.../etcdserver/Results.lean`, `api/v3rpc/Results.lean` and
  `api/v3rpc/ServerKV.lean` use `EtcdServer.wp_Range` and `wp_Txn` unchanged and rebuild. No
  other Go caller of `doSerialize` exists in the fork.

## Findings

1. **What the PR fixes is a real bug in the current code.** Recorded as
   `issues/etcd-doserialize-get-error-masked.md`.
   - Test: `notes/pr-verify/etcd-21595/base/doserialize_compacted_test.go`. With auth enabled and
     a token, a role is added during a read that fails with `ErrCompacted`.
   - At `09669450f`, `doSerialize` returns `auth: revision in header is old` (`base-fork.log`).
   - With the PR (`pr/`, `pr-fork.log`) it returns `ErrCompacted`.
   - The same fix was proposed in 2019 as etcd-io/etcd#10552, which was closed as stale.
2. **The PR does not compile on upstream `main`**, which is why it is labelled `needs-rebase`.
   `RangeStream`'s `get := func() { err = s.rangeStream(ctx, r, rs) }` must become
   `func() error`, as on the fork branch. The rebase must also keep `main`'s extra `txn.Range`
   and `txn.Txn` arguments.
3. **The PR's unit test does not exercise the race.** `TestDoSerializeGetErrorPropagated` runs
   with auth disabled. The auth info is then `nil`, so the stale-token check never runs.
   - The test does fail on the old code, which drops the error and returns `nil`.
   - It does not cover the masking that the description is about. The probe in finding 1 does,
     and could be turned into the unit test.
   - Minor: there is no blank line before the new function in `server_test.go`.
4. **Existing, not changed by the PR: a read-only `Txn` that fails auth is recorded as a
   success** (found by the reviewer). Recorded as
   `issues/etcd-txn-readonly-auth-failure-metric.md`.
   - On an auth failure, the read-only branch returns `nil, serr` without setting the `err` that
     its deferred metric and warning read.
   - So `etcd_server_request_duration_seconds{type="ReadonlyTxn"}` counts the request as
     `success="true"`, and the slow-request warning omits the error.
   - `Range` sets `err = serr` first.
   - Test: `notes/pr-verify/etcd-21595/both/txn_readonly_metric_test.go`, which fails on both
     revisions.
   - It is a one-line fix in the same lines the PR touches, so it could be folded in.
5. **Observation, not a bug of the PR.** In `RangeStream`, chunks are sent to the client during
   `get`, so the stale-token check after it cannot withhold data. It only changes the final
   status. This is unchanged by the PR. With the PR, a chunk that fails (for example the pinned
   revision compacted mid-stream) now reports its own error instead of `ErrAuthOldRevision`, as
   intended.

The reviewer found nothing unsound in the specs or proofs. Its points are findings 2-5 above.
It also noted that a read-only `Txn` failure could now be specified with `resp = null`, as for
`Range`: an optional strengthening, not done here.

## Draft review comment

> The change looks right to me: with `get` returning its error and `doSerialize` returning it
> before the revision check, a read that fails (e.g. `ErrCompacted`, `ErrFutureRev`) is no longer
> reported as `ErrAuthOldRevision` when an auth change lands during the read. I reproduced the
> masking on current `main`'s code with auth enabled: authenticate, then add a role inside `get`
> and fail it with `mvcc.ErrCompacted`; `doSerialize` returns `auth: revision in header is old`.
> With this PR it returns `ErrCompacted`.
>
> A few things:
>
> 1. After rebasing on `main`, `RangeStream` also calls `doSerialize`; its closure needs the same
>    change: `get := func() error { err = s.rangeStream(ctx, r, rs); return err }`. `main` also
>    passes an extra argument to `txn.Range`/`txn.Txn` in these closures.
> 2. `TestDoSerializeGetErrorPropagated` runs with auth disabled, so `ai` is nil and the revision
>    check never runs; it checks that the error is no longer dropped, but not the race in the
>    description. A test that enables auth (simple token), authenticates, and bumps the auth
>    revision inside `get` (e.g. `RoleAdd`) before returning `mvcc.ErrCompacted` covers it; I can
>    share mine.
> 3. Not from this PR, but in the same lines: in `Txn`'s read-only branch,
>    `if serr := s.doSerialize(...); serr != nil { return nil, serr }` doesn't set `err`, so the
>    deferred metric records an auth failure as `ReadonlyTxn success="true"` and the slow-request
>    warning logs no error. `Range` does `err = serr` first; doing the same here would fix it.
>
> (also nit: a blank line before the new test function in `server_test.go`.)
