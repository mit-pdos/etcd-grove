## Verdict

The change is sound as far as it was verified. The proofs of the raft wrapper's Ready loop
(`raftNode.start`) and the server's apply loop (`EtcdServer.run`) go through, with their specs
unchanged, over the PR's code. So the copy of the committed entries and the new gauge update change
nothing the server's apply path relies on. The new `cloneCommittedEntries` is proved to return a
fully owned copy that shares no memory with the input array. In separation logic that is the
statement that a queued `toApply` no longer points into the raft log's array.

Not covered by the proofs:
- **Memory is not modelled.** Goose has no garbage collector, so "memory is released earlier" can't be
  stated. The PR's actual goal is shown instead by a Go probe (below): with the PR a finished scheduler
  job is collected; on the base it is not.
- **`fifo.executeJob` is not translated.** The FIFO scheduler's methods are names-only, and the
  scheduler is a trust boundary (axioms for `Schedule`, `Stop`, and now `Pending`). I checked by
  hand, and the reviewer checked independently, that `f.pendings[0] = nil` is always in range and
  always clears the job that just finished. So the scheduler axioms stay true of the changed code.

One low-severity remark on the PR: the new gauge doesn't quite measure what its Help string says (see
Findings).

### The specs

- `cloneCommittedEntries(ents)` (new): from `ents ↦*{dq} L`, it returns `ents ↦*{dq} L`, a slice
  `cp ↦* L` at fraction 1 with its whole capacity (`ownSliceCap cp 1`), and `cp = nil` when `L = []`.
  Full ownership of `cp`'s cells can't coexist with anyone else's ownership of them, the raft
  storage's array included. So `cp` is a new array. The pointees (the entries) stay shared, as the PR
  says: only the pointers are copied.
- `raftNode.start` (`Spec/go_etcd_io/etcd/server/v3/etcdserver/raftNode__start.lean`), unchanged.
  Inside the proof, the payload sent on `applyc` (`rnApP`) now holds the copy `cp ↦*□ ceL`, read-only
  as the original was, instead of `rd.CommittedEntries ↦*□ ceL`. The conf-change scan still reads
  the original.
- `EtcdServer.run` (`Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__run.lean`), unchanged.
  The proof calls `sched.Pending()` (new axiom) and the gauge's `Set` (from the package fact) after
  each tracked `Schedule`. Neither takes or gives any resource, so the FIFO chain of the apply
  thread's resources is untouched.

## Findings

- **No bug in the PR.**
  - The scheduler change is safe. `executeJob(todo, false)` runs only on the worker goroutine,
    right after the worker read `todo = f.pendings[0]` from a non-empty queue. Only `Schedule` (an
    append, under `f.mu`) and the worker's own drain path (`f.pendings = nil`, which runs only
    when idle) change the queue. So at the deferred block `f.pendings[0]` is `todo` and in range.
    The base's `f.pendings[1:]` would panic in exactly the same cases, so the PR adds no new panic.
  - `finishCond.L` is `&f.mu`, so the new store is under the same lock as every other access.
    `go test -race` of the scheduler with the probe is clean.
- **The memory fix works (probe).** `notes/pr-verify/etcd-22496/schedule_retention_test.go`
  (`TestFIFOFinishedJobCollected`) passes at the PR head and fails on the base: "the finished job
  is still reachable while the next job is pending". Logs are next to it; see the
  [README](etcd-22496/README.md).
- **Low (metric semantics).** `applyBatchPending`'s Help says "the number of apply batches queued in
  the FIFO scheduler waiting for the apply goroutine". Two things differ:
  - `Pending()` is `len(f.pendings)`, which counts the batch being applied: the probe checks
    `Pending() == 1` while the only remaining job runs.
  - The gauge is set only right after a `Schedule`, so it is always at least 1 and never drops back
    to 0 when the queue drains with no new batch.

  On a busy leader this matters little, since Readys arrive at least every heartbeat. The Help text
  could say "including the batch being applied", or the gauge could also be updated when a job
  finishes.
- Reviewer (fresh subagent): no soundness problem in the specs, the new axiom or the package fact.
  The start/run specs did not change. Nothing else retains the raft log's array: `ap.snapshot` is
  already a `proto.Clone`, the channels are new, and `rd` doesn't outlive its loop iteration. Its
  bookkeeping remarks (baseline not yet updated, files untracked) were resolved before the commit.
  No open points.
- `issues/`: nothing new in the existing code.

> - `executeJob`: the deferred block only runs on the worker goroutine right after it took
