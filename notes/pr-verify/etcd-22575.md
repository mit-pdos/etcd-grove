## Verdict

The change is sound and does what it says. With the PR, `Downgrade` cannot panic for lack of a
cluster version, whatever the action: before the version is known `ENABLE` and `CANCEL` return
`ErrClusterVersionUnavailable` (as `VALIDATE` did), and once it is known they behave as before.
This is proved of the translated code (`downgrade_no_panic`, no `sorry`), down to the `Manager`'s
`allowedDowngradeVersion`, where `ENABLE`'s panic actually was, under the contracts of the
names-only parts (the cluster version goes from `nil` to non-`nil` once and stays so; the
`serverVersionAdapter`'s methods) and five new semver postulates. Not covered: the adapter, the
cluster and the raft proposal behind `DowngradeEnable`/`DowngradeCancel` (contracts), and what the
actions achieve (the specs state safety and the shape of the answer, not the downgrade protocol).
Two things the PR leaves as they were: `CANCEL` still reports success when the cancel fails
(`issues/etcd-downgrade-cancel-error-dropped.md`, a pre-existing bug since e47c3c22d), and the PR
adds no regression test. Found along the way, in code the PR calls but does not change: at a
cluster version x.0 the allowed downgrade target wraps to x.18446744073709551615
(`issues/etcd-downgrade-target-minor-underflow.md`).

## The specs

There was no spec before (the functions were names-only), so each is new; the two the PR changes
are behavior changes whose new specs the old code does not meet:

Each spec takes a flag `known` and, when it is set, the witness that the version is known
(`monoNatLbOwn γcv 1`); `ErrClusterVersionUnavailable` is then excluded.

- `downgradeEnable` (`Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__downgradeEnable.lean`):
  no panic; `ErrClusterVersionUnavailable` and no response before the version is known (only if not
  `known`); otherwise,
  once it is known (the witness `monoNatLbOwn γcv 1` in the outcome), the format's or the manager's
  error with no response, or a response, owned (`dgOutcome γcv known true`). **Old code**: the manager's
  `DowngradeValidate` needs the witness (its `GetClusterVersion` returns `nil` without it, and
  `allowedDowngradeVersion` needs a non-`nil` version), which the old `downgradeEnable` never
  obtained: its proof does not go through, exactly at the panic the issue reports.
- `downgradeCancel` (`.../EtcdServer__downgradeCancel.lean`): no panic; `ErrClusterVersionUnavailable`
  before the version is known; otherwise **a response whatever the cancel returned**. **Old code**:
  `semver.Version.String` needs a non-`nil` version, and the old code called it on
  `s.ClusterVersion()` unchecked. The second disjunct is what the code does, not what it should
  (`issues/etcd-downgrade-cancel-error-dropped.md`).
- `Downgrade` (`.../EtcdServer__Downgrade.lean`): the three actions' outcomes, weakened to
  `dgOutcome γcv known false` (a format error from `VALIDATE` may come before the version is read), and
  `ErrUnknownMethod` for another action. Restated as `downgrade_no_panic`
  (`Proof/go_etcd_io/etcd/server/v3/etcdserver/Results.lean`).
- The manager's methods (`Spec/go_etcd_io/etcd/server/v3/etcdserver/version/`): `DowngradeValidate`
  and `DowngradeEnable` require the witness (and `DowngradeEnable` a non-`nil` target), return some
  error; `DowngradeCancel` requires nothing (`GetDowngradeInfo` is never `nil`).

## Callers (step 6)

`downgradeEnable`/`downgradeCancel` are called only by `Downgrade` (verified). `Downgrade` is called
by the gRPC maintenance service (`v3rpc/maintenance.go:320`, `maintenanceServer.Downgrade`, through
the `Downgrader` interface; not translated), which sets `resp.Header` on success: the spec's success
case returns a non-`nil`, owned response, so that store is safe; on error it returns
`togRPCError(err)`, and the new error (`ErrClusterVersionUnavailable`) was already returned by
`VALIDATE` and is in the gRPC error map (`v3rpc/util.go:65`). The other callers are the
authenticating wrapper (`authMaintenanceServer.Downgrade`, `maintenance.go:396`, admin check then
the same) and the gRPC proxy, which forwards over the network. No other caller in etcd's modules
(`grep` of `Downgrade(` over the fork). The user-visible change is the new error from
`ENABLE`/`CANCEL` before the version is known, in place of a crash; the PR says so, and adds no
`CHANGELOG-3.*.md` entry.

## Findings

- **The fix** (`issues/etcd-downgrade-nil-cluster-version.md`, upstream: known, #22574): confirmed by
  the proof and by `TestDowngradeClusterVersionUnavailable` (`notes/pr-verify/etcd-22575/`): on the
  pin and on upstream's base `ENABLE` and `CANCEL` panic; with the PR all three actions return
  `ErrClusterVersionUnavailable` (`test-base.log`, `test-fork-pr.log`, `upstream/test-*.log`).
- **`CANCEL` drops the cancel's error** (`issues/etcd-downgrade-cancel-error-dropped.md`, pre-existing
  since e47c3c22d, kept by the PR): `ErrNoInflightDowngrade`, the linearizable read's and the
  proposal's errors are logged and the RPC succeeds; the gRPC error map and the e2e helper still
  expect "no inflight downgrade job". `TestDowngradeCancelWithoutDowngradeReportsError` fails on
  every revision. Out of the PR's scope, but the PR touches those lines.
- **Order of checks**: `ENABLE` now checks the version before parsing the target, so a malformed
  target before the version is known gets `ErrClusterVersionUnavailable`, where `VALIDATE` returns
  `ErrWrongDowngradeVersionFormat` (raised in the PR's review too). Harmless; noted.
- **The response's version** is now the cluster version read before the action (before, after it).
  `ENABLE` and `CANCEL` do not change the cluster version (the monitor does, later), so this is the
  same value up to a concurrent change; harmless.
- **No regression test** in the PR (a reviewer asked for one); the test here is one.
- **Found along the way, not the PR's**: `allowedDowngradeVersion`'s `Minor()-1` wraps at a minor
  version 0 (`issues/etcd-downgrade-target-minor-underflow.md`, found by the reviewer; reproduced).

## Review

A fresh reviewer subagent checked the specs, contracts, postulates and tests (its test:
`notes/pr-verify/etcd-22575/review_downgrade_test.go`, log `test-review-fork-pr.log`). Resolved:

- *The specs were weaker than their comments* (should-fix): `ErrClusterVersionUnavailable` was
  allowed even once the version was known. Fixed: every spec takes `known` with the witness
  `if known then monoNatLbOwn γcv 1` in its premise, and the `ErrClusterVersionUnavailable` outcome
  requires `known = false` (`dgOutcome γcv known ek`, `InvDowngrade.lean`); re-proved.
- *A new bug in the manager, not the PR's* (should-fix): `allowedDowngradeVersion` wraps at a minor
  version 0 (`issues/etcd-downgrade-target-minor-underflow.md`; reproduced on the pin, the fork with
  the PR and upstream `main` b25719d10: `notes/pr-verify/etcd-22575/version/`). The specs cannot see
  it (they state no values).
- Confirmed: both findings above reproduce; the semver postulates match semver v3.5.0's source;
  the contracts match the adapter and `RaftCluster` code; `clusterVersionAt` is the existing
  `clusterVersionOk` with the ghost name exposed.

Open (notes): the specs state no values (the response's version, which manager error): the result
is safety plus "a nil error comes with a response", which is what the gRPC handler needs; the
contracts in the premises (`clusterVersionAt`, `srvVersionOk`, `version.serverOk`) are not
discharged by a proof of the server's construction, and the cluster version's monotonicity rests on
`Recover` reading a backend in which the version was saved (no path back to `nil` found);
`version.dgErrVars` says only that the manager's error variables hold some value, though their
`errors.New` initialization is now translated; the semver postulates read the version without a
points-to (fine for the fresh copies `RaftCluster.Version()` returns); the response's version is read
before the action (at bootstrap the version moves from 3.0 to the real one, so a reply can report 3.0
while the validation used the newer version); `ErrUnknownMethod` has no gRPC mapping (pre-existing).
