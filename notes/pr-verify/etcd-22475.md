## Verdict

The PR's write path is correct, as far as it is verified. It was proved that:
- every key index in the tree keeps, in `liveSize`, `len(key) + len(value)` of the key's live
  version in the state after the writer's log, and `0` for a deleted key;
- `treeIndex.Put` and `treeIndex.Tombstone` return exactly the change of that key's part;
- a write transaction's `liveSizeDelta` is always the change of the whole live payload (the sum over
  the state) from the committed state to the state after its pending changes. Overwrites in one
  transaction, delete-then-put and range deletes are all included;
- `End` passes that value to `liveKVPayloadGauge.Add` when it is non-zero.

Nothing the verified code did before changed: every existing spec in mvcc and above it is re-proved
unchanged.

Not covered by the proof:
- **The gauge's own value.** Prometheus is translated names-only, and `Gauge.Add` is assumed only to
  return. "The gauge equals the live payload" follows from the proved delta only informally: `Add`s
  commute, `float64` is exact below 2^53, and restore `Set`s the total.
- **Restore.** `restoreIntoIndex` and `store.restore` are untranslated. The `store.restore` axiom
  covers an empty backend only, and is unchanged. Randomized Go tests cover restore: restarts,
  snapshot `Restore`, compaction, cache eviction, and a crash in the middle of a compaction followed
  by its resume. All pass.

Findings: no bug in the PR. One design limitation, shared with `keysGauge`: the gauge is per process,
not per store (below).

## The specs

- **The model** (`Proof/go_etcd_io/etcd/server/v3/storage/mvcc/LivePayload.lean`, new):
  - `payload s` is the sum of `len(key) + len(value)` over a state's key-values (the PR's
    definition of the metric);
  - `liveSz s k` is the key's part of it;
  - `liveW log k` and `payloadW log` are those parts after a log, as 64-bit words;
  - `pendDelta ilog pend = payloadW (ilog ++ [pend]) − payloadW ilog`.

  Lemmas:
  - `payload_applyChange`: one change moves the payload by the key's part;
  - `pendDelta_snoc`: the transaction's delta through one more change;
  - `liveW_absent`: a key without an index, even after compaction, has part `0`;
  - `stateAfter_eq_stateOfEvs`: the state is a function of the index's events.
- **The invariant** (`InvIndex.lean`): `idxLockInv` gains `ownLive L (ilog ++ [pend]) q`. Every key
  index in the tree has `liveSize ↦ liveW (ilog ++ [pend]) key`, at the lock's fraction.
  - It is fractional (`ownLiveI_split`/`_combine`), so readers holding an `RLock` fraction carry it
    unchanged.
  - The writer changes exactly the written key's field under the full lock (`ownLiveI_update`, using
    the sorted, distinct keys).
  - Compaction keeps the log and drops entries (`ownLiveI_eraseIdx`).
- **`treeIndex.Put`** (`Spec/.../mvcc/treeIndex__Put.lean`).
  - Old: the key's index gets the revision, and the writer's log the change `.put k v l`; returns
    nothing.
  - New: the same, given `valueSize = len(v)`, and it returns `liveW (ilog ++ [pend ++ [.put k v l]]) k
    − liveW (ilog ++ [pend]) k`.
  - The old code had no return value, so there is no implication lemma between the two. The only
    caller, `storeTxnWrite.put`, is re-proved.
- **`treeIndex.Tombstone`** (`Spec/.../mvcc/treeIndex__Tombstone.lean`).
  - Old: returns `nil`.
  - New: returns `(liveW after k − liveW before k, nil)`; after a delete the part is `0`.
  - The only caller, `storeTxnWrite.delete`, is re-proved.
- **`treeIndex.Insert`** (`Spec/.../mvcc/treeIndex__Insert.lean`, not changed by the PR). It now
  requires the inserted key index's `liveSize ↦ liveW (ilog ++ [pend]) k` and gives back the replaced
  one's. It has no verified caller: only the untranslated `restoreIntoIndex` calls it.
- **The write transaction** (`InvStore.lean`, `storeTxnWriteIs`/`storeTxnWriteCore`): the struct's
  new field holds `pendDelta ilog pend`. The specs of `put`, `delete`, `deleteRange`, `End`, `Write`,
  `Range` and the metrics and watchable wrappers keep their statements.
- **The trust base addition** (`Base.lean`, `mvccInit`): `liveKVPayloadGauge` is a fixed gauge whose
  `Inc`/`Dec`/`Add` return, the same assumption as for `keysGauge` and the other mvcc gauges. Its
  value is not modelled. Package init is assumed, as for every metric of mvcc.

## Findings

- **No bug found in the PR.**
- **Design limitation (low), shared with `keysGauge`.** `liveKVPayloadGauge` is a package-level
  global, and `store.restore` `Set`s it, first to 0 and then to the store's total. Two stores in one
  process therefore add into one gauge, and restarting or restoring one store discards the other's
  contribution, so the gauge can go negative.
  - etcd runs one store per server process (`server.go`), so production is unaffected.
  - In-process multi-member clusters (etcd's own integration tests, embedders running several
    servers) see a meaningless value. The PR's integration test uses a single member.
  - Reviewer's test: `TestLiveKVPayloadTwoStoresShareGauge`.
- Transient values (info): the metric reads 0 during a `Restore`, between `Set(0)` and `Set(total)`.
  After a write, readers can see the new state briefly before `End`'s `Add` (it runs after
  `tx.Unlock`). Concurrent writers' `Add`s commute. All of this matches `keysGauge`.
- The PR's open question (the tests' `fakeIndex` returns zero deltas) does not affect the verified
  code.

Tests, in `notes/pr-verify/etcd-22475/` (README there):
- `kvstore_live_payload_random_test.go`: `TestLiveKVPayloadRandomized`, 40 random histories, with
  the gauge checked against `Range` after every step. It passes on the PR head and fails on a
  mutation of `restoreIntoIndex`'s update.
- `kvstore_live_payload_review_test.go` (reviewer): the two-store sharing above, and
  `TestLiveKVPayloadPartialCompactionResume`, a crash at every point of a scheduled compaction
  followed by restart and resume. Both pass on the PR head.

## Draft review comment (for the user to edit and post)

> I went through the write path and the restore path. The per-key `liveSize` in the index, together
> with the deltas returned by `Put`/`Tombstone` and accumulated in `storeTxnWrite`, always adds up to
> the change of the sum of `len(key)+len(value)` over the live keys. That includes overwrites,
> delete-then-put and range deletes within one txn. Compaction never needs to touch it, because it
> never removes a live revision or the index entry of a live key.
>
> I also ran randomized histories against the gauge: puts, deletes, txns, compaction at random
> revisions, restarts and `Restore` with a small `restoreChunkKeys`, so that the restore cache evicts
> entries. The gauge matched a full `Range` after every step, including after a crash in the middle
> of a compaction followed by its resume.
>
> One limitation, the same as `keysGauge`: the gauge is per process, and `restore` sets it outright.
> With two stores in one process, e.g. a multi-member in-process integration cluster, the values mix,
> and restarting one store resets the other's contribution (I could make it go negative). That is
> fine for a normal etcd process with one store, but it may be worth a comment on the metric, or
> keeping the per-member tests at `Size: 1`, as the new integration test does.
