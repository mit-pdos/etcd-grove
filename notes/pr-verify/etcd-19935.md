## Verdict

**The PR does not do what it says, and it regresses the common case.** Its new test
`errors.Is(err, context.Canceled)` looks at the error accumulated so far, `err`, instead of the
stream's own error, `werr`. So (1) a stream whose `close` reports `context.Canceled`, the usual
result of closing a stream, is no longer treated as a successful close: `Close()` on a watcher
with an open watch now returns `context canceled` (wrapped by `errors.Join`) where it returned
`nil`; and (2) once a canceled stream has been joined into `err`, every later stream's real error
is skipped, so the bug the PR means to fix (a real error lost because of a `context.Canceled`)
remains, in the other order. Both are shown by Go tests at the PR head; the fork's existing test
`TestWatchProgressBroadcastAfterServerCancel` also fails intermittently with the PR (3 of 20
runs), on its final `w.Close()`. The one-word fix, `errors.Is(werr, context.Canceled)`, passes all
of them. The bug the PR describes in the old code is real and is recorded in
`issues/etcd-watcher-close-drops-error.md`.

What is verified: the existing spec of `watcher.Close` (no panic, every stream closed, the lock
protocol kept; nothing about the returned error) still holds of the PR's code, over two new
trust-boundary axioms for `errors.Join` and `errors.Is` of a joined error. The intended behavior
for canceled streams is stated (`watcher.Close.spec_canceledIsSuccess`) and proved of the code
*before* the PR, conditionally on every stream's `close` reporting `nil` or `Canceled` (a check of
`Close`'s loop logic); the PR's code does not meet it (the tests are the counterexample). The other
half of the intent ("a real error is returned") is shown by test only, for both versions; it is
not stated in Lean (it needs to track which stream returned what).

## Specs

- Old (and kept) spec, `Spec/go_etcd_io/etcd/client/v3/watcher__Close.lean`, `watcher.Close.spec`:
  given the watcher's invariant, `Close` returns some error. The proof
  (`Proof/go_etcd_io/etcd/client/v3/watcher__Close.lean`) is adapted to the new loop: the loop
  invariant now carries `joinedStatusErrOk err` (a tree of `status` errors and joins) instead of
  `statusErrOk err`, and the call to `errors.Join` with the slice literal `[err, werr]` is
  through `errors.Join.spec`.
- Intended spec, same file, `watcher.Close.spec_canceledIsSuccess`: if every stream's `close`
  reports `nil` or `context.Canceled` (the scenario `watchGRPCStream.close.spec_nilOrCanceled`,
  `Spec/go_etcd_io/etcd/client/v3/watchGRPCStream__close.lean`), `Close` returns `nil` — the
  comment "Consider context.Canceled as a successful close", which the PR keeps. Proved of the
  old code: `notes/pr-verify/etcd-19935/old-code-proof.patch` (applies to `lean` `51547df02`;
  theorem `watcher.Close.wp_canceledIsSuccess`, no `sorry`, `#print axioms` shows no `sorryAx`;
  its callee specs are hypotheses). **It is a conditional result**: its premise is a scenario
  triple over every stream's `close`, which the real `close` does not meet in general (it can
  return a real error left in `errc`), so the theorem checks `Close`'s own loop logic with `close`
  as a black box reporting `nil` or `Canceled`; it does not say the old code is right (it is not:
  `issues/etcd-watcher-close-drops-error.md`). A non-vacuous statement of both halves needs
  `close`'s spec to report each stream's outcome and `Close`'s spec stated over those outcomes;
  not done. The PR's code: not provable over these axioms (they do not determine
  `Is(Join(nil, Canceled), Canceled)`); the Go tests are the counterexample.

## Trust base (step 7)

New axioms (both at the standard library's boundary, because Perennial translates `errors`'s
`join.go` names-only, `Perennial/Code/errors.toml`):

- `errors.Join.wp_proof` (`Proof/errors/Join.lean`, spec `Spec/errors/Join.lean`): `Join(errs)`
  returns `nil` exactly when every element is `nil`, and the result is again a
  `joinedStatusErrOk` tree if the elements are. Go's `join.go`: it counts the non-nil errors,
  returns `nil` if none, else a fresh `*joinError` holding them (methods `Error`, `Unwrap()
  []error`; no `Is`/`As`).
- `errors.IsJoinedStatusErr.wp_proof` (`Proof/errors/IsJoinedStatusErr.lean`): `errors.Is(err,
  target)` on such a tree with a pointer-error target returns a boolean, `false` for `err = nil`
  and `true` for `err = target`. This is Perennial's proved `errors.Is` spec except for its
  premise `TreeTyped` (Go's typing of the tree's errors), the same assumption the existing
  `errors.IsStatusErr` axiom makes for a single `status` error.
- Shared definition `joinedStatusErrOk` (`Proof/errors/JoinedStatusErr.lean`), with proved lemmas
  `joinedStatusErrOk_nil` and `joinedStatusErrOk_of_statusErrOk`.

The axiom `errors.IsStatusErr.wp_proof` is no longer used by `watcher.Close` (still by
`isSafeRetry` and `shouldRefreshToken`). No `sorry` added. `#print axioms` of
`watcher.Close.wp_proof` on this branch versus `lean`: see "Build" below.

## Findings

1. **PR regression: a canceled stream makes `Close` fail.** `TestWatcherCloseCanceledIsSuccess`
   (one stream whose `close` reports `context.Canceled`) and `TestWatcherCloseIgnoresCanceled`
   (a real watch over a fake gRPC stream, then `Close`; fails within a few hundred iterations) fail
   at the PR head with `Close() = context canceled, want nil`; both pass at the base.
2. **PR does not fully fix the bug it describes.** `TestWatcherCloseKeepsRealError` (one stream
   with a real error, one with `context.Canceled`, map order random): at the PR head, when the
   canceled stream comes first the real error is skipped and `Close` returns `context canceled`;
   at the base, when the canceled stream comes last `Close` returns `nil` (the bug the PR
   describes; recorded as `issues/etcd-watcher-close-drops-error.md`).
3. With `!errors.Is(werr, context.Canceled)` (`notes/pr-verify/etcd-19935/fix-werr.diff`) all
   three tests pass at the PR head (`upstream-head-werr-fix.log`).
4. Reviewer's measurement (`watch_close_rate_test.go`): with a live watch over a fake gRPC
   stream, the PR's `Close()` is non-nil in about 1–2% of closes (44, 38, 15 of 2000), never at
   the base: the stream's `serveWatchClient` races `close()`'s non-blocking read of `errc`, and
   `run` usually consumes the error itself. Upstream's integration `TestWatchClose` does not catch
   it (30 of 30 pass at head, base and fix), since there the stream has left `w.streams` first.
5. Pre-existing, both versions (not filed separately, noted in the issue's scope): when `run`
   stops on a halt error it has consumed from `errc`, `close()` returns nil, so `Close` never
   reports it.
6. The author's own question on the PR (`errors.Join` always wraps, even a single error): a caller
   comparing `err == X` would now see a `*joinError`; `errors.Is` still works. With finding 1 fixed
   this only affects real errors.

All tests and logs: `notes/pr-verify/etcd-19935/` (README there).

## Review

A fresh reviewer checked the two axioms against Go 1.24's `errors/join.go` and `wrap.go` (both
true of Go and weakenings of what Go does; consistent, since `Join` has no body in the model and
`IsJoinedStatusErr` is Perennial's proved `errors.Is` spec with only `TreeTyped` assumed, as
`IsStatusErr` does), the intended spec (fair statement of the comment's intent), the tests
(deterministic apart from map order, which 200 iterations cover; the fake states are reachable),
and the fix (`werr`: passes all tests, plus its three of `watch_close_review_test.go`: all
`Canceled` gives nil, two real errors are both joined without `Canceled`, a single real error comes
back wrapped). Resolved from the review: the report wrongly said `Client.Close` returns the
watcher's error (corrected above); the old-code theorem is now described as conditional. Open:
the "real error is kept" half is not stated in Lean; `errors.Join` wraps a single error (an
optional refinement: return it unwrapped when it is the only one); whether
`context.DeadlineExceeded` should count as a successful close too is the maintainers' call.

> Thanks for this. The idea is right, but the `errors.Is` check looks at the accumulated `err`
> rather than the stream's `werr`:
>
> ```go
> if werr := wgs.close(); werr != nil && !errors.Is(err, context.Canceled) {
> ```
>
> On the first iteration `err` is nil, so a stream that reports `context.Canceled` (the normal
> result, since `close()` cancels the stream's context first) is joined into `err`, and `Close()`
> now returns `context canceled` for a watcher with an open watch, where it used to return nil.
> And once a canceled error has been joined, `errors.Is(err, context.Canceled)` is true for the
> rest of the loop, so a later stream's real error is dropped, which is the case this PR is meant
> to fix. Checking `werr` instead fixes both:
>
> ```go
> if werr := wgs.close(); werr != nil && !errors.Is(werr, context.Canceled) {
>     err = errors.Join(err, werr)
> }
> ```
>
> A test that exercises both cases without a server, in package `clientv3` (builds the streams
> directly so `close()` returns a fixed error):
>
> (attach `watch_close_errors_test.go`)
>
> `TestWatcherCloseCanceledIsSuccess` and `TestWatcherCloseKeepsRealError` fail with the current
> change and pass with `werr`. `TestWatcherCloseKeepsRealError` also fails on `main`, about half
