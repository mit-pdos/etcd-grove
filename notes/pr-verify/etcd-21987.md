## Verdict

The change is sound and does what it says. Its Go code is the same as etcd#22298's, which was
verified on `pr-verify/etcd-22298` (`notes/pr-verify/etcd-22298.md`). Both replace
`sort.Sort(wb)` under `wb.used > 1` with `wb.dedupe()` in `writeback`'s existing-bucket branch.
The two diffs differ only in a comment: #22298 adds a four-line comment, #21987 adds none.

So the translation of `tx_buffer.go` is the same term. Regenerating `Code/.../storage/backend.lean`
from this PR's fork commit changed only the source line numbers in doc comments. #22298's specs and
proofs then go through unchanged, and a full `lake build` of the branch succeeds:

- `txWriteBuffer.writeback` takes any keys in a bucket written by `put`;
- `UnsafePut` no longer needs a key to be new in its lock session;
- the server's hooks no longer have to avoid repeating a key.

No new axiom, no `sorry`. The PR fixes `issues/etcd-backend-duplicate-put-stale-read.md`: the
issue's reproduction and the PR's own test both fail at the base and pass at the PR.

Not covered:
- the separate `ConcurrentReadTx` cache bug, which neither PR touches (Findings);
- the PR's performance remark (no extra sorting of the sequential `Key` bucket). It is true of the
  code, but it is not a proved property.

### The spec, old and new

They are the same as in `notes/pr-verify/etcd-22298.md`, "The spec, old and new".

- The new spec is in `Spec/go_etcd_io/etcd/server/v3/storage/backend/txWriteBuffer__writeback.lean`.
  Its premise is `W.WfR (fun _ => True)`: a bucket written by `put` may hold any keys, while a
  bucket written only by `putSeq` must still be strictly increasing.
- The old spec, kept as `backend.txWriteBuffer.writeback.spec_old` in
  `Proof/.../backend/txWriteBuffer__writeback.lean`, had the premise
  `W.WfR (fun id => R.bks.lookup id = none)`: a bucket written by `put` could repeat a key only if
  the read buffer had no such bucket.
- The postcondition of both is unchanged. Every bucket becomes `canon (old ++ new)`: sorted, with
  only the newest value of each key. The write buffer is reset.

| | #21987 (this PR) | #22298 |

| Test | `TestWritebackDedupesIntraBatchDuplicateForNonSeqBucket`: duplicates go in through `txw.put` (which also sets `bucket2seq` to false), then a no-overlap merge, then the reader's `txr.Range(k, nil, 1)` (the single-key lookup that returned the stale value) | `TestWritebackDedupesExistingBucket`: builds the buffers and `bucket2seq` directly; covers the no-overlap and the overlap case with 2 entries; reads with `bucketBuffer.Range` over a range and checks the count |

| Verification | the same spec and proof; the same trust base | `pr-verify/etcd-22298` |

Either PR fixes the bug, and the proof covers both equally. The tests differ in what they
exercise:

- #21987's test goes through `put` and the reader's single-key `Range`, the path the bug report
  describes.
- #22298's test also covers the overlap case. With two entries, though, `sort.Sort` is stable
  (insertion sort), so that case passes at the base too.

Neither test exercises the overlap path where the base actually fails: more than 12 entries, where
`sort.Sort` is not stable. The reviewer's `TestReviewOverlapManyDups` does, and both PRs fix it.
If both PRs stay open, one should be closed in favor of the other. On content they are
interchangeable. #21987 is older and linked to the issue; #22298 has the explanatory comment.

## Findings

Tests and logs are in `notes/pr-verify/etcd-21987/` (`README.md` lists each file).

- **The PR fixes `issues/etcd-backend-duplicate-put-stale-read.md`** (etcd#21986), and the proof
  confirms it. The PR's test, the issue's reproduction (`stale_read_test.go`) and #22298's
  reviewer test (`review_dup_put_test.go`) all fail at the base (`test-base-09669450f.log`). At the
  PR (`test-pr-2fc9e9d30.log`), all pass except one check, described below.
- **No bug in the PR.** The reviewer (fresh, over the specs, the model of
  `canon`/`merge`/`dedupe` and the PR) found no soundness or modeling problem. It checked these
  claims:
  - `merge`'s only caller is `writeback`;
  - the sequential `Key` bucket, written by `putSeq`, keeps its flag `true` and is neither sorted
    nor deduped;
  - dropping `wb.used > 1` changes nothing, since `dedupe` returns early when `used <= 1`;
  - the PR's test does what it says.

  Its `review_extra_test.go` adds two cases that fail at the base and pass at the PR, plus a
  `putSeq`-only check that passes at both:
  - 11 duplicates on the overlap path: the older value survives `sort.Sort`'s unstable sort;
  - `put` and `putSeq` mixed in one bucket: the read buffer is left with a key twice.

  Logs: `review-base-09669450f.log`, `review-pr-2fc9e9d30.log`.
- **Still failing at the PR, not caused by it:** the `after commit range` check of
  `review_dup_put_test.go`. That is `issues/etcd-backend-read-buffer-cache-stale-after-commit.md`
  (already recorded): the `ConcurrentReadTx` cache is keyed by `bufVersion`, which a commit's reset
  does not bump.
- No new bug in the existing code.

## Draft review comment

> This fixes #21986 and makes `writeback`'s two branches agree. Without it, `UnsafePut` has an
> unstated precondition: a key must not be put twice in one lock session into a non-sequential
> bucket that the read buffer already holds. With it, any sequence of `UnsafePut`s in a session
> leaves the read buffer sorted, with only the newest value of each key.
>
> The bug also shows up on the overlap path, not only the no-overlap fast path the test covers.
> With more than 12 entries, `sort.Sort` is not stable, so `merge`'s `dedupe` can keep the older
> of two puts. A test with a dozen duplicates on an overlapping bucket would pin that down too.
>
> #22298 makes the same code change (with a comment explaining it), so one of the two can be closed.
