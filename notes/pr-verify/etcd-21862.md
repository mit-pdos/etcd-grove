## Verdict

The change is sound as far as it was verified. It does what it says.
- **What is proved**: `isRPCSupportedForLearner` now answers "a learner serves this" exactly for
  `*StatusRequest`, `*DefragmentRequest` and a `*RangeRequest` with `Serializable` set, and
  "rejected" for every other request.
- **The proof pins the change down**: the same spec, attempted against the old code, fails in
  exactly one case, `*DefragmentRequest`.
- **No caller is affected**: the new spec implies the old one, so the one caller, the unary
  interceptor, keeps its proof unchanged. All of v3rpc's proofs rebuild.
- **The change is safe**: the defrag path has no learner-specific behaviour. On a learner, defrag
  runs exactly as on a follower, and a snapshot install waits for it under `bemu`.
- **Not covered**: the defrag path itself (`maintenanceServer.Defragment`, `EtcdServer.Defragment`,
  the backend's `Defrag`) is not translated. The interceptor's spec does not say which requests it
  rejects, so "a learner passes a Defragment request to the handler" is proved only at the level
  of `isRPCSupportedForLearner`.
- **What the PR leaves out**:
  - With auth enabled, a client that dials only the learner still cannot defrag it.
    `Authenticate` is not on the learner allowlist, so the client cannot get a token there.
  - The new comment ("local maintenance") overstates the change.
  - There is no CHANGELOG or documentation entry for a user-visible change.

### The old and new spec

Both are in `Spec/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/isRPCSupportedForLearner.lean`.
- **Old** (`spec_old`): given the request's readable shape (`learnerReqOk`), it returns some
  boolean. The docstring described the allowlist, but the postcondition did not.
- **New** (`spec`): same precondition. It returns `b` with `b = true ↔ learnerServes req ser`,
  where `ser` is the `Serializable` field it read when `req` is a `*RangeRequest`.
  `learnerServes` holds for a `*StatusRequest`, a `*DefragmentRequest` (any pointer, nil
  included), or a `*RangeRequest` with `ser = true`.
- **The difference**: the new spec states the allowlist, with Defragment on it. The old spec
  constrained nothing.
- **The proofs**, in `Proof/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/isRPCSupportedForLearner.lean`:
  - `wp_proof` proves the new spec, with no `sorry`.
  - `spec_implies_old` proves the compatibility lemma.
- **Against the old code**: the attempted proof is
  [isRPCSupportedForLearner-old-code-attempt.lean](etcd-21862/isRPCSupportedForLearner-old-code-attempt.lean),
  built in a scratch worktree of `lean`. It closes every case but one. In the default case at
  `t = *DefragmentRequest`, the left goal is `∀ x, ¬ #l = #x`, which is false
  ([log](etcd-21862/isRPCSupportedForLearner-old-code-attempt.log)). The old code answers
  `false` there.
- **Typed nil**: `(*pb.DefragmentRequest)(nil)` and `(*pb.StatusRequest)(nil)` match their `case`
  and return true, and the spec agrees. A `(*pb.RangeRequest)(nil)` would panic on
  `r.Serializable`. The precondition excludes it with a points-to at the pointer. gRPC's
  generated handlers always pass a fresh `new(X)`.

## Findings

**In the PR** (none is a bug):
1. **With auth enabled, a learner-only client still cannot defrag.**
   - A client created with a username and password against only the learner's endpoint fails
     at creation with `etcdserver: rpc not supported for learner`. Its `Authenticate` is rejected
     by the same gate, so `etcdctl --endpoints=<learner> --user ... defrag` still fails.
   - A client authenticated at a voter can defrag the learner through
     `Maintenance.Defragment(ctx, learnerURL)`. Simple tokens are assigned by the raft-applied
     `Authenticate` on every member, the learner included.
   - So `etcdctl defrag --cluster` works.
   - Client-certificate auth (CN) and JWT tokens are checked locally on the learner.
   - Test: [maintenance_learner_auth_test.go](etcd-21862/maintenance_learner_auth_test.go), which
     passes at the PR head, showing both behaviours
     ([log](etcd-21862/maintenance_learner_auth_test-pr-head.log)).
   - The issue's reproduction does not say whether auth was on.
2. **The new comment is inaccurate.** It says "learner is allowed to serve local maintenance,
   serializable read, and endpoint status". `Hash` and `HashKV` are just as local, and they are
   still rejected, as are `Alarm`, `MoveLeader` and `Downgrade`. The only maintenance RPCs a
   learner serves are `Status`, `Defragment` and (stream) `Snapshot`. "in v3.4" also no longer
   holds for Defragment.
3. **No CHANGELOG or docs entry.** This is a user-visible behaviour change. The precedent is
   CHANGELOG-3.4's "Add Learner support Snapshot RPC". The website's learner design page says
   learners reject all requests other than serializable reads and member status. That sentence
   was already stale after the Snapshot change.
4. **The unit test checks only the positive case.** It does not check that other requests
   (`Hash`, `HashKV`, `Alarm`, a non-serializable `Range`, `Put`) are still rejected. The new
   spec states all of these. A table test would pin them in Go.

**Safety of defrag on a learner** (manual review, mine and the reviewer's): a learner behaves as
a follower.
- `EtcdServer.Defragment` takes `bemu`: `Lock` at the PR head, `RLock` at the fork pin, from the
  newer upstream "non-blocking defragmentation" commit. Either way `applySnapshot`'s
  `bemu.Lock` waits for it, so a snapshot install from the leader cannot swap the backend
  mid-defrag.
- A defrag stalls the learner's apply, as it does a follower's. A `MemberPromote` during it may
  fail with `ErrLearnerNotReady`, which is benign, and the learner is not in any quorum.
- `isPermitted` reads the learner's replicated auth store.
- The health notifier's stop-on-defrag path is the same as on a follower.
- grpc-proxy forwards the call.

**In the existing code**: nothing new for `issues/`. The reviewer noted that with
`--experimental-stop-grpc-service-on-defrag`, two overlapping defrags set the health status back
to SERVING when the first finishes (`health.go` `defragStarted`/`defragFinished` are not
counted). That code is not translated or verified, and it is not recorded as an issue here.

**Existing issue nearby**: `issues/etcd-unary-interceptor-learner-removed.md` describes the same
gate panicking if the local member is removed between `IsMemberExist` and `IsLearner`. The PR
does not touch that, and it neither fixes nor worsens it.

## Draft review comment (for the user to edit and post)

> The change looks correct and safe to me: a learner's backend is the same as a follower's, and
> `EtcdServer.Defragment` holds `bemu`, so a snapshot install from the leader waits for the
> defrag to finish. A few suggestions:
>
> - The comment now says learners serve "local maintenance", but `Hash`, `HashKV`, `Alarm`,
>   `MoveLeader` and `Downgrade` are still rejected. Maybe: "learner is allowed to serve
>   serializable read, endpoint status and defragment".
> - Could the unit test be a table that also checks requests that must stay rejected (a
>   non-serializable `RangeRequest`, `PutRequest`, `HashKVRequest`, `AlarmRequest`)? Nothing else
>   pins the rejection list.
> - With auth enabled, a client that dials only the learner still can't defragment it: creating
>   the client fails, because `Authenticate` isn't served by a learner. Defragmenting through a
>   client authenticated at a voter (`etcdctl defrag --cluster`, or `Defragment(ctx,
>   learnerURL)`) works. That covers #21740's `--cluster` case; it may be worth saying so in the
>   description, or adding `AuthenticateRequest` if learner-only access is wanted.
> - This is a user-visible change, so it probably needs a CHANGELOG entry, like the 3.4 entry
>   for learners serving Snapshot.
