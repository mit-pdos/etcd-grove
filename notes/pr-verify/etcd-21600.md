  - `go build ./...`, `go vet` and `go test -race -count=3 ./cache/...` pass, as do the PR's integration tests (`TestCacheWatchWithPrevKV`, `TestCacheUnsupportedWatchOptions`, `TestWatch`, `TestCacheLaggingWatcher`).
- **Where the verified code differs from the PR**:
  1. `Cache.Watch`: the fork's base already has progress-notify support (a timer and a `progressChan` select case), and the PR's base does not. The resolution keeps both: the PR's `mergedCtx` replaces the two `Done` cases, around the base's timer code. The `ErrUnsupportedRequest` comment drops both `WithPrevKV` and `WithProgressNotify`.
  2. `attachPrevKV`'s `clone := *ev` copies a gogoproto `Event` by value. The fork's `mvccpb` is protobuf-go v2, whose messages hold a `MessageState`; there the copy is a `go vet` error (`copylocks`) and not how to copy a message. The fork builds `clone := &mvccpb.Event{Type: ev.Type, Kv: ev.Kv}` instead.
     - This is the same for the cache: its own upstream watch does not ask for `PrevKv`, so the delivered events have none.
     - It does drop unknown fields, which the cache's events do not have.
     - Upstream `main` moved to protobuf-go v2 after the PR's base, so the PR needs this change when it is rebased.
  3. `*mvccpb.Event` instead of its alias `*clientv3.Event` in `attachPrevKV` and `isCreateEvent`. This is the fork's existing Goose rewrite, with no behavior change.
- **This branch**: `pr-verify/etcd-21600` (worktree `/shared/etcd-grove-pr/etcd-21600`), off `lean` `51547df02`. `etc/goose.py --check` fails on it by design, because the translation is of the fork branch.

## Verdict

The PR is memory-safe, as far as verified. It never writes the events it shares with other
watchers. Every `PrevKv` it attaches is the key's value in etcd's own state at some revision before
the event: never a wrong or future value.

It is not complete, though. Several ordinary situations deliver update and delete events with
`PrevKv == nil` for a key that existed, and the watch is not canceled:

- **A slow consumer**, once the store's history window has moved past the event's previous
  revision (finding 1).
- **A watch from the oldest revision still in history** (finding 2): its first event, every
  time.
- **A reconnect at an unchanged revision** (finding 3): every buffered or replayed event.

The new `store.waitForRev` can also miss its context's cancellation (finding 4). The wakeup is
lost, so the watch goroutine, and with it `Cache.Close()`, can block until the store next
changes. The fork's error cancel response has a nil `Header` (finding 5); upstream `main` has the
same problem once the PR is rebased. All five are shown by Go tests.

The proof covers safety and partial correctness only. It cannot see 1–3 because the spec allows
`nil`. It cannot see 4 because the proof is of partial correctness. It rests on one new
trust-boundary axiom (`context.AfterFunc`) and three `sorry`s, all in error-message and
event-field plumbing.

### The specs

- **`Cache.validateWatch`** (`Spec/go_etcd_io/etcd/cache/v3/Cache__validateWatch.lean`).
  - Old: rejects `WithPrevKV`, `WithFragment`, `WithCreatedNotify`, `WithFilterPut`, `WithFilterDelete`.
  - New: the same without `WithPrevKV`.
- **`Cache.Watch`** (`Spec/go_etcd_io/etcd/cache/v3/Cache__Watch.lean`).
  - Old: every received prefix is a `cacheWatchLog` in one of three forms:
    - the demux's delivery;
    - the delivery, then a compaction cancel;
    - a single reject cancel.
  - New: the same, plus two things for `WithPrevKV` (`watchPK o pfx = some pfx`):
    - a fourth form: the delivery up to a response `r0` whose lookup failed, with `r0` replaced by a cancel response that has no events;
    - every response carries `respPK`: each event either is a create event delivered as is, or has its `PrevKv` field `p` with `p = nil`, or `p` is a key-value of the event's key in etcd's state at some revision `r ≤ ModRevision-1` (`isEtcdKvs`, `prevKvOk`).
  - A `WithPrevKV` watch also needs a store reader token (`watchReader`), which its goroutine keeps.
  - For non-`PrevKV` requests the new spec says what the old one did: `pk = none`, the fourth form needs `pk ≠ none`, and `respPK none = True`.
  - Not shown as a Lean lemma: that the new spec implies the old for such requests. It holds by unfolding.
- **`Cache.attachPrevKV`** (`Spec/.../Cache__attachPrevKV.lean`), by a store reader, for `*rp` modelled by `r`:
  - either `nil`, with `*rp` a response with the same model whose events satisfy `respPrevKvs` (fresh events, or the delivered create events);
  - or an error whose `Error()` returns.
- **`store.waitForRev`** (`Spec/.../store__waitForRev.lean`): `nil` only with `storeRevLb γ rev`, else the context's error once it is done. Partial correctness: it may not return (finding 4).
- **`isCreateEvent`** (`Spec/.../isCreateEvent.lean`): `Type == PUT && CreateRevision == ModRevision`.

The old `Cache.Watch` spec does not hold of the new code for `WithPrevKV` requests: the old code
sent a single reject cancel response for them, and the new code delivers events. That is the PR's
intended change.

What `prevKvOk` does not say, from the reviewer:
- that `PrevKv` is non-nil when the key existed at `ModRevision-1` (findings 1–3 show the code does not do this);
- that the value is the one at exactly `ModRevision-1`, rather than at some earlier `r` (the reviewer found no path that returns a stale value, and believes the exact statement is provable from a stronger store invariant: open);
- that a create event's `PrevKv` is nil.

## Findings

Every test is in `notes/pr-verify/etcd-21600/` (see its `README.md`).

1. **Slow consumer loses `PrevKv`, medium.**
   - What happens: a `WithPrevKV` watcher whose buffered events fall out of the store's history window (`HistoryWindowSize` snapshots) gets `PrevKv == nil` for update and delete events. `attachPrevKV` treats `ErrCompacted` from `store.Get` as "leave nil", and the watch continues.
   - Test: `prevkv_probe_test.go` `TestCacheWatchPrevKVSlowConsumerLosesPrevKV`, deterministic. With window 4 and 10 updates, 6 events have no `PrevKv`. It fails on the PR head and on the fork branch.
   - etcd's server also omits `PrevKv` on a range error, but there that needs a real compaction. The cache's window is 2048 revisions by default.
2. **First event of a watch from the oldest revision in history has no `PrevKv`, medium (reviewer).**
   - Cause: the store and the demux keep the same number of entries, so the snapshot before the demux's oldest batch is already gone. A watch `WithRev(minRev)` is accepted, but its first event gets `nil`.
   - Test: `review_prevkv_test.go` `TestReviewPrevKVHistoricalWatchOldestRev`. It fails 20 runs out of 20.
   - Possible fix: give the store history one more slot than the demux.
3. **Reconnect at an unchanged revision drops `PrevKv`, medium (reviewer).**
   - Cause: `store.Restore` rebases the store's history to the single snapshot R, while `demux.Init(R+1)` keeps the watchers and their history. Every buffered or replayed event at a revision ≤ R then gets `nil`.
   - Test: `review_prevkv_test.go` `TestReviewPrevKVLostAfterReconnectSameRev`. It fails 20 runs out of 20.
4. **`waitForRev` misses its context's cancellation, low to medium.**
   - Cause: `context.AfterFunc(ctx, s.revCond.Broadcast)` broadcasts without the store's lock. When the broadcast lands between the waiter's `s.latest.rev < rev` check and its `Wait()`, it is lost, and `waitForRev` sleeps until the store's revision next changes.
   - Effect: with no more writes, the watch goroutine never exits, and `Cache.Close()`'s `waitGroup.Wait()` hangs. Rare, because the window is narrow.
   - Test: `prevkv_probe_test.go` `TestStoreWaitForRevLostWakeup`. It hits the race in about 1000–4000 iterations, on the PR head and on the fork branch.
   - Fix: broadcast under the write lock, or check `ctx.Err()` before `Wait()` and broadcast under the lock.
   - The pinned code's `waitTillRevision` has the same pattern: `issues/cache-waittillrevision-lost-wakeup.md`, test `waittillrevision_probe_test.go`.
5. **The error cancel response has a nil `Header`, low.**
   - In the fork, and in upstream `main` since `WatchResponse.Header` became a `*pb.ResponseHeader`, the response `WatchResponse{Canceled: true, CancelReason: err.Error()}` has no header. Every other cache response sets one. A consumer that reads `resp.Header.Revision` panics.
   - Test: `review_fork_header_test.go` `TestReviewForkPrevKVCancelNilHeader`, against the fork branch. 19 of 40 runs produced it.
   - Also: this response's `Err()` is a FailedPrecondition status, not `context.Canceled`, while a watch without `PrevKV` simply closes the channel on cancellation.
6. **Not a bug: `ModRevision - 1 == 0`.** `store.Get` reads revision 0 as "latest". etcd never sends such an event: its first write is at revision 2. `prevKvOk` exempts this case explicitly.
7. **Resources.** In the model, a `WithPrevKV` watch now uses up one of the store's reader tokens for the life of its goroutine, because `attachPrevKV` read-locks the store. Go's `RWMutex` allows 2^30 readers, so this is not a practical limit.

The existing code's bug found along the way (the lost wakeup in `waitTillRevision`) is recorded
in `issues/cache-waittillrevision-lost-wakeup.md`.

## Draft review comment

> Thanks for this! A few cases where `PrevKv` comes back nil for an update or delete of a key
> that existed, without the watch being canceled (tests attached):
>
> 1. A watcher that reads slower than the history window: once the store's snapshots have moved
>    past `ModRevision-1`, `store.Get` returns `ErrCompacted` and the event goes out without
>    `PrevKv`.
> 2. A watch started with `WithRev` at the oldest revision still in the demux's history: the
>    store keeps as many snapshots as the demux keeps batches, so the snapshot before the oldest
>    batch is already gone, and the first event never has `PrevKv`.
> 3. After the upstream watch is re-established at the same revision, `store.Restore` rebases the
>    store's history to that one revision, but the demux keeps its watchers, so their buffered or
>    replayed events lose `PrevKv`.
>
> etcd itself omits `PrevKv` only after a real compaction. Would it be better to cancel the watch
> with a compaction error in these cases, or to keep one more snapshot than the demux and avoid
> rebasing the history when the revision does not change?
>
> Also, `waitForRev` registers `context.AfterFunc(ctx, s.revCond.Broadcast)`. That broadcast is
> made without holding `s.mu`, so if the context is canceled between the `s.latest.rev < rev`
> check and `Wait()`, the wakeup is lost and the goroutine sleeps until the store's revision next
> changes. With no further writes, `Cache.Close()` then blocks on the wait group. Broadcasting
> under `s.mu.Lock()` fixes it. `waitTillRevision` has the same pattern.
>
> Minor: the cancel response sent when the lookup fails has no `Header`, unlike every other
> response from the cache. With `Header` now a pointer, a consumer reading
> `resp.Header.Revision` would panic.

## Reviewer's open points

- Strengthen `prevKvOk` to the exact revision `ModRevision-1`. This needs a store invariant: etcd's prefix state is unchanged between consecutive snapshots.
- Add `PrevKv ↦□ null` to the create case. This needs `eventAt` to carry the field.
- Tie the fourth `cacheWatchLog` form to the watch's context.
- `context.AfterFunc`'s axiom assumes that Perennial's `cancelCtx` children invariant accepts an `*afterFuncCtx`. The reviewer did not check this.
