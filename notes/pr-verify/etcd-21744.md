# Formal Verification Report: `etcd-io/etcd#21744`

- **PR**: [`etcd-io/etcd#21744`](https://github.com/etcd-io/etcd/pull/21744) — `server, e2e: auto-promote learners that have caught up with the leader`
- **PR Head SHA**: `b3a94fda4d5d860dfbf4ef9491fcb9c05264fea0`
- **Base etcd Revision (`goose-lean`)**: `bc9c3868ced67e518fb2fecba44ce0fa70b7303b`
- **Goose Fork Branch**: `pr-etcd-21744-goose-lean` (`6ffdd8496a7879fc1a61f1880cc4312e4a910fb0`)
- **Verification Branch**: `pr-verify/etcd-21744`
- **Verdict**: **CONDITIONALLY SOUND WITH 1 HIGH-SEVERITY LIVENESS BUG + 1 MEDIUM-SEVERITY ERROR-CLASSIFICATION DEFECT**
  - When `AutoPromoteLearners` is at its default (`false`, Alpha feature gate), `EtcdServer.Start` is **verified sound** (`EtcdServer.wp_Start` in [`Link.lean`](../../Proof/go_etcd_io/etcd/server/v3/etcdserver/Link.lean)) and preserves all existing server/apply/linearizable-read/lease/Start specifications and caller `common.newServer` with **zero new axioms**.
  - When `AutoPromoteLearners` is enabled (`true`), `EtcdServer.Start` (`EtcdServer.Start.wp_proof_autoPromote`), `EtcdServer.monitorAutoPromoteLearners` (`EtcdServer.wp_monitorAutoPromoteLearners`), and `EtcdServer.tryAutoPromoteLearners` (`EtcdServer.wp_tryAutoPromoteLearners`) are **memory-safe and protocol-safe** once each `s.promoteMember` call returns, **but** our specification and proof work uncovered two bugs in `tryAutoPromoteLearners`:
    1. **Finding 1 (HIGH — Missing `ReqTimeout()` deadline on `ctx` in `tryAutoPromoteLearners` can permanently deadlock `monitorAutoPromoteLearners` and leak a wait registration in `s.w`)**: `tryAutoPromoteLearners` constructs `ctx := s.authStore.WithRoot(s.ctx)` without a timeout/deadline and passes it directly to `s.promoteMember(ctx, uint64(m.ID))` -> `s.configure(ctx, &cc)`. Unlike `s.raftRequest` -> `s.processInternalRaftRequestOnce` (`v3_server.go:1110`, which wraps `ctx` in `context.WithTimeout(ctx, s.Cfg.ReqTimeout())`), `s.configure` (`server.go:1775-1812`) has no internal timeout and selects only on `<-ch`, `<-ctx.Done()`, and `<-s.stopping`. If `s.r.ProposeConfChange(ctx, cc)` returns `nil` and the `ConfChange` is never applied — for example, when `go.etcd.io/raft/v3` (`stepLeader`, `raft.go:1326-1353`) silently rewrites a concurrent `EntryConfChange` into an empty `pb.EntryNormal` (`len(Data) == 0`) while an earlier `ConfChange` is still unapplied (`r.pendingConfIndex > r.raftLog.applied`), or when leadership/quorum is lost before the proposed entry commits — `s.configure` blocks forever on `<-ch`, permanently wedging `monitorAutoPromoteLearners` for the rest of the server's lifetime and leaking `s.w.Register(cc.GetId())`. Furthermore, because `s.ctx` has no deadline, `case errorspkg.Is(err, errors.ErrTimeout)` in `tryAutoPromoteLearners`'s `switch` is **unreachable dead code** (mechanized in `EtcdServer.parseProposeCtxErr.wp_canceled_ne_timeout`).
    2. **Finding 2 (MEDIUM — Transient leadership-flip / proposal-timeout errors omitted from `tryAutoPromoteLearners`'s `switch`)**: `tryAutoPromoteLearners` classifies 10 errors as expected/benign (`Debug("auto-promote skipped")`), but omits `raft.ErrProposalDropped`, `errors.ErrTimeoutDueToLeaderFail`, and `errors.ErrTimeoutDueToConnectionLost`. When any of these transient errors is returned by `s.promoteMember`, the 10-way `switch` falls into `default:`, incrementing `learnerPromoteFailed` and logging `Warn("auto-promote failed")` (mechanized in `finding2_ErrProposalDropped_mem_false`, `finding2_ErrTimeoutDueToLeaderFail_mem_false`, `finding2_ErrTimeoutDueToConnectionLost_mem_false`, and `EtcdServer.tryAutoPromoteLearners.wp_default_forced`).

## 3. Detailed Findings

### Finding 1 (HIGH): Missing `ReqTimeout()` deadline on `ctx` in `tryAutoPromoteLearners` can permanently deadlock `monitorAutoPromoteLearners` and leak `s.w` registration

#### Location
- `server/etcdserver/server.go:2398-2406` (`(*EtcdServer).tryAutoPromoteLearners`)
- Interacts with `server/etcdserver/server.go:1525-1554` (`(*EtcdServer).promoteMember`), `server/etcdserver/server.go:1775-1812` (`(*EtcdServer).configure`), `server/etcdserver/server.go:1979-1983` (`(*EtcdServer).applyEntryNormal`), and `go.etcd.io/raft/v3/raft.go:1326-1353` (`stepLeader`).

#### Mechanism
In `tryAutoPromoteLearners` (`server/etcdserver/server.go:2398-2406`):
```go
func (s *EtcdServer) tryAutoPromoteLearners() {
	lg := s.Logger()
	ctx := s.authStore.WithRoot(s.ctx)
	for _, m := range s.cluster.Members() {
		if !m.IsLearner {
			continue
		}
		_, err := s.promoteMember(ctx, uint64(m.ID))
```
Compare how internal background monitors in `EtcdServer` invoke normal Raft requests versus membership reconfiguration (`s.configure`):
- When `s.LeaseRevoke(ctx, ...)` or `s.CorruptCheck` calls `s.raftRequest` -> `s.raftRequestOnce` -> `s.processInternalRaftRequestOnce(ctx, r)` (`server/etcdserver/v3_server.go:1110-1111`), `processInternalRaftRequestOnce` explicitly wraps `ctx` in a per-request timeout:
  ```go
  cctx, cancel := context.WithTimeout(ctx, s.Cfg.ReqTimeout())
  defer cancel()
  ```
- In contrast, `s.promoteMember(ctx, uint64(m.ID))` calls `s.configure(ctx, &cc)` (`server/etcdserver/server.go:1775-1812`), which expects its caller (normally the gRPC server interceptor or HTTP handler) to supply a deadline-bounded `ctx`:
  ```go
  func (s *EtcdServer) configure(ctx context.Context, cc *raftpb.ConfChange) ([]*membership.Member, error) {
      lg := s.Logger()
      cc.Id = new(s.reqIDGen.Next())
      ch := s.w.Register(cc.GetId())

      start := time.Now()
      if err := s.r.ProposeConfChange(ctx, cc); err != nil {
          s.w.Trigger(cc.GetId(), nil)
          return nil, err
      }

      select {
      case x := <-ch:
          ...
      case <-ctx.Done():
          s.w.Trigger(cc.GetId(), nil) // GC wait
          return nil, s.parseProposeCtxErr(ctx.Err(), start)
      case <-s.stopping:
          return nil, errors.ErrStopped
      }
  }
  ```
Because `s.ctx` is created with `context.WithCancel(context.Background())` in `NewServer` (`server.go:534`) and only canceled when the server stops (`server.go:634`), `ctx := s.authStore.WithRoot(s.ctx)` has **no deadline**.

Consequently, if `s.r.ProposeConfChange(ctx, cc)` returns `nil` (`err == nil`) and the `ConfChange` entry is never applied as an `EntryConfChange`, `s.configure` blocks forever on `<-ch`:
1. **Concurrent `ConfChange` in `go.etcd.io/raft/v3` (`pendingConfIndex > applied`)**:
   In `go.etcd.io/raft/v3` (`stepLeader`, `raft.go:1326-1353`), when `r.pendingConfIndex > r.raftLog.applied` (e.g., an earlier `ConfChange` was proposed just before `monitorAutoPromoteLearners` woke up on `firstCommitInTerm` or `monitorVersionInterval` and has not yet been applied back to Raft via `ApplyConfChange`), `stepLeader` does **not** return an error from `ProposeConfChange`; instead, it logs `"ignoring conf change ... possible unapplied conf change"` and overwrites the `EntryConfChange` in-place with `m.Entries[i] = pb.Entry{Type: pb.EntryNormal}` (`len(Data) == 0`). When `EtcdServer.applyEntryNormal` (`server.go:1979-1983`) applies that entry:
   ```go
   if len(e.Data) == 0 {
       s.firstCommitInTerm.Notify()
       return
   }
   ```
   it returns early without calling `s.w.Trigger(cc.GetId(), ...)`.
2. **Leadership or quorum loss after `ProposeConfChange` returns `nil`**:
   `ProposeConfChange` only steps `MsgProp` into the local Raft state machine. If the leader steps down before the entry is committed and a new leader overwrites the uncommitted entry, `applyConfChange` is never called for `cc.GetId()`.

In both scenarios:
- `s.configure(ctx, &cc)` blocks forever in `select { case x := <-ch: ... case <-ctx.Done(): ... case <-s.stopping: ... }`.
- The single `monitorAutoPromoteLearners` goroutine is permanently deadlocked for the remainder of the server's lifetime (even if this node remains leader or is re-elected leader later, and even if other learners in `s.cluster.Members()` are ready to be promoted).
- The wait registration `s.w.Register(cc.GetId())` is leaked in `s.w` until server shutdown.
- As proved in [`EtcdServer.parseProposeCtxErr.wp_canceled_ne_timeout`](../../Proof/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__tryAutoPromoteLearners.lean), `errors.ErrTimeout` in `tryAutoPromoteLearners`'s `switch` is dead code because `ctx.Err()` on `s.ctx` can only ever be `context.Canceled` (`errors.ErrCanceled`).

#### Suggested Fix
Wrap each learner promotion attempt in `tryAutoPromoteLearners` with `context.WithTimeout(ctx, s.Cfg.ReqTimeout())`, matching `processInternalRaftRequestOnce`:
```go
func (s *EtcdServer) tryAutoPromoteLearners() {
	lg := s.Logger()
	ctx := s.authStore.WithRoot(s.ctx)
	for _, m := range s.cluster.Members() {
		if !m.IsLearner {
			continue
		}
		cctx, cancel := context.WithTimeout(ctx, s.Cfg.ReqTimeout())
		_, err := s.promoteMember(cctx, uint64(m.ID))
		cancel()
		if err == nil {
```

### Finding 2 (MEDIUM): Incomplete transient error classification in `tryAutoPromoteLearners`

#### Location
- `server/etcdserver/server.go:2427-2451` (`(*EtcdServer).tryAutoPromoteLearners`)

#### Mechanism
`tryAutoPromoteLearners` lists 10 errors in its `switch` that are treated as expected/benign skip conditions (`lg.Debug("auto-promote skipped", ...)` without incrementing `learnerPromoteFailed`):
```go
		switch {
		case errors.Is(err, membership.ErrIDNotFound),
			errors.Is(err, membership.ErrMemberNotLearner),
			errors.Is(err, errors.ErrCanceled),
			errors.Is(err, errors.ErrStopped),
			errors.Is(err, errors.ErrTimeoutWaitAppliedIndex),
			errors.Is(err, errors.ErrTimeout),
			errors.Is(err, errors.ErrLeaderChanged),
			errors.Is(err, errors.ErrNotLeader),
			errors.Is(err, errors.ErrNotEnoughStartedMembers),
			errors.Is(err, errors.ErrLearnerNotReady):
			lg.Debug(
				"auto-promote skipped",
				zap.String("learner-id", m.ID.String()),
				zap.Error(err),
			)
		default:
			learnerPromoteFailed.WithLabelValues(err.Error()).Inc()
			lg.Warn(
				"auto-promote failed",
				zap.String("learner-id", m.ID.String()),
				zap.Error(err),
			)
		}
```
However, `s.promoteMember(ctx, uint64(m.ID))` -> `s.configure(ctx, &cc)` can also return three transient leadership-flip / proposal-timeout errors:
1. `raft.ErrProposalDropped` (`"raft proposal dropped"`): returned by `s.r.ProposeConfChange(ctx, cc)` when the node steps down between `s.isLearnerReady` (which checks `rs.Progress != nil`) and `s.r.ProposeConfChange`, or when the proposal channel is full/dropping.
2. `errors.ErrTimeoutDueToLeaderFail` (`"etcdserver: request timed out, possibly due to previous leader failure"`): returned by `s.parseProposeCtxErr(ctx.Err(), start)` (`server.go:2284`) when `ctx.Err() == context.DeadlineExceeded` and a leadership change occurred near the proposal start time.
3. `errors.ErrTimeoutDueToConnectionLost` (`"etcdserver: request timed out, possibly due to connection lost"`): returned by `s.parseProposeCtxErr(ctx.Err(), start)` (`server.go:2286`) when `ctx.Err() == context.DeadlineExceeded` and the leader had not been connected to a quorum of peers since `start`.

As proved in [`finding2_ErrProposalDropped_mem_false`](../../Proof/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__tryAutoPromoteLearners.lean), [`finding2_ErrTimeoutDueToLeaderFail_mem_false`](../../Proof/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__tryAutoPromoteLearners.lean), [`finding2_ErrTimeoutDueToConnectionLost_mem_false`](../../Proof/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__tryAutoPromoteLearners.lean), and [`EtcdServer.tryAutoPromoteLearners.wp_default_forced`](../../Proof/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__tryAutoPromoteLearners.lean), all three errors miss the 10 `switch` cases and enter `default:`, incrementing `learnerPromoteFailed` and logging `Warn("auto-promote failed")` even though `ErrNotLeader`, `ErrLeaderChanged`, and `ErrTimeout` were explicitly intended to be skipped at `Debug` level.

#### Suggested Fix
Add `raft.ErrProposalDropped`, `errors.ErrTimeoutDueToLeaderFail`, and `errors.ErrTimeoutDueToConnectionLost` to the `auto-promote skipped` `switch` case in `tryAutoPromoteLearners`.
