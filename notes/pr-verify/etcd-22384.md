## Verdict

The change is sound as far as it goes. `ResumeMutex` builds a `Mutex` whose fields are exactly the given session, `pfx + "/"`, key and revision, with no header. It is proved against the same mutex vocabulary as `NewMutex`. Every `Mutex` method's existing proved spec runs from an arbitrary state, so the methods' guarantees carry over to a resumed mutex unchanged:

- `IsOwner` is the comparison `CreateRevision(myKey) = myRev`;
- `Unlock` deletes `myKey` when it is under the prefix and `myRev > 0`;
- `Lock` and `TryLock` re-derive the key from the session's lease.

There is no bug in the code. The weak points are the PR's description and documentation:

- it claims to mirror `ResumeElection` exactly, but the prefix handling differs, and the PR's choice is the correct one;
- its motivation overstates the gap: a restarted process on the surviving lease already gets its lock back with `NewMutex` + `Lock`/`TryLock`;
- `Mutex` gives the caller no way to learn the `myRev` the function needs;
- a stale or foreign key passed to it makes `Unlock` delete a lock key the caller does not own.

These are documentation and API points for review, not reasons to reject.

## The spec

`Spec/go_etcd_io/etcd/client/v3/concurrency/ResumeMutex.lean`:

- Precondition: `isSession s γ client id ∗ isEtcdMutexClient client (pfx ++ "/")`, the same as `NewMutex`'s.
- Result: `isMutex m s γ client id (pfx ++ "/") ∗ mutexState m {key := myKey, rev := myRev, hdr := null}`.
- No ownership fact (`lockedAt`): nothing is checked, so the key and revision are the caller's claim.

`NewMutex`'s spec is the same with the state `MutexSt.init` (`""`, `-1`, `nil`). `ResumeElection`'s spec (`Spec/.../ResumeElection.lean`) uses `pfx` as given, without the `/`.

None assumes the state came from `NewMutex` or `tryAcquire`, so all of them apply to a resumed mutex.

## Findings

None of these is a bug in the PR's code. All probes pass on the PR head, and each shows the behavior described. The files are in `notes/pr-verify/etcd-22384/` (see its `README.md`).

1. **"Mirrors `ResumeElection`'s exact shape" is inaccurate, and the PR's code is the correct version.** `ResumeElection` stores `pfx` as given, while `NewElection` appends `/`. `ResumeMutex` appends `/` like `NewMutex`. Without the `/`, `tryAcquire` would build `pfx<lease>` and the owner and wait queries would range over `pfx*`. The doc comment should say that `pfx` is the prefix as passed to `NewMutex`, without the trailing `/`. A caller who passes the slashed prefix gets a handle whose `Unlock` refuses the key (`TestProbeResumeMutexSlashedPrefix`). The `ResumeElection` side is already recorded in `issues/election-campaign-key-check.md`, under "Also noticed".
2. **There is no way to get `myRev` from a `Mutex`.** `Election` has `Rev()`; `Mutex` does not. `Header().Revision` equals the key's create revision only on a fresh, uncontended put. On the reused-key branch it was 3 against 2, and after waiting it was 7 against 3. A caller who persists `Header().Revision` gets a resumed handle that is not the owner. Probes: `TestProbeMutexHeaderRevisionIsNotMyRev`, and the reviewer's `TestProbeResumeViaLock` and `TestProbeHeaderRevAfterWait`. The PR's own test uses a separate `Get(Key()).CreateRevision`. The server's `v3lock` returns only the header and key, so its users cannot get `myRev` either. A `Rev()` accessor would fit naturally in this PR.
3. **`Unlock` on a resumed handle is not fenced by `myRev`.**
   - It deletes `myKey` blindly. If the key was deleted and re-created by another handle on the same lease, `IsOwner()` correctly fails, but `Unlock` deletes the new holder's key (reviewer's `TestProbeResumedStaleUnlockDeletesRecreated`).
   - If a session is resumed with another session's key, `Unlock` deletes that session's lock key while the other session still believes it holds the lock (`TestProbeResumedForeignKeyUnlock`).

   This is the existing unfenced-`Unlock` behavior, the class of etcd-io/etcd#22082, already referenced from `issues/mutex-lock-recreated.md`. `ResumeMutex` makes it easier to reach, because a persisted (key, revision) pair is exactly what goes stale. The proved `Unlock` spec says no more than that: it deletes `myKey` and makes no ownership claim. The doc should say that the key and revision must be ones the session's own lease created and still holds. No new `issues/` entry was written, since the underlying behavior is already recorded.
4. **The motivation is overstated.** A restarted process with `WithLease(oldLease)` already gets its lock back: `NewMutex(s, pfx).Lock()` (or `TryLock()`) finds its existing key, adopts its create revision and returns after one transaction when it is first, even while others are queued (`TestProbeLockAlreadyResumes`, and the reviewer's `TestProbeResumeViaLock`). What `ResumeMutex` adds:
   - no round trip;
   - an `IsOwner` fence tied to the original revision, which fails if the key was re-created (`Lock` would silently adopt the new key);
   - handles for keys that are not the session's own, which is where finding 3's trap lies.
5. **Minor:**
   - `Header()` is nil on a resumed mutex until `Lock` or `TryLock` succeeds, so `m.Header().Revision` panics. `ResumeElection` behaves the same way.
   - `Lock` and `TryLock` overwrite the resumed key and revision (`tryAcquire`). The resumed values only matter to `IsOwner`, `Key` and `Unlock`.
   - The PR's test prefix `"/resume-mutex/"` becomes `"/resume-mutex//"`. It works because both handles agree.

The PR's own tests (`TestResumeMutex`, together with `TestResumeElection`, `TestMutexLockSessionExpired` and `TestMutexUnlock`) pass at the PR head (`notes/pr-verify/etcd-22384/pr-tests.log`). `go build ./...`, `go vet` and `go test ./concurrency/` of `client/v3` pass on the fork branch.
