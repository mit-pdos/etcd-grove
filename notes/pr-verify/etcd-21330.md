## Verdict

The change is sound as far as it is verified: for a range, put or delete whose key is empty, `kv.Do`
now returns a non-nil client error (`rpctypes.ErrEmptyKey`, through `ContextError`) before any RPC,
whatever the server would have done, and `kv.GetStream` with an empty key returns a nil channel and
`rpctypes.ErrEmptyKey` itself. The existing specs of `kv.Do`, `kv.Get`, `kv.Put` and `kv.Delete` and
everything verified above them (the client's end-to-end results and the recipes' queue over etcd's
server) were re-proved over the new code. The one cost: a new premise, the initialization fact that
`rpctypes.ErrEmptyKey` holds a non-nil client error (`emptyKeyOk`, as the existing `sortNamesOk` for
`ErrInvalidSortOption`), needed only when a key may be empty. The user-visible error is the same value as
before (the server's `ErrGRPCEmptyKey` through `ContextError`); what changes is `GetStream`'s shape (the
error is now returned, not sent on the channel) and a few error choices (an empty key wins over an invalid
sort option, as on the server, and over a canceled context). Not covered: a non-empty key's `GetStream`
(the `RangeStream` call and the receiving goroutine), and `Txn`'s operations (not checked by the PR, by
design).

## Changed functions

From the two revisions' `kv.go` (only two function bodies change; no type, field or package variable).

| Function | Kind | Before (`lean`) | After | Outcome |
|---|---|---|---|---|
| `(*kv).Do` (`client/v3/kv.go`) | behavior change | verified | verified | new spec, stronger postcondition (an empty key gives an error), stronger precondition (`emptyKeyIf o.key`); callers checked (below) |
| `(*kv).GetStream` (`client/v3/kv.go`) | behavior change | not translated (names only) | partially verified (empty key only) | translated (`Code/go_etcd_io/etcd/client/v3.toml`); new partial spec, proved |

### `kv.Do`

- Old spec (`lean`, `Spec/go_etcd_io/etcd/client/v3/kv__Do.lean`): for a range/put/delete `Op` modelled
  by `o`, with the server's spec for the method (`doRunOk`), `kv.Do` returns `doOut`: the server's answer
  with the caller's knowledge, or a client error and no response.
- New spec (same file): the same `doOut`, and also `⌜o.key = [] → err ≠ nil⌝` (an empty key always
  fails, whatever the server's spec says); one more premise, `emptyKeyIf o.key` (for an empty key the
  facts of `rpctypes.ErrEmptyKey`: `Proof/go_etcd_io/etcd/client/v3/InvKVConn.lean`, `emptyKeyOk`).
- Neither implies the other (stronger postcondition, stronger precondition), so the callers were
  re-checked. The new conjunct does not hold of the old code under the old premises: there an empty key
  goes to the server, and whether it fails depends on the server's spec `Sr`/`Sp`/`Sd`, which the
  client's spec leaves arbitrary. So the new conjunct is what the PR changes.
- Proof: `Proof/go_etcd_io/etcd/client/v3/kv__Do.lean`, the old proof for a non-empty key (the new `if`
  is false), a new case for an empty key (each of the three branches: load `ErrEmptyKey`, `break`,
  `ContextError`). Helpers `klen_zero`/`klen_ne` (the slice's length from the key's contents).
- The order of the checks: the empty key comes before the sort check, as in the server's
  `checkRangeRequest` (probe `TestProbeEmptyKeyBeforeSortCheck`).

### `kv.GetStream`

- Old: not translated (no spec).
- New partial spec (`Spec/go_etcd_io/etcd/client/v3/kv__GetStream.lean`): for a get whose key, after
  the options, is empty (`(opGetModel key gs).key = []`: `WithPrefix`/`WithFromKey` replace `""` by
  `"\x00"` and are not covered), `GetStream` returns a nil channel and exactly the value of the global
  `rpctypes.ErrEmptyKey`, a non-nil client error. It has no connection premise (no `kvObjAt`, no
  `RangeStream` registration), so no RPC is made. Proof: `Proof/go_etcd_io/etcd/client/v3/kv__GetStream.lean`
  (`OpGet` through the existing `opGet_res`). A non-empty key's path is unspecified (progressive: no spec
  of `RangeStream`'s client stream or the goroutine yet). Linked as `client.v3.kv.wp_GetStream`
  (`etc/link-lean-first-client.txt`, `Link.lean` regenerated).
- Against the old code this spec is false: there `GetStream("")` calls `RangeStream` and returns a channel
  (with `nil`), delivering the server's error on it (the reviewer's `TestReviewGetStreamShape` shows both
  shapes).

## Caller graph (step 6)

The only callers of `kv.Do` in the proofs are `kv.Get`, `kv.Put`, `kv.Delete` (`etc/link-lean-first-client.txt`).
Their specs got the premise `emptyKeyIf (<model>).key` (postconditions unchanged; proofs re-done by
framing). Then up:

- `kv.Get` → `client.isEtcdKVTodo_of_kv` (`ServerKVGet.lean`; the get contract admits any key):
  premise `emptyKeyOk` → `recipes.isRecipesKV_of_kv`, `isEtcdRecipesClient_of_kv` (`KVOfServer.lean`),
  `queue_vertical` (`Vertical.lean`), and the recipes' `recipes_kv_of_server`, `recipes_client_of_server`,
  `queue_end_to_end`, `queue_end_to_end_client` (`experimental/recipes/Results.lean`): premise `emptyKeyOk`
  beside `sortNamesOk`. Exported: a premise added, no conclusion changed.
- `kv.Get` → `client_get_end_to_end`, `client_get_after_put`, `client_range_end_to_end`
  (`client/v3/Results.lean`): premise `emptyKeyIf key` (resp. `emptyKeyIf (opGetModel key gs).key`):
  free for a non-empty key (`emptyKeyIf_of_ne`).
- `kv.Put` → `client.kv_put_result`, `isEtcdPutKVTodo_of_kv`, `isEtcdPutKV_of_kv` (`ServerKVPut.lean`):
  premise `emptyKeyIf pfx`, which gives the key's (`emptyKeyIf_mono`: the put is under the prefix,
  `put_under_key`). `client_put_end_to_end`: `emptyKeyIf key`.
- `kv.Delete` → `client.kv_delete_result`, `isEtcdDeleteKVTodo_of_kv`, `isEtcdDeleteKV_of_kv`: premise
  `emptyKeyIf pfx` (`keyRangeUnder_empty`: a range from the empty key is under no prefix but `[]`).
  `client_delete_end_to_end`: `emptyKeyIf key`.
- The recipes' `KVOfServer` gives the put and delete contracts `emptyKeyIf pfx` from `emptyKeyOk`.

Every node re-proved; no spec's conclusion changed. In Go, the callers of `kv.Do`/`Get`/`Put`/`Delete`
outside the proofs (ordering, namespace, leasing, grpc-proxy, etcdctl) see the same error value as before
(probe `TestProbeEmptyKeySameErrorAsServer`). `GetStream`'s callers in the tree (`etcdctl get --stream`,
`tools/benchmark`, the robustness and integration test clients) all check the returned error before
reading the channel, so the new shape does not affect them; a caller that ignores the error and drains the
channel would now block forever on the nil channel. The PR's description does not mention this; it is a
public-API behavior change worth a line in the CHANGELOG.

## Findings (step 8)

- **In the PR**: no bug. Behavior changes to note upstream (all probes in `notes/pr-verify/etcd-21330/`):
  - `GetStream("")` returns `(nil, ErrEmptyKey)` where it returned `(ch, nil)` with the error on `ch`
    (`TestReviewGetStreamShape`).
  - `Get(ctx, "")` on a canceled context returns `ErrEmptyKey`, not `context.Canceled` (`TestReviewCanceledCtx`).
  - An empty key with an invalid sort option returns `ErrEmptyKey`, not `ErrInvalidSortOption` (as the
    server's order; `TestProbeEmptyKeyBeforeSortCheck`).
  - `Txn` ops with an empty key are still sent (the author's stated choice).
- **In the existing code** (pinned, unchanged by the PR, outside the verified code):
  `issues/etcd-grpcproxy-kv-error-code.md`: the grpc-proxy's KV service returns `kv.Do`'s `EtcdError`,
  which has no gRPC status, so the backend's code (e.g. `Unavailable` for no leader) reaches the client as
  `Unknown` and clientv3's retry interceptor does not retry it. Reproduction:
  `notes/pr-verify/etcd-21330/kv_proxy_errcode_test.go` (fails at the PR head). Found by the reviewer.
- **Reviewer's open points**:
  - `kv.Do`'s spec does not say "no RPC" for an empty key: its premises still ask for the server's spec
    and the RPC registration, which that path does not use. A weaker precondition (`doRunOk` only for a
    non-empty key) would state it; not done (GetStream's spec does state it).
  - The new postcondition says the error is non-nil, not that it is `ErrEmptyKey`: that needs a
    stronger `ContextError` spec (that it keeps an `EtcdError`). GetStream's spec does give the exact value.

## Draft review comment (for the user to edit and post)

> I checked the change against the server's own validation. For `Get`, `Put` and `Delete`, the error a caller
> sees is unchanged: before, the server's `ErrGRPCEmptyKey` came back through `ContextError` as an
> `EtcdError` equal to `rpctypes.ErrEmptyKey`, which is what the client now returns directly. The empty-key
> check also comes before the sort-option check, matching `checkRangeRequest`.
>
> Two behavior changes may be worth a CHANGELOG line:
> - `GetStream(ctx, "")` used to return a channel and a nil error, with the error delivered on the channel. It
>   now returns `(nil, ErrEmptyKey)`. Every caller in the tree checks the error first, but a caller that ranges
>   over the channel without checking would now block forever on the nil channel.
> - With an already-canceled context, `Get(ctx, "")` now returns `ErrEmptyKey` instead of `context.Canceled`.
