# Verification of etcd-io/etcd#22261

**PR**: [etcd-io/etcd#22261](https://github.com/etcd-io/etcd/pull/22261), "fix sending v prefixed
semver version to older etcd peer versions that use the coreos/go-semver", head
`4f47eb361f772b81a958bce198df893522d3173b` (open; a maintainer has requested changes).
- **Verified at**: fork commit `22be0af01` (`mit-pdos/etcd-grove` branch
  `pr-etcd-22261-goose-lean`). It is the PR's diff, tests included, onto `goose-lean` `09669450f`.
- **Applying it**: there were no conflicts, so the verified code is the PR's code.
- **Go checks**: in the fork worktree, `go build ./...` passes, and so do the tests of `rafthttp`,
  `api/version` and `client/v3` (`-run Version`).

**What the PR does**: etcd#20915 builds etcd with `version.Version` prefixed with `v`. Members
before v3.8 parse `X-Server-Version` with coreos/go-semver, which panics on a leading `v`. The PR:
- adds `version.VersionForPeer(peerVer)`, which strips the `v` when the peer's version is unknown
  or below v3.8;
- adds a per-peer cache of versions to rafthttp's `Transport` (`peerVersions sync.Map`);
- sends `VersionForPeer(cached version)` on stream dials, pipeline posts and snapshot posts;
- answers a stream dial with `VersionForPeer` of the dialing peer's own header;
- fills the cache from every stream dial's response.

## Verdict

As it stands, the PR changes nothing on the wire:
- `Version` is `"3.8.0-alpha.0"`, with no `v`;
- the proof shows that `VersionForPeer` then returns `Version` for every peer
  (`versionForPeerOk_unprefixed`).

For a `v`-prefixed build, the case the PR exists for:
- `VersionForPeer` is proved panic-free and correct for unknown peers and for peers known to be
  below or above 3.8.0, by their (major, minor, patch);
- **but the rafthttp cache it is fed from can go stale**. After a peer is downgraded from 3.8 to
  3.7, the member keeps the 3.8.0 it cached and keeps sending `"v3.8.0"` (finding 1). The 3.7
  peer panics on that header in every handler. A failed request gets no response, so nothing
  corrects the cache. Until the member restarts, its stream dials, pipeline posts and snapshots to
  that peer all fail, and a lagging v3.7 follower can never get a snapshot from it.

Stripping the `v` unconditionally would be correct for every peer and needs no cache: v3.8+
peers parse either form. That is the suggestion a maintainer already made on the PR.

Not covered by the proof: the rafthttp functions and `client/v3`'s `minSupportedVersion`. Their
packages are translated names-only, and the findings on them come from Go tests and reading the
code.

### `VersionForPeer`

The Goose configuration now translates it with its body
(`Code/go_etcd_io/etcd/api/v3/version.toml`; the package was names-only). The spec is at
`Spec/go_etcd_io/etcd/api/v3/version/VersionForPeer.lean` and the proof at
`Proof/go_etcd_io/etcd/api/v3/version/VersionForPeer.lean`. Given the package's initialization and
`Version ↦□ ver`, `VersionForPeer(p)` does not panic and returns some `s` with the following
properties.

- **`versionForPeerOk p ver s`**:
  - `s` is `ver` or `trimPrefix ver "v"`;
  - if `p` is nil, `s` is `trimPrefix ver "v"`.
- **For any fixed `*p = pv`** (`p ↦□ pv`), `versionForKnownPeerOk pv ver s` holds:
  - if pv's (major, minor, patch) is below (3, 8, 0), then `s = trimPrefix ver "v"`;
  - if it is above, then `s = ver`.
  - At exactly 3.8.0 the pre-release decides, and the semver postulate does not model that. The
    reviewer's probe shows that 3.8.0 pre-releases get the stripped string.
- **Corollaries**, in the Spec file:
  - `versionForPeerOk_unprefixed`: when `Version` has no leading `v`, every allowed `s` is `ver`.
    So the PR is a no-op for the current `Version` and for every official build.
  - `versionForKnownPeerOk_below_3_8`: a 3.x peer with x < 8 gets the stripped string.

The first version of the spec only had `versionForPeerOk`. The reviewer pointed out that it
admits the broken variant "strip only for an unknown peer". The second part excludes it.

**Proof changes outside the function**:
- **Package initialization**: the assumption for `api/v3/version`
  (`Proof/go_etcd_io/etcd/server/v3/lease/Base.lean`) now also says that `V3_8` holds a fixed
  version with (major, minor, patch) = (3, 8, 0). The Go code is
  `V3_8 = *semver.New(3, 8, 0, "", "")`, never assigned again. The proof needs `&V3_8` non-nil and
  its value. The two proofs that open this assumption (`lessor.shouldPersistCheckpoints`,
  `EtcdServer.start`) are adjusted to the new conjunct.
- **`semver.Version.LessThan`'s postulate**
  (`Spec/github_com/Masterminds/semver/v3/Version__LessThan.lean`) is strengthened. It still
  returns some boolean, and the precondition is unchanged. The new part: for any fixed contents
  `v ↦□ vv`, `o ↦□ ov`, the result is `true` if `vv`'s (major, minor, patch) is lexicographically
  below `ov`'s, and `false` if above. This is what Masterminds' `Compare` does: it compares the
  three segments before the pre-release. The apply package's `ClusterVersionSet` discards the
  postcondition and goes through unchanged.
- **Link**: the server's link file adds `version_VersionForPeer: Version__LessThan` and the
  boundary entry `Version__LessThan:` (`Link.lean` regenerated).

## Findings

**1. The per-peer version cache goes stale when a peer is downgraded. Bug in the PR; medium; only
for `v`-prefixed builds.**
- **Where it is filled**: the cache is filled only from a stream dial's response
  (`stream.go`, `cr.tr.setPeerVersion(cr.peerID, rv)`). It is cleared only by `removePeer`.
- **What happens on a downgrade**: the member keeps the cached `3.8.0` and sends `"v3.8.0"`.
  release-3.7's `checkClusterCompatibilityFromHeader` calls `serverVersion`, which is
  `semver.Must(semver.NewVersion(verStr))` of coreos/go-semver (`rafthttp/util.go:154`). That
  panics in all three of its handlers. net/http drops the connection without a response, so no
  response ever corrects the cache.
- **What breaks**:
  - this member's stream readers to that peer;
  - its pipeline posts to that peer;
  - every `MsgSnap` to it (`snapshot_sender.go`), so a lagging v3.7 follower can never receive a
    snapshot from a `v`-built leader.
- **What keeps working**: our `streamHandler` answers the peer's own stream dials from the
  request's header, so the streams the peer dials into us keep carrying our messages to it. The
  cluster stays live, degraded, until the member restarts or the peer is removed.
- **Tests**:
  - `notes/pr-verify/etcd-22261/peer_version_downgrade_test.go` fails at the PR head as
    expected, showing the stuck member. A member without the cache reaches the same peer.
  - The reviewer's `stale_cache_direction_test.go` shows which direction still works.
  - `coreosprobe/` shows coreos/go-semver's panic.
- **Fix**: strip unconditionally (`strings.TrimPrefix(version.Version, "v")` at the four call
  sites). Every peer accepts the stripped form, so the cache, its state and its races go away.

**2. A small race in `removePeer`. Low.** `removePeer` deletes the peer's version before
`peer.stop()`. A `streamReader.dial` already in flight can re-insert the entry afterwards,
leaving a stale entry for a removed member (a leak; member IDs are not reused). Found by the
reviewer from the code; no test.

**3. The PR's tests do not test the stripping. Test gap.**
- `TestPipelinePost` and `TestServeRaftStreamPrefix` compare the header with
  `version.VersionForPeer(...)` of the same input, so they pass for any `VersionForPeer`.
- The new `TestServerVersion` case checks only that the Masterminds parser accepts `v2.1.0`.
- No test sets a `v`-prefixed `Version`.

**4. Documentation nits.**
- The comment on `Transport.peerVersions` says "< v3.7"; the code and `VersionForPeer`'s comment
  say v3.8. release-3.7 does use coreos/go-semver, so v3.8 is right.
- `minSupportedVersion`'s change from `semver.MustParse` to `semver.NewVersion` with the error
  ignored is not needed: Masterminds' `MustParse` already accepts a `v`. For an invalid `Version`,
  it turns a panic with the parse error into a nil-pointer dereference.

**5. Coverage outside rafthttp headers (not a bug in the PR).** A `v`-prefixed `Version` still
reaches v3.7 members through the `/version` endpoint (`etcdhttp/version.go`, the `etcdserver`
field). release-3.7's version monitor parses it with `semver.NewVersion`
(`version/monitor.go:164,200`), logs a warning and returns nil or false. So during a mixed-version
period, a v3.7 leader neither updates the cluster version nor sees a downgrade complete while a
`v`-built member is up. It degrades without crashing; the PR does not mention it.

**Existing code**: no bug in the pinned code was found, so nothing was added to `issues/`.

## Reviewer

A fresh reviewer subagent checked the specs, the postulate, the init assumption and the code under
concurrency.
- **Spec too weak**: resolved by the second conjunct of the postcondition and the strengthened
  `LessThan`.
- **`LessThan` precondition**: the reviewer noted that it needs no points-to for the memory it
  reads. That is unchanged, and it is sound for etcd's uses, since the compared versions are never
  written. Open, as a general weakness of that postulate.
- **Downgrade finding**: confirmed against release-3.7, with the narrower description above.
- **New**: the race of finding 2 and the "strip unconditionally" observation.
- **No problem found** for:
  - pre-release peers (stripped, which is conservative);
  - the upgrade direction (a stale 3.7 entry only means extra stripping);
  - peers that never stream (unknown, so stripped);
  - remotes;
  - the probing endpoints (no version header);
  - `X-Min-Cluster-Version` (`"3.0.0"`).

## Draft review comment

> With the current `Version` ("3.8.0-alpha.0") this change is a no-op on the wire: `VersionForPeer`
> returns `Version` for every peer. For a v-prefixed build there is a problem with the per-peer
> cache: it is only filled from a stream dial's response and only cleared by `removePeer`. If a
> peer that was cached as 3.8 is downgraded to 3.7, this member keeps sending `v3.8.0`; the 3.7
> member's `checkClusterCompatibilityFromHeader` panics parsing it (coreos/go-semver), net/http
> drops the connection, and since no response comes back the cache is never corrected. Stream
> dials, pipeline posts and snapshots to that member then fail until this member restarts (a
> lagging 3.7 follower can no longer receive a snapshot). A test reproducing it:
> [peer_version_downgrade_test.go]. Since 3.8+ members accept the version with or without the "v",
> always sending `strings.TrimPrefix(version.Version, "v")` would avoid the cache altogether (and
> the race in `removePeer`, which deletes the entry before stopping the peer's stream readers).
> Also, the updated tests compare against `VersionForPeer(...)` itself, so they would pass for any
> implementation; a test with `version.Version = "v3.8.0"` and a known 3.7 / 3.8 peer would cover
> it. Minor: the `peerVersions` comment says "< v3.7" where the code uses v3.8.
