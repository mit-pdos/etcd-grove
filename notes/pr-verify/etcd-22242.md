## Verdict

The change is safe: the read loop, rewritten as the PR does it (a logger goroutine fed by a
one-slot channel, a nonblocking send that drops the trace when the slot is taken, a deferred
`close`), is proved against its existing spec unchanged, with no new axiom and no `sorry`. The
proof shows the hand-off is clean: each trace's ownership goes with it through the channel, the
loop never touches a trace it handed off, the logger goroutine consumes each one with `Log`, only
the loop sends and it closes the channel exactly once, after its last send, on every return path.

It does what its title says for the trace only. The read loop still logs inline from
`requestCurrentIndex` (a warning every 500 ms while a ReadIndex response is late, and others) and
`sendReadIndex`, so a stalled log sink still hangs every linearizable read when read indexes are
slow, which is what a slow disk produces; a unit test shows it at the PR head
(`notes/pr-verify/etcd-22242/read_logsink_test.go`). The PR narrows #22214 rather than fixing it.
Not covered by the proof: the PR's goal itself (that the loop does not block on the sink) is a
liveness property, which these partial-correctness specs cannot state; it is checked by the tests
only.

## Findings (step 8)

- **The PR leaves #22214 open (not a bug the PR introduces).** `requestCurrentIndex` logs on the
  loop's goroutine: `lg.Warn` every `readIndexRetryTime` (500 ms) while a ReadIndex response is
  late, at the request timeout and for an out-of-date read state, `lg.Info` on a term's first
  commit; `sendReadIndex` logs `lg.Warn` when `ReadIndex` fails. With a stalled sink any of them
  parks the loop as before. `TestReadLoopStalledSink_ReadIndexRetry`
  (`notes/pr-verify/etcd-22242/read_logsink_test.go`) fails at the PR head and at the base;
  `TestReadLoopStalledSink_SlowIteration` (the PR's case) fails at the base and passes at the head
  (logs in the same directory). Under the disk stall #22214 describes, ReadIndex responses can
  plausibly be late too (read states reach the loop through the raft node's `Ready` handling, the
  goroutine that also writes the WAL), so this path is a likely next hang; not shown on a real
  cluster.
- **The loop also waits on the apply goroutine, which logs inline** (reviewer; code reading, not
  reproduced): the loop waits on `ApplyWait(confirmedIndex)`, and every apply slower than 100 ms
  logs "apply request took too long" on the apply goroutine (`apply/uber_applier.go:99`,
  `txn/util.go:94`). Parked there, it never reaches the index, and linearizable reads hang as
  before. Out of the PR's scope, but part of why #22214 stays open.
- **The logged duration includes the queue** (minor). `Trace.Log` computes the trace's end time
  when it logs (`logInfo`: `endTime := time.Now()`), so a trace that waited in the channel or behind
  a slow sink is logged with that wait in `duration` and `end`. The threshold decision is made in
  the loop, as the PR says, but the logged number is no longer the iteration's: the reviewer's probe
  (`notes/pr-verify/etcd-22242/read_review_test.go`, a 400 ms-per-write sink) logs `duration=0.400s`
  for a 0.12 s iteration, worst exactly when the sink is slow.
- **The logger goroutine outlives the loop** (nit): it is not `GoAttach`ed, so a queued trace can be
  written after `LinearizableReadLoop` returned (437 ms after in the probe), and with a sink that
  never recovers one goroutine per server stays parked. Previously every trace was written before
  the attached goroutine returned.
- **A bug in the existing code**, recorded as `issues/etcd-read-loop-log-sink-hang.md` (upstream's
  #22214; reproduction above).
- **Reviewer** (a fresh subagent, over the PR, the specs, the new lemma, `readInit` and the
  proof): no soundness problem. The unchanged spec loses nothing the old proof captured (the trace's
  ownership was consumed by `LogAllStepsIfLong`, now by the logger's `Log`); no send on a closed
  channel and no double close follow from the producer token; the logger goroutine cannot panic
  (`wp_fork`); `spsc_nonblocking_send_au`'s catch-all case is the `True` that
  `nonblockingSendAuInner` itself allows (and the channel is only ever `Buffered` or `Closed`).
  Not expressible here: "every slow trace is logged or counted" (`Inc`'s spec says nothing of the
  counter's value). Its Go findings are the three above; with `-race` the PR's test and its probe
  are clean (no data race on the handed-off trace), the metric name is unique (`MustRegister` does
  not panic), and the threshold check is equivalent to the old one.

## Draft review comment

> Moving the trace off the read loop looks right to me: each iteration's trace is handed off and
> never touched again, `traceC` is only sent on by the loop and closed once after its last send
> (also on the stop paths), and with `-race` the new test is clean.
>
> As jberkus said, though, this doesn't fix #22214 on its own. The loop still logs inline from
> `requestCurrentIndex`: the "waiting for ReadIndex response took too long, retrying" warning
> fires every `readIndexRetryTime` while a ReadIndex is slow, which is what a slow disk produces,
> and with a stalled sink that `lg.Warn` parks the loop just as `LogAllStepsIfLong` did. A variant
> of your test shows it: answer the ReadIndex only after the retry warning reached the blocked sink
> (`readIndexRetryTime = 50 * time.Millisecond` to keep it short), and the read never completes.
> The same holds for the other warnings in `requestCurrentIndex` and `sendReadIndex`, and the loop
> also waits on `ApplyWait`, whose goroutine logs "apply request took too long" inline. Maybe
> route those through the same logger goroutine (or a small rate-limited one), or narrow the
> description to the trace.
>
> A smaller point: `Trace.Log` takes the end time when it runs, so a trace that waited in
> `traceC` or behind a slow sink is logged with that wait in `duration` (with a sink taking 400 ms
> per write, a 120 ms iteration was logged as 400 ms). Recording the iteration's own duration as a
> field before the hand-off would keep the logged number meaningful when the sink is slow.
