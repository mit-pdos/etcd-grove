## Verdict

**The PR is unsound: it loses watch events, and it breaks an existing etcd test.** It cuts the
scan to `[minRev, minRev + watchBatchMaxRevs + 1)` but leaves the rest of `syncWatchers` as it
was, so it still treats the scan as reaching `curRev`. A chosen watcher with no events in the
window, or with fewer than `watchBatchMaxRevs` revisions of events there, is moved to `synced` at
`curRev + 1`. Its key's events past the window are never delivered, and its response carries
`Revision: curRev`, so a client resuming from there loses them for good.

The proof shows this exactly. Of the unchanged spec (synced watchers have every event of their key
up to the current revision), everything goes through except one obligation: that the window
reaches `curRev + 1`. That obligation is false whenever the chosen watchers are more than 1000
revisions behind, which is the case the PR is for. Go tests at the default constants fail on the
PR head and pass on the base.

The PR is right only when every chosen watcher's key has an event at every revision from the
window's start, its start revision included. The PR's own reproducer is such a case, and that
case does work.

**Confirmed: #22304's randomized delivery test fails on #22265**, 198 of 200 seeds.

**Compared with the other two PRs for #22264:**
- #22594 caps the scan by entry count. It has the same flaw (it cuts the scan and still syncs at
  `curRev + 1`) and also a non-prefix backend read.
- #22304 scans the same bounded windows, but moves a watcher to `synced` only when its window
  reached `curRev`, and otherwise leaves it unsynced at the window's end. It is the only one of the
  three proved against the unchanged spec with no `sorry`.
- #22265 is #22304 without that check.

### `syncWatchers`

- **The spec is unchanged** (`Spec/go_etcd_io/etcd/server/v3/storage/mvcc/watchableStore__syncWatchers.lean`).
  It keeps the watchable store's lock invariant (`InvWatchSync.lean` and the rest), which records
  that every synced watcher has received every event of its key up to the current revision.
- **The proof** (`Proof/go_etcd_io/etcd/server/v3/storage/mvcc/watchableStore__syncWatchers.lean`)
  binds the `watchBatchMaxRevs` fact (`#HmaxB`) and runs the PR's `if` (`wp_if_destruct`):
  - When `maxRev > curRev + 1` (the window would pass the tip), `maxRev = curRev + 1`. This is the
    old situation.
  - Otherwise `maxRev = minRev + 1001`. The lemma `mvcc.syncWatchers_window_reaches_curRev`
    (same file), `|C| ≤ sint.Z (minRev + 1000 + 1)`, together with the branch condition, gives
    `maxRev = curRev + 1`.
  - Both branches then run the old proof, unchanged (`all_goals`; hence `maxHeartbeats 800000`).
- **The lemma is a `sorry` and is false.** In the proof's context `0 ≤ minRev ≤ curRev < 2^63`, so
  it says `curRev − minRev ≤ 1000`: exactly "the cap has no effect". So the proof shows the PR is
  correct exactly when its bound does not apply. (Unlike #22594's obligation, it is cheap to state:
  no backend entry counting.)

## Findings

1. **The PR loses watch events: a watcher is synced at `curRev + 1` after a window that stopped
   short of `curRev`.** All tests are in `notes/pr-verify/etcd-22265/`. Each fails on the PR head
   and passes on the base:
   - `watchable_store_window_cut_test.go` (`TestSyncWatchersWindowCutDeliversAll`) uses the default
     `watchBatchMaxRevs` (1000). There are 1500 puts of `b` and an `a` after them; the watch on `a`
     is from revision 1. The watcher gets `[]` instead of `[1502]`, and `[2]` instead of
     `[2 1503]` with an `a` before the `b`s. Same on the fork branch (`fork.log`).
   - The reviewer's `TestReviewRealStoreWindowCut` runs the same case through `New(...)` with the
     background loops and the real `Watch` API.
   - #22304's randomized test fails on 198 of 200 seeds. #22304's sparse catch-up test and #22594's
     `TestSyncWatchersScanLimitDeliversAll` and gap test fail too.
2. **etcd's existing `TestWatchBatchUnsynced` hangs on the PR** (`batchunsynced-head.log`, passes on
   the base). It sets `watchBatchMaxRevs = 4`, puts revisions 2..13 and watches from revision 1.
   - The window `[1, 6)` holds only 4 revisions with events, so the batch has no `moreRev`.
   - The watcher is synced after `[2 3 4 5]`, and the test waits forever for the rest.
   - This is the "one event per revision" case the PR is about, off by the start revision, which
     has no event. Upstream CI would have caught it, but it has not run on the PR (no
     `ok-to-test`).
3. **Even a key with an event at every revision loses events when two watchers are chosen together**
   (the reviewer's `TestReviewEveryRevisionTwoWatchers`):
   - The window starts at the older watcher's `minRev`.
   - The younger watcher (from 502) has fewer than 1000 revisions of events in it, so it gets no
     `moreRev` and is synced at 501 events (last 1002) instead of 2500.
4. **Where the PR is right:** a single watcher whose key has an event at every revision from its
   start (`TestReviewRealStoreEveryRevisionSingleWatcher`, the PR's reproducer). Its batch fills
   1000 revisions, `moreRev` is set, and it resumes there. The scan bound and the performance claim
   hold (at most 1001 revisions per pass); but in every other case the speed comes from skipping
   events.
5. **Overflow: harmless.** `minRev + watchBatchMaxRevs + 1` wraps when `minRev` is near `MaxInt64`:
   - a `Restore` future watcher at `MaxInt64 − 2`;
   - every chosen watcher compacted, so `chooseAll` returns `MaxInt64`.

   `maxRev` is then negative, and `rangeEvents(minRev, negative)`'s byte range
   `[0x7fff…, 0x8000…)` holds no revision key. So the scan is empty, as on `main`, and nothing
   panics (`watchable_store_window_overflow_test.go`, the reviewer's `TestReviewAllCompactedOverflow`,
   both pass on head and base). The Lean model has no compaction and `minRev ≤ curRev`, so it does
   not reach these cases.
6. **Victims and `moveVictims`:** victims inherit the bug, because their `minRev` is set in
   `syncWatchers` before they become victims. `moveVictims` scans nothing and needs no bound.

No bug in the pinned code was found; nothing goes in `issues/`. The PR fixes nothing recorded in
`issues/`.

Reviewer's points, all resolved:
- the lemma now has the context's premises, so it is false exactly when the scan is cut;
- the soundness of the `all_goals` restructuring and of the translation diff was checked;
- the overflow cases were checked in Go.

## Draft review comment

> Thanks for looking at this. As written, the change can drop watch events. The scan now stops at
> `minRev + watchBatchMaxRevs + 1`, but the rest of `syncWatchers` still assumes it reached
> `curRev`. Every chosen watcher gets `w.minRev = curRev+1`, and one with no events in the window,
> or with fewer than `watchBatchMaxRevs` revisions of events there, is moved to `synced`. Its
> events between the window's end and `curRev` are never sent, and the response says
> `Revision: curRev`.
>
> Reproduction with the default constants: put `b` 1500 times, then `a` once, and watch `a` from
> revision 1. On this branch the watcher is synced without receiving the `a` event; on `main` it
> gets it.
>
> `TestWatchBatchUnsynced` (already in `watchable_store_test.go`) also hangs with this change. With
> `watchBatchMaxRevs = 4` and the watch at revision 1, the window `[1, 6)` has only 4 revisions with
> events, so the watcher is synced after `[2 3 4 5]` and never gets the rest. It only works when
> the watcher's key has an event at every revision from the window's start. Even then a second
> watcher chosen in the same pass with a later start revision is cut short.
>
> To keep the guarantee, when `maxRev <= curRev`, a watcher should stay unsynced with
> `w.minRev = max(maxRev, w.minRev)` (or `moreRev`) instead of moving to `synced`. #22304 does this
> (`reachedCurRev`).
