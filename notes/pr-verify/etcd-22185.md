## Verdict

The change is sound as far as it was verified. `progressIfSync`'s existing spec, which is
unchanged, is re-proved for the new code with no new axiom or `sorry`: the proof takes
`s.store.revMu` shared and reads `currentRev` through the lock's invariant, so the read is
race-free. Every writer of `currentRev` holds `watchableStore.mu` exclusively, so the revision read
is the same value the old `s.rev()` returned. What the proof does **not** cover is the point of the
PR. Perennial's specs are partial correctness, and `sync.RWMutex`'s specs carry no lock order, so
the deadlock and its absence are both invisible to a proof (the old code's proof held as well). The
fix is checked by the PR's test and a stress probe (both deadlock before the fix and pass after it)
and by a manual lock-order audit. One finding is about the PR's motivation, not its code:
in an etcd server, the PR's deadlock scenario looks unreachable (below).

## Findings

1. **The bug the PR fixes is a real lock-order inversion in the pinned code**, recorded as
   `issues/etcd-watch-progress-lock-order-deadlock.md`. It is reproduced on `goose-lean`
   `09669450f` by the PR's test (`notes/pr-verify/etcd-22185/watchable_store_progress_deadlock_test.go`,
   `deadlock-test-base.log`) and by the reviewer's stress probe
   (`watchable_store_progress_stress_test.go`, `stress-test-base.log`). Both pass at the PR head
   (`deadlock-test-pr-head.log`, `stress-test-pr-head.log`, the latter under `-race`).
2. **The PR's (and #22184's) server-level scenario looks unreachable** (from the reviewer, checked
   by hand). #22184 says `createMergedSnapshotMessage`'s `KV().Commit()` runs "on the snapshot-send
   goroutine". At `cb846f6d2`/`09669450f` it runs synchronously in `applyAll` (`server.go` 995;
   `snapshot_merge.go` 36; only the send after it is a goroutine). The other server takers of
   `store.mu`'s write side (`server.go` 2099's `Commit`, `Compact`, `Restore`) and every write
   transaction (`txn/put.go`, `delete.go`, `txn.go`, lease revocation) also run on the apply loop's
   one goroutine, so a write transaction and an exclusive `store.mu` never overlap. The backend's
   periodic commit does not take `store.mu`. The inversion is reachable through mvcc's API (as the
   tests do), and the fix is still right: it restores the documented order at no cost. But the
   title's "deadlocks the apply loop" is, as far as we could find, not something a server does.
3. **Remaining inversion, not touched by the PR**: `watchableStore.Restore` (`watchable_store.go`
   208–210) takes `watchableStore.mu.Lock` and then `store.mu.Lock`. It needs a concurrent write
   transaction to deadlock, which a server does not have (both run on the apply goroutine). It is
   noted in the issue file.
4. **Spec weakness, not new**: the spec of `progressIfSync` and `watcher.send`'s spec do not
   constrain a progress response's `Revision`. So the property that matters for progress
   notifications (every event at or below the revision has been delivered, and later events are
   above it) is not proved, before or after; it is plan item K1 in `notes/STATUS.md`. The
   reviewer's argument, which the stress probe checks dynamically: `currentRev` changes only under
   `watchableStore.mu` held exclusively (`watchableStoreTxnWrite.End` around `notify` and the
   increment; `watchableStore.Restore`), so under `progressIfSync`'s shared hold the revision is
   stable and consistent with the synced set, exactly as with `s.rev()`.

Reviewer (a fresh subagent): no finding against the PR's code or the proof. Its finding on the
issue file's reachability claim was resolved by rewording the file. There are no open points.
