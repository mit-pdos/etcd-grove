## Verdict

**The PR has a bug in the asynchronous path, which is the feature it adds.** On the leader, peer
messages that carry a new commit index go out before etcd raises its own committed index. Raft
v3.7 in async mode can also commit and broadcast an index in a `Ready` that has no
`MsgStorageApply`, and `processAsyncReady` never raises the committed index for such a `Ready`. So
the leader's `getCommittedIndex()` can be behind what followers have already applied.
`LeaseRenew`/`LeaseTimeToLive` on the leader wait until `applied >= getCommittedIndex()` and then
look the lease up, so a lease granted through a follower can be "not found". A unit test and an
integration test show it (Findings, F1). This is the failure of the PR's CI test
`TestV3LeaseRenewStress` ("TTL shouldn't be 0 so soon").

The legacy (`Ready`/`Advance`) path, the default once the gate defaults to false as intended, is
re-verified. The Ready loop, `applyAll`, `applySnapshot`, `run`, and the raft wrapper's
construction are proved over the PR's code with **no new axiom and no `sorry`**. The PR's
refactor of `notifyc` into explicit channels preserves what the old proofs established. One legacy
behavior does change, harmlessly: `run` now serves merged-snapshot requests as a job of their own.

The asynchronous path (`processAsyncReady`, the append worker, the storage responses) is
translated but not specified. Raft's own proofs here cover synchronous writes only
(`NewRawNode.spec` requires `AsyncStorageWrites = false`), so the asynchronous path was reviewed by
hand and by tests instead.

### The specs that changed

- **`applyAll`** (`Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__applyAll.lean`).
  - Old: it takes `notifyc`, a unit channel it receives from after applying, and serves a pending
    merged-snapshot request on `msgSnapC`.
  - New: it takes `taSyncOk ap P` (`InvApplyAll.lean`): the `waitForStorageBeforeApply` flag;
    `raftStorageReadyC`, a broadcast channel it receives from (before applying if the flag is set,
    after otherwise); the completion callback (nil, or `{P} f() {True}`, with `P`); and
    `applyCompletedC` (nil, or the right to close it). It has no `msgSnapC` handling.
  - The postcondition is unchanged.
  - The spec covers both modes' use of the flag. `run` still meets the new premise (it passes the
    payload's channels), so `run`'s spec is unchanged.
- **`newRaftNode`** (`Spec/.../newRaftNode.lean`): new premises `cv.asyncStorageWrites' = false`
  and `context.isClosedchanInit` (`context.WithCancel`'s, a fact of `context`'s initialization,
  as `EtcdServer.start` already takes). `rnParts` (`InvNodeStart.lean`) records the switch and the
  cancel function's spec.
- **`isRaftNode`** (`InvRaftNode.lean`) gains `rnAsyncAddr r ↦□ false` and the storage responses'
  cancel function, `context.cancelSpec csr γ True`. `applyc`'s payload `rnApP` replaces
  `isUnitBag notifyc` by `rnApChans ap`: no wait, no callback, `raftStorageReadyC` to receive from,
  `applyCompletedC` with its right to close (owned by the apply side; the loop keeps a view to wait
  on). As with `notifyc` before, the channels carry no proposition. The orderings they enforce
  (persist before the snapshot backend opens, apply before a follower's send) are not modeled, and
  the proofs, being partial correctness, say nothing about termination.
- **raft's `newRaft`/`NewRawNode`/`setupNode`/`StartNode`** (`Spec/go_etcd_io/raft/v3/`) give back
  `∃ cv'', c ↦ cv'' ∗ ⌜cv''.ID' = cv.ID' ∧ cv''.AsyncStorageWrites' = cv.AsyncStorageWrites'⌝`.
  This is needed because the PR reads `b.config.ID` and `b.config.AsyncStorageWrites` after
  `StartNode`. It is sound because raft keeps no pointer to the `Config`: `newRaft` copies fields
  and `validate` only fills defaults (checked by the reviewer). `RestartNode` drops the returned
  `Config`. Only the new-cluster branch of `bootstrappedRaft.newRaftNode` is specified.

## Findings

Tests and logs are in `notes/pr-verify/etcd-22223/` (see its README).

- **F1 (bug in the PR, high): the leader broadcasts a commit before etcd records it.** In
  `processAsyncReady` (`raft.go:378-449`), the peer messages of a `Ready` (including `MsgApp`s
  carrying the new commit) are sent at the `MsgStorageAppend` case (`sendMessages()`, line 396).
  `updateCommittedIndex` for the batch runs later, at the `MsgStorageApply` case (line 421). The
  legacy path raises the committed index first (line 302) and sends after. Worse, raft v3.7 in
  async mode can commit and broadcast an index in a `Ready` with no `MsgStorageApply`: the followers
  acknowledged before the leader's own write was durable. The leader's `getCommittedIndex()` then
  lags what followers have applied. `LeaseRenew`/`LeaseTimeToLive` on the leader call
  `waitAppliedIndex` (`v3_server.go:458`, 514/519/638): it waits until `applied >=
  getCommittedIndex()` and then reads the lessor, so a lease granted through a follower is not yet
  there.
  - Tests: `async_commit_order_test.go`, three unit tests against the PR head. The legacy-order
    test passes; the async one fails ("MsgApp with commit 1 sent while etcd's committed index was
    0"); real raft `RawNode`s commit index 3 in a `Ready` without `MsgStorageApply`.
  - Integration test: `async_lease_renew_test.go`, with a slow-leader-disk instrumentation. Legacy:
    ok. Async: 20 of 20 keepalives right after a successful `LeaseGrant` through a follower return
    TTL 0.
  - Fix direction: in `processAsyncReady`, raise the committed index from the `MsgStorageAppend`'s
    `HardState` commit (and from an apply message) before sending any peer message.
  - Why the proofs cannot see this: the property the legacy loop keeps ("etcd's committed index is
    at least any commit sent to peers") is not stated by any spec here. `committedLast` covers only
    the apply payload. A spec of the async path would have to state it.
- **F2 (behavior change in the PR, medium): a leader with a stalled disk keeps its leadership.**
  This is the reviewer's analysis of the PR's CI logs. The WAL save now runs on the append worker,
  so a stalled save no longer stops ticks and heartbeats. The leader is never replaced, but it
  cannot apply, so its own clients hang while writes through followers commit.
  - The e2e failures are this: `TestLeaseRevoke_IgnoreOldLeader/3_members` times out "Waiting for
    a new leader"; `TestHTTPHealthHandler/raft_loop_deadlock` gets 200 instead of a timeout.
  - The failpoints `raftBeforeLeaderSend`, `raftBeforeFollowerSend` and `raftBeforeAdvance`
    (`raft.go:314, 353, 360`) exist only on the legacy path, so the robustness scenarios that use
    them fail to trigger ("member didn't exit as expected").
  - Whether this is acceptable is a design question for the PR. The health checks and the
    failpoint scenarios need adapting either way.
- **F3 (the PR's comment overclaims; low).** `toApply.waitForStorageBeforeApply`'s comment
  (`raft.go:83-87`) and the barrier comment in `processAsyncReady` say the barrier keeps the durable
  backend consistent index from passing the durable WAL `HardState` commit.
  - The barrier closes when the append worker's `WAL.Save` returns. For a `HardState` that only
    advances `Commit`, `Save` neither syncs nor flushes (`raft.MustSync` is false).
    `wal_commit_only_save_test.go` shows a crash copy taken right after `Save` returns still has
    the old commit.
  - etcd already tolerates consistent index > durable commit (`bootstrap.go:595-602`).
  - In async mode raft hands `MsgStorageApply` only entries already stable, and those were appended
    to the `MemoryStorage` before their append response. So the barrier seems to protect neither
    durability nor the `MemoryStorage`.
  - It does add latency: the apply waits (`server.go:980`) for the worker to finish everything
    queued ahead, including the fsync of the same `Ready`'s new entries (up to 64 appends).
  - Suggest dropping the claim, or the barrier.
- **F4 (legacy behavior change; low, benign).** The PR moves the merged-snapshot send out of
  `applyAll` into `run`'s `select` (`server.go:846`), as a scheduler job of its own. A leader's
  snapshot request is now served without waiting for the next apply, still in FIFO order after the
  queued applies. The proof of `run` covers it: the job reads the applied index, term and conf
  state from the apply thread's resources and passes them on. The PR's description does not
  mention it.
- **F5 (the head is not mergeable as is).** The last commit sets the gate's default to true
  ("TODO ... should default to false"). With it on, the verified Ready/Advance path is not the one
  that runs. The composed new-cluster result (`server_raft_node_start`) also requires
  `AsyncStorageWrites = false`, as it requires `CheckQuorum`/`PreVote` off.
- **Not a bug: "entry at index N missing from unstable log; ignoring"** (the maintainer's CI
  remark). The reviewer traced it to raft attaching its last entry ID to every append response,
  including commit-only ones (`rawnode.go:274-357`). After an earlier response marked N stable,
  each later one naming N logs this at Info level (`log_unstable.go:138-143`). Raft's own
  `testdata/async_storage_writes.txt` has the line too. It does not indicate reordering: the worker
  is FIFO, and the snapshot's response is sent while the worker waits on `applyCompletedC`.
- **Checked, no problem found** (by hand and by the reviewer):
  - No deadlock on `applyc` between the main loop and the worker's snapshot send: raft emits no
    `MsgStorageApply` while a snapshot is unstable or in progress, so no apply job waits on a
    barrier queued behind a snapshot.
  - Shutdown: `run`'s defer stops the scheduler before `s.r.stop()`, so the worker is alive while
    queued jobs drain, and every blocking select has `stopped` or `asyncStopc`.
  - Batching: last-wins `HardState`, contiguous entries only, a snapshot alone, responses in order.
  - Followers' conf changes: raft refuses to campaign with an unapplied conf change, and applied
    advances only on `MsgStorageApplyResp`, sent after `ApplyConfChange`.
  - `raftAdvancedC` still fires after raft's applied index moved.
- `issues/`: nothing new in the existing (pinned) code. F1-F5 are about the PR's code and are
  recorded here, not in `issues/`. `issues/raft-async-applied-above-durable-commit.md` (branch
  `pr-verify/raft-37`) does not bite this PR: etcd does not set `Config.Applied` on restart.
- Other PR branches touch the same proofs: `pr-verify/etcd-22485` (`processMessages`'s order),
  `pr-verify/etcd-22495` (`applyAll`/`applyWait`), `pr-verify/etcd-22496` (`start`/`run`). None
  covers this PR's functions; their changes would conflict textually with this one.
