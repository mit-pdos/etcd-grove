## 1. Summary of the PR and Its Evolution on `main`

### 1.1 The Underlying Bug (`etcd-io/etcd#18667`)
Prior to PR `#18680` and commit `fbba4f46e`, `applyEntryNormal` (`server/etcdserver/server.go`, later extracted to `apply.Apply` in `server/etcdserver/apply/apply.go`) contained an optimization introduced in commit `009057374`:
```go
	needResult := s.w.IsRegistered(id)
	if needResult || !noSideEffect(&raftReq) {
		if !needResult && raftReq.Txn != nil {
			removeNeedlessRangeReqs(raftReq.Txn)
		}
		ar = s.uberApply.Apply(&raftReq, shouldApplyV3)
	}
```
where `removeNeedlessRangeReqs` stripped all top-level `*pb.RequestOp_RequestRange` operations from `raftReq.Txn.Success` and `raftReq.Txn.Failure` in-place whenever `!needResult` (`w.IsRegistered(id) == false`, which is true on **all followers** and on the leader if the client waiter timed out).

Because `removeNeedlessRangeReqs` mutated `raftReq.Txn` *before* `uberApply.Apply` ran `authApplierV3.Txn` (`CheckTxnAuth`) and `txn.Txn` (`checkTxn` -> `checkRange`), it caused **two severe leader-vs-follower state-machine divergences**:
1. **MVCC Revision Validation Divergence (`checkTxn` / `checkRange`)**:
   If a write `Txn` contained both a `RequestRange` with `Revision > rv.Rev()` (`mvcc.ErrFutureRev`) or `Revision < rv.FirstRev()` (`mvcc.ErrCompacted`) and a `RequestPut` / `RequestDeleteRange`, the leader (`needResult == true`) ran `checkRange` inside `checkTxn`, rejected the entire `Txn`, and committed nothing. On all followers (`needResult == false`), `removeNeedlessRangeReqs` stripped the `RequestRange` before `checkTxn` ran, so `checkTxn` succeeded and all followers committed the `Put`/`DeleteRange` writes (`TestIssue18667_RemoveNeedlessRangeReqs_RevisionInconsistency` in [`notes/pr-verify/etcd-18680/repro_test.go`](etcd-18680/repro_test.go)).
2. **RBAC Authorization Bypass Divergence (`authApplierV3.Txn` / `CheckTxnAuth`)**:
   When authentication was enabled, `authApplierV3.Txn` called `CheckTxnAuth` inside `uberApply.Apply`. If a user had `WRITE` permission on `"k2"` but lacked `READ` permission on `"secret"`, a `Txn` with `[RequestRange("secret"), RequestPut("k2", "pwned")]` was rejected with `auth.ErrPermissionDenied` on the leader (`needResult == true`), whereas on all followers (`needResult == false`), `removeNeedlessRangeReqs` stripped `RequestRange("secret")` before `CheckTxnAuth` ran, allowing the unauthorized write `"k2" = "pwned"` to commit on every follower (`TestIssue18667_RemoveNeedlessRangeReqs_AuthBypassInconsistency` in [`notes/pr-verify/etcd-18680/repro_test.go`](etcd-18680/repro_test.go)).

### 1.2 PR `#18680` vs. `main`'s `SkipRangeExecution` (`fbba4f46e`)
- **PR `#18680`** (`fa880f585b88`) removes `if !needResult && raftReq.Txn != nil { removeNeedlessRangeReqs(raftReq.Txn) }` and `removeNeedlessRangeReqs` completely so that leader and followers always execute the exact same `Txn` validation and range execution (`SkipRangeExecution: false` in [`server/etcdserver/apply/apply.go:43`](../../Code/go_etcd_io/etcd/server/v3/etcdserver/apply.lean#L203)).
- **On `main` (`fbba4f46e`)**, `removeNeedlessRangeReqs` was instead replaced by `InternalRaftRequestWrapper{SkipRangeExecution: !needResult && raftReq.Txn != nil}`, which runs `CheckTxnAuth` and `checkTxn` (`checkRange`) on all members, and then skips `executeRange` inside `executeTxn` (`server/etcdserver/txn/txn.go:151–158`) when `skipRangeExecution == true`.

## 2. Findings from Formal Verification

### 2.1 Remaining Leader-vs-Follower Asymmetry on `main` Eliminated by PR `#18680`
In our formal proof of `txn.executeTxn` ([`Proof/go_etcd_io/etcd/server/v3/etcdserver/txn/executeTxn.lean`](../../Proof/go_etcd_io/etcd/server/v3/etcdserver/txn/executeTxn.lean#L327-L420) and [`Proof/go_etcd_io/etcd/server/v3/etcdserver/txn/TxnRun.lean`](../../Proof/go_etcd_io/etcd/server/v3/etcdserver/txn/TxnRun.lean#L306-L314)), the precondition `GetOk` (`o.base.rev = W64 0 ∧ validSortTarget o ∧ ¬ cutEarly o`) is used **only** in the `skipRangeExecution = false` branch (which calls `executeRange`), and **not** in the `skipRangeExecution = true` branch.

Inspecting why `executeRange` requires `validSortTarget o` while `checkTxn` (`checkRange`) does not reveals a remaining leader-vs-follower asymmetry in `main`'s `SkipRangeExecution`:
- `checkRange` (`server/etcdserver/txn/range.go:174–184`) only checks `req.Revision` (`== 0`, `> rv.Rev()`, `< rv.FirstRev()`). It does **not** check `req.SortTarget`.
- Inside `executeRange` -> `sortRangeResults` (`server/etcdserver/txn/range.go:125–154`), if `!IsDefaultOrdering(r.SortTarget, sortOrder)` and `r.SortTarget` is not one of `KEY (0)..VALUE (4)`, line 145 calls:
  ```go
  lg.Panic("unexpected sort target", zap.Int32("sort-target", int32(r.SortTarget)))
  ```
- Consequently, on `main` (`SkipRangeExecution: !needResult && raftReq.Txn != nil`), if an `InternalRaftRequest` with a write `Txn` contains a `RequestRange` with an invalid `SortTarget` (e.g., from a direct Raft proposal, version skew, or unvalidated internal request), `checkTxn` succeeds on all members; on the leader (`needResult == true`, `SkipRangeExecution == false`), `executeRange` panics in `sortRangeResults` before `txnWrite.End()` (crashing the leader without committing the write), whereas on all followers (`needResult == false`, `SkipRangeExecution == true`), `executeTxn` skips `executeRange`, does **not** panic, and `txnWrite.End()` commits the write to MVCC and BoltDB!
- Similarly, if BoltDB / in-memory index corruption is encountered on a key read by a `RequestRange` in a write `Txn` (`kvstore_txn.go:127–148`), `executeRange` calls `lg.Fatal` on the leader (`SkipRangeExecution == false`) while followers (`SkipRangeExecution == true`) skip `executeRange` and commit the write.
- **With PR `#18680` (`SkipRangeExecution: false` in `apply.Apply`)**, both leader (`needResult == true`) and followers (`needResult == false`) execute `executeRange` identically (`TestMainSkipRangeExecution_InvalidSortTargetAsymmetry_FixedByPR18680` in [`notes/pr-verify/etcd-18680/repro_test.go`](etcd-18680/repro_test.go)).

### 2.2 End-to-End Client-to-Server Specification Strengthening Unlocked by PR `#18680`
In `etcd-grove` on `main`, the end-to-end client-to-server transaction predicate `TxnModel.exactGets` ([`Proof/go_etcd_io/etcd/cache/v3/InvEtcdTxn.lean:610–615`](../../Proof/go_etcd_io/etcd/cache/v3/InvEtcdTxn.lean#L610-L615)) previously had to **forbid all `Get` (`RequestRange`) operations inside any writing transaction**:
```lean
((t.thenOps ++ t.elseOps).all TxnOp.isGet = false →
  (∀ o : OpFull, TxnOp.get o ∉ t.thenOps ++ t.elseOps) ∧ ...)
```
because `apply.Apply` set `SkipRangeExecution: !needResult && raftReq.Txn != nil`, so `apply.applyStep` only guaranteed `skip = true → rq.txn.isSome = true` (leaving open the possibility that a writing transaction's `Range` responses were header-only with `skip = true`).

With PR `#18680` (`SkipRangeExecution: false` in `apply.Apply`):
1. We strengthened `apply.applyStep` ([`Proof/go_etcd_io/etcd/server/v3/etcdserver/apply/InvUber.lean:119–125`](../../Proof/go_etcd_io/etcd/server/v3/etcdserver/apply/InvUber.lean#L119-L125)) and `apply.uberApplier.Apply.spec` ([`Spec/go_etcd_io/etcd/server/v3/etcdserver/apply/uberApplier__Apply.lean:34–50`](../../Spec/go_etcd_io/etcd/server/v3/etcdserver/apply/uberApplier__Apply.lean#L34-L50)) so that every `.dispatched o skip` transition satisfies `skip = false`.
2. We proved `apply_dispatched_no_skip` and `apply_sideEffect_not_waived` in [`Proof/go_etcd_io/etcd/server/v3/etcdserver/apply/Results.lean:594–608`](../../Proof/go_etcd_io/etcd/server/v3/etcdserver/apply/Results.lean#L594-L608), establishing that no request with side effects (and in particular no `Txn` request) is ever waived (`out.waived = false`), even when no waiter is registered (`needResult == false`).
3. We relaxed `TxnModel.exactGets` ([`Proof/go_etcd_io/etcd/cache/v3/InvEtcdTxn.lean:610–615`](../../Proof/go_etcd_io/etcd/cache/v3/InvEtcdTxn.lean#L610-L615)) and strengthened `noZeroEnd_wire` and `txnCommitResultTok_of_reply` ([`Proof/go_etcd_io/etcd/client/v3/ServerKVTxn.lean:274–309`](../../Proof/go_etcd_io/etcd/client/v3/ServerKVTxn.lean#L274-L309), [`748–801`](../../Proof/go_etcd_io/etcd/client/v3/ServerKVTxn.lean#L748-L801)) so that **mixed read-write transactions** (transactions containing both `Put`/`DeleteRange` and `Get` operations with `o.base.rangeEnd ≠ [W8 0]`) are now proven end-to-end to return exact `Get` key-value results (`txnCommitResultTok`)!

### 2.3 Related Validation Discrepancy: `checkRange` vs. `mvcc.rangeKeys` on Negative `Revision`
During verification of `checkRange` (`server/etcdserver/txn/range.go:174–184`) vs. `mvcc.rangeKeys` (`server/storage/mvcc/kvstore_txn.go:73–83`), we also identified a pre-existing discrepancy when `req.Revision < 0` (e.g., `Revision: -1`):
- In `mvcc.rangeKeys` (`kvstore_txn.go:78–83`):
  ```go
  if rev <= 0 {
      rev = curRev
  }
  if rev < tr.s.compactMainRev {
      return &RangeResult{KVs: nil, Count: -1, Rev: 0}, ErrCompacted
  }
  ```
  All negative revisions `rev <= 0` are normalized to `curRev` before checking `rev < tr.s.compactMainRev`. Thus, a standalone `Range` with `Revision: -1` succeeds both before and after compaction.
- In `checkRange` (`range.go:174–184`):
  ```go
  switch {
  case req.Revision == 0:
      return nil
  case req.Revision > rv.Rev():
      return mvcc.ErrFutureRev
  case req.Revision < rv.FirstRev():
      return mvcc.ErrCompacted
  }
  ```
  `checkRange` only checks `req.Revision == 0` (not `req.Revision <= 0`). Before any compaction occurs (`rv.FirstRev() == -1`), `Revision: -1` passes `checkRange` (`-1 < -1` is false) and reads `curRev` in `rangeKeys`. Once any compaction occurs (`rv.FirstRev() >= 1`), `checkRange` rejects `Revision: -1` with `mvcc.ErrCompacted` (`TestCheckRangeVsRangeKeys_NegativeRevisionAfterCompaction` in [`notes/pr-verify/etcd-18680/repro_test.go`](etcd-18680/repro_test.go)).

### 2.4 Performance Tradeoff of PR `#18680` (Why PR `#18680` Was Marked `[WIP]`)
PR `#18680` lists `- [ ] evaluate the performance impact` as an open item. Specifically:
- In a write `Txn` that includes a `RequestRange` (e.g., reading a large range of keys alongside a `Put`), `executeTxn` runs while holding `txnWrite = kv.Write(trace)` (`tx.LockInsideApply()` on BoltDB's `batch_tx` and `s.mu.RLock()` on the MVCC store) on the single-threaded Raft apply loop.
- With PR `#18680` (`SkipRangeExecution: false`), every follower (and the leader when a waiter has timed out) executes the full `executeRange` (B-tree index traversal, BoltDB `tx.UnsafeRange` lookups, `proto.Unmarshal` of every `mvccpb.KeyValue`, `filterRangeResults`, and `sortRangeResults`) even though `needResult == false` and the resulting `*pb.RangeResponse` is discarded.
- Note that if `main`'s `SkipRangeExecution` optimization is retained instead of PR `#18680`, `checkRange` in `server/etcdserver/txn/range.go` should be strengthened to also validate `req.SortTarget` and `req.SortOrder` (and `req.Revision <= 0`) so that `checkTxn` cannot pass on an operation that would panic `executeRange`.
