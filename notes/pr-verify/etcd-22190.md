# Verification of etcd-io/etcd#22190

- **PR**: etcd-io/etcd#22190, "etcdserver: don't read storage version from a closed backend",
  https://github.com/etcd-io/etcd/pull/22190, head `455bf3f8a30406899268c6925e607beaf6f52cac` (one
  commit; open, "needs rebase"; two required Prow jobs failed on it, not looked into). Fixes
  etcd-io/etcd#22189.
- **Verified at**: `mit-pdos/etcd-grove` branch `pr-etcd-22190-goose-lean` (`f150c16f9`): the PR's
  diff, with its test, applied onto the pinned `goose-lean` `09669450f`.
- **Conflict**: one, in `Cleanup`. The PR's first change (`s.bemu.Lock()`/`Unlock()` around
  `s.be.Close()`) has been in upstream `main` since d6af8028d ("Support non-blocking
  defragmentation", etcd-io/etcd#22425, merged 2026-10-09), so it is in the pin too. That is why the PR needs a rebase. I kept the pin's
  lock and added the PR's comment above it. So on the verified code, as on today's `main`, the
  PR's only code change is `StorageVersion`'s check of `s.stopping`. Apart from that, the
  verified code is exactly the PR's.

## Verdict

The fix is sound. With the check, `StorageVersion` never reads a closed backend, and the proof
covers it running concurrently with `Cleanup`. `StorageVersion` and `Cleanup` are both proved
with no `sorry`, over a new lock invariant for `s.bemu`: under the lock there is either a share
of the backend's "open" token, or the backend is closed for good and `s.stopping` is closed.
`run`'s shutdown, re-proved, is what makes the PR's argument hold: it closes `stopping` before
`Cleanup`. The code without the check does not meet the spec.

What is not covered:
- the Go callers of `StorageVersion` (the `Status` RPC, `/version`, the storage-version monitor)
  are not verified;
- `schema.DetectSchemaVersion` is assumed (a new trust-boundary axiom);
- the server's backend contract is a construction premise, not yet derived from the verified
  backend's proofs.

The PR fixes one instance of a wider bug. Three other paths still use the backend after
`Cleanup`, and the PR leaves them as they are:
- `Defragment`: `lg.Fatal`;
- the `Snapshot` RPC's storage-version read: the same nil dereference;
- `Compact`'s `ForceCommit`: `lg.Fatal`.

### Old and new specs

- **`s.bemu`'s lock invariant** (`Proof/.../etcdserver/InvBackendLife.lean`, `bemuP`; before:
  `InvApplyAll.lean`, `∃ b, s.be ↦{q} b`). Now `bemuP s L q` holds:
  - half of `s.be`, scaled by `q`;
  - the backend's contract `beLifeOk b L.O`: a fractional open token `L.O`, `ReadTx()` returning a
    `schemaReadTx` of it, and `Close()` taking all of it;
  - and either `L.O q` or `beShut s L`. `beShut` means the backend is closed for good (the closer's
    flag, discarded at `true`) and `s.stopping` is closed (its done view, which is persistent).

  `bemuP_fractional` proves it fractional. A reader slot is `srvBemuReader s := ∃ L, ownRWMutex
  bemu (bemuP s L)`. The other half of `s.be` is in `Cleanup`'s resources, because `Cleanup` reads
  `s.be` before taking the lock. This models Go correctly: the apply goroutine is `s.be`'s only
  writer.
- **`StorageVersion`** (`Spec/.../EtcdServer__StorageVersion.lean`; before: no spec). The caller
  holds a reader slot of `bemu`, the logger, and a view `cl` of `stopping`, any time after `start`
  and concurrently with `Cleanup`. Under these:
  - the backend is read only with a share of its open token (`DetectSchemaVersion`'s contract asks
    for one);
  - the result is `nil` or a fresh `*semver.Version`;
  - the result is `nil` if `cl` is the done view.

  The proof: in the shut case, the done view makes the non-blocking receive ready, so the function
  returns `nil` without reading. In the open case, both branches of the `select` hold the share.
  Without the PR's `select`, the shut case has no share to give `DetectSchemaVersion`, so the
  pinned code does not meet the spec.
- **`Cleanup`** (`Spec/.../EtcdServer__Cleanup.lean`). Old: `{{ True }} Cleanup() {{ True }}`, an
  axiom. New: given `srvCleanupRes s` and the done view of `stopping`, it returns. `srvCleanupRes s`
  is:
  - a reader slot of `bemu`;
  - the closer's flag `beCloser L`;
  - the other half of `s.be`;
  - the contracts of `lessor.Stop`, `kv.Close`, `authStore.Close` and `compactor.Stop`, each
    "returns, or the field is nil".

  The proof: the closer's flag rules out the shut case, so the write lock yields the whole open
  token. `Close` consumes it, and the resource goes back as shut. The new spec has a stronger
  precondition than the old one: an incompatible change, followed to the callers below.
- **`schema.DetectSchemaVersion`** (`Spec/go_etcd_io/etcd/server/v3/storage/schema/DetectSchemaVersion.lean`,
  a new axiom). Given a `schemaReadTx rt O` and `O q`, it returns some version and some error, and
  gives back `O q`. `schemaReadTx` says three things:
  - `RLock` turns `O q` into a held state;
  - `UnsafeRange` keeps the held state and returns read-only slices;
  - `RUnlock` gives `O q` back.

## Callers (step 6)

- `Cleanup` (incompatible spec). Its only caller in the server is `run`'s deferred shutdown,
  which is verified. The new precondition holds there: `run` holds `srvCleanupRes s` (a new row
  `"Hcln"` of `isServerRun`, `InvRun.lean`), and it has just closed `stopping` itself (GoAttach's
  protocol: `close(s.stopping)` under `wgMu`), which gives the done view
  (`EtcdServer__run.lean`, `run_shutdown`). So the PR's premise "`stopping` is closed strictly
  before `Cleanup`" is checked in `run`.
  - `run` is called by `start` (verified, via `go s.run()`). It forwards the row from the
    construction premise `isServerBuilt` (new row `"Hcln"`, `InvStart.lean`; `Start`'s spec,
    unchanged, takes that premise).
  - Spec changes stop there: `run`, `start` and `Start` keep their statements. Only the premise's
    rows changed.
  - Not verified: `embed.StartEtcd`'s `InitialCheck` failure path calls `e.Server.Cleanup()`
    before `Start`, with `s.stopping` still nil. No client is served yet, so it is harmless, but
    the PR's comment ("readers arriving afterwards observe `s.stopping` as closed") does not hold
    there.
- `StorageVersion` (new spec; before, the function had none). Its callers:
  - `serverVersionAdapter.GetStorageVersion`, from `maintenanceServer.Status` and
    `version.Monitor.UpdateStorageVersionIfNeeded`;
  - the `/version` HTTP handler.

  None of them is translated with its body, and `monitorStorageVersion` is a names-only axiom, so
  this path stops at an exported API. The user-visible behavior change: during shutdown, `Status`
  omits `storageVersion` and `/version` reports "unknown". The PR says so, and that is harmless.

  One effect the PR does not mention: in the window between `close(s.stopping)` and the monitor
  goroutine's exit, `UpdateStorageVersionIfNeeded` can now see `nil`. It then calls
  `UpdateStorageVersion`, which runs `UnsafeMigrate` against the backend, still open (since
  `Cleanup` waits for `s.wg`). When the versions already match, the plan is empty and nothing is
  written. If a downgrade is enabled, it can log "The server is ready to downgrade" spuriously.
  This was not reproduced.
- The other users of `bemu`'s invariant, re-checked over the new `bemuP`:
  - `Backend()`, re-proved (`EtcdServer__Backend.lean`);
  - `applyAll`, `newBackendQuota`, `NewQuotaKVServer`, which take `srvBemuReader s`, rebuilt
    unchanged;
  - `applySnapshot`, the writer, is unaffected as verified. It is proved under raft's
    no-snapshot contract, so it never swaps the backend.

    Verifying the swap would need a redesign (the reviewer's point). `bemuP` has one open token
    for every backend, and `applySnapshot` closes the old backend outside `bemu`. The half of
    `s.be` it would need as the writer is in `run`'s resources.

The whole build is `lake build`, 5109 jobs, with no errors.

Compared with `lean`:
- **Gone**: `EtcdServer.Cleanup.wp_proof`, the axiom `{{ True }} Cleanup() {{ True }}` that `run`
  rested on.
- **New**: `schema.DetectSchemaVersion.wp_proof`. It is believed because `DetectSchemaVersion`
  (`schema.go:85`) only calls `tx.RLock()`, then `UnsafeReadStorageVersion` and
  `UnsafeReadConsistentIndex` (up to three `UnsafeRange`s on the meta bucket, reading
  `vs[0]`), then `tx.RUnlock()`. Everything else is pure parsing (`semver.NewVersion`) or
  `version.V3_5`. Its contract requires exactly what the verified backend's reads require: a share
  of the open token (`readTx.RLock`'s `bOpen γ q`).
- `etc/tcb-baseline.txt` is updated (`--check --update`).

These are not axioms, but they are assumptions, so `etc/tcb-report.py` does not list them:
- **The construction premise's new row**: `isServerBuilt`'s `"Hcln" ∷ srvCleanupRes s`. It
  assumes:
  - the server's backend satisfies `beLifeOk`;
  - `Stop`/`Close` of the lessor, the KV, the auth store and the compactor return;
  - one closer's flag;
  - the other half of `s.be`.

  `Cleanup`'s trust moved here from the old axiom. It did not disappear.
- **The backend's contract**: `beLifeOk`/`schemaReadTx` is not yet derived from the verified
  backend (`storage/backend`). Its `readTx.RLock` also wants a linear reader slot (`rdTok`), and
  its `UnsafeRange` wants a bucket and the key slices, which a fractional `O` and this contract do
  not carry. So `srvCleanupRes` cannot yet be discharged from the backend's own proofs. A bridge
  lemma is the open step.
- **The existential `L`**: it is quantified separately in each holder's slot (`srvBemuReader`,
  `srvCleanupRes`). No proof relies on two holders having the same `L`, so this is sound. A real
  construction gives them the same `L` anyway: there is one `init_RWMutex` per mutex, and one lock
  invariant.

## Findings

1. **The bug the PR fixes is in the pinned code**: `issues/etcd-storageversion-closed-backend.md`.
   - Reproduced at the base, where the PR's test and the probe `TestProbeStorageVersionAfterCleanup`
     panic with the nil `*bolt.Tx` dereference of #22189. Without the PR, the concurrent subtest
     also hangs (`notes/pr-verify/etcd-22190/base-goose-lean.log`).
   - With the PR, they pass (`pr-goose-lean.log`).
   - The proof confirms the fix: `StorageVersion` reads only with a share of the open token, and
     there is none after `Cleanup`.
2. **The same class of bug, in existing code, not fixed by the PR**:
   `issues/etcd-backend-use-after-cleanup.md`. All of these fail at both the base and the PR head:
   - `Defragment` after `Cleanup`: `FATAL failed to commit tx {"error": "tx closed"}`, a process
     exit.
   - `Compact`'s `ForceCommit` after `Cleanup`: `FATAL failed to begin tx {"error": "database not
     open"}`.
   - The Maintenance `Snapshot` RPC's first step, `schema.ReadStorageVersion(Backend().ReadTx())`:
     the same nil dereference as #22189 (the reviewer's probe,
     `notes/pr-verify/etcd-22190/snapshot_after_cleanup_probe_test.go`).

     `Backend()` releases `bemu` before the caller reads, so the PR's pattern cannot cover
     `Backend()`'s callers. They need a closed check in the backend itself, or `ErrStopped` before
     the call.

   Probes: `closed_backend_probe_test.go`. Logs: `base-goose-lean.log`, `pr-goose-lean.log`. The
   probes call the methods after `Cleanup` directly. That the RPCs can arrive in that window is
   the same window as #22189's; it was not reproduced end to end.
3. **No bug in the PR.** In the PR's test, the `ConcurrentWithCleanup` subtest's goroutines may
   still be running `StorageVersion` before `close(s.stopping)`. That is the intended interleaving,
   and the proof covers it.

## Reviewer

A fresh reviewer subagent checked the specs, the axiom, the invariant and the interleavings. Its
conclusions, and what I did with them:
- **PR change**: correct. `monitorStorageVersion` is a `GoAttach` goroutine, so it finishes
  before `Cleanup`. The remaining callers after `Cleanup` are `Status` and `/version`, which is
  the race the PR fixes.
- **New bug**: `Snapshot`'s `ReadStorageVersion(Backend().ReadTx())` (finding 2). Added to the
  issue file, with its probe.
- **The axiom was too strong**: `schemaReadTx`'s `UnsafeRange` returned slices with no ownership,
  while `DetectSchemaVersion` indexes them. The axiom, quantified over every `schemaReadTx`, was
  therefore false for some instantiations. Fixed: `UnsafeRange` now returns read-only key and
  value slices and value bytes (`InvBackendLife.lean`, `schemaReadTx`), and the proofs rebuilt.
- **`beLifeOk` is not related to the verified backend**: open, see "Trust base".
- **Cleanup's trust moved into the premise**: said above.
- **`applySnapshot` would need a redesign of the invariant**: noted above and in `notes/STATUS.md`.
- **Checked, no issue**:
  - `bemuP_fractional`;
  - the existential `L`;
  - the cases closed by contradiction: `beCloser_not_shut`, and the done view's ready receive;
  - `wp_select_stopping` proving both branches of a non-blocking receive;
  - no `sorry`.
- **Minor**: `StorageVersion` has no verified caller (its callers are untranslated, or names-only
  axioms), and its result is not related to the stored version. Both are acceptable for what the
  PR is about.
- **The stopping window's spurious `UpdateStorageVersion`**: harmless, as described under
  "Callers".

## Draft review comment (for the PR)

> The `select` on `s.stopping` under `bemu.RLock()` closes the race. `run` closes `stopping`
> before `s.wg.Wait()` and `Cleanup()`, and `Cleanup` closes the backend under `bemu.Lock()`. So
> a reader holding the read lock either sees `stopping` closed, or holds the lock while the backend
> is still open. Since #22425 ("Support non-blocking defragmentation") was merged, `main` already takes `bemu` in `Cleanup()`, so
> after a rebase only the `StorageVersion` hunk and the comment remain.
>
> The same "use after `Cleanup`" pattern is in a few other places that this PR doesn't touch, and
> they fail the same way in unit tests that call them after `close(s.stopping); s.Cleanup()`:
> - `Defragment()` (`s.be.Defrag()` under `bemu.RLock()`) exits with `failed to commit tx
>   {"error": "tx closed"}`;
> - `Compact`'s `s.be.ForceCommit()` exits with `failed to begin tx {"error": "database not open"}`;
> - `maintenanceServer.Snapshot`'s `schema.ReadStorageVersion(ms.bg.Backend().ReadTx())` hits the
>   same nil `*bolt.Tx` dereference as #22189. `Backend()` releases `bemu` before the read, so a
>   check like this one can't cover it.
>
> They may be worth a follow-up, maybe with `ErrStopped` returned once the server is stopping.
>
> A smaller side effect: during the stopping window, `UpdateStorageVersionIfNeeded` now sees `nil`
> from `GetStorageVersion()`, and calls `UpdateStorageVersion` with the cluster version. That is a
> no-op when the versions match, but it can log "The server is ready to downgrade" when a
> downgrade is enabled.
