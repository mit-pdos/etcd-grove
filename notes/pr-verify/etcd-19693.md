## Verdict

**Not safe as is.** Opening the WAL at the backend's consistent index instead of at its last
snapshot breaks two restart cases the current code handles, and a third the PR's own code does
not: (1) a follower that crashed after persisting a leader's snapshot but before swapping in its
database no longer recovers the database (`RecoverSnapshotBackend` is gone) and raft panics on
restart; (2) when the backend's consistent index is past the commit index of the WAL's last durable
`HardState` (which the code's own `--force-new-cluster` comment says happens), raft panics on a
plain restart (`state.commit 5 is out of range [8, 10]`); (3) at the PR's head, a backend without a
persisted conf state (written before v3.5, or never through a membership change since) makes
`MemoryStorage.Append` panic (`missing log entry`); rebased onto current upstream this becomes
`--force-new-cluster` removing none of the other members. All are shown by Go tests that pass on
the base; (1), (2) and the force-new-cluster case also fail on the verified fork code. What the proofs establish: the new raft
storage is exactly "snapshot at the backend position + the WAL's entries after it"
(`bootstrappedWAL.MemoryStorage`, proved over raft's verified `MemoryStorage`), and
`bootstrapWALFromBackend` returns the backend's position and conf state and the WAL's state, with
nothing tying the WAL's commit index to that position — which is what raft's restart needs.

Not covered: `bootstrap`, `bootstrapBackend`, `openWALFromPosition` (a postulate) and the `wal`
package (names-only), `bootstrapWALFromBackend` with `--force-new-cluster`, `MinimalEtcdVersion`,
the tools.

## The specs

- `Spec/go_etcd_io/etcd/server/v3/etcdserver/bootstrappedWAL__MemoryStorage.lean`: given the WAL's
  entries `p` continuing the base (the first at `pos.Index + 1` with a conf state, at `1` without),
  `MemoryStorage()` returns a fresh `MemoryStorage` whose raft view is `bwalStor pos confstate cs
  p` — a data-less snapshot at `pos` with `cs` (or none), then `p` — and whose hard state is the
  WAL's. Over raft's `NewMemoryStorage`, `ApplySnapshot`, `SetHardState`, `Append` (the append right
  from `memStorage_handout`).
- `Spec/.../etcdserver/bootstrapWALFromBackend.lean`: with the backend's meta keys `m0` fixed
  (nothing writes the backend during bootstrap), `ForceNewCluster = false`: the WAL's `pos` is
  `ciPos m0` (what `ReadConsistentIndex` reads), its conf state the backend's (`nil` or owned), its
  hard state and entries the WAL's after `pos` (`EntsAfter`), `haveWAL` set.
- `Spec/.../storage/schema/ReadConfStateFromBackend.lean`: `UnsafeConfStateFromBackend` under the
  read lock; `nil` or a fresh, owned conf state.
- `Proof/.../etcdserver/InvBootWAL.lean`: `RestartOk σ hs` restates `raft.loadState`'s premise
  (`committed ≤ hs.Commit ≤ lastIndex`, `Spec/go_etcd_io/raft/v3/raft__loadState.lean`) on the
  storage `newRaft` reads; `bwalStor_restartOk_iff`: for the PR's storage it is `pos.Index ≤
  Commit ≤ pos.Index + |p|`; `restartOk_counterexample`: finding 2's numbers violate it.
  `force_commit_lower`: the `--force-new-cluster` branch's `max(Commit, consistentIndex)` meets the
  lower bound, the plain path has no such step. (raft's `RestartNode.spec` covers only an empty
  storage, so the chain to `loadState` is stated, not proved.)
- `Proof/.../etcdserver/InvBootWALFromBackend.lean`: `entsAfter_head` (with a conf state, the
  WAL's entries meet `MemoryStorage`'s premise), `entsAfter_head_noConfState` (without one and with
  a non-zero consistent index they do not: finding 3, where `Append` panics).

No old spec existed for any of them; the specs pin what the PR does, and the lemmas state where it

## Findings

Tests: `notes/pr-verify/etcd-19693/` (README there: revisions and commands).

1. **Crash between persisting a received snapshot and applying its database: the member cannot
   restart.** The PR deletes `recoverSnapshot`, and with it `RecoverSnapshotBackend`, which swaps
   in `<index>.snap.db` when the WAL's latest snapshot is past the backend's consistent index
   (`server/storage/backend.go:102`; the e2e `TestRecoverSnapshotBackend` crashes at the failpoint
   `applyBeforeOpenSnapshot` for exactly this). With the PR the backend stays at its old index, the
   WAL is opened there, and raft gets a storage at index 3 with `HardState.Commit` 10: `raft:
   state.commit 10 is out of range [3, 3]` (panic). The PR comments out the unit test case for this
   ("have data files and snapshot db file") rather than replacing it. Test
   `TestRestartAfterSnapshotPersistedBeforeApplied`: fails at the PR head and on the fork branch,
   passes at both bases.
2. **Consistent index past the WAL's durable commit index: a plain restart panics.** etcd writes a
   `HardState` whose only change is `Commit` without an fsync, while the backend's commits are
   fsynced; the code's own comment in the `--force-new-cluster` branch ("This can result in
   consistent_index > CommitIndex", raft#300) describes it. Before the PR, raft restarted at the WAL
   snapshot with commit 5 and re-delivered 6..8, which the apply loop skips (index ≤ consistent
   index). With the PR the raft storage starts at 8: `state.commit 5 is out of range [8, 10]`.
   The PR applies the `max(Commit, consistentIndex)` fix only with `--force-new-cluster`. Lean:
   `restartOk_counterexample`. Test `TestRestartWithConsistentIndexPastWALCommit`: fails at the PR
   head and on the fork branch, passes at both bases.
3. **No conf state in the backend: `MemoryStorage.Append` panics (PR head).** etcd persists the
   conf state in the backend only since v3.5 and only when it applies a membership change or
   receives a snapshot (`BackendHooks.SetConfState`, called from `applyConfChange`), so a cluster
   created before v3.5 with no membership change since has none. The PR then applies no snapshot
   and appends the entries after the consistent index to an empty storage: `missing log entry
   [last: 0, append at: 4]`. Lean: `entsAfter_head_noConfState`. Test
   `TestRestartWithBackendWithoutConfState`: fails at the PR head, passes at the base. On a
   rebase onto current upstream the v3-store override hides this in `MemoryStorage()`, but not in
   the `--force-new-cluster` branch, which computes the members to remove from the backend's conf
   state (nil) plus the WAL entries after the consistent index: **on the verified fork code,
   `--force-new-cluster` on a member of `{1,2,3}` whose backend has no conf state removes no one**
   (`added [1] removed []`; the base removes 2 and 3 from the WAL snapshot record's conf state), so
   the remaining voters (from the v3 store) keep the forced node from electing itself. Test
   `fork/force_new_cluster_confstate_test.go` (the reviewer's): fails on the fork branch, passes on
   the fork base.

No bug in the existing (pinned) code was found; `issues/` is unchanged.

## Draft review comment

> Opening the WAL at the backend's consistent index changes three restart cases:
>
> 1. A follower that persisted a leader's snapshot to the WAL and crashed before applying its
>    `.snap.db` (the `applyBeforeOpenSnapshot` failpoint of `TestRecoverSnapshotBackend`) now
>    restarts with the old db, and raft panics with `state.commit N is out of range [ci, ci]`.
>    `RecoverSnapshotBackend` is no longer called, and the unit test for it is commented out.
> 2. If the backend's consistent index is ahead of the last fsynced `HardState.Commit` (a
>    commit-only `HardState` is written without fsync; the force-new-cluster comment in this
>    function describes the same case), a plain restart panics: the raft log now starts at the
>    consistent index, above the commit index. The `max(Commit, consistentIndex)` adjustment is
>    only applied with `--force-new-cluster`.
> 3. With no conf state in the backend (only persisted since v3.5, and only on a membership
>    change), `MemoryStorage()` applies no snapshot and `Append` panics with `missing log entry`;
>    on current main (where the conf state is rebuilt from the v3 store after `Finalize`),
>    `--force-new-cluster` then computes the members to remove from that nil conf state and the
>    entries after the consistent index, and removes none of the other members.
>
> Unit tests reproducing all three (they pass before this PR): <link>. Would it work to keep
> recovering the snapshot db when the WAL's latest snapshot is past the consistent index, raise
> `HardState.Commit` to the consistent index on every restart, and fall back to the WAL snapshot's
> conf state when the backend has none?

## Reviewer

A fresh reviewer subagent was given the PR, the conflict resolutions, the specs, the three new
axioms and findings 1-3, and asked to check the axioms (notably `openWALFromPosition`'s
`EntsAfter` against `WAL.ReadAll`), the resolutions, the reachability of the findings, and other
failing inputs. Its final report did not arrive before this report was written; the one result it
left, the `--force-new-cluster` test (`fork/force_new_cluster_confstate_test.go`), was run here and
confirms the force-new-cluster part of finding 3. Open points, not independently checked:

- `openWALFromPosition`'s `EntsAfter`: argued from `ReadAll`'s code (`offset > len(ents)` is an
  error, `ents = append(ents[:offset], e)`), so the returned entries are at `pos.Index+1, +2, ...`;
  the `2^61` bound is a client assumption (raft's storage bound). Its hard state is claimed
  `nil`-or-read-only although `ReadAll` returns a fresh, owned one and the force branch writes
  `st.Commit`: sound for the non-force spec, too weak for a force-path proof.
- Other failure modes of opening at an arbitrary position, unexamined: a WAL snapshot record at
  exactly `pos.Index` with a different term (`ErrSnapshotMismatch` → `Fatal`), a backend
  consistent index beyond the WAL's last entry (raft would start with an empty log above the
  commit index: `RestartOk`'s upper bound), `selectWALFiles` at an index inside a segment.
- `tools/etcd-dump-logs` still tests for `ErrSnapshotNotFound`, which `ReadAll` no longer returns
  (dead code, harmless).
