# etcd-io/etcd#21612: verification report

- **PR**: etcd-io/etcd#21612, "Add --keys-only option for mvcc range" (nwnt), open, one commit,
  head `efad77f50780ac31035787303817260b4a713f6b`, base `main` at `9186f6a2f`. Part of
  etcd-io/etcd#20386 ("Optimize Range WithKeysOnly to avoid loading values in memory"). The
  description: "We need the option so that the mvcc can perform --keys-only operation on the
  backend side."
- **The whole diff**: one line, a field `Key bool` added to `mvcc.RangeOptions`
  (`server/storage/mvcc/kv.go`), after `Count bool`. No function changes; nothing reads or sets the field.
- **Verified at**: the Goose fork commit `b54ae1748` (`mit-pdos/etcd-grove` branch
  `pr-etcd-21612-goose-lean`), the PR applied to the fork's `goose-lean` `09669450f`, the etcd pin.
- **Proofs**: branch `pr-verify/etcd-21612` of this repository (worktree `/shared/etcd-grove-pr/etcd-21612`):
  only the re-translation (`Code/` and `GeneratedProof/` of `server/v3/storage/mvcc`); no spec or proof changed.

## Verdict

The change is harmless and has no effect: the new field is dead. Every existing mvcc and txn
proof, and the server, apply, v3rpc and read proofs that build on them, check unchanged against
the PR's code. They rest on exactly the same axioms as on `lean`. The specs of mvcc's `Range`
quantify over any `RangeOptions` value. So the proved range behavior holds for either value of
`Key`, which shows the field has no effect.

The PR is **superseded**, though. Upstream renamed `Count` to `CountOnly` (6b049c3ec). Then
etcd-io/etcd#21791, by the same author and for the same issue, merged on 2026-05-27 (7624a8a2e).
It added `RangeOptions.FastKeysOnly`, the option this PR was a placeholder for, wired through
`txn.executeRange` and `storeTxnCommon.rangeKeys`. This repository already verifies that path
(see etcd-io/etcd#22550's report for its latest change). #21612 no longer applies to `main`. Its
`Key` field would sit unused next to `FastKeysOnly`, with a name that does not say what it means.
The right outcome for the PR is to close it as done by #21791.

## Applying the PR

`git apply -3` conflicted on the struct's context: the base has `Count`, the fork (= upstream at
09669450f) has `CountOnly`, `FastKeysOnly`, `WithTotalCount`. Resolution: the fork's struct with `Key bool`
inserted after `CountOnly`, the position the PR gives it after `Count`. This is the only difference
from the PR, and it does not change behavior. `go build ./...`, `go vet ./storage/mvcc/` and
`go test ./storage/mvcc/ ./etcdserver/txn/` pass in `server/`. No other module has an unkeyed
`mvcc.RangeOptions{...}` literal that the new field would break.

it with `DeepEqual`, but `Key` is false on both sides. No open points.
