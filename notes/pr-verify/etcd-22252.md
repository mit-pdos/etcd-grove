# Verification of etcd-io/etcd#22252

**PR**: [etcd-io/etcd#22252](https://github.com/etcd-io/etcd/pull/22252), "pkg/adt: fix int64
overflow in Int64Comparable.Compare", head `cd4a82b516cf129c6bd16a28df09e09e3627a83e`.
- **Verified at**: fork commit `853cc10e8` (`mit-pdos/etcd-grove` branch
  `pr-etcd-22252-goose-lean`), which is the PR's non-test diff onto `goose-lean` `09669450f`.
- **Applying it**: there were no conflicts, so the verified code is the PR's code.
- **Go checks**: `go build ./...` and `go test ./adt`, with the PR's tests, pass in the fork
  worktree.

It is the same `Compare` fix as etcd-io/etcd#22358 (verified on branch `pr-verify/etcd-22358`,
report `notes/pr-verify/etcd-22358.md` there). This report covers only what differs.

## Verdict

The PR is correct. `Int64Comparable.Compare` now returns the signed three-way order for every
pair of int64s.
- **Proof**: the code is the same as etcd#22358's `Compare`; only a code comment differs, and the
  Goose translations are byte-identical. #22358's spec and proof go through unchanged: no
  `sorry`, no new axiom.
- **`NewInt64Point`**: unlike #22358, this PR leaves it unchanged, so `NewInt64Point(MaxInt64)`
  is still the wrapped `[MaxInt64, MinInt64)`, whose `Begin > End`. With the fixed `Compare`, that
  interval overlaps nothing, as a query or as a stored interval. That is proved over the model of
  `Interval.Compare`, and a randomized probe of the tree finds no difference from #22358's results.

So #22252 fixes the bug that matters, and #22358's extra change is cosmetic as far as the tree's
answers go.

Not covered, as for #22358:
- the interval tree's own proof is over string-affine intervals, so `Stab` and `Intersects` on
  int64 trees are covered only by the pure model and the probes;
- no production code in etcd uses int64 intervals.

**Spec**: `v.Compare(Int64Comparable(w))` returns `int64Cmp v w`, which is -1, 0 or 1 by the
signed order (`int64Cmp_spec`, `Proof/go_etcd_io/etcd/pkg/v3/adt/Int64Ivl.lean`). The spec has
no premise. The old code returned the sign of the wrapping difference `v - w`.

**New on this branch**: two lemmas in `Int64Ivl.lean`, both over `int64IvlCmp`, the model of
`Interval.Compare`'s Go body.
- `int64IvlCmp_oldMaxPoint`: the unfixed point `[MaxInt64, MaxInt64+1)` (that is,
  `[MaxInt64, MinInt64)`) as a query is right of every interval.
- `int64IvlCmp_oldMaxPoint_stored`: as a stored interval, it overlaps no query, and neither does
  #22358's `[MaxInt64, MaxInt64)`.

`NewInt64Point` is not specified here, since the PR does not change it.

## Findings

1. **The bug the PR fixes is confirmed.** It is `issues/etcd-adt-int64-compare-overflow.md`
   (upstream: known, #22357), copied from #22358's branch with this PR's part added.
   - On the base, the PR's `TestInt64ComparableCompare` fails 5 of its 10 cases, and
     `TestIntervalCompareInt64Overflow` fails too (`notes/pr-verify/etcd-22252/pr-tests-base.log`).
     The case `-1` vs `MaxInt64`, which the PR marks "(overflows)", in fact passes on the base:
     `-1 - MaxInt64` is exactly `MinInt64`, which does not wrap.
   - On the head, the PR's tests pass, and so do #22358's probes
     (`notes/pr-verify/etcd-22252/int64_extremes_probe_test.go`, `probe-head.log`).
2. **No bug in the PR.**
3. **Reviewer: the unfixed `NewInt64Point(MaxInt64)` does no harm in the tree.**
   - The probe is `notes/pr-verify/etcd-22252/int64_maxpoint_probe_test.go`, with its output in
     `probe-output.txt`. It runs 3000 random trees mixing the wrapped point with intervals at both
     ends of int64.
   - After each operation it checks the tree's order, `max` fields and red-black properties, and
     compares Insert, Delete, Find, Stab, Visit, Intersects, Contains and Union against brute force.
   - It found 0 failures with this PR's constructor and 0 with #22358's.
   - Why it is safe: `updateMax` takes a maximum over Ends, and an End of `MinInt64` never raises
     a maximum.
   - The only differences between the PRs:
     - here the stored point's End reads back as `MinInt64`;
     - `Find(NewInt64Interval(MaxInt64, MaxInt64))` does not find this PR's point, because it is
       a different key.
4. **Comparing with #22358.**
   - Both have the same `Compare`.
   - #22358 also keeps `Begin <= End` for the point at `MaxInt64`. That is a cleaner invariant, but
     no tree answer changes.
   - #22252's tests cover more `Compare` cases: both orders, `±1` against both extremes, and an
     `Interval.Compare` test.
   - #22358's points about its code comment and the `Find`/`Stab` asymmetry at `MaxInt64` do not
     apply to #22252.
   - The affine-point issue that #22358's verification found (`etcd-adt-affine-point-empty-key.md`
     on that branch) is untouched by either PR.
