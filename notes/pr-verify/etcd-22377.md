# etcd-io/etcd#22377: a watch from the compaction revision misses the delete

etcd-io/etcd#22377 (open) fixes `keyIndex.doCompact` for a revision that deletes a key and puts it
again (`issues/etcd-compaction-delete-then-put.md`). With it, a bug of its own (2026-11-01, found by
this repository's review of watches across a compaction, `notes/watch-compaction-plan.md`): of
revision `c`'s two changes of the key, the fixed `doCompact` keeps the put and not the tombstone, so
`scheduleCompaction` deletes the tombstone's backend key, and a watch from `c` (where a client
re-watches after `ErrCompacted`) gets the `PUT` alone, where an uncompacted store sends `DELETE` then
`PUT`.

Reproduced at the fork pin through mvcc's API (`TestWatchFromCompactRevLosesEvent`, package `mvcc`:
`newWatchableStore`, a write txn deleting then putting `foo`, `Compact` at its revision, a watch from
it, which gets 1 event instead of 2). Reachable through gRPC only while #22395 is not merged (it
rejects the delete-then-put txn). A fix keeps both of `c`'s changes in the backend when `c`
re-created the key (the index's generations are unaffected), or treats a watch at exactly `c` as
compacted.

Not yet raised on #22377: worth a review comment there.
