## Verdict

The PR is correct as far as it is verified. It fixes the bug it targets and does not change #18274's behaviour.

The proof rests on a model of compaction. That model now follows the PR's loop: it walks past a generation
whose tombstone is below the compaction revision `c`, or at `c` with the next generation created at `c`.
`keyIndex.doCompact` and the new `generation.isRecreatedAt` are proved against this model. Over it, the
model's coverage theorem holds **with no premise**: for every key, compaction at `c` keeps the revision that
any read at or above `c` returns (`kiGet_avail`). Before the PR this theorem was false unless revision `c` did
not delete a key and put it again (`NoDelPutAt`), which is how the bug was found here.

So the premise is gone from `store.Compact`'s spec, from its internal callees' specs and from the store's
invariants. The new spec implies the old one, and this is proved (`store.Compact.spec_implies_old`). Every
reader of a compacted store (`storeTxnCommon.rangeKeys` and the readers above it) re-proves without it. A
tombstone that is the key's last word at `c` is still kept (`kiAvail_tomb`, #18274's case).

Not covered by the proof:
- **Hashes**: the hasher is axiomatized. The PR's claim that `keep()` and `HashByRev` match pre-#18274 is
  checked only by tests: the PR's sweep and the reviewer's exhaustive sweep, 0 differences in 6786 cases.
- **Rebuilding the index from the backend** (`restoreIntoIndex` and its helpers, not translated) is also
  checked only by tests: the probe below and the reviewer's sweep both re-open the store after compaction.
- **Mixed-version clusters**: once the affected shape is compacted, a member on the new code and one on
  the old code have different backends, and every later hash differs. This is new alarm behaviour during
  an upgrade (finding 1).

No types, struct fields or package-level variables changed, and no locking changed.

**Old and new spec of `doCompact`** (`Spec/go_etcd_io/etcd/server/v3/storage/mvcc/keyIndex__doCompact.lean`,
text unchanged). The spec returns `compactGenIdx atRev ki.gens`, the generation index, and adds
`kiAvail atRev ki` to `available`.
- **Old** (`lean`'s `compactGenIdx`): the first generation that is the last one or whose tombstone has
  main ≥ `atRev`.
- **New** (`Proof/.../mvcc/Compact.lean`, `SkipGen`, `compactGenIdx`): the first generation that is the last
  one, or that it does not walk past. It walks past a generation when the tombstone's main < `atRev`, or
  when the main = `atRev` and the next generation has a first revision with main `atRev` (`RecreatedAt`).

The two differ exactly on the bug's shape. The old spec does not hold of the new code, and the new spec does
not hold of the old code: on that shape the old code keeps the superseded tombstone, the new code keeps the
put. (The issue's reproduction is that case.)

## The caller graph (step 6)

The model change reaches everything defined from `compactGenIdx`: `kiCompact`, `kiAvail`, `kiKeep`, the
pure theorems of `Compact.lean`, and `CompactIdx.lean`. Every node is rebuilt against the new model:

- `keyIndex.compact`, `keyIndex.keep`, `treeIndex.Compact`, `treeIndex.Keep`: spec text unchanged (in terms of
  `kiCompact`/`kiKeep`), proofs unchanged, rebuilt. Their behaviour changes with the model, and only on the
  bug's shape.
- The pure model's theorems on compaction, all re-proved for the new `compactGenIdx`:
  - compaction answers as before at or above `c` (`kiGet_kiCompact`);
  - compactions compose (`kiCompact_kiCompact`, `_le`);
  - compaction commutes with the writer's next event (`kiCompactO_step`). Its lemma `compactGenIdx_put` now
    needs that event to be above `c`, which every caller already had.
  - the index's representation under compaction (`IdxCRep.*`).
- **`kiGet_avail`, `named_not_del`, `rangeAnswers_not_del`**: re-proved **without `NoDelPutAt`**. This is
  the substance of the fix.
- `store.Compact`, `store.compactLockfree`, `store.updateCompactRev`: `NoDelPutAt` dropped from the
  precondition. The invariants `crevSafe`, `delKey` and `compactJobPre` no longer carry it
  (`InvStore.lean`, `InvCompact.lean`). `store.scheduleCompaction` and `storeTxnCommon.rangeKeys` are re-proved.
  - `store.Compact` is the exported API. Its spec change is compatible: the precondition is weaker and the
    postcondition is the same, proved in `store.Compact.spec_implies_old`
    (`Proof/.../mvcc/store__Compact.lean`, with the old statement as `spec_old`).
  - No verified code calls `store.Compact` (the server's apply of a compaction is not verified), so the
    path stops there.
- Everything above mvcc (txn, apply, v3rpc, the server, the clients) rebuilds unchanged in the full build.

Exported behaviour changes as the PR says: a compaction at a revision that deleted and re-put a key keeps
the key's value. The CHANGELOG entry says so too.

## Findings (step 8)

**Bugs in the PR: none found.**
- The reviewer's exhaustive single-key sweep, `notes/pr-verify/etcd-22377/key_index_review_test.go`, covers
  1131 histories compacted at every revision. It passes on the PR and fails 3234 of 6786 cases on the base.
  Its cases include delete/put/delete in one revision, several re-creations in one revision, an index rebuilt
  from the remaining rows, and composition.
- The store-level random probe, `notes/pr-verify/etcd-22377/kvstore_compact_recreate_probe_test.go`, passes
  on the PR (300 histories) and fails 8 of 300 on the base with the `range failed to find revision pair` fatal.
- `notes/pr-verify/etcd-22377/README.md` lists every file, the revision it runs against and its command.

**The bug the PR fixes**: `issues/etcd-compaction-delete-then-put.md`. The proof confirms the fix: the
premise that recorded the bug is no longer needed anywhere. That issue file now notes this (on this branch).

**Reviewer's open points:**
1. **Medium, mixed-version clusters** (`kvstore_hash_review_test.go`, logs `review-tests.{pr,base}.log`).
   - After the bug's shape is compacted, `HashByRev` and the next compaction's hash differ between the base
     (1346811925) and the PR (292945832). The compaction hash at the affected revision itself is the same on
     both (493118507).
   - So during a rolling upgrade, the corruption checks flag the members still on the old code. They really
     did lose the row; before the fix every member lost it identically.
   - Members on pre-#18274 code (≤ 3.5.15) agree with the PR.
   - A member that already compacted with the buggy code is not repaired: its backend keeps only the
     tombstone.
   - The PR's text says hashes are unchanged; that holds only for the compaction at the affected revision.
     The PR should say this, and so should its backports.
2. Low: hash consistency is outside the proof (the hasher is axiomatized), as above.
3. Low, resolved: #18274's behaviour was only implicit in the exact model. It is now stated and proved
   (`kiAvail_tomb`).
