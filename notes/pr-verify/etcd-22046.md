## Verdict

The PR fixes #18055. The proofs show the bookkeeping is right:
- `SaveDBFrom` adds the index to the pending set before it reports success.
- `ReleaseSnapDBs` removes a file only after a check, under the lock, that the file's index is
  below the snapshot's and not pending.
- `OpenSnapshotBackend` drops the mark only after the rename that consumes the file.

The raft loop releases snapshot B only after raft has handed the earlier snapshot A to the apply
loop, and A's mark was set before raft saw A. So the apply loop's lookup of A's file can no
longer fail, a scenario reproduced at the base and fixed at the head
(`TestReleaseSnapDBsDeletesDBPendingApply`).

The PR has one real cost, a regression: a received snapshot database that is never applied is
now never deleted until restart. This happens when raft drops the snapshot message (stale term,
index already committed) or when the same snapshot is received again after it was applied, and
each such file is the size of the database. The PR's comment on `ReleaseDBSnapshot` says the
second case is cleaned up; it is not.

Not covered:
- The callers' protocol (raft loop, apply loop, snapshot receiver) is argued from the code, not
  proved.
- There is no file-system model.

### The specs

The files are in `Spec/go_etcd_io/etcd/server/v3/etcdserver/api/snap/` and
`Spec/go_etcd_io/etcd/server/v3/storage/OpenSnapshotBackend.lean`. The vocabulary is in
`Proof/go_etcd_io/etcd/server/v3/etcdserver/api/snap/Defs.lean`.

- **The invariant**:
  - The mutex `pendingDBsMu` guards the map's contents `M`, with half of a ghost variable at `M`.
  - The other half, `snapPending γ M`, is the abstract pending set. The receiver, the raft loop and
    the apply loop share it through an invariant of their own.
  - `isSnapshotter s γ dir` (persistent) holds the read-only fields (`lg`, `dir`, `fsyncDir`,
    `pendingDBs`) and the mutex.
- **The mark operations**: `markPendingDB`, `isPendingDB` and `ReleaseDBSnapshot` are logically
  atomic. Each linearization point is the map operation inside the critical section.
- **`ReleaseSnapDBs(snap)`** takes a persistent hook from its caller, `snapRemoveHook γ dir idx`:
  - For each name with parsed index `i` (`snapDBIndexOf name = some i`, the abstract
    `ParseUint(TrimSuffix(Base(name), ".snap.db"), 16, 64)`) and `i < idx`, the hook is an atomic
    look at `M`. If `i ∉ M` at that instant, it yields `fs.removable (dir/name)`.
  - `os.Remove(p)`'s trust-boundary spec requires `fs.removable p`. So the spec says: a file is
    removed only if, at the linearization point of its pending check, its index was below the
    snapshot's and not pending.
  - The removal itself happens later, outside the lock. That window (finding 3) is for the caller
    to justify.
- **`SaveDBFrom(r, id)`** is atomic. It returns `nil` (`ok`) only after `markPendingDB(id)`, which
  comes after the rename and the directory sync. Every error path leaves `M` unchanged.
- **`OpenSnapshotBackend`** is atomic. It returns success only after renaming
  `<idx>.snap.db` onto `db` (`fs.renamePending`), with `M ↦ M \ {idx}` at `ReleaseDBSnapshot`.
  On either error (no file, rename failed) `M` is unchanged.

## Findings

All of these are against the PR head. Each test is in `notes/pr-verify/etcd-22046/` (see its
`README.md`).

1. **A saved snapshot db that is never applied is never released (regression, low-medium).**
   - **What**: `SaveDBFrom` marks every saved file, and only `OpenSnapshotBackend` of that index
     drops the mark. If raft never applies the snapshot, the mark stays, and `ReleaseSnapDBs`
     keeps the file until restart. Before the PR, the next release removed it.
   - **When raft never applies it**:
     - the `MsgSnap` is from a deposed leader (lower term), for example after a leader change
       during a long transfer;
     - its index is at or below the commit index;
     - `Process` fails;
     - a second `MsgSnap` replaces it in raft's unstable log before `Ready`.
   - **Cost**: each such file is a full database copy.
   - **Test**: `TestReleaseSnapDBsUnappliedDBIsKept` fails at the head (`pr-head.log`). Its
     base-compatible copy `snapshotter_unapplied_base_test.go` passes at the base (`base.log`).
2. **A db re-received after its apply is re-marked and never released (low; the comment is
   wrong).**
   - **What**: `ReleaseDBSnapshot`'s comment says dropping the mark lets `ReleaseSnapDBs` clean
     up a file "when the same snapshot db is received again". A copy that arrives after the apply
     has consumed the first is re-marked by `SaveDBFrom`, and raft ignores it, so nothing drops
     that mark.
   - **Test**: `TestReleaseSnapDBsReceivedAgainAfterApplyIsKept` fails at the head.
3. **The check and the removal are not atomic (benign in the server).**
   - **What**: `SaveDBFrom` renames the file into place, syncs the directory, and only then marks
     it. `ReleaseSnapDBs` checks the mark, then removes the file without the lock. A release that
     lists the directory in that window deletes a file that `SaveDBFrom` then reports as saved
     and marks.
   - **Test**: `TestSaveDBFromRacesReleaseSnapDBs` hits this on the first trial on disk
     (`pr-head.log`).
   - **Why it is benign**:
     - The window needs a release at an index B above the saved index S while S is being
       received.
     - A release at B runs only after raft's commit index reached B: in the raft loop after
       `ApplySnapshot(B)`, or in `snapshot()` at `appliedi`, which is at most the commit index.
     - So raft's `restore` rejects S (`index <= committed`), and nothing will look for the file.
   - **Proof view**: this is the step the hook spec leaves to the caller. The mark left behind is
     harmless.
4. **The PR description is inaccurate.** It says "stale files from a previous run are still
   cleaned up at boot". Nothing at boot removes `.snap.db` files; they go at the first `Release`
   after boot. The PR's test also calls `ReleaseDBSnapshot` directly rather than through
   `OpenSnapshotBackend`, and covers neither finding 1 nor 2.

**A fix for 1 and 2** (reviewer's suggestion, endorsed): a mark at or below the applied index is
stale, because that snapshot was either applied or will never be. So `OpenSnapshotBackend(S)` (or
`applySnapshot`) could drop every mark `≤ S`, and `snapshot()` every mark `≤ appliedi`, before
releasing. That keeps #18055 fixed and restores cleanup.

**The bug in the existing code that the PR fixes** (#18055) is recorded in
`issues/etcd-snap-release-pending-db.md`. Its reproduction is
`snapshotter_release_pending_test.go` (`release-pending.log`: fails at the base, passes at the
head). The proof confirms the fix in the sense above.

**Reviewer's points**, resolved on this branch:
- the hook did not tie the checked index to the removed name (now `snapDBIndexOf name = some i`);
- `dbFilePath`'s and `DBFilePath`'s postulates had no precondition, although the methods read
  `s.dir` (they now take `isSnapshotter`).

Open:
- **No file-system model.** The specs give no file-system meaning to "`id ∈ M`" (that the file
  exists).
- **`fs.dirHandle` naming.** `fs.dirHandle` is reused for regular files.
