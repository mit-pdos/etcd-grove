## Verdict

The PR is correct and it fixes the finding `issues/etcd-txn-delete-then-ignore-put.md`.
`checkIntervals` now reads a from-key delete (`RangeEnd = "\x00"`) as `[Key, +∞)`, which is how the
executor reads it (`mkGteRange`). The proof of `checkIntervals` against its spec goes through for
the new code, with no `sorry` and no new axiom. Two results follow from it:
- The check's purpose, "a branch that passes the gRPC checks writes each key at most once and
  deletes none of the keys it puts" (`check_gives_nodup`), no longer needs the premise "no from-key
  delete". Only the separate later-sibling gap remains (`issues/etcd-txn-check-intervals-sibling.md`).
- A new result, `check_gives_ignOk`, derives the apply path's premise that excludes the panic: every
  `IgnoreValue`/`IgnoreLease` put finds its key when it runs.

What the proof does not cover:
- `check_gives_ignOk` still carries the sibling premise, which is believed unneeded but is not
  removed.
- It is a pure lemma. It is not yet composed with the apply thread's `TxnPre`.
- As the finding says, the PR keeps bad entries out of the log, but it does not make an entry that
  is already committed applicable.

The PR changes behaviour that clients can see, and its description does not say so (Findings,
below).

### The spec change

The Lean statement (`Spec/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/checkIntervals.lean`) is
textually unchanged: `checkIntervals` returns what the pure model `ivCheck` computes. The model
changes in `delIvl` (`Proof/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/Defs.lean`):

- **Old**: a delete's interval is a point when `RangeEnd` is empty, otherwise `[Key, RangeEnd)`.
  This includes `"\x00"`, where `[Key, "\x00")` is empty and overlaps no put.
- **New**: a point when `RangeEnd` is empty, `[Key, +∞)` (the affine `""`) when `RangeEnd` is
  `"\x00"`, otherwise `[Key, RangeEnd)`.

So `ivCheck` now rejects more requests: every transaction with a from-key delete and a put at or
after its key, in the same transaction at any depth that the check compares. The new spec does not
imply the old one: `ivCheck`'s answer differs on those requests. The callers were therefore
re-checked (below).

The old spec does not hold of the new code. On
`Then(OpDelete("a", WithFromKey()), OpPut("a", ...))`, the old `ivCheck` gives `some`, while the
new code returns `ErrGRPCDuplicateKey`. That is exactly what the PR changes.

The proof (`Proof/.../v3rpc/checkIntervals.lean`, the first loop's delete case) follows the new
code: `rangeEnd := dreq.RangeEnd`, the test `len(rangeEnd) == 1 && rangeEnd[0] == 0`, and
`rangeEnd = nil`, with `string(nil) = ""`. It covers three cases:
- `RangeEnd = "\x00"`;
- a one-byte `RangeEnd` other than 0;
- a longer `RangeEnd`.

The premise `reqOpsWire` (a delete's `RangeEnd` is `nil` or non-empty, as protobuf decodes it) is
unchanged.

### What the check is for: the results restated

- **`check_gives_nodup`** (`Proof/.../v3rpc/CheckNodup.lean`; `intervalsOkCheckStmt` in `Defs.lean`;
  `checkIntervals_nodup` in `Results.lean`):
  - Premises: a branch passing `checkRequestOp` and `checkIntervals`, with no nested put deleted by a
    later sibling (`siblingSafeL`).
  - Conclusion: run by the server at any state, the branch puts distinct keys and deletes none of
    them.
  - The old statement also needed `ReqOp.noFromKeyDelL` (no from-key delete at any depth). The new
    one drops it, so it is strictly stronger and the existing callers are unaffected.
  - `goodDel` is now just "non-empty key". `hits_of_inRange` and `unionSel_mem` gain the from-key
    case: a nested `[k, +∞)` survives `Union`'s filter `["\x00", +∞)`.
- **`check_gives_ignOk`** (new, `Proof/.../v3rpc/CheckIgn.lean`; restated as
  `checkIntervals_ignOk` in `Results.lean`):
  - Premises: the same checks, run from a sorted read view `s0`, with the gets' own premises
    (`OpsGetsOk`).
  - Conclusion: the run's whole premise `txn.OpsOk true` holds, i.e. `TxnPre`'s run conjunct.
  - In particular every `IgnoreValue`/`IgnoreLease` put finds its key when it runs, unless the key
    was already missing at `s0`, in which case `checkTxn` rejects the transaction.
  - This is the finding's impact (`put` indexing `prevKV.KVs[0]` of an empty list in the apply loop)
    excluded at the API.
  - On the pinned code this result does not hold: the finding's request is a counterexample.

## Findings

The finding the PR fixes, `issues/etcd-txn-delete-then-ignore-put.md`:
- **Expected behaviour**: the transaction is rejected before it is proposed.
- **Proof**: `checkIntervals_ignOk`, with the sibling premise. On the pinned code, the same result
  needed "no from-key delete".
- **Tests**: all of the finding's reproductions pass at the PR head (`eb347e2b4`, scratch upstream
  worktree):
  - the finding's `TestCheckIntervalsFromKeyDelete`: all 8 rows, including the nested and the
    `Key "\x00"` rows;
  - its integration test `TestTxnDeleteFromKeyThenIgnorePut` (`tests/integration/clientv3`): the
    `IgnoreValue` and `IgnoreLease` txns get `ErrDuplicateKey` and the member does not panic;
  - the PR's own `TestCheckIntervalsOpenEndedDeleteRange`;
  - the existing `go test ./etcdserver/api/v3rpc/ ./etcdserver/txn/` and the clientv3 `TestTxn*`.
- **What the fix does not cover** (as the finding says): an entry already committed still panics on
  replay.
- **Related**: the compaction finding `issues/etcd-compaction-delete-then-put.md` was reachable
  through gRPC by the same from-key route (`notes/STATUS.md`, "`NoDelPutAt` is not met by the gRPC
  checks"). With the PR that route is closed too, since `check_gives_nodup` holds without the
  from-key exclusion. The lemma from `NoDupKeysPerRev` to `NoDelPutAt` still does not exist.

Behaviour the PR changes without saying so, which a reviewer should weigh:
- **Rejected in either order**: any put of a key at or after a from-key delete's key in the same
  transaction is now rejected with `ErrGRPCDuplicateKey`. This holds whether the put comes before or
  after the delete, and across nesting levels.
- **Affected pattern**: "wipe and re-seed",
  `Then(OpDelete("", WithPrefix()), OpPut("cfg", v))`. The client sends `Key = RangeEnd = "\x00"`.
  `main` accepts it; the PR rejects it (checked with a probe of `checkIntervals` at both
  revisions).
- **The rejection is consistent**: the same overlap written with an explicit range end was already
  rejected.
- **Why it should be documented**: the old acceptance was what let a from-key delete followed by an
  `IgnoreValue` put crash the cluster, and let a delete and a put of one key in one revision break
  compaction. Still, it is a compatibility change that deserves a CHANGELOG line.
- **Not mentioned in the PR**: the apply-loop panic. The PR also calls the bug "not a security fix",
  which understates it: one request from any client allowed to write the key takes down every
  member, permanently.

A bug in the existing code, found along the way (by the reviewer), not touched by the PR:
- `issues/etcd-grpcproxy-cache-from-key.md`: the gRPC proxy's range cache (`server/proxy/grpcproxy/cache/store.go:97`, `:145`) has the same reading of `"\x00"`. A cached from-key range is not invalidated by a write through the proxy, and a from-key delete does not invalidate the cached ranges after its key, so stale serializable reads follow. It has a Go reproduction, fails at the PR head, and the PR names it as out of scope.

Bugs in this repository's specs and proofs: none.

### The reviewer's open points

- **Sibling premise**: `check_gives_ignOk` takes `siblingSafeL` only because it goes through
  `check_gives_nodup`. The panic needs a delete that runs before the put, and `checkIntervals` checks
  every such order: the unchecked order, an earlier sibling's put with a later sibling's delete, runs
  the put first. The statement without the premise should hold. It is not proved.
- **Not linked to the apply thread**: nothing yet connects `check_gives_ignOk` to `txn.TxnPre`. That
  needs the request's chosen branch as the apply's `t.branch (txnOk …)` and `s0 = stateAfter log`,
  which `mvcc.stateAfter_sorted` gives.
- **The `reqOpsWire` premise** (`RangeEnd` is nil or non-empty) is assumed, not derived. It is
  harmless in practice: the request is marshalled before raft, so the check and the apply see the
  same bytes.

## Draft review comment (for the user to edit and post)

> I checked this change against a model of how the txn executor reads range ends. With it,
> `checkIntervals` treats `RangeEnd == "\x00"` as `[Key, +inf)`, the same as `mkGteRange`, so a txn
> whose put falls at or after a from-key delete's key is rejected, at any nesting depth the check
> compares. Without it, a put inside such a delete is accepted. I could not find another input
> where the check and the executor disagree on a from-key delete.
>
> The bug this fixes is worse than an order-dependent result, though. A transaction like
> `Then(OpDelete("a", WithFromKey()), OpPut("a", "", WithIgnoreValue()))` (or `WithIgnoreLease()`)
> passes `checkIntervals`. It also passes `checkTxn`, because `a` exists at the read view. Then it
> panics in `put` (`prevKV.KVs[0]` of an empty list) on every member while applying the committed
> entry, and again on every restart, since the entry is in the WAL past the consistent index.
> `etcdctl put a v; printf '\ndel a --from-key\nput a --ignore-value\n\n\n' | etcdctl txn` takes
> down a 3-member cluster on `main`. It may be worth saying so in the description and the
> CHANGELOG. With this PR the txn gets `ErrDuplicateKey` and the cluster stays up. A member that
> already has such an entry in its WAL still panics on replay.
>
> Two smaller points:
> - This rejects some transactions `main` accepts, for example `Then(OpDelete("", WithPrefix()),
>   OpPut("cfg", v))`, a "clear and re-seed" pattern. I think that is correct, since the same
>   overlap with an explicit range end is already rejected, but it is a visible behaviour change
>   and probably deserves a CHANGELOG entry.
> - The grpcproxy cache you mention (`server/proxy/grpcproxy/cache/store.go:97` and `:145`) does
>   have the same problem. A cached `Range{Key: "a", RangeEnd: "\x00"}` survives
>   `Invalidate("b", nil)`, and `Invalidate("a", "\x00")` leaves a cached `["b", "z")`, so a client
>   of the proxy reads stale serializable results after its own writes. That could be a follow-up.
