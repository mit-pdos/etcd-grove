# etcd-io/etcd#22493: verification report

- **PR**: etcd-io/etcd#22493, "perf(auth): use process-local root identity for internal requests",
  https://github.com/etcd-io/etcd/pull/22493. Head `fb1d045e88174ff8d6ccfa3b219d9daad2293022`
  (one change commit and three merges of `main`; merge base `88235ecd0`). Open, not yet
  `ok-to-test`. It says it fixes etcd-io/etcd#14616.
- **What it does**: adds `auth.WithRootInternal(ctx, store)`. For the built-in `*authStore` with
  the built-in JWT provider (`*tokenJWT`) and auth enabled, this returns
  `context.WithValue(ctx, internalRootContextKey{}, internalRootContextValue{as, as.Revision()})`
  instead of signing a root JWT. Otherwise it returns `store.WithRoot(ctx)`. On the reading side,
  `authStore.AuthInfoFromCtx` checks that value first, after `IsAuthEnabled` and before the
  request's token, and returns root at the captured revision when the value is of this store. The
  server's three in-process root requests use it: `revokeExpiredLeases`, the `/health` range
  (`checkAPI`) and the `/readyz` and `/livez` range check (`readCheck`).

## Verdict

**The change does what it says, and I found no bug in it.**
- The proofs establish the two halves of the PR:
  - `WithRootInternal`, over the real store, either returns a context that carries a root value
    of that very store (only when the provider is the built-in JWT one), or returns `WithRoot`'s
    context, which adds no such value.
  - `AuthInfoFromCtx`, for a context that carries a root value of its own store, returns root at
    the captured revision (or nothing when auth is disabled), whatever token the request carries.
    For every other context it behaves as before: the old spec is derived from the new one.
- It also fixes a real bug in the current code. With a verify-only JWT key, expired leases are
  never revoked (etcd-io/etcd#14616, closed as stale but not fixed). I reproduced this end to end
  on upstream `main`, and the same test passes at the PR head.
- **Not covered**:
  - The proofs do not connect the two halves through the callers: that the lease revocation and
    the health checks really run as root. Two things are missing:
    - `revokeExpiredLeases` is still a names-only trust boundary, and `etcdhttp` is not
      translated.
    - The specs of the wrappers in between (`context.WithTimeout`, the tracer's `Start`,
      `traceutil.EnsureTrace`) do not yet say that the root value survives them.
  - Which branch a JWT store takes, and which revision it captures, are not constrained: the
    `IsAuthEnabled` and `Revision` specs return any value. This is the same as for `WithRoot`'s
    token.
- **One behaviour difference** is worth a line in the PR's doc comment. With `WithRoot`, a user
  token added later to the context wins (the request runs as that user). With the fast path, root
  wins (finding 2). Nothing in etcd adds a token to these contexts.

## The specs

**`authStore.AuthInfoFromCtx`** (`Spec/go_etcd_io/etcd/server/v3/auth/authStore__AuthInfoFromCtx.lean`;
the proof and `spec_old` and `spec_implies_old` are in
`Proof/go_etcd_io/etcd/server/v3/auth/authStore__AuthInfoFromCtx.lean`).
- **Old**: for any context, it returns an auth info (nil, or one with read-only fields) and
  `nil` or `ErrInvalidAuthToken`.
- **New**: for a context that is not nil and carries the root value `o` (`ctxRootIs ctx o`),
  it returns the same, and also `rootInfoIf st o a err`: if `o` is a value of this store `st`,
  then there is no error and the info is nil (auth disabled) or `root` at the value's revision.
- The context must now be non-nil. The old spec allowed a nil context only because
  `metadata.FromIncomingContext`'s trust-boundary spec hid that `ctx.Value` panics on one. The
  new code calls `ctx.Value` itself. The only caller, `isReqAuth_of_authInv`, already had a
  non-nil context.

**`WithRootInternal`** (`Spec/go_etcd_io/etcd/server/v3/auth/WithRootInternal.lean`; proof
`Proof/go_etcd_io/etcd/server/v3/auth/WithRootInternal.lean`).
- The spec is for the real store, which is what the server passes. It returns a context `c'`,
  not nil, that is derived from `ctx` (`ctxDerived`: a context with the same description). And
  either:
  - the provider is the built-in JWT one (`jwtProvider st`) and `c'` carries
    `internalRootContextValue{st, rev}` for the revision `rev` that `Revision()` returned; or
  - `c'` is `WithRoot`'s result, which carries `ctx`'s root value unchanged (`ctxRootKept`).
- So a store with another provider (simple tokens) never gets the fast path; this follows from
  `jwtProvider` and the read-only provider field.
- I did not check whether this spec holds of the old code: the function is new, and there is no
  old code to check it against.

**Shared definitions** (`Proof/go_etcd_io/etcd/server/v3/auth/RootCtx.lean`): `rootValIs` and
`ctxRootIs`, which say what `ctx.Value(internalRootContextKey{})` returns, in the shape of
`traceutil.ctxTraceIs`, plus `rootInfoIf`, `ctxDerived`, `ctxRootKept` and `jwtProvider`.

**Invariant change**: `auth.tokenProviderOk` (`InvAuth.lean`) gains `⌜ti.v.isPanic = false⌝`:
the provider's dynamic value is a Go value, not a panic value.
- It is needed because `as.tokenProvider.(*tokenJWT)` binds that value, and a GooseLang `let` of
  a value of unknown shape needs the fact to step. This is a Perennial limitation, recorded in
  `notes/STATUS.md`.
- `authInv` is a premise everywhere (no proof builds it), so this adds an assumption that is
  trivially true of Go values. Nothing that was proved has to be redone.

## Trust base (step 7)

`etc/tcb-report.py --collection etc/tcb-collections/pr-etcd-22493.txt` (roots `WithRootInternal`,
`authStore__AuthInfoFromCtx`, `EtcdServer__AuthInfoFromCtx`) reports 3 roots and no `sorry`.

They rest on these axioms:
- `auth.authStore.WithRoot.wp_proof`: **new**;
- `context.WithValueInternalRoot.wp_proof`: **new**;
- `auth.redactToken`, `metadata.FromIncomingContext`, `zap.Logger.Warn`, `zap.String`: already
  there for `AuthInfoFromCtx` on `lean`.

`EtcdServer.wp_AuthInfoFromCtx` rests on none: it takes the store's contract as a premise.
`etc/tcb-baseline.txt` and the `server` collection gain the three new axioms (they are linked
results of the server's `Link`).

The new postulates, and why they are believed:
- **`auth.authStore.WithRoot`**
  (`Spec/go_etcd_io/etcd/server/v3/auth/authStore__WithRoot.lean`): it returns a context derived
  from `ctx` that carries `ctx`'s root value, and keeps the `enabledMu` reader slot.
  - The body (`store.go:1159-1196`) returns either `ctx` itself or
    `metadata.NewIncomingContext(ctx, md)`. That is a `WithValue` at grpc's `mdIncomingKey{}`, a
    different type from `internalRootContextKey{}`.
  - It is names-only because it signs a token with `assign`, which is not translated.
- **`context.WithValueInternalRoot`** (`Spec/context/WithValueInternalRoot.lean`):
  `WithValue(parent, internalRootContextKey{}, x)` returns a non-nil `valueCtx` derived from the
  parent, whose `Value` at that key returns `x`.
  - Go's `WithValue` panics only on a nil parent or key, or an incomparable key; the key here is
    an empty struct.
  - The value is immutable, so it reads the same from any goroutine.
  - Perennial translates `context` without `WithValue`'s body, as for the existing
    `context.WithValue.spec`.
- **`context.ValueInternalRoot`** (`Spec/context/ValueInternalRoot.lean`): every context's
  `Value` at the key returns, with no effect, a fixed value. This is Go's documented contract of
  `Context.Value`.
  - As stated it is broader than true. It covers every interface value, including a typed-nil
    context or a custom `Context` with a stateful `Value`.
  - It holds of the contexts the server sees: chains of the standard library's contexts, grpc's
    and otel's `WithValue`s. etcd defines no `Value` of its own.
  - Base `AuthInfoFromCtx` already called `ctx.Value` (inside grpc, at the trust boundary) on any
    context.
  - It is used only by `spec_implies_old` and `isReqAuth_of_authInv`. No linked result's
    statement needs it, so it shows up in the baseline but not in the collection's roots.

## Findings (step 8)

1. **A bug in the existing code, fixed by the PR**:
   `issues/etcd-auth-verify-only-jwt-internal-root.md`.
   - With `--auth-token=jwt,pub-key=...` and no `priv-key`, `WithRoot` cannot sign
     (`ErrVerifyOnly`), so the leader's lease revocations run with no user and fail with
     `ErrUserEmpty`. Expired leases and their keys stay forever.
   - The same path makes the health range check run unauthenticated (read from the code; not
     reproduced separately).
   - Reproduction: `notes/pr-verify/etcd-22493/tests/integration/v3_auth_verify_only_lease_test.go`
     fails on upstream `f061acd09` (`integ-upstream-base.log`) and passes at the PR head
     (`integ-upstream-pr.log`).
   - The proof confirms the mechanism of the fix: the fast path does not depend on the provider
     being able to sign. It does not prove the end-to-end lease revocation (see Verdict).
2. **Behaviour difference (reviewer)**: a token added later no longer overrides root.
   - With `WithRoot`, `metadata.NewIncomingContext(rootCtx, userToken)` runs as the user, because
     the later incoming metadata replaces the root token. With `WithRootInternal`'s JWT fast
     path, `AuthInfoFromCtx` checks the root value first, so the request runs as root.
   - No caller in etcd derives such a context (the only other `NewIncomingContext`, in
     `peer.go:146`, is on an HTTP request context).
   - It does widen what the new function hands out compared with `WithRoot`, and the doc
     comment could say so.
   - Test: `notes/pr-verify/etcd-22493/reviewer/server/auth/withrootinternal_precedence_test.go`,
     which passes at the PR head.
3. **Checked, no problem (reviewer and me)**:
   - **Revision semantics**: both paths capture `as.Revision()` at creation. Both are refused
     with `ErrAuthOldRevision` once auth changes, so the PR's
     `TestWithRootInternalPreservesTokenRevisionSemantics` holds. The fast path stores a
     `uint64`, where the JWT's claim is a `float64` that is exact only up to 2^53.
   - **Auth disabled or enabled concurrently**: `AuthInfoFromCtx` checks `IsAuthEnabled` first,
     and `isOpPermitted` checks again.
   - **Two stores in one process**: `value.store == as` keeps them apart.
   - **Wrapped `AuthStore` implementations** take the fallback.
   - **Context values do not cross grpc** (the PR's integration test). The in-process v3client
     adapter would pass the value through, as it passes the old root token's incoming metadata.
     Nothing hands it a `WithRootInternal` context.
   - **TTL**: the JWT root token's TTL is gone, but the contexts are request-scoped and used at
     once.
4. **This repository's specs** (`notes/STATUS.md`): `metadata.FromIncomingContext`'s
   trust-boundary spec is stated for a nil context too, on which grpc panics. That was harmless
   because every caller passes a non-nil context. The new `AuthInfoFromCtx` spec requires one.

The PR's own tests pass: `notes/pr-verify/etcd-22493/pr-own-tests.log`. The files are listed in
`notes/pr-verify/etcd-22493/README.md`.

## Draft review comment (for the user to edit and post)

> I went through this change in detail, including the interaction with the existing token paths.
> The fast path looks correct to me:
> - `WithRootInternal` only takes it for the built-in JWT provider with auth enabled.
> - `AuthInfoFromCtx` only honours a value of the same store.
> - The captured revision is checked exactly as a JWT's is, so any auth change invalidates it
>   (`ErrAuthOldRevision`).
> - Simple tokens and wrapped stores keep `WithRoot`.
>
> It also fixes #14616 for real. With `--auth-token=jwt,pub-key=...,sign-method=RS256` and no
> private key, expired leases are never revoked on `main`: the leader logs "token signing
> attempted with verify-only key" and then "failed to revoke lease ... user name is empty", and
> the key stays. A small integration test shows it: a single member with that option, a key put
> under a 2s lease, then auth enabled. The key is still there 10s later on `main`, and it is gone
> within ~3s with this PR. It may be worth adding that end-to-end test to the PR, next to the
> unit-level `TestWithRootInternalVerifyOnlyJWT`.
>
> One behaviour difference that the doc comment could mention: a context from `WithRoot` that
> later gets a user token added as incoming metadata (`metadata.NewIncomingContext`) runs as that
> user. With `WithRootInternal`, the root value takes precedence over any token. Nothing in etcd
> does this today, but since the function is exported, saying "the returned context
> authenticates as root regardless of any token later attached to it" would make the contract
> explicit.
