## Verdict

The counter is correct on 64-bit platforms, as far as it is verified. It was proved that
`s.logicalBytes` always equals the sum of `len(key) + len(value)` over the live keys (mod 2^64) of
the writer's state. Before a write transaction opens, and after it ends, that state is the
committed one. Inside a transaction it is the committed state plus the changes made so far.
`PutSize` returns the key's live size before the put. `TombstoneSize` returns the size it removes.
`put`, `delete` and `deleteRange` keep the counter exact, including overwrites, delete-then-put
and range deletes in one transaction. Every existing spec in mvcc and above it is re-proved
unchanged.

**But the PR panics on 32-bit platforms.** It updates a plain `int64` struct field with
`sync/atomic`. On `GOARCH=386`, `store.logicalBytes` is at offset 116, which is not 8-byte
aligned, so `NewStore` panics with `unaligned 64-bit atomic operation`. That breaks etcd on
386/arm/mips (supported with `ETCD_UNSUPPORTED_ARCH`, and built by `make build-all`). It also
breaks the PR's own tests and the existing mvcc tests under etcd's 386 unit-test job. The
verification model assumes 64-bit words, so the proof cannot see this. The fix is a one-liner:
make the field an `atomic.Int64`.

Not covered by the proof:
- the restore path with data (`restoreIntoIndex`, untranslated; the `store.restore` axiom covers
  an empty backend). Randomized Go tests cover it: restarts, snapshot `Restore`, compaction and
  cache eviction all pass;
- the Prometheus wiring (`dbLogicalSize`, `reportDbLogicalSize`, `setupMetricsReporter`: names-only).

## The specs

- **The model** (`Proof/.../mvcc/LivePayload.lean`, from #22475): `payloadW log` is the sum of
  `len(key)+len(value)` over the state after `log`, as a word, and `liveW log k` is the key's part.
  New lemmas:
  - `payloadW_snoc`: one change moves the payload by the key's part;
  - `payloadW_nil`: an empty pending revision leaves the payload unchanged;
  - `payloadW_init`.
- **The index invariant** (`InvIndex.lean`, from #22475): `idxLockInv` has
  `ownLive L (ilog ++ [pend]) q`. Every key index's `liveSize ↦ liveW (ilog ++ [pend]) key`.
- **The store's counter** (`InvStore.lean`, new):
  - `StoreNames.lb` is a `ghostVar w64`.
  - `isStore` has `inv lbN (∃ w, s.logicalBytes ↦ w ∗ ghostVar γ.lb ½ w)`.
  - The other half is the writer's: `writerRes` (the batch lock's resource) holds
    `ghostVar γ.lb ½ (payloadW ilog)`. `storeTxnWriteIs`/`storeTxnWriteCore` hold
    `ghostVar γ.lb ½ (payloadW (ilog ++ [pend]))`.
  - `put` and `delete` open the invariant around their `atomic.AddInt64` and move both halves to
    the payload with the change. `End` returns the half to `writerRes`, using `payloadW_nil` for
    an empty revision.
- **`treeIndex.PutSize`** (`Spec/.../mvcc/treeIndex__PutSize.lean`): premise
  `size = W64 (len k + len v)`, returns `liveW (ilog ++ [pend]) k`. Compared with #22475's
  `Put(key, rev, valueSize)`, which returns the delta (`liveW after − liveW before`), this one
  returns the old size and the caller computes the delta.
- **`treeIndex.TombstoneSize`** (`Spec/.../mvcc/treeIndex__TombstoneSize.lean`): returns
  `(liveW (ilog ++ [pend]) k, nil)`. #22475's `Tombstone` returns its negation.
- **`treeIndex.Put` / `Tombstone`** (`Spec/.../mvcc/treeIndex__{Put,Tombstone}.lean`):
  - Old (lean): the index and the writer's log get the change; `Put` returns nothing, `Tombstone`
    returns `nil`.
  - New: the same, with a premise that records the hazard the PR leaves. The put must leave the
    key's live size unchanged. The delete needs the key's live size to be already 0.
  - Callers: none in production. All the store's writes go through `PutSize`/`TombstoneSize`.
- **`store.LogicalBytes`** (`Spec/.../mvcc/store__LogicalBytes.lean`): for
  `o : Option w64`, with the writer's half at `w` when `o = some w`, it returns `v` with
  `o = some w → v = w`.
- **The trust-boundary axiom `store.restore`** (`Spec/.../mvcc/store__restore.lean`, changed):
  - It also takes and returns `s.logicalBytes ↦ 0`. On the empty backend the axiom covers,
    `restore` stores `restoreIntoIndex`'s 0, the value already there. That store is modelled as no
    write, as the axiom already does for `currentRev`.
  - Not modelled (stated in its docstring): `setupMetricsReporter` publishes `s` to the global
    metrics callback, which may read the counter atomically, as 0, before `NewStore` puts it in
    the invariant.

## Findings

- **Bug in the PR (high): 32-bit platforms panic.**
  - `store.logicalBytes int64` is updated with `atomic.AddInt64`/`LoadInt64`/`StoreInt64`. On
    386 it sits at offset 116, and the first atomic access (`StoreInt64` in `restore`, reached
    from `NewStore`) panics: `unaligned 64-bit atomic operation`.
  - The PR's `TestStoreLogicalBytes` and the existing `TestKVRestore` panic under `GOARCH=386`.
    The whole mvcc package passes on 386 at the merge base.
  - The reviewer found that etcd's presubmits include `pull-etcd-unit-test-386`, which has not
    run yet because the PR lacks `ok-to-test`.
  - Fix: `logicalBytes atomic.Int64` (always aligned), or move the field first.
  - Test: `notes/pr-verify/etcd-22096/kvstore_logical_bytes_386_test.go`, with logs.
- **Hazard left in the API (low).** `index.Put`/`Tombstone` remain in the interface but no longer
  maintain `liveSize`, so any future caller would silently desync the counter. Their specs here
  carry that as a premise. Suggest removing them (as #22475 does, by changing their signatures),
  or making them call the sized versions.
- **Transients (info).** The counter moves inside a write transaction, before `End` makes the
  changes visible. A delete-then-re-put of one key shows the counter dip, e.g. to 0, while readers
  still see the old state. This is the same as #22475's gauge between `tx.Unlock` and `Add`, but
  longer: per operation rather than per transaction. Reviewer's test: `TestReviewLogicalBytesMidTxn`.
- **One gauge per process (info).** `reportDbLogicalSize` is a global that the last store to call
  `setupMetricsReporter` overwrites, the same as the existing `db_total_size_in_bytes`. Because the
  counter itself is per store (not a global gauge as in #22475), values never mix. With several
  stores, the metric shows the last one. Reviewer's test: `TestReviewLogicalBytesGlobalGauge`.
- `keyIndex.equal` ignores `liveSize` (test-only `treeIndex.Equal`), so index-equality tests
  cannot catch a wrong `liveSize`; #22475 compares it.
- No bug was found in the existing (pinned) code, so `issues/` is unchanged.

Tests, in `notes/pr-verify/etcd-22096/` (README there):
- `kvstore_logical_bytes_random_test.go`: 40 random histories, with `LogicalBytes()` checked
  against `Range` after every step, including restarts, `Restore` and restore-cache eviction.
  Passes on the PR head.
- `logical_bytes_review_test.go` (reviewer): mid-transaction values, the global gauge, and
  concurrent writers/readers/compaction/`Restore` under `-race`. All pass.
- `kvstore_logical_bytes_386_test.go`: the alignment panic.

## Comparison with etcd-io/etcd#22475 ("mvcc: add live KV payload size metric")

Both PRs track the same quantity, the sum of `len(key)+len(value)` over live keys, with the same
per-key field `keyIndex.liveSize` and the same restore logic.

- **Index API.**
  - #22475 changes `Put`/`Tombstone` to return a delta.
  - #22096 adds `PutSize`/`TombstoneSize`, which return the previous size, and keeps the old
    methods, which leaves the hazard above.
- **Where the sum lives.**
  - #22475 accumulates a per-transaction `liveSizeDelta` and adds it to a global Prometheus gauge
    in `End`. Its weakness: the gauge mixes stores in one process.
  - #22096 keeps an atomic per-store counter updated at each operation, read by a `GaugeFunc`
    and exposed as `KV.LogicalBytes()`. Its weaknesses: the misaligned field panics on 32-bit,
    and the counter shows uncommitted operations.
- **Proof reuse.**
  - Reused unchanged: #22475's model and index invariant. Its `Put`/`Tombstone` proofs became
    `PutSize`/`TombstoneSize` with small edits (the return value).
  - Not reused: #22475's `liveSizeDelta` field and gauge facts in `mvccInit`. In their place, a
    store-level invariant with a ghost variable shared with the writer.
  - #22096's spec is stronger at the store level: the counter's value itself is proved,
    because it is ours rather than Prometheus'.
- **Metric names.** `etcd_mvcc_db_logical_size_in_bytes` (#22096) vs
  `etcd_mvcc_live_kv_payload_bytes` (#22475). Only one of the PRs should merge.
