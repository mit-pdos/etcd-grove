## Verdict

As far as the proof reaches, index-driven compaction is safe. Every bucket key it deletes is a revision at
or below the compaction revision that compaction keeps for no key, with the right tombstone mark, so a read
at or above the compaction revision never loses its row. The keys it computes for a key are exactly the
revisions the compacted index stops holding (`kiRevs_kiDel`).

On ordinary histories it deletes the same rows as the range scan. A random differential test of 780
histories, including reopen, found no difference. On the #22376 shape (delete, then put, in the
compaction revision) it is the mode that keeps the live row.

The PR is not ready as it is:

1. **High: it does not take `LockForSafeRangeDelete`.** It must, once rebased onto current `main`, where
   non-blocking defrag is on by default. The rebase does not conflict, so the gap would ship silently.
2. **Failpoint builds break**: five failpoints are declared twice.
3. **The default path pays for the feature**: with the gate off, `treeIndex.Compact` still builds a map of
   every deleted revision, under the index lock.
4. **Not documented**: with the gate on, the compaction-hash corruption check goes silent, and the gate's
   description does not say so.

Not covered by the proof:
- **Completeness at the bucket level**: that every obsolete row is deleted. The specs prove safety only (an
  empty delete set would meet them). Completeness also needs every bucket row to be in the index, which
  depends on `restoreIntoIndex` (not verified) and on finding 1.
- **Crash ordering**: the batches commit one by one. Crash safety needs ascending order, so that each key
  keeps a suffix of its revisions. The PR sorts ascending, but the `sort.Slice` axiom promises only a
  permutation, and crashes are not modelled.

**`keyIndex.compact`** (`Spec/.../mvcc/keyIndex__compact.lean`):
- **Old**: the key index compacted (`kiCompact`), and the kept revision added to `available`.
- **New**: the same, and `del` gets `delAdd D (kiDel atRev ki)`. `kiDel` (`Proof/.../mvcc/CompactDel.lean`)
  is every revision of the generations before `doCompact`'s, the last of each marked a tombstone, plus the
  revisions before `doCompact`'s revision index in its generation.

**`treeIndex.Compact`** (`Spec/.../mvcc/treeIndex__Compact.lean`):
- **Old**: it returned `m` with `keepSetIs`.
- **New**: it returns `(m, md)`, `m` as before, and `md` with `delSetOk D log rev` (`InvCompactDel.lean`).
  That is, every bucket key in `D` satisfies `DelOk`: a revision of the certified log with main in
  `[0, rev]`, kept by no key (`¬ keepAt`), marked a tombstone exactly when its event is a delete.
- **Proof**: per key, `kiDel_ok` (`CompactDel.lean`) is applied to the tree's compacted key index of the
  current log, through `reader_prefix_from`.

**`store.scheduleCompactionIndexDriven`** (`Spec/.../mvcc/store__scheduleCompactionIndexDriven.lean`):
- **Spec**: `scheduleCompaction`'s, but it returns the zero `KeyValueHash`. Either `nil` and
  `compactedAt γ rev`, or the store stopped and `fmt.Errorf`'s error; the compactor token at `rev` either way.
- **Proof**: each `UnsafeDelete` gets `delKey` from `DelOk.keyDel`.

## Pure facts proved (`Proof/.../mvcc/CompactDel.lean`)

- `kiRevs_kiDel`: `kiRevs ki = (kiDel c ki).map fst ++ kiRevs (kiCompact c ki)`. The delete set is exactly
  what the index drops, each revision once, in order. This is completeness relative to the index.
- `kiDel_main_le`, `kiDel_lt_avail`: every deleted revision is at or below `c`, and below the revision
  compaction keeps for the key.
- `kiDel_tomb`, `KiEvs.kiCompact`: the mark is the event's (delete ↔ tombstone), also of an already
  compacted key index.
- `kiDel_ok`: the above, lifted to the tree's key indexes (compacted at earlier levels, with later events).

## Findings (step 8)

**1. High: no `LockForSafeRangeDelete` in the index-driven pass** (the reviewer's
`kvstore_compaction_review_test.go`, log `review-test.fork.log`, against the fork branch).
- Upstream `main` (`d6af8028d`, "Support non-blocking defragmentation", gate `NonBlockingDefrag`, beta, on
  by default) requires every delete from the key bucket to hold `Backend.LockForSafeRangeDelete`.
  `scheduleCompaction` takes it for the whole pass.
- The PR's base predates that commit, so its new function does not take the lock. A rebase merges cleanly
  and keeps the gap.
- With both gates on, a defrag concurrent with compaction can carry deleted rows into the new db. That
  member's hash then differs from the others'.
- It is worse than for the range scan. The range scan deletes such rows at the next compaction; the
  index-driven pass deletes only revisions the in-memory index still has, so the rows stay until a restart
  rebuilds the index.
- The proof does not see this: the backend model's `LockForSafeRangeDelete` protects nothing. That is a gap
  of this repository's model (`notes/STATUS.md` on this branch).
- Fix: take `s.b.LockForSafeRangeDelete()` / `defer s.b.UnlockForSafeRangeDelete()` at the start of
  `scheduleCompactionIndexDriven`, as `scheduleCompaction` does.

**2. Medium: failpoint builds fail** (`gofail-build.sh`, `gofail-build.pr.log`).
- `kvstore_compaction.go` now declares five failpoints more than once: `compactAfterAcquiredBatchTxLock`
  (three times), `compactBeforeCommitBatch`, `compactAfterCommitBatch`, `compactBeforeSetFinishedCompact`
  and `compactAfterSetFinishedCompact`.
- After `gofail enable`, the package does not compile (`__fp_... redeclared`, `label ... already defined`).
  This breaks the failpoint builds the e2e and robustness tests use. The base builds.
- Fix: give the new function's failpoints their own names, or share one helper.

**3. Medium: the default path does the new work** (`TestProbeDefaultPathBuildsDeleteSet`).
- `treeIndex.Compact` always allocates `del`, and `keyIndex.compact` fills it under `ti.Lock`, even with the
  gate off. `scheduleCompaction` then discards it.
- That is one map entry per obsolete revision, held for the whole pass. An estimate, not measured: roughly
  0.5 GB for 10M revisions. Index-lock holds are longer too.
- With the gate on, the sorted copy doubles the memory, against the range scan's bounded batches. This may
  explain the worse tail latency in the PR's own benchmark comment.
- Fix: pass `nil` for `del` on the standard path (`keyIndex.compact` already checks `del != nil`).

**4. Low: the compaction hash is not stored under the gate** (`TestProbeIndexDrivenStoresNoHash`).
- Skipping it is unavoidable, since nothing is scanned. But it silently turns off `CompactHashCheck` on a
  leader with the gate on.
- With mixed settings, peers are skipped for lack of a matching hash: there is no false alarm, but there is
  no check either.
- The gate's description should say so.

**5. Low: the PR's test comment overstates equivalence** (`TestProbeDeletePutAtCompactRev`, the reviewer's
`TestReviewDeleteThenPutModes`).
- The test says both modes leave "exactly the same key bucket". On the #22376 shape they do not: the range
  scan deletes the live row (the read then panics, `range failed to find revision pair`), and the
  index-driven pass keeps it.
- So the index-driven mode does not have #22376. But members with different gate settings have different
  backends on that shape, and so different `HashByRev`.
- The specs here do not credit the gate-on path for this: `DelOk` is relative to `keepAt`, which still
  needs `NoDelPutAt` for reads (`issues/etcd-compaction-delete-then-put.md`, unchanged).

**Bugs in the existing (pinned) code**: none new. #22376 is already recorded.

**Reviewer's open points**:
- Bucket-level completeness and crash ordering are not proved (see the verdict).
- Completeness could be carried to `treeIndex.Compact`'s spec at the index level. That is not done.

> revision can still name. A randomized comparison with the range-scan path (780 histories over a few keys,

>    re-declares `compactAfterAcquiredBatchTxLock`, `compactBeforeCommitBatch`, `compactAfterCommitBatch`,

>    under the index lock), and `scheduleCompaction` throws it away. Passing `nil` there would keep the
>    default path as it was.
> 4. With the gate on, no compaction hash is stored, so the compaction-hash corruption check does nothing.
>    Worth saying in the gate's description.
> 5. The test comment says both modes leave exactly the same bucket. That's not true when a single
>    transaction at the compaction revision deletes and re-puts a key (#22376): the range scan deletes the
