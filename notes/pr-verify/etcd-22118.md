## Verdict

The change is sound as far as it is verified. The three new methods are proved against specs
written from the PR's description, and with them `delete`, `txnLeasing.Commit`, and the exported
`Delete` and `Do` meet stronger specs: a delete, or a transaction whose then or else branch has a
delete, whose range intersects the lease prefix returns an error before anything else happens,
and a delete that succeeds had no key with the prefix in its range, in etcd's own sense of a range
(a key alone, `[key, end)`, or from a key on). The proof of the second part needs nothing beyond
the code's check (theorem `leaseDelIntersects_false`). Every new spec implies the old one, so the
other callers are unaffected. Not covered: nested transactions inside a leasing `Txn` (the leasing
specs only model plain operations there, as before; the PR's `gatherOps` does reach them and its
test covers them); and the PR reserves the prefix only for deletes. A put through the leasing KV
to a key under the prefix still breaks the protocol, and makes later writes of the user key block
(a pre-existing bug, reproduced, `issues/leasing-put-into-prefix.md`).

### The behavior changes

The guard both changed specs gain (`Proof/go_etcd_io/etcd/client/v3/leasing/InvLeasingPrefix.lean`):

```lean
def LeaseDeleteGuard (pfx : GoString) (os : List OpFull) (err : GoInterface) : Prop :=
  ((∃ o ∈ os, leaseDelRejected pfx o = true) → err ≠ GoInterface.nil) ∧
  (err = GoInterface.nil → ∀ o ∈ os, o.t = W64 3 → LeaseKeysOutside pfx o)
```

where `LeaseKeysOutside pfx o` is `∀ k, pfx <+: k → inRange o.key o.base.rangeEnd k = false` (etcd's
`inRange`: the key alone if the end is empty, every key from `key` on if it is `"\x00"`).

- `leasingKV.delete` (`Spec/go_etcd_io/etcd/client/v3/leasing/leasingKV__delete.lean`). Old
  (`spec_old`): returns an error, or the range's delete committed at a revision `≥ lo`
  (`deleteCommitted`), lease keys included. New: the same plus `LeaseDeleteGuard pfx [o] err`.
  The old code does not meet the new spec (it commits `Delete("b", WithFromKey())`, which
  intersects `"pfx/"`; `TestLeasingDeleteFromKeyStaleRead` shows the effect), so the new spec pins
  down exactly what the PR changed.
- `txnLeasing.Commit` (`Spec/.../txnLeasing__Commit.lean`). Old: `commitOutcome` (the cache's
  evaluation or the client's answer). New: the same plus
  `LeaseDeleteGuard pfx (b.thenOs ++ b.elseOs) err`, both branches' operations whichever runs.
- `leasingKV.Delete` and `leasingKV.Do` (`Spec/.../leasingKV__Delete.lean`, `leasingKV__Do.lean`):
  the guard propagated to the exported API (for `Do`, in its delete and transaction cases). The
  PR's `doc.go` states the change for users: "Delete operations that intersect this range fail
  with a gRPC InvalidArgument status." The spec says "an error"; that the error is
  `InvalidArgument` is not stated, since `status.Errorf` is a trust-boundary axiom that promises
  only a non-nil error.

The new pure model is `leaseDelIntersects` (the Go function step by step, using `leaseInRange`,
the existing model of `cache.go`'s `inRange`, and `prefixRangeEnd`, the model of
`GetPrefixRangeEnd`). Its theorem `leaseDelIntersects_false` (in `Results.lean` as
`leasing_delete_spares_lease_keys`): for a non-empty prefix, a delete the check lets through has
no key with the prefix in its range. The cases are: the key alone; `"\x00"` (from key); a range;
and a prefix of `0xff` bytes, whose `prefixRangeEnd` is `"\x00"`, open-ended for both `inRange`s.
The converse does not hold exactly: the check also rejects ranges that delete nothing but start
in the prefix (`["pfx/b", "pfx/a")`), which is conservative and harmless
(`TestLeasingDeleteReservedPrefixRejected`).

## Findings

1. **The PR fixes etcd#22083, as the proof confirms.** The bug is in the pinned code
   (`issues/leasing-delete-removes-lease-keys.md`); the PR's result is the guard above. Its user-visible
   effect, stale cached reads after the delete, is shown by `TestLeasingDeleteFromKeyStaleRead`
   (`notes/pr-verify/etcd-22118/leasing_prefix_put_test.go`). It fails at the pin
   (`expected: "new"`, `actual: "old"`, `run-pin.log`) and passes at the PR's head
   (`run-upstream-pr.log`).
2. **Incompleteness (pre-existing bug the PR leaves): puts into the prefix.** `lkv.Put(ctx, "pfx/b", …)`
   is accepted. It replaces `b`'s lease key with a lease-0 record, so the holder ignores the next
   writer's `"REVOKE"`, and that writer's `Put("b")` blocks until its context ends
   (`TestLeasingPutIntoPrefixBlocksWriters`: `context deadline exceeded` at both revisions).
   Recorded in `issues/leasing-put-into-prefix.md`. In the proof, this run is outside the protocol
   premise `LeasingStepOk` (2) (a lease key that keeps its create revision keeps its lease). The
   PR's documentation sentence names deletes only, so the PR does not claim to cover this; a
   follow-up could reject writes into the prefix the same way.
3. **Empty prefix.** With `NewKV(cl, "")` every delete is now rejected (`GetPrefixRangeEnd("")` is
   `"\x00"`). The leasing KV is unusable with an empty prefix anyway: the lease key of `k` would be
   `k` itself. The verified `NewKV` takes `pfx ≠ ""` as a premise, so this is outside the specs.
4. **Not covered by the specs: nested transactions in `Txn`.** The leasing transaction specs model
   plain operations only (`LTxnBuild`, as before the PR). `validateDeleteOps`'s own spec covers
   nested operations (through `gatherOps`), but `Commit`'s precondition does not admit them.

### The reviewer's points

A fresh reviewer read the PR, the specs, the model and the proofs. It confirmed that
`leaseDelIntersects` is faithful to the Go code, including the `"\x00"` ends and the all-`0xff`
prefix. It confirmed that `LeaseKeysOutside` uses the same `inRange` as `deleteCommitted`, so the
two together say that no lease key is deleted. It found the `spec_implies_old` lemmas sound,
`codes.InvalidArgument = 3` correct, and no concurrency concern (the check reads only the
immutable `lkv.pfx`). Its points:

- *Incompleteness (= finding 2)*: it reproduced the put-into-prefix breakage through a leasing
  `Txn` put: another client's `Put` of the key blocks and the holder's `Get` stays stale
  (`TestReview22118TxnPutIntoPrefix` in `notes/pr-verify/etcd-22118/leasing_review22118_test.go`,
  `run-review-upstream-pr.log`). It suggests that either `doc.go` say "Delete operations" rather
  than "reserves a key range", or puts be rejected too.
- *Spec gap, open*: on the error path the guard holds trivially. The specs do not state that a
  rejected delete reached no server, nor that its code is `InvalidArgument`. Stating "rejected
  implies nothing committed" would need the error disjunct of `deleteCommitted`'s callers to carry
  etcd's state; left open. The behavior is tested: `TestReview22118Precedence` (passes) shows the
  rejection taking precedence over a cancelled context, rejecting a delete in an else branch that
  cannot run, and rejecting nested-transaction deletes through `Txn` and `Do`, all with
  `InvalidArgument`.
- *Spec gap, inherited (= finding 4)*: nested-transaction rejection is proved at
  `validateDeleteOps` only, not end to end through `Commit` and `Do`.
- *Nits (= findings 3 and the empty-range note)*: an empty prefix rejects every delete; some empty
  ranges are rejected. Both are harmless.

## Draft review comment (for the user to edit and post)

> Thanks, this fixes #22083 for deletes. I checked the new check against how the server reads a
> range: a single key, `[key, end)`, from-key (`"\x00"`), and a prefix of all `0xff` bytes. A delete
> that passes the check can never remove a key under the leasing prefix, and every delete whose
> range contains such a key is rejected, including in either branch of a `Txn`, in nested `Txn`s
> and through `Do`. Two notes:
>
> 1. The doc comment says the prefix "reserves a key range for leasing protocol state", but only
>    deletes are rejected. A `Put` (or a `Txn` put) through the leasing KV to `pfx/k` is still
>    accepted. It replaces the owner's lease key with one that has no lease, so the owner ignores
>    the next writer's revoke, and that writer's `Put(k)` then blocks until its context expires
>    (the owner keeps serving its cached value). A test that shows it:
>    `lkv1.Get("b")`, `lkv2.Put("pfx/b", "x")`, then `lkv2.Put(ctxWithTimeout, "b", "v2")` returns
>    `context deadline exceeded`. Either reject writes into the prefix as well, or narrow the
>    comment to deletes and track writes separately.
> 2. Ranges that start inside the prefix but are empty (`Delete("pfx/b", WithRange("pfx/a"))`) are
>    rejected too. That seems fine, but it might be worth a test case, since "intersects" could be
>    read either way.
