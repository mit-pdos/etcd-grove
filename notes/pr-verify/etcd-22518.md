## Verdict

The PR does what it says, safely. The proof shows that `OpenSnapshotBackend` now reports success
only after the rename of `<index>.snap.db` onto `db` has been followed by a successful `fsync` of
the directory that holds `db`. When the sync fails, it returns a nil backend and an error.

The callers then make this sufficient for #22498. The consistent index takes the snapshot's index
only after `OpenSnapshotBackend` returns (`consistIndex.SetBackend(newbe)`, then
`lessor.Recover`/`kv.Restore`). Only then do the old backend's commits write it into the old file.
This was checked by reading `applySnapshot` and the bootstrap path; neither has a proof here.

What is not covered:
- **Crash semantics.** Perennial has no crash or file-system model, so durability is an abstract
  resource here, produced only by the trust-boundary `Fsync` spec (below). The Linux claim behind
  that spec is assumed, not proved: a directory `fsync` makes an earlier rename into it durable.
- **The callers.** `applySnapshot` and `RecoverSnapshotBackend` are not proved over the new spec
  (step 6).
- **The `ServerConfig` instances.** The proof of `OpenSnapshotBackend` reaches six generated
  `sorry -- axiomatized type` instances. `ServerConfig` is passed by value, and its fields of
  names-only types have no typed points-to (trust base, below).

The PR has minor problems with its tests and code structure (Findings), not with what it does.

### The spec

`Spec/go_etcd_io/etcd/server/v3/storage/OpenSnapshotBackend.lean` takes a snapshot `snapshot` (not
`nil`, owned as `ownSnapM` at any fraction) and returns `(be, err)` with the snapshot unchanged,
where either:
- `err = nil` and `fs.entryDurable (snapDBPath ss idx) (cfgBackendPath cfg.DataDir)`, with `idx`
  the snapshot's index: the directory entry `db` is durable and names the snapshot's database
  file; or
- `be = nil` and `err` is an error whose `Error()` returns a string.

`Spec/.../storage/syncSnapDir.lean` takes a pending rename of `src` onto `dst` in `dir`. On `nil`
it returns `fs.entryDurable src dst`. On an error, nothing is known of the rename.

The durability vocabulary is in `Proof/.../storage/InvSnapshotBackend.lean`: `fs.renamePending`,
`fs.entryDurable`, `fs.dirHandle`, `fs.dirOf`, `snapDBPath`, `cfgSnapDir`, `cfgBackendPath`.
- They are Lean `opaque` constants, not axioms.
- The specs of the trust-boundary functions are their only introduction and elimination rules.
- `os.Rename` gives `renamePending src dst`.
- `fileutil.Fsync` of a handle of `fs.dirOf dst` turns it into `entryDurable`. A failed `Fsync`
  consumes it: after an `fsync` error, Linux does not promise that a retry makes anything durable.

## Trust base (step 7)

`etc/tcb-report.py --collection etc/tcb-collections/pr-etcd-22518.txt` (the root
`storage.wp_OpenSnapshotBackend`) rests on 11 of this repository's axioms. Eight are new:

- `os.Rename.wp_proof`: on success, `renamePending src dst`.
- `os.File.Close.wp_proof`: consumes a directory handle.
- `fileutil.OpenDir.wp_proof`: on success, a handle of `dir`.
- `fileutil.Fsync.wp_proof`: a handle of `dir` plus `renamePending src dst` with
  `dirOf dst = dir`. On success it gives `entryDurable src dst`. This is the Linux/ext4/xfs
  semantics of a directory `fsync`, and the PR's whole premise.
- `snap.Snapshotter.DBFilePath.wp_proof`: on success, `snapDBPath ss id`.
- `config.ServerConfig.SnapDir.wp_proof` and `config.ServerConfig.BackendPath.wp_proof`: functions
  of `DataDir`, with `dirOf (BackendPath) = SnapDir`. This is
  `datadir.ToBackendFileName = Join(ToSnapDir, "db")`.
- `storage.OpenBackend.wp_proof`: returns some backend. bbolt open errors are fatal in
  `backend.New`.

The other three were already there: `fmt.Errorf`, `zap.Logger.Info` and `zap.String`.

**New `sorry`s reached: 6.** These are the generated `sorry -- axiomatized type` instances
(`TypedPointsto`, `IntoValTypedUnderlying`) of `transport.TLSInfo`, `types.URLs` and
`v3discovery.DiscoveryConfig`:
- They are reached because the Go function takes `config.ServerConfig` by value, so Goose spills it

## Findings

No bug in the PR. No bug was found in the existing (pinned) code beyond #22498 itself. That bug is
upstream's: the pinned `OpenSnapshotBackend` lacks the sync. It is reported upstream and was not
verified code here (names-only), so it is not added to `issues/`. The reviewer's points, all minor:

1. **The PR's tests check a log line, not the sync.** `Test_t1`, `Test_t2` and `Test_t5` assert
   that "fsynced snap directory after adopting database snapshot" is logged. They would pass if
   the line were emitted without syncing. `Test_t5_..._fsync_failure_returns_nil_backend_and_error`
   does not exercise a failure: it repeats `Test_t1`. `Test_t4` duplicates the existing
   `TestSaveDBFromSyncsDirectory`. The `Test_tN_snake_case` names are not etcd's style.
2. **The failure path cannot be injected.** The new `syncSnapDir` duplicates `snap.fsyncSnapDir`
   (`server/etcdserver/api/snap/db.go`) without that function's `snapDBDirSyncError` gofail point or
   the `Snapshotter.fsyncDir` hook. So neither unit tests nor robustness tests can make it fail.
   Reusing the snapshotter's hook (`ss`) would fix both, and the tests could then observe the sync
   itself rather than a log line.
3. **The nil-logger check is dead code.** `if cfg.Logger != nil` guards the new log line, but
   `OpenBackend`, called right after, logs through `cfg.Logger` unconditionally.
4. **Platforms: nothing new.** On darwin (`F_FULLFSYNC` on a directory fd) and on Windows
   (`OpenDir` with `GENERIC_WRITE` and backup semantics, then `FlushFileBuffers`), the helper does
   exactly what the existing snap and WAL directory syncs do.

Open points of the model (this repository's specs, not the PR):
- `fs.entryDurable src dst` is not exclusive. A second rename onto `dst` without a sync would leave
  the first fact in place. No code verified here renames onto `db` twice, but an exclusive per-entry
  token would rule it out.
- The error case says nothing about the file system after a successful rename and a failed sync.
- The success case does not say `be ≠ nil`.
