## Verdict

The handler is safe: `connStatsHandler.HandleConn` is proved not to panic (the leaf is read
only after the length check, the peer is non-nil, the TLS info is a value type assertion), and
to record exactly one observation in `etcd_server_client_cert_expiration_seconds` when the event
is a `ConnBegin` on a TLS peer of a server that asks for client certificates and the peer sent
one, and nothing otherwise. What the observation counts is not what the PR says, though: grpc
calls `HandleConn(ConnBegin)` once per connection only when the client URL serves gRPC alone; on
the default client URL (gRPC and HTTP on one port, gRPC served through `grpc.Server.ServeHTTP`) it
calls it once per HTTP/2 request, i.e. per RPC and per stream, so the same histogram counts
connections in one deployment and requests in the other (probe below: 10 Puts over one
connection give 1 sample vs 11). Not covered: `Server`'s registration of the handler and
`metrics.go`'s `init` (names only), the observed value (time and floats are outside the model:
any `float64`).

**`HandleConn(ctx, s)`**: for any token `P` that the histogram's `Observe(x)` turns into `Q x`
(`certExpHist P Q`), from `P` it returns either `⌜connRecords s hs o oti⌝ ∗ ∃ f, Q f` (one
observation) or `⌜¬ connRecords s hs o oti⌝ ∗ P` (none). `connRecords`: `s` is a
`*stats.ConnBegin`; the context's peer (`peer.inCtx ctx o`) exists and its `AuthInfo` is a
`credentials.TLSInfo` (`oti = some ti`); `hs.clientAuth ≠ tls.NoClientCert`;
`len(ti.State.PeerCertificates) > 0`. Premises: the peer read-only (`p ↦□ pr`), the TLS state's
certificate slice read-only and the leaf's `NotAfter` (`tlsCertsOk`), a `*ConnBegin` in `s` is a
pointer (`connEventOk`).

## Callers (step 6)

`HandleConn` and the three other methods are called only by grpc, through the `stats.Handler`
interface (`server.go`'s `serveStreams`, for every `ServerTransport`: the HTTP/2 transport of
`Serve`, once per connection, and the handler transport of `ServeHTTP`, once per request). The
spec's premises are what grpc v1.84.0 establishes there: `peer.NewContext(ctx, st.Peer())`, a fresh
non-nil `*Peer` never written after; `AuthInfo` a `credentials.TLSInfo` value (`credentials/tls.go`'s
`ServerHandshake`, `handler_server.go`'s `TLSInfo{State: *r.TLS, ...}`), its `ConnectionState`
fixed after the handshake. `RecordClientCertExpiration` is exported but called only by `HandleConn`
in etcd. `Server` (the registration) is names only: not checked. Nothing else changed, so no other
spec moved.

## Trust base

New, this work:

- `peer.inCtx` (axiom, `Proof/google_golang_org/grpc/peer/Defs.lean`): an opaque predicate, the
  peer a context carries. Believed: it is only a name for grpc's `peerKey{}` value.
- `peer.FromContext.wp_proof` (axiom, `Proof/google_golang_org/grpc/peer/FromContext.lean`):
  `FromContext` returns the carried peer's pointer and `true`, or `(nil, false)`. Believed: grpc's
  `ctx.Value(peerKey{}).(*Peer)`; a context with a nil `*Peer` under the key, which grpc never
  builds, is excluded by `inCtx`.
- Premises (not axioms): `certExpHist` (the histogram's `Observe` returns; prometheus is names
  only, as the existing watch metrics), `connTLSOk`, `connEventOk`, `peer.ctxOwn` (grpc's side).

Already there: `time.Duration.Seconds.wp_proof` (any `float64`), Perennial's `time.Until` (any
duration). No `sorry`. (`#print axioms` of `conn_stats_handle_conn`: see "Build" below.)

Translation changes this needed (in `etc/goose.py` and `Code/**/*.toml` of this branch): new
names/types-only packages `crypto/tls` (with types: `ConnectionState`, `ClientAuthType`),

## Findings

1. **The histogram counts RPCs, not connections, on the default client URL** (design concern
   in the PR). On a gRPC-only client URL (`--listen-client-http-urls` set separately) grpc owns
   the TLS handshake and calls `HandleConn(ConnBegin)` once per connection. On the default client
   URL, where gRPC and HTTP share the port (`embed/serve.go`: `grpcHandlerFunc`, served by the
   HTTP server's TLS listener), gRPC is served through `grpc.Server.ServeHTTP`, which runs
   `serveStreams` (`TagConn`, `HandleConn(ConnBegin)`, `HandleConn(ConnEnd)`) for every HTTP/2
   request. So a long-lived client with one connection is sampled on every unary RPC and every
   stream, and the bucket counts are not comparable between the two deployments. The PR's e2e test
   notes "we don't assert an exact count because etcdctl may open more than one gRPC connection";
   the extra samples come from this. Probe:
   `notes/pr-verify/etcd-21621/cert_expiry_metric_count_test.go` (output `...test.log`: 10 Puts
   over one connection give 1 sample on a gRPC-only URL, 11 on the default URL). This is what
   kube-apiserver's similar metric does (per authenticated request), but then the help text
   ("for TLS connections") and the per-connection handler are misleading, and gRPC-only
   deployments count differently.

No bug in the existing (pinned) code was found: nothing added to `issues/`.
