## Verdict

As far as this framework can see, the change is safe. The new backoff function never panics
(the quorum is never 0, so the `%` and `/` cannot divide by zero), always returns a wait, and
gives the retry interceptor what its already-verified proof needs (`backoffOk`). Every caller
spec is unchanged.

The wait's value is not covered by the proof. It is float arithmetic, which Perennial does not
model. Go tests checked it instead, and found the PR does less than it says:

- **Compatibility regression.** The default exponent 1.0 is described as keeping the old
  behavior, but it silently caps an existing `BackoffWaitBetween` above 5s to 5s.
- **Overflow.** A very large `BackoffMaxWaitBetween` (such as `math.MaxInt64`) overflows the
  conversion back to `time.Duration`. The wait becomes negative and the client retries without
  waiting.
- **Smaller issues:**
  - the first backoff is already `exponent × BackoffWaitBetween`;
  - jitter can push the wait above the max;
  - an exponent below 1 is accepted and shrinks the wait to 0.

`dialSetupOpts`, where the two new settings get their defaults, is not translated. It was checked
by reading only.

## The specs

- **Old** (none). The function was names-only on `lean`. The retry interceptor's proof assumes, in
  `retryOptsAt`, that the options' backoff function satisfies `backoffOk`, and nothing proved this
  of the dial's backoff function.
- **New** (`Spec/go_etcd_io/etcd/client/v3/Client__roundRobinQuorumBackoff.lean`): given the
  client invariant `retryClientOk c`, which includes a non-nil logger, the result `bf` satisfies
  `backoffOk bf`. That is, `bf(attempt)` returns some duration for every attempt and never panics.
  The proof discharges the divisor check: `uint.Z (len/2 + 1) ≠ 0` (`rrQuorum_ne_zero`).
  `withBackoff` (verified, unchanged) turns `backoffOk` into `optApplyOk`, which the interceptor
  consumes, so the PR's backoff function meets the interceptor's requirement.
- **What the spec does not say**: anything about the wait's value. Perennial's `float64` is an
  opaque bit pattern with uninterpreted operations, and it has no semantics for
  `Convert go.float64 time.Duration`. So the values of `expBackoff` and `jitterUp` cannot be
  stated, and their bodies cannot even be run in the program logic. This is recorded as a
  Perennial limitation in this branch's `notes/STATUS.md`. The PR's numeric claims were checked
  with Go tests instead (Findings).

## Findings (step 8)

All tests are in `notes/pr-verify/etcd-20731/`; its `README.md` gives the commands. They ran at the
PR head on linux/amd64, with `GOTOOLCHAIN=go1.26.4`.

1. **A `BackoffWaitBetween` above 5s is capped to 5s with the default exponent (compatibility
   regression).** `dialSetupOpts` always passes `defaultBackoffMaxWaitBetween = 5s` when it is
   unset, and `expBackoff` takes `min(1.0^g × wait, 5s)`. So an existing configuration with
   `BackoffWaitBetween: 10*time.Second` now waits 5s.
   - The PR says the default exponent of 1.0 "disables exponential backoff for reverse
     compatibility", so this case should behave as before.
   - Test `TestPR20731DefaultExponentCapsLargeWaitBetween` in `backoff_pr20731_test.go` fails
     (5s, want 10s). At the base, `TestBaseLargeWaitBetweenNotCapped` in `backoff_base_test.go`
     passes (10s).
   - Fix: apply the cap only when the exponent is not 1, or default the max to
     `max(5s, BackoffWaitBetween)`.
2. **The first backoff is already scaled.** The retry loop calls the backoff function only for
   `attempt > 0`, and a wait happens only when `attempt % quorum == 0`, so the generation is
   always at least 1.
   - With exponent 2 and 100ms, the first wait is 200ms; with 3 endpoints, the waits are 200, 400
     and 800ms.
   - `expBackoff`'s doc ("A generation of 0 will return minDelay") describes a case that never
     happens, and `BackoffWaitBetween` is never the actual first wait.
   - The new code computes `attempt/quorum`, which the second commit adopted from a Copilot review
     suggestion. `attempt/quorum - 1` would make the first wait `BackoffWaitBetween`.
   - Test `TestPR20731FirstBackoffIsGenerationOne` (logs).
3. **A huge `BackoffMaxWaitBetween` disables backoff once the cap is reached.**
   - **Cause:** with `BackoffMaxWaitBetween = math.MaxInt64` (a common "no cap" value), the capped
     delay is `float64(MaxInt64) = 2^63`, and `time.Duration(2^63)` is out of range. On amd64 the
     result is `MinInt64`. `waitRetryBackoff` waits only when `waitTime > 0`, so every capped
     retry goes out immediately: 60 of 60 in the test, `TestPR20731HugeMaxWaitBetweenGivesNegativeBackoff`
     (fails).
   - **Wider range:** the reviewer found that any max above about `2^63/(1+jitter)` ns overflows
     inside `jitterUp`. With 9e18 ns, 376 of 1000 capped waits are ≤ 0
     (`TestReviewLargeMaxJitterOverflow` in `review_pr20731_test.go`).
   - **Other platforms:** on arm64 the conversion saturates instead; this was not tested.
   - **Fix:** clamp in the integer domain, or clamp the float to below 2^63 before converting.
4. **An exponent in (0, 1) is accepted and drives the wait to 0.** `dialSetupOpts` checks only
   `> 0`. With exponent 0.5 and 25ms, the wait is 23µs at attempt 10 and 0 from attempt 25 on.
   - Snapshot streams retry without a bound, so such a client can retry in a tight loop; the old
     flat backoff did not allow that.
   - Copilot raised this in review and it is not addressed.
   - Tests `TestPR20731ExponentBelowOneShrinks` and `TestReviewSmallExponentZeroWait`.
5. **The wait can exceed `BackoffMaxWaitBetween`.** Jitter is applied after the cap, so with max 5s
   and jitter 0.1, 492 of 1000 capped waits are above 5s, up to 5.4995s.
   - The `Config` doc calls the field "the max wait time before retrying".
   - Test `TestReviewJitterExceedsMax` (reviewer).

Not caused by the PR:

- **A nil logger panics.** `c.WithLogger(nil)` (public, deprecated) makes every later log call
  panic, the backoff function's included. The proofs assume it away with the existing premise
  `isClientLogger`. Recorded as `issues/etcd-client-withlogger-nil.md`, with the reviewer's
  `TestReviewNilLoggerPanics`.
- **An infinite jitter gives no wait.** `BackoffJitterFraction = +Inf` makes `jitterUp` return a
  wait ≤ 0 (`TestReviewInfInputs`). `jitterUp` is unchanged and the configuration is absurd, so it
  is not recorded in `issues/`.

The reviewer found nothing else wrong:

- **Endpoint changes.** `Endpoints()` copies under `RLock`. When the endpoint count changes
  between attempts, the quorum changes and the pattern jumps (`TestReviewQuorumChange`), as it did
  before the PR.
- **The stream-retry path.** It restarts the attempt counter per message.

The reviewer's one open point at review time, the closure proof still being a `sorry`, has since
been resolved: the proof is complete.

## Draft review comment (for the user to edit and post)

> Thanks for this. A few things I noticed while testing the new backoff function directly:
>
> 1. **Behavior change with default settings.** With `BackoffExponent` unset (1.0) the cap
>    still applies, so a client configured with `BackoffWaitBetween: 10*time.Second` now waits 5s
>    instead of 10s. Since 1.0 is meant to keep the old behavior, could the cap apply only when the
>    exponent is above 1, or could the default max be at least `BackoffWaitBetween`?
> 2. **Overflow with a large max.** With `BackoffMaxWaitBetween: time.Duration(math.MaxInt64)`,
>    `expBackoff` returns `time.Duration(float64(1<<63))`, which is out of range (`MinInt64` on
>    amd64). The retry interceptor treats a negative wait as no wait, so retries stop backing off
>    exactly when they should wait longest. Anything above about `2^63/(1+jitter)` ns overflows in
>    `jitterUp` too. Clamping before the conversion would fix it.
> 3. **The first wait is already scaled.** The backoff function is only called for attempt ≥ 1, so
>    the first generation is 1 and the first wait is `exponent * BackoffWaitBetween` (200ms for
>    2.0 and 100ms). `expBackoff`'s comment about generation 0 never applies. Was
>    `attempt/quorum - 1` intended?
> 4. **The jitter is applied after the cap,** so waits go up to `BackoffMaxWaitBetween * (1 +
>    jitter)`, above the documented max.
> 5. **Exponents in (0, 1) are accepted** and the wait reaches 0 after a couple dozen attempts.
>    Validating `>= 1` (as suggested earlier) seems worth doing.
>
> A unit test of `roundRobinQuorumBackoff` itself (waits per attempt, for a few endpoint counts)
> would cover all of these. I can share the tests I used.
