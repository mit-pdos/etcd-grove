## 1. Executive Summary

`etcd-io/etcd#21401` instruments the gRPC unary interceptor (`v3rpc`), the Raft proposal path (`etcdserver`), linearizable reads (`etcdserver/read`), `traceutil`, and `rafthttp` so that a per-request ID (`requestID`) generated at the unary gRPC boundary is propagated via `context.Context` (`requestid.NewContext` / `requestid.FromContext`) into:
1. Unary request/response debug logs (`newLogUnaryInterceptor`, `logUnaryRequest`, `logUnaryResponseStats`, `requestLogFields`),
2. `traceutil.New` traces (attaching `req-id` from `ctx`),
3. `ReadState.LinearizableReadNotify` and `ReadState.readIndexLoop` debug logs,
4. `EtcdServer.processInternalRaftRequestOnce` (`header.ID = requestID`), and
5. `rafthttp.logRaftCommunication` debug logs across `pipeline.go` and `stream.go`.

We translated all changed packages to Lean 4 via Goose and formally verified every changed function and all affected callers end-to-end across `requestid`, `traceutil`, `etcdserver/read`, `etcdserver`, `rafthttp`, `v3rpc`, `client/v3`, `cache/v3`, and `examples`.

Formal verification in Iris/Perennial and accompanying Go reproduction tests ([`notes/pr-verify/etcd-21401/repro_test.go`](./etcd-21401/repro_test.go), [`repro_test.log`](./etcd-21401/repro_test.log)) uncovered **five concrete bugs/hazards**:

1. **[HIGH — Safety / Linearizability / Server Panic] Request ID Reuse Across Multiple Raft Proposals Sharing a `context.Context` (`server/etcdserver/v3_server.go:1067–1077`, `server/etcdserver/api/v3rpc/interceptor.go:82–83`)**:
   - Before PR `#21401`, `processInternalRaftRequestOnce` unconditionally generated a fresh, unique ID via `id := s.reqIDGen.Next()` for every Raft proposal and registered it in `s.w.Register(id)` (`wait.Wait`).
   - With PR `#21401`, `newLogUnaryInterceptor` generates one `requestID := s.RequestID()` per unary gRPC request and stores it in `ctx = requestid.NewContext(ctx, requestID)`. `processInternalRaftRequestOnce` extracts `requestID := requestid.FromContext(ctx)` and reuses it whenever `requestID != 0`.
   - In Iris (`InvProposer.lean`), the freshness token `idFresh ρ.ids id` (`idUnclaimed ρ.ids id ∗ idSlot ρ.ids id`) required by `s.w.Register(id)` and the proposal mint invariant (`srvPropMint`) is a **linear, single-use** resource inside `reqIdCtx ρ ctx`: once consumed by one proposal, the same `ctx` no longer holds `idFresh ρ.ids id` for a second proposal.
   - In etcd's actual Go codebase, multiple code paths execute more than one Raft proposal on the same unary gRPC `ctx` (or a child context derived from `ctx`, which inherits `requestID` via `Context.Value`):
     - `EtcdServer.Authenticate(ctx, r)` (`server/etcdserver/v3_server.go:853–887`) runs a `for` loop that retries `s.raftRequest(ctx, &pb.InternalRaftRequest{Authenticate: internalReq})` with the **same `ctx`** whenever `checkedRevision != s.AuthStore().Revision()`.
     - `v3lock.lockServer.Lock(ctx, req)` (`server/etcdserver/api/v3lock/lock.go:35–50`) and `v3election.electionServer.Campaign(ctx, req)` (`server/etcdserver/api/v3election/election.go:40–92`) are registered on the same `*grpc.Server` (`server/embed/serve.go:148–150, 184–186`) behind `newLogUnaryInterceptor` and use `v3client.New(s)` (`server/etcdserver/api/v3client/v3client.go:30–52`) in-process, passing the unary gRPC `ctx` directly to `s.Txn` and `s.DeleteRange` across multiple sequential Raft proposals (`waitDeletes`, `Proclaim`, `Unlock`/`Resign`).
     - `quotaAlarmer.check(ctx, r)` (`server/etcdserver/api/v3rpc/quota.go:48`) calls `qa.s.Alarm(ctx, req)` -> `s.raftRequest(ctx, ...)` on the incoming unary gRPC `ctx`.
   - **Consequences**:
     - **(1A — Server Panic)**: If two proposals on the same `ctx` overlap in `s.w.Register(requestID)`, `wait.list.Register` panics with `panic("dup id %x")`, crashing the etcd server.
     - **(1B — Cross-Contaminated Apply Result / Linearizability Violation)**: If an earlier proposal on `ctx` times out locally after `s.r.Propose` (cleaning up its waiter via `s.w.Trigger(id, nil)`) while the Raft entry is still in flight in the Raft log, and a subsequent proposal on the same `ctx` (or child context) registers the same `requestID`, when the first proposal finishes applying in `applyAll`, `s.w.Trigger(header.ID, res1)` delivers **Proposal 1's stale `*apply.Result`** to Proposal 2's waiter channel!
     - **(1C — Heterogeneous Proposal Type-Assertion Panic in `v3election.Campaign` / `v3lock.Lock`)**: In `v3election.electionServer.Campaign`, if `Proclaim(ctx, ...)` (which proposes a `Txn`) times out locally while in flight in Raft and `Campaign`'s error path calls `e.Resign(ctx)` (which proposes a `DeleteRange`) on the same `ctx`, both proposals register the same `requestID`. When the committed `Txn` entry finishes applying, `s.w.Trigger(requestID, res)` delivers a `*pb.TxnResponse` to `DeleteRange`, which immediately panics at `return resp.(*pb.DeleteRangeResponse), nil` (`server/etcdserver/v3_server.go:323`).

2. **[HIGH — Crash / `SIGSEGV`] Nil-Pointer Dereferences in `rafthttp.logRaftCommunication` (`server/etcdserver/api/rafthttp/transport.go:458–493`, `pipeline.go:100`, `stream.go:209, 505`)**:
   - **Bug 2a (`lg == nil` / `p.tr == nil` / `cr.tr == nil`)**: `logRaftCommunication(lg *zap.Logger, ...)` immediately calls `lg.Debug(...)` (`transport.go:459`) without checking `if lg == nil`. Furthermore, `pipeline.go:100` passes `p.tr.Logger` without checking `if p.tr != nil`, and `stream.go:209, 505` passes `w.tr.Logger` / `cr.tr.Logger` without checking `if w.tr != nil` / `if cr.tr != nil`. Existing upstream unit tests `TestSendMessage` and `TestPipelineSend` in `server/etcdserver/api/rafthttp` **immediately crash with `SIGSEGV`** at `transport.go:459` (see [`repro_test.log`](./etcd-21401/repro_test.log)).
   - **Bug 2b (`r.Header == nil` on `MsgProp`)**: In `logRaftCommunication` (`transport.go:467`), after `r.Unmarshal(e.Data)` for `raftpb.MsgProp`, the code unconditionally evaluates `zap.Uint64("req-id", r.Header.ID)` without checking `if r.Header != nil`. Any `MsgProp` entry whose `InternalRaftRequest` has `Header == nil` (e.g., v2/legacy/test proposals or malformed messages) crashes the transport goroutine with `SIGSEGV`.
   - In our formal specification (`Spec/go_etcd_io/etcd/server/v3/etcdserver/api/rafthttp/logRaftCommunication.lean`), proving `logRaftCommunication` required explicit non-null preconditions `⌜lg ≠ null⌝` and `⌜hdr ≠ null⌝` for every `MsgProp` entry.

3. **[MEDIUM/HIGH — Production Log Storm] Every Internal Background Raft Proposal Logs a Spurious `WARN` (`server/etcdserver/v3_server.go:1069–1072`)**:
   - In `processInternalRaftRequestOnce`:
     ```go
     requestID := requestid.FromContext(ctx)
     if requestID == 0 {
         lg.Warn("RequestID not set in context when proposing, generating a new one")
         requestID = s.RequestID()
     }
     ```
   - All internal server proposals that do not originate from a unary gRPC interceptor—including `publishV3` (`server.go:1592`), `LeaseCheckpoint` (`server.go:1232`), corruption alarms (`corrupt.go:258`), `DowngradeEnable` (`server.go:2405`), and streaming RPCs (`Watch`, `LeaseKeepAlive`)—pass `s.ctx` or `context.Background()`, where `requestid.FromContext(ctx) == 0`. Every such internal proposal now emits a spurious `WARN` log in production.

4. **[MEDIUM — Concurrency & Nil-Logger Hazard] Unconditional `s.Logger()` (`lgMu.RLock()`) on Every `LinearizableReadNotify` & `processInternalRaftRequestOnce`, and Removal of `if lg != nil` in `newLogUnaryInterceptor` (`read/read.go:89`, `v3_server.go:1066`, `v3rpc/interceptor.go:84`)**:
   - `LinearizableReadNotify` (`read/read.go:89`) and `processInternalRaftRequestOnce` (`v3_server.go:1066`) now acquire `s.lgMu.RLock()` via `s.Logger()` on every read and write request even when debug logging is disabled.
   - `newLogUnaryInterceptor` (`v3rpc/interceptor.go:84`) removed the existing `if lg != nil` guard and calls `lg.Core().Enabled(zap.DebugLevel)` unconditionally, which panics if `s.Logger()` is ever `nil`.

5. **[MEDIUM — Protobuf v2 Interface Mismatch & Duplicate Zap Key] Dead `Sizer` Type Assertion and Duplicate `"size"` Field in `logUnaryResponseStats` (`server/etcdserver/api/v3rpc/interceptor.go:115–201`)**:
   - `interceptor.go:115–121` defines `type Sizer interface { Size() int }` and `type ProtoSizer interface { ProtoSize() int }`, checking `Sizer` first. Because etcd's `etcdserverpb` messages use `google.golang.org/protobuf` (protobuf v2) with `marshaler`/`unmarshaler`/`sizer` disabled (`goproto_size_all = false`), `*pb.RangeResponse` and `*pb.PutResponse` only implement `ProtoSize() int`, never `Size() int`.
   - `logUnaryResponseStats` (`interceptor.go:130–137`) adds `zap.Int("size", size)` to `fields` and then appends `getRangeResponseStatFields(_resp)` (`interceptor.go:200`), which appends a **second** `zap.Int("size", size)` field with the same key `"size"`, producing duplicate `"size"` keys in JSON logs.

### 2.2 Key Specification and Proof Insights

1. **Modeling `requestid` in `context.Context` and Single-Use `idFresh` (`InvContext.lean`, `InvProposer.lean`)**:
   - We defined `requestid.ctxReqIDIs (ctx : GoInterfaceOk) (o : Option w64)` in [`Proof/context/InvContext.lean`](file:///shared/etcd-grove-pr/etcd-21401/Proof/context/InvContext.lean) and proved `requestid.FromContext` ([`Proof/go_etcd_io/etcd/server/v3/etcdserver/requestid/FromContext.lean`](file:///shared/etcd-grove-pr/etcd-21401/Proof/go_etcd_io/etcd/server/v3/etcdserver/requestid/FromContext.lean)) and `requestid.NewContext` ([`Proof/go_etcd_io/etcd/server/v3/etcdserver/requestid/NewContext.lean`](file:///shared/etcd-grove-pr/etcd-21401/Proof/go_etcd_io/etcd/server/v3/etcdserver/requestid/NewContext.lean)).
   - We also proved `traceutil.ctxReqIdStrIs_of_reqID` showing that `traceutil.New`'s `ctx.Value("requestID")` (which looks up a `go.string` key `"requestID"`, whereas `requestid.NewContext` uses `requestid.requestIDKey("requestID")` of named type `requestid.requestIDKey`) never collides with `requestid.requestIDKey` and returns `nil` on standard gRPC contexts (`grpcRunCtx`).
   - In [`Proof/go_etcd_io/etcd/server/v3/etcdserver/InvProposer.lean`](file:///shared/etcd-grove-pr/etcd-21401/Proof/go_etcd_io/etcd/server/v3/etcdserver/InvProposer.lean), we defined:
     ```lean
     def reqIdForAt (γi : IdNames) (o : Option w64) : IProp GF :=
       iprop(idCred γi 1 ∗
         match o with
         | none => True
         | some id => if id = W64 0 then True else idFresh γi id)

     def reqIdCtxAt (γi : IdNames) (ctx : GoInterfaceOk) : IProp GF :=
       iprop(∃ o : Option w64, requestid.ctxReqIDIs ctx o ∗ reqIdForAt γi o)
     ```
   - `newLogUnaryInterceptor` ([`Proof/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/newLogUnaryInterceptor.lean`](file:///shared/etcd-grove-pr/etcd-21401/Proof/go_etcd_io/etcd/server/v3/etcdserver/api/v3rpc/newLogUnaryInterceptor.lean)) calls `s.RequestID()` (which consumes `idCred γi 1` to produce `∃ id, idFresh γi id`, including `id ≠ 0` from `idGen`'s non-zero counter invariant) and `requestid.NewContext(ctx, requestID)` to establish `reqIdCtxAt γi ci'` for the downstream handler.
   - `processInternalRaftRequestOnce` ([`Proof/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__processInternalRaftRequestOnce.lean`](file:///shared/etcd-grove-pr/etcd-21401/Proof/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__processInternalRaftRequestOnce.lean)) consumes `reqIdCtx ρ ctx`:
     - When `o = some id` with `id ≠ 0`, `requestid.FromContext(ctx)` returns `id`, and the proof consumes the linear `idFresh ρ.ids id` to claim `id` in `srvPropMint` and register `id` with `s.w.Register(id)`.
     - When `o = none` or `some 0`, `requestid.FromContext(ctx)` returns `0`, and the `if requestID == 0` branch logs the warning and calls `s.RequestID()` using `idCred ρ.ids 1` to obtain a fresh `idFresh ρ.ids id`.
   - Because `idFresh ρ.ids id` is linear (not persistent), `reqIdCtx ρ ctx` **cannot** be duplicated to satisfy two calls to `processInternalRaftRequestOnce` on the same `ctx` when `o = some id` (`id ≠ 0`). This directly Pinpoints **Bug 1**.

## 3. Detailed Bug Analysis & Reproduction

All reproduction tests and logs are committed in [`notes/pr-verify/etcd-21401/`](./etcd-21401/):
- [`notes/pr-verify/etcd-21401/repro_test.go`](./etcd-21401/repro_test.go)

### Bug 1 (HIGH): Request ID Reuse Across Multiple Raft Proposals on the Same `ctx`

- **Location**: `server/etcdserver/v3_server.go:1067–1077`, `server/etcdserver/api/v3rpc/interceptor.go:82–83`
- **Mechanism**:
  ```go
  // server/etcdserver/api/v3rpc/interceptor.go:82-83
  requestID := s.RequestID()
  ctx = requestid.NewContext(ctx, requestID)
  ```
  ```go
  // server/etcdserver/v3_server.go:1067-1077
  requestID := requestid.FromContext(ctx)
  if requestID == 0 {
      lg.Warn("RequestID not set in context when proposing, generating a new one")
      requestID = s.RequestID()
  }
  ...
  r.Header = &pb.RequestHeader{
      ID: requestID,
      ...
  }
  ...
  ch := s.w.Register(requestID)
  ```
- **Callers Performing Multiple Proposals on the Same `ctx`**:
  1. `EtcdServer.Authenticate(ctx context.Context, r *pb.AuthenticateRequest)` (`server/etcdserver/v3_server.go:853–887`):
     ```go
     for {
         checkedRevision, err = s.AuthStore().CheckPassword(r.Name, r.Password)
         ...
         resp, err = s.raftRequest(ctx, &pb.InternalRaftRequest{Authenticate: internalReq})
         if err != nil {
             return nil, err
         }
         if checkedRevision == s.AuthStore().Revision() {
             break
         }
         lg.Info("revision when password checked became stale; retrying")
     }
     ```
  2. `v3lock.lockServer.Lock(ctx, req)` (`server/etcdserver/api/v3lock/lock.go:35–50`) and `v3election.electionServer.Campaign(ctx, req)` (`server/etcdserver/api/v3election/election.go:40–92`): registered on the same `*grpc.Server` (`server/embed/serve.go:148–150, 184–186`) with `newLogUnaryInterceptor` and calling `v3client.New(s)` (`server/etcdserver/api/v3client/v3client.go:30–52`) in-process on `ctx`, executing multiple Raft proposals (`Txn` for `waitDeletes` and `Proclaim`, `DeleteRange` for `Unlock`/`Resign`) with the same `requestID` (see `TestReproBug1C_V3ElectionCampaignResignTypeAssertionPanic`).
  3. `quotaAlarmer.check(ctx context.Context, r any)` (`server/etcdserver/api/v3rpc/quota.go:40–51`): calls `qa.s.Alarm(ctx, ar)` -> `s.raftRequest(ctx, ...)` using the unary RPC's `ctx`.
  4. Any caller that retries a proposal on a child context `ctx2, cancel := context.WithTimeout(ctx, ...)` after a local timeout, because `ctx2.Value(requestIDKey)` delegates to parent `ctx` and returns the same `requestID`!
- **Recommended Fix**:
  - Do **not** use the gRPC context's logging `requestID` as the `wait.Wait` channel registration ID (`r.Header.ID`), **or** generate a distinct proposal ID `propID := s.reqIDGen.Next()` per Raft proposal while logging both `req-id` (from `ctx`) and `prop-id` (in `r.Header.ID`).

### Bug 2 (HIGH): Nil-Pointer Dereferences (`SIGSEGV`) in `rafthttp.logRaftCommunication`

- **Location**: `server/etcdserver/api/rafthttp/transport.go:458–493`, `pipeline.go:100`, `stream.go:209, 505`
- **Mechanism**:
  1. `logRaftCommunication` does not check `if lg == nil { return }` before calling `lg.Debug(...)` (`transport.go:459`), and `pipeline.go:100` / `stream.go:209, 505` dereference `p.tr.Logger` / `w.tr.Logger` / `cr.tr.Logger` when `tr` or `tr.Logger` can be `nil` in tests or partial initialization.
  2. In `transport.go:462–468`:
     ```go
     if m.Type == raftpb.MsgProp {
         for _, e := range m.Entries {
             var r pb.InternalRaftRequest
             if err := r.Unmarshal(e.Data); err == nil {
                 lg.Debug("MsgProp raft message",
                     zap.Uint64("req-id", r.Header.ID),
                 )
             }
         }
     }
     ```
     `r.Header` is a pointer (`*pb.RequestHeader`) and is `nil` whenever the marshaled `InternalRaftRequest` had no `Header` populated. Dereferencing `r.Header.ID` panics with `SIGSEGV`.
- **Reproduction (`go test ./etcdserver/api/rafthttp -run TestSendMessage`)**:
  ```text
  === RUN   TestSendMessage
  panic: runtime error: invalid memory address or nil pointer dereference
  [signal SIGSEGV: segmentation violation code=0x1 addr=0x0 pc=0xb1f12d]

  goroutine 62 [running]:
  go.uber.org/zap.(*Logger).Core(...)
  go.etcd.io/etcd/server/v3/etcdserver/api/rafthttp.logRaftCommunication(0x0, 0x1, 0x52837e8c340, 0x2, {0xbb25a2, 0x4})
  	/root/etcd-pr/etcd-21401/server/etcdserver/api/rafthttp/transport.go:459 +0x4d
  go.etcd.io/etcd/server/v3/etcdserver/api/rafthttp.(*streamWriter).run(0x52837c95600)
  	/root/etcd-pr/etcd-21401/server/etcdserver/api/rafthttp/stream.go:209 +0x11ff
  ```
- **Recommended Fix**:
  - Guard `if lg == nil || !lg.Core().Enabled(zap.DebugLevel) { return }` at the top of `logRaftCommunication`, guard `if p.tr != nil` / `if w.tr != nil` / `if cr.tr != nil` at call sites, and guard `if r.Header != nil` before accessing `r.Header.ID`.

### Bug 3 (MEDIUM/HIGH): Spurious `WARN` Log on Every Internal Raft Proposal

- **Location**: `server/etcdserver/v3_server.go:1069–1072`
- **Mechanism**: Internal server proposals (`publishV3`, `LeaseCheckpoint`, `corrupt.go` alarms, `DowngradeEnable`, `LinearizableReadNotify` via `s.ctx`, streaming `Watch`/`LeaseKeepAlive` RPCs) do not go through `newLogUnaryInterceptor`, so `requestid.FromContext(ctx)` is always `0`, emitting `lg.Warn("RequestID not set in context when proposing, generating a new one")` on every call.
- **Recommended Fix**: Remove the `lg.Warn(...)` or downgrade it to `lg.Debug(...)` (or attach a request ID in internal callers).

### Bug 4 (MEDIUM): Unconditional `s.Logger()` RLock Contention and Removed `if lg != nil` Guard

- **Location**: `server/etcdserver/read/read.go:89`, `server/etcdserver/v3_server.go:1066`, `server/etcdserver/api/v3rpc/interceptor.go:84`
- **Recommended Fix**: Restore `if lg != nil` in `newLogUnaryInterceptor` (`debug := lg != nil && lg.Core().Enabled(zap.DebugLevel)`), and avoid calling `s.Logger()` on every read/proposal hot path when not needed.

### Bug 5 (MEDIUM): Dead `Sizer` Type Assertion Under Protobuf v2 & Duplicate `"size"` Zap Field

- **Location**: `server/etcdserver/api/v3rpc/interceptor.go:115–137, 197–202`
- **Recommended Fix**: Remove the redundant `zap.Int("size", size)` from `getRangeResponseStatFields` (since `logUnaryResponseStats` already logs `zap.Int("size", size)` for all responses), and use `proto.Size` / `ProtoSizer`.
