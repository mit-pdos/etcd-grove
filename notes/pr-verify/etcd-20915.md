## Verdict

#22261's verdict assumed a `v`-prefixed build, and this PR makes every scripted build one:
- `scripts/build_lib.sh` now injects `-X .../api/v3/version.Version=$VERSION`;
- `$VERSION` defaults to `git describe --always --dirty --tags --match='v*' --abbrev=14`, e.g.
  `v3.8.0-alpha.0-236-gb7e2d97fc251f8` at the PR head.

So `VersionForPeer` (proved, no `sorry`) is no longer a no-op. #22261's finding 1 applies to real
builds: after a peer is downgraded to 3.7, the stale per-peer cache keeps sending it `v3.8.0`, and
every request to it fails.

The build change adds a bug of its own (finding A). The script falls back to a value that is not
a semantic version, and etcd built that way panics within seconds of starting. Without reachable
`v*` tags, `$VERSION` is the bare commit hash. Without `.git`, it is `GitNotFound`. Before the PR,
the same builds kept the source constant `3.8.0-alpha.0` and worked.

## Findings

**A. Builds without a `v*` tag panic at startup. Bug in the PR (its build scripts); medium.**
- **The cause**: `scripts/build_lib.sh` and `scripts/build-binary.sh` now set `version.Version`
  from `git describe --always ... || echo "GitNotFound"`. When no `v*` tag is reachable,
  `--always` returns the abbreviated commit hash (`b7e2d97fc251f8`). Without git metadata, the
  fallback is `GitNotFound`.
- **When that happens**: a source tarball, a shallow or `--no-tags` clone (common in CI), or a
  fork without upstream tags.
- **What breaks**: neither value parses as a semantic version. The server's
  `semver.MustParse(version.Version)` calls assume it does. There are seven of them, in
  `etcdserver/version/monitor.go:159`, `storage/schema/schema.go:47`, `membership/cluster.go`,
  `rafthttp/stream.go` and `util.go`, and `cluster_util.go`. Until now that held, because
  `Version` was a source constant.
- **Reproduced**: by `notes/pr-verify/etcd-20915/build-without-tags.sh`, output in
  `build-without-tags.log`. Both PR-head builds exit 2 within seconds of starting, with
  `panic: invalid semantic version` from `(*Monitor).membersMinimalServerVersion`. The base's
  tarball build reports `3.8.0-alpha.0` and keeps serving.
- **Fix**: fall back to the source constant (do not inject `-X ...version.Version` when `$VERSION`
  is not of the form `v<major>.<minor>.<patch>...`), or validate it in the script.
- **The release path**: `build-release.sh`, which `cloudbuild.yaml` runs, uses
  `git describe --tags --always --dirty` without `--match`. Under `set -e`, it fails outright
  without git. Whether Cloud Build gets the tags was not checked; the PR reports one successful
  build.

**B. #22261's finding 1 is live with this PR. Medium.** It no longer needs a hypothetical
`v`-prefixed build: every scripted build is one, release builds included (`v3.8.0`).
- **Reproduced**: #22261's `peer_version_downgrade_test.go`, run at this head, fails as at
  #22261's (`notes/pr-verify/etcd-20915/peer_version_downgrade_test.log`).
- **Fix**: the one suggested there. Always send `strings.TrimPrefix(version.Version, "v")`, and
  drop the cache.

**C. #22261's finding 5 is live too.** The `v`-prefixed version also reaches v3.7 members through
the `/version` endpoint. There, release-3.7's version monitor fails to parse it and skips
cluster-version updates during the mixed-version period. It degrades; nothing crashes.

**Not repeated here**: #22261's findings 2 (the race in `removePeer`), 3 (the tests compare
`VersionForPeer` with itself) and 4 (documentation nits). They apply unchanged.

**Existing code**: no bug in the pinned code; nothing added to `issues/`. Finding A breaks an
invariant that the existing code relies on but does not document: `version.Version` parses. It is
not a bug in that code.

**Reviewer**: none started. The Go changes are #22261's, whose specs and proofs a reviewer
already checked. The new finding A is a build-script fact shown by running it.
