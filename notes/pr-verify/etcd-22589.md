## Verdict

The PR does what it says, as far as verified: with it, `Downgrade` (all three actions) cannot
panic on a nil cluster version, at any of the reads, under any interleaving (every read of the
cluster version is modelled as possibly `nil`, independently of the others). A nil version makes
the manager's `DowngradeValidate` return `ErrClusterVersionUnavailable` and, through it,
`DowngradeEnable` propose nothing; a malformed target still gets `ErrWrongDowngradeVersionFormat`
before anything else; `downgradeCancel` with a nil version returns `ErrClusterVersionUnavailable`
and proposes nothing. All proofs are complete (no `sorry`); they rest on five new trust-boundary
axioms for names-only callees (semver, `convertToClusterVersion`) and two contracts of the
server (`s.Version()`'s adapter, `s.ClusterVersion()`), stated as premises.

Not covered: the PR's claim "no cluster version means no downgrade can be in flight" (the
cluster's state is not modelled); the gRPC layer above `Downgrade`. Two things to tell the
author: `downgradeCancel` still reports success when the cancel fails (pre-existing, not the
PR's: `issues/etcd-downgrade-cancel-error-dropped.md`), and the PR's handler-level cancel test
does not exercise the crash it guards against (Findings).

### The specs

Vocabulary: `Proof/go_etcd_io/etcd/server/v3/etcdserver/version/Base.lean` (the manager's side)
and `Proof/go_etcd_io/etcd/server/v3/etcdserver/BaseDowngrade.lean` (the server's).

- **The manager's `Server`** (`version.isServer vs RE CVR EP CP`): `LinearizableReadNotify`'s
  error satisfies `RE`, `GetClusterVersion`'s result `CVR`, `GetDowngradeInfo` returns a non-nil
  copy the caller owns, `DowngradeEnable` consumes `EP` and needs a non-nil target,
  `DowngradeCancel` consumes `CP`. `EP`/`CP` are proposal rights: a postcondition that gives one
  back says nothing was proposed. The predicates are the caller's; the server instantiates `RE` trivially, `CVR` as
  `srvCVR γcv` (nil, or non-nil with `clusterVersionOk`'s witness) and `EP`, `CP` as the
  handler premise's (`srvVersionOk`); the PR's mock as "read succeeds" and "version is nil".
- `version.Manager.DowngradeValidate`
  (`Spec/go_etcd_io/etcd/server/v3/etcdserver/version/Manager__DowngradeValidate.lean`): for a
  non-nil target, returns `version.validateOutcome RE CVR err`: the read's error; or the read
  succeeded and the version was `nil`, `ErrClusterVersionUnavailable`; or it was non-nil and
  `ErrInvalidDowngradeTargetVersion`, `ErrDowngradeInProcess` or `nil`. Old behaviour: a nil
  version panics.
- `version.Manager.DowngradeEnable` (`.../Manager__DowngradeEnable.lean`): validation failed
  (its non-nil error, `EP` back) or the enable was proposed after a successful read saw a non-nil
  version.
- `version.Manager.DowngradeCancel` (`.../Manager__DowngradeCancel.lean`): the read's error or
  `ErrNoInflightDowngrade` with `CP` back, or the cancel was proposed.
- `version.allowedDowngradeVersion` (`.../allowedDowngradeVersion.lean`): a non-nil version in, a
  non-nil version out.
- `EtcdServer.downgradeEnable` (`Spec/go_etcd_io/etcd/server/v3/etcdserver/EtcdServer__downgradeEnable.lean`,
  `dgEnablePost`): unconvertible target, `ErrWrongDowngradeVersionFormat` with `EP` back; manager
  validation failed, its error with `EP` back; proposed and failed, its error; else a response
  and `nil` (the response's version read cannot be nil once the manager's was not: `srvCVR`). Old: the response's `String()` panics on a nil
  version (only reachable after the manager's own read, which panicked first).
- `EtcdServer.downgradeCancel` (`.../EtcdServer__downgradeCancel.lean`, `dgCancelPost`): a nil
  version gives `ErrClusterVersionUnavailable` with `CP` back; otherwise a response and `nil`,
  whatever the cancel returned. Old: after the cancel attempt, `String()` of a nil version panics.
- `EtcdServer.downgradeValidate` (`.../EtcdServer__downgradeValidate.lean`, `dgValidatePost`):
  unconvertible target first, then `ErrClusterVersionUnavailable` (its own guard or the manager's),
  then the manager's errors, else a response. It holds neither proposal right, so it
  proposes nothing.
- `EtcdServer.Downgrade` (`.../EtcdServer__Downgrade.lean`): dispatches on `r.Action`: 0/1/2 to the
  three posts above (validate keeps both rights, enable keeps `CP`, cancel keeps `EP`), else
  `ErrUnknownMethod`.
- **The PR's manager test as theorems** (`Proof/go_etcd_io/etcd/server/v3/etcdserver/version/Results.lean`):
  `version.validate_nilClusterVersion` and `version.enable_nilClusterVersion`: over a server whose
  read succeeds and whose version is `nil`, `ErrClusterVersionUnavailable`, and the enable gives
  `EP` back.

   manager-level `TestDowngradeValidateNilClusterVersion` does hit the real path
   (`allowedDowngradeVersion`).

   `GetDowngradeInfo()` must not be nil (`DowngradeValidate` checks, `DowngradeCancel` does not;
   `issues/etcd-version-manager-cancel-nil-downgradeinfo.md`). Unreachable with etcd's adapter.
4. **The bug the PR fixes** is recorded as `issues/etcd-downgrade-nil-cluster-version.md`
   (from `pr-verify/etcd-22575`; known upstream, #22574); the proofs confirm the fix.
5. **Pre-existing, from `pr-verify/etcd-22575`:** `allowedDowngradeVersion` wraps at x.0
   (`issues/etcd-downgrade-target-minor-underflow.md`); the PR does not touch it, and the spec here
   (non-nil in, non-nil out) does not exclude it.

## Review

A fresh reviewer subagent audited the specs, postulates and contracts against the Go code
(semver v3.5.0, the adapter, membership) and looked for failing interleavings. Resolved:

- **"Nothing proposed" was vacuous at the handler level.** `srvVersionOk` quantified the
  proposal rights inside the contract (`□ ∀ EP CP`), so a handler's proof could pick its own and
  give the caller's back. Now the rights are parameters of the premise
  (`srvDowngradeOk s l EP CP`, `srvVersionOk s γcv EP CP`): a handler can propose only by
  spending the caller's `EP`/`CP`, and `downgradeValidate`, which holds neither, provably proposes
  nothing.
- **The handler specs allowed an enable committed and answered with
  `ErrClusterVersionUnavailable`.** The adapter's cluster-version reads now share
  `clusterVersionOk`'s ghost witness (`srvCVR γcv`: both read `s.cluster.Version()`), so after
  the manager saw a version, the response's read is non-nil (`known = true`) and the PR's second
  guard in `downgradeEnable` is dead code. This uses `clusterVersionOk`'s monotonicity (the version
  never returns to `nil` once set), the premise `start` already rests on.

Open (recorded, not changed):

- **`downgradeCancel` checks the local cluster version before the linearizable read** (minor,
  not reproduced). The PR's comment "no cluster version means no downgrade can be in flight" holds
  for the member's applied state (a downgrade is enabled only after a version is set, applied in
  log order), not cluster-wide: a member whose applied state lags behind both entries refuses the
  cancel, where the manager would have caught up through the read. The answer is a retryable
  `FailedPrecondition`, never a wrong success. Reading the version for the response after the
  cancel (nil-guarded) would avoid it.
- **`TestDowngradeEnableMalformedTargetNilClusterVersion` passes at the base too**: it pins the
  error precedence but is not a regression test.
- `downgradeValidate` (unchanged) reads the version for the response before the manager's
  linearizable read, so the two may differ; the PR's cancel follows the same pattern.

Checked and found fine by the reviewer: the semver postulates (`New` never nil; `Major`, `Minor`,
`String` value receivers, so they need a non-nil pointer; `Equal` nil-safe), the
`convertToClusterVersion` postulate (deterministic, so the opaque predicate is consistent), the
adapter's `GetDowngradeInfo` (a fresh non-nil copy), the unlocked read of `s.lg`, the independent
nil-possible model of each cluster-version read, the mapping of `ErrClusterVersionUnavailable` to
`FailedPrecondition` (`v3rpc/util.go:65`), and that no post allows `(nil, nil)`
(`maintenanceServer.Downgrade` writes `resp.Header`).

## Comparison with etcd-io/etcd#22575

The same bug, a competing fix, verified on branch `pr-verify/etcd-22575`
(`notes/pr-verify/etcd-22575.md`). Both are sound: with either, `Downgrade` cannot panic on a nil
cluster version. Differences:

- **Where the guard is.** #22575 guards only the two handlers, before anything else; #22589 guards
  the manager's `DowngradeValidate` too, so every caller of the manager is safe (today the
  handlers are its only callers), and keeps the handler guard of `downgradeEnable` after the
  enable (dead code under the monotone version, above).
- **Error precedence.** #22575's `ENABLE` checks the version before parsing the target, so a
  malformed target with an undecided version gets `ErrClusterVersionUnavailable`; #22589 keeps
  `ErrWrongDowngradeVersionFormat` first (`dgEnablePost`'s first disjunct), as `VALIDATE` does.
- **Tests.** #22575 adds none; #22589 adds three, of which only the manager-level one reproduces
  the crash (Findings).
- **Both keep** the cancel's error dropped (`issues/etcd-downgrade-cancel-error-dropped.md`) and
  the x.0 underflow of `allowedDowngradeVersion` (`issues/etcd-downgrade-target-minor-underflow.md`,
  found on that branch).

The two branches specify the same functions independently (same file paths, different specs:
#22575's states safety and the answer's shape over its own contracts; this one adds the proposal
rights and the PR's test as theorems) and each adds the same five semver/`convertToClusterVersion`
names, so at most one can be merged into `lean` as is. #22575's branch proves
`convertToClusterVersion` from a `semver.NewVersion` postulate, where this branch postulates it;
it also generalises `etc/gen-link.py` (two-component names, `semver_v3_New`) where this branch adds
a one-entry `QUAL_OVERRIDE`. The issue files are shared: this branch takes #22575's three verbatim
(their names, `etcd-downgrade-nil-cluster-version`, `etcd-downgrade-cancel-error-dropped`,
`etcd-downgrade-target-minor-underflow`) and adds only
`issues/etcd-version-manager-cancel-nil-downgradeinfo.md`; this branch's integration test of the
dropped cancel error (`notes/pr-verify/etcd-22589/tests/integration/v3_downgrade_cancel_test.go`)
is a second reproduction of the shared issue.
