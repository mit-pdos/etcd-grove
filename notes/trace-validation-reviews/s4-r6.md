### F1. P2 (no compaction, so no snapshot) has no channel into raft

**The claim.**
- "Layer B's other premises enter through the API ... the configuration ..., no `ProposeConfChange` (P3) and no `RestartNode` (P1) with a logger; each `StartNode` takes its node's `simNode` ... (P4)" (sim note, lines 479-483).
- The plan's Q6 (4) gives the same list.
- P2 is "discharged by layer D" (line 352).

**The evidence.**
- `MsgSnap` is traced as a `SendAppendEntriesRequest` (`state_trace.go:303-304`) and as a receive (`:325`). Gap 3 says the specification cannot follow it, so the send hook in `maybeSendSnapshot` (`raft.go:629`, `:647`, `:664`) has an obligation raft cannot meet.
- Raft reaches `maybeSendSnapshot` whenever the storage reports `ErrCompacted`.
- Compaction is the client's choice:
  - `MemoryStorage.Compact.spec` needs only `memStorAt`, a snapshot lower bound and the log or `memCompacted` (`interface/.../MemoryStorage__Compact.txt`);
  - `StartNode` hands the storage's protocol to the client (`restartStorage γ si … F K`);
  - `concurrent.go:332-336` itself compacts when `SnapshotEvery > 0`. `DefaultCConfig` has 0, so `Main` meets P2, but raft cannot see that.
- Round 5's A2 argument applies unchanged: raft's proof uses P2 at a hook, so P2 must reach raft through a resource. Layer D can only supply what the API takes.

**Who it affects.**
- The send hooks of `sendAppend`/`maybeSendSnapshot`.
- Q6 as put to the user.
- Layer D.

**Repair.**
- Add P2 to the gated premises and to Q6 (4). With a logger, the storage's compaction must need a permit that the allocation never hands out. One option is a gated conjunct in `restartStorage`'s protocol: the "compacted past" authority held by `simInv`. Another is a scope restriction that `StartNode` with a logger takes the storage's compaction right and never returns it.
- State it as a marked scope restriction, like P1.
- Re-check every premise P1-P9 for its channel. Today:
  - P6 and P8 come from the tokens;
  - P9 from F2's mechanism;
  - P3, P1, P4 and the configuration half of P5/P7 from the listed gates;
  - P2 from nothing;
  - P7's read-index and transfer half from nothing (S4).

### F2. "`Step` takes a token above the frontier" is not a premise a client can establish, and the clause that makes it exclude gap 6 is missing

**The claim.** "`simInv` keeps per link the frontier of what was received, and `Step` takes a token above the frontier, which the FIFO harness proves (Q5 (a))" (lines 474-478). Q6 (4) adds "each message token's position on its link".

**The evidence.**
1. **The premise is not stable.**
   - The frontier is an authoritative value in `simInv` that grows at every receipt on the link. "Position `p` above the frontier" is an upper bound on a growing value, which is never persistent.
   - At `Node.Step`'s call, the client could assert it only through an exclusive fragment that pins the frontier, and nothing in the list gives one.
   - Raft cannot prove it at `raft.Step`'s entry (`node.go:394-399`) from a premise checked at `Node.Step` (`node.go:514-523`). In between, any other holder of a later token on the same link may have stepped it.
   - The FIFO harness knows its delivery goroutine is the link's only stepper, but raft's spec does not. "The FIFO harness proves" needs an API resource that carries that exclusivity.
   - The hand-off adds a subtlety. `Node.Step` returns once the run loop has taken `m` (unbuffered `recvc`), before `raft.Step(m)` moves the frontier. So the resource must be passed on at the hand-off, not at the step.
2. **The clause that turns the frontier into a refusal is not stated.** The stale-`MsgVote` case needs all of:
   - (a) a persistent per-term record: `c`'s `MsgVote(T)` to `i` was handed out at a position below every term-`T` append or heartbeat from `c` to `i`. `campaign` sends it to every other voter (`raft.go:1058-1077`), and `c` hands it out at its campaign `Ready`, before it can lead.
   - (b) a node-local clause of `i`: "`s.lead = c` in term `T` with `s.vote = None` ⇒ frontier(`c→i`) is past that position". `σ` has no `lead`, so this is a `simNode i` clause, set at the receipt that set `lead`.

   Round 5 proposed (b). Revision 6 does not have it, and the frontier alone excludes nothing.

**Who it affects.**
- `Node.Step`'s increment-2 spec, which is unprovable as stated.
- Q6 (4).
- The FIFO harness's proof in layer D.

**Repair.** State the mechanism and add its resource to Q6. Option (i) is the simplest:
- (i) **An exclusive per-link cursor** `linkCur γt (c,i) f`, allocated with `γt` and owned by the client (the link's delivery goroutine).
  - `Node.Step` takes `inFlight` at position `p > f` with `linkCur … f`.
  - It returns `linkCur … p` on success, and `linkCur … f` with the token on a timeout or stop.
  - `simInv` keeps frontier `≤` cursor.
  - The run loop's `recvc` protocol carries "`p` above the frontier" from the hand-off to `raft.Step`. Raft's run loop steps the message it took before it takes another.

  Drops just skip positions.
- (ii) **Or a drop law** `inFlight p ==∗ dropped p` (persistent), with `Node.Step` taking `p` and witnesses that every lower position on the link was handed off or dropped. This replaces "a dropped message's token is thrown away" (line 157).

In either case, add the clauses (a) and (b) above to the table of `simInv`/`simNode` clauses.

## Second tier

### S1. B4's "to check", resolved: tickets carry a forwarded proposal only in a non-`dup` cluster and only for a non-filler entry

**The claim.** "a forwarded `MsgProp` needs nothing more if raft's per-proposal tickets (`entTk`, `stTks`) already carry it to the leader's append (to check)" (lines 484-487). B3's log bound relies on the same: "each proposal's entry is appended once".

**The evidence.**
- Tickets are consumed at the append (`propTk_set`, `Ghost.lean:1233`), but with two exceptions.
- **`dup` clusters.** In a `γ.dup = true` cluster the ticket is persistent and never consumed (`Ghost.lean:403-409`, `:1199-1207`). The cluster's `dup` is the client's choice (`Cluster.dup`).
- **Filler entries.** `entTk` is `emp` for a `Filler` (`Ghost.lean:1353-1355`), and `Filler ty d := d = [] ∧ (ty = 0 ∨ ty = 2)` (`:1171`).
  - So `node.Propose` with empty data, which its spec allows (`interface/.../node__Propose.txt`), yields a `MsgProp` whose `msgCredits` is `emp`.
  - A client holding the persistent `sentMsg` and a clone (as `concurrent.go:283` clones) can step it any number of times. Each copy reaching a leader is appended.
  - With a budget taken only at `Propose`, "entries appended this term `≤` credits `+ 1`" (P5) then fails.

**Repair.** Either:
- (a) add to the gate `γ.dup = false` and, with a logger, `data ≠ []` at `Propose`; `Main` proposes `"v"+k`, which is non-empty; or
- (b) take the note's alternative: the credit travels with the forwarded `MsgProp`. That covers both cases.

Record the choice in Q6 (2) and delete "(to check)".

### S2. B1's copy: the clause's domain and its tie to the commit quorums are unstated, and the obvious reading is not maintainable

**The claim.** "a per-server copy of raft's `histsOk` ... refreshed at `j`'s hooks (every acknowledgement leaves through a traced `MsgAppResp` send, whose hook fires first)" (lines 300-308). Table row: "`j`'s acknowledgements' histories | raft's `histsOk` of `j` ..., copied at `j`'s hooks".

**The evidence.**
- **Why the obvious reading fails.** A `simInv` clause "for every `isAcked γ j t i`, `hist γ (σ.s j's log) t i B`" quantifies over a persistent fact that raft's ghost makes true outside any hook.
  - The ack is inserted by the step's ghost update (`StepGhost.lean:562` `ack_invs_insert`, after the branch's `StepCD`), not inside a hook's atomic update.
  - From that point until `j`'s next hook, `simInv` would be false. Another node's hook that opens and closes `simInv` meanwhile cannot re-prove it.
  - I did not trace exactly where the ghost update runs relative to `send`'s hook: uncertain. The note's own "whose hook fires first" says the hook precedes the ack, which is the bad order for this reading.
- **What the copy has to be.** It must be keyed by a set `S_j` snapshotted at `j`'s hooks.
- **The missing tie.** Some clause must connect `S_j` to the acks a `QuorumLogInv` proof uses.
  - Raft's `cq` gives only `isAcked` (`Ghost.lean:3189`, `cqAt`), with no provenance.
  - Round 5's B1 suggested "tied to `isAcked` through the bag's responses"; revision 6 dropped it.

**Repair.**
- `simInv` holds, per `j`, a set `S_j` with `hist` of `σ.s j`'s log for each element.
- `S_j` is refreshed at `j`'s hooks, the receive line included, from the message's facts as line 343 says, and at the latest at the `Ready` line that hands out the response.
- Add a bag clause: every successful `MsgAppResp` handed out has `(term, matchIndex) ∈ S_src`, or `matchIndex ≤` the source's `commitIndex` (the `index ≤ commitIndex` reply).
- Prove `QuorumLogInv` at a `Commit` line from `σ.matchIndex[l]`'s quorum rather than from raft's `cq`:
  - each member `j` has `Match_j = 0` or `(T, Match_j) ∈ S_j`, which gives `hist`;
  - or `Match_j ≤ commit_j`, which gives `isCommitted`.
- A follower's commit inherits the property through a σ-level commit record. Either extend the commit-point clause to name the quorum, or carry the record with each request's commit, as the commit-point clause already does.
