## First tier

### F1. Every send and receive event fails the premise: `MsgEvOf` leaves `rejectHint` free (open from round 1)

**Evidence.**
- `TraceEv.NumsBelow` requires `uint.nat m.rejectHint < K` (`TraceSim.lean:186`), as
  `Event.Bounded` does (`Rep.lean:201`).
- `MsgEvOf` (`TracedCap.lean:119-122`) fixes `typ, term, frm, to, entries, logTerm, index, commit,
  reject`, and not `rejectHint`.
- So `SendEvOf evt id s c m e` holds for an `e` whose message has any `rejectHint`, including
  `2^64-1`. Hence `∀ e, SendEvOf … e → TraceEv.Ok n e` is false whenever the hook logs.
- Go writes the field: `RejectHint: m.GetRejectHint()` (`state_trace.go:158`), and `absMsg` carries
  it as `Msg.rejecthint` (`Defs.lean:189`).

**Callers affected.**
- `raft.send.tracedSpec`'s new premise (`TracedHooksDraft.lean:249-250`) cannot be discharged for any
  traced message type.
- The same holds for every use of `trCap_fire`, `_any` and `_booted` with `sendGate`'s predicate, and
  of `trCap_fire_recv` with `recvGate`'s (`TracedCap.lean:155-165`, also `SendEvOf`). That covers
  every send and receive line `raft.Step` will log.

**Repair.**
- Add `tm.rejectHint = m.rejecthint` to `MsgEvOf`. This changes `msgEvOf_traceMsgOf` in
  `TracedMsg.lean` and `msgEvOf_absMsg_from` in `raft__send.lean`.
- Add `sendEvOf_ok`, stated from the state's numbers and the message's `term`, `index`, `logterm`,
  `commit`, `rejecthint` and `entries.length`, each below `traceNumBound`. Its `InScope` part follows
  from `msgTypeStr m.ty ≠ "MsgSnap"` for the types `sendEvt` traces.

The plan records this as the re-freeze's blocker (`notes/trace-validation-plan.md:827-833`).
`TracedCap.lean:15` already calls the amendment "the re-freeze `trace-check-frozen-a1`", but that tag
does not exist (`git tag -l` shows only `trace-check-frozen`). Say "pending" there until F1 lands.

### F2. The bootstrap lines' `OkBoot` premise sits on a capability their callers cannot hold (pre-existing root; uncertain how the plan routes bootstrap)

**Evidence.**
- `trCapB … c …` holds `(elements c.incoming).Perm C ∧ id ∈ C` (`TracedCap.lean:719`), so it is
  `False` unless `c` is the whole cluster.
- `raft.becomeFollower.traced` (`TracedHooks.lean:410-419`) and `trCapB_hookGate_bf`
  (`TracedHooksGlobal.lean:1479-1486`) use one `c` for three things:
  - the raft struct (`ownRaftPhysCV c V`, whose tracker is `ownTrackerC c`, `InvRaftPhys.lean:1193`);
  - the event (`NodeEvOf (W64 2) id s c`, which logs `c`'s voters);
  - the capability.
- At the one unbooted `BecomeFollower` (`bootstrap.go:52`, `becomeFollower(1, None)`), raft's
  tracker is still empty: the `applyConfChange` calls come after it (`:78-80`), and `newRaft`
  restored an empty `ConfState`.
- So the `b = false` branch's precondition (`ownRaftPhysCV c` at the real tracker, `∗ trCapB … c …`)
  is unsatisfiable, and its new `OkBoot` conjunct is never used.

The same holds for the bootstrap `ApplyConfChange` lines: `CCEvOf id s c cn`, with `c` the old
configuration of 0 to |C|-1 voters. `traceInitState.tracedSpec`'s own docstring admits the empty
configuration (`TracedHooksDraft.lean:183-186`, "round 1's S5, open").

The amendment also proves `OkBoot` only at the event's own configuration:

- `nodeEvOf_okBoot` (`TracedCap.lean:335-341`) concludes `OkBoot (elements c.incoming).length`
  with `c` the event's configuration;
- there is no `CCEvOf` lemma, and an `ApplyConfChange`'s `newconf` has |c|+1 voters, more than its
  event's `c`.

So when the event's configuration and the capability's differ (all bootstrap lines), the provided
lemmas do not give the law's premise. There is also no `OkBoot`/`Ok` monotonicity law to bridge
the gap; only `confsWithin_mono` exists.

**Callers affected.** The `Bootstrap`/`newRaft` call sites: `InitState`, the bootstrap
`BecomeFollower`, and the `ApplyConfChange` lines through `trCap_fire_boot`. These are the only
users of `OkBoot`.

**Repair.**
1. Give the bootstrap hooks a capability whose configuration is not the struct's: separate `c`
   (event and struct) and `cC` (capability, `≡ C`) parameters in `trCapB_hookGate_bf` and
   `becomeFollower.traced`, or a bootstrap-only gate over `trCap_fire_boot`.
2. State the event lemmas at a free bound, as `nodeEvOf_confsWithin` already is: `nodeEvOf_okBoot n`
   with `(elements c.incoming).length ≤ n`.
3. Add `ccEvOf_okBoot n` with `(elements c.incoming).length ≤ n` and
   `(elements cn.incoming).length ≤ n`.
4. Add `TraceEv.Ok.mono`/`OkBoot.mono` in `n`.

Until (1) is done, say in `becomeFollower.traced`'s docstring that its `b = false` branch has no
real caller yet.

  bootstrap facts as one `∃ t, newTrace … = .ok t ∧ t.init = … ∧ …` and keep the `∃` once (round 1's
