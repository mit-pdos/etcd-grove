## First tier

### A. Every send and receive event fails the premise: `MsgEvOf` leaves `rejectHint` free (open since round 1)

**Evidence.**
- `TraceEv.NumsBelow` bounds `uint.nat m.rejectHint` (`TraceSim.lean:186`). `TraceEv.Ok` includes
  `NumsBelow` (`:196-197`).
- `MsgEvOf` (`TracedCap.lean:119-122`) fixes every `TraceMsg` field except `rejectHint` (and `vote`,
  which `SendEvOf` pins to some `decStr v`). So `SendEvOf evt id s c m e` holds for an `e` whose
  message's `rejectHint` is `2^64 - 1`.
- Therefore `∀ e, SendEvOf evt id s c mm e → TraceEv.Ok n e` is false whenever the gate is `some`.

**Callers affected.**
- `raft.send.tracedSpec`'s new premise (`TracedHooksDraft.lean:248-250`) cannot be discharged for
  any traced message type, so the traced `send` cannot be used.
- The same holds for `trCap_fire`, `_any` and `_booted` instantiated with `sendGate`'s predicate.
- It holds for `trCap_fire_recv` with `recvGate`'s (`TracedCap.lean:155-165`, also `SendEvOf`).
- Together that is every send and receive line `raft.Step` will log.

**Go and model.**
- Go writes the field: `makeTracingMessage` sets `RejectHint: m.GetRejectHint()`
  (`state_trace.go:158`).
- `traceMsgOf` records it (`TracedMsg.lean:50, 54`).
- `absMsgFrom` carries it as the abstract message's `rejecthint` (`Defs.lean:189`).

**Repair.** This is a Draft vocabulary change, part of the re-freeze:
1. Add `tm.rejectHint = m.rejecthint` to `MsgEvOf`.
2. Re-prove `msgEvOf_traceMsgOf` (`TracedMsg.lean:57`, by `rfl`).
3. Give `msgEvOf_absMsg_from` (`raft__send.lean:212`) the hypothesis
   `m'.RejectHint' = m.RejectHint'`. `send` stamps only `From` and `Term`.
4. Add `sendEvOf_ok`. Its premises: the state's numbers, and the message's `term`, `index`,
   `logterm`, `commit`, `rejecthint` and `entries.length`, each below `traceNumBound`. Its
   `InScope` part follows from `msgTypeStr ty ≠ "MsgSnap"` for every `ty` that `sendEvt` traces.

### B. `raft.maybeCommit.tracedSpec`'s `hΛ` is at the pre-state, and its new `hOk` at the outcome: the statement is false at `b = true` (outside the amendment, which edited it)

**Evidence.**
- Go logs the `Commit` line after the commit: `defer traceCommit(r)` (`raft.go:794`).
- The Draft's `hΛ` (`TracedHooksDraft.lean:116`) gives `Λ'` only of `NodeEvOf rsmCommit id s c`'s
  events, at the pre-state.
- Its post's capability carries `Λ'` of the last logged event (`trCapB`'s `∃ o, simBoot … ∗ ⌜Λ o⌝`,
  `TracedCap.lean:743`). When `b = true`, that event has `commit = N`.
- Counterexample: take `Λ' o := ∀ e, o = some e → e.commit = s.logst.committed`. It meets `hΛ`, but
  it fails at the logged event whenever the commit advances, which is reachable.

The amendment's `hOk` (`:118-120`) is stated at the outcome state, correctly. The two premises of
one statement now disagree, so the inconsistency is in plain view.

The derived `TracedHooks.raft.maybeCommit.traced` (`TracedHooks.lean:449-454`) states both at the
outcome. The Draft statement is not proved (blocked, `:108-113`), so nothing unsound is proved. But
it is the frozen contract a re-freeze would carry.

**Caller affected.** The planned call sites of `maybeCommit` in `raft.Step`'s leader handlers, if
they rely on the Draft statement.

**Repair.** State `hΛ` as `TracedHooks.raft.maybeCommit.traced` does:
`∀ b N, maybeCommitOut c s b N → ∀ e, NodeEvOf rsmCommit id (if b then … else s) c e → Λ' (some e)`.
Do it at this re-freeze, since the statement is being re-frozen anyway.

### C. The unbooted `BecomeFollower` and bootstrap `ApplyConfChange` lines cannot meet `trCapB`'s configuration (pre-existing, outside the amendment)

**Evidence.**
- `trCapB … c …` requires `(elements c.incoming).Perm C ∧ id ∈ C` (`TracedCap.lean:741`).
- `raft.becomeFollower.traced` uses one `c` for the struct (`ownRaftPhysCV c V`, whose tracker is
  `ownTrackerC c`, `InvRaftPhys.lean:1193-1195`), the event and the capability.
- Under `StartNode`, raft's tracker is empty at both unbooted `BecomeFollower`s:
  - `newRaft`'s `r.becomeFollower(r.Term, None)` (`raft.go:487`), after `switchToConfig` restored an
    empty `ConfState` (`:479`);
  - `Bootstrap`'s `becomeFollower(1, None)` (`bootstrap.go:52`), before the `applyConfChange`s
    (`:78-80`).
- So the `b = false` precondition is unsatisfiable there, and the amendment's `OkBoot` conjunct
  (`TracedHooks.lean:419`; `TracedHooksGlobal.lean:1485`) has no real caller.

The amendment's lemmas are ready for the eventual routing: `nodeEvOf_okBoot` and `ccEvOf_okBoot`
take a free `n`.

**Repair.** This belongs to the bootstrap clause's work:
1. Give the bootstrap hooks separate configurations: one for the struct and the event, another
   (`≡ C`) for the capability.
2. Meanwhile, say in `raft.becomeFollower.traced`'s docstring (`TracedHooks.lean:407-409`) that its
   `b = false` branch has no satisfiable caller yet.
