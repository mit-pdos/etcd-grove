### First tier

**F1. The `Ready` line is logged after the Ready is handed to the application, so a receipt can be
logged before its sender's `Ready` line. The specification then cannot receive the message.**
- **Claim.** The design and the harness both claim the opposite: "a message is logged as sent ...
  before the Ready that hands it to the application, so before the network has it, so before its
  receipt is logged" (`concurrent.go:27-30`, `notes/raft-trace-validation.md:35`). The design
  builds on it in `α` ("`pendingMessages` = ... not yet handed out in a Ready") and in its ghost
  ("`inFlight γt m` ... created at the `Ready` line, owned by ... the harness's network").
- **Code.**
  - `node.go:435-436` runs `case readyc <- rd: n.rn.acceptReady(rd)`, and `traceReady` is the last
    statement of `acceptReady` (rawnode.go:437). The application already holds `rd.Messages` when
    the `Ready` line is logged.
  - The application sends them at once (`handleReady`, `concurrent.go`). The network goroutine's
    delay can be 0, and Perennial's `time.Sleep` ignores its delay (`Spec/time/Sleep.lean`).
  - So the receiver's run loop can log `Receive*` while the sender's run goroutine has not yet
    reached `traceReady`.
  - `Trace.receive` looks only in `messages` (`Trace.lean`, `ts.s.messages.domain`). The message
    is still in `pendingMessages`, so no successor exists and `Main` panics.
- **Witness.**
  - Setup: a scratch copy with `time.Sleep(20ms)` inserted between the channel send and
    `acceptReady` in `node.go`. This is a scheduling the unmodified program allows, in Go and in
    Goose's semantics.
  - Command: `go test -tags with_tla -run TestConcurrentTraces` with `TRACE_SEEDS=2`.
  - Result: both seeds fail, "no behavior steps through line 43" (seed 1) and "line 64" (seed 2).
  - `checktrace -explain` on seed 1: line 43 is `ReceiveRequestVoteRequest nid 3` of
    `MsgVote 2→3`, while node 2's vote requests are still pending ("messages 3, pending 3"). Node
    2's `Ready` line comes later.
- **Who it affects.** Layer B's `α` and the `inFlight` tokens: the network holds a message before
  its token can exist. Layer D. The closed theorem as stated is false of the harness.
- **Repair.**
  - Make the harness order it. The simplest fix: in `handleReady`, do one round trip through the
    node's run loop before sending, for example `r.node.Status()`. The run goroutine serves it only
    after `acceptReady` returns. Alternatively, send the Ready's messages after `r.node.Advance()`.
    Either way the harness's `Main` changes: per the plan's "Still the user's", record it and take
    it pending the user's veto.
  - State it as a premise of B (P8: "a traced message is received only after its sender's `Ready`
    line"), discharged by D. Create the `inFlight` tokens at the `Ready` line and give them to the
    application at that round trip. Until then the application holds the messages without tokens,
    and the network must not deliver them.
  - Correct `concurrent.go:27-30` and `notes/raft-trace-validation.md:35`.
  - Upstream's own trace validation has the same ordering hazard: its 1ms sleep in
    `traceReceiveMessage` only makes the race unlikely. Consider a `nonissues/` entry (found by
    code reading, `blocks-proof: no` once the harness orders it).

**F2. A further gap (the sixth): raft refuses a vote that `etcdraft.tla` grants, when the voter
knows its term's leader but has not voted. With 4 or more voters, layer B's statement is false.**
- **Code and specification.**
  - Raft (raft.go:1232-1235): `canVote := r.Vote == m.From || (r.Vote == None && r.lead == None)
    || ...`.
  - `HandleRequestVoteRequest` (`Spec.lean:304`) grants on `votedFor = Nil ∨ votedFor = j` and
    ignores `lead`.
  - A voter that learned the term-`T` leader from a heartbeat or `MsgApp` without voting
    (`becomeFollower(T, from)`, `Vote = None`) refuses a second term-`T` candidate. The
    specification grants and sets `votedFor`.
- **Witness.** A scratch test drives five `RawNode`s through `Sim` from `sim.go`:
  1. Nodes 1 and 2 campaign at term 2.
  2. Nodes 3 and 4 vote for 1, which wins.
  3. Node 5 gets node 1's heartbeat first (term 2, lead 1, no vote).
  4. Node 5 then gets node 2's `MsgVote`.

  Result: "no behavior steps through line 124", where node 2 receives node 5's rejection while the
  specification's bag holds `RVResp{5->2 t2 granted=true}`
  (`/tmp/claude-1000/-workspace-etcd-grove/8e48033c-792a-435a-bae3-16d75b0d1a02/scratchpad/w2/tc/witness_lead_test.go`).
- **Three voters are safe.** If the leader `L` of `T` is known to `F`, `L` won with two votes. A
  second candidate `C` of `T` voted for itself, so `F` voted for `L`, and `Vote` is not reset
  within a term (`reset`, raft.go:803-806). So `F.Vote = L` and both sides reject.
  `DefaultCConfig` is not affected.
- **Who it affects.** Layer B, which the plan says is proved "once, under premises on how the
  application uses raft": its statement over any number of voters is false.
- **Repair.** Add a premise P8': at most three voters, or more weakly, "no voter learns a leader of
  a term it has not voted in". Discharge it in D from `DefaultCConfig.Nodes = 3`. Record the gap in
  `notes/raft-trace-validation.md`'s list as the sixth. Note that a fix to `etcdraft.tla` would add
  `lead` to the specification's state.

**F3. P5's discharge is false under Goose's semantics: the log grows by one entry per election,
elections are unbounded, and a `MaxSizePerMsg` cut to a lagging follower is reachable.**
- **Claim.** "nor cut by `MaxSizePerMsg` (1 MiB against the workload's entries)" counts proposals
  only. Every election appends an empty entry (`becomeLeader` → `appendEntry`, raft.go:980-983).
- **Why elections are unbounded.** Perennial's `time.Sleep` "ignores the delay" and a ticker's
  channel "may yield some time at a receive" (`Spec/time/Sleep.lean`, `Spec/time/NewTicker.lean`).
  During one isolation (or any run of drops, which the model admits), two replicas can hold
  arbitrarily many elections within `n < 2^61` steps.
- **Failing execution.**
  - After roughly 10^5 elections, the empty entries exceed 1 MiB (`entsSize`).
  - The isolated follower comes back. After its probe is rejected, the leader's
    `maybeSendAppend` takes `raftLog.entries(pr.Next, maxMsgSize)` (raft.go:643), and the batch is
    cut.
  - The `MsgApp` carries `Commit: committed` (raft.go:656), which is past its last entry.
    `AppendEntriesIfLogged` validates `mcommitIndex = Min(commitIndex, lastEntry)`, so the trace is
    rejected (gap 5).
- **Who it affects.** The closed theorem: `Main` panics on that execution.
- **Repair.**
  - Set `MaxSizePerMsg: math.MaxUint64` (raft's `noLimit`; 0 would mean one entry per message) in
    `RunConcurrent`'s `raft.Config`.
  - Restate P5 as a configuration premise that layer B can be proved under: `MaxSizePerMsg =
    noLimit` and `MaxInflightMsgs > 1 + the entries a leader appends in one term`. As written, P5
    ("every `MsgApp` raft sends carries ...") is a fact about raft's internals that D cannot
    discharge from the application's side.
  - The second conjunct still needs B to prove the inflight bound (a `Progress` invariant). Name
    it.
  - Alternatively, bound the ticks in the harness. That narrows the workload, which is the user's
    decision.

**F4. `α`'s bags are false: the specification answers every stale request, and raft (with
check-quorum and pre-vote off) answers none.**
- **Specification.** It replies to a request of a lower term:
  - `RejectAppendEntriesRequest` (`Spec.lean:322`, `m.term < currentTerm`) replies to an append
    request.
  - `HandleRequestVoteRequest` replies `voteGranted := false` to a vote request when
    `m.term < currentTerm`.
- **Raft.** In `Step`'s `m.Term < r.Term` branch (raft.go:1165-1203), the reply is only under
  `checkQuorum || preVote` (off by P7). Otherwise raft logs "ignore other cases" (raft.go:1200)
  and sends nothing.
- **Consequences.**
  - The table's last row ("maybe a response (skipped)") is wrong.
  - So is `α`'s "`pendingMessages` = `msgAbs` of ... the outbox's traced messages". Each stale
    request leaves a *phantom* reply in `pendingMessages`, moved to `messages` at the next
    `Ready(i)` and never received.
- **Harmless for matching.** A phantom equals the real rejection with the same fields, if raft ever
  sends one, so `MsgsDet` survives. The `Bag` counts then differ by the phantoms.
- **Repair.** Add a ghost multiset of phantom replies to `simAuth` and define the bags as `msgAbs`
  of the real messages plus the phantoms. State `MsgsDet` over both, and say which receive lines
  can never consume a phantom.

### Second tier

**S1. "`a = α_i(s)`" cannot be literal.**
- `stepLine` deduplicates with `TState.eq`: bags as multisets (`Bag.eq`, order-free), `matchIndex`
  compared on `server` only (`Server.eq`).
- A function `α` of raft's state cannot reproduce the order of the bag's list, which depends on
  the history of sends.
- Repair:
  - State the step on the concrete `σ` the checker computes, kept in `simAuth`.
  - `R` relates each node's state to `σ.s i` up to equality of fields, and the bags by counts.
  - Each action needs a congruence lemma for `Bag.eq`, unless `σ` itself is carried.
- The statement "`stepLine t ⟨α(before),…⟩ = ([⟨α(after),…⟩], {})`" should read "returns a
  single state, the next `σ`".

**S2. An entry point and its lines are missing: the application's `ApplyConfChange` of the
bootstrap entries.**
- **What happens.**
  - Every replica's first Ready carries the three bootstrap configuration entries as committed.
    `handleReady` applies them (`r.node.ApplyConfChange`), and `switchToConfig` logs
    `ApplyConfChange` three times after the node's first `Ready` line.
  - These are not bootstrap lines (`confc` is served by the run loop after `acceptReady`). Lines
    30-32 of the F1 witness trace are such lines.
  - The specification follows them by `ApplySimpleConfChange`, which is a no-op here.
- **At a leader.** `switchToConfig` then calls `maybeCommit` (a `Commit` line) and
  `maybeSendAppend` (`MsgApp` lines) (raft.go:2011-2028). This is reachable in the model: a node
  can tick into a campaign before taking its first Ready, and win before the application applies
  the entries.
- **Repair.**
  - P3 should read "no `ChangeConf`; the bootstrap entries are applied, as `ApplyConfChange`
    lines that change nothing".
  - The list of "hooks inside other calls" should add `ApplyConfChange`. `Tick` at a leader
    (`bcastHeartbeat`) also belongs there: the note's "Tick → campaign" is not all `Tick` does.
  - `traceConfChangeEvent`'s non-nil spec has to work at an opened tracker (`raft__switchToConfig`
    and `newRaft.lean:452`, per the hooks note's survey).

**S3. `CommittedIsDurableInv`: the stated reason is false, and route (b) for it needs a route-(a)
fact.**
- "The leader counts its own match only from its self-response" is false. `becomeLeader`'s `reset`
  sets `Progress[self].Match = lastIndex` (raft.go:820-821), and the specification's
  `BecomeLeader` sets `matchIndex[i][i] := Len(log[i])`.
- The invariant is still true, but proving it inductively needs three facts:
  1. At `BecomeLeader`, `Len(log) ≤ durable.log`: every granted vote, its own included, needs a
     `Ready(i)` after `Timeout`, and a candidate's log does not change.
  2. A follower's `AppendEntriesAlreadyDone` reply carries `mmatchIndex := commitIndex[j]`. Bounding
     that by the leader's `durable.log` needs leader completeness (the follower's committed prefix
     is in the leader's log at its election).
  3. That is one of the invariants assigned to route (a).
- Repair: give the actual strengthening, and either move `CommittedIsDurableInv` to route (a) or
  let route (b) use route (a)'s facts.

**S4. `MoreThanOneLeaderInv` and `ElectionSafetyInv`: the strengthening is not "`MsgsDet` and
`votedFor`".**
- `votedFor` forgets a vote when the term changes, and `MsgsDet` is about matching.
- What is needed is an evidence invariant: every record of `j` granting at term `T` names the same
  candidate. The records are:
  - granted responses in either bag (the bag never forgets them, dropped ones included);
  - `votesGranted` of a server that is candidate or leader at `T`;
  - `votedFor[j]` while `currentTerm[j] = T`.
- `ElectionSafetyInv` also needs "at most one leader of `T` ever", which follows from that, plus
  the pairwise slice consistency of S8.
- This is feasible, but it is the core of a Raft proof at the specification level, not light
  strengthening. Restate the plan with its size.

**S5. Route (a) must cover the intermediate states of a receive line, and some of them are no
state of raft.**
- `stepRound` checks the invariants at every fresh state, including each one-entry truncation
  of `ConflictAppendEntriesRequest`. Raft's `maybeAppend` truncates in one step, so those
  intermediate logs are no state of raft's.
- The suggested route (prove the line's start from raft's pre-state facts, then preserve the
  invariants through each action) needs per-action lemmas:
  - `QuorumLogInv`: the truncated entries are in no server's `Committed`.
  - `MoreUpToDateCorrectInv`: truncating `i` can make another server `j` "at least as up to date"
    as `i`, so it needs `Committed(i) ⊑ log[j]` from raft's facts.
- Neither lemma is in the existing list. Name them in the plan before the freeze.

**S6. `TraceLoggerOk` cannot be "widened in place".** This also bears on target 2.
- Increment 2 makes the contract `isTraceLogger γt tl`: an `IProp`, with a ghost name and the
  simulation's update.
- `⌜TraceLoggerOk tl⌝` (a `Prop` of `tl` alone) occurs in the 13 hook specs, `switchToConfig`,
  `ownRaftPhysG`, `ownRaftPhysReady`, the constructors' premise (Q1: `NewRawNode`, `StartNode`,
  `RestartNode`, `newRaft`, `setupNode`) and the server's `bootOk` (`InvNodeStart.lean:87`).
  Every one of those statements changes shape. The design's own note says as much ("Each hook's
  spec takes the node's `simNode`").
- Repair:
  - Drop the "in place" claim from `InvLogger.lean`'s docstring and the specs' docstrings.
  - Q1 should be put to the user with its final shape (a `γt`-indexed `IProp` premise), not
    the `Prop`.
  - Consider defining `TraceLoggerOk` now as an `IProp` with a `γt` parameter, so that the
    callers' text does not change again.

**S7. At the `BecomeLeader` hook, raft's vote tally is already gone.**
- `becomeLeader` calls `reset` (`trk.ResetVotes()`, raft.go:812) before `traceBecomeLeader`
  (raft.go:978).
- `α`'s "`votesGranted` = ... while a candidate" relates nothing there, while the specification's
  `BecomeLeader` needs `isQuorum(votesGranted)`.
- The hook's spec has to carry the won tally from before the reset (the ghost win table in
  `raftCommitInv`, or a fact `stepCandidate`'s proof hands in). Say so in the handling-phase
  design.

**S8. Restate `AppSlices` pairwise.**
- "A slice of the term-`T` leader's log" refers to a log that `σ` loses once that server is
  truncated in a later term.
- The invariant determinism needs is pairwise: two append requests of term `T` from the same
  source agree where their ranges overlap, and agree with the source's log while it leads `T`.
- That form is inductive on `σ` and survives truncation.
