## First tier

### F1. The compaction gate leaves the harness's `ApplySnapshot` branch unprovable; Q6 lacks the export that closes it

**The claim.** P2 (sim.md:377-381): "a logger-gated conjunct of the generic storage bound `storBnd`"
that "the allocation never hands out". Q6 (6) lists "the compaction permit as a gated conjunct of
the storage bound `storBnd`". The gate paragraph (sim.md:524-532) lists no change to `Ready`.

**The evidence.**
- `handleReady` (`concurrent.go:294-296`) calls `r.storage.ApplySnapshot(rd.Snapshot)` whenever
  `!raft.IsEmptySnap(rd.Snapshot)`.
- `MemoryStorage.ApplySnapshot.spec` needs `J.B (index)` (`MemoryStorage__ApplySnapshot.txt`:
  `memStorAt ms γs J o iprop(J.B … ∗ J.SV sv ∗ J.DL …)`).
- Every client's `J.B` is `storBnd` by definition (`KVStorageInstance.lean:274-275`,
  `KvrStorageApi.lean:275-276`, `KdStorageApi.lean:148-149`: `memBnd (…J γ K) c ⊢ storBnd γ K c`
  by `rfl`). The harness's must be too, since `isStorage` fixes `Bnd := storBnd γ K`
  (`InvNodeRule.lean:613`).
- What `Ready` hands the client for a snapshot is `readySnap`'s `some l` branch
  (`InvApi.lean:2115-2130`): `nodeAppliedLbU γ K idx` etc., with `0 < idx`. From that the client
  builds `storBnd` today.
- With the gate, the client cannot build `storBnd`: the permit is never handed out. The exported
  `Ready`/`isReadyChan` spec still allows `L = some l`, so the harness proof can neither discharge
  `J.B` nor show the branch dead.
- Raft can prove the branch dead with a logger (no `MsgSnap` token is ever created, since the
  sender's `maybeSendSnapshot` is dead, and `Node.Step` with a logger takes a token). But no
  exported spec carries that fact to the client.
- This is round 7's F1 pattern in the other direction: a raft-side fact with no API channel to the
  layer-D proof that needs it.

**Who it affects.** Layer D's proof of `handleReady` (and so `Main`). Q6 as put to the user.

**Repair.** One Q6 line, and the gate paragraph:
- With the trace gate, `Ready`'s snapshot is empty: `readySnap`'s `L = none`, or `rd.Snapshot' = null`
  on `isReadyChan`'s delivery.
- Raft proves it from the gated `storBnd` through the tokens (no `MsgSnap` in `simInv`'s bag).
- Also note in P2 that `CreateSnapshot`/`Compact` in `handleReady` are dead by `DefaultCConfig`'s
  `SnapshotEvery = 0` (`concurrent.go:104-107`, `:333`), a layer-D fact.

## Second tier

### S1. Say where the gate lives: a cluster field, not "a non-nil logger" of node `K`

**The claim.** "gated on a non-nil logger" (sim.md:524), and "a logger-gated conjunct of `storBnd`"
(P2). Q6 adds: "The existing clients (nil logger) carry nothing new."

**The evidence.**
- `storBnd γ K c` (`InvNodeRule.lean:603-604`) is built by clients that compact. The server's
  `EtcdServer__compactRaftLog.lean:119,130` builds it from `nodeAppliedLb`; so do the kv examples.
- A per-node gate ("node `K` has a logger") makes them prove that node `K` is untraced. That needs a
  new witness in `StartNode`'s/`RestartNode`'s post, which contradicts "carry nothing new".
- F1 needs a fact about the *sender's* compaction at the *receiver*. That is a cluster-level fact.
- The cluster record already has this pattern: `RaftNames.dup : Bool := false`,
  `reSnapReg`/`reDec : Option GName := none`, "pure data, fixed at allocation"
  (`Ghost.lean:395-411`).

**Repair.**
- Make the gate a `RaftNames` field `reTrace : Option GName := none`. The trace allocation sets
  `some γt`, alongside its `dup = false` and `|peers| ≤ 3`.
- `storBnd γ K c` gets the conjunct `⌜γ.reTrace = none⌝ ∨ permit`, so existing clients discharge it
  by their allocation's default.
- The other gates (`ProposeConfChange`, `RestartNode`, the P7 calls, `Propose`'s non-empty data) key
  on the same field.
- With a logger, `StartNode` requires `γ.reTrace = some γt`.
- Q6 then says "gated on a traced cluster".

### S2. `CommittedIsDurableInv`: the inherited-commit argument revision 8 wrote is not an argument

**The claim** (sim.md:339-341): "the commit index a leader inherits at its election is within its
durable log by induction on `CommittedIsDurableInv` itself (round 7's T3: an `index ≤ commitIndex`
reply raises no commit index)".

**The evidence.**
- `committedIsDurableInv` constrains only leaders (`Invariants.lean`:
  `state != leader || commitIndex ≤ durable.log`).
- The commit a new leader `l` inherits was learned while `l` was a follower. In raft a follower's
  `committed` can exceed its persisted log: `handleAppendEntries` commits to `lastnewi` in the
  unstable log.
- The invariant at the old leader says nothing about `l`'s `durable`.
- Round 7's T3 concerned a different case: a quorum member's `index ≤ commitIndex` *reply*. Revision
  8 replaced revision 7's inherited-commit sentence with T3's conclusion.
- The true reason is the campaign:
  1. `l`'s `MsgVote`s are handed out at a `Ready` line after `BecomeCandidate`.
  2. A win needs a response to one of them (P8), or `|peers| = 1`.
  3. That line sets `durable := durableOf` (`Spec.lean:150`), which covers `l`'s whole log.
  4. A candidate's commit and log do not move until `BecomeLeader`: a same-term append makes it a
     follower.
  5. So `commitIndex ≤ len(log) = durable.log` at `BecomeLeader`.
  6. With `|peers| = 1`, `campaign` wins before any `Ready`. The commit is then the bootstrap's
     `|peers|`, within `TraceInit`'s durable log.

**Who it affects.** Layer B's proof of `CommittedIsDurableInv`; its author would try the stated
induction and fail.

**Repair.**
- Restore the inherited-commit case with the campaign-`Ready` argument above.
- Keep T3's point separately, for the quorum member's reply: `c_j ≥ n ≥ E_T` was learned from the
  term-`T` leader's own request, handed out at a `Ready` where its commit was durable. That case is
  the induction.

### S3. Two `Match` clauses are false for the leader's own entry between `BecomeLeader` and its self-ack

**The claim.**
- The commit-point row (sim.md:363): "a leader's `Match[j]` is 0, at or past its term's empty
  entry, or at most `j`'s commit index".
- `QuorumLogInv` (sim.md:331-333): "a leader's `matchIndex[l][j]` is 0, or its response is in
  `j`'s set, or at most `j`'s commit index".

**The evidence.**
- `reset` sets `pr.Match = r.raftLog.lastIndex()` for `id == r.id` (`raft.go:817-819`).
- The specification's `BecomeLeader` sets `matchIndex[i][i] := Len(log)` (`Spec.lean:220`).
- Both are `E_T − 1`: neither 0 nor `≥ E_T`, in general above `l`'s commit, and with no response
  of term `T` yet in `l`'s set.
- The self-ack (`appendEntry`'s `MsgAppResp` to self, `raft.go:863`, which `AppendEntriesToSelf`
  puts in the set) comes later in the same call. It is received only at `Advance`.
- As `simInv` clauses they must hold at every state, including the ones between those lines.
- No use is harmed: heartbeats go only to `j ≠ l`, and `AdvanceCommitIndex` commits only `n ≥ E_T`,
  so a self match of `E_T − 1` never counts.

**Repair.** Restrict both clauses to `j ≠ l`. Add the self case: "`matchIndex[l][l]` is
`E_T − 1` (set at `BecomeLeader`), or a self response of term `T` at or past it is in `l`'s set".

### S4. The frontier split: name what carries "`p` above the frontier" across the `recvc` hand-off

**The claim** (sim.md:514-518): "the frontier is split, its authority in `simInv` (frontier `≤`
cursor) and an exclusive fragment in the receiver's `simNode`, so '`p` above the frontier' stays
true from `Node.Step`'s hand-off … to `raft.Step`".

**The evidence.**
- Pinning the frontier makes "`frontier < p`" *stable* once the run loop knows it. But the split as
  stated does not let the run loop *learn* it.
- The deliverer knows `p > f` and, through `simInv`, `frontier ≤ f`. It cannot name the
  fragment's value.
- After the hand-off `stepWithWaitOption` returns `nil` (`node.go:515-517`) and the deliverer gets
  `linkCur … p`. From then on `simInv` gives only `frontier ≤ p`.
- So the strict bound has to cross the channel exchange inside `Node.Step`'s proof. Either:
  1. a `simInv` clause on a per-link hand-off slot: "a token handed to `recvc` at `p` and not yet
     stepped has `frontier < p`". It is established at the exchange, while the deliverer still
     holds `linkCur … f`. It is consumed at `raft.Step`. At most one is pending per link, since the
     run loop steps before its next `select` (`node.go:394-399`).
  2. the frontier advanced at the exchange instead of at the step.

**Who it affects.** `Node.Step`'s new spec, and `raft.Step`'s `MsgVote` receipt hook.

**Repair.** Name the mechanism (option 1 fits the note's existing token states).
