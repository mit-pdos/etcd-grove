## First tier

### A1. P5's inflight half is a workload bound that raft's proof has no way to receive

**Claim** (P5): "by the configuration: `MaxSizePerMsg` unlimited ... and `MaxInflightMsgs` above the entries a leader appends in one term (256 against at most `Proposals` + 1 ...), so no `MsgApp` is throttled or cut."

**Evidence.**
- **"Not throttled" depends on how many proposals the harness makes.** `Proposals: 60` in `DefaultCConfig` (`concurrent.go:105`, the proposer loop at `:195-203`). That is a property of the harness's calls, not of raft's `Config`.
  - Under Goose's semantics elections are unbounded. Only the 60 `Propose` calls bound the entries per term.
  - Throttling is exactly gap 5: `maybeSendAppend` sends an empty `MsgApp` with `Commit = committed` when `pr.Inflights.Full()`.
- **The fact is used inside raft's proof, at every `SendAppendEntriesRequest` line.**
  - The determinism section's item 2 needs it.
  - So does B1's clause: every successful ack index is at or past the leader's empty entry.
  - The simulation is raft's own (`simInv` in raft's package). Raft's `isMessage .app` gives only `m.entries <+: plogFrom bL l (m.index + 1)`, a prefix of the leader's log (`GhostState.lean:196-197`), not "to its end".
- **No channel brings the bound to raft.** The note's increment 2 lists, as node API changes, only:
  - the constructors' premise;
  - the `inFlight` tokens on `Advance`/`Step`.

  The plan's layer D discharges only "never restarts, compacts or proposes a configuration change" (`notes/trace-validation-plan.md:239-241`).
- **The same bound is what B5 needs.** It would bound the log length: boot entries + terms × (proposals + 1).

**Who it affects.**
- S5, for the determinism at every append request.
- Layer D, for discharging P5.
- Raft's node API.

**Repair.** Make the bound something raft's proof holds. Two options:

- **(a) A proposal budget.**
  - A finite pool of credits is allocated with `γt`.
  - `Node.Propose` (and `RawNode.Propose`) takes one credit when the logger is non-nil.
  - A forwarded `MsgProp` carries its credit through `Ready` and `Node.Step`, like the `inFlight` tokens.
  - The leader's invariant gets "entries appended this term ≤ credits spent + 1 < `MaxInflight`".
  - List it with the other node API changes for the user's approval.
- **(b) A raft-level lifetime counter** in the style of `notes/bounds-plan.md`, whose constant the adequacy theorem fixes, as raft's term ceiling `gh.tc` already is (`Defs.lean:1077-1082`).

In either case:
- restate P5 as "a configuration and a proposal budget";
- add a `maybeSendAppend` lemma: with `maxMsgSize = noLimit` and the inflights not full, the entries are the whole suffix from `Next`.

### A2. The bootstrap mode needs preconditions on the node API that the note does not list

**Claim.** "In bootstrap mode the hooks' updates append without stepping ... the harness's transition law flips simInv to simulation mode from the authoritative side and the three witnesses."

**Evidence.**
- **Node 1's run loop exists before the flip.** `StartNode` forks it (`node.go:273`), before node 3's `StartNode` and before the flip.
- **It can log a non-bootstrap line as soon as any channel fires:**
  - a `Tick`: `tickc` is buffered;
  - a `Step`, a `Propose`, or a receive on `Ready()`;
  - an `ApplyConfChange`.
- **That line cannot be handled in bootstrap mode.** The hook's update would "append without stepping", while the specification steps it (`TraceNext`: only `l ∈ BootstrapLogIndices` is `UNCHANGED`). The simulation is then lost.
- **Raft cannot exclude it, and the harness cannot help.** In `Main` it cannot happen: the application goroutines start after the `StartNode` loop (`concurrent.go:177-180`), and nothing else drives the nodes. But:
  - raft's proof (where the hooks' updates are proved) needs "the mode has flipped" before any non-bootstrap line;
  - the harness cannot hand that to the run loop's `simNode`, since the note itself says it cannot touch them.
- **So every node API entry that can make the run loop log needs a persistent "simulation mode" witness in its precondition:** `Tick`, `Step`, `Propose`, the `Ready` channel's receive and `ApplyConfChange`. This is another node API change.

**Repair.** Simpler, and closer to the TLA+:

- Allocate `σ_init` in simulation mode up front, from the peers list.
  - `Bootstrap` is deterministic, so each server's `serverOf` value is known before any line: term 1, follower, vote 0, the `|peers|` config entries of term 1 with `newconf = peers`, commit `|peers|`, `matchIndex` 0.
  - `server` is the peers, with the invariant "only these ids log".
- Give each `simNode` a per-node "bootstrap segment" flag, cleared at the node's first non-bootstrap line.
  - This is exactly `BootstrapLogIndicesForServer`, which is per node (`Traceetcdraft.tla`, `Trace.lean:191-199`): the TLA+ allows node 1's later lines to interleave with node 3's bootstrap.
- What this removes:
  - the global mode, the transition law and the new preconditions;
  - P4's first half ("every node's `StartNode` before any other line"), which the specification does not need;
  - P4's extra premise reduces to the flag.

## Second tier

### B1. The `MoreUpToDateCorrectInv` clause is false at truncation states; a commit-point clause works and answers the LC source

**Claim** (table, row 6): "`σ.s j`'s commit index learned from a leader of a term `≤ lastTerm(σ.s j.log)`", maintained at receive lines from P5. Row 4: "`cmtLb γ ldr t n` with the message that raised `j`'s commit (to check: whether raft's proof hands it to the receiver)".

**Evidence.**
- **The clause fails at a `ConflictAppendEntriesRequest` state with P5 holding.**
  - Witness: `/tmp/claude-1000/-workspace-etcd-grove/8e48033c-792a-435a-bae3-16d75b0d1a02/scratchpad/r4/tc/r4_test.go`, `TestR4TruncationClause`. It uses five voters and unlimited batches.
  - Node 4 learns commit 6 from the leader of term 3 at line 157, getting `e2@6` and `e3@7` with it.
  - At line 196, the leader of term 4 sends `MsgApp` prev 6 (term 2), `[e4@7]`. The specification truncates `e3`, leaving log `[1..6]` with last term 2 < 3.
  - So the clause is false at that state, while the invariant holds.
  - The checker and TLC both accept the trace:

    ```
    cd .../scratchpad/r4/tc; PATH=/usr/local/go/bin:$PATH GOTOOLCHAIN=go1.27.1 GOFLAGS=-mod=mod \
      go test -tags with_tla -count=1 -run TestR4TruncationClause -v .
    ... events 199, verdict ok (at most 1 states per line)
    JSON=.../r4/r4trunc.ndjson java ... tlc2.TLC -config Traceetcdraft.cfg Traceetcdraft.tla ...
    Model checking completed. No error has been found. ... 212 distinct states found
    ```
- **With three voters the clause does hold, but only by an argument the note does not make.** The receiver and the leader then hold the leader's empty entry, which is a majority of two, so no later leader truncates it. The note's other routes do not use three voters.
- **What does hold under P5, at every state, is a commit-point property.** For every server `j`, `j`'s commit index `c` is covered by a commit quorum at a term `t ≤ term(log_j[c])`.
  - It holds at truncation states: entry `c` is never removed.
  - The cases of a received commit:
    - a `MsgApp` carries the leader's `committed` (P5: `min(m.Commit, lastnewi) = m.Commit`);
    - a heartbeat carries `min(Match, committed)`. Under P5, `Match` is 0, or at least the leader's empty entry (then the result is a term-`T` entry committed in `T`), or the receiver's own commit index (the `prev < committed` reply).
  - It implies `MoreUpToDateCorrectInv` with `lc_core`: a log at least as up to date has last term `≥ term(log_j[c]) ≥ t`.
  - It implies the corrected LC: `t ≤ currentTerm[j] ≤ currentTerm[l]`.
- **Raft already has the basis, and it is not `cmtLb`.**
  - `isMessage` of `.app` and `.heartbeat` carries `commitIn γ F m.commit m.term` (`GhostState.lean:199`, `:217`). Its `commitJ` (`Ghost.lean:3248-3252`) is "a `cq γ t n G` with `c ≤ n` and `t ≤ m.term`", or the bootstrap arm.
  - A node's own state is paired with `commitIn γ F S.commit S.term` in raft's restart argument (`Enter.lean:1088`, `:1221`). Whether a live node's invariant holds it persistently I did not verify; this is uncertain.
  - `cmtLb` is not in `isMessage` at all. It appears in `committedJust` (`GhostState.lean:795`).
  - So row 4 (corrected LC) is `commitJ` as it stands, since `t ≤ m.term ≤` the receiver's term.
  - Row 6 needs `commitJ` strengthened by P5 to `t ≤ term(log_j[c])`.

**Repair.**
- Replace rows 4 and 6 by one clause: "`j`'s commit index has a `commitJ` whose quorum term is at most the term of `j`'s entry there". Its sources:
  - raft's `commitIn` on messages and node state;
  - P5, for the strengthening (A1).
- Drop "to check".

### B2. `QuorumLogInv`'s reason at truncation states is false

**Claim.** "a truncation removes only entries past the follower's commit index, which no committed prefix needs".

**Evidence.**
- Entries past `j`'s own commit index can belong to another server's committed prefix. Example:
  - the leader commits 7 with `j` in the quorum;
  - `j`'s commit index is still 5;
  - so `j`'s 6 and 7 are in `Committed(leader)`.
- What keeps them is the table's term row with `lc_core`:
  - only leaders of terms above `j`'s term truncate `j`;
  - they hold every prefix whose commit quorum `j` belongs to;
  - the truncation stops at the first conflict with their log.

**Repair.** State that reason in the truncation bullet, citing the term row.

### B3. `ElectionSafetyInv`'s route-(b) invariant is not inductive as stated

**Claim.** "every append request of term `T` in the bags carries a slice of the log of `T`'s leader".

**Evidence.**
- `electionSafetyInv` bounds the term-`T` entries of *every* server's log (`Invariants.lean:45-50`).
- Term-`T` entries also arrive in append requests of later terms `T' > T`. The leader of `T'` carries them while a stale leader of `T` still leads: no check-quorum, item 7's situation.
- An invariant about term-`T` requests alone does not bound those.

**Repair.** Make the invariant: "while `i` leads `T`, every term-`T` entry in any server's log and in any append request (of any term) is at an index `≤ len(σ.s i.log)`". It holds:
- only `i` creates term-`T` entries;
- `i`'s log only grows while it leads;
- truncation and `ClientRequest` preserve it.

### B4. Raft's API is coupled to the example's transcription again

- `isTraceLogger` (in the constructors' premise, a public spec) quantifies over `e : Event`, "the checker's Event" (`Trace.lean:61`, under `Proof/github_com/mit_pdos/etcd_grove/examples/raft/tracecheck/`).
- simInv and the exported law ("`L` steps ... to a unique state with the invariants") name `State` and `stepLine` too.
- So raft's API module imports an example's proof directory. Round 3's B6 is answered for the tokens only, and the note does not say where the transcription lives.

**Repair.**
- Index the trace by a raft-side record mirroring `TracingEvent` (in `ApiVocab`), and give `ConvertEvents`' spec the pure map to `Event`.
- Move the transcription to a module root raft may import, listed in `etc/api/raft.txt` (or an api file of its own), or say why it stays.
- Either way, the layout check (`etc/api-check.py`) must accept it.

### B5. The `int` conversions need values below `2^63`, which raft's proof does not give

**Evidence.**
- `ConvertEvents` converts with `int(...)`: the term, the log size, the commit, and the message's term, index, commit and log term (`main.go:49-58`).
- The transcription's numbers are `Int` (plan, S2: "the checker's proof (S6) carries the bounds the Go's `int` needs").
- `R` and the hooks' `e = eventOf …` therefore need every such value below `2^63`. Raft's proof bounds:
  - terms by the ceiling `gh.tc < 2^64` (`Defs.lean:1077-1082`, `InvNodeRunHup.lean:63`);
  - the log by `last < 2^61 + 2^63`. `InvRaftlog.lean:21-42` explains that a `< 2^63` bound cannot be carried.
- The plan puts the bound in S6. But the hooks' updates (S5) also need it, and the log's half has no source.

**Repair.** Derive both bounds from A1's budget:
- terms from a term ceiling below `2^62`;
- the log length from boot entries + terms × (proposals + 1).

State them as clauses of simInv.
