   date. Only `TraceSimMatch`, `TracedMsg`, `TracedMsgType`, `raft__send` mention `MsgEvOf`, all up to

2. **A received message's numbers have no source** (r1's F4, open). `trCap_fire_recv` with `recvGate` asks,
   through `sendEvOf_ok`, for the received message's numbers below `traceNumBound`; `simInv`'s bags hold
   `msgAbs` images, which drop `rejectHint` (and a rejected `MsgAppResp`'s index, a heartbeat's unused
   fields); raft's message facts (`Protocol/GhostState.lean:212, 324`) bound `rejecthint ≤ index` only.
   Yet `MainSim.lean:19-22` and `sendEvOf_ok`'s docstring name "raft's message facts or a `simInv` clause
   on the bags". It reaches sends too: a rejected `MsgAppResp` takes `Index` from the received `MsgApp`
   (`raft.go:1841-1846`), so "a sent message's numbers from the state it is built of" is wrong there.
   Repair (no law changes): `Msg.NumsBelow K m`; `sendEvOf_numsBelow`/`sendEvOf_ok` over it (seven
   premises to one); the send line, which proves it, records it as a persistent, trace-mode-gated fact of
   the message, read back by the receiver. Record the decision in the plan and the docstrings before the tag.
3. **The other bootstrap gates are missing** (owed by the bootstrap clause): no lemma parsing
   `InitState`/`ApplyConfChange` as bootstrap names (`nodeEvOf_bf_boot`'s counterpart, which
   `trCap_fire_boot`'s first premise needs); no either-mode `ApplyConfChange` gate with `cC` apart from `c`
   for `switchToConfig` (`b = false` in `Bootstrap`, `b = true` in the application's apply); no intro law

4. **`trCapB`'s docstring is ambiguous** (`TracedCap.lean:832-838`): "raft's configuration once the node's
   bootstrap is over" could mean Go's `Bootstrap` returning or the flag `b`; between them `b = false` with

   the voters'; raft's whenever raft's tracker holds all voters, which `b = true` implies".
5. **Dead code:** `TraceEv.ok_mono`/`okBoot_mono` (`TraceSim.lean:209-215`) are unused now, `ok_mono`'s
