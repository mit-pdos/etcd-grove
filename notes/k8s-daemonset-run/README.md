## The top-level spec

The driver is `examples/k8sdaemonset/dsmain` (`Main(checks)`): the real controller (two workers)
and client-go's real informers over the model API server with every fault flag on, a checker that
lists the pods and panics if two pods controlled by the DaemonSet target one node (S1,
`MaxOnePodPerNode`). The closed theorem (`dsonepod_safe`): for every `checks`, no thread of the
program panics or is stuck (partial correctness: a hang is not excluded).

## Driver gate 1 (green under stress): fails, as recorded by D51

`TestAmbiguousWritesDetected` (`-race`, 200 runs of `Main(2000)`, 2026-11-03): the checker
panicked in **5 of 200 runs** (628 s). The failing runs are the known bug
`issues/k8s-daemonset-ambiguous-create-duplicate-pod.md`: a pod create that commits and returns an
error is never recorded in the consistency store, so a later sync on a stale pod cache creates a
second pod. The plan's fork-fix gate would decide a fix; here the user reserved that decision (D51:
"the controller is left unfixed until the S1 proof genuinely gets stuck here, or the user fixes
it"), and there is no Kubernetes fork to carry a fix. So, per the plan ("an autonomous run does not
prove toward a theorem Go refutes unless the fix lands; without it, the run may still prove the
rest and report the stuck point"): every spec and proof is written for the code as it is, and the
one place S1's proof cannot pass is the ambiguous branch of `syncNodes`' create goroutine, left as
a named `sorry` with the counterexample `ambiguous_create_breaks_S1` beside it.

- R5 (2026-11-03, track B's `queueKeysCanon`): the work queue gets a pure item predicate `Pk`

- R6 (2026-11-04, track A's question): handler registration and `AddIndexers` are specified for
  before `Start` only, by a **per-informer "not started" token** (a fractional ghost variable under
  a new name of `InfNames`: the start lock holds part, kept in step with `started`; `Informer()`
  hands out the callers' part; `AddEventHandlerWithOptions`/`AddIndexers` borrow a fraction;
  `RunWithContext` needs it whole, so the factory's `Start` takes the callers' parts of every
  informer it made). Chosen over a factory-wide token because `isInformer` then names nothing of the
  factory (locality). A thaw of `Start`, `StartWithContext`, `Informer()`; track C threads the
  tokens from the constructor to `factory.Start`. (`AddIndexers` succeeds after the start in Go:
  only a stopped informer refuses; the restriction is the spec's, which the controller meets.)

## The invariant stage (2026-11-04, track B)

Every operation that touches the API state or the consistency store has a proved step of `s1Ok`
(`daemon/S1Steps.lean`, `daemon/S1Writes.lean`, no `sorry`): the bookkeeping (`register`,
`raiseLd`, `ensureReady`, `claim`, `unclaim`, `wrote`, `wroteAt`, `release`), both `Clear`s
(`clear_noop`: `deleteDaemonset` on a gone DaemonSet; `clear_notfound_noop`), every read
(`noop_step`), the admin's node and DaemonSet creates, the controller's revision writes, pod create
(the claimant's), pod delete, DaemonSet status write. **The only operation with no step is the
ambiguous pod create** (`ambiguous_create_breaks_S1`). What the steps forced: `recDs` (a record only
for a stored DaemonSet seen by the DaemonSet informer, so `syncDaemonSet` raises `Ld` before any
`WroteAt`); pods without finalizers (`dsWf`: with finalizers and surge, a deleted terminating pod
plus a new one is two pods on a node, intended behaviour outside `Main`'s scenario, not a bug);
every claim made before the sync's first create. Premises for `Main`: the created DaemonSet's
`dsWf` and a unique revision name; the status write keeps the collision count.

  registration and need `s1Inv`, allocated after the constructor. Track A2.
