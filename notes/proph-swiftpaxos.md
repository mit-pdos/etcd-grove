### The event value: why a string of words
An event carries variable-length, nested lists (a command's value bytes, a pre-accept's dependencies, a
report's entries with their values and dependencies, a sync's replicas). A Go value that holds a list's
*contents* without allocation is a string (a slice or a pointer in the value resolves as its address: the
prediction made at registration could not see the contents). So each event's value is a string: the
event's existing words `sp.encP e` (L2Words.lean), each word as ten one-byte strings
`string(byte(w>>7k&127))`, k = 0..9 (a byte below 128 converts to that one byte: `go.runeString`). The helpers
build it in a local `s` with `s += ...` (one statement per word, unrolled; counted loops for the lists),
then `nodeProph.Resolve(s)`: the resolved value is `#(interface.mkOk go.string #(strW (encP e)))` =: `encE e`.
`encE` is injective on well-formed events by `encP_inj` (the existing prefix-free lemma, with empty rests)
and the fixed width of a word's string. So the prefix-free machinery stays (it is what makes a flat encoding
of nested lists injective); `decodeP` over words can stay too (design (I) below).

### Two prophecies
The rule admits resolving only a prophecy of the package itself (`notes/proph-patch-rule.md`: no calls of
another package's helpers; a resolution's prophecy is the package's own variable or field). The fork had one
node ghost in `client`, which swift reached through `client.GhostStep`. Now `client.nodeProph` serves a
client node's events and `swift.nodeProph` a replica node's (every node initializes both packages; a node
claims the one of its kind).

## Finding: the invariant's mask (the main remaining work)
"The mutex resource becomes an invariant opened around the single resolve" means each site's protocol
update must run *inside* the opened node-prophecy invariant (namespace `client.nodeProphN`), i.e. at
mask `⊤ ∖ ↑client.nodeProphN`, not `⊤`: the update consumes the node's half of `γ.pred` (in the
invariant, with the prophecy), and must happen in the same atomic step as the resolution, or another
goroutine of the node could resolve (and step) in between and the prediction's order would not be the
steps' order. (Running the update before the resolve, or after with the half checked out, fails for that
reason: a second resolver cannot wait.) So:
- client side: `sp.l2_invoke`/`sp.l2_accept` already take a mask `E` with `↑spN ⊆ E`: use
  `E = ⊤ ∖ ↑client.nodeProphN` (no change to L2Laws).
- swift side: `swift.ghostUpd` (GhostSteps.lean) is `∀ W', predPre ... ={⊤}=∗ predPost ... ∗ Q`; it must
  become `={⊤ ∖ ↑client.nodeProphN}=∗`, and the step lemmas its 11 sites use must be generalized from
  `|={⊤}=>` to a mask `E` (with `↑swift.nodeN ⊆ E` and `↑sp.spN ⊆ E ∖ ↑swift.nodeN`, replacing their
  `(⊤ \ ↑swift.nodeN) swift.nodeN_diff` arguments to `sp.upd_*`, which already take `E`):
  `swift.handle_stepDN` (HandleStepN), `swift.newBallot_stepD`, `computeSync_stepD`, `takeSync_stepD`
  (SyncStepD), `swift.commit_dstep`/`commit_dstep'`, `preaccept_dstep` (DescNode), `accept_dstep_pre`,
  `reaccept_dstep`, `recommit_dstep` (AcceptPre), `swift.fill_report` (FillAckN's), and whatever they call
  at `⊤ \ ↑swift.nodeN` (e.g. `swift.nodeX_newBal`). Sites: HandleProposalProof, HandleSyncProof,
  NewLeaderProof, NewLeaderAckNs, AcksHandler, HandleSyncEntry, HandleProposeProof (2), FastAck (2),
  FillAckN.
